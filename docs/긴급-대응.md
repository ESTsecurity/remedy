# 긴급 대응 — 룰만 바뀐 출시를 빨리 내는 길

공개 시연이나 실제 공격이 있는 취약점 · 퍼지는 악성코드에 **룰을 더하거나 고쳐** 빨리 내야 할 때 쓴다. 평소 출시는
rc 를 내려받아 두 OS 의 rc 묶음(A/B · 1.24.0 실측 약 66분)을 **공개 전에** 돌린다. 긴급 경로는 공개 전에 **필수 점검**(새 룰
하네스 · 정식 파일 · 기존 동작 · G9 · 넘길 파일)만 보고, rc 묶음과 콘솔 기준선은 **공개 뒤 24시간 안에** 돌린다.

**목표는 요청을 받은 뒤 2시간 안에 공개하는 것이다**(아래 [시간 목표](#시간-목표--요청-뒤-2시간)). 한 번의 출시로 위협을 다
덮을 수는 없으므로 **1차는 최소 범위로 빨리** 내고, 남은 범위는 **2 · 3차로 같은 출시 줄에서** 넓힌다(아래
[1차 · 2차 · 3차](#1차--2차--3차--넓혀-가는-배포)). AI 작업자에게는 [1차 프롬프트](#1차-프롬프트)를 그대로 준다.

**잰 값** — 1.15.0(Apache CVE-2026-119618): 룰 PR 의 CI 시작 → 공개 **47분 3초**(같은 일을 평소 경로로 낸 1.14.0 은 1시간
50분 36초). 요청 → 공개는 1.17.0(Apache Windows) 2시간 16분 · Java4Shell(CVE-2026-114938) 1차 2시간 40분 · 2차 1시간 47분이다
(1.15.0 은 이 경로를 만드는 일과 함께 온 요청이라 견주지 않는다).

## 쓰는 조건

| | |
|---|---|
| **쓴다** | 바뀐 것이 룰(`plugins/` — 룰 버전 `plugins/RULES-VERSION` 포함) · 하네스 · 문서뿐이다 — `crates/` · `xtask/` 0줄(PR 에서 `git diff --stat origin/main...HEAD -- crates/ xtask/`) · 엔진 버전은 그대로다 |
| **쓰지 않는다** | 엔진을 고쳐야 한다 → 평소 경로(rc 와 A/B 를 공개 전에) |
| **승인** | 건마다 사용자가 정한다 — 요청문에 함께 적을 수 있다(아래 견본). "긴급 · 빨리" 라는 말만으로는 승인이 아니다 |
| **멈춘다** | 필수 점검이 하나라도 실패하면 공개하지 않는다 · 1차 출처(공급사 · 상류 공지 · 배포판 추적기)가 없으면 룰을 짓기 전에 사용자에게 묻는다 |
| **고친 판이 없다** | 영향 판을 *취약*(2)으로 낼지 *확인 필요*(6)로 낼지, 완화 설정을 흔적으로 볼지를 사용자가 정한다(카드) — 고친 판이 나오면 룰을 다시 낸다 |
| **엔진이 모자라다** | 1차는 지금 엔진으로 되는 만큼 룰만으로 이 경로로 내고, 엔진 몫은 다음 차수로 평소 경로에서 낸다([1차 범위](#1차-범위)) |
| **main 이 앞서 있다** | main 에 지금 Latest 뒤의 엔진 변경이 있거나 진행 중인 출시(rc · 정식 태그 · 초안)가 있으면 처음부터 [긴급 가지](#main-이-앞설-때--긴급-가지)로 간다 — 단계 0 전에 가린다 |

**룰이 보이는 시간.** `AGENTS.md` 는 사고 대응 중에 배포보다 룰이 먼저 보이는 것을 막으라고 한다 — 대응 중인 위협의
룰은 공개 저장소 밖에서 짓고 **배포하는 커밋에 함께** 올린다. 긴급 경로도 같다: 룰 · 하네스 · 검사를 로컬에서 다 마친 뒤
PR 을 올리고, 그때부터 공개까지(1.15.0 은 47분)가 룰이 먼저 보이는 시간이다. 이 시간을 줄이는 것이 이 경로의 목적이기도
하다.

## 요청하는 법

AI 작업자에게 이렇게 맡긴다 — 이 문서를 가리키면 단계를 다시 설명하지 않아도 된다.

```text
긴급: <위협 이름 · CVE> — <공지 링크 또는 붙여 넣은 설명>.
요청 받은 시각: <YYYY-MM-DD HH:MM KST>
docs/긴급-대응.md 의 긴급 경로로 1차를 낸다(이 건의 긴급 출시를 승인한다).
```

받은 작업자가 사용자에게 묻는 것은 결정이 필요한 칸뿐이다 — 판정 정책(예: 설정 흔적이 없으면 확인 필요인가),
고친 판을 정하지 못한 배포판의 처리, 대상 OS 의 차례. 사실(영향 판 · 고친 판 · 악용 조건)은 1차 출처에서 직접 잰다.
작업자에게 줄 전체 지시는 [1차 프롬프트](#1차-프롬프트)다.

## 시간 목표 — 요청 뒤 2시간

- **재는 법** — 요청 받은 시각(요청문 · 위협 지원 이슈에 적는다) → GitHub Release 공개(Latest). 근무 시간 밖에 온 요청은
  착수한 시각부터 잰다. 다운로드 페이지 게시는 회사 쪽 일이라 넣지 않고, [사용방법 글](#사용방법-틀--다운로드-페이지)을
  공개와 함께 넘긴다.
- **목표** — 룰만으로 되는 건은 **120분**. 더 빠르게(90분)는 아래 *준비 중* 두 줄이 된 뒤다. 엔진이 모자란 건은 1차를
  룰만으로 120분 안에 내고 엔진 몫은 다음 차수로 낸다(평소 경로 · PR → 공개 목표 3시간).
- **기록** — 건마다 요청 · PR · CI 끝 · 병합 · 태그 · 자산 · 공개 시각을 그 건의 기록에 남긴다(gh 의 실행 · 릴리스 기록으로
  다시 잴 수 있게 실행 번호도). 앞선 건들은 요청 시각을 시 단위로만 적어 다시 재기 어려웠다 — 요청문에 분 단위로 받는다.

| 단계 | 잰 값 | 예산 |
|---|---|---|
| 사실 · 룰 · 하네스 · 커밋 전 검사(PR 전) | 60.8분(Java4Shell 2차) · 100.2분(1차) | 60분 — [1차 범위](#1차-범위)로 줄인다 |
| PR CI(두 OS · 늘 Windows 가 임계) | 17.4 ~ 26.3분 — 엔진 0줄인 PR 에도 Windows `cargo test` 가 17.8분 | 22분 — 룰만 바뀐 PR 의 CI 를 줄이면 약 4분(*추정* · 준비 중) |
| 태그 → 초안 자산 | 13.3 ~ 22.2분(코드서명 전) · 코드서명이 붙은 뒤 v 태그 20.3 ~ 26.2분 | 26분 — 지난 공개본의 서명된 실행 파일을 그대로 쓰면 약 8분(*추정* · 준비 중) |
| 출시 전 필수 점검 | 9 ~ 11분 | 11분 |
| 공개 | 1분 안 | 1분 |
| **합** | 1차 2시간 40분 · 2차 1시간 47분 | **120분 → 준비가 끝나면 약 84분(*추정*)** |

## 1차 · 2차 · 3차 — 넓혀 가는 배포

한 번의 출시로 위협을 다 덮을 수는 없다. **1차는 아래 최소 범위로 2시간 안에** 내고, 이번에 하지 않은 범위는 대기열에 남겨
**2 · 3차로 같은 출시 줄에서** 넓힌다. Java4Shell 이 그렇게 나갔다 — 1차 `rules-2026.11.18` → 2차 `rules-2026.11.18.2` →
3차 `v1.24.0`(엔진 몫 포함), 하루에 세 번.

### 1차 범위

- **취약점 — 핵심만 점검한다.** 1차 출처의 영향 버전 · 고친 버전으로 표준 설치 자리 · 패키지 기록 · 실행 중인 프로세스를
  본다. 그 밖에서 돌거나 서비스로 등록된 것은 *확인 필요*(6)로 알린다. 판단할 근거가 없으면 0 이 아니라 6 이다. 완화
  옵션(설정 · 실행 인자)을 판정에 넣을지는 결정이 필요한 칸이다 — 위 *고친 판이 없다* · *요청하는 법* 의 판정 정책대로
  카드로 묻고, 권장 기본은 *꼭 할 일* 의 안내다(Apache 룰은 HTTP/2 설정을 판정에 넣었다).
- **악성코드 — 중단 · 재감염 방지 · 확산 방지만 한다.**
  - 중단: 악성 프로세스 종료(`process.kill`) · 서비스 정지 · 사용 안 함
  - 재감염 방지: 자동 실행 · 예약 작업 · 서비스 같은 지속 수단 제거(유발자 먼저) · 주 페이로드 격리(되돌릴 수 있다)
  - 확산 방지: 공격자가 바꾼 hosts(두 OS) · 방화벽 허용 규칙 · 프록시 · 백신 예외(Windows)를 되돌린다
  - 엔진에 없는 일 — 네트워크 차단 · 계정 · 자격 증명 재설정 · WMI 등과 리눅스의 폴더째 삭제 · 방화벽 · 프록시 · 백신 예외
    되돌리기(Op 과 OS 는 [`plugin-guide/machine/REFERENCE.md`](plugin-guide/machine/REFERENCE.md) 의 *파괴·변경 동작* 표) — 은
    위협별 안내의 *꼭 할 일* 로 사람에게 넘긴다
  - 지표는 **공개 출처에 있는 것만** 쓴다 — 꾸러미가 룰을 평문으로 담아 배포가 곧 공개다
- **엔진이 모자라면** — 1차는 지금 엔진으로 되는 만큼(점검 · 탐지만이라도 · 모르면 6) 룰만으로 내고, 엔진 몫은 다음 차수로
  평소 경로(rc 와 A/B 를 공개 전에)에서 낸다(룰만으로 넓힐 몫이 먼저면 그 뒤 차수 — Java4Shell 은 3차). 엔진은 고객 기계에서
  끄고 지우는 코드라 공개 전 검증을 줄이지 않는다.
- **이름은 1차에 정한다** — 룰 이름 · id 는 두 OS 몫까지 1차에 정하고 2 · 3차에도 바꾸지 않는다(폐기 목록 · 찾기 · 사용방법
  글이 그 이름을 쓴다). 그 위협의 룰은 2 · 3차에도 **빠른 검사**에 남게 둔다 — 뿌리를 `%FIXED_DISKS%` 로 바꾸면 정밀 검사로만
  간다. 디스크 전체 몫이 필요하면 룰을 따로 더한다.
- **위협별 안내 절을 1차에 만든다** — [위협별 안내](위협별-안내.md)에 그 위협 절(세 줄 · 자세히)과 제목 위의 고정 주소
  `<a id="<위협>"></a>`(빈 줄로 제목과 뗀다), README *위협별 안내* 표에 고정 주소로 잇는 한 줄. 사용방법 글이 그 주소를 가리킨다.

### 2 · 3차

- **같은 출시 줄이다** — 룰만 바뀌면 `rules-<룰 버전>`, 엔진이 바뀌면 `v<엔진 버전>`. 그 위협만 담은 따로 된 꾸러미 · 태그는
  두지 않는다 — 빨라지지 않고(배포에서 룰 몫은 룰당 약 13초) 받는 주소가 달라져 사용방법 글을 고쳐야 한다.
- **차수마다 함께 고친다** — 룰 `version` · 업데이트 내역 칸 · 그 룰의 `RELEASE.md` · [위협별 안내](위협별-안내.md)의 그 위협
  절(대응 기록 줄 · 보는 자리 · 못 보는 것). **사용방법 글은 고치지 않는다.**
- **대기열** — 이번에 하지 않은 범위와 까닭 · 필요한 것(엔진 · 실물 · 공지)을 그 룰 `RELEASE.md` 의 맨 위 버전 절에 *다음 차수
  후보* 로 적는다. 차수를 낼 때만 고친다 — `RELEASE.md` 는 `MANIFEST` 에 들어 고치면 개발 키로 다시 서명해야 하고(아니면
  하네스가 변조로 거절한다) 버전 검사가 룰 변경으로 센다. 이 파일은 배포 파일에 실려 받는 사람이 본다 — 탐지 조건 · 지표는
  적지 않는다.
- **미룬 검증이 겹치면** — 다음 차수도 룰만 바뀐 출시이고 그 미룬 검증이 앞 차수 공개 뒤 24시간 안에 끝날 때만, 뒤 차수의
  미룬 검증을 **앞 차수 바로 앞의 공개본** 대 뒤 차수로 돌려 앞 차수 몫을 함께 잰다. 뒤 차수가 엔진 출시면 앞 차수의 rc
  묶음 A/B(다름도 실패)는 따로 돌린다 — 콘솔 재캡처만 엔진 출시의 재캡처로 합칠 수 있다.
- **차수는 릴리스 이름 · 파일 이름 · 사용방법 글에 넣지 않는다** — 받는 것은 늘 *최신 버전* 이다. 차수는 위협별 안내의 대응
  기록에만 적는다. 언제 다시 받을지는 그 대응 기록과 GitHub 의 *Watch → Custom → Releases* 로 알린다.

## 1차 프롬프트

새 위협이 오면 AI 작업자(Claude Code · Antigravity 등)에게 이것을 채워 그대로 준다.

```text
긴급 1차: <위협 이름 · CVE> — <공지 링크 또는 붙여 넣은 설명>
요청 받은 시각: <YYYY-MM-DD HH:MM KST>
docs/긴급-대응.md 의 긴급 경로로 1차를 낸다(이 건의 긴급 출시를 승인한다).

1. AGENTS.md 와 docs/긴급-대응.md 를 읽고 그 단계(0 사실 → 7 미룬 검증)를 따른다. 단계 0 전에 main 이 지금 Latest 보다
   앞섰는지 가린다("main 이 앞설 때" 절) — 앞섰으면 처음부터 긴급 가지로 간다. 사실은 1차 출처(공급사 · 상류 공지 · 배포판
   보안 추적기)에서 직접 잰다. 지표는 공개 출처에 있는 것만 쓴다.
2. 범위는 "1차 범위" 절대로 줄인다 — 취약점은 핵심 점검, 악성코드는 중단 · 재감염 방지 · 확산 방지. 룰 이름 · id 는
   두 OS 몫까지 정하고 빠른 검사에 남게 짓는다. 엔진을 고쳐야 1차가 되면 멈추고, 룰만으로 줄인 1차를 카드로 묻는다.
3. 결정이 필요한 칸만 카드로 묻는다(권장안을 맨 앞에). 나머지는 묻지 않고 간다.
4. 산출물 셋을 낸다.
   (1) 룰 · 하네스(0 · 2 · 6 — 치료 룰은 치료 → 복원까지) · 위협별 안내의 그 위협 절과 고정 주소 · README 표 한 줄 ·
       긴급 출시(필수 점검 ①~⑤, 치료 룰은 ⑥ · G9 를 빠뜨리지 않는다)
   (2) 다운로드 페이지 글 — "사용방법 틀" 을 채운다. 바뀌는 사실(프로그램 · 룰 버전, 영향 · 고친 버전 표, 보는 자리 · 못
       보는 것, 해시, 메뉴 번호, 흔적)은 쓰지 않는다. 페이지의 사실 칸(대상 버전 · 현상 · 대상 악성코드)은 1차 출처의
       문장과 링크로 따로 낸다
   (3) 2 · 3차 대기열 — 이번에 하지 않은 범위 · 까닭 · 필요한 것
5. 단계마다 시각을 남긴다. 끝에 요청 → 공개 시간 · 단계별 시간 · 산출물 셋을 보고한다.
```

## 사용방법 틀 — 다운로드 페이지

회사 다운로드 페이지에 올리는 글이다. **2 · 3차가 나가도 고치지 않게** 바뀌지 않는 것만 쓴다 — 고정 주소(`releases/latest`) ·
고정 파일 이름 · 실행 순서 · *빠른 검사* · 결과의 종류 · 다시 받는 법. 바뀌는 것 — 프로그램 · 룰 버전, 영향 · 고친 버전 표,
보는 자리 · 못 보는 것, 해시, 메뉴 번호, 흔적 — 은 쓰지 않고 [위협별 안내](위협별-안내.md)의 그 위협 고정 주소로 보낸다.
위협별 안내는 위협 절마다 제목과 따로 고정 주소(`#java4shell` 꼴)를 둔다. 위협 절 제목은 바꾸지 않는다 — 이미 공개한 릴리스
본문과 업데이트 내역이 제목에서 만든 주소로 잇는다. 새 링크는 고정 주소로 적는다.

**어느 출시든**(평소 · 긴급 · 다른 위협) 이 틀이 인용한 화면 낱말(관리자 권한으로 다시 열기 · 빠른 검사 · 찾은 것 모두
치료하기 · 결과 줄)이나 첫 화면의 꼴을 바꾸면, 그 출시에 살아 있는 다운로드 페이지 글 모두의 고침을 함께 넘긴다 —
`releases/latest` 는 모든 위협의 글이 함께 가리킨다. 첫 화면의 꼴은 조건이 붙어 있다: *빠른 검사* 줄은 디스크 전체를 보는
룰(지금은 Log4j)이 다른 룰과 함께 있을 때만 서고, 한 OS 의 룰이 20개를 넘으면 목록이 묶음 · 찾기로 바뀐다.

페이지의 사실 칸(대상 버전 · 현상 · 대상 악성코드)은 사용방법과 떼어 **1차 출처의 문장과 링크**로 적는다 — 공급사가 공지를
고치면 그 칸만 고친다. *'해당하지 않는 버전'* 을 단정하지 않는다 — Java4Shell 은 1차 뒤 Java SE 8 성능 빌드 · GraalVM EE 21.3
(바탕 Java 11 · 8 포함)이 취약으로 더해졌는데, 페이지에 남은 *'Java 8·11은 해당 취약점의 영향 대상이 아닙니다.'* 가 틀린 안내가
됐다.

```text

   https://github.com/ESTsecurity/remedy/releases/latest 에서 운영체제에 맞는 파일 하나를 받습니다.
   - Windows 10 · 11 · Server 2016 이상(64비트): remedy-windows-x64.zip

     [추가 정보] → [실행] 을 누릅니다. 관리자 권한 없이 열리면 첫 화면의 '관리자 권한으로 다시 열기' 를 고릅니다.
   - Linux: tar -xzf remedy-linux-x64.tar.gz && cd remedy-linux-x64 && sudo ./remedy
   설치하지 않습니다. 검사는 아무것도 바꾸지 않고, 치료는 화면에서 따로 승인할 때만 합니다.
3. 점검
   첫 화면의 '빠른 검사'(그 줄이 없으면 '모두 검사만 하기')가 이 취약점을 함께 점검합니다. 이 취약점만 보려면 목록에서
   '<룰 이름>' 을 고릅니다(항목이 많으면 '이름 · 제품 · CVE 로 찾기' 에 <CVE> 를 넣습니다).

   - 취약: 고친 버전으로 올리고(지원이 끝났거나 고친 버전이 아직 없으면 아래 주소의 '꼭 할 일' 에 적은 방법으로 막고)
     그 프로그램(서비스)을 다시 시작합니다.
   - 확인 필요 · 다 보지 못함: 화면의 '확인이 필요한 항목' 과 '주의' 줄이 적은 경로와 까닭을 직접 확인합니다.

   판정 기준 · 보는 자리 · 꼭 할 일: <위협별 안내의 고정 주소>

치료합니다. 지운 파일은 격리해 두어 되돌릴 수 있습니다. 4. 결과(맨 아래 요약으로 읽습니다): 위협 발견(치료 완료 · 치료 안 함) ·
일부 실패(까닭을 풀고 다시 검사 · 치료) · 위협 없음 · 해당 없음(검사할 경로가 이 기계에 없습니다) · 다 보지 못함 — 치료한 뒤 꼭
할 일은 <위협별 안내의 고정 주소> 에 있습니다. 5. 새 버전: 같은 주소에서 다시 받아 다시 검사하십시오. 치료한 옛 폴더는 지우지
마십시오(복원에 필요합니다).*

**예 — Java4Shell(CVE-2026-114938)** 의 칸: `<위협 이름>(<CVE>)` = *Java4Shell(CVE-2026-114938)* · `<룰 이름>` = *Java4Shell 점검
(CVE-2026-114938)*(1 ~ 3차 같은 이름) · `<위협별 안내의 고정 주소>` =

## main 이 앞설 때 — 긴급 가지

버전 검사(`ci/version-check.sh`)는 첫 부모 역사에서 가장 가까운 **정식 태그**(공개 전 초안의 태그도 든다)와 엔진을 견준다.
그래서 main 에 그 태그 뒤의 엔진 변경이 있으면 rules 태그가 멈춘다 — 2026-11-17 21:29(PR #100 병합)부터 v1.23.0 태그를 민
11-18 07:45 까지가 그랬다(공개는 08:06). 반대로 정식 태그를 민 뒤 공개 전에 main 에서 민 rules 태그는 검사를 지나, 공개되지
않은 엔진을 실은 채 지어진다. 둘 다 이 길로 간다.

**먼저 가린다(단계 0 전).** `git fetch origin --tags` 뒤 `L=$(gh release view --json tagName -q .tagName)`(지금 Latest). 다음 가운데
하나라도 맞으면 처음부터 이 길로 간다 — `git diff --quiet "$L" origin/main -- crates Cargo.toml Cargo.lock rust-toolchain.toml
.cargo/config.toml` 가 1(다르다) · `git tag --contains "$L"` 에 L 말고 다른 태그(L 뒤에 민 rc · 정식 태그)가 있다.

1. `git switch -c emergency-<위협> "$L"` — 그 위에서 단계 1 · 2(룰 · 하네스 · 잠금 · 위협 표 · README · 위협별 안내 · 업데이트
   내역 칸 · 룰 버전 · 커밋 전 검사)를 한다. 룰 버전과 고치는 룰의 `version` 은 L 과 main 둘보다 높게 잡는다
   (`git show origin/main:plugins/RULES-VERSION` · `git show origin/main:plugins/versions.lock.json`).
2. 가지를 밀고 **그 머리에서 CI 를 돌린다** — `gh workflow run ci.yml --ref emergency-<위협>`. PR 의 CI 는 main 과 합친 결과를
   시험하고, 충돌이 있으면 돌지도 않는다. 그 실행의 linux · windows 가 초록이고 `bash ci/version-check.sh rules-<룰 버전>` 이
   통과하면 그 머리에 `rules-<룰 버전>` 태그를 단다. 태그를 달기 전에는 main 을 가지에 합치지 않는다(가지 머리에 main 의
   엔진이 들어와 버전 검사에서 멈춘다). 이후는 단계 4 ~ 7 그대로다.
3. 공개 뒤 PR(그 가지 → main)을 열어 충돌(`plugins/RULES-VERSION` · `versions.lock.json` · 위협 표 · README · 위협별 안내 · 업데이트
   내역)을 풀고, CI 가 초록이면 **병합 커밋으로** 병합한다(squash · rebase 금지 — 태그 커밋이 main 역사에 남아야 한다). 병합 뒤
   main 의 `plugins/` 가 긴급 태그와 다르면 main 의 룰 버전이 긴급 출시보다 **높아야** 한다 — 지금 버전 검사는 첫 부모 역사만
   봐서 병합으로 들어온 긴급 태그를 지나친다(보완 준비 중). 사용방법 글은 이 병합 뒤에 넘긴다 — 그 전에는 main 의 위협별
   안내에 그 절 · 고정 주소가 없다.
4. main 에 진행 중인 출시(L 뒤의 rc · 정식 태그나 초안)가 있으면 그 rc 커밋의 정식 태그는 공개하지 않는다 — 3 의 병합 커밋에서
   rc 부터 다시 낸다. 정식 태그를 이미 밀었으면 그 초안과 태그를 지운 뒤 다시 낸다. 그 출시가 Latest 가 되면 긴급 룰이 빠진
   파일로 돌아가기 때문이다 — 공개 직전 검사(단계 6)가 이것을 막는다.

**아직 리허설하지 않은 길이다.** 처음 쓸 때는 2 에서 버전 검사 결과를 먼저 보고 태그를 단다.

바뀐다).

cargo xtask yara --rules plugins/<룰>/rules --rule <YARA 규칙 이름> --scan <정상 파일 폴더> --expect clean
```

`--rules` 는 `.yar` 가 든 `rules/` 폴더다. 정상 설치의 파일을 꺼내는 길: 그 배포판 이미지에 소프트웨어를 깐 컨테이너를
`docker export` 해 `/etc` · `/usr` 를 Windows 에서 보이는 폴더에 푼다 — `bash testbed/harness/linux/g9-corpus.sh <꺼낼 폴더>
<이미지>…`. 리눅스 링크는 Windows 가 열지 못해 *못 훑음* 으로 세어지니 그 수를 스크립트가 적은 링크 수와 대조한다. 점검 룰은 `--expect clean` 이 맞은 것을 '오탐' 으로 적어도, 그것이 그 규칙이
뜻한 파일인지로 판정한다.

```bash
# ①②③ 리눅스(WSL · 저장소 루트) — 랩과 나란히 돌리지 않는다. --harness 는 빠뜨릴 수 없다(리눅스 룰이 아니면 none)
bash testbed/harness/linux/emergency-checks.sh --new <받은 remedy-linux-x64.tar.gz> \
     --prev <지금 Latest 의 remedy-linux-x64.tar.gz> --out <결과 폴더> \
     --harness testbed/harness/linux/<룰>-verify.sh
```

```powershell
# ②③ Windows(호스트 · 저장소 루트) — 내려받은 zip 을 푼 폴더로. 끝에 랩을 되돌린다
.\testbed\harness\host\Invoke-EmergencyChecks.ps1 -Package <푼 폴더>\remedy-windows-x64 -LogDir <결과 폴더>
```

**Windows 룰이면 ① 은 그 룰의 하네스를 같은 푼 폴더로 따로 돌린다** — 위 스크립트는 새 룰의 하네스를 돌리지 않는다(리눅스
쪽은 `--harness none`). 예: `.\testbed\harness\host\Invoke-ApacheVerify.ps1 -Package <푼 폴더>\remedy-windows-x64 -ApacheZip
<zip> -LogDir <결과 폴더>`. 둘 다 랩 VM 을 쓰므로 나란히 돌리지 않는다(이 하네스는 놓은 것을 스스로 치운다).

```bash
# ⑤ 공개 3분 뒤
bash testbed/harness/linux/release-anon-check.sh rules-<룰 버전> <①~④ 에서 잰 파일 폴더> <빈 작업 폴더>
```

두 스크립트는 하나라도 실패하면 종료 1 이다. `summary.txt` 의 줄이 단계마다 통과 · 실패와 그 까닭을 적는다.

③의 화면 차이는 기계가 판정하지 않는다 — `scan-all/*.diff` 가 **새 룰의 메뉴 줄 · 번호 밀림 · 그 룰의 검사 덩어리 ·
요약 한 줄**뿐인지 본다. 1.15.0 은 86줄이 전부 그것이었다.

## 뒤로 미루는 것 — 공개 뒤 24시간 안

| 무엇 | 왜 미룰 수 있나 |
|---|---|
| 두 OS 의 rc 묶음 A/B(지난 공개본 대 공개된 판) | 엔진 코드가 그대로다 — 기존 룰의 판정은 ③ 이 대표 경우로 보고, 묶음이 나머지 경우를 본다 |
| 콘솔 기준선 재캡처 · 화면 문서의 룰 버전 줄 | CI 는 문서와 기준선을 서로 견줄 뿐 실행 파일과 견주지 않는다 — 그 사이 기준선은 지난 판의 화면이다(머리말 첫 줄의 룰 버전) |

rc 묶음은 [`개발-안내.md`](개발-안내.md) "출시 검증" 의 4 와 같은 명령이다 — `--new` · `-Package` 에 **공개한 그
파일**을 준다. 리눅스를 먼저(시료를 받는다), WSL 캐시를 비운 뒤 Windows. 룰만 바꾼 출시이므로 A/B 의 **다름도
실패**다(엔진이 그대로인데 기존 룰의 종료 코드가 바뀌었다는 뜻이다). 콘솔 재캡처는 두 언어를 한 번에 받는
`testbed/harness/host/Invoke-ConsoleRecapture.ps1`(랩 VM) 다음 `testbed/harness/linux/console-recapture.sh`(WSL)로 하고,
`cargo xtask console-diff` 로 견준 뒤 기준선과 화면 문서를 후속 PR 로 올린다.

**미룬 검증이 실패하면** 다음 출시를 멈추고 보고한다. 기본은 고친 판을 새 rules 출시로 **앞으로** 내는 것이다 — 공개한
Release 는 불변이라 그 파일을 바꿀 수 없고, 고친 판은 새 버전이다. 지난 공개본을 다시 Latest 로 두는 것(`gh release edit <지난
공개본의 태그> --latest`)은 기존 항목을 해친 때뿐이다(룰만 바뀐 출시의 A/B 다름이 그 경우다). 되돌리면 다운로드 페이지 글의
`releases/latest` 가 그 위협의 룰이 없는 버전을 준다 — 1차를 되돌렸으면 그 글을 내리도록 회사에 알린다.

## 버전 번호

[`개발-안내.md`](개발-안내.md) "버전 번호" 그대로다 — 긴급 경로라고 다르지 않다. 룰만 바뀐 출시라 **엔진 버전은 그대로
두고 룰 버전만** 올린다(`plugins/RULES-VERSION` — 그날 날짜, 같은 날 둘째면 `.2`). 태그는 `rules-<룰 버전>` 이고, 엔진 코드가
지난 공개본과 다르거나 룰 버전을 올리지 않았으면 배포 워크플로가 태그에서 멈춘다(`ci/version-check.sh`). 실행 파일은 다시
지어지지만 엔진 코드와 버전은 그대로다. 1.15.0 · 1.17.0 은 이 정책 전이라 엔진 버전의 마이너를 올렸다.
