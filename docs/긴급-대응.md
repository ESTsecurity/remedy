# 긴급 대응 — 룰만 바뀐 출시를 빨리 내는 길

공개 시연이나 실제 공격이 있는 취약점 · 퍼지는 악성코드에 **룰을 더하거나 고쳐** 빨리 내야 할 때 쓴다. 평소 출시는
rc 를 내려받아 두 OS 의 rc 묶음(A/B · 1.24.0 실측 약 66분)을 **공개 전에** 돌린다. 긴급 경로는 공개 전에 **필수 점검**(새 룰
하네스 · 정식 파일 · 기존 동작 · G9 · 넘길 파일)만 보고, rc 묶음과 콘솔 기준선은 **공개 뒤 24시간 안에** 돌린다.

**2026-11-21 부터 공개 공지에 근거한 취약점 점검 룰은 이 길이 기본 길이다**(결정 D) — 건마다 내지 않고 **모아 낸다**: 룰 PR 은
자기 룰 폴더 · 하네스 · 업데이트 내역 조각 · 위협별 안내의 그 위협 절(· 그 제품의 찾는 조건 원본 `products/`)만 더해 병합하고, 출시는 `bash ci/batch.sh` 한 명령이 그때의 main 머리를 묶어
태그 → 필수 점검 → 승인 한 번 → 공개 워크플로까지 간다([`개발-안내.md`](개발-안내.md#룰만-바뀐-출시--모아-내기) *모아 내기*).

**목표는 요청을 받은 뒤 2시간 안에 공개하는 것이다**(아래 [시간 목표](#시간-목표--요청-뒤-2시간)). 한 번의 출시로 위협을 다
덮을 수는 없으므로 **1차는 최소 범위로 빨리** 내고, 남은 범위는 **2 · 3차로 같은 출시 줄에서** 넓힌다(아래
[1차 · 2차 · 3차](#1차--2차--3차--넓혀-가는-배포)). AI 작업자에게는 [1차 프롬프트](#1차-프롬프트)를 그대로 준다.

**잰 값** — 1.15.0(Apache CVE-2026-119618): 룰 PR 의 CI 시작 → 공개 **47분 3초**(같은 일을 평소 경로로 낸 1.14.0 은 1시간
50분 36초). 요청 → 공개는 1.17.0(Apache Windows) 2시간 16분 · Java4Shell(CVE-2026-114938) 1차 2시간 40분 · 2차 1시간 47분이다
(1.15.0 은 이 경로를 만드는 일과 함께 온 요청이라 견주지 않는다). 모두 태그마다 엔진을 짓던 길에서 잰 값이다 — 2026-11-21
부터 룰만 바뀐 출시는 엔진을 짓지 않고(지난 공개본의 서명된 실행 파일을 그대로 싣는다 · 코드서명 걸음이 없다) 룰 · 문서 ·
하네스만 바뀐 PR 의 CI 는 가벼운 길로 간다. 새 길로 낸 첫 출시(룰 2026.11.21)의 태그 → 초안 자산 셋은 시험판 4분 1초 · 정식
5분 14초였다(앞 rules 태그 넷은 23.4 ~ 25.8분) — 아래 [시간 목표](#시간-목표--요청-뒤-2시간)의 표.

## 처음 하는 사람 — 한 장

조직 Owner 누구나 이 차례로 건 하나를 공개까지 낸다 — 주인이 없어도, 이 저장소를 처음 봐도(2026-11-22). 사람이 맡는 자리와
그 자리에 답이 없을 때의 기본값은 바로 아래 [사람의 자리](#사람의-자리)다.

1. **이슈** — 그 위협의 지원 이슈를 연다(양식 *위협 지원 요청* — `.github/ISSUE_TEMPLATE/위협-지원-요청.yml` ·
   [고르는 화면](https://github.com/ESTsecurity/remedy/issues/new/choose) · 붙는 라벨은
   [`이슈-처리.md`](이슈-처리.md#1-받는-것) *받는 것*). 이슈를 연 시각이 접수 시각이다 — 다른 길로 받았으면 받은 시각(분)을 첫
   댓글에 적는다. 담당(Assignees)에 짓는 사람과, 그 건을 짓지 않을 Owner 하나(**승인 담당** — 승인 · 결정을
   먼저 맡는다)를 함께 건다. 이슈에는 진행 단계만 적는다(탐지 조건 · 지표는 적지 않는다 — `AGENTS.md`). 시작하기 전에
   `bash ci/batch.sh status` 로 진행 중인 출시 · 멈춤 이슈를 본다(원격에 쓰지 않는다 — git fetch · gh 조회와 `cargo xtask changes`
   다. 새 PC 의 첫 실행은 xtask 를 짓느라 더 걸리고, 짓기가 실패해도 끝 줄이 '(없다)' 로 보인다).
2. **차례** — 한꺼번에 여럿이면 실제 공격(공급사 · CISA KEV · 보안 공지의 '악용 확인') → 공개 시연 · PoC → 그 밖. 같은 급은
   접수 순이고, 모르면 '그 밖' 이다. 시계는 늦게 시작한 건도 접수 시각부터 잰다.
3. **짓기** — AI 작업자에게 [1차 프롬프트](#1차-프롬프트)를 채워 준다(사람이 지어도 같은 단계 — 아래 [단계와 시간](#단계와-시간)).
   결정이 필요한 칸은 승인 담당에게 묻고, 답이 없으면 기본값으로 1차를 낸다. `AGENTS.md` 의 여는 줄 견본이 말하는 *채점
   픽스처* 는 그 룰을 재는 하네스와 그 자리 채우기다(실검체 없음).
4. **PR** — 룰 폴더 · 하네스 · 업데이트 내역 조각 · 위협별 안내의 그 위협 절만 더한다. 두 OS 의 PR CI 가 그 룰의 하네스까지
   러너에서 돈다. PR 을 열 때 승인 담당에게 곧 묶음의 공개 승인이 든다고 알린다 — 기다림이 PR → 공개 60분 상한 안에 들기
   때문이다. 초록이면 머리를 고정해 병합한다 — `gh pr merge <번호> --merge --match-head-commit <PR 머리의 sha>`.
5. **묶어 내기** — `bash ci/batch.sh` 가 태그 → 초안 → 러너의 필수 점검 → 승인 → 공개까지 간다. 작업자가 돌리면 승인 대기
   (종료 3)에서 멈춘다 — 결과를 보고 승인한 Owner 의 말을 받아 `bash ci/batch.sh approve <태그>`. YARA 를 더하거나 고친 룰이면
   G9 기록 파일(`G9_DONE` — 그 묶음의 바뀐 `.yar` 를 모두 담은 한 파일 · 아래 [단계와 시간](#단계와-시간)의 2)이 있는 PC 에서
   돌린다(아래 *출시 전 필수 점검* ④).
6. **알리기** — 지원 이슈에 릴리스 주소와 시각을 남기고 닫는다. 다운로드 페이지 글은 새로 쓰지 않는다 — 고정 글 하나가 위협별
   안내를 가리킨다(아래 [사용방법 틀](#사용방법-틀--다운로드-페이지)).
7. **24시간 안** — 미룬 검증(아래 [뒤로 미루는 것](#뒤로-미루는-것--공개-뒤-24시간-안)).

공개 공지에 근거한 점검 룰은 그 룰의 하네스를 PR 전에 돌리지 않는 것이 기본이다 — 위 4 의 PR CI 가 돌고, PR 전
60분([시간 목표](#시간-목표--요청-뒤-2시간) 표의 첫 줄) 안에 들 때만 미리 돈다. YARA 를 더하거나 고친 룰의 G9 는 그 CI 를
기다리는 동안 돈다(2026-11-25). 악성코드 탐지 · 치료 룰과 아직 공지되지 않은 취약점의 룰은 다르다 — 공개 저장소 밖에서 짓고
하네스 · G9 도 올리기 전에 돌린 뒤 배포하는 커밋에 함께 올린다. 이 길을 쓰는 것은 건마다 승인 담당이 승인한다(`AGENTS.md`).

### 사람의 자리

조직 Owner 누구나 맡는다. **그 건을 짓지 않은 Owner 가 먼저**다 — 지원 이슈의 승인 담당에게 묻고, 30분 안에 답이 없으면
지은 Owner 가 스스로 정하고 그 까닭을 이슈에 남긴다(2026-11-22 — 30분은 2시간 안에서 승인 대기에 줄 수 있는 몫이다. 승인을
청한 때부터 센다). 승인하는 사람은 필수 점검 결과(두 잡의 요약 · 화면 차이)와 그 룰의
[검토 목록](plugin-guide/40-review-checklist.md) 아홉 가지를 본다.

| 자리 | 답이 없을 때 |
|---|---|
| 묶음의 공개 승인(`batch.sh` 의 y · `approve`) | 지은 Owner 가 위의 둘을 보고 승인한다 |
| 악성코드 · 미공지 룰이 이 길을 쓰는 승인(건마다) | 지은 Owner 가 공개 시연 · 실제 공격의 1차 출처를 이슈에 적고 승인한다 |
| 판정 정책 — 상류에 고친 판이 없는 영향 판 · 완화 설정 | 영향 판은 *취약*(2)이다 — 상류에 고친 판이 없어도(지원이 끝난 갈래 · nginx2root 의 1.29.x 갈래 · 백포트하는 배포판의 패키지는 아래 줄). 완화 설정은 판정에 넣지 않고 *꼭 할 일* 로 안내한다 — 결함이 특정 모듈 · 기능에 있어도 판으로 판정하는 룰은 그 모듈을 실었는지 보지 않는다(모듈을 빼는 것이 *꼭 할 일* · 2026-11-23 · 같은 공지를 remedy-net 이 이미 판정하면 그 정책 — 아래 *판정 정책*). 모듈이 따로 된 패키지(RHEL · Fedora 의 `mod_md`)면 판은 그 패키지의 것이고, 그 패키지가 깔리지 않은 기계에는 그 결함의 코드가 없다(0 — 2026-11-23 Apache 모의의 룰과 정답이 같았다). 설정으로만 가르는 룰은 [`24-check-plugins.md`](plugin-guide/24-check-plugins.md) *같은 제품의 룰* 대로 |
| 고친 판을 정하지 못한 배포판 | 상류 기준으로 가른다(2026-11-23). 상류 판 번호를 따르는지는 배포판이 아니라 **패키지(스트림)마다** 그 배포판의 지난 보안 갱신으로 가린다 — 늘 상류의 새 판으로 올렸으면 따른다(Ubuntu 의 postgresql · PGDG 저장소), 같은 상류 판에 개정만 올려 고쳤으면 백포트다(Ubuntu 의 apache2 · RHEL 의 httpd) — 같은 소스 패키지를 그 배포판의 어느 릴리스에서든 한 번이라도 그렇게 고쳤으면 백포트로 본다(2026-11-25 · Debian 의 git 은 bookworm 에서 개정으로 고쳐 왔으므로 trixie 도 백포트 → 공지 전까지 6). 지난 보안 갱신은 이번 CVE 가 아니라 그 패키지의 이력에서 읽는다 — 공급사마다의 자리는 [단계와 시간](#단계와-시간)의 *공급사 추적기*(2026-11-24). 이력을 읽지 못해 가리지 못하면 백포트로 본다(*모르면 6* — 대기열에 *받지 못함 · 본 시각(분)*). 따르는 패키지는 공지가 없어도 상류의 고친 판과 견준다(2 · 0 — `upstream_version` 을 `version_lt` 로 · 청정 코퍼스에 그 판이 깔려 G1 이 막으면 아래 *G1*). 백포트하는 패키지는 그 배포판이 고친 패키지 판을 적은 공지(DSA · USN · RHSA 등)와 견주고, 그 공지가 아직 없으면 *확인 필요*(6)다 — 추적기 · VEX 가 *영향 있음* 만 적었어도, 상류 지원이 끝난 갈래여도 6 이다(고친 패키지가 나온 뒤 다음 차수 전까지 고친 기계를 *취약* 으로 보지 않게). 배포판이 고치지 않는다고 밝힌 판(지원 끝 · won't fix)만 2. 공지가 나오면 다음 차수 |
| 대상 OS 의 차례 · 엔진이 모자랄 때 줄인 1차 | 1차 출처가 영향을 적은 OS 를 모두 1차로 하되, 2시간에 다 닿지 않으면 닿는 OS 부터 낸다. 엔진 몫은 다음 차수(평소 경로) |
| 치료 방식이 갈리는 칸(트로이 판의 서비스 지정 대 프로세스 종료 등) | 1차는 탐지만 낸다 — 치료는 정한 뒤 다음 차수 |
| 1차 출처가 없다 | 짓지 않는다 — 이슈에 `자료 대기`(출처가 나오면 시작) |
| 랩 VM 이 드는 걸음(악성코드 Windows 룰의 올리기 전 하네스) | 랩이 있는 PC 의 Owner 에게 그 걸음을 넘긴다. 30분 안에 없으면 다른 OS 몫이 있을 때 그것만 1차로 내고 Windows 몫은 다음 차수다. Windows 에만 있는 위협이면 이슈에 '랩 대기' 를 적고 기다린다 |
| 미룬 검증 실패 · 60분 상한을 넘은 룰 · 다운로드 고정 글을 고칠 일 | 승인 담당에게 알리고, 멈추는 일은 '모아 내기 멈춤' 이슈로 한다 |

### 새 PC 준비

- **늘 드는 것** — git · Git Bash(Windows) · gh(`gh auth login` — 조직 Owner 계정) · rustup(판은 `rust-toolchain.toml` 이
  1.96.0 으로 받는다). Windows 면 MSVC 빌드 도구(Visual Studio Build Tools 의 *C++ 를 사용한 데스크톱 개발*)도 든다. 첫
  `cargo xtask all` 은 도구를 처음 짓느라 더 걸린다(미측정).
- **이 PC 만의 값** — `.cargo/*.example.yml` 을 복사해 채운다(`AGENTS.md` *운영 정보는 저장소에 두지 않는다*). `host.yml` 의
  `wsl.cargo_home` 에는 Windows 쪽 `CARGO_HOME`(보통 `%USERPROFILE%\.cargo`)을 WSL 에서 본 경로(`/mnt/…`)로 적는다 —
  그 아래 `registry` 를 리눅스 빌드 컨테이너에 붙인다(`musl-dev-build.sh` · 콘솔 재캡처 등). 누출 검사의 로컬 목록
  `.cargo/leaks.yml` 은 [`개발-안내.md`](개발-안내.md#커밋하기-전에) *커밋하기 전에*.
- **리눅스 룰이면** — WSL2(`wsl --install`) 와 docker(Docker Desktop 의 WSL2 백엔드 등)가 든다. 단계 0 의 사실(배포판 이미지에
  깔아 기본 설정 · 판 재기) · YARA 를 더하거나 고친 룰의 G9 코퍼스(아래 *출시 전 필수 점검* ④ — 배포판 이미지를 풀어 정상
  파일을 만든다) · `--local` · 리눅스 콘솔 재캡처가 쓴다. 하네스는 PR CI 가 러너에서 돌아 이 PC 에 없어도 된다 — 악성코드 ·
  미공지 리눅스 룰은 올리기 전에 이 PC 에서 돈다(아래 [단계와 시간](#단계와-시간)의 1 · `musl-dev-build.sh`).
- **Windows 랩 VM** — 미룬 검증의 Windows 몫(rc 묶음 · 콘솔 재캡처)과 악성코드 Windows 룰의 올리기 전 하네스에만 든다. 지금
  한 PC 에만 있다 — 없으면 [사람의 자리](#사람의-자리). 세우는 법은 [하네스 README](../testbed/harness/README.md)이고, 랩을
  돌리는 호스트는 VMware Workstation 과 함께 node.exe(rc 묶음이 랩으로 옮긴다) · python · Docker Desktop 도 쓴다.

| **쓴다** | 룰 PR 이 바꾼 것이 룰(`plugins/`) · 하네스 · 문서 · 업데이트 내역 조각(`docs/changes/`)뿐이다 — `crates/` · `xtask/` 0줄(PR 에서 `git diff --stat origin/main...HEAD -- crates/ xtask/ Cargo.toml Cargo.lock rust-toolchain.toml .cargo/config.toml` — 뒤의 넷은 버전 검사가 엔진으로 세는 자리다 · `ci/version-check.sh` 의 `ENGINE_PATHS`). **공개 공지에 근거한 취약점 점검 룰은 늘 이 길이다**(모아 낸다). 악성코드 탐지 · 치료 룰과 아직 공지되지 않은 취약점의 룰은 공개 시연 · 실제 공격이 있을 때만 쓴다 |
| **쓰지 않는다** | 엔진을 고쳐야 한다 → 평소 경로(rc 와 A/B 를 공개 전에) |
| **승인** | **출시(묶음)마다 사람이 한 번** — `bash ci/batch.sh` 의 y, 또는 작업자가 필수 점검 결과를 카드로 보이고 받은 승인(`bash ci/batch.sh approve <태그>`). 악성코드 · 공지 전 취약점 룰은 이 길을 쓰는 것 자체도 건마다 승인 담당이 정한다 — 요청문에 함께 적을 수 있다(아래 견본). 승인하는 사람과 답이 없을 때는 위 [사람의 자리](#사람의-자리). "긴급 · 빨리" 라는 말만으로는 승인이 아니다 |
| **멈춘다** | 필수 점검이 하나라도 실패하면 공개하지 않는다 · '모아 내기 멈춤' 이슈가 열려 있으면 다음 묶음을 시작하지 않는다(`batch.sh` 가 막고, 공개 확인 j 가 공개 앞에서 다시 본다) · 1차 출처(공급사 · 상류 공지 · 배포판 추적기 — 악성코드는 분석한 곳의 원 보고)가 없으면 룰을 짓기 전에 승인 담당에게 묻는다 · 원 보고 없이 보도만 있어도 묻는다 — 답이 없으면 짓지 않는다(`자료 대기`) |
| **상류에 고친 판이 없다** | [사람의 자리](#사람의-자리)의 기본값대로 낸다 — 영향 판은 2 · 완화는 *꼭 할 일* · 백포트하는 배포판의 패키지는 *고친 판을 정하지 못한 배포판* 줄(2026-11-23). 다르게 하려면(완화 설정을 흔적으로 보기 등) 승인 담당에게 카드로 묻는다. 고친 판이 나오면 룰을 다시 낸다 |
| **엔진이 모자라다** | 1차는 지금 엔진으로 되는 만큼 룰만으로 이 경로로 내고, 엔진 몫은 다음 차수로 평소 경로에서 낸다([1차 범위](#1차-범위)). 싣는 엔진은 지금 Latest 의 것이다 — 그 엔진이 읽지 못하는 룰(높은 `min_core` · 새 술어)은 PR 의 CI 가 막는다 |
| **main 이 앞서 있다** | 그래도 main 에서 낸다 — 룰 출시는 늘 main 머리에 태그하고 지금 Latest 의 엔진을 싣는다(2026-11-21 · 긴급 가지는 은퇴했다 · 아래 [main 이 앞설 때](#main-이-앞설-때)) |

**룰이 보이는 시간.** `AGENTS.md` 는 사고 대응 중에 배포보다 룰이 먼저 보이는 것을 막으라고 한다 — 대응 중인 위협의
룰은 공개 저장소 밖에서 짓고 **배포하는 커밋에 함께** 올린다. **공개 공지에 근거한 취약점 점검 룰은 예외다**(결정 E) — 모아
내므로 PR 을 연 때부터 공개까지 보이고, 그 시간은 **60분**까지다. 공개 워크플로가 룰마다 그 시간(조각을 들인 PR 을 연 때 →
공개)을 재고, 넘은 룰이 있으면 그 출시는 공개하되 '모아 내기 멈춤 — <태그>' 이슈를 열어 까닭을 적을 때까지 다음 묶음을 막는다.
짓기 · 커밋 전 검사는 지금처럼 올리기 전에 끝내고, 가지는 PR 을 열 때 함께 민다(노출의 시작이 PR 을 연 시각이다). 하네스는
PR CI 가 러너에서 돈다(2026-11-22 · 아래 *단계와 시간* 의 1 · 3) — 올리기 전에 docker · 랩 VM 으로 돌지 않아도 되지만, CI 의
하네스가 실패하면 고치는 시간도 60분에 든다.
악성코드 탐지 · 치료 룰과 아직 공지되지 않은 취약점의 룰은 위 규칙 그대로다 — PR 을 연 뒤 병합 · 출시를 미루지 않는다(1.15.0 은
PR → 공개 47분).

## 요청하는 법

AI 작업자에게 이렇게 맡긴다 — 이 문서를 가리키면 단계를 다시 설명하지 않아도 된다.

```text
긴급: <위협 이름 · CVE> — <공지 링크 또는 붙여 넣은 설명>.
요청 받은 시각: <YYYY-MM-DD HH:MM KST> · 지원 이슈 #<번호> · 승인 담당 <GitHub 계정>
docs/긴급-대응.md 의 긴급 경로로 1차를 낸다.
```

악성코드 탐지 · 치료 룰이나 아직 공지되지 않은 취약점이면 셋째 줄 끝에 *(이 건의 긴급 경로를 승인한다 — <승인한 Owner>)* 를
붙인다. 공개 공지에 근거한 취약점 점검 룰은 건마다 승인하지 않는다 — 묶음의 공개 승인 한 번이다.

받은 작업자가 승인 담당에게 묻는 것은 결정이 필요한 칸뿐이다 — 대상 OS 의 차례 · 치료 방식이 갈리는 칸, 그리고 판정 정책
(예: 설정 흔적이 없으면 확인 필요인가)이나 고친 판을 정하지 못한 배포판의 2 · 6 을 [사람의 자리](#사람의-자리)의 기본값
(2026-11-23 에 정했다)과 다르게 하려는 칸. 30분 안에 답이 없으면 그 기본값으로 간다.
사실(영향 판 · 고친 판 · 악용 조건)은 1차 출처에서 직접 잰다. 작업자에게 줄 전체 지시는 [1차 프롬프트](#1차-프롬프트)다.

## 시간 목표 — 요청 뒤 2시간

- **재는 법** — 요청 받은 시각(요청문 · 위협 지원 이슈에 적는다) → GitHub Release 공개(Latest). 근무 시간 밖에 온 요청은
  착수한 시각부터 잰다. 근무 시간 안에 여럿이 겹쳐 늦게 시작한 건은 접수 시각부터 잰다([처음 하는 사람](#처음-하는-사람--한-장)
  의 2). 다운로드 페이지는 고정 글이라 건마다 넘기지 않는다([사용방법 틀](#사용방법-틀--다운로드-페이지)).
- **목표** — 룰만으로 되는 건은 **120분**. 더 빠르게(90분)는 아래 표의 두 줄(PR CI · 태그 → 초안 자산)을 줄인 새 길
  (2026-11-21 부터)의 잰 값으로 정한다 — 첫 출시(룰 2026.11.21)에서 두 줄을 쟀고, 새 룰만 더한 PR 의 CI 는 아직 재지 않았다. 엔진이 모자란 건은 1차를
  룰만으로 120분 안에 내고 엔진 몫은 다음 차수로 낸다(평소 경로 · PR → 공개 목표 3시간).
- **기록** — 건마다 요청 · PR · CI 끝 · 병합 · 태그 · 자산 · 공개 시각을 그 건의 기록(그 위협의 지원 이슈)에 남긴다(gh 의 실행 · 릴리스 기록으로
  다시 잴 수 있게 실행 번호도). 앞선 건들은 요청 시각을 시 단위로만 적어 다시 재기 어려웠다 — 요청문에 분 단위로 받는다.

## 1차 · 2차 · 3차 — 넓혀 가는 배포

한 번의 출시로 위협을 다 덮을 수는 없다. **1차는 아래 최소 범위로 2시간 안에** 내고, 이번에 하지 않은 범위는 대기열에 남겨
**2 · 3차로 같은 출시 줄에서** 넓힌다. Java4Shell 이 그렇게 나갔다 — 1차 `rules-2026.11.18` → 2차 `rules-2026.11.18.2` →
3차 `v1.24.0`(엔진 몫 포함), 하루에 세 번.

### 1차 범위

- **취약점 — 핵심만 점검한다.** 1차 출처의 영향 버전 · 고친 버전으로 아래 자리를 본다.
  - **보는 자리** — 표준 설치 자리 · 패키지 기록 · 실행 중인 프로세스. 표준 설치 자리는 배포판 패키지가 까는 자리 · 상류의
    기본 접두사(Apache `/usr/local/apache2`) · 널리 쓰는 묶음 배포의 기본 자리(XAMPP `/opt/lampp`)다. 같은 제품을 흔히 까는 다른
    이름의 자리(Apache 의 `/usr/local/httpd` · `/opt/apache2` 꼴)도 적어도 버전을 읽는 파일(실행 파일 · `release` 등)은 넣는다 —
    돌지 않는 설치본은 프로세스로 잡히지 않는다. 프로세스 · 서비스(`process` · `service`)는 늘 돌거나 서비스로 뜨는 제품의
    자리 밖을 찾는 길이다 — runc 처럼 다른 프로그램이 불러 잠깐 도는 실행 파일에는 넣지 않고, 자리 밖은 부르는 쪽의
    설정(runc 면 컨테이너 엔진 설정)으로 찾거나 위협별 안내의 *못 보는 것* 에 적는다(2026-11-24). 넣어도 검사하는 순간 떠
    있는 일이 드물어 잡는 것이 거의 없고, `process` 가 있으면 리눅스의 컨테이너 안 실행은 다른 사용자의 프로세스를 못 본
    것만으로 *다 보지 못함*(6)이 된다(`crates/remedy-collect/src/derived.rs` · 아래 *컨테이너 하네스*).
    상류의 기본 접두사가 둘이면(Git — 소스 `Makefile` 은 `$HOME` · `configure` 는 `/usr/local`) 둘 다 넣는다 — Java4Shell 이
    사용자마다 깐 자바를 2차에 더한 것은 위 정의(2026-11-19) 전이라 따라 미루지 않는다. 홈 쪽은 홈 전체가 아니라 아래 자리만
    `%ALLUSERPROFILES%/bin` 꼴로 붙여 적는다(적는 법은 [지정 확장 토큰](plugin-guide/10-manifest.md#지정-확장-토큰) · 보기
    `plugins/java4shell-check-linux/plugin.yaml` · `plugins/node2shell-check-linux/plugin.yaml` · 2026-11-25). 리눅스에서 그
    토큰은 `/home` 바로 아래 폴더(링크 제외)마다와 `/root` 로 펴진다 — 이름순으로 64개까지만 보고, 넘으면 *주의* 줄만 서고
    판정은 6 이 되지 않는다(`MAX_PROFILES` 는 `crates/remedy-platform/src/linux.rs` · `/root` 는 이름순 맨 뒤라 먼저 빠진다).
    `/home` 밖의 홈(`/var/www` 등)은 보지 않는다. 그래서 위협별 안내의 *보는 자리* 에는 '모든 사용자' 가 아니라 '`/home` 아래
    각 사용자와 root' 로 적고, *못 보는 것* 에 `/home` 밖에 홈을 둔 계정과 64개를 넘는 홈을 적는다([Java 절](위협별-안내.md#java4shell)
    꼴). 보기 두 룰의 머리 주석이 적은 '모든 사용자를 본다' 는 이 규칙 전의 글이다 — 따라 쓰지 않고, 그 룰의 다음 차수에
    고친다(2026-11-25).
    `scan_roots` 에는 토큰 뒤에 글롭 뿌리(`%ALLUSERPROFILES%/bin/git*`)도 쓸 수 있고, 폴더 칸의 와일드카드(`/home/*/bin`)는
    lint 가 막는다. `collect_extra` 의 `glob` · `path` 는 토큰을 펴지 않으므로 홈 아래 본문은 `ref` 로 담는다(`ref` 는 8 MiB
    고정 — 이슈 #172).
    접두사 안에서는 설정(`conf` · 묶음 배포의 `etc`) · 실행 파일(`bin`) · 판
    파일(`build/config_vars.mk` 등)만 겨눈다 — 설정 읽기(`text_config`)를 접두사 전체에 걸면 웹 문서(`htdocs`)의 `.env` ·
    `.ini` 같은 줄이 결과 파일에 그대로 담긴다(`crates/remedy-collect/src/config.rs` 의 `TEXT_EXT`). 하네스에 가짜 비밀 칸(웹
    문서의 `.env` · 설정 폴더의 키 파일 자리 — 키 모양이 아닌 표지 문자열로)을 두고 결과 폴더에 그 표지가 0 인지 잰다.
  - **모르면 6** — 위 자리 밖에서 돌거나 서비스로 등록된 것, 판단할 근거가 없는 것은 0 이 아니라 *확인 필요*(6)다. 모듈 ·
    라이브러리 파일이 없다는 것만으로 0 을 내지 않는다(실행 파일에 정적으로 넣은 빌드가 있다).
  - **판정 정책** — 완화 옵션(설정 · 실행 인자)은 판정에 넣지 않고 *꼭 할 일* 로 안내한다([사람의 자리](#사람의-자리)의
    기본값 · 다르게 하려면 위 *요청하는 법* 대로 카드로 묻는다). 같은 공지(CVE)를 remedy-net 이 이미 판정하면(지금 PHP2Shell ·
    Node2Shell · Apache HTTP/2 — `crates/remedy-net/src/scan/rules/`) 그 정책을 따르고 카드에 사실로 적는다. 그 정책은 엔진 코드에
    있어 긴급 경로로 바꾸지 못하므로, 다르게 고르면 두 프로그램이 같은 서버를 다르게 판정한다. 예: Apache HTTP/2 는 본체 룰과
    remedy-net 이 같게, 영향 판에 HTTP/2 를 켠 흔적(모듈 적재 + `Protocols` 의 `h2` · `h2c`)이 다 있을 때만 *취약* 이고 그 밖은
    *확인 필요*(6)다(정책은 `crates/remedy-net/src/scan/rules/apache.rs` 머리 · 흔적의 자리 — 설정 경로 · Debian 의
    `mods-enabled` 를 이름으로 보는 법 — 는 `crates/remedy-net/src/scan/apacheconf.rs` 머리). 이 꼴은 remedy-net 에 맞춘 예외다 —
    같은 제품의 다른 공지는 모듈 · 기능을 켰는지 보지 않고 판으로 판정하며(2026-11-23) *remedy-net(이미지 · 컨테이너 · url
    점검)은 이 CVE 를 보지 않는다* 를 사실로 적는다.
- **악성코드 — 중단 · 재감염 방지 · 확산 방지만 한다.**
  - 중단: 악성 프로세스 종료(`process.kill`) · 서비스 정지 · 사용 안 함. `process.kill` 은 같은 조건에 걸린 대상이 상한
    (기본 8 · `crates/remedy-plan/src/limits.rs` 의 `kill_targets`)을 넘으면 **하나도 끝내지 않고** 그 동작을 멈춘다 — 일꾼을
    여럿 띄우는 서버 프로그램이면 서비스를 멈추는 쪽을 함께 보고, 하네스에 실제 일꾼 수만큼 프로세스를 띄운다(`sleep`
    사본 — 스크립트를 띄우면 `image_path` 가 인터프리터다 · `testbed/harness/linux/new-fixtures.sh` 의 process 절). 메모리
    파일(memfd)에서 도는 꼴은 그 사본을 python3 `os.memfd_create("<이름>")` 의 fd 에 써서 `os.execv("/proc/self/fd/<fd>", …)`
    로 띄운다 — `image_path` 가 `/memfd:<이름> (deleted)` 다(2026-11-25)
  - 재감염 방지: 자동 실행 · 예약 작업 · 서비스 같은 지속 수단 제거(유발자 먼저) · 주 페이로드 격리(되돌릴 수 있다)
  - 정상 프로그램을 덮은 트로이 판(공급사 실행 파일 · 공급사 서비스가 곧 지속 수단) — 격리하면 그 서비스는 다시 뜨지 못한다
    (리눅스는 도는 실행 파일을 옮겨도 그 프로세스가 계속 돈다 — 지금 도는 것을 멈추는 것은 아래 서비스 `ref` 나
    `process.kill` 이다). 정상 판으로 되돌리는 것은 엔진 밖이라 *꼭 할 일*(패키지를 최신 판으로 다시 깐다)로 넘긴다. 공급사 유닛을 서비스 `ref` 로 넣으면 정지 →
    사용 안 함 → 유닛 삭제까지 가고(`crates/remedy-plan/src/derive.rs` 의 `removal_ops`), `process.kill` 만 쓰면 `Restart=` 의
    다시 띄우기와 위 상한을 진다 — 어느 쪽으로 할지는 카드로 묻는다. *꼭 할 일* 에는 *'다시 깐 뒤에는 복원하지 마십시오(복원은
    격리한 파일로 새로 깐 파일을 덮습니다)'* 를 넣고, 공격자가 남긴 사본(백업)을 복구원으로 권하지 않는다
  - 확산 방지: 공격자가 바꾼 hosts(두 OS) · 방화벽 허용 규칙 · 프록시 · 백신 예외(Windows)를 되돌린다
  - 엔진에 없는 일 — 네트워크 차단 · 계정 · 자격 증명 재설정 · WMI 등과 리눅스의 폴더째 삭제 · 방화벽 · 프록시 · 백신 예외
    되돌리기(Op 과 OS 는 [`plugin-guide/machine/REFERENCE.md`](plugin-guide/machine/REFERENCE.md) 의 *파괴·변경 동작* 표) — 은
    위협별 안내의 *꼭 할 일* 로 사람에게 넘긴다
  - 지표는 **공개 출처에 있는 것만** 쓴다 — 꾸러미가 룰을 평문으로 담아 배포가 곧 공개다
  - **흔적만 남은 기계** — *모르면 6*(룰이 내는 *확인 필요*)은 점검 룰(`kind: check`)만 낸다 — 악성코드 룰에

    넣고([`plugin-guide/40-review-checklist.md`](plugin-guide/40-review-checklist.md) 2번 · `31-nonexistent.md` *판정 문법* 의
    `or`), 그 밖은 흔적으로 두어 0 이 나가므로 그 0 이 뜻하는 것을 룰 `RELEASE.md` 의 *이 룰이 보지 않는 것* 과 위협별 안내의
    *못 보는 것* 에 적는다(2026-11-24 · 보기 `plugins/cwpdoor-1-check/RELEASE.md`)
  - **하네스 · YARA** — 감염이 없는 0 칸은 룰이 훑는 자리를 채운 정상 설치로 세우고 YARA 대상 경로식에서 링크를 뺀다(아래
    [단계와 시간](#단계와-시간)의 *단계 0 ~ 2 에서 걸리는 것* — *깨끗한 칸* · *YARA 경로식과 링크*). 사용자 홈을 보면 위 취약점

- **엔진이 모자라면** — 1차는 지금 엔진으로 되는 만큼(점검 · 탐지만이라도 · 모르면 6) 룰만으로 내고, 엔진 몫은 다음 차수로

  끄고 지우는 코드라 공개 전 검증을 줄이지 않는다.
- **이름은 1차에 정한다** — 룰 이름 · id 는 두 OS 몫까지 1차에 정하고 2 · 3차에도 바꾸지 않는다(폐기 목록 · 찾기 · 사용방법
  글이 그 이름을 쓴다 — 이름은 끝에 CVE 를 더하는 것만 된다 · 아래). id 의 OS 꼬리(`-check-linux` · `-check-windows`)는
  두 OS 에 걸친 위협을 OS 마다 다른 룰로 가를 때만 단다 — 1차가 한 OS 만 내도 그 꼴로 짓는다(`nginx2root-check-linux`).
  한 OS 에만 있는 위협(1차 출처가 그 OS 만 적는다)은 꼬리 없이 짓는다(`ebury-check` · `openssh-musl-check`).
  악성코드 룰(`kind` 없이 `<사고>-1-check` · `<사고>-2-clean` — [`24-check-plugins.md`](plugin-guide/24-check-plugins.md)
  *규약* 6)을 OS 마다 가르면 그 끝에 OS 를 단다(`<사고>-1-check-linux` · `<사고>-2-clean-windows` 꼴). 한 OS 로 낸 위협에
  뒤에 다른 OS 가 더해지면 있던 id 는 그대로 두고 새 룰만 그 OS 꼬리로 짓는다(2026-11-24).
  nginx2root 같은 별칭이 없는 공급사 보안 업데이트(여러 CVE 를 판으로만 가르는 것)는 그 업데이트를 낸 해 · 달로 짓는다 —
  id 의 바탕 `<제품>-<YYYY>-<MM>`(`php-2026-11-check-linux`) · 이름 `<제품> <M>월 보안 업데이트 점검 (CVE-… · CVE-…)`.
  CVE 하나로 결함의 자리(기능 · 플랫폼)가 뚜렷하면 그 자리로 짓고(`<제품>-<자리>` — `apache-http2` · `php-session` ·
  `openssh-musl`), 같은 달의 다음 업데이트는 새 id 없이 그 룰의 다음 차수로 맡긴다(이름 끝에 CVE 를 더한다 — 아래 · 2026-11-25).
  룰 이름에는 그 위협의 CVE 를 모두 `CVE-YYYY-NNNNN` 꼴 그대로
  넣는다 — 화면의 찾기는 이름 · 폴더 이름의 글자를 그대로만 맞춘다(`crates/remedy-cli/src/guided.rs` 의 `matching`). CVE 가 많아도
  줄이지 않는다 — '등 N건' 으로 줄이면 빠진 CVE 로는 찾지 못한다(2026-11-23 · 이름이 길어지는 것은 받아들인다). 2 · 3차에 그
  룰에 CVE 를 더하거나 맡기면 이름 끝에 그 CVE 를 더한다(2026-11-23 — 폐기 목록은 id · 버전만 본다 · 콘솔 기준선에 그 줄의
  차이가 나는 것은 의도한 변경이다). PHP 11월 두 룰의 '등 18건' 은 이 규칙 전의 이름이다 — 따라 쓰지 않고, 그 위협의 다음
  차수에 풀어 쓴다. 그 위협의 룰은 2 · 3차에도 **빠른 검사**에 남게
  둔다 — 뿌리를 `%FIXED_DISKS%` 로 바꾸면 정밀 검사로만 간다. 디스크 전체 몫이 필요하면 룰을 따로 더한다.
- **위협별 안내 절을 1차에 만든다** — [위협별 안내](위협별-안내.md)에 그 위협 절(세 줄 · 자세히)과 제목 위의 고정 주소
  `<a id="<위협>"></a>`(빈 줄로 제목과 뗀다)와 그 바로 아래 표지 줄 `<!-- 안내 표: <위협> | <OS> | <링크 글> -->`(README *위협별
  안내* 표는 그 줄에서 하루 한 번 짓는다 — README 는 고치지 않는다). 사용방법 글이 그 주소를 가리킨다.

  가까운 제품의 마지막 절 바로 뒤(Java 는 Log4j 뒤 · nginx 는 Apache 뒤), 없으면 그 종류의 끝(악성코드는 Log4j 절 앞 · 점검
  룰은 `<a id="url-check">` 앞)에 넣고, README *위협별 안내* 표가 이 차례 그대로다. 같은 자리에 절을 넣은 두 PR 은 그
  파일에서 충돌하므로, 뒤에 병합하는 PR 만 main 을 받아 먼저 들어간 절 뒤로 옮긴다.
  그 절의 자세히가 가리키는 룰 `RELEASE.md` 첫 판에는 판정 표 · 고친 판 표와 공지 번호 · 게이트 줄(G1 · G9 · 하네스)을 두고,
  점검 룰(`kind: check`)은 맨 앞에 *0 을 내는 갈래* 표(갈래마다 근거 · 그 갈래를 재는 하네스 칸 — `cargo xtask rule-records` 가
  본다 · 새 룰은 빈틈 없이)를 둔다. 악성코드 룰은 0 이 뜻하는 것을 위 *흔적만 남은 기계* 대로 *이 룰이 보지 않는 것* 에
  적는다(2026-11-25 — 이 표를 두어도 `rule-records` 는 보지 않는다). 위협별 안내 그 절에는 룰 버전(`rules-…`)을 적지 않는다 —
  출시 때 `batch.sh` 가 정해 PR 에서는 모른다(2026-11-23 · 그
  차수를 실은 출시는 릴리스 본문의 조각이 보인다). *대응 기록* 줄은 1차부터 두고 차수 · 날짜(PR 을 연 한국 날짜 — 그 차수 `RELEASE.md` 버전 절 머리도)와 그 차수가
  더한 것만 적는다(보기: `1차 2026-11-23(리눅스 — 배포판 패키지 · 공식 이미지의 버전)`). 첫 줄 · 못 보는 것의 *언제부터* 도
  차수로 적는다(*Windows 는 2차부터 — 아래 대응 기록*). 이미 적힌 차수의 `rules-…` 는 지우지 않는다.
  두 OS 에 걸친 위협을 1차가 한 OS 만 담아 내면 절의 첫 줄(무엇을 보는지)에 *지금은 리눅스를 봅니다 — Windows 는 다음 버전에서
  더합니다(아래 대응 기록)* 꼴로 적고 그 OS 를 더한 차수에 지운다. 제목에는 OS 를 넣지 않는다 — 제목은 바꾸지 않는다.
  표지 줄의 OS 칸도 룰이 있는 OS 만 적고(`Linux`) 그 OS 를 더한 차수에 `Windows · Linux` 로 넓힌다 — README *다루는 위협*
  표가 룰에서 짓는 OS 와 같게(2026-11-25).

- **대기열** — 이번에 하지 않은 범위와 까닭 · 필요한 것(엔진 · 실물 · 공지)을 그 룰 `RELEASE.md` 의 맨 위 버전 절에 *다음 차수
  후보* 로 적는다. 차수를 낼 때만 고친다 — `RELEASE.md` 는 룰 폴더의 파일이라 고치면 버전 검사가 룰 변경으로 센다(그 출시에
  실린다 — 조각 하나를 더한다. `plugin-lock` 은 `plugin.yaml` · `rules/` 만 보므로 룰의 `version` 은 그 둘을 고칠 때 오른다). 이
  파일은 배포 파일에 실려 받는 사람이 본다 — 탐지 조건 · 지표는 적지 않는다.
- **미룬 검증이 겹치면** — 다음 차수도 룰만 바뀐 출시면, 앞 차수의 미룬 검증이 이미 24시간을 넘겼어도 뒤 차수와 합쳐
  **가장 오래된 미검증 공개의 바로 앞 공개본** 대 지금 Latest 로 한 번 돈다 — 그쪽이 앞 차수의 결과도 가장 빨리 낸다(2026-11-23).
  넘긴 차수는 지원 이슈에 '밀림' 으로 적는다. 다름이 나오면 사이 공개본으로 갈라 어느 출시의 것인지 본다. 뒤 차수가 엔진
  출시면 앞 차수의 rc 묶음 A/B(다름도 실패)는 따로 돌린다 — 콘솔 재캡처만 엔진 출시의 재캡처로 합칠 수 있다.
- **차수는 릴리스 이름 · 파일 이름 · 사용방법 글에 넣지 않는다** — 받는 것은 늘 *최신 버전* 이다. 차수는 위협별 안내의 대응
  기록에만 적는다. 언제 다시 받을지는 그 대응 기록과 GitHub 의 *Watch → Custom → Releases* 로 알린다.

## 1차 프롬프트

새 위협이 오면 AI 작업자(Claude Code · Antigravity 등)에게 이것을 채워 그대로 준다.

```text
긴급 1차: <위협 이름 · CVE> — <공지 링크 또는 붙여 넣은 설명>
요청 받은 시각: <YYYY-MM-DD HH:MM KST> · 지원 이슈 #<번호> · 승인 담당 <GitHub 계정>
docs/긴급-대응.md 의 긴급 경로로 1차를 낸다.

1. AGENTS.md 와 docs/긴급-대응.md 를 읽고 그 단계(0 사실 → 7 미룬 검증)를 따른다. 단계 0 전에 `bash ci/batch.sh status`
   로 진행 중인 출시 · 멈춤 이슈를 본다(원격에 쓰지 않는다). 사실은 1차 출처(공급사 · 상류 공지 · 배포판 보안 추적기 — 악성코드는 분석한 곳의
   원 보고)에서 직접 잰다. 지표는 공개 출처에 있는 것만 쓴다.
2. 범위는 "1차 범위" 절대로 줄인다 — 취약점은 핵심 점검, 악성코드는 중단 · 재감염 방지 · 확산 방지. 룰 이름 · id 는
   두 OS 몫까지 정하고 빠른 검사에 남게 짓는다. 새 룰과 새 위협(CVE)을 맡긴 룰은 매니페스트에 `added: "<PR 을 연 한국 날짜>"`
   를 적어 고르는 화면 맨 위(*새로 추가된 항목*)에 올린다(min_core 1.25.0 · `plugin-guide/10-manifest.md`). 대응 기록의
   날짜와 같은 날이다 — 자정을 넘겨 룰 버전이 다음 날이 돼도 고치지 않는다(2026-11-24). 룰 `RELEASE.md` 첫 버전 절
   머리(`## <버전> — 1차 (<날>)`)의 날도 이 날이다 — 적은 날과 PR 을 여는 날이 다르면(짓다가 자정을 넘겼거나 PR 을 늦게
   열면) 열기 전에 룰마다의 `added` · `RELEASE.md` 머리와 그 안에 옮겨 적은 `added` · 대응 기록을 모두 여는 날로
   맞춘다('고치지 않는다' 는 PR 을 연 뒤의 일이다 · 2026-11-25). 룰은 지금 Latest 의 엔진으로 나간다 — 그 엔진이 읽지 못하는 룰은 PR 의 CI 가 막는다. 엔진을 고쳐야 1차가 되면 멈추고, 룰만으로
   줄인 1차를 카드로 묻는다.
3. 결정이 필요한 칸만 승인 담당에게 카드로 묻는다(권장안을 맨 앞에). 30분 안에 답이 없으면 "사람의 자리" 의 기본값으로
   가고 그 까닭을 지원 이슈에 남긴다. 나머지는 묻지 않고 간다.
4. 산출물 셋을 낸다.
   (1) 룰 · 하네스(단계 1 의 0 · 2 · 6 · 치료 룰은 ⑥ 까지 · 머리 줄 셋) · G1(청정 코퍼스) · G9(YARA 를 더하거나 고친 룰 —
       `.yar` 가 정해진 뒤 · 공개 공지에 근거한 점검 룰은 PR CI 를 기다리는 동안, 악성코드 · 미공지 룰은 올리기 전에
       저장소의 `.yar` 로 돌고 잰 `.yar` 의 sha256 을 기록에 남긴다) · 위협별
       안내의 그 위협 절과 고정 주소 · 안내 표 표지 줄 · 업데이트 내역 조각(`docs/changes/`) · 고치는 룰이 remedy-net 기준과
       같은 공지(CVE)를 쓰면 그 기준 데이터 룰(같은 제품의 새 공지면 고치지 않는다) · PR(가지는 PR 을 열 때 민다) · 병합 →
       출시(`bash ci/batch.sh` — 필수 점검 ①~⑤, 치료 룰은 ⑥ · G9 기록은 `G9_DONE=<기록 파일>` 로 준다 · 승인 대기에서 결과를
       카드로 보이고 승인을 받아 `bash ci/batch.sh approve <태그>`)
   (2) 사실 칸 — 위협별 안내 그 절의 대상 버전 · 현상 · 대상 악성코드를 1차 출처의 문장(원문 *"…"* — 한국어가 아니면
       바로 뒤에 풀이)과 링크로 적는다. 다운로드 페이지 글은 새로 쓰지 않는다(고정 글 — "사용방법 틀")
   (3) 2 · 3차 대기열 — 이번에 하지 않은 범위 · 까닭 · 필요한 것
5. 단계마다 시각을 지원 이슈에 남긴다. 끝에 요청 → 공개 시간 · 단계별 시간 · 산출물 셋을 보고한다.
```

## 사용방법 틀 — 다운로드 페이지

회사 다운로드 페이지에는 **고정 글 하나**를 둔다(2026-11-22 — 위협마다 새 글을 쓰지 않는다. 하루 30건이면 하루 30편이
된다). 글은 바뀌지 않는 것만 담는다 — 고정 주소(`releases/latest`) · 고정 파일 이름 · 실행 순서 · *빠른 검사* · 결과의 종류 ·
다시 받는 법. 위협마다 바뀌는 것(위협 이름 · CVE · 항목 이름 · 영향 · 고친 버전 · 보는 자리 · 못 보는 것 · 꼭 할 일)은
[위협별 안내](위협별-안내.md)와 README *다루는 위협* 표로 보낸다. 새 위협은 위협별 안내에 그 절과 표지 줄을 더할 뿐이고,
글은 고치지 않는다. 위협별 안내는 위협 절마다 제목과 따로 고정 주소(`#java4shell` 꼴)를 둔다. 위협 절 제목은 바꾸지
않는다 — 이미 공개한 릴리스 본문과 업데이트 내역이 제목에서 만든 주소로 잇는다. 새 링크는 고정 주소로 적는다.

**글을 고치는 때는 하나다** — 어느 출시든(평소 · 긴급 · 다른 위협) 이 글이 인용한 화면 낱말(관리자 권한으로 다시 열기 ·
빠른 검사 · 모두 검사만 하기 · 이름 · 제품 · CVE 로 찾기 · 찾은 것 모두 치료하기 · 결과 줄)이나 첫 화면의 꼴을 바꾸면, 고친
글을 그 출시와 함께 회사 다운로드 페이지 담당에게 넘긴다. 넘기는 길은 저장소 밖이라 조직 Owner 가 넘긴다(지원 이슈에 '고정 글
고침' 을 적는다). 첫 화면의 꼴은 조건이 붙어 있다: *빠른 검사* 줄은 디스크 전체를 보는 룰(지금은 Log4j)이 다른 룰과 함께
있을 때만 서고, 한 OS 의 룰이 20개를 넘으면 목록이 묶음 · 찾기로 바뀐다. 릴리스 본문의 틀(`.github/release-notes.md`)의
1. 도 같은 화면 낱말과 이 조건(빠른 검사 · 정밀 검사)을 고정 글로 적으므로 함께 고친다.

**사실 칸은 위협별 안내의 그 절에 둔다** — 대상 버전 · 현상 · 대상 악성코드는 사용방법과 떼어 **1차 출처의 문장과 링크**로
적는다. 문장은 원문 그대로 *"…"* 로 적고, 원문이 한국어가 아니면 바로 뒤에 한국어 풀이를 붙인다 — 둘이 어긋나면
원문을 따른다. 풀이만 두면 고친 공지와 글자로 견주지 못하고 원문에 없는 단정이 끼어들 수 있다(2026-11-25 · 인용의 꼴은
[WinWyvern 절](위협별-안내.md#winwyvern) — 원문이 한국어라 풀이는 없다). 공급사가 공지를 고치면 그 칸만 고친다. *'해당하지 않는 버전'* 을 단정하지
않는다 — Java4Shell 은 1차 뒤 Java SE 8
성능 빌드 · GraalVM EE 21.3(바탕 Java 11 · 8 포함)이 취약으로 더해졌다. 그때 다운로드 페이지에 남은 *'Java 8·11은 해당
취약점의 영향 대상이 아닙니다.'* 가 틀린 안내가 됐다. 대상 버전을 상류 번호로 적으면 바로 아래에 *'배포판 패키지는 상류와
다른 번호에서 영향을 받거나 고쳐집니다 — 각 배포판 공지를 보십시오.'* 한 줄과 배포판 공지 링크를 둔다 — 배포판은 새 코드 ·
고친 코드를 옛 번호에 넣는다(백포트). Apache 는 Ubuntu 22.04 의 2.4.52 가 상류 영향 범위(2.4.55 ~ 2.4.70) 아래 번호인데도
영향을 받았다(새 mod_http2 를 넣었다). 두 OS 에 걸친 위협을 1차가 한 OS 만 담으면 절의 첫 줄(*지금은 리눅스를 봅니다* 꼴 —
[1차 범위](#1차-범위))이 알린다 — 고정 글은 두 OS 의 받기 · 실행 줄을 늘 담는다.

```text
remedy 점검 · 치료 도구 사용방법

1. 내려받기
   https://github.com/ESTsecurity/remedy/releases/latest 에서 운영체제에 맞는 파일 하나를 받습니다.
   - Windows 10 · 11 · Server 2016 이상(64비트): remedy-windows-x64.zip
   - Linux x86_64(RHEL 계열 · Debian · Ubuntu · Alpine): remedy-linux-x64.tar.gz
   같은 곳의 SHA256SUMS 로 받은 파일이 배포한 파일인지 확인할 수 있습니다.
2. 실행
   - Windows: 압축을 풀고 remedy.exe 를 실행합니다. 'Windows의 PC 보호' 창이 뜨면 위 주소에서 받은 파일이 맞는지 확인한 뒤
     [추가 정보] → [실행] 을 누릅니다. 관리자 권한 없이 열리면 첫 화면의 '관리자 권한으로 다시 열기' 를 고릅니다.
   - Linux: tar -xzf remedy-linux-x64.tar.gz && cd remedy-linux-x64 && sudo ./remedy
   설치하지 않습니다. 검사는 아무것도 바꾸지 않고, 치료는 화면에서 따로 승인할 때만 합니다.
3. 점검 · 검사
   첫 화면 목록에서 보려는 위협의 항목을 찾습니다 — 목록 대신 묶음이 보이면 '이름 · 제품 · CVE 로 찾기' 에 위협 이름이나
   CVE 번호를 넣습니다. '빠른 검사'(그 줄이 없으면 '모두 검사만 하기')는 목록의 항목을 함께 보고, 한 위협만 보려면 그
   항목을 고릅니다. 악성코드를 찾으면 '찾은 것 모두 치료하기' 로 치료합니다 — 지운 파일은 격리해 두어 되돌릴 수 있습니다.
   찾아도 그 항목이 없으면 받은 버전은 이 운영체제에서 그 위협을 아직 보지 않습니다 — 그때 빠른 검사의 결과는 그 위협의
   결과가 아닙니다. 다루는 위협과 운영체제:
   https://github.com/ESTsecurity/remedy#%EB%8B%A4%EB%A3%A8%EB%8A%94-%EC%9C%84%ED%98%91
4. 결과
   - 취약: 고친 버전으로 올리고(지원이 끝났거나 고친 버전이 아직 없으면 그 위협 안내의 '꼭 할 일' 에 적은 방법으로 막고)
     그 프로그램(서비스)을 다시 시작합니다.
   - 위협 발견: 치료했으면 그 위협 안내의 '꼭 할 일' 을 합니다. 치료한 옛 폴더는 지우지 마십시오(복원에 필요합니다).
   - 확인 필요 · 다 보지 못함 · 일부 실패: 화면의 '확인이 필요한 항목' 과 '주의' 줄이 적은 경로와 까닭을 직접 확인합니다.
   - 해당 없음 · 취약한 곳 없음 · 위협 없음: 점검할 프로그램이 없거나, 이 도구가 보는 범위에서 찾지 못했다는 뜻입니다.
   위협마다의 판정 기준 · 보는 자리 · 꼭 할 일:
   https://github.com/ESTsecurity/remedy/blob/main/docs/%EC%9C%84%ED%98%91%EB%B3%84-%EC%95%88%EB%82%B4.md
5. 새 버전
   새 위협과 넓힌 범위는 같은 주소의 새 버전에 더합니다. 다시 받아 새 폴더에 풀고 다시 점검하십시오. 새 버전 소식은 GitHub
   저장소의 Watch → Custom → Releases 로 받을 수 있습니다.
```

**예 — Java4Shell(CVE-2026-114938)** 의 사실 칸: 위협별 안내의 그 절(고정 주소 `#java4shell`)에 OpenJDK 공지
(<https://openjdk.org/groups/vulnerability/advisories/2026-11-17>)와 Oracle 위험 표
(<https://www.oracle.com/security-alerts/cspunov2026.html>)의 문장과 링크로 적는다. 고정 글은 그대로다. 그 절의 문장은 이
꼴(원문 *"…"* + 풀이 · 2026-11-25) 전에 적은 풀이뿐이다 — 따라 쓰지 않고, 그 위협의 다음 차수에 원문을 더한다.

## main 이 앞설 때

**긴급 가지는 은퇴했다**(2026-11-21). 전에는 버전 검사가 첫 부모 역사에서 가장 가까운 정식 태그와 엔진을 견줘, main 에 그 태그
뒤의 엔진 변경이 있으면 rules 태그가 멈췄다(첫 공개 뒤 시간의 42% — 2026-11-17 21:29 PR #100 병합부터 v1.23.0 을 민 11-18
07:45 까지 등). 그래서 지금 Latest 에서 가지를 내 따로 냈고, 병합으로 들어온 그 긴급 태그를 첫 부모 역사가 건너뛰어 낮은 룰
버전의 태그가 지나는 틈이 있었다. 이제 버전 검사는 **지금 Latest** 와 견주고(Latest 가 그 커밋의 조상인가 · 룰 버전이 더
높은가 · 날짜), 룰만 바뀐 출시는 main 의 엔진이 앞서 있어도 **지금 Latest 의 실행 파일**을 싣는다 — 늘 main 에서 낸다.

남는 경우는 둘이다.

| 경우 | 하는 일 |
|---|---|

  깔았다 · 까닭은 재지 않았다). 인증서 검사를 끄는 우회는 하지 않는다. 공개 공지에 근거한 점검 룰이면 그 배포판의 하네스 칸도
  실제로 까는 꼴로 짓고 PR CI 의 러너에서 재게 둔다(위 3 · 처음 도는 칸이 실패하면 고치는 시간도 60분에 든다). 악성코드 ·
  미공지 룰은 올리기 전에 돌아야 하므로(`AGENTS.md`) 닿는 PC · 망에서 돌린다 — 닿는 곳이 없으면 그 배포판 몫은 다음 차수다(승인
  담당에게 알린다). 이 PC 에서 미리 볼 때는 자리 채우기로 잰다(dpkg · apk 는 패키지 기록의 판 줄 · RPM 은 rpmbuild 로 지은
  rpm). 깔아야 재는 것은 짐작하지 않는다 — RPM epoch(아래)는 epoch 를 적은 1차 출처나 러너의 하네스가 깐 패키지의 `rpm -q` 로
  받고, 받지 못한 줄은 6 으로 두고 대기열에 적는다. G9 코퍼스(아래 ④)도 깐 이미지에서 꺼내므로 닿는 곳에서 짓는다.
- **RPM epoch** — RPM 공지는 판을 epoch 없이 적는다. 그 배포판 이미지에 패키지를 깔아 `rpm -q --qf '%{EPOCHNUM}:%{VERSION}-%{RELEASE}\n'
  <패키지>` 로 epoch 를 재고 `rpm_version_lt` 값에 붙인다. Amazon Linux 의 mod_http2 는 epoch 가 1 이다 — `0:` 으로 적으면 영향 판
  `1:2.4.69` 가 고친 판보다 높게 읽혀 0(거짓 양호)이 된다. 개정으로 RHEL 계열(백포트)을 가르는 정규식은 `.el<N>` 말고 모듈
  빌드의 `+el<N>`(AlmaLinux 는 `_el<N>` — 8 에서 쟀다)도 받고, 공급사가 그 배포판이 아닌 패키지(EPEL 의 `Fedora Project`)는
  릴리스 꼴만으로 백포트로 보지 않는다(2026-11-24).
- **하네스 범위** — 룰의 판 줄마다 2(또는 6)와 0 을 하나씩 둔다 — 특히 백포트(Ubuntu 22.04) · 스트림(RHEL EUS) · epoch 줄. 직접
  빌드는 룰이 읽는 파일만 바꾼 자리 채우기로 끝내지 말고 실물(공식 이미지의 실행 파일 판)과 함께 잰다. Amazon Linux 2023 은
  저장소 판이 이미지 릴리스에 묶여 `dnf --releasever=latest` 로 깔고(2026-11-22 — 예전에 받은 이미지는 고치기 전 판을
  깔았다) 그 깐 그대로를 0 칸으로 둔다. 2 칸은 하나 앞 판을 저장소에서 찾지 않아도 된다 — 룰이 읽는 판만 바꾼다(rpm 기록이면
  rpmbuild 로 지은 그 공급사 꼴 · epoch 의 rpm — `testbed/harness/linux/apache-verify.sh` 의 r08 · r12 · 2026-11-25).
- **깨끗한 칸**(기대 0) — 바탕 이미지 그대로가 아니라 룰이 훑는 자리를 채운 정상 설치(그 룰의 G9 코퍼스에 쓰는 이미지 —
  systemd · cron · dbus 를 깐 배포판 등)로 세워 0 을 잰다 — 바탕 이미지에는 그 자리가 비어 있어 링크 · 정상 파일에 걸리는
  룰(아래 *YARA 경로식과 링크*)도 하네스를 지나고, G1 은 YARA 미평가를 알림으로만 센다(2026-11-25 · 새로 짓는 하네스부터 —
  지금 하네스는 그 룰의 다음 차수에 맞춘다 · 이것을 막는 검사는 아직 없다).
- **YARA 경로식과 링크** — 룰의 YARA 대상 경로식(`path` 정규식 · 글롭)이 패키지가 둔 심볼릭 링크까지 덮으면 엔진은 링크의
  본문을 담지 않아(링크는 해시하지 않는다) 그 YARA 를 평가하지 못하고 *다 보지 못함*(6 — 관측 불완전)이 된다. systemd 를 깐
  깨끗한 기계(`/usr/lib/systemd/` 아래의 링크 · `/etc/systemd/system/` 의 별칭 링크)가 그 꼴이다. 그런 경로식에는
  `{ field: sha256, op: exists }` 를 더해 링크를 뺀다 — 링크에는 `sha256` 이 없다(`crates/remedy-collect/src/lib.rs` · 같은 폴더
  `extra.rs` · 보기 `plugins/ebury-check/plugin.yaml` 은 첫 판부터 이 줄을 둔다 · 2026-11-25 에 이 줄이 없는 룰은 깨끗한
  systemd 기계 셋에서 6 이었고 줄을 더하니 0 이었다).
  이 줄은 해시 상한(32 MiB)을 넘는 파일(`hash_large` 에 이름이 없는 것)과 읽지 못한 파일도 함께 빼므로, 그 파일은 6 이 아니라
  0 으로 지나간다. 룰이 겨누는 파일이 그보다 클 수 있으면 그 이름을 `hash_large` 에 적거나(해시가 서서 이 줄을 지나고, 본문을
  담지 못하면 6 — [`10-manifest.md`](plugin-guide/10-manifest.md)) 룰 `RELEASE.md` 의 *이 룰이 보지 않는 것* 에 적는다.
- **remedy-net 기준** — 고치는 룰이 remedy-net 기준과 같은 공지를 쓰면(지금 `php2shell-check-*` · `node2shell-check-*` ·
  `apache-http2-check-linux` — `xtask/src/netcriteria.rs` 머리가 견주는 칸을 적는다) `plugins/remedy-net-criteria/` 의 그 파일을
  룰과 같은 값으로 맞추고, 그 데이터 룰의 `version` 을 올리고 `RELEASE.md` 에 버전 절을 더한다(조각의 `rules` 에 그 데이터 룰을
  위협 룰과 함께 적는다 — 데이터 룰만 적은 조각은 `fragments` 가 거절한다). 룰에 공급사 · 배포판 줄을 더했으면 기준에도 그 줄을
  더한다. 잠금은 git 바탕(가지를 낸 커밋)과 견주므로 따로 지을 것이 없다. Apache 기준에 지금과 다른 고친
  판을 더하면 `xtask/src/netcriteria.rs` 의 시험 `a_changed_apache_value_is_caught`(서로 다른 고친 판의 수 18 을 박아 둠 —
  `same_as` 는 일부러 틀린 값을 넣어 잡는지만 보므로 룰 `version` 을 올려도 깨지지 않는다)가 깨진다. `cargo xtask all` 은 그
  시험을 돌리지 않는다 — 커밋 전 검사의 `cargo test --workspace` 나 PR CI 에서 드러난다. 고치려면 `xtask/` 를 바꿔야 하는데
  긴급 경로는 `xtask/` 0줄이 조건이다(위 *쓰는 조건* — 엔진 변경은 아니다). 1차는 그 공급사를 6 으로 두고 대기열(평소 경로)에
  넣는다.
- **검사가 막는 것과 못 막는 것** — `same_as` 와 기준에 이미 있는 값이 룰과 어긋나면 `net-criteria` 가, `version` 을 빠뜨리면
  `plugin-lock` 이 막는다(둘 다 `cargo xtask all` · PR 의 CI). 룰에 새로 더한 줄이 기준에서 빠진 것은 다 막지 못한다 —
  `url.json` 은 기준의 줄이 룰에 있는지만, `apache.json` 은 고친 판의 모음과 기준 쪽 공급사만 본다(RHEL · Rocky 처럼 고친
  판이 같은 공급사 줄은 빠뜨려도 지나간다). 같은
  제품이라도 다른 공지의 룰이면 기준을 고치지 않는다(이 검사가 보지 않고, remedy-net 몫은 엔진 일이라 다음 차수 · 평소 경로).
- **기준을 고치면 remedy-net 판정도 바뀐다** — PR 전에 remedy-net 개발 빌드(`musl-dev-build.sh <폴더> --net`)로 잰다.
  - 개발 빌드가 읽을 기준은 그 자리에서 일회용 키로 서명한다 — `bash ci/dev-sign.sh --out target/dev-sign
    plugins/remedy-net-criteria` 가 사본(`target/dev-sign/remedy-net-criteria`)과 앵커(`target/dev-sign/anchor.txt`)를 낸다(저장소의
    룰 폴더에는 서명이 없다 · 2026-11-21).
  - Apache(`apache.json`) — [`개발-안내.md`](개발-안내.md#출시-검증) *출시 검증* 의 `net-apache-verify.sh`(약 6분 · 위 사본과
    `--anchor "$(cat target/dev-sign/anchor.txt)"`). 판정이 바뀐 칸의 기대값을 함께 고친다 — 이미지 칸은 `net-apache-cases.txt`,
    컨테이너 칸은 `net-apache-dind.sh`, url 칸은 `net-apache-verify.sh` 의 `url_case` 줄.
  - PHP · Node(`url.json` · `baseline.json`) — PR 전 판정 하네스가 없다. 서명은 그 개발 빌드를 `REMEDY_LANG=ko
    REMEDY_NET_CRITERIA=target/dev-sign/remedy-net-criteria REMEDY_NET_ANCHOR="$(cat target/dev-sign/anchor.txt)"
    <폴더>/remedy-net url --help` 로 불러 `기준(PHP):` 줄이 서는지로 본다(서명이 맞지 않으면 *이 자리에서 확인하지 못했다*).
    판정의 차이는 미룬 rc 묶음의 `net-ab` 가 잰다.
  - 미룬 rc 묶음의 `net-ab` 에서 그 값이 바꾼 경우의 차이는 의도한 변경이다(업데이트 내역 조각에 적는다). `net-apache` 는 기대값
    표로 판정하므로 PR 에서 표를 고쳤으면 통과해야 한다 — 실패는 실패다.
- **서명** — 룰 PR 은 서명하지 않는다(2026-11-21 부터 저장소의 룰 폴더에는 `MANIFEST` · `MANIFEST.minisig` 가 없다 — 되살리면
  `fragments` 가 막는다). 배포 꾸러미는 배포 잡이 배포 키로 서명하고, 개발 빌드가 서명을 읽는 자리는 위 일회용 키 하나다
  ([`개발-안내.md`](개발-안내.md#서명) *서명*).
- **컨테이너 하네스** — 서비스를 띄워 프로세스를 재는 칸은 `--cap-add SYS_PTRACE` 로 띄운다. 컨테이너의 root 는 그 권한이 없어
  다른 사용자(`www-data` 등)로 도는 일꾼의 `/proc/<pid>/maps` 를 못 읽고, 그것만으로 *다 보지 못함*(6)이 된다. 근거(경로 · 소켓
  이름)는 화면이 아니라 결과 폴더(`--out-dir`)의 결과 파일에서 찾는다 — 치료 룰의 드라이런 화면은 계획만 적는다
  (`testbed/harness/linux/ebury-verify.sh` 꼴).
- **G1(청정 코퍼스)** — `cargo xtask g1` 이 저장소의 룰 전부(데이터 · 원격 점검 룰 빼고)를 `corpus/clean` 의 그 OS 스냅샷에 모두
  대어 판정 · 파괴 동작 0 을 본다(2026-11-22 · PR CI 의 리눅스 잡 걸음 — 룰을 더하면 저절로 든다). 전에는 G1 시험
  (`crates/remedy-core/tests/corpus.rs`)의 손으로 적는 목록 밖 룰을 `remedy evaluate` 손 루프로 돌았다. 관측 모자람(6)은
  실패가 아니라 알림이다 — 스냅샷에 YARA 가 볼 본문이 없는 자리(코퍼스의 한계)와 룰이 선언한 확인 필요가 거기 든다. 그 룰의
  `RELEASE.md` 게이트 줄에는 그 걸음의 결과(판정 0 · 파괴 동작 0 · 알림 수)를 적는다. 청정 스냅샷에 실제 영향 판이 깔려 있어
  점검 룰의 2 가 거기서 서면(2026-11-23 — Ubuntu 24.04 스냅샷의 `postgresql-16` · `postgresql-client-16` 16.15) G1 이 막는다 —
  G1 이 판정을 낸 그 판 · 그 패키지의 줄만 6 으로 좁히고(같은 룰의 다른 판 줄은 2 · 0 그대로) 그 룰의 `RELEASE.md` G1 줄에
  스냅샷 · 판을 적고 다음 차수 후보로 남긴다(맞게 양성인 점검을 G1 이 받는 길은 아직 없다 — `xtask/` · `corpus/` 를 고치는
  평소 PR 의 일이다).

- **worktree 에서 일하면** — [`개발-안내.md`](개발-안내.md#커밋하기-전에) *커밋하기 전에* 의 worktree 단락(커밋하지 않는
  `.cargo/*.yml` · xtask 를 그 자리에서 짓기 · leaks 머리줄).

## 출시 전 필수 점검

**내려받은 초안 그 파일로 잰다** — 공개하는 것이 그 파일이다. 받은 뒤에는 배포 워크플로를 다시 돌리지 않는다(자산이
바뀐다). ④ 는 YARA 가 지금 Latest 와 달라진 룰이 있을 때 G9 기록(`G9_DONE=<기록 파일>`)을 요구하고 그 기록에 적힌 sha256 에
초안 꾸러미의 그 `.yar` 가 있는지 견준다 — G9 를 잰 사람은 잰 `.yar` 의 `sha256sum` 줄을 기록에 남긴다. 승인 뒤 공개 워크플로가
⑤ 를 본다 — 공개 전에는 초안의 자산이 점검한 그 파일의 digest 와 같은지, 공개 180초 뒤에는 익명으로 받은 바이트가 같은지.

**①②③ 은 GitHub 호스팅 러너가 돈다**(2026-11-22 · 목표 기준 4 — 어느 PC 에서나 명령 하나와 승인 하나로 나간다).
`bash ci/batch.sh` 가 초안의 자산 셋을 받아 해시 목록과 그 열쇠(목록의 sha256)를 짓고 `.github/workflows/checks.yml` 을 그
태그에서 부른다 — 실행 제목 `점검 <태그> <열쇠>`. 잡 둘이 각자 초안을 받아 그 해시와 대조하고, 잡 토큰을 돌려준 뒤 지난
공개본을 익명으로 받는다. 바뀐 룰의 하네스는 잡이 스스로 셈한다(머리의 `# 룰:` 줄 · `bash ci/batch.sh harnesses`).

- **리눅스 잡**(ubuntu-24.04) — 아래 `emergency-checks.sh` 그대로. 하네스가 쓸 이미지는 머리의 `# 이미지:` 줄대로 미리 받는다
- **Windows 잡**(windows-2025) — 러너가 자기 자신을 랩으로 쓴다(`testbed/harness/host/Initialize-RunnerLab.ps1` — 로컬 관리자
  계정 · 루프백 원격 · 랩 설정 파일 · 이미지에 깔린 Apache · nginx 서비스 정리). ②③ 은 `Invoke-EmergencyChecks.ps1 -Runner`
  (되돌릴 스냅숏이 없어 시연 기계를 되돌리지 않고 세운다), ① 은 바뀐 Windows 룰의 하네스를 `Invoke-RuleHarness.ps1` 로 —
  그 하네스 머리의 `# 입력:` 줄대로 공식 zip 을 받아 대조해 준다
- **공개 확인 i** — 공개 워크플로가 그 태그 커밋 · 그 자산 셋(제목의 열쇠) · 잡 linux · windows 둘의 성공을 다시 본다. 점검한
  바이트와 공개할 바이트를 기계가 묶는다
- **러너는 랩이 아니다** — Windows Server 2025 · Defender 실시간 감시 꺼짐 · 이미지의 소프트웨어(매주 바뀐다). 랩(Windows 10 ·
  Defender 켬)과의 차이는 24시간 안의 **미룬 검증**(랩 rc 묶음)이 그대로 잰다
- **`--local`** — 차례 3 전의 길(리눅스 몫은 이 PC 의 docker · WSL, Windows 몫은 랩 VM). 러너가 막힌 날 · 둘을 견줄 때 쓴다.
  Windows 룰 하네스(①)는 돌리지 않는다(그 룰의 PR CI 가 돈 하네스 기록을 승인 전에 본다). 공개 확인은 i 대신 d(점검한 파일의 해시)로
  묶는다 — 공개 실행 제목에 '(PC 점검)' 이 붙는다

| ② | 정식 파일이 온전한가 | 체크섬(리눅스는 스크립트가 받은 `SHA256SUMS` 로 · Windows 는 README 의 한 줄로 zip 을) · 두 OS 의 엔진과 동반 프로그램 버전 · 꾸러미의 룰 전부 서명 · 판정 기준 줄 · Windows 실행 파일 둘의 코드서명(유효 · 주체 · 타임스탬프) · **실행 파일 둘이 지난 공개본과 같은 바이트인가**(룰만 바뀐 출시는 그 파일을 그대로 싣는다 — 엔진 버전이 같은데 다르면 실패 · 리눅스는 `--prev` 로 · Windows 는 `-Prev` 를 줬을 때) |
| ③ | 기존 동작이 그대로인가 | 리눅스 — 깨끗한 컨테이너에서 지난 공개본과 메뉴 '모두 검사' 의 **종료 코드가 같고** 화면 차이가 새 룰의 줄뿐 · Windows — 시연 게이트와 메뉴 하네스(러너가 자기 자신을 랩으로 · `--local` 이면 이 PC 의 랩) |
| ④ | **G9 — 룰의 검체 오탐**(`AGENTS.md` 의 릴리스 전 게이트) | 새 룰 · 고친 룰에 YARA 가 있으면 `cargo xtask yara` 로 정상 파일 코퍼스에 전수. 치료 · 탐지 룰은 **맞음 0**, 점검 룰은 맞은 파일이 **모두 그 뜻의 파일**(설정 · 실행 파일)인가 · 못 훑은 것은 수와 사유. 단계 1 끝에 저장소의 `.yar` 로 쟀으면 초안 꾸러미의 `.yar` 가 잰 것과 같은 바이트인지 견준다 |
| ⑤ | 넘길 파일 = 시험한 파일 | 공개 전 — ①~④ 에서 잰 파일이 초안의 지금 자산이다 · 공개 뒤 — 익명으로 받은 바이트가 같다(다르면 곧바로 지난 공개본을 다시 Latest 로 두고 보고 — 1차였으면 위협별 안내 그 절의 첫 줄에 *지금 받는 버전에는 이 항목이 없습니다* 를 적는다 · 고정 글은 고치지 않는다) |

**치료 룰이면 ⑥** — 치료 → 다시 검사(0 또는 6) → 복원 → 원래 파일과 같은 바이트로 돌아온다. 새 룰의 하네스에 그 칸을 둔다
(`testbed/harness/linux/cwpdoor-verify.sh` 의 C 칸이 그 꼴이다).

```bash
# ④ G9 — 저장소 루트. 정상 파일 코퍼스는 그 룰이 보는 배포판의 파일 시스템(`/etc` · `/usr` 등)이다.
cargo xtask yara --rules plugins/<룰>/rules --rule <YARA 규칙 이름> --scan <정상 파일 폴더> --expect clean --max-bytes 67108864
```

`--rules` 는 `.yar` 가 든 `rules/` 폴더다. `--rule` 은 이름 하나만 받는다 — 규칙마다 따로 돌린다(2026-11-19 모의 1차 — 정상
설치 8개의 파일 47,834개에 규칙당 약 160초). G9 는 룰의 `.yar` 가 정해진 단계 1 끝에 저장소의 `.yar` 로 돌리고(공개 공지에
근거한 점검 룰은 PR CI 를 기다리는 동안도 된다 — 악성코드 · 미공지 룰은 올리기 전에 · 규칙이 여럿이면 초안 뒤에 돌릴 때 필수
점검 예산 11분을 넘는다), ④ 에서는 초안 꾸러미의 `.yar` 가 잰
것과 같은 바이트인지 견준다(1.17.0 의 꼴). 정상 설치의 파일을 꺼내는 길: 그 배포판 이미지에 소프트웨어를 깐 컨테이너를
`docker export` 해 `/etc` · `/usr` 를 Windows 에서 보이는 폴더에 푼다 — `bash testbed/harness/linux/g9-corpus.sh <꺼낼 폴더>
<이미지>…`.
악성코드 룰은 그 배포판의 루트에 더해 룰이 훑는 자리(`scan_roots`)를 채우는 정상 패키지를 깐 이미지(유닛 · cron 을 보면
systemd · cron · dbus)와 그 악성코드가 덮거나 흉내 내는 정상 판(공급사 · 배포판의 그 파일)을 코퍼스에 넣고 갈래마다 수를
적는다(2026-11-25 · 원칙 [설계-03](design/설계-03-안전장치.md) §10 · 보기 `plugins/cwpdoor-2-clean/RELEASE.md` ·
`plugins/ebury-check/RELEASE.md` 의 G9 줄).
리눅스 링크는 Windows 가 열지 못해 *못 훑음* 으로 세어지니 그 수를 스크립트가 적은 링크 수와 대조한다(*안 맞음*
에는 스크립트가 꺼낸 폴더에 남기는 `<이미지>.tar-errors.txt` 가 이미지마다 하나씩 더해진다). 상한을 넘는 파일도 *못 훑음* 이라
위 명령은 `--max-bytes` 를 64 MiB 로 준다(2026-11-24) — 제품이 YARA 로 훑는 본문은 본문 총량 상한(64 MiB)을 넘지
않고(`max_size` 를 더 크게 적어도 그렇다), 빼면 16 MiB 라 1.15.0 의 `libicudata` 셋 · PHP 공식 이미지의 실행 파일이 *못 훑음*
에 들었다. 그래도 링크 수와 어긋나면 `--list <못 훑음 수>` 로 사유를 다 본다(빼면 20줄). 점검 룰은 `--expect clean` 이 맞은
것을 '오탐' 으로 적어도, 그것이 그 규칙이 뜻한 파일인지로 판정한다. 맞은 목록도 같은 `--list` 로 잘리니('... 외 N건') 점검 룰의
맞은 목록까지 다 보려면 `--list <맞음 수와 못 훑음 수 가운데 큰 값>` 을 준다 — 못 훑음 수만 주면 맞음이 더 많을 때 여전히
잘린다(2026-11-25 · 아래 1.15.0 기록의 `apache_version_affected` 가 맞음 28). `--list` 는 숫자만 받는다(그 밖의 값은 말없이
20 — `xtask/src/yara.rs`).

## 뒤로 미루는 것 — 공개 뒤 24시간 안

| 무엇 | 왜 미룰 수 있나 |
|---|---|
| 두 OS 의 rc 묶음 A/B(지난 공개본 대 공개된 판) | 싣는 실행 파일이 지난 공개본과 같은 바이트다(②) — 기존 룰의 판정은 ③ 이 대표 경우로 보고, 묶음이 나머지 경우를 본다 |
| 콘솔 기준선 재캡처 · 화면 문서의 룰 버전 줄 | CI 는 문서와 기준선을 서로 견줄 뿐 실행 파일과 견주지 않는다 — 그 사이 기준선은 지난 판의 화면이다(머리말 첫 줄의 룰 버전) |

rc 묶음은 [`개발-안내.md`](개발-안내.md) "출시 검증" 의 4 와 같은 명령이다 — `--new` · `-Package` 에 **공개한 그
파일**을 준다. 리눅스를 먼저(시료를 받는다), WSL 캐시를 비운 뒤 Windows. 룰만 바꾼 출시이므로 A/B 의 **다름도
실패**다(엔진이 그대로인데 기존 룰의 종료 코드가 바뀌었다는 뜻이다). 다만 remedy-net 기준 데이터 룰을 고친 출시는
`net-ab` 에서 그 값이 바꾼 경우의 차이만 의도한 변경이다(`net-apache` 는 기대값 표라 통과해야 한다) — 그 밖의 다름은
실패다. 콘솔 재캡처는 두 언어를 한 번에 받는 `testbed/harness/host/Invoke-ConsoleRecapture.ps1`(랩 VM) 다음 `testbed/harness/linux/console-recapture.sh`(WSL)로 하고,
`cargo xtask console-diff` 로 견준 뒤 기준선과 화면 문서를 후속 PR 로 올린다. 부르기 전에 저장소 뿌리의 `plugins/RULES-VERSION`
(커밋하지 않는 자리)에 공개한 룰 버전 한 줄을 쓰고 끝나면 지운다 — 지은 꾸러미가 그 파일을 실어야 머리말에 룰 버전이 서고, 없으면 두
스크립트가 멈춘다(종료 2 · 2026-11-23 — 그 파일이 저장소에서 빠진 2026-11-21 뒤로는 줄이 빠진 캡처가 될 자리였다).

**누가 · 언제까지**(2026-11-22) — 리눅스 rc 묶음은 러너가 하루 한 번 돈다(2026-11-23 · `.github/workflows/deferred-linux.yml` —
07:37 KST — 정각에 둔 첫 일정이 돌지 않아 옮겼다(2026-11-24) · A 는 24시간 전의 Latest · B 는 지금 Latest · 결과는 그 실행의
기록과 잡 요약). 빨강이면 미룬 검증을 맡은 Owner 가 잡
요약의 다름 · 실패 칸을 보고 판정한다 — 다름은 대개 그 사이 공개한 룰이 의도한 변경이다(판정 기준 데이터 룰을 고친 출시의
`net-ab` 처럼). 일정 실행이 돌지 못했거나 다시 돌 때는 Owner 누구나 손으로 부른다(`gh workflow run deferred-linux.yml -f prev=<A 태그>
-f new=<B 태그>`) — 러너에서 돌지 못한 날은 WSL2 + docker 가 있는 PC 에서 돌아도 된다. 리눅스 콘솔 재캡처는 WSL2 + docker 가 있는
PC 의 Owner 누구나,
Windows 몫(rc 묶음 · 콘솔 재캡처)은 랩 VM 이 있는 PC 의 Owner 가 돈다(지금 랩은 한 PC 에만 있다 · Windows 묶음이 읽는 시료는 그 PC 의
`testbed/harness/results/rc-inputs` 다 — 없으면 그 PC 에서 리눅스 묶음을 한 번 돌아 채운다). **하루 한 번의 차례**(2026-11-23) —
러너의 리눅스 실행(07:37 KST)이 끝난 뒤 근무 시간에, 그 잡 요약의 A · B 그대로 Windows 랩 묶음 → 두 OS 콘솔 재캡처를 돈다(랩과
컨테이너 일을 겹치지 않는다). 결과(러너 실행 주소 · Windows 묶음의 판정 · 재캡처의 차이)는 기준선 후속 PR 본문에 적는다 — 그 PR 이
그날 미룬 검증의 기록이다. 그날 공개가 없었으면(러너 실행이 'A 와 B 가 같다' 로 끝났으면) 돌지 않는다.
24시간 안에 못 돌면 지원 이슈에 '밀림' 과 까닭을 적고
다음 근무일의 첫 일로 돈다 — 그동안 다음 묶음은 막지 않는다(실패가 드러나면 아래대로 멈춘다). 여러 출시의 미룬 검증이 겹치면
[2 · 3차](#2--3차)의 *미룬 검증이 겹치면* 대로 묶는다. **하루치의 기한**(2026-11-23) — 미룬 검증은 가장 오래된 미검증 공개의
24시간 안에 끝낸다. 한 번이 그 사이 공개된 출시를 모두 덮으므로, 하루 여러 번 낸 날에도 하루 한 번 돌면 된다.

**미룬 검증이 실패하면** '모아 내기 멈춤 — <태그>' 이슈를 열어 다음 묶음을 멈추고(`batch.sh` 는 그 이슈가 열린 동안 시작하지
않고, 이미 시작한 묶음은 공개 확인 j 에서 멈춘다) 지원 이슈의 승인 담당에게 알린다. 기본은 고친 판을 새 rules 출시로 **앞으로** 내는 것이다 — 공개한
Release 는 불변이라 그 파일을 바꿀 수 없고, 고친 판은 새 버전이다. 지난 공개본을 다시 Latest 로 두는 것(`gh release edit <지난
공개본의 태그> --latest`)은 기존 항목을 해친 때뿐이다(룰만 바뀐 출시의 A/B 다름 — 기준 데이터 룰의 `net-ab` 예외
말고 — 이 그 경우다). 되돌리면 고정 글의
`releases/latest` 가 그 위협의 룰이 없는 버전을 준다 — 1차를 되돌렸으면 위협별 안내 그 절의 첫 줄에 *지금 받는 버전에는 이
항목이 없습니다* 를 적는다(고정 글은 고치지 않는다).

## 버전 번호

[`개발-안내.md`](개발-안내.md) "버전 번호" 그대로다 — 긴급 경로라고 다르지 않다. 룰만 바뀐 출시라 **엔진 버전은 그대로
두고 룰 버전만** 오른다. 룰 버전은 룰 PR 이 아니라 `bash ci/batch.sh` 가 출시 때 정한다(그날 한국 날짜 · 같은 날 둘째부터
`.2` … · 2026-11-21 — 전에는 PR 마다 `plugins/RULES-VERSION` 을 고쳐 같은 값이 조용히 합쳐지면 둘째 출시가 태그에서 막혔다).
태그는 `rules-<룰 버전>` 이고, 지금 Latest 가 그 커밋의 조상이 아니거나 룰 버전이 Latest 보다 높지 않거나 날짜가 내일을 넘으면
배포 워크플로가 태그에서 멈춘다(`ci/version-check.sh`). 실행 파일은 다시 짓지 않는다 — 지금 Latest 의 실행 파일 둘을 그대로
실어(main 의 엔진이 앞서 있어도) 받는 사람의 실행 파일은 그 공개본과 같은 바이트(Windows 는 같은 코드서명)다. 1.15.0 ·
1.17.0 은 이 정책 전이라 엔진 버전의 마이너를 올렸다.
