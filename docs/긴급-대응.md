# 긴급 대응 — 룰만 바뀐 출시를 빨리 내는 길

공개 시연이나 실제 공격이 있는 취약점 · 퍼지는 악성코드에 **룰을 더하거나 고쳐** 빨리 내야 할 때 쓴다. 평소 출시는
rc 를 내려받아 두 OS 의 rc 묶음(A/B · 1.24.0 실측 약 66분)을 **공개 전에** 돌린다. 긴급 경로는 공개 전에 **필수 점검**(새 룰
하네스 · 정식 파일 · 기존 동작 · G9 · 넘길 파일)만 보고, rc 묶음과 콘솔 기준선은 **공개 뒤 24시간 안에** 돌린다.

**목표는 요청을 받은 뒤 2시간 안에 공개하는 것이다**(아래 [시간 목표](#시간-목표--요청-뒤-2시간)). 한 번의 출시로 위협을 다
덮을 수는 없으므로 **1차는 최소 범위로 빨리** 내고, 남은 범위는 **2 · 3차로 같은 출시 줄에서** 넓힌다(아래
[1차 · 2차 · 3차](#1차--2차--3차--넓혀-가는-배포)). AI 작업자에게는 [1차 프롬프트](#1차-프롬프트)를 그대로 준다.

**잰 값** — 1.15.0(Apache CVE-2026-119618): 룰 PR 의 CI 시작 → 공개 **47분 3초**(같은 일을 평소 경로로 낸 1.14.0 은 1시간
50분 36초). 요청 → 공개는 1.17.0(Apache Windows) 2시간 16분 · Java4Shell(CVE-2026-114938) 1차 2시간 40분 · 2차 1시간 47분이다
(1.15.0 은 이 경로를 만드는 일과 함께 온 요청이라 견주지 않는다).

## 쓰는 조건

| | |
|---|---|
| **쓴다** | 바뀐 것이 룰(`plugins/` — 룰 버전 `plugins/RULES-VERSION` 포함) · 하네스 · 문서뿐이다 — `crates/` · `xtask/` 0줄(PR 에서 `git diff --stat origin/main...HEAD -- crates/ xtask/`) · 엔진 버전은 그대로다 |
| **쓰지 않는다** | 엔진을 고쳐야 한다 → 평소 경로(rc 와 A/B 를 공개 전에) |
| **승인** | 건마다 사용자가 정한다 — 요청문에 함께 적을 수 있다(아래 견본). "긴급 · 빨리" 라는 말만으로는 승인이 아니다 |
| **멈춘다** | 필수 점검이 하나라도 실패하면 공개하지 않는다 · 1차 출처(공급사 · 상류 공지 · 배포판 추적기 — 악성코드는 분석한 곳의 원 보고)가 없으면 룰을 짓기 전에 사용자에게 묻는다 · 원 보고 없이 보도만 있어도 묻는다 |
| **고친 판이 없다** | 영향 판을 *취약*(2)으로 낼지 *확인 필요*(6)로 낼지, 완화 설정을 흔적으로 볼지를 사용자가 정한다(카드) — 고친 판이 나오면 룰을 다시 낸다 |
| **엔진이 모자라다** | 1차는 지금 엔진으로 되는 만큼 룰만으로 이 경로로 내고, 엔진 몫은 다음 차수로 평소 경로에서 낸다([1차 범위](#1차-범위)) |
| **main 이 앞서 있다** | main 에 지금 Latest 뒤의 엔진 변경이 있거나 진행 중인 출시(rc · 정식 태그 · 초안)가 있거나, 지금 Latest 가 main 에 없으면(긴급 가지로 낸 것을 아직 합치지 않았다) 처음부터 [긴급 가지](#main-이-앞설-때--긴급-가지)로 간다 — 단계 0 전에 가린다 |

**룰이 보이는 시간.** `AGENTS.md` 는 사고 대응 중에 배포보다 룰이 먼저 보이는 것을 막으라고 한다 — 대응 중인 위협의
룰은 공개 저장소 밖에서 짓고 **배포하는 커밋에 함께** 올린다. 긴급 경로도 같다: 룰 · 하네스 · 검사를 로컬에서 다 마친 뒤
PR 을 올리고, 그때부터 공개까지(1.15.0 은 47분)가 룰이 먼저 보이는 시간이다. 이 시간을 줄이는 것이 이 경로의 목적이기도
하다.

## 요청하는 법

AI 작업자에게 이렇게 맡긴다 — 이 문서를 가리키면 단계를 다시 설명하지 않아도 된다.

```text
긴급: <위협 이름 · CVE> — <공지 링크 또는 붙여 넣은 설명>.
요청 받은 시각: <YYYY-MM-DD HH:MM KST>
docs/긴급-대응.md 의 긴급 경로로 1차를 낸다(이 건의 긴급 출시를 승인한다).
```

받은 작업자가 사용자에게 묻는 것은 결정이 필요한 칸뿐이다 — 판정 정책(예: 설정 흔적이 없으면 확인 필요인가),
고친 판을 정하지 못한 배포판의 처리, 대상 OS 의 차례. 사실(영향 판 · 고친 판 · 악용 조건)은 1차 출처에서 직접 잰다.
작업자에게 줄 전체 지시는 [1차 프롬프트](#1차-프롬프트)다.

## 시간 목표 — 요청 뒤 2시간

- **재는 법** — 요청 받은 시각(요청문 · 위협 지원 이슈에 적는다) → GitHub Release 공개(Latest). 근무 시간 밖에 온 요청은
  착수한 시각부터 잰다. 다운로드 페이지 게시는 회사 쪽 일이라 넣지 않고, [사용방법 글](#사용방법-틀--다운로드-페이지)을
  공개와 함께 넘긴다.
- **목표** — 룰만으로 되는 건은 **120분**. 더 빠르게(90분)는 아래 *준비 중* 두 줄이 된 뒤다. 엔진이 모자란 건은 1차를
  룰만으로 120분 안에 내고 엔진 몫은 다음 차수로 낸다(평소 경로 · PR → 공개 목표 3시간).
- **기록** — 건마다 요청 · PR · CI 끝 · 병합 · 태그 · 자산 · 공개 시각을 그 건의 기록에 남긴다(gh 의 실행 · 릴리스 기록으로
  다시 잴 수 있게 실행 번호도). 앞선 건들은 요청 시각을 시 단위로만 적어 다시 재기 어려웠다 — 요청문에 분 단위로 받는다.

| 단계 | 잰 값 | 예산 |
|---|---|---|
| 사실 · 룰 · 하네스 · 커밋 전 검사(PR 전) | 60.8분(Java4Shell 2차) · 100.2분(1차) | 60분 — [1차 범위](#1차-범위)로 줄인다 |
| PR CI(두 OS · 늘 Windows 가 임계) | 17.4 ~ 26.3분 — 엔진 0줄인 PR 에도 Windows `cargo test` 가 17.8분 | 22분 — 룰만 바뀐 PR 의 CI 를 줄이면 약 4분(*추정* · 준비 중) |
| 태그 → 초안 자산 | 13.3 ~ 22.2분(코드서명 전) · 코드서명이 붙은 뒤 v 태그 20.3 ~ 26.2분 | 26분 — 지난 공개본의 서명된 실행 파일을 그대로 쓰면 약 8분(*추정* · 준비 중) |
| 출시 전 필수 점검 | 9 ~ 11분 | 11분 |
| 공개 | 1분 안 | 1분 |
| **합** | 1차 2시간 40분 · 2차 1시간 47분 | **120분 → 준비가 끝나면 약 84분(*추정*)** |

## 1차 · 2차 · 3차 — 넓혀 가는 배포

한 번의 출시로 위협을 다 덮을 수는 없다. **1차는 아래 최소 범위로 2시간 안에** 내고, 이번에 하지 않은 범위는 대기열에 남겨
**2 · 3차로 같은 출시 줄에서** 넓힌다. Java4Shell 이 그렇게 나갔다 — 1차 `rules-2026.11.18` → 2차 `rules-2026.11.18.2` →
3차 `v1.24.0`(엔진 몫 포함), 하루에 세 번.

### 1차 범위

- **취약점 — 핵심만 점검한다.** 1차 출처의 영향 버전 · 고친 버전으로 아래 자리를 본다.
  - **보는 자리** — 표준 설치 자리 · 패키지 기록 · 실행 중인 프로세스. 표준 설치 자리는 배포판 패키지가 까는 자리 · 상류의
    기본 접두사(Apache `/usr/local/apache2`) · 널리 쓰는 묶음 배포의 기본 자리(XAMPP `/opt/lampp`)다. 같은 제품을 흔히 까는 다른
    이름의 자리(Apache 의 `/usr/local/httpd` · `/opt/apache2` 꼴)도 적어도 버전을 읽는 파일(실행 파일 · `release` 등)은 넣는다 —
    돌지 않는 설치본은 프로세스로 잡히지 않는다. 접두사 안에서는 설정(`conf` · 묶음 배포의 `etc`) · 실행 파일(`bin`) · 판
    파일(`build/config_vars.mk` 등)만 겨눈다 — 설정 읽기(`text_config`)를 접두사 전체에 걸면 웹 문서(`htdocs`)의 `.env` ·
    `.ini` 같은 줄이 결과 파일에 그대로 담긴다(`crates/remedy-collect/src/config.rs` 의 `TEXT_EXT`). 하네스에 가짜 비밀 칸(웹
    문서의 `.env` · 설정 폴더의 키 파일 자리 — 키 모양이 아닌 표지 문자열로)을 두고 결과 폴더에 그 표지가 0 인지 잰다.
  - **모르면 6** — 위 자리 밖에서 돌거나 서비스로 등록된 것, 판단할 근거가 없는 것은 0 이 아니라 *확인 필요*(6)다. 모듈 ·
    라이브러리 파일이 없다는 것만으로 0 을 내지 않는다(실행 파일에 정적으로 넣은 빌드가 있다).
  - **판정 정책은 카드로** — 완화 옵션(설정 · 실행 인자)을 판정에 넣을지는 위 *고친 판이 없다* · *요청하는 법* 의 판정
    정책대로 묻고, 권장 기본은 *꼭 할 일* 의 안내다. 같은 공지(CVE)를 remedy-net 이 이미 판정하면(지금 PHP2Shell · Node2Shell ·
    Apache HTTP/2 — `crates/remedy-net/src/scan/rules/`) 그 정책을 카드에 사실로 적는다. 그 정책은 엔진 코드에 있어 긴급
    경로로 바꾸지 못하므로, 다르게 고르면 두 프로그램이 같은 서버를 다르게 판정한다. 예: Apache HTTP/2 는 본체 룰과
    remedy-net 이 같게, 영향 판에 HTTP/2 를 켠 흔적(모듈 적재 + `Protocols` 의 `h2` · `h2c`)이 다 있을 때만 *취약* 이고 그 밖은
    *확인 필요*(6)다(정책은 `crates/remedy-net/src/scan/rules/apache.rs` 머리 · 흔적의 자리 — 설정 경로 · Debian 의
    `mods-enabled` 를 이름으로 보는 법 — 는 `crates/remedy-net/src/scan/apacheconf.rs` 머리). 같은 제품의 다른 공지면 *remedy-net(이미지 · 컨테이너
    · url 점검)은 이 CVE 를 보지 않는다* 를 사실로 적는다.
- **악성코드 — 중단 · 재감염 방지 · 확산 방지만 한다.**
  - 중단: 악성 프로세스 종료(`process.kill`) · 서비스 정지 · 사용 안 함. `process.kill` 은 같은 조건에 걸린 대상이 상한
    (기본 8 · `crates/remedy-plan/src/limits.rs` 의 `kill_targets`)을 넘으면 **하나도 끝내지 않고** 그 동작을 멈춘다 — 일꾼을
    여럿 띄우는 서버 프로그램이면 서비스를 멈추는 쪽을 함께 보고, 하네스에 실제 일꾼 수만큼 프로세스를 띄운다
  - 재감염 방지: 자동 실행 · 예약 작업 · 서비스 같은 지속 수단 제거(유발자 먼저) · 주 페이로드 격리(되돌릴 수 있다)
  - 정상 프로그램을 덮은 트로이 판(공급사 실행 파일 · 공급사 서비스가 곧 지속 수단) — 격리하면 그 서비스는 다시 뜨지 못한다
    (리눅스는 도는 실행 파일을 옮겨도 그 프로세스가 계속 돈다 — 지금 도는 것을 멈추는 것은 아래 서비스 `ref` 나
    `process.kill` 이다). 정상 판으로 되돌리는 것은 엔진 밖이라 *꼭 할 일*(패키지를 최신 판으로 다시 깐다)로 넘긴다. 공급사 유닛을 서비스 `ref` 로 넣으면 정지 →
    사용 안 함 → 유닛 삭제까지 가고(`crates/remedy-plan/src/derive.rs` 의 `removal_ops`), `process.kill` 만 쓰면 `Restart=` 의
    다시 띄우기와 위 상한을 진다 — 어느 쪽으로 할지는 카드로 묻는다. *꼭 할 일* 에는 *'다시 깐 뒤에는 복원하지 마십시오(복원은
    격리한 파일로 새로 깐 파일을 덮습니다)'* 를 넣고, 공격자가 남긴 사본(백업)을 복구원으로 권하지 않는다
  - 확산 방지: 공격자가 바꾼 hosts(두 OS) · 방화벽 허용 규칙 · 프록시 · 백신 예외(Windows)를 되돌린다
  - 엔진에 없는 일 — 네트워크 차단 · 계정 · 자격 증명 재설정 · WMI 등과 리눅스의 폴더째 삭제 · 방화벽 · 프록시 · 백신 예외
    되돌리기(Op 과 OS 는 [`plugin-guide/machine/REFERENCE.md`](plugin-guide/machine/REFERENCE.md) 의 *파괴·변경 동작* 표) — 은
    위협별 안내의 *꼭 할 일* 로 사람에게 넘긴다
  - 지표는 **공개 출처에 있는 것만** 쓴다 — 꾸러미가 룰을 평문으로 담아 배포가 곧 공개다
- **엔진이 모자라면** — 1차는 지금 엔진으로 되는 만큼(점검 · 탐지만이라도 · 모르면 6) 룰만으로 내고, 엔진 몫은 다음 차수로
  평소 경로(rc 와 A/B 를 공개 전에)에서 낸다(룰만으로 넓힐 몫이 먼저면 그 뒤 차수 — Java4Shell 은 3차). 엔진은 고객 기계에서
  끄고 지우는 코드라 공개 전 검증을 줄이지 않는다.
- **이름은 1차에 정한다** — 룰 이름 · id 는 두 OS 몫까지 1차에 정하고 2 · 3차에도 바꾸지 않는다(폐기 목록 · 찾기 · 사용방법
  글이 그 이름을 쓴다). 룰 이름에는 그 위협의 CVE 를 모두 `CVE-YYYY-NNNNN` 꼴 그대로 넣는다 — 화면의 찾기는 이름 · 폴더 이름의
  글자를 그대로만 맞춘다(`crates/remedy-cli/src/guided.rs` 의 `matching`). 그 위협의 룰은 2 · 3차에도 **빠른 검사**에 남게
  둔다 — 뿌리를 `%FIXED_DISKS%` 로 바꾸면 정밀 검사로만 간다. 디스크 전체 몫이 필요하면 룰을 따로 더한다.
- **위협별 안내 절을 1차에 만든다** — [위협별 안내](위협별-안내.md)에 그 위협 절(세 줄 · 자세히)과 제목 위의 고정 주소
  `<a id="<위협>"></a>`(빈 줄로 제목과 뗀다), README *위협별 안내* 표에 고정 주소로 잇는 한 줄. 사용방법 글이 그 주소를 가리킨다.
  그 절의 자세히가 가리키는 룰 `RELEASE.md` 첫 판에는 판정 표 · 고친 판 표와 공지 번호 · 게이트 줄(G1 · G9 · 하네스)을 둔다.
  두 OS 에 걸친 위협을 1차가 한 OS 만 담아 내면 절의 첫 줄(무엇을 보는지)에 *지금은 리눅스를 봅니다 — Windows 는 다음 버전에서
  더합니다(아래 대응 기록)* 꼴로 적고 그 OS 를 더한 차수에 지운다. 제목에는 OS 를 넣지 않는다 — 제목은 바꾸지 않는다.

### 2 · 3차

- **같은 출시 줄이다** — 룰만 바뀌면 `rules-<룰 버전>`, 엔진이 바뀌면 `v<엔진 버전>`. 그 위협만 담은 따로 된 꾸러미 · 태그는
  두지 않는다 — 빨라지지 않고(배포에서 룰 몫은 룰당 약 13초) 받는 주소가 달라져 사용방법 글을 고쳐야 한다.
- **차수마다 함께 고친다** — 룰 `version` · 업데이트 내역 칸 · 그 룰의 `RELEASE.md` · [위협별 안내](위협별-안내.md)의 그 위협
  절(첫 줄의 보는 OS · 대응 기록 줄 · 보는 자리 · 못 보는 것) · 고치는 룰이 remedy-net 기준과 같은 공지를 쓰면 그 기준 데이터
  룰(아래 *단계 0 ~ 2 에서 걸리는 것*). 하네스를 고치면 rc 묶음 · 메뉴 하네스가 넘기는 인자(리눅스
  `testbed/harness/linux/rc-bundle.sh` · Windows `testbed/harness/host/Invoke-RcBundle.ps1` 의 그 단계 줄)와 픽스처를 지킨다.
  하네스끼리도 묶여 있다 — 리눅스 Apache 하네스(`apache-verify.sh`)가 짓는 이미지 `remedy-harness/apache:*` 열하나를
  `net-apache-verify.sh` 가 요구하므로 다시 쓰면 그 이름 · 꼬리표를 그대로 짓게 둔다. **사용방법 글은 고치지 않는다.**
- **대기열** — 이번에 하지 않은 범위와 까닭 · 필요한 것(엔진 · 실물 · 공지)을 그 룰 `RELEASE.md` 의 맨 위 버전 절에 *다음 차수
  후보* 로 적는다. 차수를 낼 때만 고친다 — `RELEASE.md` 는 `MANIFEST` 에 들어 고치면 개발 키로 다시 서명해야 하고(서명을
  저절로 확인하는 것은 메뉴가 룰을 고를 때와 remedy-net 이 기준을 읽을 때뿐이라 `xtask all` · CI · `scan --plugin` 하네스는 낡은
  서명을 막지 않는다 — 손으로 챙긴다 · [`개발-안내.md`](개발-안내.md#서명)) 버전 검사가 룰 변경으로 센다. 이 파일은 배포 파일에 실려 받는 사람이 본다 — 탐지 조건 · 지표는
  적지 않는다.
- **미룬 검증이 겹치면** — 다음 차수도 룰만 바뀐 출시이고 그 미룬 검증이 앞 차수 공개 뒤 24시간 안에 끝날 때만, 뒤 차수의
  미룬 검증을 **앞 차수 바로 앞의 공개본** 대 뒤 차수로 돌려 앞 차수 몫을 함께 잰다. 뒤 차수가 엔진 출시면 앞 차수의 rc
  묶음 A/B(다름도 실패)는 따로 돌린다 — 콘솔 재캡처만 엔진 출시의 재캡처로 합칠 수 있다.
- **차수는 릴리스 이름 · 파일 이름 · 사용방법 글에 넣지 않는다** — 받는 것은 늘 *최신 버전* 이다. 차수는 위협별 안내의 대응
  기록에만 적는다. 언제 다시 받을지는 그 대응 기록과 GitHub 의 *Watch → Custom → Releases* 로 알린다.

## 1차 프롬프트

새 위협이 오면 AI 작업자(Claude Code · Antigravity 등)에게 이것을 채워 그대로 준다.

```text
긴급 1차: <위협 이름 · CVE> — <공지 링크 또는 붙여 넣은 설명>
요청 받은 시각: <YYYY-MM-DD HH:MM KST>
docs/긴급-대응.md 의 긴급 경로로 1차를 낸다(이 건의 긴급 출시를 승인한다).

1. AGENTS.md 와 docs/긴급-대응.md 를 읽고 그 단계(0 사실 → 7 미룬 검증)를 따른다. 단계 0 전에 main 이 지금 Latest 보다
   앞섰는지 가린다("main 이 앞설 때" 절) — 앞섰으면 처음부터 긴급 가지로 간다. 사실은 1차 출처(공급사 · 상류 공지 · 배포판
   보안 추적기 — 악성코드는 분석한 곳의 원 보고)에서 직접 잰다. 지표는 공개 출처에 있는 것만 쓴다.
2. 범위는 "1차 범위" 절대로 줄인다 — 취약점은 핵심 점검, 악성코드는 중단 · 재감염 방지 · 확산 방지. 룰 이름 · id 는
   두 OS 몫까지 정하고 빠른 검사에 남게 짓는다. 새 룰과 새 위협(CVE)을 맡긴 룰은 매니페스트에 `added: "<오늘 한국 날짜>"`
   를 적어 고르는 화면 맨 위(*새로 추가된 항목*)에 올린다(min_core 1.25.0 · `plugin-guide/10-manifest.md`). 엔진을 고쳐야
   1차가 되면 멈추고, 룰만으로 줄인 1차를 카드로 묻는다.
3. 결정이 필요한 칸만 카드로 묻는다(권장안을 맨 앞에). 나머지는 묻지 않고 간다.
4. 산출물 셋을 낸다.
   (1) 룰 · 하네스(단계 1 의 0 · 2 · 6 · 치료 룰은 ⑥ 까지) · G1(청정 코퍼스) · 위협별 안내의 그 위협 절과 고정 주소 ·
       README 표 한 줄 · 고치는 룰이 remedy-net 기준과 같은 공지(CVE)를 쓰면 그 기준 데이터 룰(같은 제품의 새 공지면 고치지
       않는다) · 긴급 출시(필수 점검 ①~⑤, 치료 룰은 ⑥ · G9 를 빠뜨리지 않는다)
   (2) 다운로드 페이지 글 — "사용방법 틀" 을 채운다. 바뀌는 사실(프로그램 · 룰 버전, 영향 · 고친 버전 표, 보는 자리 · 못
       보는 것, 해시, 메뉴 번호, 흔적)은 쓰지 않는다. 페이지의 사실 칸(대상 버전 · 현상 · 대상 악성코드)은 1차 출처의
       문장과 링크로 따로 낸다
   (3) 2 · 3차 대기열 — 이번에 하지 않은 범위 · 까닭 · 필요한 것
5. 단계마다 시각을 남긴다. 끝에 요청 → 공개 시간 · 단계별 시간 · 산출물 셋을 보고한다.
```

## 사용방법 틀 — 다운로드 페이지

회사 다운로드 페이지에 올리는 글이다. **2 · 3차가 나가도 고치지 않게** 바뀌지 않는 것만 쓴다 — 고정 주소(`releases/latest`) ·
고정 파일 이름 · 실행 순서 · *빠른 검사* · 결과의 종류 · 다시 받는 법. 바뀌는 것 — 프로그램 · 룰 버전, 영향 · 고친 버전 표,
보는 자리 · 못 보는 것, 해시, 메뉴 번호, 흔적 — 은 쓰지 않고 [위협별 안내](위협별-안내.md)의 그 위협 고정 주소로 보낸다.
위협별 안내는 위협 절마다 제목과 따로 고정 주소(`#java4shell` 꼴)를 둔다. 위협 절 제목은 바꾸지 않는다 — 이미 공개한 릴리스
본문과 업데이트 내역이 제목에서 만든 주소로 잇는다. 새 링크는 고정 주소로 적는다.

**어느 출시든**(평소 · 긴급 · 다른 위협) 이 틀이 인용한 화면 낱말(관리자 권한으로 다시 열기 · 빠른 검사 · 모두 검사만
하기 · 이름 · 제품 · CVE 로 찾기 · 찾은 것 모두 치료하기 · 결과 줄)이나 첫 화면의 꼴을 바꾸면, 그 출시에 살아 있는 다운로드 페이지 글 모두의 고침을 함께 넘긴다 —
`releases/latest` 는 모든 위협의 글이 함께 가리킨다. 첫 화면의 꼴은 조건이 붙어 있다: *빠른 검사* 줄은 디스크 전체를 보는
룰(지금은 Log4j)이 다른 룰과 함께 있을 때만 서고, 한 OS 의 룰이 20개를 넘으면 목록이 묶음 · 찾기로 바뀐다.

페이지의 사실 칸(대상 버전 · 현상 · 대상 악성코드)은 사용방법과 떼어 **1차 출처의 문장과 링크**로 적는다 — 공급사가 공지를
고치면 그 칸만 고친다. *'해당하지 않는 버전'* 을 단정하지 않는다 — Java4Shell 은 1차 뒤 Java SE 8 성능 빌드 · GraalVM EE 21.3
(바탕 Java 11 · 8 포함)이 취약으로 더해졌는데, 페이지에 남은 *'Java 8·11은 해당 취약점의 영향 대상이 아닙니다.'* 가 틀린 안내가
됐다. 대상 버전을 상류 번호로 적으면 바로 아래에 *'배포판 패키지는 상류와 다른 번호에서 영향을 받거나 고쳐집니다 — 각 배포판
공지를 보십시오.'* 한 줄과 배포판 공지 링크를 둔다 — 배포판은 새 코드 · 고친 코드를 옛 번호에 넣는다(백포트). Apache 는
Ubuntu 22.04 의 2.4.52 가 상류 영향 범위(2.4.55 ~ 2.4.70) 아래 번호인데도 영향을 받았다(새 mod_http2 를 넣었다).

**1차가 한 OS 만 담아도 다른 OS 의 받기 · 실행 줄(1 · 2)은 지우지 않는다** — 2 · 3차에 글을 고치지 않게. 그동안은 3 의
조건 문장(찾아도 그 항목이 없으면 받은 버전은 그 OS 에서 이 위협을 아직 점검하지 않는다)과 위협별 안내 절의 첫 줄(*지금은
리눅스를 봅니다* 꼴 — [1차 범위](#1차-범위))이 알린다. 위협이 처음부터 한 OS 에만 있으면(리눅스 전용 악성코드 등) 다른 OS 의 받기 ·
실행 줄을 뺀다.

```text
<위협 이름>(<CVE>) 점검도구 사용방법

1. 내려받기
   https://github.com/ESTsecurity/remedy/releases/latest 에서 운영체제에 맞는 파일 하나를 받습니다.
   - Windows 10 · 11 · Server 2016 이상(64비트): remedy-windows-x64.zip
   - Linux x86_64(RHEL 계열 · Debian · Ubuntu · Alpine): remedy-linux-x64.tar.gz
   같은 곳의 SHA256SUMS 로 받은 파일이 배포한 파일인지 확인할 수 있습니다.
2. 실행
   - Windows: 압축을 풀고 remedy.exe 를 실행합니다. 'Windows의 PC 보호' 창이 뜨면 위 주소에서 받은 파일이 맞는지 확인한 뒤
     [추가 정보] → [실행] 을 누릅니다. 관리자 권한 없이 열리면 첫 화면의 '관리자 권한으로 다시 열기' 를 고릅니다.
   - Linux: tar -xzf remedy-linux-x64.tar.gz && cd remedy-linux-x64 && sudo ./remedy
   설치하지 않습니다. 검사는 아무것도 바꾸지 않고, 치료는 화면에서 따로 승인할 때만 합니다.
3. 점검
   먼저 이 취약점의 항목이 있는지 봅니다 — 첫 화면 목록에서 CVE 번호(<CVE>)가 든 항목('<룰 이름>')을 찾고, 목록 대신 묶음이
   보이면 '이름 · 제품 · CVE 로 찾기' 에 그 CVE 번호를 넣습니다. 그 항목이 있으면 '빠른 검사'(그 줄이 없으면 '모두 검사만
   하기')가 이 취약점을 함께 점검하고, 이 취약점만 보려면 그 항목을 고릅니다. 찾아도 없으면 받은 버전은 이 운영체제에서
   이 취약점을 아직 점검하지 않습니다 — 그때 빠른 검사의 결과(해당 없음 · 취약한 곳 없음)는 이 취약점의 결과가 아닙니다.
   운영체제마다 점검하는 범위는 <위협별 안내의 고정 주소> 에 있습니다.
4. 결과
   - 취약: 고친 버전으로 올리고(지원이 끝났거나 고친 버전이 아직 없으면 아래 주소의 '꼭 할 일' 에 적은 방법으로 막고)
     그 프로그램(서비스)을 다시 시작합니다.
   - 확인 필요 · 다 보지 못함: 화면의 '확인이 필요한 항목' 과 '주의' 줄이 적은 경로와 까닭을 직접 확인합니다.
   - 해당 없음 · 취약한 곳 없음: 점검할 프로그램이 없거나, 이 도구가 보는 범위에서 찾지 못했다는 뜻입니다.
   판정 기준 · 보는 자리 · 꼭 할 일: <위협별 안내의 고정 주소>
5. 새 버전
   점검 범위를 계속 넓혀 갑니다. 같은 주소에 새 버전이 나오면 다시 받아 새 폴더에 풀고 다시 점검하십시오.
   새 버전 소식은 <위협별 안내의 고정 주소> 의 대응 기록과 GitHub 저장소의 Watch → Custom → Releases 로 받을 수 있습니다.
```

악성코드 전용백신이면 틀 첫 줄의 '점검도구' 를 '전용백신' 으로 바꿔 제목을 `<위협 이름>(<CVE>) 전용백신 사용방법` 으로 하고
(CVE 가 없으면 `(<CVE>)` 를 빼 `<위협 이름> 전용백신 사용방법`), 3 ~ 5 를 이렇게 바꾼다 —
*3. 검사와 치료: 먼저 목록에서 이 위협의 항목('<룰 이름>')을 찾습니다(묶음이
보이면 '이름 · 제품 · CVE 로 찾기' 에 위협 이름을 넣습니다). 그 항목이 있으면 '빠른 검사'(그 줄이 없으면 '모두 검사만 하기')
뒤 찾은 것이 있을 때 '찾은 것 모두 치료하기' 로 치료합니다. 지운 파일은 격리해 두어 되돌릴 수 있습니다. 찾아도 그 항목이
없으면 받은 버전은 이 운영체제에서 이 위협을 아직 검사하지 않습니다 — 운영체제마다 검사하는 범위는 <위협별 안내의 고정
주소> 에 있습니다. 4. 결과(맨 아래 요약으로
읽습니다): 위협 발견(치료 완료 · 치료 안 함) · 일부 실패(까닭을 풀고 다시 검사 · 치료) · 위협 없음 · 해당 없음(검사할
경로가 이 기계에 없습니다) · 다 보지 못함 — 치료한 뒤 꼭 할 일은 <위협별 안내의 고정 주소> 에 있습니다. 5. 새 버전: 같은
주소에서 다시 받아 다시 검사하십시오. 치료한 옛 폴더는 지우지 마십시오(복원에 필요합니다). 새 버전 소식은 <위협별 안내의
고정 주소> 의 대응 기록과 GitHub 저장소의 Watch → Custom → Releases 로 받을 수 있습니다.*

**예 — Java4Shell(CVE-2026-114938)** 의 칸: `<위협 이름>(<CVE>)` = *Java4Shell(CVE-2026-114938)* · `<룰 이름>` = *Java4Shell 점검
(CVE-2026-114938)*(1 ~ 3차 같은 이름) · `<위협별 안내의 고정 주소>` =
<https://github.com/ESTsecurity/remedy/blob/main/docs/%EC%9C%84%ED%98%91%EB%B3%84-%EC%95%88%EB%82%B4.md#java4shell>. 사실 칸은
OpenJDK 공지(<https://openjdk.org/groups/vulnerability/advisories/2026-11-17>)와 Oracle 위험 표
(<https://www.oracle.com/security-alerts/cspunov2026.html>)의 문장과 링크로 적는다.

## main 이 앞설 때 — 긴급 가지

버전 검사(`ci/version-check.sh`)는 첫 부모 역사에서 가장 가까운 **정식 태그**(공개 전 초안의 태그도 든다)와 엔진을 견준다.
그래서 main 에 그 태그 뒤의 엔진 변경이 있으면 rules 태그가 멈춘다 — 2026-11-17 21:29(PR #100 병합)부터 v1.23.0 태그를 민
11-18 07:45 까지가 그랬다(공개는 08:06). 반대로 정식 태그를 민 뒤 공개 전에 main 에서 민 rules 태그는 검사를 지나, 공개되지
않은 엔진을 실은 채 지어진다. 둘 다 이 길로 간다.

**먼저 가린다(단계 0 전).** `git fetch origin --tags --prune --prune-tags`(원격에서 지운 태그를 로컬에서도 지운다 — 여러
작업이 함께 쓰는 기계에서 로컬에만 있는 태그, 곧 `git tag` 에는 있고 `git ls-remote --tags --refs origin` 에는 없는 것이 있으면
`--prune-tags` 를 빼고 돌린다 · 아래 고리가 원격에 있는 태그만 본다) 뒤 `L=$(gh release view --json tagName -q .tagName)`(지금
Latest). 다음 가운데 하나라도 맞으면 처음부터 이 길로 간다 — `git diff --quiet "$L" origin/main -- crates Cargo.toml Cargo.lock
rust-toolchain.toml .cargo/config.toml` 가 1(다르다) · `git tag --contains "$L"` 에 **L 과 다른 커밋**을 가리키는 원격 태그(L
뒤에 민 rc · 정식 태그)가 있다 · `gh release list` 에 초안(Draft)이 있다 · L 이 main 에 없다(긴급 가지로 낸 Latest 를 아직
main 에 합치지 않았다 — L 에서 가지를 내 이어 간다). 평소 경로의 정식 태그는 rc 커밋에 달리므로 L 의 rc 태그도 `--contains`
에 나온다 — 그것은 L 자신이다. 커밋으로 가린다:

```bash
R=$(git ls-remote --tags --refs origin | sed 's#.*refs/tags/##')
for t in $(git tag --contains "$L"); do
  printf '%s\n' "$R" | grep -qxF "$t" || continue
  [ "$(git rev-list -n1 "$t")" = "$(git rev-list -n1 "$L")" ] || echo "앞선 태그: $t"
done
git merge-base --is-ancestor "$L" origin/main || echo "L 이 main 에 없다: $L"
```

1. `git switch -c emergency-<위협> "$L"` — 그 위에서 단계 1 · 2(룰 · 하네스 · 잠금 · 위협 표 · README · 위협별 안내 · 업데이트
   내역 칸 · 룰 버전 · 같은 공지면 remedy-net 기준 데이터 룰 · 커밋 전 검사)를 한다. 룰 버전과 고치는 룰의 `version` 은 L 과 main 둘보다 높게 잡는다
   (`git show origin/main:plugins/RULES-VERSION` · `git show origin/main:plugins/versions.lock.json`).
2. 가지를 밀고 **그 머리에서 CI 를 돌린다** — `gh workflow run ci.yml --ref emergency-<위협>`. PR 의 CI 는 main 과 합친 결과를
   시험하고, 충돌이 있으면 돌지도 않는다. 그 실행의 linux · windows 가 초록이고 `bash ci/version-check.sh rules-<룰 버전>` 이
   통과하면 그 머리에 `rules-<룰 버전>` 태그를 단다. 태그를 달기 전에는 main 을 가지에 합치지 않는다(가지 머리에 main 의
   엔진이 들어와 버전 검사에서 멈춘다). 이후는 단계 4 ~ 7 그대로다.
3. 공개 뒤 PR(그 가지 → main)을 열어 충돌(`plugins/RULES-VERSION` · `versions.lock.json` · 위협 표 · README · 위협별 안내 · 업데이트
   내역 · remedy-net 기준 데이터 룰 — 데이터 룰의 충돌을 풀었으면 다시 서명 · 잠금)을 풀고, CI 가 초록이면 **병합 커밋으로** 병합한다(squash · rebase 금지 — 태그 커밋이 main 역사에 남아야 한다). 병합 뒤
   main 의 `plugins/` 가 긴급 태그와 다르면 main 의 룰 버전이 긴급 출시보다 **높아야** 한다 — 지금 버전 검사는 첫 부모 역사만
   봐서 병합으로 들어온 긴급 태그를 지나친다(보완 준비 중). 사용방법 글은 이 병합 뒤에 넘긴다 — 그 전에는 main 의 위협별
   안내에 그 절 · 고정 주소가 없다.
4. main 에 진행 중인 출시(L 뒤의 rc · 정식 태그나 초안)가 있으면 그 rc 커밋의 정식 태그는 공개하지 않는다 — 3 의 병합 커밋에서
   rc 부터 다시 낸다. 정식 태그를 이미 밀었으면 그 초안과 태그를 지운 뒤 다시 낸다. 그 출시가 Latest 가 되면 긴급 룰이 빠진
   파일로 돌아가기 때문이다 — 공개 직전 검사(단계 6)가 이것을 막는다.

**아직 리허설하지 않은 길이다.** 처음 쓸 때는 2 에서 버전 검사 결과를 먼저 보고 태그를 단다.

**단계 0 ~ 2 에서 걸리는 것**(2026-11-19 모의 1차 둘 — 새 작업자가 이 문서로 Apache 리눅스 룰을 지었고 `cargo xtask all` 의

문서만으로 48.9분에 커밋 전 검사 가운데 `cargo xtask all` · `leaks` 까지 갔다 — 모의라 fmt · clippy · 전체 시험 · deny 는 돌리지
않았으므로 이 값을 시간 목표 표의 'PR 전' 줄과 그대로 견주지 않는다)

- **공급사 추적기** — 리눅스 패키지면 Debian · Ubuntu · Red Hat · Rocky · AlmaLinux · Oracle · CentOS Stream · Fedora ·
  Amazon(ALAS) · SUSE · Alpine 을 다 본다(앞선 Apache 룰이 가른 공급사 — `plugins/apache-http2-check-linux/RELEASE.md`). 공지가
  아직 없는 곳은 6 으로 두고 대기열에 *받지 못함 · 본 시각(분)* 을 적는다. 웹 화면이 스크립트 · 봇 차단으로 열리지 않으면 기계용
  응답을 쓴다(2026-11-19 모의에서 쓴 자리 — Rocky 는 `apollo.build.resf.org/api/v3/advisories/<RLSA>`, Fedora 는 Bodhi 의 JSON,
  Red Hat 은 `access.redhat.com/hydra/rest/securitydata/cve/<CVE>.json`, 공지를 내지 않는 CentOS Stream 은 그 패키지 spec 의
  `%changelog`).
- **RPM epoch** — RPM 공지는 판을 epoch 없이 적는다. 그 배포판 이미지에 패키지를 깔아 `rpm -q --qf '%{EPOCHNUM}:%{VERSION}-%{RELEASE}\n'
  <패키지>` 로 epoch 를 재고 `rpm_version_lt` 값에 붙인다. Amazon Linux 의 mod_http2 는 epoch 가 1 이다 — `0:` 으로 적으면 영향 판
  `1:2.4.69` 가 고친 판보다 높게 읽혀 0(거짓 양호)이 된다.
- **하네스 범위** — 룰의 판 줄마다 2(또는 6)와 0 을 하나씩 둔다 — 특히 백포트(Ubuntu 22.04) · 스트림(RHEL EUS) · epoch 줄. 직접
  빌드는 룰이 읽는 파일만 바꾼 자리 채우기로 끝내지 말고 실물(공식 이미지의 실행 파일 판)과 함께 잰다.
- **remedy-net 기준** — 고치는 룰이 remedy-net 기준과 같은 공지를 쓰면(지금 `php2shell-check-*` · `node2shell-check-*` ·
  `apache-http2-check-linux` — `xtask/src/netcriteria.rs` 머리가 견주는 칸을 적는다) `plugins/remedy-net-criteria/` 의 그 파일을
  룰과 같은 값으로 맞추고, 그 데이터 룰의 `version` 을 올리고 `RELEASE.md` 에 버전 절을 더한 뒤 개발 키로 다시 서명한다. 룰에
  공급사 · 배포판 줄을 더했으면 기준에도 그 줄을 더한다. `plugin-lock --write` 는 룰 · 기준을 다 고친 뒤 한 번 돈다 — 같은
  버전을 잠근 뒤 또 고치면 `--write` 도 거부하니, 잠금 파일을 가지를 낸 커밋의 것으로 되돌리고(`git checkout
  "$(git merge-base HEAD origin/main)" -- plugins/versions.lock.json` · 긴급 가지면 `"$L"`) 다시 돈다. Apache 기준에 지금과 다른 고친
  판을 더하면 `xtask/src/netcriteria.rs` 의 시험 `a_changed_apache_value_is_caught`(서로 다른 고친 판의 수 18 을 박아 둠 —
  `same_as` 는 일부러 틀린 값을 넣어 잡는지만 보므로 룰 `version` 을 올려도 깨지지 않는다)가 깨진다. `cargo xtask all` 은 그
  시험을 돌리지 않는다 — 커밋 전 검사의 `cargo test --workspace` 나 PR CI 에서 드러난다. 고치려면 `xtask/` 를 바꿔야 하는데
  긴급 경로는 `xtask/` 0줄이 조건이다(위 *쓰는 조건* — 엔진 변경은 아니다). 1차는 그 공급사를 6 으로 두고 대기열(평소 경로)에
  넣는다.
- **검사가 막는 것과 못 막는 것** — `same_as` 와 기준에 이미 있는 값이 룰과 어긋나면 `net-criteria` 가, `version` 을 빠뜨리면
  `plugin-lock` 이 막는다(둘 다 `cargo xtask all` · PR 의 CI). 룰에 새로 더한 줄이 기준에서 빠진 것은 다 막지 못한다 —
  `url.json` 은 기준의 줄이 룰에 있는지만, `apache.json` 은 고친 판의 모음과 기준 쪽 공급사만 본다(RHEL · Rocky 처럼 고친
  판이 같은 공급사 줄은 빠뜨려도 지나간다). 다시 서명하지 않은 것도 둘 다 보지 않는다 — 아래 개발 빌드 확인이 거절한다. 같은
  제품이라도 다른 공지의 룰이면 기준을 고치지 않는다(이 검사가 보지 않고, remedy-net 몫은 엔진 일이라 다음 차수 · 평소 경로).
- **기준을 고치면 remedy-net 판정도 바뀐다** — PR 전에 remedy-net 개발 빌드(`musl-dev-build.sh <폴더> --net`)로 잰다.
  - Apache(`apache.json`) — [`개발-안내.md`](개발-안내.md#출시-검증) *출시 검증* 의 `net-apache-verify.sh`(약 6분 · `--anchor`
    는 `dev_sign.public_key` 파일의 둘째 줄). 판정이 바뀐 칸의 기대값을 함께 고친다 — 이미지 칸은 `net-apache-cases.txt`,
    컨테이너 칸은 `net-apache-dind.sh`, url 칸은 `net-apache-verify.sh` 의 `url_case` 줄.
  - PHP · Node(`url.json` · `baseline.json`) — PR 전 판정 하네스가 없다. 서명은 그 개발 빌드를 `REMEDY_LANG=ko
    REMEDY_NET_CRITERIA=plugins/remedy-net-criteria REMEDY_NET_ANCHOR=<공개키 둘째 줄> <폴더>/remedy-net url --help` 로 불러
    `기준(PHP):` 줄이 서는지로 본다(서명이 낡으면 *이 자리에서 확인하지 못했다*). 판정의 차이는 미룬 rc 묶음의 `net-ab` 가 잰다.
  - 미룬 rc 묶음의 `net-ab` 에서 그 값이 바꾼 경우의 차이는 의도한 변경이다(업데이트 내역 칸에 적는다). `net-apache` 는 기대값
    표로 판정하므로 PR 에서 표를 고쳤으면 통과해야 한다 — 실패는 실패다.
- **개발 키 서명** — 키 · 암호 파일의 자리는 `.cargo/host.yml` 의 `dev_sign`, 명령은 [`개발-안내.md`](개발-안내.md#서명) *서명*
  이다. `--signed-at` 은 빠뜨릴 수 없다.
- **컨테이너 하네스** — 서비스를 띄워 프로세스를 재는 칸은 `--cap-add SYS_PTRACE` 로 띄운다. 컨테이너의 root 는 그 권한이 없어
  다른 사용자(`www-data` 등)로 도는 일꾼의 `/proc/<pid>/maps` 를 못 읽고, 그것만으로 *다 보지 못함*(6)이 된다. 근거(경로 · 소켓
  이름)는 화면이 아니라 결과 폴더(`--out-dir`)의 결과 파일에서 찾는다 — 치료 룰의 드라이런 화면은 계획만 적는다
  (`testbed/harness/linux/ebury-verify.sh` 꼴).
- **G1(청정 코퍼스)** — G1 시험(`plugins_find_nothing_in_clean_environments`)은 손으로 적는 목록(`crates/remedy-core/tests/corpus.rs`
  의 `plugins()`)만 돈다. 그 목록을 고치면 엔진 변경으로 세므로 새 룰은 긴급 경로로 넣을 수 없다 — 그 대신 `corpus/clean` 의
  그 OS 스냅샷(`.json.gz` 를 푼 것)마다 `remedy evaluate --artifacts <스냅샷.json> --plugin plugins/<id>/plugin.yaml --out <파일>`
  이 모두 종료 0 인지 보고 그 룰의 `RELEASE.md` 게이트에 적는다. 그 OS 의 스냅샷을 다 돈다 — 리눅스는 `docker-*` · `wsl-*`,
  Windows 는 `win10x64-*`(Apache 리눅스 룰의 G1 줄이 이 꼴이지만 `docker-*` 13개만 돌았다). 목록에 넣는 것은 다음 평소 출시의
  대기열이다.

  ```bash
  # 리눅스 룰 — 저장소 루트 · <remedy> 는 개발 빌드
  T=$(mktemp -d); for f in corpus/clean/docker-*.json.gz corpus/clean/wsl-*.json.gz; do
    gzip -dc "$f" >"$T/a.json"
    <remedy> evaluate --artifacts "$T/a.json" --plugin plugins/<id>/plugin.yaml --out "$T/s.json" >/dev/null 2>&1
    echo "$? $f"
  done
  ```

- **worktree 에서 일하면** — [`개발-안내.md`](개발-안내.md#커밋하기-전에) *커밋하기 전에* 의 worktree 단락(커밋하지 않는
  `.cargo/*.yml` · xtask 를 그 자리에서 짓기 · leaks 머리줄).

## 출시 전 필수 점검

**내려받은 초안 그 파일로 잰다** — 공개하는 것이 그 파일이다. 받은 뒤에는 배포 워크플로를 다시 돌리지 않는다(자산이
바뀐다).

| # | 무엇 | 어떻게 |
|---|---|---|
| ① | 새 룰이 계약대로인가 | 새 룰의 하네스를 정식 파일의 실행 파일과 **배포 키로 서명된** 룰로 |
| ② | 정식 파일이 온전한가 | 체크섬(리눅스는 스크립트가 받은 `SHA256SUMS` 로 · Windows 는 README 의 한 줄로 zip 을) · 두 OS 의 엔진과 동반 프로그램 버전 · 꾸러미의 룰 전부 서명 · 판정 기준 줄 · Windows 실행 파일 둘의 코드서명(유효 · 주체 · 타임스탬프) |
| ③ | 기존 동작이 그대로인가 | 리눅스 — 깨끗한 컨테이너에서 지난 공개본과 메뉴 '모두 검사' 의 **종료 코드가 같고** 화면 차이가 새 룰의 줄뿐 · Windows — 랩의 시연 게이트와 메뉴 하네스 |
| ④ | **G9 — 룰의 검체 오탐**(`AGENTS.md` 의 릴리스 전 게이트) | 새 룰 · 고친 룰에 YARA 가 있으면 `cargo xtask yara` 로 정상 파일 코퍼스에 전수. 치료 · 탐지 룰은 **맞음 0**, 점검 룰은 맞은 파일이 **모두 그 뜻의 파일**(설정 · 실행 파일)인가 · 못 훑은 것은 수와 사유. 단계 1 끝에 저장소의 `.yar` 로 쟀으면 초안 꾸러미의 `.yar` 가 잰 것과 같은 바이트인지 견준다 |
| ⑤ | 넘길 파일 = 시험한 파일 | 공개 전 — ①~④ 에서 잰 파일이 초안의 지금 자산이다 · 공개 뒤 — 익명으로 받은 바이트가 같다(다르면 곧바로 지난 공개본을 다시 Latest 로 두고 보고 — 1차였으면 다운로드 페이지 글을 내리도록 회사에 알린다) |

**치료 룰이면 ⑥** — 치료 → 다시 검사(0 또는 6) → 복원 → 원래 파일과 같은 바이트로 돌아온다. 새 룰의 하네스에 그 칸을 둔다
(`testbed/harness/linux/cwpdoor-verify.sh` 의 C 칸이 그 꼴이다).

```bash
# ④ G9 — 저장소 루트. 정상 파일 코퍼스는 그 룰이 보는 배포판의 파일 시스템(`/etc` · `/usr` 등)이다.
cargo xtask yara --rules plugins/<룰>/rules --rule <YARA 규칙 이름> --scan <정상 파일 폴더> --expect clean
```

`--rules` 는 `.yar` 가 든 `rules/` 폴더다. `--rule` 은 이름 하나만 받는다 — 규칙마다 따로 돌린다(2026-11-19 모의 1차 — 정상
설치 8개의 파일 47,834개에 규칙당 약 160초). 규칙이 여럿이면 G9 는 룰의 `.yar` 가 정해진 단계 1 끝에 저장소의 `.yar` 로
돌리고(PR CI 를 기다리는 동안도 된다), ④ 에서는 초안 꾸러미의 `.yar` 가 잰 것과 같은 바이트인지 견준다(1.17.0 의 꼴) — 초안
뒤에 돌리면 필수 점검 예산 11분을 넘는다. 정상 설치의 파일을 꺼내는 길: 그 배포판 이미지에 소프트웨어를 깐 컨테이너를
`docker export` 해 `/etc` · `/usr` 를 Windows 에서 보이는 폴더에 푼다 — `bash testbed/harness/linux/g9-corpus.sh <꺼낼 폴더>
<이미지>…`. 리눅스 링크는 Windows 가 열지 못해 *못 훑음* 으로 세어지니 그 수를 스크립트가 적은 링크 수와 대조한다(*안 맞음*
에는 스크립트가 꺼낸 폴더에 남기는 `<이미지>.tar-errors.txt` 가 이미지마다 하나씩 더해진다). 점검 룰은 `--expect clean` 이 맞은
것을 '오탐' 으로 적어도, 그것이 그 규칙이 뜻한 파일인지로 판정한다.

```bash
# ①②③ 리눅스(WSL · 저장소 루트) — 랩과 나란히 돌리지 않는다. --harness 는 빠뜨릴 수 없다(리눅스 룰이 아니면 none)
bash testbed/harness/linux/emergency-checks.sh --new <받은 remedy-linux-x64.tar.gz> \
     --prev <지금 Latest 의 remedy-linux-x64.tar.gz> --out <결과 폴더> \
     --harness testbed/harness/linux/<룰>-verify.sh
```

```powershell
# ②③ Windows(호스트 · 저장소 루트) — 내려받은 zip 을 푼 폴더로. 끝에 랩을 되돌린다
.\testbed\harness\host\Invoke-EmergencyChecks.ps1 -Package <푼 폴더>\remedy-windows-x64 -LogDir <결과 폴더>
```

**Windows 룰이면 ① 은 그 룰의 하네스를 같은 푼 폴더로 따로 돌린다** — 위 스크립트는 새 룰의 하네스를 돌리지 않는다(리눅스
쪽은 `--harness none`). 예: `.\testbed\harness\host\Invoke-ApacheVerify.ps1 -Package <푼 폴더>\remedy-windows-x64 -ApacheZip
<zip> -LogDir <결과 폴더>`. 둘 다 랩 VM 을 쓰므로 나란히 돌리지 않는다(이 하네스는 놓은 것을 스스로 치운다).

```bash
# ⑤ 공개 3분 뒤
bash testbed/harness/linux/release-anon-check.sh rules-<룰 버전> <①~④ 에서 잰 파일 폴더> <빈 작업 폴더>
```

두 스크립트는 하나라도 실패하면 종료 1 이다. `summary.txt` 의 줄이 단계마다 통과 · 실패와 그 까닭을 적는다.

③의 화면 차이는 기계가 판정하지 않는다 — `scan-all/*.diff` 가 **새 룰의 메뉴 줄 · 번호 밀림 · 그 룰의 검사 덩어리 ·
요약 한 줄**뿐인지 본다. 1.15.0 은 86줄이 전부 그것이었다.

## 뒤로 미루는 것 — 공개 뒤 24시간 안

| 무엇 | 왜 미룰 수 있나 |
|---|---|
| 두 OS 의 rc 묶음 A/B(지난 공개본 대 공개된 판) | 엔진 코드가 그대로다 — 기존 룰의 판정은 ③ 이 대표 경우로 보고, 묶음이 나머지 경우를 본다 |
| 콘솔 기준선 재캡처 · 화면 문서의 룰 버전 줄 | CI 는 문서와 기준선을 서로 견줄 뿐 실행 파일과 견주지 않는다 — 그 사이 기준선은 지난 판의 화면이다(머리말 첫 줄의 룰 버전) |

rc 묶음은 [`개발-안내.md`](개발-안내.md) "출시 검증" 의 4 와 같은 명령이다 — `--new` · `-Package` 에 **공개한 그
파일**을 준다. 리눅스를 먼저(시료를 받는다), WSL 캐시를 비운 뒤 Windows. 룰만 바꾼 출시이므로 A/B 의 **다름도
실패**다(엔진이 그대로인데 기존 룰의 종료 코드가 바뀌었다는 뜻이다). 다만 remedy-net 기준 데이터 룰을 고친 출시는
`net-ab` 에서 그 값이 바꾼 경우의 차이만 의도한 변경이다(`net-apache` 는 기대값 표라 통과해야 한다) — 그 밖의 다름은
실패다. 콘솔 재캡처는 두 언어를 한 번에 받는 `testbed/harness/host/Invoke-ConsoleRecapture.ps1`(랩 VM) 다음 `testbed/harness/linux/console-recapture.sh`(WSL)로 하고,
`cargo xtask console-diff` 로 견준 뒤 기준선과 화면 문서를 후속 PR 로 올린다.

**미룬 검증이 실패하면** 다음 출시를 멈추고 보고한다. 기본은 고친 판을 새 rules 출시로 **앞으로** 내는 것이다 — 공개한
Release 는 불변이라 그 파일을 바꿀 수 없고, 고친 판은 새 버전이다. 지난 공개본을 다시 Latest 로 두는 것(`gh release edit <지난
공개본의 태그> --latest`)은 기존 항목을 해친 때뿐이다(룰만 바뀐 출시의 A/B 다름 — 기준 데이터 룰의 `net-ab` 예외
말고 — 이 그 경우다). 되돌리면 다운로드 페이지 글의
`releases/latest` 가 그 위협의 룰이 없는 버전을 준다 — 1차를 되돌렸으면 그 글을 내리도록 회사에 알린다.
