# 긴급 대응 — 룰만 바뀐 출시를 빨리 내는 길

공개 시연이나 실제 공격이 있는 취약점 · 퍼지는 악성코드에 **룰을 더하거나 고쳐** 빨리 내야 할 때 쓴다. 평소 출시는
rc 를 내려받아 두 OS 의 rc 묶음(A/B · 약 54분)을 **공개 전에** 돌린다. 긴급 경로는 공개 전에 **필수 점검**(새 룰 하네스 ·
정식 파일 · 기존 동작 · G9 · 넘길 파일)만 보고, rc 묶음과 콘솔 기준선은 **공개 뒤 24시간 안에** 돌린다.

**처음 쓴 날 잰 값** — 1.15.0(Apache CVE-2026-119618): 룰 PR 의 CI 시작 → 공개 **47분 3초**. 같은 일을 평소 경로로 낸
1.14.0 은 1시간 50분 36초였다.

## 쓰는 조건

| | |
|---|---|
| **쓴다** | 바뀐 것이 룰(`plugins/`) · 하네스 · 문서와 버전 줄뿐이다 — `crates/` · `xtask/` 0줄(PR 에서 `git diff --stat origin/main...HEAD -- crates/ xtask/`) |
| **쓰지 않는다** | 엔진을 고쳐야 한다 → 평소 경로(rc 와 A/B 를 공개 전에) |
| **승인** | 건마다 사용자가 정한다 — 요청문에 함께 적을 수 있다(아래 견본). "긴급 · 빨리" 라는 말만으로는 승인이 아니다 |
| **멈춘다** | 필수 점검이 하나라도 실패하면 공개하지 않는다 · 1차 출처(공급사 · 상류 공지 · 배포판 추적기)가 없으면 룰을 짓기 전에 사용자에게 묻는다 |
| **고친 판이 없다** | 영향 판을 *취약*(2)으로 낼지 *확인 필요*(6)로 낼지, 완화 설정을 흔적으로 볼지를 사용자가 정한다(카드) — 고친 판이 나오면 룰을 다시 낸다 |

**룰이 보이는 시간.** `AGENTS.md` 는 사고 대응 중에 배포보다 룰이 먼저 보이는 것을 막으라고 한다 — 대응 중인 위협의
룰은 공개 저장소 밖에서 짓고 **배포하는 커밋에 함께** 올린다. 긴급 경로도 같다: 룰 · 하네스 · 검사를 로컬에서 다 마친 뒤
PR 을 올리고, 그때부터 공개까지(1.15.0 은 47분)가 룰이 먼저 보이는 시간이다. 이 시간을 줄이는 것이 이 경로의 목적이기도
하다.

## 요청하는 법

AI 작업자에게 이렇게 맡긴다 — 이 문서를 가리키면 단계를 다시 설명하지 않아도 된다.

```text
긴급: <위협 이름 · CVE> — <공지 링크 또는 붙여 넣은 설명>.
docs/긴급-대응.md 의 긴급 경로로 낸다(이 건의 긴급 출시를 승인한다).
```

받은 작업자가 사용자에게 묻는 것은 결정이 필요한 칸뿐이다 — 판정 정책(예: 설정 흔적이 없으면 확인 필요인가),
고친 판을 정하지 못한 배포판의 처리, 대상 OS 의 차례. 사실(영향 판 · 고친 판 · 악용 조건)은 1차 출처에서 직접 잰다.

## 출시 전 필수 점검

**내려받은 초안 그 파일로 잰다** — 공개하는 것이 그 파일이다. 받은 뒤에는 배포 워크플로를 다시 돌리지 않는다(자산이
바뀐다).

| # | 무엇 | 어떻게 |
|---|---|---|
| ① | 새 룰이 계약대로인가 | 새 룰의 하네스를 정식 파일의 실행 파일과 **배포 키로 서명된** 룰로 |
| ② | 정식 파일이 온전한가 | 체크섬(리눅스는 스크립트가 받은 `SHA256SUMS` 로 · Windows 는 README 의 한 줄로 zip 을) · 두 OS 의 엔진과 동반 프로그램 버전 · 꾸러미의 룰 전부 서명 · 판정 기준 줄 |
| ③ | 기존 동작이 그대로인가 | 리눅스 — 깨끗한 컨테이너에서 지난 공개본과 메뉴 '모두 검사' 의 **종료 코드가 같고** 화면 차이가 새 룰의 줄뿐 · Windows — 랩의 시연 게이트와 메뉴 하네스 |
| ④ | **G9 — 룰의 검체 오탐**(`AGENTS.md` 의 릴리스 전 게이트) | 새 룰 · 고친 룰에 YARA 가 있으면 `cargo xtask yara` 로 정상 파일 코퍼스에 전수. 치료 · 탐지 룰은 **맞음 0**, 점검 룰은 맞은 파일이 **모두 그 뜻의 파일**(설정 · 실행 파일)인가 · 못 훑은 것은 수와 사유 |
| ⑤ | 넘길 파일 = 시험한 파일 | 공개 전 — ①~④ 에서 잰 파일이 초안의 지금 자산이다 · 공개 뒤 — 익명으로 받은 바이트가 같다(다르면 곧바로 지난 공개본을 다시 Latest 로 두고 보고) |

**치료 룰이면 ⑥** — 치료 → 복원 → 원래 파일과 같은 바이트로 돌아온다. 새 룰의 하네스에 그 칸을 둔다
(`testbed/harness/linux/cwpdoor-verify.sh` 의 C 칸이 그 꼴이다).

```bash
# ④ G9 — 저장소 루트. 정상 파일 코퍼스는 그 룰이 보는 배포판의 파일 시스템(`/etc` · `/usr` 등)이다.
cargo xtask yara --rules plugins/<룰>/rules --rule <YARA 규칙 이름> --scan <정상 파일 폴더> --expect clean
```

`--rules` 는 `.yar` 가 든 `rules/` 폴더다. 정상 설치의 파일을 꺼내는 길: 그 배포판 이미지에 소프트웨어를 깐 컨테이너를
`docker export` 해 `/etc` · `/usr` 를 Windows 에서 보이는 폴더에 푼다 — `bash testbed/harness/linux/g9-corpus.sh <꺼낼 폴더>
<이미지>…`. 리눅스 링크는 Windows 가 열지 못해 *못 훑음* 으로 세어지니 그 수를 스크립트가 적은 링크 수와 대조한다. 점검 룰은 `--expect clean` 이 맞은 것을 '오탐' 으로 적어도, 그것이 그 규칙이
뜻한 파일인지로 판정한다.

```bash
# ①②③ 리눅스(WSL · 저장소 루트) — 랩과 나란히 돌리지 않는다. --harness 는 빠뜨릴 수 없다(리눅스 룰이 아니면 none)
bash testbed/harness/linux/emergency-checks.sh --new <받은 remedy-linux-x64.tar.gz> \
     --prev <지금 Latest 의 remedy-linux-x64.tar.gz> --out <결과 폴더> \
     --harness testbed/harness/linux/<룰>-verify.sh
```

```powershell
# ②③ Windows(호스트 · 저장소 루트) — 내려받은 zip 을 푼 폴더로. 끝에 랩을 되돌린다
.\testbed\harness\host\Invoke-EmergencyChecks.ps1 -Package <푼 폴더>\remedy-windows-x64 -LogDir <결과 폴더>
```

**Windows 룰이면 ① 은 그 룰의 하네스를 같은 푼 폴더로 따로 돌린다** — 위 스크립트는 새 룰의 하네스를 돌리지 않는다(리눅스
쪽은 `--harness none`). 예: `.\testbed\harness\host\Invoke-ApacheVerify.ps1 -Package <푼 폴더>\remedy-windows-x64 -ApacheZip
<zip> -LogDir <결과 폴더>`. 둘 다 랩 VM 을 쓰므로 나란히 돌리지 않는다(이 하네스는 놓은 것을 스스로 치운다).

```bash
# ⑤ 공개 3분 뒤
bash testbed/harness/linux/release-anon-check.sh v<버전> <①~④ 에서 잰 파일 폴더> <빈 작업 폴더>
```

두 스크립트는 하나라도 실패하면 종료 1 이다. `summary.txt` 의 줄이 단계마다 통과 · 실패와 그 까닭을 적는다.

③의 화면 차이는 기계가 판정하지 않는다 — `scan-all/*.diff` 가 **새 룰의 메뉴 줄 · 번호 밀림 · 그 룰의 검사 덩어리 ·
요약 한 줄**뿐인지 본다. 1.15.0 은 86줄이 전부 그것이었다.

## 뒤로 미루는 것 — 공개 뒤 24시간 안

| 무엇 | 왜 미룰 수 있나 |
|---|---|
| 두 OS 의 rc 묶음 A/B(지난 공개본 대 공개된 판) | 엔진 코드가 그대로다 — 기존 룰의 판정은 ③ 이 대표 경우로 보고, 묶음이 나머지 경우를 본다 |
| 콘솔 기준선 재캡처 · 화면 문서의 버전 줄 | CI 는 문서와 기준선을 서로 견줄 뿐 실행 파일과 견주지 않는다 — 그 사이 기준선은 지난 판의 화면이다 |

rc 묶음은 [`개발-안내.md`](개발-안내.md) "출시 검증" 의 4 와 같은 명령이다 — `--new` · `-Package` 에 **공개한 그
파일**을 준다. 리눅스를 먼저(시료를 받는다), WSL 캐시를 비운 뒤 Windows. 룰만 바꾼 출시이므로 A/B 의 **다름도
실패**다(엔진이 그대로인데 기존 룰의 종료 코드가 바뀌었다는 뜻이다). 콘솔 재캡처는 두 언어를 한 번에 받는
`testbed/harness/host/Invoke-ConsoleRecapture.ps1`(랩 VM) 다음 `testbed/harness/linux/console-recapture.sh`(WSL)로 하고,
`cargo xtask console-diff` 로 견준 뒤 기준선과 화면 문서를 후속 PR 로 올린다.

**미룬 검증이 실패하면** 다음 출시를 멈추고, 지난 공개본을 다시 Latest 로 두고(`gh release edit v<지난 버전> --latest`),
고친 판을 낼지 보고한다. 공개한 Release 는 불변이라 그 파일을 바꿀 수 없다 — 고친 판은 새 버전이다.

## 판 번호

[`개발-안내.md`](개발-안내.md) "판 번호" 그대로다 — 긴급 경로라고 다르지 않다. 새 룰은 마이너(1.14.0 → 1.15.0), 기존
룰의 판정 고침 · 고친 버전 표 갱신은 패치다. 새 룰을 패치로 내면 배포 워크플로가 태그에서 멈춘다(`ci/new-rule-minor.sh`).
룰만 바뀌어도 실행 파일이 다시 지어진다 — 버전 문자열이 바뀌기 때문이다.

## 1.15.0 — 처음 쓴 기록

**빠뜨린 것 — G9.** 이 문서의 첫 판에 G9 가 없어 1.15.0 은 G9 를 공개 전에 돌리지 않았다(1.14.0 의 OpenSSH 룰도 그랬다).
공개 뒤(2026-11-14) 돌렸다 — 정상 설치 열넷(Debian 12 · Ubuntu 24.04 · 22.04 · Rocky 9 · 8 · AlmaLinux 9 · Oracle Linux 9 ·
Amazon Linux 2023 · 2 · openSUSE Leap 15.6 · Alpine 3.22 · OpenSSH 하네스 이미지 셋)의 `/etc` · `/usr` 에 `cargo xtask yara`:

| 규칙 | 맞음 | 맞은 것 |
|---|---|---|
| `apache_h2_loadmodule` | 10 / 79,684 | 모두 mod_http2 를 싣는 설정 |
| `apache_h2_protocols` | 8 / 79,684 | 설정 5 · RHEL 계열이 까는 mod_http2 의 README 문서 3 — 룰은 YARA 를 설정 자리에만 걸어(경로식 · 글롭) 그 문서는 평가되지 않는다 |
| `apache_version_affected` | 28 / 79,684 | 모두 판 2.4.55 ~ 2.4.70 배포판의 Apache 실행 파일 · 모듈 — 룰은 패키지가 깔지 않은 직접 빌드의 `bin/httpd` 에만 건다 |
| `sshd_password_authentication_off`(1.14.0) | 0 / 90,202 | — |

못 훑은 것은 리눅스 링크뿐이다(11,660). 16 MiB 를 넘은 3개(`libicudata`)는 64 MiB 상한으로 다시 읽어 맞음 0.

**미룬 검증** — 두 OS 의 rc 묶음(지난 공개본 1.14.0 대 공개된 1.15.0)을 공개 21분 뒤 · 1시간 18분 뒤에 마쳤다. 리눅스
17단계 · Windows 17단계 모두 통과 — 하네스 여섯(Apache 55/55 포함) · A/B 는 1.14.0 의 rc 결과와 같고, 다른 것은 리눅스 메뉴에
Apache 가 든 줄뿐이다.

## 1.17.0 — 둘째 기록 (Windows 룰)

같은 Apache 건의 Windows 룰(`apache-http2-check-windows`)을 이 경로로 냈다. **PR CI 시작 → 공개 56분 54초** — CI(두 OS 26분) ·
태그 → 초안 20분 · 필수 점검 9분(리눅스 36초 · Windows 긴급 점검 7분 · 새 룰 하네스 1분).

- **G9 를 공개 전에 했다** — 진짜 Apache Lounge 2.4.71 트리 999개와 이 기계의 `C:\Windows\System32` 28,694개에 `cargo xtask yara`.
  공개할 꾸러미의 `.yar` 가 잰 것과 같은 바이트인지도 견줬다(`plugins/apache-http2-check-windows/RELEASE.md` 의 G9 줄).
- **Windows 룰의 ① 은 새 룰 하네스를 따로** 돌렸다 — `Invoke-EmergencyChecks.ps1` 은 새 룰의 하네스를 돌리지 않는다(위 명령 아래 줄).
- `leaks` 가 하네스의 가짜 키 머리를 잡았다 — 가짜 키는 키 모양이 아닌 표지로 둔다(리눅스 하네스와 같다). 공개 트리에 키 머리를
  두지 않는다.
- **미룬 검증**을 공개 1시간 34분 뒤에 마쳤다 — 리눅스 rc 묶음 17단계 · Windows 18단계(새 `apache` 단계 31/31) 모두 통과 · 콘솔
  재캡처 넷은 버전 줄뿐(새 룰은 콘솔 캡처의 꾸러미에 들지 않는다).
