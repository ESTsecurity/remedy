# 이슈 처리 — 받아서 닫기까지

버그 신고 · 오탐 신고 · 위협 지원 요청을 GitHub Issues 로 받는다. 이 문서는 **받은 이슈를 분류하고 처리하는
사람**이 읽는다 — 신고하는 사람은 양식만 채우면 된다(README *지원 · 신고*).

- **1 영업일 안에** 분류와 판단을 첫 댓글로 남긴다.
- **공개 저장소다.** 이슈 · 댓글 · 첨부 파일 · 편집 기록을 누구나 본다. 고객 자료가 올라오면 다른 일보다 먼저 가린다(§6).
- **대응 중인 위협의 룰은 공개 저장소 밖에서 짓는다.** 이슈에는 진행 단계만 적고, 출시한 뒤 릴리스 주소를 남기고 닫는다.

```text
접수 ............ 양식이 `접수` 를 붙인다
 |
 v
분류 ............ 1 영업일 안에 첫 댓글 (고객 자료가 보이면 6 먼저)
 |
 v
판단 --+--------> 이미 있는 룰 -> 받는 곳을 알리고 닫기
       +--------> 대응하지 않음 -> 까닭을 적고 닫기
       +--------> 공개 시연, 실제 공격 -> 긴급 경로 (긴급-대응.md)
       |
       v
작업 (공개 저장소 밖) -> 출시 -> 릴리스 주소를 남기고 닫기
```

## 1. 받는 것

| 양식 | 누가 | 양식이 붙이는 라벨 | 이슈에 올리지 않고 비공개로 받는 것 |
|---|---|---|---|
| 버그 신고 | 쓰는 사람 누구나 | `버그` · `접수` | 신고 묶음 · 결과 파일 · 로그 |
| 오탐 신고 | 쓰는 사람 누구나 | `오탐` · `접수` | 신고 묶음 · 결과 파일 |
| 위협 지원 요청 | 팀원 · 누구나 | `위협 지원` · `접수` | 검체 · `artifacts.json` · 고객 환경에서 본 값 |

- 비공개 경로는 [`SECURITY.md`](../SECURITY.md) 다. 보안 취약점 신고도 그쪽으로만 받는다 — 양식을 고르는 화면 맨
  아래의 링크가 그 문서다.
- **아직 공개되지 않은 위협**(비공개로 받은 검체에서만 아는 것)은 이슈로 받지 않는다. 위협 이름조차 공개 정보가 아니다 —
  비공개 경로로 받는다.
- 빈 이슈는 막혀 있다(`.github/ISSUE_TEMPLATE/config.yml`). 쓰기 권한자는 *Maintainers only* 로 빈 이슈를 열 수 있다.
- 양식의 필수 칸 · 확인 칸은 공개 저장소에서만 강제된다(GitHub). 이 저장소는 공개라 강제된다. 그래도 신고자가 확인
  칸을 체크하고 고객 자료를 붙일 수 있다 — §6 은 그때를 위한 것이다.

## 2. 분류 — 1 영업일 안에

1. 고객 자료(고객사 · 기계 · 사용자 이름, 결과 파일, 검체)가 보이면 **§6 먼저**.
2. 담당을 정하고(Assignees) `접수` 를 뗀다. 종류 라벨이 틀렸으면 고친다.
3. 같은 건이 있으면 그 이슈 번호를 적고 *중복* 으로 닫는다.
4. 판단에 모자란 것이 있으면 무엇이 필요한지 적고 `자료 대기` 를 붙인다.
5. 아래 견본으로 첫 댓글을 남긴다.

```text
분류: <버그 | 오탐 | 위협 지원> · 담당 <이름>
판단: <이미 있는 룰 | 새 룰 | 코어 작업 | 대응하지 않음> — <한 줄 까닭>
자립률: <해당 없음 | T1·T2 룰만으로 | T3 관찰 대상 없음(필요한 subject) | T3 파괴 동작 없음(필요한 Op) | T3 로직 표현 한계>
경로: <평소 — 다음 출시 | 긴급 후보 — 출시 승인자에게 알렸다 | 해당 없음>
다음: <무엇을 · 언제>
```

## 3. 판단

### 위협 지원 요청

| 차례 | 묻는 것 | 그렇다면 |
|---|---|---|
| ① | 이미 있는 룰인가 — README [다루는 위협](../README.md#다루는-위협) 표 | 그 룰이 최신 릴리스에 들었는지 [`업데이트-내역.md`](업데이트-내역.md) 로 보고, 릴리스 주소와 메뉴의 항목 이름을 답한 뒤 닫는다(§5) |
| ② | 1차 출처가 있나 — 공급사 · 상류 공지 · 배포판 보안 추적기 · 보안 업체 분석 | 없으면 `자료 대기`. 출처 없이 룰을 짓지 않는다 |
| ③ | 룰만으로 쓸 수 있나 — [설계-01](design/설계-01-아키텍처-결정.md) D10 의 세 층 | 룰만으로(T1 · T2) → 새 룰. 아니면 코어 작업(T3) — 사유 셋 가운데 무엇인지 분류 댓글에 적는다. T3 사유는 자립률의 '사람이 적는 목록' 이 된다([설계-09](design/설계-09-개발-Phase.md) *자립률*) |
| ④ | 무엇을 하는 룰인가 | 취약점은 점검 룰(아무것도 바꾸지 않는다) · 악성코드는 탐지 룰, 되돌릴 수 있게 치료할 수 있으면 치료까지([룰 작성 안내](plugin-guide/README.md)) |
| ⑤ | 공개 시연이나 실제 공격이 있나 | 있으면 **긴급 경로 후보** — ③ 에서 코어 작업(T3)이 나와도 1차는 지금 엔진으로 되는 만큼 룰만으로 낸다([`긴급-대응.md`](긴급-대응.md) *1차 범위*). 엔진 몫은 다음 차수(평소 경로). 출시를 승인하는 조직 Owner 에게 바로 알리고 `긴급 경로` 를 붙인다 — 긴급 출시는 건마다 승인을 받는다(같은 문서 *쓰는 조건*). 요청 받은 시각을 분 단위로 이슈에 남긴다(*시간 목표*). 그 밖은 평소 경로(다음 출시) |

### 버그

재현한다 → 고칠 자리(코어 · 룰 · 문서)를 적는다 → 평소 경로. 엔진을 고치는 출시는 긴급 경로를 쓰지 않는다.

### 오탐

신고자가 아직 복원하지 않았으면 복원부터 안내한다(메뉴 *치료 전으로 복원하기*). 그 뒤는 룰 작성 안내의
[오탐 신고가 들어오면](plugin-guide/40-review-checklist.md#오탐-신고가-들어오면) 다섯 단계다 — 재현 · 그 환경을 청정 코퍼스에
넣기 · 폐기 목록 · 재발 방지 조건을 출시 게이트로.

## 4. 작업 — 공개 저장소 밖에서

- **대응 중인 위협의 룰은 공개 저장소 밖에서 짓고, 배포하는 커밋에 함께 올린다**([`AGENTS.md`](../AGENTS.md)). 가지를
  push 하는 순간 공개된다. 그동안 이슈에는 `작업 중` 만 붙이고 룰의 내용(탐지 조건 · 지표)을 쓰지 않는다.
- **룰에 적는 지표는 공개 출처에 있는 것만이다.** 배포 파일이 룰을 평문으로 담아 배포가 곧 공개다 — 비공개로 받은
  검체의 지표는 룰에 넣지 않는다.
- PR 본문에 `Closes #번호` 를 쓰지 않는다 — main 에 병합해도 받는 사람에게는 아직 없다(배포는 태그로 한다). 병합하면
  `작업 중` 을 `출시 대기` 로 바꾼다.

## 5. 닫기

- **출시했다** — 릴리스 주소 · 버전 · 메뉴의 항목 이름을 댓글로 남기고 *완료* 로 닫는다. `출시 대기` 를 뗀다.
- **이미 있는 룰** — 같은 댓글(릴리스 주소 · 항목 이름)을 남기고 *완료* 로 닫는다.
- **대응하지 않는다** — 까닭(범위 밖 · 1차 출처 없음 · 재현 안 됨 · 답이 없음)을 적고 *계획 없음* 으로 닫는다.

닫는 까닭은 라벨이 아니라 GitHub 의 닫기 종류(*완료* · *계획 없음* · *중복*)로 남긴다.

## 6. 고객 자료가 올라왔을 때

공개 저장소의 첨부 파일은 로그인 없이 열리고, 글의 편집 기록은 읽기 권한자 누구나 본다(GitHub 문서). 글을 고치는
것만으로는 지워지지 않는다.

| 누가 | 무엇을 |
|---|---|
| 분류 담당(Triage) | 남의 글을 고치거나 숨기지 못한다 — 그 자리에서 Owner 에게 알린다. 신고자에게는 비공개 경로로 다시 보내 달라는 댓글을 남긴다(그 값을 되풀이하지 않는다) |
| Owner | ① 글을 고쳐 그 값을 지운다 ② 편집 기록에서 그 값이 든 판을 지운다(글쓴이 · 쓰기 권한자가 할 수 있다) ③ 첨부 파일은 글을 고쳐도 주소로 계속 열릴 수 있다 — GitHub 지원에 그 파일의 삭제를 요청한다(직접 지우는 길이 GitHub 문서에 없다) |

이슈를 통째로 지우는 것은 조직 설정(기본 꺼짐)이 켜져 있어야 한다. 조직 단위 설정이라 이 저장소에서 정하지 않는다.

## 7. 권한

| 역할 | 할 수 있는 것 | 누가 받나 |
|---|---|---|
| 읽기 | 이슈 열기 · 댓글 | GitHub 계정이 있는 누구나(공개 저장소) |
| **Triage** | 라벨 붙이고 떼기 · 담당 · 닫기 · 다시 열기 · 중복 표시 | 이슈를 분류하는 팀원 — 조직 Owner 가 이 저장소에 준다 |
| Owner | 위 전부 · 남의 글 고치기 · 편집 기록 지우기 · 라벨 만들기 · 출시 | 조직 Owner |

- 분류 담당이 아직 없으면 Owner 가 맡는다.
- Triage 는 쓰기 권한이 아니다 — 이 권한을 주는 것만으로는 Code Owners 승인을 켤 일이 없다. 쓰기 권한 이상을 주는
  날은 [`AGENTS.md`](../AGENTS.md) 의 규칙대로 켠다.
- 분류 담당이 고객 자료를 직접 가려야 하면 GitHub 의 *Moderate* 역할이 있다(남의 이슈 글 고치기 · 댓글 숨기기 — 쓰기
  권한 없음). 이 조직에서 고를 수 있는지는 아직 재지 않았다.

## 8. 라벨

| 라벨 | 뜻 |
|---|---|
| `버그` · `오탐` · `위협 지원` | 종류 — 양식이 붙인다 |
| `접수` | 아직 분류하지 않았다 — 양식이 붙이고 분류 담당이 뗀다 |
| `자료 대기` | 신고자의 답이나 비공개 자료를 기다린다 |
| `작업 중` | 룰 · 코어 · 하네스를 고치고 있다(공개 저장소 밖) |
| `출시 대기` | 고쳤고 다음 출시에 실린다 |
| `긴급 경로` | 공개 시연 · 실제 공격 — 승인을 받아 긴급 경로로 낸다 |

양식이 붙이는 라벨은 저장소에 먼저 있어야 붙는다 — 없는 라벨은 조용히 빠진다(GitHub). 라벨 이름을 바꾸면 양식
(`.github/ISSUE_TEMPLATE/*.yml` 의 `labels`)도 함께 바꾼다.
