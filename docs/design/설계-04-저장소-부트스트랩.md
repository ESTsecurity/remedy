# 설계 04 — 저장소 구조 · 첫 플러그인 · testbed 검증 계획

> 작성일: 2026-08-20 · 선행: [설계-01](설계-01-아키텍처-결정.md) · [설계-02](설계-02-SDK-계약.md) · [설계-03](설계-03-안전장치.md)

## TL;DR

- **무엇을**: 승인 직후 착수할 수 있도록 저장소 배치, 첫 플러그인(EvilAI) 룰 골격, 그리고 안전 기준 G1~G8을 실제로 돌릴 검증 하네스를 확정한다.
- **핵심 배치 결정**: 실행기 크레이트(`remedy-apply`)가 탐지 크레이트(`remedy-detect`)를 **의존하지 않도록** 크레이트를 쪼갠다. 설계-03의 불변식 P("계획에 없는 동작은 실행될 수 없다")를 주석이 아니라 **빌드가 강제**하게 만드는 장치다.
- **첫 플러그인의 정직한 한계**: 룰 골격은 확정할 수 있지만 YARA 문자열·해시는 실검체 분석 산출물이다. 이 문서는 자리를 비워 두고 무엇을 채워야 하는지 명시한다 — **지어내지 않는다.**
- **판단 포인트**: 5주 부트스트랩 순서(§5)가 팀 사정에 맞는가.

### 의존 방향이 안전 속성을 강제한다

크레이트를 이렇게 쪼갠 이유는 모듈성이 아니라 **컴파일러가 안전 규칙을 지키게 하기 위해서**다. 아래 세 개의 금지는 주석이 아니라 의존 그래프다.

| 금지된 의존 | 이것이 보장하는 것 |
|---|---|
| `remedy-detect` → `remedy-platform` | **플러그인 룰은 시스템에 접근할 수 없다.** 탐지는 불활성 스냅샷 위에서만 돈다 (설계-03 §1) |
| `remedy-apply` → `remedy-detect` | **실행기는 새 대상을 탐색할 수 없다.** 계획에 있는 것만 수행한다 |
| `remedy-apply` → `remedy-collect` | 위와 동일. 술어 해소에 필요한 최소 읽기는 `remedy-platform` 의 **좁은 read trait**으로만 |
| `remedy-detect` → `remedy-enrich` | **판정 코드가 조회를 호출할 수 없다.** 평가의 결정성이 유지된다 (설계-01 D9) |
| `remedy-apply` → `remedy-enrich` | 파괴 경로에 네트워크 코드가 링크되지 않는다 |
| `remedy-collect` → `remedy-apply` | **진단 모드에 파괴 코드가 링크되지 않는다** (설계-00 §5). 고객 PC 에서 `collect` 만 돌리고 분석은 사내에서 하는 경로가 이것이다. 지금까지는 "의존하지 않는다" 는 사실에 기대고 있었을 뿐 빌드가 강제하지 않았다 |

`xtask` 에 `cargo metadata` 를 파싱해 이 여섯 규칙을 검사하는 테스트를 둔다. 누군가 편의상 의존을 추가하면 CI가 실패한다. **안전 불변식이 사람의 기억이 아니라 빌드에 걸려 있어야 한다.**

뒤의 세 줄은 한 문장으로 요약된다 — **`collect` / `evaluate` / `plan` / `apply` 를 수행하는 바이너리 경로에는 네트워크를 말하는 코드가 존재하지 않는다.** 고객 PC에서 도는 것이 정확히 이 경로다.

### 크레이트별 판단 근거

**`remedy-core` 를 되살린 이유.** 초안에서 빠졌는데, 없으면 파이프라인 조립 로직이 `remedy-cli` 안으로 들어간다. 그러면 나중에 GUI 셸이 얹힐 자리가 없어져 GUI가 CLI를 **프로세스로 호출**하는 구조가 되고, 진행률·취소·오류 전달이 전부 텍스트 파싱이 된다. `remedy-core` 를 라이브러리로 두면 GUI는 이것을 링크하면 된다.

**`remedy-platform` 을 read/write trait으로 나눈 이유.** 하나로 두면 `remedy-apply` 가 임의 열거 능력을 갖게 되어 위 세 번째 금지가 형식적인 것이 된다. 크레이트를 더 쪼개는 대신 **trait 경계**로 나누고, `apply` 는 `PlatformWrite` 와 좁은 `ProcessQuery` 만 받는다. Windows/Linux 고유 의존은 `cfg` 로 분기하되, **크레이트 하나에 두어 두 OS 구현이 같은 trait을 만족하는지 컴파일 시점에 확인**되게 한다.

**`remedy-wintrust` 를 분리한 이유 — `unsafe` 를 한 곳에 가둔다.** 다른 크레이트는 전부 `#![forbid(unsafe_code)]` 이고 Windows API 는 안전 래퍼(`winreg` · `windows-permissions`)로만 닿는다. 그런데 설계-03 §3 2층(신뢰 서명 검증)에는 안전 래퍼가 **존재하지 않는다** — crates.io 에 `WinVerifyTrust` 를 감싼 유지되는 크레이트가 없고, 순수 Rust 구현들은 카탈로그 서명을 볼 수 없어 `System32` 의 정상 파일을 전부 "서명 없음" 으로 읽는다(2026-08-25 실측).

`remedy-platform` 전체의 `forbid` 를 푸는 대신 크레이트를 나눈 것은 **아래 `remedy-yara` 와 같은 판단**이다. 한 크레이트에 가두면 "어디에 `unsafe` 가 있는가" 가 크레이트 이름으로 드러나고, 나머지 17개는 `forbid` 를 유지한다.

**그 예외가 하나로 남은 이유 — PE 버전은 `unsafe` 없이 읽는다** (2026-10-27 · C-1b). 실행 파일의 버전을 담는 `remedy-collect/src/peversion.rs` 는 `GetFileVersionInfo` 를 부르지 않고 `.rsrc` 를 직접 걷는다. 서명과 **판단이 갈리는 지점**이 분명하다: 서명은 카탈로그와 X.509 체인이 끼어 **안전한 코드가 틀린 답을 내지만**, 버전 리소스는 자기완결 구조라 OS 지식이 필요 없다. 실물 PE 750개를 파일 바이트와 대조해 불일치 0 으로 확인했다. 그래서 `remedy-collect` 는 `forbid(unsafe_code)` 를 유지하고 **예외는 여전히 `remedy-wintrust` 하나**다.

읽는 수단으로 `object` 를 쓴다 — **새 의존이 아니다.** `yara-x` 가 이미 끌어오고 `xtask` 가 배포 바이너리의 임포트 테이블을 읽는 데 쓰던 크레이트다(루트 `Cargo.toml` 주석). 위 금지 표는 내부 `remedy-*` 쌍만 보므로 이 의존은 그 검사의 대상이 아니고, **읽기 전용 파서라 §1 의 세 금지가 지키는 성질(네트워크 없음 · 탐색 없음 · 파괴 없음)에 닿지 않는다.**

**`remedy-yara` 를 분리한 이유.** yara-x 에는 우리가 다뤄야 할 특성이 있다 — 32비트에서 Pulley 인터프리터로 떨어지는 것, 강화 환경에서 JIT용 실행 페이지가 막히는 것, `memmap2` 기반 스캔의 SIGBUS 위험(설계-01 미결 4). 이것들을 한 크레이트에 가두면 대응도 교체도 한 곳에서 끝난다.

**`remedy-yara` 를 의존하는 것은 `remedy-detect` 하나뿐이다.** YARA는 탐지의 일부이지 파이프라인 조립의 일부가 아니므로, `remedy-core` 는 `remedy-detect` 를 통해서만 닿는다. P0 구현에서 core가 yara를 직접 참조하도록 썼다가 컴파일러가 미선언 의존으로 잡아 이 경계를 명확히 하게 됐다 — 손으로 그린 그래프에서는 보이지 않던 것이다.

**`remedy-artifacts` 와 `remedy-collect` 를 나눈 이유.** 포맷과 수집기가 같은 크레이트에 있으면 스냅샷을 *읽기만* 하려는 쪽(`detect`, 테스트, 코퍼스 도구)이 수집기의 OS 의존을 함께 끌고 온다. 포맷만 있는 크레이트는 어느 플랫폼에서도 빌드된다.

**`remedy-testkit`.** 코퍼스 로더와 계획 비교기(정규화 규칙 포함, 설계-04 §3.2)를 여러 테스트가 공유한다. 정규화 규칙이 테스트마다 복사되면 어느 순간 서로 달라지고, 비교가 아무것도 잡지 못하게 된다.

### `corpus/` 가 1급 디렉터리인 이유

`corpus/clean/` 에 쌓이는 아티팩트 스냅샷이 **오탐 방지의 실질적 사거리**다(설계-03 §1). VM 이미지로는 몇 개밖에 못 돌리지만 스냅샷은 CI에서 수백 개를 초 단위로 돌린다. 그리고 §6의 오탐 대응 경로에서 **한 번 겪은 오탐 환경이 여기에 편입**되므로, 시간이 갈수록 이 디렉터리가 제품의 핵심 자산이 된다.

용량 관리: 스냅샷은 텍스트(JSON) 기반이며 파일 **내용**은 기본적으로 담지 않는다. 내용이 필요한 경우만 별도 번들로 두고 `.gitattributes` 에서 바이너리로 처리한다. 특정 임계를 넘으면 Git LFS 도입을 검토하되, **처음부터 LFS로 시작하지 않는다** — 폐쇄망 CI에서 LFS는 추가 인프라가 된다.

### 루트 파일 중 빠뜨리기 쉬운 것

- **`SECURITY.md`** — 보안 제품에 취약점 신고 경로가 없으면 곤란하다. 파괴 능력을 가진 도구이므로 더욱 그렇다
- **`.gitattributes`** — 줄바꿈을 고정하지 않으면 Windows/Linux 러너를 오가며 diff 잡음이 생기고, 서명 대상 파일의 해시가 플랫폼마다 달라지는 사고로 이어질 수 있다. **서명이 파일 다이제스트 기반이므로 이건 기능적 요구다**
- **`deny.toml`** — 크레이트 280여 개의 라이선스·취약점을 1주차부터 상시 검사(설계-01 미결 6)
- **`CODEOWNERS`** — `crates/` 는 코어팀 승인 필수. 파괴 동작 추가가 플러그인 작성자 재량으로 들어오지 않게 하는 조직적 장치(설계-03 §2)
- **`.gitlab/issue_templates/`** — 오탐 신고 템플릿이 §6의 "무엇을 첨부해야 하는지"를 구조화한다

### 유지되는 원칙

**`docs/` 와 작업 기록의 분리.** `docs/` 는 공개하는 문서다 — 플러그인 작성 가이드(`plugin-guide/`) · 운영 안내(`operator.md`) · 설계(`design/`). 작업 중의 분석·회차 기록은 저장소에 넣지 않는다. 섞이면 무엇을 외부에 공개해야 하는지 판단할 수 없다.

**`plugins/` 는 당분간 같은 저장소에 둔다.** 첫 플러그인을 만들며 SDK의 부족한 점을 찾는 것이 목적이므로, 분리는 SDK가 안정된 뒤가 맞다.

**`remedy-sdk` 가 스키마의 유일한 출처.** 검증기와 실행기가 각자 필드 목록을 들고 있으면 CrowdStrike Channel File 291과 같은 불일치가 생긴다(설계-03 §9). 스키마 타입과 JSON Schema 산출물을 이 크레이트 하나에서 만들고 나머지는 참조만 한다. CI의 `schema` 작업이 재생성 diff로 이를 강제한다(§4).

## 2. 첫 플러그인 — `evilai-locust` 룰 골격

설계-02의 스키마로 표현한 것이다. **구조는 확정, 탐지 문자열은 미확정.**

```yaml
schema_version: 1
id: evilai-locust
version: 0.1.0
min_core: "0.1.0"
platforms: [windows]
name:
  ko: "EvilAI(Locust) 제거"
  en: "EvilAI (Locust) Removal"
scan_roots:
  - "%SystemRoot%\\System32\\Tasks"     # 작업 정의를 읽기 위해
  - "%SystemRoot%\\System32"            # 작업이 이 하위를 가리킬 수 있으므로 (파생 경로 상한)
  - "%LOCALAPPDATA%\\Programs"
subjects: [persistence, file, autorun, av_exclusion]

detect:
  - id: malicious-task
    subject: persistence
    where:
      all:
        - { field: command,                op: matches,     value: "(?i)\\\\node\\.exe$" }
        - { field: args,                   op: matches,     value: "(?i)\\.js(\\s|$)" }
        - { field: win.task.register_path, op: starts_with, value: "\\Microsoft\\Windows\\" }
        - any:
            - { field: source, op: contains, value: "\\System32\\" }
            - { field: source, op: contains, value: "\\AppData\\Local\\Programs\\" }
    capture:
      script_path: "args | first_path"
      script_dir:  "${script_path} | dirname"
    exclude:
      - { field: "file(command).signature.subject", op: equals,   value: "Microsoft Corporation" }
      - { field: source,                           op: contains, value: "\\Microsoft VS Code\\" }
    score: 90

  - id: dropped-payload
    subject: file
    from: "${malicious-task.script_dir}"
    where:
      - { yara: "rules/evilai.yar:evilai_locust_js" }

  - id: runkey
    subject: autorun
    where:
      - { field: command, op: contains, value: "${malicious-task.script_dir}" }

  - id: av-exclusion
    subject: av_exclusion
    where:
      - { field: value, op: contains, value: "${malicious-task.script_dir}" }

verdict:
  require: "malicious-task and dropped-payload"

remediate:
  remove:
    - { ref: malicious-task }
    - { ref: dropped-payload }
    - { ref: runkey }
    - { path: "${malicious-task.script_dir}", recursive: true, guard: dropped-payload }
  restore:
    - av_exclusions
  verify:
    after_reboot: true
```

> **2026-09-30 표시** — 위 예시의 `exclude` 두 줄(`file(command).signature.subject` · `source contains`)은
> 지금 매니페스트에 없다. 둘 다 발동할 수 없음이 실측으로 드러나 P9 에서 지웠다 — 실기기의 `node.exe` 는
> OpenJS 서명이고, 예약 작업의 `source` 는 정의 파일 경로라 설치 경로가 들어갈 자리가 없다. 값을 고쳐
> 살릴 수 있는 술어도 아니다(위협이 정상 실행 파일을 그대로 쓴다). 지금의 매니페스트와 그 까닭은
> `plugins/evilai-locust/plugin.yaml` 의 주석에 있다.

### 사전조사 초안에서 달라진 점과 이유

| 변경 | 이유 |
|---|---|
| `score: 90` + `threshold: 80` → **`verdict.require: "malicious-task and dropped-payload"`** | 휴리스틱 하나가 임계값을 넘겼다는 이유로 파일이 삭제되면 안 된다. 독립적인 두 근거의 논리곱을 요구한다 (설계-02 §5) |
| `steps:` 순서 나열 → **`remove:` 대상 선언** | 프로세스 종료·비활성화·백업·삭제의 순서는 코어가 정한다. 플러그인마다 순서 실수가 재발하지 않게 한다 (설계-03 §2) |
| `delete_path` → **`path` + `guard` 필수** | 재귀 삭제는 "그 디렉터리 안에서 악성 판정된 파일이 실제로 확인됨"을 조건으로만 계획에 들어간다. capture 해석이 어긋나도 폭주하지 않는다 (설계-03 §4) |
| `restore_defender_exclusions` 를 steps 안에 → **`restore:` 절로 분리** | 원복은 파괴가 아니므로 상한·백업·롤백의 대상이 아니다 |
| `av-exclusion` 을 **탐지 규칙으로도 추가** | 자기 경로를 보안 제품 예외 목록에 등록하는 행위 자체가 탐지 근거다. 원복 대상이기도 하고 증거이기도 하다 |

### 실검체로 채운 것과 채우지 못한 것 (2026-08, P9)

`rules/evilai.yar` 는 **채워졌다.** VT 에서 확보한 검체 16건에서 뽑아 교차 확인했고, 지어낸 문자열은 없다.

| 채워야 했던 것 | 상태 |
|---|---|
| 드롭된 `.js` 페이로드의 고유 문자열 (검체 3건 이상 교차 확인) | **끝** — 군집 3개, 상수 101개 + 골격 룰 1개. 탐지 16/16, 오탐 0/25,863(호스트)·0/3,750(VM)·0/625(타 패밀리) |
| 설치 파일·부모 프로세스의 해시 | 부분 — PE 2건 확보. 부모 프로세스는 시스템 설치 `node.exe` 로 관측됨 |
| **서명 주체(subject/thumbprint)** | **채우지 못했다 — 아래** |
| `%LOCALAPPDATA%\Programs` 하위 실제 디렉터리명 패턴 | 관측: `SystemSoftwareUpdaterV2-q5ty`, `MicrosoftResourcesAgentV12-we9i6` — 시스템을 사칭한 이름 + `-<랜덤 4~5자>` |

**서명 주체를 채우지 못했다.** 이 자리는 원래 "EvilAI 계열은 정상 코드서명 인증서로 서명된 AI 관련 애플리케이션으로 위장하는 것이 특징" 이라는 전제 위에 있었으나, 확보한 검체에서 그 특징을 확인하지 못했다 — `engines:meadowlocust tag:signed` 0건, 구성원 40건 개별 조회에서 `signature_info.subject` 보유 0건, 내려받은 PE 2건은 파일 바이트에서 인증서 테이블 크기 0.

"EvilAI 는 서명되지 않는다" 는 뜻이 아니다. 확보한 것은 detect 규칙과 행위가 일치하는 VT `meadowlocust` 군집이고, 공개 보고가 말하는 서명된 설치 파일 단계는 그 라벨을 달지 않았을 수 있다. **못 봤다를 없다로 적지 않는다.**

따라서 `signed_malware` 는 **비워 둔다.** 열거 없는 포괄적 무시가 불가능하므로(설계-03 §3), 서명된 대상을 만나면 2층이 삭제를 막고 그 사실이 보고된다 — 근거 없이 예외를 여는 것보다 옳은 실패 방향이다.

> **아직 답이 없는 것:** 페이로드 디렉터리 안에 **정상 서명된 실행 파일**(자체 동봉한 Node/Electron 런타임 등)이 들어 있는가. 있다면 `path: script_dir, recursive: true` 가 서명된 파일을 건드리므로, 악성코드의 서명 여부와 무관하게 2층이 발동한다. 샌드박스에서는 시스템 설치 `node.exe` 를 쓰는 것만 관측됐다. 이것은 `corpus/infected/` 또는 실제 감염 스냅샷이 있어야 답할 수 있다.

**첫 플러그인을 만들면서 "이 API가 없어서 불편하다"를 기록한다.** 그 기록이 설계-02 §7 스크립트 API 목록의 근거가 되고, 그 전까지 스크립트 런타임은 도입하지 않는다(설계-01 D4).

## 3. testbed — G1~G8을 실제로 돌리는 방법

설계-03 §10의 기준은 문서에 적어 두는 것만으로는 아무것도 막지 못한다. 아래가 그것을 실행하는 방법이다.

### 3.1 검증은 2층이다 — 속도가 사거리를 만든다

수집과 평가를 나눈 덕분에(설계-03 §1) 검증의 대부분이 VM 없이 돌아간다. 이 차이가 결정적이다. VM 기반 검증은 비싸서 몇 개밖에 못 돌리지만, 코퍼스 기반 검증은 수백 개를 매 커밋마다 돌린다.

**1층 — 코퍼스 기반 (매 커밋, 수 초)**

```
  corpus/clean/*.json  -> evaluate -> plan
      -> 파괴 Action 0건인가?                    ... G1  (수백 개 환경에서)
      -> 결과가 결정적인가? (두 번 돌려 동일)     ... G3 전제

  corpus/infected/*.json -> evaluate -> plan
      -> 기대 계획과 일치하는가?                  ... 탐지 회귀

  조작된 입력 (계획기·신뢰 모듈 단위 테스트)
      -> 상한 초과 계획 -> 무인 모드 중단?        ... G5
      -> 보호 경로 대상 -> 계획 단계 거부?        ... G6
      -> because 빈 파괴 Action 존재?             ... G7
      -> 미서명 / 변조 / 폐기 플러그인 로드        ... G8
```

**2층 — VM 기반 (야간, 분 단위)**

```
  [감염 스냅샷 복원]
      -> apply    -> 계획 외 Action 0건인가?      ... G3
      -> 재부팅 + verify -> 잔존 / 재생성 0건?     ... G4
      -> restore  -> 원본 스냅샷과 비교            ... G2
      -> 파괴 중 실패를 주입 -> 롤백하지 않고 이어가는가? (설계-03 §5)
```

**G1이 1층으로 내려온 것이 이 구조의 핵심 이득이다.** 오탐 방지는 "얼마나 다양한 정상 환경에서 확인했는가"에 비례하는데, VM으로는 그 수를 늘릴 수 없다. `remedy-cli` 를 한 줄 고쳐도 수백 개 청정 환경에 대한 무해성이 즉시 재확인된다.

**G5~G8은 부트스트랩 2주차부터 상시 강제한다.** VM 하네스보다 먼저 넣는다.

### 3.2 계획 비교가 성립하는 이유

`plan.json` 은 참조가 남아 있지 않은 완전 구체화 형태이므로(설계-02 §8) 기대 파일과 그대로 비교할 수 있다. 이것이 성립하려면 탐지가 결정적이어야 하고, 그래서 설계-02 §7이 스크립트에 실시간 시계·난수·네트워크를 주지 않는다. **결정성 요구는 취향이 아니라 이 회귀 검증을 성립시키기 위한 것이다.**

비교 시 정규화가 필요한 필드: 실행 식별자, 타임스탬프, 호스트명, 사용자 SID, 임의 경로 접두. 이 목록을 하네스에 명시적으로 두고, **정규화 대상을 늘릴 때마다 리뷰를 받는다** — 정규화를 남발하면 비교가 아무것도 잡지 못하게 된다.

### 3.3 골든 클린 이미지 세트

G1은 **깨끗한 기본 설치본에서만 통과하면 의미가 없다.** EvilAI 룰이 `node.exe` + `.js` 조합을 보고 예약 작업을 훑는다는 것은, **정상 Node 개발 환경이 바로 첫 번째 오탐 후보**라는 뜻이다.

| 분류 | 반드시 포함할 것 |
|---|---|
| OS 기본 | Windows 클라이언트/서버 각 1, 주요 리눅스 배포판 |
| **오탐 유발 후보** | **Node.js 개발 환경**, VS Code, 원격 관리 도구, 예약 작업을 많이 만드는 백업·동기화 도구, 브라우저 확장 다수 |
| 국내 환경 | 은행·공공 보안 프로그램류 (예약 작업·자동실행 항목을 다수 생성), **한글 사용자명·한글 경로** |
| 보안 제품 공존 | **자사 제품이 설치된 환경** (설계-00 §5-1). 실시간 감시가 켜진 상태와 꺼진 상태 각각 |
| 비트수 조합 | 32비트 Windows, 그리고 **64비트 OS + 32비트 빌드** (WOW64 리다이렉션 확인, 설계-02 §4) |

한글 경로를 명시적으로 넣는 이유는 유니코드 정규화(NFC/NFD) 처리가 실제로 동작하는지 확인할 수 있는 유일한 방법이기 때문이다. 코드 리뷰로는 잡히지 않는다.

**코퍼스와 VM 이미지는 다른 것이다.** `corpus/clean/` 에는 위 환경들에서 뽑은 **아티팩트 스냅샷**이 들어가고 매 커밋 검증에 쓰인다. `testbed/images/` 에는 apply·restore 검증(G2·G4)에 필요한 **VM 이미지의 메타데이터와 해시**만 기록하고 본체는 외부 저장소에 둔다. 새 환경을 확보하면 **먼저 스냅샷을 떠서 코퍼스에 넣고**, VM 이미지 확보는 필요할 때 한다 — 스냅샷 쪽이 훨씬 싸고 즉시 검증 사거리를 늘린다.

### 3.4 파서 퍼징과 속성 기반 테스트

G1~G8은 **플러그인**의 게이트다. **코어 자체**의 결함은 다른 방법으로 잡아야 한다.

**퍼징이 필요한 이유는 우리가 인용한 사고 그 자체다.** CrowdStrike Channel File 291은 데이터를 파싱·소비하는 코드의 경계 검사 결함이었다(설계-03 §9). remedy에는 신뢰할 수 없거나 손상 가능한 입력을 파싱하는 지점이 여럿 있으며, 전부 퍼징 대상이다.

| 퍼징 타깃 | 입력 출처 | 손상 시 결과 |
|---|---|---|
| `plugin.yaml` 파서 | 플러그인 (서명되지만 실수 가능) | 잘못된 룰 해석 → 오탐 |
| 룰 조건식·`capture` 표현식 파서 | 동상 | 동상 |
| `artifacts.json` 파서 | 고객 PC에서 수집, 전송 중 손상 가능 | 잘못된 증거 |
| `plan.json` 파서 | 파일로 보관·재실행되는 계획 | **잘못된 파괴 대상** |
| 격리 컨테이너 파서 | 디스크에 오래 남는 파일 | 복원 실패 또는 오복원 |
| 폐기 목록 파서 | 오프라인 반입 경로 존재 | 신뢰 판정 오류 |
| 아티팩트 원본(작업 XML, cron 라인 등) | **악성코드가 쓴 값** | 수집 단계 크래시 |
| 인텔 조회 응답 파서 | 사내 시스템, 그러나 네트워크 경유 | 잘못된 제외 판정 (설계-00 §2 T4) |

마지막 줄이 특히 중요하다. 예약 작업 XML이나 cron 항목의 내용은 **공격자가 자유롭게 쓸 수 있는 값**이므로, 수집기 파서는 처음부터 적대적 입력을 가정해야 한다.

**속성 기반 테스트가 필요한 곳은 격리·복원이다.** 예제 몇 개로는 메타데이터 조합을 덮을 수 없다. 검증할 속성은 하나로 요약된다.

> 임의의 파일 내용과 메타데이터 조합에 대해, **격리했다가 복원하면 원본과 같아야 한다** — 단 복원 불가로 문서화된 항목(ctime, btime)은 제외하고, 그 제외 목록이 실제 손실 항목과 정확히 일치해야 한다.

두 번째 속성도 넣는다. **계획기는 어떤 입력에도 보호 경로를 대상으로 하는 Action을 만들지 않는다.** 임의의 Evidence를 생성해 계획기에 넣고 결과를 검사하면, 손으로 짠 예제가 놓치는 경로를 찾는다.

### 3.5 단계적 배포와 연결

설계-03 §9(3)의 링 배포는 testbed 통과가 **첫 번째 링**이라는 뜻이다. `testbed → 사내 → 카나리 고객 → 전체` 순으로 승격하며, 각 단계의 관측 지표는 감사 로그(설계-03 §7)에서 나온다. 특히 **"제외(스킵)된 대상과 사유"** 통계가 링 승격 판단의 핵심 지표다 — 파괴 Action 수만 보면 오탐은 보이지 않는다.

| `schema` | Linux | 매 커밋 | `remedy-sdk` 에서 JSON Schema **와 가이드 레퍼런스**를 재생성 후 커밋본과 diff (설계-06 §4) |
| `guide` | Linux | 매 커밋 | `docs/plugin-guide/examples/*` 를 실행해 `expected-plan.json` 과 비교, 각 예제의 청정 코퍼스 G1 (설계-06 §5) |
| `corpus` | Linux | 매 커밋 | `corpus/clean/*` 전체에 대해 **G1**, `corpus/infected/*` 탐지 회귀 |
| `build:windows` | Windows | 매 커밋 | `x86_64-pc-windows-msvc`, `i686-pc-windows-msvc`, `+crt-static` |
| `build:linux` | Linux | 매 커밋 | 정적화 방식 판정 후 확정 (musl vs glibc `+crt-static`) |
| `fuzz` | Linux | 야간 | §3.4 타깃들. 코퍼스는 저장소에 커밋해 재현 가능하게 |
| `testbed` | 전용 러너 | 야간 | VM 기반 **G2·G4** + 실패 주입 |

세 작업이 각각 다른 사고 유형을 막는다. `arch` 는 안전 불변식이 사람의 기억으로 유지되는 것을, `schema` 는 검증기와 실행기가 갈라지는 것을(설계-03 §9), `corpus` 는 오탐이 넓은 환경에서 확인되지 않는 것을 막는다. **세 작업이 없으면 나머지 설계가 문서에만 존재하게 된다.**

`corpus` 작업이 매 커밋에 들어갈 수 있는 것은 수집과 평가를 나눈 덕분이다(설계-03 §1). VM 기반이었다면 야간으로 밀렸을 것이고, 그러면 오탐 회귀를 하루 늦게 발견한다.

## 5. 부트스트랩 순서 (주차 계획 — 대체됨)

> **이 절은 [설계-09 개발 Phase](설계-09-개발-Phase.md)로 대체되었다.**
> 아래 주차 계획은 워크스루 두 차례로 SDK 표면이 넓어지기(Op 12→24, subject 9→18) 전에 작성된 것이며, 달력 기준이라 검증 게이트가 없다. **실제 착수는 설계-09를 따른다.** 이 절은 초기 판단의 기록으로만 남긴다.

| 주 | 산출물 | 완료 판정 |
|---|---|---|
| **1** | 워크스페이스 스캐폴딩, `rust-toolchain.toml`, CI(`lint`/`deny`/`arch`), 루트 파일 일습 | Windows 64/32비트 정적 바이너리가 CI에서 나온다. **Linux 정적화 방식 확정.** Windows 7 지원이 필요하다면 **tier 3 빌드 가부를 여기서 판정** |
| **2** | `remedy-sdk` 스키마 단일 소스, `remedy-artifacts` 포맷, `schema` CI 작업 | 스키마 재생성 diff가 CI를 막는다. 아키텍처 테스트 3건 통과 |
| **3** | **`remedy-collect` Windows 수집기 + `collect` 명령** | 실제 머신에서 `artifacts.json` 이 나온다. **여기서부터 코퍼스 수집을 병렬로 시작한다** — 임계 경로 |
| **4** | `remedy-detect` 평가기, `remedy-yara` 통합, `evaluate` 명령 | 스냅샷에서 Evidence가 나온다. **`corpus` CI 작업이 켜지고 G1이 상시 강제된다.** 32비트 WOW64·mmap·성능 예산 확정 |
| **5** | `remedy-plan` 완성, 격리 컨테이너(키 wrap 3종), 저널, 재시도 큐, `restore` | **G5·G6·G7 상시 강제.** 격리→복원 속성 기반 테스트 통과. 파괴 중 실패 시 롤백하지 않고 이어가는 동작 확인 |
| **6** | `evilai-locust` 플러그인, VM testbed 하네스, 서명 검증(G8), 계획 렌더러 | G2·G4가 VM에서 돈다. **"없어서 불편한 API" 목록이 문서화된다** |

### 인텔 조회는 v1 코어 이후 · 제출은 제품 밖

`enrich`(설계-01 D9)는 위 6주에 넣지 않는다. 치료가 동작하기 전에 인텔 배관을 먼저 놓으면, **정작 검증할 치료 결과가 없는 상태에서 데이터 규격을 정하게 된다.**

> **`submit` 은 제품에서 뺐다 (2026-08-28 P13 결정).** 이유는 설계-09 "제출을 제품 밖으로" 절에 한 번 적혀 있다. `remedy-submit` 크레이트와 `remedy-apply ↛ remedy-submit` 금지 규칙도 함께 지웠다 — 존재하지 않는 크레이트에 대한 규칙은 지킬 것이 없고, 그 사실을 `cargo xtask arch` 가 바로 잡아냈다.

| 단계 | 산출물 | 선행 조건 |
|---|---|---|
| **7주** | `indicator` 추출 + `file.zone` 수집 (조회 없이) | 수집기 완성(3주차) |
| **8주** | `remedy-enrich` — 해시 조회, 캐시, 응답 퍼징 (내부 문서 설계-05 §2) | 전제는 내부 문서 설계-05 §8 |

7주차를 앞에 둔 이유는 **조회 없이도 지표 추출과 감염 소스 수집이 그 자체로 가치가 있기 때문**이다. 분석가가 `artifacts.json` 만 보고도 C2 후보와 유입 경로를 알 수 있다. 조회는 그 위에 얹는 것이지 전제가 아니다.

9주차의 선행 조건이 기술이 아니라 법무인 것이 핵심이다. 마스킹을 아무리 잘 만들어도 **무엇을 받아도 되는지가 정해지지 않으면 만들 수 없다.**

### T2 확장 능력은 3~4주차에 함께 넣는다

설계-01 D10의 T2 — **와일드카드 레지스트리 열거, 파일 글로브 열거, `text_config` subject, `registry.delete_key` / `text_config.remove_line`** — 는 나중에 붙이는 기능이 아니라 **수집기와 계획기의 기본 능력**이다. 3주차 수집기와 5주차 계획기에 처음부터 포함한다.

뒤로 미루면 첫 플러그인이 T1만으로 작성되고, 그 형태가 사실상의 표준이 되어 이후 룰 작성자가 T2를 쓰지 않게 된다. **능력이 있어도 쓰이지 않으면 자립률은 오르지 않는다.**

`docs/plugin-guide/` 의 구성과 산출 시점은 설계-06에 있다. **가이드를 SDK가 굳은 뒤로 미루지 않는다** — 4주차에 "불변식 + 퀵스타트 + 실행되는 예제 하나 + 린트"가 갖춰지면 그때부터 AI 작성 루프가 성립하고, **AI가 무엇을 틀리는지가 관측되기 시작한다.** 그 관측이 나머지 문서의 목차를 정한다.

여기에 **"새 subject·Op를 코어에 추가하는 체크리스트"**도 함께 둔다. T3가 불가피한 이상, T3의 리드타임을 줄이는 것이 자립률만큼 중요하다.

**3주차가 임계 경로다.** 수집기가 나오는 순간부터 다른 인원이 각종 환경에서 스냅샷을 뜨기 시작할 수 있고, 그렇게 쌓인 `corpus/clean/` 의 크기가 곧 오탐 방지의 사거리가 된다(§3.1). 수집기를 뒤로 미루면 코퍼스가 얇은 채로 첫 플러그인을 내보내게 된다.

이전 계획(5주)에서 한 주가 늘었다. 수집과 평가를 나누면서 3·4주차가 갈라졌기 때문이며, 그 대가로 G1이 VM에서 코퍼스로 내려와 **매 커밋 검증**이 되었다.

`cargo-deny` 를 1주차에 넣는 이유는 크레이트 280여 개의 라이선스를 상용 배포 직전에 몰아서 보면 늦기 때문이다. 계획 렌더러를 마지막에 두는 이유는 승인 게이트가 성립하려면 사람이 계획을 이해해야 하고(설계-01 D5), 그것은 첫 플러그인의 실제 계획을 보고 나서야 제대로 만들 수 있기 때문이다.

Linux 수집기는 6주차 이후다. 첫 위협이 Windows이므로 Windows를 먼저 완성하되, **`remedy-platform` 의 추상화 경계는 1주차에 잡아 둔다** — 나중에 끼워 넣으면 Windows 개념이 인터페이스에 새어든다.

## 6. 출시 후 오탐 대응 경로

G1~G8을 통과해도 오탐은 발생한다. 발생했을 때의 경로를 **미리 정해 두는 것**이 게이트만큼 중요하다.

```
  고객이 오탐 의심
     -> 1. remedy restore --run <id>      (즉시 복구. 격리물은 자동 삭제되지 않으므로 항상 가능)
     -> 2. 신고               (result.json + 감사 로그 첨부. 도구가 첨부 파일 경로를 안내)
     -> 3. 재현·판정          (testbed 클린 세트에 해당 환경을 추가 -> 이후 상시 회귀 대상)
     -> 4. 폐기               (온라인 폐기 목록 + 다음 코어 릴리스의 min_plugin_version 상향)
     -> 5. 기준 추가          (재발 방지 조건을 설계-03 G 항목으로 승격)
```

3번이 핵심이다. **한 번 겪은 오탐 환경은 골든 클린 세트에 편입**되어 이후 모든 플러그인이 그 환경에서 검증된다. 그렇지 않으면 같은 유형의 오탐이 플러그인마다 반복된다.

신고를 받기 위한 최소 요건: **첨부해야 할 파일 목록과 그 경로가 명시**되어야 한다. 고객에게 "로그를 보내 주세요"라고 하면 무엇을 보낼지 몰라 대응이 지연된다.

> **2026-08-26 (P10-G) 구현 — `result.json` 이 아니라 명령이 그 자리를 진다.** `remedy support-bundle --run <id>` 가 계획·저널·환경 정보를 모아 디렉터리 하나를 만들고, **무엇이 담겼고 무엇이 빠졌는지를 README 에 적는다.** 목록을 결과 파일에 박으면 경로가 굳고, 명령이 그때그때 실제 파일을 확인하는 편이 정확하다 — 사용자가 무엇을 보낼지 알게 된다는 취지는 그대로다. `apply` 가 끝날 때 그 명령을 안내한다.
>
> **봉인 키(`machine.key`)와 격리 컨테이너는 담지 않는다.** 키를 보내면 컨테이너를 누구나 열 수 있고, 컨테이너에는 검체와 사용자 파일 내용이 있다. 다만 **빠진 사실과 경로를 적는다** — 그러지 않으면 "왜 없지" ↔ "다 보냈는데" 왕복이 생기고 그것이 이 절이 없애려는 지연이다. 그리고 **마스킹하지 않는다**: 오탐 판정은 경로를 봐야 서므로, 가리는 대신 무엇이 담겼는지 명시해 사람이 보내기 전에 판단하게 한다.
