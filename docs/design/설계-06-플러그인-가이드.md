# 설계 06 — 플러그인 작성 가이드 (`docs/plugin-guide/`)

> 작성일: 2026-08-20 · 대상: 배포 산출물인 작성 가이드 자체의 설계
> 선행: [설계-02 SDK 계약](설계-02-SDK-계약.md) · [설계-01 D10](설계-01-아키텍처-결정.md) · [설계-03 안전장치](설계-03-안전장치.md)

## TL;DR

- **무엇을**: 플러그인 룰을 **AI가 작성한다**는 전제로 가이드 문서 폴더를 설계한다. 현재 설계에서 `docs/` 는 두 줄짜리 언급뿐이었다.
- **가장 중요한 전환**: 사람은 모르면 묻지만 **AI는 그럴듯하게 지어낸다.** 따라서 가이드의 1차 목표가 "설명"에서 **"환각 차단"**으로 바뀐다. 존재하지 않는 필드·연산자·Op를 발명하지 못하게 하는 장치가 문서의 본체다.
- **핵심 결정 세 가지**:
  1. **레퍼런스는 `remedy-sdk` 에서 생성**하고 CI가 diff로 강제한다. 손으로 적은 필드 목록은 반드시 코드와 어긋난다.
  2. **모든 예제는 CI에서 실행되는 코퍼스 테스트 케이스**다. 깨진 예제로 AI가 학습하는 경로를 없앤다.
  3. **`plugin lint` 의 오류 메시지가 가이드의 일부**다. AI의 실제 학습 경로는 산문이 아니라 오류 → 수정 루프다.
- **판단 포인트**: §7의 과광범위 린트 규칙이 실무에서 너무 빡빡한지 — 첫 플러그인 작성 후 조정한다.

## 1. 주 독자가 AI로 바뀌면 무엇이 달라지는가

| 사람 대상 문서의 전제 | AI 대상에서 깨지는 방식 | 대응 |
|---|---|---|
| 처음부터 끝까지 읽는다 | **일부만 문맥에 들어온다** | 파일마다 자립적으로. "위에서 말한" 금지 |
| 모르면 묻는다 | **그럴듯하게 지어낸다** | 전수 열거 + 존재하지 않는 것 목록(§6) |
| 예제를 참고만 한다 | **예제를 패턴으로 복제한다** | 예제가 곧 정답이어야 하고, 예제별 값에 표시가 있어야 함 |
| 문서가 조금 낡아도 이해한다 | **낡은 필드명을 그대로 출력한다** | 레퍼런스 생성 + CI diff(§4) |
| 산문에서 뉘앙스를 읽는다 | **"권장"과 "필수"를 구분 못 할 수 있다** | 규범 표현을 고정 어휘로(§3) |
| 오류를 보면 문서를 다시 읽는다 | **오류 메시지만 보고 고친다** | 오류 메시지에 허용 목록과 문서 앵커 포함(§7) |

**"등등"과 "예를 들어"를 쓰지 않는다.** 사람에게는 생략이 친절이지만 AI에게는 빈칸이고, AI는 빈칸을 채운다.

## 2. 폴더 구조

한 폴더에서 관리하되 파일은 나눈다. 번호 접두로 순서를 고정하고 사이를 비워 삽입 여지를 둔다.

```
  docs/plugin-guide/
  |
  |-- README.md                    # 라우터: 무엇을 하려면 어느 파일을 읽는가
  |-- 00-invariants.md             # 절대 규칙. 항상 로드. 2 KB 이내
  |-- 01-quickstart.md             # 최소 동작 플러그인 + 반복 루프
  |
  |-- 10-manifest.md               # 매니페스트 키 (일부 생성)
  |-- 11-subjects.reference.md     # [생성] subject x 필드 전수
  |-- 12-operators.reference.md    # [생성] 연산자 전수 + 정규화 규칙
  |-- 13-ops.reference.md          # [생성] 파괴 동작 전수 + 되돌림/백업/위험 등급
  |
  |-- 20-detect-recipes.md         # 과업별: 지속성 / 파일 / 레지스트리 / 설정파일
  |-- 21-verdict-and-groups.md     # 증거 그룹, require 식
  |-- 22-remediate-recipes.md      # 제거 대상 선언 패턴
  |-- 23-collect-and-submit.md     # collect_extra / submit_hint
  |
  |-- 30-antipatterns.md           # 거부되는 패턴과 이유 (부정 예제)
  |-- 31-nonexistent.md            # 존재하지 않는 기능 목록 (환각 차단)
  |-- 32-lint-errors.md            # [생성] 오류 코드 -> 원인 -> 수정
  |
  |-- 40-review-checklist.md       # 사람이 서명 전에 확인할 것
  |
  |-- examples/                    # 예제 = CI 에서 실행되는 테스트 케이스
  |     |-- ex01-scheduled-task/   #   plugin.yaml + artifacts.json + expected-plan.json
  |     |-- ex02-registry-ifeo/
  |     |-- ex03-text-config/
  |     +-- ...
  |
  +-- machine/                     # 기계 판독용 산출물
        |-- plugin.schema.json     # [생성] JSON Schema — 권위 있는 정의
        |-- subjects.json          # [생성] subject/필드 카탈로그
        |-- ops.json               # [생성] Op 카탈로그
        +-- AI-CONTEXT.md          # [생성] 압축 전체 요약. 통째 주입용. 8 KB 이내
```

`README.md` 는 설명이 아니라 **라우터**다. "지속성 항목을 탐지하려면 → `20-detect-recipes.md` §지속성 + `11-subjects.reference.md` 의 `persistence`" 식으로, **과업 → 읽을 파일** 매핑만 담는다.

> **2026-08-26 (P11 마감) — `21-verdict-and-groups.md` 는 쓰지 않았다.**
> 위 구조가 요구한 파일이지만 **관측이 그것을 가리키지 않았다.** AI 합격 시험
> 다섯 회차가 전부 `verdict` 를 정확히 썼고, 그 내용은 `01-quickstart.md` ·
> `30-antipatterns.md`(2·7) · 예제 셋 · `40-review-checklist.md` ·
> `AI-CONTEXT.md` 에 나뉘어 있다.
>
> **한 파일로 모으는 것이 나아지는지는 관측되지 않았다.** §10 이 *"우리가
> 상상한 목차가 아니라"* 고 적은 규칙을 지킨 결과이고, 빈 파일을 두는 것보다
> **왜 없는지를 라우터에 적는 편**이 다음 사람에게 정확하다.

`machine/AI-CONTEXT.md` 는 폴더 전체를 넣을 수 없을 때 **하나만 넣는 파일**이다. 불변식·전수 카탈로그의 요약·금지 목록을 압축해 담으며, **생성물이므로 본문과 어긋날 수 없다.**

## 3. 규범 어휘를 고정한다

산문의 뉘앙스는 AI에게 신뢰할 수 없는 신호다. 네 단어만 쓴다.

| 표현 | 의미 | 위반 시 |
|---|---|---|
| **필수** | 없으면 로드되지 않는다 | `plugin lint` 오류 |
| **금지** | 있으면 로드되지 않는다 | `plugin lint` 오류 |
| **경고** | 동작하지만 검토 대상이다 | `plugin lint` 경고 |
| **권장** | 취향이 아니라 근거 있는 기본값 | 검사 없음 |

"~하는 것이 좋다", "가급적", "일반적으로" 를 쓰지 않는다. 넷 중 하나로 분류되지 않는 문장은 가이드에 넣지 않는다.

**식별자는 번역하지 않는다.** `file.delete` 를 `파일_삭제` 로 적지 않는다. AI가 그대로 출력해야 하는 문자열은 원문 그대로 두고, 설명만 한국어로 쓴다.

## 4. 레퍼런스는 생성물이다

`11`·`12`·`13`·`32` 와 `machine/*` 은 **`remedy-sdk` 에서 생성**한다. 손으로 적지 않는다.

이것은 편의가 아니라 안전 요구다. 검증기와 실행기가 각자 필드 목록을 들고 있으면 CrowdStrike Channel File 291과 같은 불일치가 생긴다는 것이 설계-03 §9의 결론이었다. **문서도 같은 문제를 겪는다** — 문서가 실제로 없는 필드를 말하면, AI는 그 필드를 쓴 룰을 만들고 작성자는 왜 안 되는지 모른다.

CI의 `schema` 작업을 확장해 **가이드 생성물의 diff까지 검사**한다(설계-04 §4). 재생성 결과가 커밋본과 다르면 실패한다. 즉 SDK를 고치고 문서를 안 고치면 머지되지 않는다.

수기로 쓰는 것은 개념·가드레일·레시피·부정 예제뿐이다.

> **2026-08-26 (P11) — 생성물 둘을 더했다.** `32-lint-errors.md` 와
> `machine/AI-CONTEXT.md`. 생성물이 6개에서 8개가 됐고 `OUT_DIR` 기준을
> `docs/plugin-guide` 로 올렸다 — **`machine/` 밖에도 생성물이 있다.**
>
> **오류 표는 실제로 린트를 돌려 만든다.** 사례 매니페스트 14개를 `lint()` 에
> 통과시켜 나온 진단을 그대로 싣는다. 손으로 적은 오류 표는 반드시 낡고,
> **낡은 오류 메시지를 읽은 AI 는 지금은 없는 수정법을 시도한다.** 사례가
> 발동하지 않으면 문서에 그렇게 적히고 테스트가 실패한다.
>
> `AI-CONTEXT.md` 가 싣는 최소 매니페스트도 **생성기가 린트에 통과시킨다.**
> 문서에 실린 예제는 복제되므로(§5) 거부되는 형태를 가르치면 안 된다.

> **2026-08-26 (P11) — 이 규칙이 실제로 깨져 있었다.** `01-quickstart.md` 에 "지금 쓸 수 있는 것" 요약 표가 손으로 적혀 있었고, **P2 시절 그대로 낡아 있었다** — `subject` 가 둘, `Op` 이 없다고 말하고 있었다(실제로는 18종·29종). 그 표는 "권위는 생성물 쪽" 이라는 단서를 달고 있었지만, §1 이 말한 대로 **AI 는 낡은 목록을 그대로 출력한다.** 표를 걷어 내고 어디를 보는지만 남겼다.

## 5. 예제는 문서가 아니라 테스트다

`examples/exNN-*/` 는 세 파일을 함께 둔다.

```
  ex02-registry-ifeo/
    plugin.yaml          # 룰
    artifacts.json       # 입력 스냅샷 (감염 상태)
    expected-plan.json   # 기대 계획
    README.md            # 이 예제가 가르치는 것 한 문단
```

CI가 `evaluate` + `plan` 을 돌려 `expected-plan.json` 과 비교한다. **가이드의 예제가 곧 코퍼스 테스트 케이스**이므로, 스키마가 바뀌면 예제가 먼저 깨지고 문서를 고치지 않을 수 없다.

이것이 중요한 이유는 AI의 학습 경로 때문이다. AI는 예제를 **패턴으로 복제**한다. 깨진 예제가 문서에 남아 있으면 그 형태가 그대로 재생산된다. 사람은 "이건 좀 이상한데" 하고 넘어가지만 AI는 넘어가지 않는다.

**예제마다 청정 스냅샷 대조도 함께 돌린다.** 각 예제는 `corpus/clean/` 전체에서 파괴 Action 0건이어야 한다. 예제가 그 자체로 G1을 통과하지 못하면 가이드에 넣지 않는다.

**예제 고유 값에는 표시를 단다.** `%LOCALAPPDATA%\Programs` 같은 값이 복제되면 안 되는 자리에는 주석으로 `# 예제 고유 값 — 대상 위협에 맞게 교체` 를 붙인다.

> **2026-08-26 (P11) — 셋을 채웠다.** `ex01`(예약 작업·Windows) ·
> `ex02`(레지스트리 IFEO·Windows) · `ex03`(설정 파일·**Linux**).
>
> **하나뿐이면 그 형태가 사실상의 표준이 된다.** 실제로 AI 합격 시험 두 회차가
> 모두 `ex01` 의 예약 작업 구조를 그대로 복제했다 — 그것이 옳은 답이었으므로
> 문제가 드러나지 않았을 뿐, 레지스트리나 설정 파일 위협이 왔다면 참고할 실물이
> 없었다.
>
> `ex02`·`ex03` 은 `remediate` 까지 선언한다. `ex01` 은 탐지에서 끝나므로
> **제거를 가르치는 예제가 하나도 없었다.**
>
> `ex03` 을 Linux 로 둔 이유가 하나 더 있다 — **평가 경로가 Linux 스냅샷을 실제로
> 다루는지 P12 전에 확인된다.** 돌려 보니 `text_config` 수집 · `%HOME%` 토큰 ·
> 경로 정규화가 전부 동작했다.

## 6. 환각을 차단하는 두 파일

### `30-antipatterns.md` — 부정 예제

AI는 정답만 보면 **그럴듯한 변형**을 만든다. 거부되는 형태를 실물로 보여주는 것이 설명보다 강하다. 각 항목은 세 부분으로 쓴다.

```
  [거부되는 형태]  실제 YAML
  [왜 거부되는가]  한 문장
  [올바른 형태]    실제 YAML
```

최소한 아래를 담는다. 전부 설계에서 이미 금지된 것들이다.

- 점수 임계값으로 판정 게이트를 만드는 형태 (`score >= 80`) → `verdict.require` 불 대수식
- `remediate` 에서 `reputation` 참조 → 조회는 삭제를 늘릴 수 없다
- 리터럴 절대 경로를 제거 대상으로 지정 → 증거 참조만 허용
- `guard` 없는 재귀 삭제 / 키 삭제
- `scan_roots` 밖을 가리키는 파생 경로
- 단일 조건만으로 구성된 `verdict.require`
- 경로 제약 없는 프로세스명 매칭 (`command matches "node.exe"`)
- `platforms` 선언 없이 `win.*` 필드 사용

마지막 두 개가 실무에서 가장 위험하다. **정상 Node 개발 환경이 첫 번째 오탐 후보**라는 것을 예제로 못 박는다.

### `31-nonexistent.md` — 존재하지 않는 기능 목록

사람 대상 문서에는 없는 종류의 페이지다. AI가 흔히 있다고 가정하는 것들을 **명시적으로 부정**한다.

- 임의 명령 실행 Op는 **없다** (`exec`, `run_command`, `powershell` 등)
- 파일 **쓰기·수정** Op는 없다. 파괴와 원복만 있다
- 네트워크 요청 기능은 없다. 조회는 `enrich` 단계이며 룰이 호출하지 않는다
- 스크립트 런타임은 **현재 버전에 없다** (설계-01 D4·D10)
- 백업을 끄는 옵션은 없다
- 삭제 상한·보호 경로를 플러그인이 조정할 수 없다
- 정규식은 RE2다. 역참조·전방탐색이 **없다**
- `verdict` 에 점수 임계값 문법이 없다

각 항목에 **"대신 무엇을 쓰는가"**를 함께 적는다. 부정만 하면 AI는 다른 방식으로 같은 것을 시도한다.

## 7. 오류 메시지가 가이드의 절반이다

AI의 실제 작업 루프는 산문 독해가 아니라 이것이다.

```
  작성 -> plugin lint -> 오류 읽기 -> 수정 -> evaluate (코퍼스) -> 계획 확인 -> 반복
```

이 루프가 **빠르고 오프라인**이어야 한다. 수집과 평가를 나눈 설계(설계-03 §1)가 여기서 배당을 낸다 — 감염 VM 없이 스냅샷만으로 초 단위 반복이 된다.

### 오류 메시지 요건

모든 `plugin lint` 진단은 네 가지를 담는다.

1. **무엇이 잘못됐는가** — 위치(파일·라인·YAML 경로)
2. **왜 거부되는가** — 한 문장
3. **무엇이 허용되는가** — 유효값 전수 또는 근접 후보
4. **문서 앵커** — `docs/plugin-guide/13-ops.reference.md#filedelete`

3번이 핵심이다. `unknown field "cmdline"` 만 주면 AI는 다시 지어낸다. `unknown field "cmdline" — 유효 필드: command, args, principal, source, id, name, enabled, trigger` 를 주면 그 자리에서 고친다.

### 린트가 검사할 것

| 분류 | 검사 |
|---|---|
| 스키마 | 알 수 없는 키 **거부**(무시 아님), 타입, 필수 키, `platforms` 와 `win.*`/`linux.*` 일치 |
| 참조 | 규칙 참조 순환, 미정의 참조, `guard` 누락, `${}` 미해결 참조 |
| 범위 | 파생 경로가 `scan_roots` 밖, `subjects` 미선언 대상 사용 |
| 방향 제약 | `remediate` 의 `reputation` 참조, `confidentiality_min` 하향 시도 |
| 정규식 | RE2 컴파일, 과도하게 짧은 리터럴 |
| **본문 수집** | `yara:` 를 쓰는데 본문을 담는 `collect_extra` 가 하나도 없다 (P11 실측) |
| **`from` 의 subject** | `path` 필드가 없는 subject 에 `from` 을 걸었다 — 그 규칙은 영영 매치되지 않는다 (P11 r0) |
| **원복의 짝** | `restore: [av_exclusions]` 인데 `av_exclusion` 탐지 규칙이 없다 — 되돌릴 증거가 안 잡힌다 (P11 r0) |
| **과광범위(경고)** | 아래 |

**과광범위 검사**가 AI 작성 시대에 새로 필요해진 것이다. AI는 "탐지되게 만들기"에 최적화하고 "정상을 지키기"를 잊는다.

- `verdict.require` 가 **단일 항목**이면 경고 — 독립 근거 2개 이상을 권장
- 파일·프로세스 매칭에 **경로 제약이 하나도 없으면** 경고
- 정규식이 **극히 짧거나** 흔한 실행 파일명만 매칭하면 경고
- 와일드카드 열거가 **상위 경로에서 시작**하면 경고
- 재귀 삭제 대상이 **사용자 홈 직하**이면 경고 — 2026-08-25 (P10-C) 구현

> **파생 경로는 값을 알 수 없다.** `${task.payload_dir}` 같은 대상은 증거에서 오므로 매니페스트만 보고는 무엇이 될지 모른다. 그래서 **상한을 본다** — 파생 경로의 상한은 `scan_roots` 이고(설계-02 §4), 그 아래에 홈 직하가 들어갈 수 있으면 이 재귀 삭제도 거기 닿을 수 있다. 모르는 것을 통과로 읽지 않는 것이 이 파일의 다른 검사들과 같은 규칙이다.
>
> 저장소의 매니페스트 5개에 돌려 **오경보 0건**이다. `evilai-locust` 는 `recursive: true` 를 쓰지만 `scan_roots` 가 `%LOCALAPPDATA%\Programs`(홈에서 세 칸 아래)라 걸리지 않는다.

경고는 로드를 막지 않는다. 다만 **서명 단계에서 경고가 남아 있으면 사람의 확인을 요구**한다 — §8의 리뷰 체크리스트가 그 지점이다.

## 8. 두 번째 독자 — 서명하는 사람

AI가 쓴 룰은 **사람이 서명한다.** 서명은 "이 파괴 지시서에 우리 이름을 건다"는 뜻이므로, 리뷰어가 무엇을 봐야 하는지가 가이드에 있어야 한다.

`40-review-checklist.md` 는 다음을 묻는다.

1. `verdict.require` 의 각 항목이 **서로 독립적인 근거**인가. 같은 사실의 두 표현이 아닌가
2. 정상 소프트웨어가 이 조건을 만족할 수 있는가. **구체적으로 어떤 제품인지 이름을 댈 수 있는가**
3. 제거 대상이 전부 증거에서 파생됐는가
4. 재귀 삭제·키 삭제에 `guard` 가 붙어 있고, 그 guard 가 실제로 그 디렉터리·키 안의 것인가
5. `scan_roots` 가 필요 이상으로 넓지 않은가
6. 청정 코퍼스에서 파괴 Action 0건인가 (G1 결과 첨부)
7. 린트 경고가 남아 있다면 각각에 대해 남긴 이유가 설명되는가
8. `submit_hint` 의 `confidentiality_min` 이 대상 데이터에 맞는가

2번이 가장 중요하다. **"오탐 가능성이 낮다"가 아니라 "어떤 정상 제품이 걸릴 수 있는지 이름을 대라"**고 요구한다. 이름을 대지 못하면 검토가 이뤄지지 않은 것이고, 이름을 대면 그 제품이 청정 코퍼스에 추가된다(설계-04 §3.3).

## 9. 크기 예산과 버전 헤더

문맥에 들어가는 것이 전제이므로 크기를 제약한다.

| 파일 | 상한 | 이유 |
|---|---|---|
| `00-invariants.md` | 2 KB | 항상 로드된다 |
| `machine/AI-CONTEXT.md` | 8 KB | 하나만 넣을 때 쓰는 파일 |
| 각 레시피·레퍼런스 파일 | 12 KB | 두세 개를 함께 넣을 수 있어야 함 |
| 폴더 전체 | 제한 없음 | 라우터로 선택 로드 |

상한을 넘으면 파일을 쪼갠다. **쪼개는 기준은 분량이 아니라 과업**이다 — 한 과업을 두 파일로 나누면 AI가 절반만 읽는다.

> **2026-08-26 (P11) — `AI-CONTEXT.md` 실측 6.4 KB** (상한 8 KB). 전수
> 카탈로그(subject × 필드 · Op 29 · 연산자 · capture 함수)와 최소 예제를 담고,
> **레시피와 안티패턴은 뺐다** — 판단을 가르치는 자리는 8 KB 에 들어가지
> 않는다. 대신 어느 파일을 봐야 하는지만 남겼다. 생성기 안에서도 상한을
> 검사한다(생성 시점에 넘으면 커밋된 파일이 이미 넘은 상태가 된다).
>
> **2026-08-26 (P11) — 크기 예산을 빌드가 잰다.** `cargo xtask guide` 가 상한과 헤더를 검사하고 `all` 에 들어간다. **상한을 정해 놓고 아무도 재지 않으면 넘고, 넘은 파일은 절반만 읽히거나 아예 빠진다** — 그러면 AI 가 규칙의 절반만 보고 룰을 쓴다. 바이트로 잰다(문자 수가 아니다) — 한글은 3바이트이고 문맥에 들어가는 것은 바이트다.

모든 파일 머리에 동일 형식의 헤더를 둔다.

```
  <!-- schema_version: 1 | min_core: 1.0.0 | generated: false -->
```

`generated: true` 인 파일을 사람이 고치면 CI가 되돌린다. AI가 낡은 가이드를 읽고 낡은 스키마용 룰을 쓰는 것을 막으려면, **문서가 자기 버전을 말할 수 있어야 한다.**

## 10. 언제 만드는가

가이드는 SDK가 굳은 뒤가 아니라 **첫 플러그인과 함께** 만든다. 순서가 반대면 쓰이지 않는 설명이 쌓인다.

| 시점 | 산출 |
|---|---|
| 2주차 (SDK 스키마) | `machine/plugin.schema.json` 생성 파이프라인, `schema` CI에 가이드 diff 포함 |
| 4주차 (evaluate 동작) | `00-invariants.md`, `01-quickstart.md`, `examples/ex01` — **AI 반복 루프가 성립하는 최소 집합** |
| 5주차 (계획기·린트) | `32-lint-errors.md` 생성, 과광범위 검사, `30-antipatterns.md` |
| 6주차 (첫 플러그인) | 레시피 3종, `31-nonexistent.md`, `40-review-checklist.md`, 예제 3개 |

**4주차 집합이 최소 기준선이다.** 불변식 + 퀵스타트 + 실행되는 예제 하나 + 린트가 있으면 AI가 반복할 수 있고, 그 시점부터 "AI가 무엇을 틀리는가"가 관측된다. **그 관측이 나머지 문서의 목차를 정한다** — 우리가 상상한 목차가 아니라.

### 1 회차 관측 (2026-08-26)

절차와 채점기는 `testbed/ai-exam/` 에 있다 — 고정되는 넷(프롬프트·위협 설명·
주입 파일 14개·합격 판정)과, **모델은 고정할 수 없다**는 사실을 함께 적었다.
채점은 `cargo xtask exam` 이 전부 자동으로 한다.

세 회차를 돌렸고, **셋 다 오염됐다**(같은 세션에서 저장소를 보며 썼다). 그래서
이 회차들이 실측한 것은 모델 성능이 아니라 **시험 자체의 성립 여부**다.

| 관측 | 무엇이 드러났나 | 어디에 반영했나 |
|---|---|---|
| 위협 설명을 검체 없이 썼더니 코퍼스와 5 항목이 어긋났다 | **문제와 채점 데이터가 갈라지면 응시자는 도달할 수 없다** | `THREAT.md` 를 코퍼스에서 실측해 다시 씀 + 그 규칙을 파일에 명시 |
| YARA 상수 도출은 검체를 쥐어야 되는 일이다 | 위협 설명만으로 재도출 불가 — **시험 범위가 잘못 잡혀 있었다** | 분석가가 도출한 룰을 **함께 주는** 형태로 변경 |
| 틀린 위협 설명을 검증 없이 룰로 옮겼다 | 린트·청정 코퍼스를 다 통과하고 **조용히 안 맞는다** | 안티패턴 11 |
| 관측된 것보다 좁게 썼다 (`_0x` 로 난독화기 특정) | 좁은 룰은 오탐이 아니라 **미탐**을 낳는다 | 안티패턴 10 |
| `collect_extra` 를 몰라 안 썼다 | **제품 결함이 드러났다** — YARA 가 실기기에서 미평가가 되는데 코퍼스가 그것을 가린다 | 린트 검사 신설(§7) + `20-detect-recipes.md` |

마지막 줄이 이 시험의 값을 가장 잘 보여 준다. **채점을 통과한 답이 실기기에서는
아무것도 탐지하지 못하는 상태였고**, 그 사실이 가이드의 빈칸이 아니라 **린트의
빈칸**을 가리켰다. 문서로 메울 것이 아니라 검사로 메울 자리였다.

**아직 없는 것: 오염되지 않은 회차.** 그것이 나오기 전까지 이 시험은 절차만
검증된 상태다.

### 2 차 (2026-08-26) — 마찰을 없앴고, 어제 만든 검사의 결함을 찾았다

**손으로 17 개 조각을 붙이는 절차는 반복되지 않는다.** 이 시험은 모델이 바뀔
때마다 다시 돌려야 가치가 있으므로, `cargo xtask exam --bundle` 이 한
덩어리(91 KB)로 조립한다. 조립 실수가 곧 회차 오염인데 사람은 그것을 눈치채지
못한다.

**출제 메모는 응시자에게 가지 않는다.** `THREAT.md` 구분선 위쪽에는 지난 회차가
어떻게 무너졌는지가 적혀 있다. 꾸러미는 구분선 아래만 취하고, `xtask guide` 가
누출·블록 수·치환 실패를 검사한다. 문서에 구분선이 하나 늘면 조용히 엉뚱한
데서 잘리므로 **개수까지 검사한다.**

**§7 에 신설한 본문 수집 검사에 결함이 있었다.** `collect_extra` 의 `subject`
형을 "본문을 담는다" 로 셌는데 담지 않는다 — 그것만 있고 YARA 를 쓰는
매니페스트가 통과했다. 만들 때 타입 정의만 보고 동작을 보지 않은 것이 원인이고,
`23-collect-and-submit.md` 를 쓰면서 세 형태의 차이를 설명해야 해서 드러났다.
**설명할 수 없는 것은 대개 틀린 것이다.**

### r0 (2026-08-26) — **첫 오염 없는 회차**. 그리고 채점의 한계가 드러났다

claude.ai 웹의 새 대화에서 절차대로 받았다. 앞선 셋과 달리 **이 저장소를 읽은
적 없는 응시자**다.

**입력이 깨진 채로 도달했다.** 절차가 `--bundle > 파일` 이라고 적고 있었고,
셸이 그 바이트를 세 번 손댔다 — 콘솔 코드페이지 디코드 · 리다이렉트 재인코딩 ·
개행 변환. 응시자가 받은 꾸러미는 **산문의 한글 절반이 `?` 로 소실**돼 있었다.
같은 명령이 Bash 93,884 바이트 · PowerShell 96,405 바이트를 냈다. `xtask` 가
파일에 직접 쓰도록 고쳤고 두 셸이 이제 같은 바이트를 낸다.

**그런데 §4 가 우연히 검증됐다.** *"레퍼런스는 생성물이다"* 가 만든
`machine/*.json` 이 ASCII 라서 사고를 견뎠고, 그 답에 **필드 수준 오류가
0건**이다. 손으로 적은 표였다면 함께 깨졌을 것이다.

**세 판정을 전부 통과했는데 계획이 2건 부족했다.**

| 빠진 것 | 왜 위험한가 |
|---|---|
| `autorun.remove` | 위협 설명이 *"둘 중 하나만 지우면 나머지가 다시 살린다"* 고 경고한 항목이다 |
| `av.restore_exclusions` | Defender 제외가 남아 다음 검체가 같은 폴더를 그대로 쓴다 |

`deferred` 는 0건이었다 — **조용히 빠졌다.**

| 관측 | 무엇이 드러났나 | 어디에 반영했나 |
|---|---|---|
| `from` 을 `autorun`·`process` 에 걸었다 | `from` 은 `path` 필드를 읽는다. 없는 subject 는 **전부 걸러진다** | `20-detect-recipes.md` 두 절 + 린트(§7) |
| `where` 값의 `${}` 보간을 못 썼다 | **가이드에 그 예제가 0건이었다.** 첫 플러그인은 쓰는데 | 〃 §경로가 아닌 것을 부모에 묶는 법 |
| `restore` 만 쓰고 탐지 규칙을 안 뒀다 | 무엇을 되돌리는지 가이드가 말하지 않았다 | `22-remediate-recipes.md` + 린트(§7) |
| **채점이 무엇을 지우는지 안 봤다** | 3 번은 판정만 본다 | **채점 4 번 신설** — `expected-ops.txt` |
| 응시자 지적 (e) | **§6 의 안티패턴 8 이 `process` 에 없는 필드를 썼다** | `30-antipatterns.md` §8 수정 |

마지막 줄이 §5 의 경고가 실현된 사례다 — *"AI 는 예제를 패턴으로 복제한다"*.
거부 예제뿐 아니라 **"올바른 형태" 예제도 틀려 있었다.**

응시자가 **자기 가정 다섯 개를 명시적으로 나열한 것**이 이 전부를 찾게 했다.
가정을 적지 않았다면 "왜 안 지워지는가" 로 남았을 것이다.

### r1 (2026-08-26) — **첫 온전한 합격.** 메운 빈칸이 효과를 냈다

Fable 5 (claude.ai 웹, effort 최대). 오염 없음, 온전한 입력.

```
  1. 린트 오류 0 · 2. 청정 코퍼스 파괴 0 · 3. 감염 탐지 판정 1 · 4. 계획 완결성 빠짐 0
```

채점 밖에서도 확인했다 — 감염 스냅샷 계획이 첫 플러그인과 **Op 뿐 아니라 대상까지

*"restore 가 되돌릴 증거"*. r0 이 가리킨 빈칸을 메운 것이 그대로 작동했다.

**이 Phase 의 검증 방식이 성립한다는 실증이다.** 관측 → 빈칸 → 메움 → 다음
회차에서 확인, 이 한 바퀴가 돌았다.

#### 새로 드러난 것 — 채점은 `scan_roots` 를 못 본다

응시자가 `%ALLUSERPROFILES%\AppData\Local\Programs` 로 상한을 넓혔다(첫
플러그인은 `%LOCALAPPDATA%\Programs`). 근거 있는 선택이지만 **채점이 그 차이를
전혀 못 본다.** 그 줄을 `C:/전혀없는폴더` 로 바꿔도 네 판정을 전부 통과한다.

평가기는 `remedy-platform` 을 의존할 수 없어(설계-04 §1) 토큰을 확장하지 못하고
**스냅샷에 이미 기록된 수집 범위**를 쓴다. 매니페스트의 `scan_roots` 는 수집
시점에만 쓰인다.

**r0 도 같은 자리에서 갈렸다** — `scan_roots` 에 레지스트리 경로를 넣었고,
그것은 무의미했다. `Scope::allows` 는 경로만 보고 레지스트리 계열 subject 는
`path` 가 없어 그 검사를 거치지 않는다.

**두 회차가 모두 `scan_roots` 규격을 추측했다.** `10-manifest.md` 를 썼다 —
무엇에 걸리고 무엇에 안 걸리는지, 그리고 **좁은 쪽은 아무도 경고하지 않는다**는
것. 자동 판정은 만들지 않았다(토큰 확장을 흉내 내면 그 흉내가 틀릴 때 오탐이
난다). 대신 `40-review-checklist.md` 가 실기기 `scan` 결과를 요구한다.

- §7 과광범위 검사의 임계값 — 첫 플러그인 실측 후 조정. 너무 빡빡하면 경고가 무시되기 시작하고, 그러면 검사가 없는 것과 같다
- 가이드 언어 — 현재 한국어 기준. 플러그인 작성이 사외로 확장되면 영문 병기 필요 여부 재검토
