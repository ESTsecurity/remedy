# 설계 08 — 플러그인 워크스루 2차

> 작성일: 2026-08-20 · 1차: [설계-07](설계-07-플러그인-워크스루.md)
> 1차와 겹치지 않는 위협군으로 설계의 다른 면을 때린다

## TL;DR

- **무엇을**: 랜섬웨어 잔재·DLL 사이드로딩·브라우저 하이재킹·안전모드 파괴·파일리스·USB 웜 여섯 가지를 실물 룰로 적고 코어 동작을 추적했다.
- **가장 위험한 발견**: **안전 모드 가용성을 확인하지 않고 안전 모드를 제안한다.** 악성코드가 `SafeBoot` 키를 지워 놓은 상태에서 우리가 안전 모드 재시작을 권하면 **사용자를 부팅 불가로 몰아넣는다.** 같은 문제가 재부팅 제안에도 있다.
- **가장 구조적인 발견**: **"재생성 유발자(regenerator)"와 "산출물"을 구분하지 않는다.** Chrome 정책 레지스트리를 남긴 채 확장을 지우면 브라우저가 즉시 재설치한다. 표준 순서에 이 개념이 없다.
- **누락 4건**: `.lnk` 바로가기, JSON·XML 구조화 설정, 부팅 구성, 이동식 매체 — 전부 실무 빈도가 높다.
- **자기 모순 1건**: 이동식 매체를 "기본 제외, 플러그인이 명시 선언"이라 했는데 **선언할 문법이 없다.**

## 시나리오 E — 랜섬웨어 잔재 정리

암호화는 이미 끝났다. 우리가 할 일은 **잔재 제거와 환경 원복**이다.

```yaml
detect:
  - id: ransom-note
    subject: file
    from: "%ALLUSERPROFILES%"                 # <-- 이 토큰이 없다 (결함 E3)
    where:
      all:
        - { field: path, op: glob,   value: "**\\HOW_TO_RESTORE_*.txt" }
        - { field: size, op: lt,     value: 8192 }
        - { field: sha256, op: in,   value: ["3f2a...", "9c81..."] }

  - id: assoc-hijack
    subject: registry_value
    where:
      all:
        - { field: key,  op: equals, value: "HKCR\\.txt" }
        - { field: name, op: equals, value: "" }
        - { field: data, op: not_equals, value: "txtfile" }

  - id: boot-recovery-off                      # <-- subject 가 없다 (결함 E4)
    subject: boot_config
    where:
      - { field: recoveryenabled, op: equals, value: false }
```

### 결함 E1 — 삭제 상한이 정상 치료를 막는다

랜섬노트는 감염 시 **모든 폴더에 뿌려진다.** 실제로 수천 개다. 현재 총 삭제 파일 수 상한은 1000이다.

대화형 모드는 계획 전문을 보여주고 승인받으면 진행되지만, **랜섬웨어 대응은 대개 기업 대량 배포 상황**이고 무인 모드는 프롬프트 없이 중단한다. 즉 **가장 필요한 상황에서 막힌다.**

문제의 뿌리는 상한이 **동작의 성격을 구분하지 않는다**는 점이다. "서로 다른 5천 개 파일을 지운다"와 "동일 해시의 랜섬노트 5천 장을 지운다"는 위험이 전혀 다르다.

**수정**: 상한을 **동질성(homogeneity) 기준으로 분리**한다.

- 일반 삭제: 총 1000개 (현행)
- **동일 해시 반복 항목**: 별도의 높은 상한 (초기값 20000). 같은 해시라는 것은 판정 근거가 한 번만 필요했다는 뜻이므로 위험이 개수에 비례하지 않는다
- 플러그인은 상한을 **조정할 수 없고**, 어느 상한이 적용될지는 계획기가 Action 집합을 보고 판단한다

### 결함 E2 — 대량 해시 비교의 수집 비용

`sha256 in [...]` 로 판정하려면 collect가 후보 파일을 전부 읽어야 한다. `%ALLUSERPROFILES%` 아래 사용자 문서 전체를 해시하면 성능과 프라이버시가 모두 문제다.

**수정**: 수집기가 **크기 선필터를 먼저 적용**한다. 위 룰에서 `size lt 8192` 가 `sha256` 앞에 있으므로, 계획기가 조건을 재배열해 **싼 조건을 먼저 평가**하고 통과한 것만 해시한다. 이것을 스키마 수준의 보장으로 명시한다 — 작성자가 조건 순서를 최적화하지 않아도 되게.

### 결함 E3 — 모든 사용자 프로필을 가리키는 토큰이 없다

레지스트리에는 `HKU\*` 라는 지정 확장을 두었는데(설계-02 §3), **파일 경로에는 대응물이 없다.** `C:\Users\*` 를 `scan_roots` 에 적으면 범위가 지나치게 넓고 드라이브 문자가 고정된다.

**수정**: `%ALLUSERPROFILES%` 토큰을 지정 확장으로 추가한다. `HKU\*` 와 대칭이며, 확장 결과에 프로필 수 상한을 건다.

### 결함 E4 — 부팅 구성을 다룰 수 없다

랜섬웨어는 흔히 복구를 막는다 — `recoveryenabled No`, `bootstatuspolicy ignoreallfailures`. 이것을 되돌리지 않으면 **다음 사고 때 사용자가 복구 환경에 들어가지 못한다.** 재발 방지의 정확한 대상인데 subject도 Op도 없다.

**수정**: `boot_config` subject + `boot.restore_default` Op. 값 집합이 작고 OS 기본값이 명확하므로 카탈로그 방식이 잘 맞는다.

### 확인된 비목표

볼륨 섀도 복사본은 이미 삭제됐고 **복구하지 않는다** — 데이터 복구는 비목표다(설계-00 §3). `vssadmin` 실행을 앞으로 막는 것도 하지 않는다 — 새 방어 추가는 비목표다. **설계가 여기서는 흔들리지 않았다.**

## 시나리오 F — DLL 사이드로딩

정상 서명된 `LegitApp.exe` 옆에 악성 `version.dll` 을 두어, 정상 프로그램이 악성 코드를 로드하게 한다.

### 버틴 것 — 재귀 삭제 가드가 정상 프로그램을 지켰다

`dir.delete_recursive` 의 guard 조건은 "그 디렉터리 안에 악성 판정 파일 1개 이상"이다. 사이드로딩 폴더에는 악성 DLL이 있으므로 **guard만 보면 통과한다** — 그러면 정상 프로그램 폴더가 통째로 사라진다.

그런데 설계-03 §4의 세 번째 조건이 이것을 막는다.

> 하위에 신뢰 서명 파일이 존재하면 거부

`LegitApp.exe` 가 유효 서명을 가지므로 재귀 삭제가 **파괴 직전에 거부된다.** 작성자는 DLL만 개별 삭제하도록 룰을 고치게 된다. 설계 의도대로다.

> **2026-08-25 (P10-C) 정정 — "계획에 들어가지 않는다" 가 아니다.** 이 조건을 실제로 채우려고 보니 **계획기가 판정할 재료를 가질 수 없었다.** 스냅샷에는 매치된 증거만 담기고 그 디렉터리 아래의 모든 파일이 아니며, 계획기는 파일 시스템을 열거할 수 없다(설계-03 §1). 실행기가 백업 **전에** 확인하고 거부하므로 "정상 프로그램 폴더가 통째로 사라지는 것을 막는다" 는 성질은 그대로다. 판정 자리가 옮겨진 것이고, 설계-03 §4 에 `process.kill` 상한과 함께 예외로 적었다.
>
> 이 시나리오가 실제 시험이 됐다 — `remedy-platform` 의 `trusted_in_dir` 이 실기기 `notepad.exe` 를 악성 파일 옆에 두고 그 폴더가 거부되는지 잰다.

### 결함 F1 — 로드된 모듈로 프로세스를 지목할 수 없다

악성 DLL은 정상 프로세스에 로드되어 **잠겨 있다.** 잠금을 풀려면 그 프로세스를 종료해야 하는데, `process.kill` 의 `match` 는 `image_path` 와 `cmdline_contains` 만 지원한다. **"이 DLL을 로드한 프로세스"를 지목할 문법이 없다.**

`process` subject에 `modules[]` 는 있으므로 관찰은 되는데 종료 술어에서 쓸 수 없다.

**수정**: `process.kill` 의 `match` 에 `loaded_module` 조건 추가.

### 결함 F2 — "프로그램이 깨질 수 있다"를 말하지 않는다

악성 DLL을 지우면 `LegitApp.exe` 는 실행 시 오류가 난다. **정상 프로그램을 지우지 않은 것은 옳지만, 그 프로그램이 더 이상 동작하지 않는다는 사실은 사용자가 알아야 한다.**

현재 `user_impact` 는 `app_terminate`(작업 손실)만 상정했다.

**수정**: `user_impact.kind` 에 `app_broken` 추가 — "이 프로그램을 다시 설치해야 할 수 있습니다".

## 시나리오 G — 브라우저 하이재킹 (가장 많이 무너진 곳)

```yaml
detect:
  - id: force-policy
    subject: registry_value
    where:
      all:
        - { field: key,  op: glob, value: "HKLM\\SOFTWARE\\Policies\\*\\Chrome\\ExtensionInstallForcelist" }
        - { field: data, op: contains, value: "${ext.ext_id}" }

  - id: ext
    subject: browser_extension
    where:
      - { field: ext_id, op: equals, value: "kkoj..." }

  - id: pref-hijack
    subject: structured_config          # <-- subject 가 없다 (결함 G2)
    from: "%ALLUSERPROFILES%\\AppData\\Local\\Google\\Chrome\\User Data\\*\\Preferences"
    where:
      - { field: "homepage", op: contains, value: "search-hijack" }

  - id: lnk-hijack
    subject: shortcut                    # <-- subject 가 없다 (결함 G1)
    where:
      all:
        - { field: target, op: matches,  value: "(?i)\\\\chrome\\.exe$" }
        - { field: args,   op: contains, value: "--load-extension=" }

remediate:
  remove:
    - { ref: force-policy }
    - { ref: ext }
  edit:
    - { ref: lnk-hijack,   op: strip, value: "--load-extension=${ext.ext_dir}" }
    - { ref: pref-hijack,  op: set_key, key: "homepage", to: default }
```

### 결함 G1 — `.lnk` 바로가기를 다룰 수 없다 (실무 빈도 최상위)

애드웨어의 기본 수법이다. 브라우저 바로가기의 **인자에 확장 로딩 옵션이나 광고 URL을 덧붙인다.** 사용자가 바탕화면 아이콘을 누를 때마다 재감염된 것처럼 보인다.

`.lnk` 는 바이너리 포맷이라 `text_config` 로 다룰 수 없고, subject도 Op도 없다. **바로가기를 지우면 사용자의 아이콘이 사라지므로 삭제는 답이 아니다 — 인자만 떼어내야 한다.**

**수정**: `shortcut` subject(`path, target, args, working_dir, icon`) + `shortcut.strip_args` Op.

### 결함 G2 — JSON·XML 설정을 다룰 수 없다

Chrome `Preferences` 는 JSON이고 브라우저 정책·일부 애플리케이션 설정은 XML이다. `text_config` 는 **라인 기반**이라 맞지 않는다. JSON 한 줄에 전체가 들어 있을 수도 있고, 라인을 지우면 파일이 깨진다.

**수정**: `structured_config` subject — 포맷(json/xml/ini)을 선언하고 **키 경로**로 지정한다. Op는 `structured_config.remove_key` 와 `structured_config.restore_default`.

라인 편집과 구조 편집을 같은 subject로 묶지 않는 이유는 **깨뜨리는 방식이 다르기 때문**이다. 라인 제거는 최악의 경우 설정 하나를 잃지만, JSON 라인 제거는 **파일 전체를 파싱 불가로 만든다.**

### 결함 G3 — 재생성 유발자와 산출물을 구분하지 않는다 (구조적)

`ExtensionInstallForcelist` 정책을 남긴 채 확장을 지우면, **Chrome이 다음 실행에서 즉시 재설치한다.** 확장은 산출물이고 정책이 유발자다.

현재 표준 순서(설계-03 §2)는 이렇다.

```
  1. 자동 소생 차단 : 서비스 복구 동작 제거, 서비스 정지
  2. 잠금 해제      : 프로세스 정지 -> 종료
  3. 재기동 차단    : 작업·서비스·자동실행 비활성화
  4. 백업
  5. 제거·편집
```

**정책 레지스트리는 3단계의 "작업·서비스·자동실행" 어디에도 속하지 않는다.** 그래서 5단계에서 확장과 나란히 제거되고, 순서가 보장되지 않는다.

같은 형태가 곳곳에 있다.

| 유발자 | 산출물 |
|---|---|
| Chrome 정책 `ExtensionInstallForcelist` | 브라우저 확장 |
| 예약 작업 | 드롭되는 페이로드 파일 |
| 서비스 | 작업 디렉터리 |
| MDM·GPO 유사 설정 | 설치되는 구성 |

**수정**: Op마다 **`regenerator` 속성**을 두고, 계획기가 3단계를 "재기동·재설치 유발자 제거"로 확장한다. 산출물 제거보다 **반드시 먼저** 수행한다.

이것은 플러그인이 순서를 적는 것이 아니다 — 코어가 Op의 성격을 알고 정렬한다. 설계-03 §2의 "순서는 플러그인이 아니라 코어가 정한다" 원칙 그대로다.

### 결함 G4 — 다중 프로필 순회 (E3과 동일)

`User Data\*\Preferences` 의 프로필 와일드카드는 글로브로 되지만, `C:\Users\*` 는 E3의 `%ALLUSERPROFILES%` 토큰이 필요하다.

## 시나리오 H — 안전 모드 파괴 (가장 위험한 발견)

악성코드가 `HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot` 를 삭제해 **안전 모드 진입을 막는다.** 실제로 흔한 수법이다.

### 결함 H1 (치명) — 안전 모드를 확인 없이 제안한다

설계-00 §6은 이렇게 되어 있다.

> `apply` 중 실패 발생 → 실패 유형이 (파일 잠금 · 접근 거부 · 재생성 확인) 인가? → 예: **안전 모드 재시작을 제안**

**안전 모드가 살아 있는지 확인하지 않는다.** `SafeBoot` 키가 지워진 상태에서 사용자가 우리 제안을 따르면 **부팅이 되지 않는다.** 치료하러 온 도구가 시스템을 못 쓰게 만드는 것이며, 설계-00 §1의 1순위를 정면으로 위반한다.

**수정**: 안전 모드 제안 **전에 가용성을 확인**한다. `SafeBoot` 키 존재와 최소 하위 구조를 점검하고, 손상됐으면 제안하지 않고 **손상 사실 자체를 보고**한다.

### 결함 H2 (치명) — 재부팅 제안에도 같은 문제가 있다

`verify_after_reboot` 와 재시도 큐는 재부팅을 전제한다. 그런데 부팅 구성이 이미 망가진 상태(BCD 변조, 부트 파일 손상)라면 **"재부팅하세요"가 최악의 조언**이 된다.

**수정**: 재부팅을 요구하는 계획은 **부팅 건전성 점검을 선행 Action으로 포함**한다. 점검 실패 시 재부팅을 요구하지 않고 부분 치료로 마감하며, 복구 매체 준비를 안내한다.

### 결함 H3 — 손상된 OS 구조의 복원 한계

`SafeBoot` 하위에는 수백 개 항목이 있다. `registry.restore_default` 의 카탈로그로 전부 담는 것은 현실적이지 않다.

**정직한 결론**: v1에서 **복원하지 않고 탐지·보고만 한다.** 복원은 OS 복구 도구의 영역이며, 우리가 어설프게 복원하면 더 나빠질 수 있다. 다만 **탐지는 반드시 한다** — 알지 못한 채 안전 모드를 권하는 것이 결함 H1이기 때문이다.

### 결함 H4 — `registry.restore_default` 카탈로그 범위가 정의되지 않았다

무엇이 카탈로그에 들어가는지, 없는 항목을 요구하면 어떻게 되는지 정하지 않았다.

**수정**: 카탈로그는 **값 하나로 복원이 완결되는 항목**만 담는다(`Winlogon\Shell`, `Winlogon\Userinit`, 주요 확장자 연결, 부팅 구성 플래그). 카탈로그에 없는 대상을 `to: default` 로 지정하면 `plugin lint` 가 거부하고 유효 목록을 보여준다.

## 시나리오 I — 파일리스 (레지스트리 페이로드)

페이로드를 `HKCU\Software\Classes\<랜덤>` 값에 base64로 저장하고, 예약 작업이 PowerShell로 읽어 실행한다.

### 결함 I1 — YARA를 파일 밖 데이터에 적용할 수 없다

`yara:` 연산자는 파일 대상으로만 설계됐다(`from:` 경로). **레지스트리 값의 `data` 에 YARA 룰을 돌릴 문법이 없다.** 파일리스 위협에서 페이로드는 파일이 아니다.

**수정**: `yara` 연산자를 **바이트열을 제공하는 모든 필드**에 적용 가능하게 한다 — `registry_value.data`, `text_config.line`, `structured_config` 값, 파일 내용. 스키마에서 필드가 바이트열을 제공하는지 여부를 표시한다.

### 결함 I2 — 인코딩을 풀 수 없다

값이 base64면 원문 패턴이 매치되지 않는다. `capture` 파이프 함수 목록(`first_path` `dirname` `basename` `lower` `expand_env` `trim_quotes`)에 디코딩이 없다.

**수정**: `base64_decode` · `hex_decode` 추가. 디코딩 결과 크기에 상한을 두고, 초과 시 미매치로 처리한다.

### 결함 I3 — 인코딩된 커맨드라인

`powershell.exe -EncodedCommand <base64>` 는 `cmdline_contains` 로 원문을 찾을 수 없다.

**수정**: 수집기가 `process` 에 **디코딩된 커맨드라인**을 부가 필드로 제공한다(`cmdline_decoded`). 이것은 룰이 아니라 수집기가 하는 것이 옳다 — 모든 플러그인이 같은 디코딩을 반복 구현하면 품질이 갈린다.

## 시나리오 J — USB 웜 (설계 자기 모순)

`autorun.inf` + 페이로드를 이동식 매체에 둔다.

### 결함 J1 — 선언할 문법이 없다

설계-00 §5-2는 이렇게 되어 있다.

> 네트워크 드라이브·이동식 매체 상의 대상 → 기본 제외. **포함하려면 플러그인이 명시 선언**

**그 명시 선언을 적을 곳이 없다.** `scan_roots` 는 경로를 적는데 이동식 매체는 드라이브 문자가 고정되지 않는다.

**수정**: 매니페스트에 `allow_removable: true` 를 두고, `scan_roots` 에 `%REMOVABLE%` 지정 토큰을 허용한다. 이 조합이 없으면 이동식 매체는 수집 대상에서 제외된다.

### 결함 J2 — 이동식 매체 삭제는 별도 승인이 필요하다

USB는 **다른 사람의 것일 수 있고**, 작업 도중 뽑힐 수 있다. 무인 모드에서 자동으로 남의 USB를 지우는 것은 허용해서는 안 된다.

**수정**: `%REMOVABLE%` 대상 파괴 Action은 **대화형에서 별도 승인**을 받고, 무인 모드에서는 계획에 포함되지 않는다. 연결 해제는 실패로 기록하고 재시도 큐에 넣지 않는다(다음 부팅 때 다른 매체일 수 있으므로).

|---|---|---|---|

## 2차에서 버틴 것

- **재귀 삭제의 신뢰 서명 조건**이 DLL 사이드로딩에서 정상 프로그램 폴더를 지켰다 (시나리오 F)
- **데이터 복구·새 방어 추가 비목표**가 랜섬웨어 앞에서 흔들리지 않았다 (시나리오 E)
- **부분 편집(`edit`)** 이 1차에서 추가되지 않았다면 시나리오 G가 전부 막혔을 것이다 — 1차 수정이 2차에서 값을 했다
- **`user_impact`** 역시 1차 추가분이며 F2에서 종류만 늘리면 됐다
- **T3 경계**가 이번에도 조용한 미탐이 아니라 린트 오류로 나타난다

## 두 차례 워크스루가 시사하는 것

1차 9건, 2차 17건. **수렴하지 않고 있다.** 이것은 설계가 나쁘다는 뜻이 아니라 **위협의 표현 공간이 넓다**는 뜻이며, 설계-01 D10의 판단을 뒷받침한다 — T2(선언적 확장)를 넓게 잡지 않으면 자립률이 오르지 않는다.

동시에 경고이기도 하다. **SDK 표면이 계속 넓어지면 스키마 검증과 린트가 따라가지 못한다.** 3차 워크스루를 하기 전에 **부트스트랩 2주차의 스키마 단일 소스와 린트를 먼저 만들고, 그 위에서 워크스루를 반복하는 편이 낫다.** 지금은 문서만으로 검증하고 있어 놓치는 것이 반드시 있다.
