# 설계 00 — 위협 모델 · 범위 · 지원 대상

> 작성일: 2026-08-20 · 다른 모든 설계 문서의 전제
> 후속: [설계-01](설계-01-아키텍처-결정.md) · [설계-02](설계-02-SDK-계약.md) · [설계-03](설계-03-안전장치.md) · [설계-04](설계-04-저장소-부트스트랩.md)

## TL;DR

- **무엇을**: remedy가 무엇과 싸우고 무엇과는 싸우지 않는지, 어떤 환경에서 도는지를 확정한다. 이것이 없으면 안전장치의 강도를 정할 근거가 없다.
- **가장 중요한 비목표 두 가지**: remedy는 **커널 모드 루트킷을 다루지 않고**, **활성 악성코드와 정면으로 싸워 이기려 하지 않는다.** 그 경우 안전 모드·부팅 미디어로 회피한다.
- **확인된 제약**: Rust 기본 Windows 타깃은 **Windows 7/8.1을 지원하지 않는다.** 지원하려면 tier 3 타깃과 nightly 빌드가 필요하다 — 지원 여부를 사업 판단으로 먼저 결정해야 한다(§4).

---

## 1. 보호해야 할 것

우선순위 순이며, 충돌 시 위가 이긴다.

1. **사용자 시스템의 무결성** — 오탐으로 정상 파일·설정을 파괴하지 않는다. 이것이 1순위인 이유는 설계-03 서두에 있다
2. **격리물의 복원 가능성** — 잘못 지운 것을 되돌릴 수 있어야 한다
3. **도구가 전용되지 않을 것** — 서명된 파괴 도구가 임의 지시서를 받아들이면 그 자체가 무기다
4. **치료의 실효성** — 위협이 실제로 제거되고 재부팅 후에도 돌아오지 않는다

4번이 마지막인 것은 의도적이다. **못 지우는 것보다 잘못 지우는 것이 나쁘다.**

## 2. 공격자 모델

### T1. 감염 호스트에서 활동 중인 악성코드

**가정하는 능력** (사용자 권한 ~ 관리자/SYSTEM):

- 종료된 프로세스를 **재생성**한다 (watchdog 쌍, 예약 작업, 서비스)
- 파일·레지스트리 키에 **거부 ACL**을 걸어 삭제를 막는다
- 파일을 **잠근다** (열린 핸들, 공유 거부)
- **시스템 시계를 조작**한다
- **보안 제품 예외 목록**에 자기 경로를 등록한다
- 우리 프로세스를 **종료시키려 한다**
- 정상 코드서명 인증서로 **서명되어 있다** (EvilAI 계열의 실제 특징)

**대응하는 설계**:

| 능력 | 대응 | 위치 |
|---|---|---|
| 프로세스 재생성 | 술어 기반 종료 + 유한 재시도 + 재부팅 후 재시도 큐 | 설계-03 §1·§5 |
| 잠긴 파일 | 재부팅 시점 삭제 예약 | 설계-02 §6 Op |
| 시계 조작 | 신뢰 판정을 만료가 아닌 **컴파일 내장 버전 정수**로 | 설계-03 §6 |
| 예외 목록 등록 | 탐지 근거이자 원복 대상으로 1급 취급 | 설계-02 §3 |
| 서명된 악성코드 | 서명 화이트리스트를 플러그인이 명시적으로 뚫도록 | 설계-03 §3 2층 |

**대응하지 않는 것 (명시적 비목표)**:

- **커널 모드 루트킷** — 사용자 모드 도구는 은폐된 파일·키·프로세스를 볼 수 없다. **보이지 않는 것은 지울 수 없다.** 우리는 이를 탐지 실패로 조용히 넘기지 않고, 정황(예: 예약 작업 XML은 있는데 API가 반환하지 않음)을 발견하면 **부팅 미디어 경로를 안내**한다
- **자기방어 경쟁** — 악성코드가 우리를 죽이고 우리가 다시 뜨는 식의 경쟁을 하지 않는다. 그런 위협은 안전 모드·오프라인 부팅으로 회피하는 것이 정답이다
- **드라이버 언로드·커널 패치 복구**

### T2. 플러그인 작성자 (악의 또는 실수)

훨씬 현실적인 위협은 악의가 아니라 **실수**다. 오탐 룰 하나가 고객 PC를 망가뜨리는 경로가 가장 짧다.

- 미서명 플러그인 로드 거부
- 파괴 동작은 **닫힌 집합**, 새 동작은 플러그인이 아니라 코어에 추가
- 보호 경로 불가침, 삭제 상한, 증거 링크 필수
- `scan_roots` 로 읽기 범위 제한
- 출시 게이트 G1~G8 통과 강제

**대응하지 않는 것**: 서명 키 자체의 유출. 이 경우는 폐기 목록 + 최소버전 상향으로 사후 대응한다(설계-03 §6).

### T3. 배포 경로 공격자

- 매니페스트 전체 서명 + 역행 금지
- 폐기 목록도 서명 대상

**대응하지 않는 것**: 우리 빌드·서명 인프라 자체의 침해. 이는 공급망 보안 영역이고 이 문서의 범위 밖이다. 다만 **코어 바이너리도 서명해 배포**한다(설계-01 D7).

### T4. 인텔 경로 (조회 응답 · 제출 채널)

`enrich` 와 `submit` 을 넣으면서 생긴 표면이다(설계-01 D9).

| 위협 | 대응 |
|---|---|
| 조회 응답을 조작해 **정상 파일을 지우게 유도** | 구조적으로 불가능하다. 조회는 삭제를 **줄일 수만** 있고 늘릴 수 없다 (D9 결정 3, 설계-03 §3 5층) |
| 조회 응답을 조작해 **치료를 회피** | 결과는 "치료 안 함"이며, 도구를 실행하지 않은 상태와 같다. 오탐보다 나은 실패다 |
| 조회 응답 파서를 노린 **손상된 응답** | 응답 파서를 퍼징 대상에 포함 (설계-04 §3.4) |
| 제출 데이터 가로채기 | 전송은 우리가 하지 않는다 — 파일 생성이 기본이고, 전송 주체는 고객사 인프라 (D9 결정 4) |
| **사내 분석 시스템 자체의 침해** | 조회 결과가 파괴를 늘릴 수 없으므로 피해가 "잘못된 제외"로 한정된다. 시스템 자체의 보호는 이 문서 범위 밖 |

**첫 줄이 이 설계의 요점이다.** 조회 결과가 파괴 대상을 만들 수 있었다면 위 표의 나머지가 전부 심각해졌을 것이다. 방향을 한쪽으로 막아 두었기 때문에 인텔 경로가 뚫려도 최악이 미탐에 그친다.

## 3. 비목표 (Non-goals)

혼동을 막기 위해 명시한다. remedy는 아래를 **하지 않는다.**

| 하지 않는 것 | 이유 |
|---|---|
| 실시간 보호·상주 감시 | 본 제품 엔진의 역할. remedy는 단발 실행 도구다 |
| 범용 안티바이러스 스캔 (전 디스크) | 특정 위협 제거가 목적. 스캔 범위는 플러그인이 선언한다 |
| 커널 드라이버 | 사용자 모드 전용. 드라이버를 넣는 순간 2차 사고의 폭발 반경이 커지고, 그것이 이 제품의 존재 이유와 정면 충돌한다 |
| 루트킷 탐지·제거 | T1 참조 |
| 랜섬웨어 복호화·데이터 복구 | 별개 문제 영역 |
| 원격 관리 콘솔 | CLI + JSON 이 통합 지점. 콘솔은 상위 제품이 담당 |
| 네트워크 차단·방화벽 제어 | hosts·프록시 **원복**은 하지만 능동 차단은 하지 않는다 |

### "재발 방지"의 경계

remedy의 재발 방지는 **악성이 바꿔 놓은 것을 원복하는 데까지**다 — 보안 제품 예외 목록, `hosts`, 프록시 설정, 악성 루트 인증서, 오염된 로그온 값. 이것들을 되돌리지 않으면 파일과 프로세스를 다 지워도 재감염 경로가 열려 있다.

**새로운 방어를 추가하는 것은 아니다.** 방화벽 규칙 추가, 정책 강화, 실행 차단 목록 등록은 하지 않는다. 그것은 본 제품 엔진의 역할이고, 전용백신이 고객 시스템에 새 정책을 심으면 **제거 시점에 무엇을 되돌려야 하는지 아무도 모르게 된다.**

이 경계를 플러그인 작성 가이드에 명시한다(설계-06). 명시하지 않으면 작성자가 룰로 방어 정책을 심으려 한다.

## 4. 지원 대상 환경

### Windows

| 대상 | 지원 | 근거 |
|---|---|---|
| Windows 10/11 (x64) | **v1 지원** | Rust `x86_64-pc-windows-msvc` 기본 타깃. 실측 검증 완료 |
| Windows 10/11 (x86 32비트) | **v1 지원** | `i686-pc-windows-msvc`. yara-x 빌드·실행 실측 완료 |
| Windows Server 2016+ | **v1 지원** | 위와 동일 타깃. GUI 없는 환경이라 CLI 필수 |
| **Windows 7 / 8.1 / Server 2008 R2·2012** | **미정 — 사업 판단 필요** | 아래 |
| Windows on ARM (aarch64) | v1 범위 밖 | 수요 확인 후 |

**Windows 7 문제 (확인된 사실)**: 로컬 툴체인에서 `x86_64-win7-windows-msvc` / `i686-win7-windows-msvc` 가 **별도 타깃으로 존재**하고, `rustup target list` 에는 **없다**. 즉 tier 3이며 표준 라이브러리 프리빌트가 배포되지 않는다. 지원하려면 nightly + `-Z build-std` 로 std를 직접 빌드해야 하고, yara-x·wasmtime 의존 트리 전체가 그 타깃에서 빌드되는지는 **미검증**이다.

> **이것은 기술 결정이 아니라 사업 결정이다.** 국내 산업 현장·폐쇄망에 Windows 7이 남아 있는지, 그 환경이 전용백신의 실제 배포 대상인지를 먼저 확인해야 한다. 대상이라면 부트스트랩 1주차에 tier 3 빌드 가능성을 실증하고, 불가하면 **해당 환경은 별도 수단(기존 단품 도구)으로 대응한다고 명시적으로 선언**해야 한다. 조용히 지원하지 않는 것이 가장 나쁘다.

### Linux

| 대상 | 지원 |
|---|---|
| x86_64 주요 배포판 (RHEL 계열, Debian/Ubuntu) | **v1 지원** (수집기는 6주차 이후) |
| aarch64 | v1 지원 (동일 코드, 타깃만 추가) |
| 32비트 Linux | v1 범위 밖 |

### macOS

v1 범위 밖. Apple의 SDK 계약상 비-Apple 하드웨어 크로스 빌드가 불가하므로, 지원 시 **Apple 하드웨어 CI 러너 확보가 선행**되어야 한다(설계-01 D3).

## 5. 실행 환경과 모드

| 모드 | 용도 | 안전 정책 |
|---|---|---|
| **진단** (`collect`) | 지원 엔지니어가 고객 PC에서 아티팩트만 수집 | **파괴 동작이 존재하지 않는다.** 플러그인도 필요 없다 |
| **대화형** | 사용자·엔지니어가 직접 실행 | 계획을 사람이 읽을 형태로 제시하고 승인받는다. 신선도 경고는 표시하되 진행 |
| **무인** (`--yes`) | 기업 대량 배포 | 가드 위반 시 프롬프트 없이 **중단**. 신선도는 온라인 확인 또는 **오프라인 폐기 목록 반입**으로 충족 (설계-03 §6) |
| **분석가** | `collect`/`evaluate`/`plan`/`apply` 분리 실행 | 계획을 파일로 검토·보관·재실행. 스냅샷으로 룰 반복 개발 |
| **안전 모드** | 활성 악성코드 회피 | 잠금·재생성 문제가 확인되면 안내. §6 |
| **부팅 미디어** | 최후 수단 (루트킷 정황, 부팅 불가) | v1 범위 밖. 경로만 설계에 남긴다 |

### 진단 모드가 별도로 존재하는 이유

전용백신은 보통 **고객 지원 채널을 통해** 배포된다. 실제 흐름은 "고객 신고 → 지원 엔지니어 진단 → 분석가 판단 → 플러그인 제작 → 배포"인데, 앞의 두 단계에 쓸 도구가 설계에 없었다. `collect` 는 그 자리를 메운다.

- 고객 PC에서는 **아무것도 지우지 않는다.** 파괴 동작 자체가 그 코드 경로에 없다
- 산출물(`artifacts.json`)이 곧 **새 플러그인의 입력**이자 **회귀 코퍼스의 재료**가 된다
- 분석가가 사내에서 `evaluate` 를 돌려 룰을 만들고, 그 룰이 같은 스냅샷에서 검증된다

이 하나가 "첫 플러그인을 만들며 없는 API를 기록한다"는 반복 주기를 몇 주에서 몇 시간으로 줄인다.

### 권한 — 기계를 만지면 관리자를 요구한다 (2026-09-01 결정)

이 표의 어느 모드에도 *"비관리자로 돈다"* 는 약속이 없었다. 그런데 코드에는
그것을 막는 것도 없어서, 권한이 모자란 실행이 **반쯤 돌았다.**

실측(2026-08-31, 감염된 실기기): 표준 사용자로 `scan` 을 돌리면
`System32\Tasks` 가 거부되고 **증거 0건 · 판정 0건**이 나온다. 종료 코드는
6이었다 — 관측 완전성 장치가 제 일을 해서 *"이 결과 위에서 '위협 없음' 을 말할
수 없다"* 고 말했다. 그 자체는 옳다. **그러나 그것은 마지막 방어선이지 첫 줄이
아니다.** 할 수 없는 일이면 시작하기 전에 한 문장으로 말해야 한다.

그래서 **기계를 만지는 명령은 관리자(Windows) · root(Linux) 를 요구한다.**
없으면 종료 코드 5(안전 가드 중단)로 무엇을 하라고 말하고 끝낸다. 사용법
오류(4)가 아니다 — 명령은 옳고 환경이 모자라며, 무인 배포에서 그 둘은 완전히
다른 후속 조치를 요구한다.

경계는 하나다 — **이 명령이 이 기계를 읽거나 쓰는가.**

| | 명령 |
|---|---|
| **요구한다** | `collect` · `scan` · `run` · `apply` · `resume` · `restore` · `verify` |
| **요구하지 않는다** | `evaluate` · `plan` · `plugin lint`/`verify` · `revocation`/`allowlist` 의 `verify`·`import` · `support-bundle` · `selftest` · `--version` |

아래쪽은 **명령줄로 받은 파일만** 만진다. 위 표의 *분석가 모드* — 사내에서
스냅샷으로 룰을 반복 개발하는 자리 — 와 룰 작성자가 자기 PC 에서 `plugin lint`
를 돌리는 자리가 거기다. 그 둘에 관리자를 요구하면 룰 개발이 통째로 막힌다.
(`import` 는 상태 디렉터리에 쓰지만 그것은 우리 폴더이지 기계가 아니다.)

**관리자라고 다 되는 것은 아니다.** 실측(2026-08-31, 관리자 세션): 프로세스
159개 중 19개의 명령줄을 읽지 못했다(csrss·services·wininit). 변조 방지가 막는
Defender 예외 키, `TrustedInstaller` 가 소유한 `SafeBoot` 하위도 그대로 남는다.
**그러므로 이 요구가 관측 완전성 보고(종료 코드 6)를 대신하지 않는다.** 둘 다
있어야 한다 — 앞의 것은 "시작할 수 있는가", 뒤의 것은 "본 것을 믿어도 되는가"
를 답한다.

권한을 **재지 못한 경우**(`None`)도 거절한다. 모르는 것을 "괜찮다" 로 접지
않는다.

**어떻게 재는가.** 토큰을 직접 묻는 길은 `unsafe` 를 요구하고 그 크레이트는
`forbid` 를 지킨다(설계-04 §1). 그래서 **관리자만 열 수 있는 자리를 하나 읽어
본다** — Windows 는 `System32\Tasks`, Linux 는 `/proc/self/status` 의 유효 UID.
Windows 쪽을 굳이 이 자리로 고른 것은, 그곳이 못 읽었을 때 실제로 손해가 나는
바로 그 디렉터리이기 때문이다. 권한 질문의 대리 지표가 아니라 질문 그 자체다.
레지스트리에 시험 삼아 써 보는 방법은 쓰지 않는다 — 죽으면 찌꺼기가 남고, 어떤
환경에서는 가상화되어 **거짓으로 통과한다**(실측: 샌드박스 안에서
`HKLM\SYSTEM\CurrentControlSet\Services` 에 값이 써졌다).

**실측 (2026-09-01, 배포 빌드 · Win10x64-Test VM)**

| 잰 것 | 결과 |
|---|---|
| 관리자 세션에서 `collect` | `exit 0` · 산출물 생성됨 — 문이 길을 막지 않는다 |
| 표준 사용자로 `collect` | `exit 5` · 산출물 없음 · *"관리자 권한이 필요하다 … 다시 부를 것"* |
| 표준 사용자로 `--version` | `exit 0` — 문을 지나지 않는 명령은 그대로 돈다 |
| 표준 사용자 + 시험용 되돌림 | `exit 5` — **되돌림은 배포 빌드에 없다**(`debug_assertions` 로 컴파일 시점에 사라진다) |
| 재부팅 뒤 RunOnce 의 `verify` | `outcome=clean exit=0` — P10-F 7건 전부 통과. HKLM RunOnce 가 권한을 가지고 돈다는 §2 의 전제가 이 문 아래에서도 성립한다 |

> Windows 앱 매니페스트의 `requireAdministrator` 는 **넣지 않았다.** 그것은
> Windows 가 프로세스 시작 자체를 막는 방식이라 UAC 프롬프트를 띄우는데, 무인
> 배포(`--yes`)에서 프롬프트는 응답할 사람이 없어 그대로 멈춘다. 런타임 검사는
> 같은 자리에서 거절하면서 **왜 그런지 stderr 로 말하고 종료 코드를 남긴다.**

### 동시 실행

전역 뮤텍스로 **동일 호스트에서 한 번에 하나만** 실행한다. 두 인스턴스가 같은 대상을 지우려 하면 저널·격리소가 깨진다.

## 5-1. 보안 제품과의 공존 — 주 배포 환경은 "이미 백신이 깔린 PC"다

remedy가 도는 곳은 백신이 없는 깨끗한 실험실이 아니다. **대개 자사 제품이 이미 설치되어 실시간 감시가 돌고 있는 고객 PC**다. 이 사실을 설계에 넣지 않으면 현장에서 다음이 벌어진다.

| 충돌 | 증상 |
|---|---|
| 실시간 감시가 파일 삭제를 가로챈다 | 삭제 실패인데 원인이 악성코드인지 백신인지 구분 안 됨 |
| 백신이 remedy를 의심스러운 도구로 탐지 | 실행 자체가 차단되거나 격리됨 |
| 백신이 remedy의 격리 컨테이너를 탐지·격리 | 복원 불가 상태가 됨 |
| 백신이 삭제 직후 파일을 자기 격리소로 가져감 | 우리 격리소와 이중 격리, 복원 시 충돌 |

**설계에 반영하는 것:**

- **코드서명 기반 사전 등록.** remedy 바이너리는 서명되며(설계-01 D7), 자사 제품 쪽에 **서명 주체 기준으로 사전 화이트리스트**를 요청한다. 경로나 해시 기준이면 버전마다 갱신해야 하므로 서명 기준이어야 한다
- **실시간 감시를 끄지 않는다.** 치료 도구가 백신을 무력화하는 기능을 가지면 그 기능 자체가 악성코드의 표적이 된다. 대신 **실패를 정확히 진단**한다 — 접근 거부의 원인이 보안 제품인지 악성코드인지 구분해 보고한다
- **설치된 보안 제품 목록을 진단 정보에 포함**한다. 타사 제품과의 충돌은 통제할 수 없지만, 지원 대응에서 이 정보가 있고 없고가 해결 시간을 가른다
- **격리 컨테이너 봉인**(설계-03 §5)의 목적 중 하나가 정확히 이것이다 — 타 백신이 격리물을 재탐지해 가져가는 것을 막는다
- **자사 제품의 예외 목록도 `av_exclusion` 관찰 대상에 포함**한다. 악성코드가 Defender만 건드린다는 보장이 없다

### 전용백신이 최종 목적지가 아니라는 점

이 제품의 전략적 목적은 **치료 능력을 검증해 본 제품 엔진으로 승격시키는 것**이다. 그렇다면 승격에 필요한 것이 처음부터 산출되어야 한다.

- **룰 스키마는 엔진 팀이 읽고 이관할 수 있는 형태**여야 한다. 그래서 선언적 룰이고(설계-01 D4), 그래서 스키마가 단일 소스에서 생성된다
- **감사 로그가 정량 근거가 되어야 한다.** "치료가 잘 됐다"가 아니라 **치료 성공률·잔존율·오탐 건수·복원 요청 건수**가 집계 가능해야 한다. 로그 스키마(설계-03 §7)에 이 집계가 가능한 필드가 들어 있는지를 설계 검토 항목으로 둔다
- 이관 시점에 다시 만들지 않아도 되도록, **격리·복원 모듈이 엔진에서 재사용 가능한 경계**로 분리되어 있어야 한다(설계-04 §1의 `remedy-quarantine` 독립 크레이트)

## 5-2. 다뤄야 할 예외 상황

설계가 조용히 가정하고 있던 것들을 명시한다.

| 상황 | 처리 |
|---|---|
| **디스크 공간 부족** | 격리 백업 전에 필요 용량을 계산해 확인한다. 부족하면 **파괴를 시작하지 않는다**(백업 없는 삭제 금지) |
| **다중 사용자 프로필** | `HKU\*` 전체와 각 사용자 홈을 순회한다. 현재 로그온 사용자만 보면 미탐이 된다 |
| **네트워크 드라이브·이동식 매체 상의 대상** | 기본 제외. 포함하려면 플러그인이 명시 선언. 연결이 끊기면 부분 실패가 되고, 다른 PC의 공유 폴더를 지우는 사고가 가능하다 |
| **도메인·로밍 프로필** | 로밍 프로필의 변경은 로그오프 시 서버로 동기화된다. 격리·복원 결과가 다른 PC에 전파될 수 있음을 인지하고 진단 정보에 도메인 여부를 기록 |
| **시스템 복원 지점** | Windows에서 치료 전 복원 지점 생성을 **시도**하되 실패해도 진행한다. 이것은 우리 격리소의 대체재가 아니라 추가 안전망이다 |
| **디스크 암호화·볼륨 잠김** | 접근 불가 대상은 실패로 기록하고 사용자에게 잠금 해제를 안내 |
| **시계 이상** | 파일 타임스탬프가 미래이거나 시스템 시각이 빌드 시각보다 이전이면 **경고를 남긴다.** 신뢰 판정은 시계에 의존하지 않지만(설계-03 §6), 감사 로그의 시각은 의심 대상이 된다 |
| **로그·출력 인코딩** | 파일 출력은 **UTF-8 고정**. 한글 Windows 콘솔의 기본 코드페이지에 맞춰 출력하면 파일로 리다이렉트했을 때 깨진다 |

## 6. 안전 모드 치료 흐름 (v1 포함)

활성 악성코드 대응의 정답은 싸우는 것이 아니라 회피하는 것이다.

```
  apply 중 실패 발생
     -> 실패 유형이 (파일 잠금 | 접근 거부 | 재생성 확인) 인가?
        -> 아니오: 부분 치료로 보고
        -> 예:
             [1] 안전 모드 가용성 확인   <-- 이것이 없으면 안 된다
             [2] 부팅 건전성 확인
                  -> 둘 중 하나라도 손상: 재시작을 제안하지 않는다.
                     손상 사실을 보고하고 복구 매체 준비를 안내
                  -> 정상: 안전 모드 재시작을 제안
                           승인 시 자동 재개 항목 등록 -> 재부팅
                           저장된 plan.json 으로 재개 (재스캔 안 함)
                           완료 -> 재개 항목 스스로 제거 -> 정상 부팅
```

### 재시작을 제안하기 전에 반드시 확인한다

악성코드는 **안전 모드 진입을 막는다.** `HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot` 를 지우는 것이 흔한 수법이고, 부팅 구성을 손대는 경우도 있다.

그 상태에서 우리가 "안전 모드로 재시작하세요"라고 하면 **사용자는 부팅되지 않는 컴퓨터를 받는다.** 치료하러 온 도구가 시스템을 못 쓰게 만드는 것이며, §1의 1순위를 정면으로 위반한다. 같은 문제가 **일반 재부팅 제안**에도 있다 — `verify_after_reboot` 와 재시도 큐는 재부팅을 전제하는데, 부팅 구성이 이미 망가져 있으면 "재부팅하세요"가 최악의 조언이 된다.

따라서 **재부팅이나 안전 모드를 요구하는 계획은 선행 점검 Action을 반드시 포함한다.**

| 점검 | 확인 대상 |
|---|---|
| 안전 모드 가용성 | `SafeBoot\Minimal` · `SafeBoot\Network` 키 존재와 최소 하위 구조 |
| 부팅 건전성 | 부팅 구성의 복구 활성화 여부, 부트 항목 정상 여부 |

**손상을 발견해도 v1에서는 복원하지 않는다.** `SafeBoot` 하위에는 수백 개 항목이 있어 카탈로그 복원이 현실적이지 않고, 어설픈 복원은 더 나쁜 상태를 만든다. 복원은 OS 복구 도구의 영역이다.

**다만 탐지는 반드시 한다.** 알지 못한 채 안전 모드를 권하는 것이 이 결함의 본체이기 때문이다. 손상이 확인되면 사용자에게 그 사실과 함께 **복구 매체를 먼저 준비하라**고 안내한다.

**재개는 새 스캔이 아니라 저장된 계획의 실행이다.** 안전 모드에서 다시 스캔하면 환경이 달라 다른 계획이 나오고, 사용자가 승인한 것과 다른 일이 벌어진다. 설계-03 §1 불변식 P의 연장이다.

자기 흔적 규칙은 설계-03 §8과 동일하게 적용한다 — 재개용 자동실행 항목은 식별 가능한 고정 이름을 쓰고, 완료 즉시 스스로 제거하며, 감사 로그에 자기 항목으로 기록한다.

> **v1 은 여기까지다 (2026-09-30 결정)** — 위 흐름의 **자동 재개 항목은 만들지 않는다.** v1 은
> 부분 치료를 종료 코드 3 으로 보고하고, 부팅 건전성을 확인한 뒤 재시작·안전 모드를 **안내**한다(§5 의
> 모드 표 그대로). 안전 모드에서 다시 하는 것은 새 검사다 — 끝난 회차의 계획은 다시 적용하지 않는다.

## 7. 데이터 취급

전용백신은 고객 PC에서 실행되고 파일 경로·사용자명·프로세스 정보를 수집한다. **치료 경로는 밖으로 나가지 않는다**(설계-01 D8). 인텔 조회와 제출은 별도 단계이며(D9), 각각 다른 규칙을 따른다.

### 세 개의 경계를 구분한다

| 경계 | 무엇이 여기까지 오는가 | 기본값 |
|---|---|---|
| **로컬 보관** | 아티팩트, 감사 로그, 격리물, 계획·결과 | 항상. 자동 삭제·자동 전송 없음 |
| **조회로 나가는 것** (`enrich`) | 해시, 도메인, IP, URL — **지표만** | 사내 실행. 고객 PC에서는 기본 없음 |
| **제출로 나가는 것** (`submit`) | 감염 소스, 선택된 아티팩트, 경우에 따라 검체 | **기본 비활성.** 명시적 동의 |

**핵심 규칙: 파일 본문은 조회로 나가지 않는다.** 조회는 해시로 한다. 본문이 필요한 경우는 제출이며, 그것은 다른 동의 아래 있다.

### 조회 자체가 정보다

해시를 조회한다는 것은 조회받는 쪽에 **"이 조직의 어떤 PC가 이 파일을 갖고 있다"**를 알리는 행위다. 사내 시스템이면 감수할 수 있지만, 두 가지를 못 박아 둔다.

- **외부 서비스로 조회 대상을 확장하지 않는다.** 확장하려면 그때 다시 판단한다. "사내 시스템에 물어본다"와 "외부에 물어본다"는 전혀 다른 결정이다
- 조회 기록도 감사 로그에 남긴다. 무엇을 물어봤는지 나중에 확인할 수 있어야 한다

### 제출에는 개인정보가 실제로 들어 있다

> **이 절은 지금 "제출을 켜지 않는 이유" 로 읽힌다 (2026-08-28).** 제출 기능을 제품 범위에서 뺐다 — 아래 여섯 조건 중 법무 검토가 선행이고 그 넷은 설계로 결정할 수 없다. 분석가가 손으로 올리고 remedy 는 `support-bundle` 까지만 만든다 (설계-09 "제출을 제품 밖으로").
>
> **지우지 않는 이유**: 언젠가 켜게 되면 아래가 그대로 선행 조건이다. 지우면 그 조건을 다시 발명해야 한다.

이 부분을 낙관하면 안 된다. 수집되는 값에는 다음이 그대로 포함된다.

| 값 | 포함될 수 있는 것 |
|---|---|
| 파일 경로 | **사용자 계정명**, 회사·부서명, 프로젝트명, 고객사명 |
| `zone.referrer_url` / `host_url` | 사내 시스템 주소, **계정이 포함된 URL**, 개인 클라우드 링크 |
| 프로세스 커맨드라인 | **자격증명이 인자로 넘어간 경우** |
| 검체 파일 | 문서가 오탐으로 잡혔다면 **문서 내용 전부** |

**따라서 제출은 아래를 모두 만족해야 한다.**

1. **기본 비활성.** 켜야 만들어진다
2. **필드 단위 동의.** "데이터 수집 동의" 한 덩어리가 아니라, 지표만 / 아티팩트까지 / 검체까지의 단계를 나눈다
3. **제출 전 미리보기 필수** (`submit --preview`). 사람이 보지 않고 나가는 데이터가 없어야 한다
4. **자동 마스킹.** 사용자명·홈 경로는 자리표시자로 치환하고, URL의 쿼리 문자열과 자격증명 부분은 제거한다. 마스킹은 기본 동작이고 해제가 옵트인이다
5. **파일 생성이 기본, 전송은 옵트인** (설계-01 D9 결정 4). 폐쇄망에서 파일 반출이 유일한 경로이기도 하다
6. **제출 꾸러미도 로컬에 남긴다.** 무엇을 보냈는지 나중에 확인할 수 있어야 하고, 폐쇄망에서는 그 파일이 곧 반출 대상이다

### 그 외

- **감사 로그**: 로컬 파일. 전송은 사용자·관리자가 명시적으로 지정한 경로로만
- **격리물**: 사용자 문서가 오탐으로 격리될 수 있다. 로컬 보관, 자동 삭제 없음, 자동 전송 없음
- **capture 값 크기 상한** (설계-02 §7): 파일 본문이 감사 로그로 새는 경로를 막는다
- **보존 기간**: 로컬 산출물의 보존은 사용자·관리자가 정한다. 사내 시스템에 축적된 인텔의 보존 정책은 이 문서 범위 밖이며, **그쪽 정책이 별도로 필요하다**

> **법무 검토가 선행되어야 하는 지점이다.** 개인정보 최소 수집, 동의 방식(EULA 포괄 동의로 충분한지 기능별 동의가 필요한지), 국외 이전 여부, 보존 기간 — 이 넷은 설계로 결정할 수 없다. 제출 기능을 실제로 켜기 전에 확인이 끝나 있어야 한다.
