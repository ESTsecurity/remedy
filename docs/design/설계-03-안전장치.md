# 설계 03 — 안전장치와 오탐 사고 방지 기준

> 작성일: 2026-08-20 · 대상: `remedy` 코어 엔진
> 선행 문서: [설계-01-아키텍처-결정.md](설계-01-아키텍처-결정.md) · [설계-02-SDK-계약.md](설계-02-SDK-계약.md)

## TL;DR

- **무엇을**: 전용백신이 정상 파일을 지워 2차 사고를 내는 경로를 구조적으로 차단하고, 그것을 **숫자로 검증 가능한 출시 게이트**로 만든다.
- **왜**: 2022년 알약 오진 사태의 재발 방지가 이 제품의 존재 조건이다. "조심해서 만들자"는 기준이 될 수 없다.
- **핵심 결정**: 안전성을 런타임 검사에 의존하지 않고 **아키텍처 불변식**으로 확보한다 — 모든 파괴적 동작은 실행 전에 `plan.json`으로 완전히 확정되며, 계획에 없는 동작은 실행 단계에서 발생할 수 없다. 상한 초과·보호 경로 침범은 **실행 중이 아니라 계획 단계에서** 거부된다.

## 1. 근본 불변식: 계획 완전 결정 (Plan Completeness)

모든 안전장치가 이 하나에서 파생된다.

```
  collect  ---> artifacts.json (시스템 아티팩트 스냅샷 : 판단 없는 원본 관찰)
  evaluate ---> scan.json      (Evidence[]  : 룰 평가 결과)
  plan     ---> plan.json      (Action[]    : 완전히 구체화된 파괴/변경 동작)
  apply    ---> result.json    (+ 격리 컨테이너, 저널)
```

`scan` 은 `collect` + `evaluate` 를 이어 붙인 편의 명령이다.

### 수집과 평가를 나누는 이유

이 분리가 만들어 내는 성질이 크다.

**(1) 플러그인 룰은 시스템에 접근하지 않는다.** `evaluate` 는 `artifacts.json` 이라는 **불활성 데이터**만 입력으로 받는다. 신뢰할 수 없는 콘텐츠(플러그인 룰)가 살아 있는 시스템을 만나는 지점이 사라지므로, **오작동하는 룰이 탐지 단계에서 시스템에 할 수 있는 일이 구조적으로 없다.** 크레이트 의존 그래프에서 `remedy-detect` 가 `remedy-platform` 을 의존하지 않는 것으로 강제한다.

**(2) 청정 환경 검증(G1)이 VM 없이 대량으로 가능해진다.** 골든 클린 이미지를 VM으로 유지하면 비싸고 느려서 몇 개밖에 못 쓴다. 아티팩트 스냅샷이면 수백 개를 CI에서 초 단위로 돌린다. **이것이 오탐 방지의 실질적 사거리를 결정한다.**

> 스냅샷 평가가 G1에 대해 **건전한(sound) 과대근사**라는 점이 중요하다. `verdict.require` 는 모든 구성 규칙의 논리곱이므로, 메타데이터 규칙(예약 작업 형태 등)이 매치되지 않으면 파일 내용을 보는 YARA 규칙과 무관하게 판정이 성립하지 않는다. **스냅샷만으로 "파괴 계획 0건"이 나오면 실제 시스템에서도 0건이다.**

**(3) 룰 개발이 초 단위로 반복된다.** 감염 VM을 매번 복원하며 룰을 고칠 수는 없다. 스냅샷 하나를 두고 `evaluate` 만 돌리면 된다.

**(4) 지원 엔지니어와 분석가의 작업이 분리된다.** 고객 PC에서는 `collect` 만 수행하고(파괴 동작 없음, 권한 요구 낮음), 분석은 사내에서 한다. 새 플러그인의 입력이 곧 이 스냅샷이다.

**(5) 라이브 실행에서도 같은 코드가 돈다.** `remedy-platform` 에 **라이브 시스템 백엔드와 스냅샷 백엔드**를 두고 위를 같은 인터페이스로 덮는다. 테스트에서 도는 코드와 고객 PC에서 도는 코드가 갈라지지 않는다.

스냅샷에 파일 **내용**을 얼마나 담을지는 정책이다. 기본은 메타데이터와 해시만 담고, `scan_roots` 하위의 크기·확장자 조건을 만족하는 파일만 내용을 포함한다. 내용을 담지 않은 스냅샷에서는 YARA 규칙이 **미평가**로 표시되며, 미평가 규칙이 있는 판정은 **감염 확정에 쓸 수 없다**(치료 불가, 보고만).

**불변식 P**: `apply` 단계는 `plan.json`에 열거된 Action만 실행한다. 새 대상을 탐색하지 않고, 경로를 재해석하지 않으며, 조건 분기로 동작을 추가하지 않는다.

### 예외 하나 — 실행 시점에만 존재하는 대상

프로세스는 계획 작성 시점의 PID가 실행 시점에 유효하다는 보장이 없다. 악성코드가 종료 후 **재생성**하면 PID가 바뀌고, PID를 계획에 박아 두면 그 Action은 아무 일도 하지 않거나 **엉뚱한 프로세스를 죽인다**(PID 재사용). 그렇다고 실행 중에 자유롭게 탐색하면 불변식이 무너진다.

해소 방법은 **대상을 값이 아니라 술어로 계획에 고정**하는 것이다.

```json
{ "seq": 1, "op": "process.kill",
  "match": { "image_path": "C:\\...\\node.exe", "cmdline_contains": "C:\\...\\locust\\main.js" },
  "max_targets": 8, "max_retries": 3,
  "because": ["malicious-task#0"] }
```

- 술어 조건은 `image_path` · `cmdline_contains` · **`loaded_module`** 이다. 마지막 것이 없으면 **DLL 사이드로딩을 다룰 수 없다** — 악성 DLL을 로드해 잠그고 있는 프로세스는 이미지 경로가 정상 프로그램이라 다른 조건으로 지목되지 않는다
- 술어는 **계획에 문자열로 존재**하므로 드라이런에 그대로 표시되고 감사 로그에 남는다. 사람이 승인한 것과 실행되는 것이 여전히 일치한다
- 해소 결과 수에 `max_targets` 상한을 둔다. 초과하면 실행하지 않고 **가드 중단**(종료 코드 5). 술어가 지나치게 넓게 잡힌 경우를 실행 전에 잡는다
- **PID를 직접 지정하는 Op는 존재하지 않는다.** 계획에 PID가 들어갈 자리가 없다

따라서 불변식 P의 정확한 진술은 **"실행되는 동작의 종류와 선정 기준은 계획에 완전히 고정된다"**이다. 술어가 실행 시점에 몇 개의 프로세스를 지목하는지는 계획이 결정할 수 없지만, **무엇을 지목할지는 계획이 전부 결정한다.**

### 재생성에 대한 대응

`process.kill` 은 술어를 재평가하며 최대 `max_retries` 회 반복한다. 그래도 남아 있으면 **실패로 기록하고 다음으로 넘어간다** — 무한 재시도로 악성코드와 경쟁하지 않는다(설계-00 §2 T1 비목표). 남은 것은 재부팅 후 재시도 큐로 넘기고, 사용자에게는 안전 모드 재시작을 제안한다(설계-00 §6).

이 불변식이 주는 것:

| 얻는 것 | 불변식 P 없이는 |
|---|---|
| 드라이런이 **정확**하다 (보여준 것과 실행한 것이 동일) | "아마 이걸 지울 겁니다" 수준의 추정 |
| 삭제 상한을 **실행 전에** 걸 수 있다 | 100개 지운 뒤 상한에 걸려 중단 → 이미 사고 |
| 감사 로그가 완전하다 | 실행 중 파생된 동작이 누락 |
| 계획을 사람이 검토·보관·재실행할 수 있다 | 매 실행이 비결정적 |
| testbed가 "계획 비교"만으로 회귀를 잡는다 | 실제 파괴를 수행해야만 검증 가능 |

**강제 방법**: `apply` 실행기는 Action 배열만 입력으로 받는다. 탐지 코드(스캐너·룰 평가기·스크립트 런타임)는 `apply` 바이너리 경로에서 호출되지 않으며, 이를 아키텍처 테스트로 강제한다(실행기 패키지가 스캐너 패키지를 import 하면 빌드 실패).

> 이 불변식 때문에 **플러그인 스크립트는 탐지에서만 허용되고 치료에는 허용되지 않는다.** 스크립트가 파괴 동작을 할 수 있으면 실행하기 전에는 계획을 알 수 없고, 위 표의 모든 항목이 무너진다. 상세 근거는 설계-01.

## 2. 파괴 동작은 닫힌 집합이다

플러그인은 새로운 파괴 동작을 정의할 수 없다. 코어가 제공하는 Op 목록만 사용 가능하며, 각 Op는 되돌림 등급·필수 백업 종류·위험 등급을 코어가 정한다.

| Op | 되돌림 | 필수 백업 | 위험 |
|---|---|---|---|
| `process.kill` | 불가 | 없음 (커맨드라인·이미지 경로 기록) | 중 |
| `persistence.disable` / `persistence.delete` | 가능 | 작업 정의 XML | 중 |
| `service.clear_recovery` | 가능 | 복구 동작 설정 | 중 |
| `service.stop` | 불가 | 없음 (상태 기록) | 중 |
| `service.disable` / `service.delete` | 가능 | 서비스 설정 | 중 |
| `autorun.remove` | 가능 | 원본 항목(레지스트리 값 / 셸 라인 / 유닛 파일) | 중 |
| `registry.delete_value` | 가능 | 값 타입 + 원본 데이터 | 중 |
| `registry.delete_key` | 가능 | 키 전체(하위 키·값 포함) | **고** |
| `registry.strip_value` | 가능 | **값 원본 전체** | 중 |
| `registry.restore_default` | 가능 | 값 원본 전체 | 중 |
| `env.strip_path` | 가능 | 환경변수 원본 전체 | 중 |
| `file.delete_stream` | 가능 | 스트림 내용 + 호스트 경로 | 중 |
| `text_config.remove_line` | 가능 | 원본 라인 + 파일 + 위치 + 권한 | 중 |
| `structured_config.remove_key` | 가능 | 파일 원본 전체 | 중 |
| `structured_config.restore_default` | 가능 | 파일 원본 전체 | 중 |
| `shortcut.strip_args` | 가능 | 바로가기 원본 전체 | 저 |
| `boot.restore_default` | 가능 | 변경 전 부팅 구성 | **고** |
| `file.quarantine_only` | 가능 | 파일 본문 + 메타데이터 | 저 |
| `file.delete` / `file.delete_on_reboot` | 가능 | 파일 본문 + 메타데이터 | 중 |
| `dir.delete_recursive` | 가능 | 하위 전체 | **고** |
| `av.restore_exclusions` | 복원계 | 변경 전 목록 | 저 |
| `hosts.restore_line` | 복원계 | 원본 라인 | 저 |
| `browser_ext.remove` | 가능 | 확장 디렉터리 | 중 |
| `cert_store.remove` | 가능 | 인증서 DER + 저장소 위치 | **고** |
| `proxy.restore` | 복원계 | 변경 전 설정 전체 | 저 |
| `firewall.restore_rule` | 복원계 | 변경 전 규칙 전체 | 저 |

**새 파괴 동작이 필요하면 플러그인이 아니라 코어에 추가한다.** 의도적인 마찰이다 — 파괴 동작 추가는 코드 리뷰를 거쳐야 하고, 플러그인 작성자의 재량으로 우회될 수 없어야 한다.

### `file.quarantine_only` 와 `file.delete` 의 차이

둘 다 백업이 "파일 본문 + 메타데이터" 로 같아 보이지만 하는 일이 다르다.

- **`file.quarantine_only`** — 파일을 **격리소로 옮긴다.** 원본 자리에서는 사라지고 바이트는 컨테이너 안에 있다. 되돌리기가 이 Op 의 정의 자체에 들어 있으므로 위험 **저**다.
- **`file.delete`** — 파일을 **지운다.** 백업은 하지만 되돌리기는 별도 경로이고, 잠긴 파일·재생성·`delete_on_reboot` 같은 복잡도가 따라붙는다. 위험 **중**이다.

P6 이 `file.quarantine_only` 하나로 시작하는 이유가 여기 있다. **"지우기 전에 되돌리기"가 실제로 성립하는지를 가장 단순한 형태로 먼저 증명한다** — 파일이 제자리에서 사라지고, `restore` 가 바이트까지 같게 되돌린다. 이것이 성립하지 않으면 그 위의 어떤 파괴도 정당화되지 않는다.

### 계획기는 **구현된 것 중 가장 덜 위험한** 제거 Op 를 고른다

플러그인은 "무엇이 남아 있으면 안 되는가" 만 말한다(설계-02 §6). 어느 Op 으로 그것을 이룰지는 계획기가 정하며, **같은 목적을 이루는 Op 이 여럿이면 위험이 낮은 쪽을 고른다.**

그래서 파일 제거는 P6 에서 `file.quarantine_only` 로, `file.delete` 가 들어오는 P7 이후에도 잠금 등으로 격리가 불가능한 경우가 아니면 계속 `file.quarantine_only` 다.

**아직 구현되지 않은 Op 이 필요한 항목은 조용히 빠지지 않는다.** 그 항목은 계획에서 빠지되 `plan.json` 에 **미룬 이유와 함께 남고**, 계획을 받아 든 쪽이 "이 계획이 치료의 전부인가" 를 물을 수 있어야 한다. 관측이 불완전할 수 있듯 계획도 불완전할 수 있고, 둘 다 **말하지 않으면 완전한 것으로 읽힌다.**

### 순서는 플러그인이 아니라 코어가 정한다

플러그인은 **"무엇이 남아 있으면 안 되는가"**(제거 대상)를 선언하고, 실행 순서는 계획기가 도출한다.

> **제거 대상 하나가 Action 하나인 것은 아니다.** 계획기는 subject 마다 "택일" 과 "차례" 를 구분한다 — 파일은 격리하거나 지우거나 **하나**지만, 서비스는 아래 차례를 **전부** 낸다. 하나만 해서는 서비스가 사라지지 않기 때문이다. 플러그인은 여전히 순서도 개수도 적지 않는다.
>
> | subject | 계획기가 내는 것 |
> |---|---|
> | 서비스 | `service.clear_recovery` → `service.stop` → `service.disable` → `service.delete` |
> | 파일 | `file.quarantine_only` **또는** `file.delete` (잠겨 있으면 `file.delete_on_reboot`) |
>
> P8 게이트를 올리기 전까지 서비스 자리는 우선순위 목록이었고, 계획기는 언제나 `service.disable` 하나만 냈다. VM 하네스가 실증한 "복구 제거를 먼저 하면 SCM 을 이긴다" 를 **실제 계획으로는 만들 수 없는 상태**였다 (설계-09 P8).

> **그래서 계획기는 매니페스트를 입력으로 받는다.** `remediate` 는 매니페스트에 있고 `scan.json` 에는 없다 — `scan.json` 은 "룰 평가 결과"(§1)이지 치료 지시가 아니다. 계획기가 `scan.json` 만 받으면 Action 을 만들 자리가 없다.
>
> 대안으로 `evaluate` 가 `remediate` 를 `scan.json` 에 실어 보내는 방식을 검토했으나 채택하지 않았다. 그러면 아직 해소되지 않은 치료 지시가 관찰 결과 안에 들어가 두 문서의 성격이 섞이고, capture 보간을 평가기가 떠맡게 된다. `evaluate` 가 스냅샷과 매니페스트를 함께 받는 것과 같은 모양으로 두는 편이 일관된다.
>
> 산출물이 **홀로 읽혀야 한다**(§1)는 요구는 여전히 지켜진다 — 그것은 만들어진 `plan.json` 을 읽는 쪽의 요구이지 만드는 쪽의 입력 제약이 아니다. `apply` 는 `plan.json` 만 보고, 그 안의 Action 은 완전히 구체화되어 있다.

```
  1. 자동 소생 차단 : 서비스 복구 동작(failure action) 제거, 서비스 정지
  2. 잠금 해제      : 대상에 연결된 프로세스를 정지 -> 종료 (아래)
  3. 재기동 차단    : 작업·서비스·자동실행 비활성화 (삭제 아님)
  4. 백업           : 이후 파괴·편집될 모든 대상을 격리소에 기록 + 무결성 확인
  5. 유발자 제거    : 재생성·재설치를 일으키는 설정을 먼저 제거
  6. 산출물 제거·편집 : 의존 역순으로 삭제, 부분 편집 수행
  7. 복원           : 보안 제품 예외 목록·정상 기본값 되돌리기
  8. 사후 확인      : 부팅 건전성 점검 후 재부팅 검증 예약
```

### 유발자를 산출물보다 먼저 제거한다

5단계와 6단계를 나눈 이유가 있다. **재생성을 일으키는 설정을 남긴 채 산출물만 지우면 즉시 되돌아온다.**

| 유발자 | 산출물 | 순서를 어기면 |
|---|---|---|
| Chrome 정책 `ExtensionInstallForcelist` | 브라우저 확장 | 다음 실행에서 브라우저가 재설치 |
| 예약 작업 | 드롭되는 페이로드 파일 | 다음 트리거에서 재생성 |
| 서비스 | 작업 디렉터리 | 서비스 기동 시 재생성 |
| 설치 관리자 구성 | 설치되는 구성 요소 | 자가 복구가 되돌림 |

3단계(재기동 차단)가 이것을 다 덮지 못한다. 정책 레지스트리는 **작업도 서비스도 자동실행도 아니기** 때문이다.

**Op마다 `regenerator` 속성을 둔다.** 계획기가 그 속성을 보고 5단계에 배치하며, 플러그인은 여전히 순서를 적지 않는다 — §2 서두의 "순서는 코어가 정한다" 원칙 그대로다.

**1단계가 2단계보다 앞인 것이 핵심이다.** 악성 서비스는 대개 실패 시 자동 재시작이 설정돼 있어, 복구 동작을 먼저 제거하지 않고 프로세스를 종료하면 **SCM이 즉시 되살린다.** 종료 재시도는 서비스 관리자와의 경쟁일 뿐 이기지 못한다.

### 프로세스 종료는 정지 후 종료다

워치독 쌍(서로를 되살리는 두 프로세스)에서 순차 종료는 진다. A를 죽이는 사이 B가 A를 되살린다. 따라서 `process.kill` 의 실행 규칙을 고정한다.

```
  술어로 대상 집합 해소  ->  전부 정지(suspend)  ->  전부 종료  ->  재평가
     |                                                              |
     +--------------- 남아 있으면 max_retries 까지 반복 -------------+
```

정지가 먼저이므로 재생성 코드가 돌지 못한다.

#### 정지를 못 하는 플랫폼은 강등하고, 그 사실을 적는다

**이 코어는 정지를 못 한다.** Windows 에서 정지는 raw FFI 뿐이고, `forbid(unsafe_code)` 를 지키면서 도달할 길이 없다 — OS 가 제공하는 관리 도구도 없다 (설계-01 D13). 그래서 규칙은 이렇게 읽는다.

```
  정지할 수 있으면  : 해소 -> 전부 정지 -> 전부 종료 -> 재평가
  정지할 수 없으면  : 해소 -> 전부 종료 -> 재평가  + **저널에 강등을 적는다**
```

강등을 적는 것이 규칙의 일부다. **말하지 않으면 저널은 규칙이 다 돈 것처럼 읽힌다** — 관측이 불완전할 수 있듯 실행도 불완전할 수 있고, 둘 다 말하지 않으면 완전한 것으로 읽힌다. 오늘 `process.kill` 은 매번 `정지(suspend) 단계를 건너뛰었다` 를 남긴다.

강등이 실무에서 버티는 근거는 실측이다. 30ms 로 되살리는 워치독 쌍에게 **집합 종료만으로 이겼다** (설계-09 P8 시나리오 A). 지는 픽스처가 나오면 그때 정지가 값을 치르고 들어온다.

#### 자손 확장 — 계보로만 식별되는 감시자

`include_descendants: true` 를 주면 해소된 대상의 **자손 프로세스까지** 집합에 포함한다 — 부모-자식 관계로만 식별되는 감시자를 술어로 잡을 수 없는 경우를 위한 것이다. **계획이 명시적으로 켜야 하고**, 기본은 꺼짐이다. 계획기가 스스로 켜지 않는다.

세 가지가 함께 걸린다.

- **상한은 확장된 집합 전체에 걸린다.** 뿌리 하나가 상한 안이어도 자손까지 세어 넘으면 **하나도 종료하지 않는다.**
- **보호 대상인 뿌리는 자손의 문이 되지 않는다.** 술어가 보호 대상을 지목했다면 그것은 술어가 빗나간 것이고, 빗나간 자리에서 계보를 펼치면 실수가 트리 하나만큼 커진다. 뿌리는 보호 대상을 걸러 낸 뒤의 집합이며, 확장된 자손도 다시 한 번 걸러진다.
- **재사용된 PID 를 자손으로 세지 않는다.** Windows 는 부모가 죽어도 자식의 부모 PID 를 고치지 않으므로(Unix 처럼 재양육하지 않는다), 그 PID 가 재사용되면 남남인 프로세스가 자손으로 보인다. 그래서 시작 시각을 함께 본다 — **자식은 부모보다 먼저 시작할 수 없다.** 시작 시각을 읽지 못한 프로세스는 관계를 확인하지 못한 것이므로 자손으로 세지 않는다.

계보를 걷지 못하는 백엔드는 **빈 목록이 아니라 오류를 낸다.** `Ok(vec![])` 을 돌려주면 계획이 켠 `include_descendants` 가 조용히 무시되고, "자손이 없다" 와 "자손을 못 봤다" 가 같은 값이 된다.

한계 하나를 적어 둔다. **재평가는 술어가 지목하는 것만 본다.** 뿌리가 모두 죽고 나면 자손은 계보로 다시 찾을 수 없으므로(부모가 없다), 계보로 더해진 것들은 저널에 PID 로 남는다. 재평가로 확인한 것과 기록만 한 것을 섞지 않는다.

### 부분 편집의 백업은 값 전체다

`registry.strip_value` · `env.strip_path` 는 값의 일부만 제거하지만, **백업은 편집 전 값 전체**를 저장한다. 복원하면 오염된 원본이 그대로 돌아오며, **그것이 옳은 동작이다** — 사용자가 복원을 요청했다는 것은 우리 판정이 틀렸다고 본다는 뜻이므로, 우리가 "옳다고 생각한 부분"만 남겨서는 안 된다.

### 임의 값 쓰기는 허용하지 않는다

`registry.restore_default` 는 **코어가 내장한 OS 기본값 카탈로그**에서만 값을 가져온다(`Winlogon\Shell` → `explorer.exe` 등). 플러그인이 임의 값을 지정할 수 없다. 서명된 도구가 임의 레지스트리 값을 쓸 수 있으면 그 자체가 공격 도구이기 때문이다.

**카탈로그에는 값 하나로 복원이 완결되는 항목만 담는다.** `Winlogon\Shell`·`Userinit`, 주요 확장자 연결, 부팅 구성 플래그가 여기 해당한다. 반대로 `SafeBoot` 하위처럼 **수백 개 항목의 구조 전체**가 필요한 대상은 담지 않는다 — 어설픈 부분 복원이 손상을 키운다. 그런 대상은 **탐지·보고만 하고 OS 복구 도구의 영역으로 넘긴다**(설계-00 §6).

카탈로그에 없는 대상을 `to: default` 로 지정하면 `plugin lint` 가 거부하고 유효 목록을 보여준다.

근거: 플러그인 작성자가 `steps`를 임의 순서로 나열할 수 있으면 "백업 전 삭제", "비활성화 전 삭제 → 재생성", "프로세스 종료 전 파일 삭제 → 실패 후 부분 파괴" 같은 사고가 플러그인마다 재발한다. 순서 결정은 코어가 한 번만 옳게 하면 되는 문제다.

## 3. 화이트리스트 계층 (평가 순서 고정)

아래 순서로 평가하며, **1번은 플러그인·사용자 누구도 뒤집을 수 없다.**

**1층 — 코어 내장 불변 보호 목록**

- Windows: `%SystemRoot%\System32`·`SysWOW64`·`WinSxS`, 부트 구성 파일, `\Program Files\Windows Defender`, 드라이브 루트, `\Users\<user>` 디렉터리 자체
- Linux: `/bin /sbin /usr /lib /lib64 /boot /proc /sys /dev`, `/etc` 디렉터리 자체, `$HOME` 자체

규칙은 **디렉터리 단위 금지 + 개별 파일 조건부 허용**이다.

- 위 경로에 대한 `dir.delete_recursive` → **항상 거부**
- 위 경로 하위의 **개별 파일** `file.delete` → "신뢰 서명 없음 + 증거 링크 존재" 두 조건을 모두 만족할 때만 허용

이 이중 규칙이 필요한 이유: 악성코드는 실제로 `System32`에 드롭된다(첫 플러그인 대상 EvilAI의 탐지 조건에도 `\System32\` 경로가 포함된다). 디렉터리를 통째로 막으면 첫 플러그인부터 동작하지 않고, 통째로 열면 OS 파괴 경로가 열린다.

#### 1층에는 경로만이 아니라 **프로세스**도 들어간다

경로 보호 목록은 종료를 막지 못한다. 종료는 파일을 건드리는 동작이 아니기 때문이다. 그런데 악성코드가 정상 프로세스명으로 위장하거나 정상 프로세스에 인젝션한 경우, `image_path` 로 매칭하는 룰이 **임계 시스템 프로세스를 대상으로 잡을 수 있다.**

`csrss.exe` · `winlogon.exe` · `smss.exe` · `wininit.exe` · `lsass.exe` · `services.exe` 를 종료하면 **즉시 블루스크린**이다. Linux의 `init`/`systemd`(PID 1)도 같다.

- 이 목록은 **코어 내장이며 플러그인이 뒤집을 수 없다.** 술어가 이들을 지목하면 해당 대상만 제외하고 감사 로그에 사유를 남긴다
- 판정 기준은 이름이 아니라 **경로 + 부모 관계**다. 이름만 보면 `C:\Temp\lsass.exe` 같은 위장이 보호를 얻는다
- **PID 1 · PID 4 등 고정 PID 시스템 프로세스**는 무조건 제외

정상 프로세스에 인젝션된 위협은 프로세스 종료로 다루지 않는다 — 지속성 아티팩트를 제거하고 **재부팅으로 정리**한다. 살아 있는 시스템 프로세스와 싸우지 않는 것이 설계-00 §2 T1의 비목표와 일관된다.

**2층 — 신뢰 서명 검증**

유효한 신뢰 벤더 서명이 있는 실행 파일은 기본적으로 삭제 대상에서 제외한다.

단, **서명된 악성코드는 실재한다.** 따라서 플러그인이 `signed_malware: true`와 함께 서명 주체(subject/thumbprint)를 명시적으로 열거한 경우에만 이 층을 통과할 수 있다. 열거 없는 포괄적 무시는 불가.

> **실검체 확인 (2026-08, P9) — 첫 플러그인은 이 예외를 쓰지 못한다.** 이 문단은 원래 EvilAI 를 "정상 인증서로 서명된 AI 앱으로 위장하는 것이 특징" 이라고 예시로 들었으나, 확보한 검체에서 그것을 확인하지 못했다. VT `meadowlocust`(행위가 detect 규칙과 일치하는 그 군집) 기준으로 `engines:meadowlocust tag:signed` 는 0건, 구성원 40건을 개별 조회해도 `signature_info.subject` 보유는 0건, 내려받은 PE 2건은 파일 바이트에서 인증서 테이블 크기가 0이다.
>
> **이것은 "EvilAI 는 서명되지 않는다" 가 아니다.** 공개 보고가 말하는 서명된 설치 파일 단계가 그 라벨을 달지 않았을 수 있다 — 못 봤다와 없다를 섞지 않는다 (§1).
>
> 실무적 귀결은 오히려 단순하다. **`signed_malware` 를 비워 둔다.** 열거 없는 포괄적 무시가 불가능하므로, 서명된 대상을 만나면 2층이 삭제를 막고 그 사실이 보고된다 — 근거 없이 예외를 여는 것보다 옳은 실패 방향이다.

#### 2층은 아직 없다 — 그리고 그 사실이 조용하다

> **2026-08-25 (P10-B) — 이 절은 역사다. 2층이 섰다.**
> `FileRecord.signature` 는 이제 수집 단계에서 채워진다(실행 파일 한정,
> `remedy-collect/src/signature.rs`). 신뢰 판정은 **이 기계의 루트 저장소**에
> 앵커되며 자기서명은 통과하지 못한다 — 실측으로 확인했다. 계획기가 신뢰 서명
> 대상을 삭제에서 빼고 그 사실을 보고한다. 아래 표의 세 얼굴 중 첫째와 셋째는
> 해소됐고, 둘째(`dir.delete_recursive`)는 §4 조건 3 을 판정할 재료가 생겼으므로
> **P10-C 에서 열린다.**

**P8 시점의 실측이다.** `FileRecord.signature` 는 언제나 `None` 이고, 어떤
Phase 의 산출 목록에도 이것을 채우는 항목이 없었다. 레코드 주석은 *"P4 에서
채운다"* 라고 적고 있지만 설계-09 P4 산출에 그 줄이 없고, P4 는 그대로 닫혔다.
`zone`·`streams` 도 같은 주석을 달고 같은 상태다.

이 층이 없다는 것이 세 곳에서 서로 다른 얼굴로 나타난다.

| 어디 | 지금 무슨 일이 일어나나 |
|---|---|
| **모든 삭제 Op** (P6·P7) | 서명된 정상 실행 파일이 다른 층에 걸리지 않으면 그대로 지워진다 |
| **`dir.delete_recursive`** (§4 조건 3) | 판정 재료가 없어 언제나 거부. 그래서 **P10 으로 옮겼다** (설계-09 §3.2) |
| **첫 플러그인의 오탐 방어** | 초안 EvilAI 룰의 `exclude` 첫 줄이 `file(command).signature.subject == "Microsoft Corporation"` 이었다. 필드가 없으므로 **한 번도 발동하지 않았다** — 아래 |

마지막 줄이 가장 위험하다. 평가기는 **없는 필드를 조용한 미매치로 넘기고**
`issues` 에도 남기지 않는다 — 오타든 미구현이든 결과가 같다. 그래서 "정상
Node 개발 환경" 이라는 첫 번째 오탐 후보를 막으려고 쓴 줄이 무력한 채로 있고,
아무도 그것을 모른다. 이 도구가 존재하는 이유(§0 의 2022년 오진 사고)와 정면으로

> `CN=OpenJS Foundation` 서명이라, 2층이 서서 `signature.subject` 가 채워져도

> 실측한 값으로 다시 세워야 한다"* 로 이어졌으나, **그렇게 하면 안 된다.**
> 매니페스트 주석이 더 깊은 근거를 이미 적고 있었다 — EvilAI 는 정상
> `C:\Program Files\nodejs\node.exe` 를 **그대로 실행한다**(LOLBin). 서명 주체를
> 실측값(`O=OpenJS Foundation`)으로 바꿔 넣으면 그 줄은 **위협 자체를
> 제외한다.** 값이 틀린 것이 아니라 **술어의 종류가 틀렸다.**

> 2층은 플러그인의 `exclude`(3층)가 아니라 **코어가 건다.** 계획기가 신뢰 서명
> 대상을 삭제에서 빼고 그 사실을 `deferred` 로 보고한다
> (`remedy-plan/src/derive.rs::layer2_holds`). 첫 플러그인의 `exclude` 는 비어
> 있는 채로 옳다.

**일정**: 2층은 **P10-B 에서 왔다** (설계-09 P10). 원래 근거는 *"플러그인 서명과
재료가 같다"* 였으나 **실측으로 뒤집혔다** — 우리 서명은 minisign(Ed25519 직접
서명)이라 PKCS#7 도 X.509 체인도 쓰지 않는다(설계-09 P10 정정). 겹치는 코드는
없었고, 그래서 두 작업을 나눠 순서대로 했다.

**그 전까지의 규칙**: 서명을 확인하지 못한 것을 "서명 없음" 으로 읽지 않는다.
`Signature` 가 `None` 인 것은 **"확인하지 않았다"** 이며, 그 위에서 2층을
통과했다고 말하지 않는다.

**3층 — 플러그인 선언 제외** (`exclude`)
**4층 — 사용자 지정 제외** (설정 파일 / `--exclude`)

**5층 — 조직 서명 허용 목록** (2026-08-29 부터) · 인텔 조회 결과

**사람이 판단해 부여한 화이트리스트**가 확인된 대상은 제외된다.

> **출처가 바뀌었다 (2026-08-28 P13 결정 · 2026-08-29 구현).** 원래는 사내 분석 시스템이 부여한 태그를 조회해 쓰려 했고, 그래서 이 층이 `enrich`(P13)에 묶여 있었다. 대신 **조직이 서명한 목록을 우리가 직접 갖는다** — 부여·회수 주체와 이력이 우리 서명 체계 안에 있어 감사에 답할 수 있고, 저쪽 운영 부담이 없으며, **v1 에서 이 층이 선다.**
>
> 인텔 조회는 그대로 남는다. P13 이 오면 아래 방향 제약을 그대로 지고 이 층에 합류한다.

#### 허용 목록의 규칙

폐기 목록(§6)과 **같은 레일**이다 — minisign 서명, 파일 하나에 서명과 본문, 단조 증가 `serial`, `import` 로만 들어온다. 다른 것은 **방향**뿐이다.

| | 무엇 |
|---|---|
| 무엇으로 지목하나 | **SHA-256 하나뿐.** 경로로 지목하면 그 자리에 파일을 놓는 것만으로 면제를 얻고, 서명 주체로 지목하는 것은 2층이 이미 한다 |
| 사유 | **비울 수 없다.** 서명 도구가 만들 때 막는다 — 사유가 이 목록이 감사에 답하는 방식이다 |
| 목록이 없으면 | **면제가 없다.** 폐기 목록과 실패 방향이 반대다 — 없는 것이 안전한 쪽이므로 경고하지 않는다 |
| 서명이 틀리면 | 멈춘다. *"없다"* 와 *"바꿔치기했다"* 는 다르다 — 뒤엣것을 조용히 빈 목록으로 만들면 공격자가 파일 하나를 망가뜨려 조직의 면제를 통째로 없앨 수 있고, 그러면 정상 파일이 지워진다 |
| 역행 금지 | **회수된 면제가 옛 목록으로 되살아날 수 없다.** 반입 때 한 번, 읽을 때 한 번 본다 — 파일을 직접 바꿔 넣는 길이 있다 |
| 해시가 없는 대상 | 이 층으로 면제되지 않는다. 레지스트리 값·예약 작업이 그렇고, 그것은 다른 종류의 결정이다 |

**판정은 그대로 선다.** 이 층은 판정을 지우는 것이 아니라 **파괴를 막는 것**이고, 빠진 것은 사유와 함께 보고된다 — 조용히 사라지지 않는다.

```
  ** 1건은 코어가 **하지 않기로** 했다 — Op 은 있다:
     - remediate.remove[0] : file.quarantine_only — 설계-03 §3 5층 —
       조직 허용 목록에 있어 삭제하지 않는다: 사내 빌드 도구 (sha256 239f59ed55e7…)
```

> **보고를 두 갈래로 가른 이유.** 한동안 이 자리가 *"아직 이 코어에 없는 Op 을 요구한다"* 하나로 렌더됐다. 2층이 선 뒤로 신뢰 서명 때문에 빠진 것까지 그렇게 보고됐는데 **그 Op 은 있었다.** 운영자가 할 일이 완전히 다르다 — 앞은 코어를 올리는 일이고 뒤는 서명·목록·매체를 다루는 일이다.

#### 인텔 조회의 방향 제약

이 층에는 **방향 제약**이 걸려 있다.

| 조회 신호 | 제외 근거로 사용 |
|---|---|
| 명시적 화이트리스트 태그 | **가능** — 사람이 판단해 부여한 것 |
| `verdict == clean` (점수 20 미만) | **불가** — 회피·패킹·부분 실패도 낮은 점수를 받는다 |
| `verdict == malicious` | **불가** — 파괴 대상을 만들 수 없다. 보고·우선순위 표시에만 |
| `unscored` · 분석 미완료 · 조회 실패 · **0건** | **불가** — 정보 없음이지 무해 증거가 아니다 |

마지막 줄에 0건이 들어간 이유는 조회 결과가 **조회하는 쪽의 권한에 달려** 있을 수 있기 때문이다. 0건은 "분석된 적 없음"이 아니라 "내 권한 안에서 보이지 않음"이다(내부 문서 설계-05 §3).

비대칭인 이유는 감염 호스트의 네트워크를 신뢰할 수 없기 때문이다. DNS·프록시 하이재킹을 이미 위협으로 가정했으므로(설계-00 §2 T1), 조회 응답을 근거로 파괴를 늘리면 **공격자가 응답을 조작해 정상 파일을 지우게 만들 수 있다.** 반대 방향으로 조작되면 결과는 "치료 안 함"이고, 그것은 도구를 실행하지 않은 것과 같은 상태다.

이 제약은 문서가 아니라 **스키마 검증으로 강제한다** — `remediate` 절에서 `reputation` 을 참조하는 룰은 로드되지 않는다(설계-02 §3).

## 4. 폭주 차단 (계획 단계 상한)

상한은 **계획 단계에서** 평가한다. 초과 시 무인 모드는 프롬프트 없이 **중단(fail-closed)**, 대화형 모드는 계획 전문을 보여주고 명시적 승인을 받는다.

| 상한 | 범위 | 초기값 | 성격 |
|---|---|---|---|
| 총 삭제 파일 수 | 실행 전체 | 1000 | 정책 파라미터 |
| **동일 해시 반복 항목** | 실행 전체 | 20000 | 아래 |
| 총 삭제 바이트 | 실행 전체 | 512 MiB | 정책 파라미터 |
| 재귀 삭제 1건당 하위 항목 수 | Action 1건 | 500 | 정책 파라미터 |
| 재귀 삭제 최대 깊이 | Action 1건 | 8 | 정책 파라미터 |
| 서로 다른 최상위 디렉터리 수 | 실행 전체 | 5 | 확산 탐지용 |
| `process.kill` 술어당 대상 수 | Action 1건 | 8 | §1 `max_targets` |
| 증거 그룹 수 | 실행 전체 | 50 | 룰 과광범위 탐지용 |

**상한 사이의 관계를 명시적으로 강제한다.** 실행 전체 상한은 개별 Action 상한의 합보다 **크거나 같아야** 하고, 설정 로드 시 이 부등식을 검사해 위반하면 기동을 거부한다. 개별 상한이 총계를 넘으면 총계가 무의미해지고, 어느 쪽이 먼저 걸리는지가 계획 순서에 따라 달라져 재현되지 않는다.

> 초기값은 근거 있는 실측치가 아니라 **출발점**이다. 첫 플러그인(EvilAI)의 실제 감염 스냅샷에서 관측된 값을 기준으로 조정하고, 조정 근거를 이 문서에 기록한다. 값 자체보다 "계획 단계에서 fail-closed" 라는 성질이 안전장치의 본체다.

### 동일 해시 반복 항목은 별도 상한을 받는다

랜섬웨어는 **모든 폴더에 같은 랜섬노트를 뿌린다.** 실제로 수천 장이며, 단일 상한 1000에 걸려 치료가 중단된다. 대화형은 승인으로 넘어갈 수 있지만 **랜섬웨어 대응은 대개 무인 대량 배포 상황**이고 거기서는 fail-closed다 — 가장 필요한 곳에서 막힌다.

문제의 뿌리는 상한이 **동작의 성격을 구분하지 않는다**는 점이다. "서로 다른 5천 개 파일을 지운다"와 "동일 해시 5천 장을 지운다"는 위험이 전혀 다르다. 후자는 **판정 근거가 한 번만 필요했으므로 위험이 개수에 비례하지 않는다.**

- 계획기가 Action 집합을 보고 **어느 상한을 적용할지 스스로 판단**한다. 플러그인은 상한을 조정할 수 없다
- 동일 해시 판정은 계획 단계에서 이미 확보된 `sha256` 으로 한다
- 두 상한은 **독립적으로** 걸린다. 서로 다른 파일 1001개는 여전히 중단된다

### 싼 조건을 먼저 평가한다

`sha256 in [...]` 같은 조건은 대상 파일을 읽어야 판정된다. `%ALLUSERPROFILES%` 범위에서 이것을 무차별로 하면 성능과 프라이버시가 함께 나빠진다.

**계획기가 조건을 재배열해 크기·경로·확장자 같은 싼 조건을 먼저 평가하고, 통과한 것만 해시한다.** 이것을 스키마 수준의 보장으로 둔다 — 작성자가 조건 순서를 최적화하지 않아도 되게 하고, AI가 쓴 룰이 순서에 따라 성능이 갈리지 않게 한다.

**계획 단계에서 판정할 수 없는 것이 둘 있다.** 둘 다 **apply 시작 직후, 백업과 파괴 이전**에 판정한다 — 판정 시점이 파괴 이전이므로 "폭주를 실행 전에 막는다"는 성질은 유지된다. 문서와 코드 양쪽에 이 예외를 적어 두어, "모든 상한은 계획 단계"라는 일반화가 조용히 틀리는 일을 막는다.

| 무엇 | 왜 계획 단계가 아닌가 |
|---|---|
| `process.kill` 술어당 대상 수 | 술어가 몇 개의 프로세스를 지목할지는 실행 시점에야 알 수 있다 (§1) |
| **재귀 삭제의 하위 신뢰 서명** (§4 조건 3) | 계획기는 파일 시스템을 열거할 수 없다 (§1 — 탐지는 불활성 스냅샷 위에서만 돈다). 그 디렉터리에 무엇이 들어 있는지는 실행기만 안다 |

> **2026-08-25 (P10-C) 추가.** 두 번째 줄은 원래 "계획에 포함되기 위한 조건" 으로 적혀 있었다. 실제로 채우려고 보니 **계획기가 판정할 재료를 가질 수 없다** — 스냅샷에는 매치된 증거만 담기고, 재귀 삭제 대상 아래의 모든 파일이 아니다. 담게 하면 스냅샷이 불어나고, 담아도 계획과 실행 사이에 파일이 바뀔 수 있어 실행 시점 확인이 여전히 필요하다. `process.kill` 과 같은 성격이므로 같은 자리에 둔다.

### 재귀 삭제 추가 가드

`dir.delete_recursive` 는 아래를 모두 만족해야 한다. **어디서 판정하는지가 조건마다 다르다.**

| 2 | 해당 디렉터리 안에서 **악성 판정된 파일이 최소 1개 확인**되어야 한다 (`guard` 참조 필수) | 계획 | 〃 |

| 6 | 하위 항목 수·깊이가 **규모 상한**을 넘으면 거부 | **실행** (백업 전) | `apply::refusal_before_backup` → `PlatformWrite::survey_recursive_target` |

> **2026-08-26 — 조건 6 을 더했다.** 위 상한 표가 *"재귀 삭제 1건당 하위 항목
> 500 · 최대 깊이 8"* 을 정했고 `Limits` 에 필드도 있었는데 **어디서도 비교되지
> 않았다.** `apply` 가 `remove_dir_all` 을 그냥 불렀다.

> 조건 1~5 는 **어디를** 지울지 좁힌다. **얼마나** 를 막는 것이 없었다 —
> `capture` 가 뽑은 폴더 안에 사용자 트리가 있으면 통째로 사라진다. 백업은
> 되므로 되돌릴 수는 있지만, 격리소 용량과 실행 시간에 상한이 없었다.
>

> 계획에 없으면 실행기가 거부한다 — 재귀 삭제가 상한 없이 도는 것은 그 Op 의
> 정상 상태가 아니다.
>
> 조건 3 과 **한 번에 훑는다.** 두 번 훑으면 그 사이에 트리가 바뀔 수 있고
> I/O 도 두 배다.

3 번이 실행 시점인 이유는 위 표에 있다. **확인하지 못하면 거부한다** — 읽을 수 없는 파일, 서명을 판정하지 못한 파일, 링크 너머, 그리고 다 보지 못한 경우가 전부 거부다. `Ok(빈 목록)` 은 "지워도 된다" 를 뜻하므로 그 값을 낼 수 있을 때만 낸다.

2번이 핵심이다. capture 해석이 어긋나 `script_dir`가 엉뚱한 상위 경로로 잡혀도, 그 안에 악성 판정 파일이 없으면 계획이 만들어지지 않는다.

> **2026-08-26 (P11 r2) — 2번이 못 막는 경우가 있어 조건 5를 더했다.** 페이로드가 상한 바로 아래에 있으면 `dirname`이 상한 자체가 되는데, **그 안에 악성 판정 파일이 있으므로 조건 2는 통과한다.** 실측으로 첫 플러그인이 `%LOCALAPPDATA%\Programs` 전체를 재귀 삭제 대상으로 삼았다 — 사용자가 설치한 정상 프로그램이 전부 있는 자리다.
>
> 상한과 같아졌다는 것은 capture가 예상대로 풀리지 않았다는 신호이고, **상한 전체를 지우는 것이 어떤 룰의 의도일 수는 없다.** AI 합격 시험 r2가 룰 쪽에서 이 모양을 막는 조건을 스스로 넣어 드러났다.

### 레지스트리 키 삭제는 재귀 삭제와 같은 가드를 받는다

`registry.delete_key` 는 값이 아니라 **하위 트리 전체**를 지운다 — 파일시스템의 `dir.delete_recursive` 와 같은 성격이다. 따라서 같은 조건을 요구한다.

1. 대상 키가 **증거에서 추출된 것**이어야 한다 (리터럴 키 경로 금지)
2. 그 키 안에서 **악성 판정된 값이 최소 1개 확인**되어야 한다 (`guard` 필수)
3. 하위 키·값 수와 깊이에 상한
4. **OS 구조 키는 1층 보호 목록에 준해 취급한다** — `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options` 자체는 지울 수 없고, **그 아래 개별 하위 키만** 대상이 된다

4번이 실무상 가장 중요하다. IFEO 항목을 제거한다는 것은 `...\Image File Execution Options\notepad.exe` 를 지우는 것이지 `Image File Execution Options` 를 지우는 것이 아니다. 와일드카드 열거로 대상을 잡을 때 **한 단계 위를 잡는 실수**가 나기 쉬우므로, 보호 목록에 부모 키를 넣어 구조적으로 막는다.

### 인증서 제거는 고위험으로 분류한다

`cert_store.remove` 는 파일 삭제보다 위험하다. 신뢰 루트를 잘못 지우면 **시스템 전체의 TLS 연결이 깨지고**, 기업 환경에서는 사내 CA를 지워 전사 장애를 만들 수 있다. 다음을 강제한다.

- OS 기본 신뢰 루트 목록은 **1층 보호 목록에 준해 취급**한다. 플러그인이 지정해도 계획에 포함되지 않는다
- 지문(thumbprint)을 **정확히 일치**로만 지정할 수 있다. 발급자·주체에 대한 부분 일치 삭제는 불가
- 무인 모드에서도 이 Op는 **항상 명시적 승인 대상**이다

### 여러 플러그인이 동시에 도는 경우

- **상한은 실행 단위로 합산한다.** 플러그인별 상한이면 10개를 함께 돌려 상한을 10배로 만드는 우회가 생긴다
- 서로 다른 플러그인이 **같은 대상을 지목하면 Action을 하나로 합치고**, `because` 에 양쪽 증거를 모두 기록한다. 같은 파일을 두 번 지우려다 두 번째가 실패로 기록되는 잡음을 없앤다
- 한 플러그인이 가드에 걸려 중단되면 **실행 전체가 중단된다.** 나머지 플러그인만 진행하지 않는다 — 부분 실행 상태가 사용자에게 설명 불가능해진다

## 5. 격리와 복원

### 격리 컨테이너

실행 1회당 파일 1개(`<quarantine>/<run_id>.rq`). 포함 항목: 파일 본문, 레지스트리 값(타입+원본 데이터), 작업 정의 XML, cron 라인과 원본 위치, systemd 유닛, 셸 자동실행 라인, 브라우저 확장 디렉터리.

- **봉인 목적**: (1) 격리물 재실행 방지, (2) 타 백신의 재탐지·재격리로 인한 혼선 방지, (3) 우발적 유출 완화
- **정직한 한계 명시**: 패스프레이즈 없는 기본 모드의 암호화는 *기밀성 보장이 아니라 봉인*이다. 감염 호스트에서 관리자 권한을 가진 악성코드는 로컬 키에 접근할 수 있다. 문서와 UI에 그대로 쓴다
- **보존 정책**: 자동 삭제하지 않는다. 삭제는 사용자의 명시적 `purge` 명령으로만

### 평문 헤더는 세 물음에만 답한다

**바이트 배치는 설계-02 §9가 소유한다.** 여기서는 *무엇을 평문에 두는가*와 그 근거만 정한다 — 배치를 두 문서에 적으면 갈라진다.

평문이 답해야 하는 물음은 셋뿐이고, 그 이상은 담지 않는다.

1. **이 파일이 무엇인가** — `magic` · `fmt_ver` · `core_version`
2. **내가 이것을 열 수 있는가** — `wraps[]` 의 `kind` · `key_id` · `cipher`
3. **어느 실행에서 나왔는가** — `run_id` · `created`

나머지는 전부 암호 영역이다 — 플러그인 ID, 위협 이름, 규칙 참조, 엔트리 색인과 원본 절대 경로, 항목 메타데이터와 본문. **엔트리 개수도 평문에 두지 않는다.**

**플러그인 ID와 위협 이름은 평문에 두지 않는다.** 불투명 식별자로 바꿔 두는 절충도 채택하지 않는다 — 그 값이 **결정적**이면 여러 대의 컨테이너를 모았을 때 "이 12대가 같은 위협"이 그대로 드러나 이름만 가린 상관관계가 되고, **무작위**면 묶는 기능이 없어 존재 이유가 사라진다. 무엇보다 **키 없이 위협 이름을 알아야 하는 시나리오가 없다.** 복원은 "이 run 의 격리물을 되돌려라"이지 "EvilAI 격리물을 되돌려라"가 아니다. 지원 상황에서는 `run_id` 로 감사 로그(§7)와 대조하고, 로그가 없으면 키가 있는 머신에서 연다.

**호스트 이름도 담지 않는다.** 어느 머신 것인지는 로컬 키 wrap 의 `key_id`(키 지문)가 가리키며, 조직 복구 시에는 자산 대장과 대조한다. 사람이 읽을 수 있는 기계 이름을 평문에 둘 이유가 없다.

**포맷은 알고리즘에 중립이다.** `cipher` 와 `wraps[].alg` 를 헤더에 명시하고, 지금은 각각 하나만 구현한다. 격리물은 자동 삭제하지 않으므로(위 보존 정책) **포맷 실수는 영구적이다** — 교체 여지를 처음부터 남긴다.

> **이 구분이 지키는 것의 정확한 범위**: 기본 모드의 암호 영역은 *같은 머신의 관리자에게는 열린다*(위 "정직한 한계"). 그러므로 평문/암호 구분이 실제로 지키는 것은 **컨테이너가 그 머신 밖으로 나갔을 때**뿐이다 — 백업에 섞여 나가거나 지원팀에 전달될 때 위협 이름과 원본 경로가 드러나지 않는다. 그 이상을 주장하지 않는다.

### 채택 알고리즘

| 자리 | 선택 | 근거 |
|---|---|---|
| AEAD | **X**ChaCha20-Poly1305 | 논스가 192비트라 컨테이너마다 난수로 뽑아도 재사용 위험이 없다. 카운터를 관리하는 설계는 재설치·복원·병렬 실행에서 그 관리가 깨진다. AES-NI 없는 32비트 대상에서도 소프트웨어 상수시간 |
| 패스프레이즈 KDF | Argon2id | 메모리 하드 |
| 조직 복구 wrap | X25519 + HKDF-SHA256 | **RSA 를 쓰지 않는다.** `deny.toml` 의 RUSTSEC-2023-0071 예외가 "코어가 RSA 개인키를 다루면 즉시 재평가"를 조건으로 달고 있고, 설계-01 미결 5의 서명 후보도 Ed25519 계열이다. 공개키만 배포하면 되는 성질도 그대로 유지된다 |
| 로컬 머신 wrap | 플랫폼 고유 (Windows DPAPI · Linux 루트 전용 키 파일) | `remedy-platform` 에 둔다 |

`cargo deny check` 통과를 확인하고 채택했다.

### 키 관리 — 복원 불가 상태를 만들지 않는다

로컬 키 하나로 암호화하면 **머신을 재설치하는 순간 격리물이 영구히 열리지 않는다.** 오탐으로 격리된 사용자 문서가 그대로 소실된다는 뜻이고, 이는 도구가 존재하는 이유와 정면으로 충돌한다.

컨테이너마다 **무작위 콘텐츠 키**를 만들고, 그 키를 여러 방법으로 **감싸서(wrap) 헤더에 함께 저장**한다.

```
  content_key (컨테이너마다 무작위)
     +-- wrap #1: 로컬 머신 키        -> 같은 머신에서 즉시 복원 (기본 경로)
     +-- wrap #2: 사용자 패스프레이즈  -> 지정한 경우에만. 머신과 무관하게 복원
     +-- wrap #3: 조직 복구 공개키    -> 기업 배포 시 설정. 재설치 후에도 복원 가능
```

- 최소 하나의 wrap은 반드시 존재한다. 로컬 키 wrap만 있는 경우 **"이 머신을 재설치하면 복원할 수 없다"를 격리 시점에 경고**한다
- 조직 복구 키는 **공개키만 배포**한다. 감염 호스트에 개인키가 없으므로 악성코드가 훔칠 것이 없다
- 패스프레이즈 wrap을 쓸 때만 실질적 기밀성이 생긴다. 그 외에는 봉인이다

`purge` 는 컨테이너 파일 삭제이며, 되돌릴 수 없음을 확인받는다.

### 저널 — 그리고 자동 롤백을 하지 않는 이유

파일·레지스트리·작업에 걸친 진짜 원자성은 불가능하다. **fsync 된 append-only 저널**을 쓰되, 그 목적은 자동 롤백이 아니라 **복원 가능성의 보장과 정확한 상태 보고**다.

```
  각 Action 마다:  intent 기록 -> 백업 완료 기록 -> 수행 -> 결과(성공/실패) 기록
```

**치료 도중 실패해도 이미 수행한 파괴를 자동으로 되돌리지 않는다.** 이것은 일반적인 트랜잭션 설계와 반대이며, 의도적이다.

> 로더와 페이로드를 지우는 계획에서 로더는 지워졌고 페이로드 삭제가 실패했다고 하자. 여기서 롤백하면 **로더가 복원되어 위협이 재무장된다.** 절반만 제거된 상태가 위험한 것은 사실이지만, 온전한 악성코드로 되돌리는 것보다는 낫다. 데이터 트랜잭션의 직관("전부 아니면 전무")을 위협 제거에 그대로 옮기면 안 된다.

실패 단계별 정책은 다음과 같다.

| 실패 지점 | 동작 | 근거 |
|---|---|---|
| **백업 중 실패** | **즉시 중단.** 아직 아무것도 파괴되지 않았다 | 복원 불가능한 파괴를 시작하지 않는다 |
| **파괴 중 실패** | 롤백하지 않고 **나머지 계획을 계속 수행**. 실패 항목은 재부팅 재시도 큐로 | 부분 제거 > 완전 복구된 악성코드 |
| **크래시 후 재기동** | 저널을 읽어 미완 계획을 **이어서 수행** (되돌리지 않음) | 위와 동일 |
| 사용자가 오탐이라 판단 | `remedy restore` 를 **명시적으로 호출** | 되돌리기는 사람의 결정이다 |

`process.kill` 처럼 보상 불가능한 Action은 되돌림 가능한 Action보다 **먼저** 배치되고(§2 순서), 멱등하게 설계한다.

**결과 보고는 상태를 있는 그대로 말한다.** "롤백했습니다"라고 뭉뚱그리지 않고, 제거된 것·남은 것·재부팅 후 재시도할 것·복원 방법을 각각 명시한다. 부분 치료는 종료 코드 3으로 구분되며(설계-02 §8), 무인 배포에서는 이 코드가 후속 조치의 트리거가 된다.

### 재부팅 재시도 큐

파괴 중 실패한 Action은 **원래 계획의 일부 그대로** 큐에 남는다. 재부팅 후 `remedy verify` 가 이 큐를 이어 실행한다 — **새로 스캔하지 않는다.** 재스캔하면 환경이 달라 다른 계획이 나오고, 사용자가 승인한 것과 다른 일이 벌어진다. 큐에는 유한한 시도 횟수와 만료를 두어, 영원히 재부팅마다 되살아나는 항목이 생기지 않게 한다.

> **v1 에서 하지 않는다 (2026-09-30 결정)** — 파괴 중 실패는 `Failed` 로 남고 부분 치료(종료
> 코드 3)로 보고된다. 위 문단은 큐를 `verify` 가 이어 실행한다고 적지만, §8 은 `verify` 를 재평가 전용으로
> 두고 이어 실행은 `resume` 에 맡겼다 — 둘이 어긋나 있었다. 저널의 빈 구조(`Outcome::Deferred` 등)는
> 지웠다(`bc584be`).

### 복원 명령

`remedy restore --run <run_id>` (전체) / `--entry <id>` (개별). 복원은 파일 본문뿐 아니라 타임스탬프·소유자·권한까지 되돌린다. **복원 시 되살릴 수 없는 메타데이터가 있으면 복원 전에 목록으로 경고한다.**

경고가 *복원 전*이라는 것이 명령의 형태를 정한다. 두 단계다.

1. **계산** — 무엇을 어디에 되돌리며 무엇을 못 살리는지 먼저 낸다
2. **수행** — 그 목록을 확인한 뒤에만

`--extract-to <dir>` 는 제자리 복원 대신 지정한 디렉터리로 본문만 꺼낸다. **조직 복구 공개키 wrap 이 실제로 사는 것이 이 경로다** — 머신을 재설치한 뒤에는 원래 자리도 원래 SID도 없으므로, 되찾아야 하는 것은 내용이다. 제자리 복원이 원래 머신에서만 보장되는 이유는 설계-02 §9 "여는 것과 되돌리는 것은 다르다"에 있다.

### 복원도 쓰기다

**불변식 R**: `restore` 는 컨테이너에 기록된 항목만, 기록된 **절대 경로 그대로** 되돌린다. 경로를 재해석하지 않고, 새 대상을 탐색하지 않으며, 환경 변수 토큰을 전개하지 않는다 — **컨테이너에는 전개된 절대 경로만 들어간다.** 토큰을 넣으면 다른 머신·다른 사용자에서 다른 곳으로 복원된다.

불변식 P(§1)는 `apply` 에 대한 것이고 입력이 `plan.json` 이다. `restore` 의 입력은 컨테이너이므로 따로 진술한다. 컨테이너는 "이미 한 번 승인·수행된 것"의 기록이고 그 정확한 역만 수행하므로, 탐색 금지라는 성질은 같다.

**그리고 복원 대상 경로도 보호 목록 검사를 받는다.** 컨테이너가 변조되면 임의 경로 쓰기가 되는데, 헤더를 AAD 로 묶어 변조는 탐지되지만 **탐지에만 기대지 않는다.** §3의 보호 목록에 걸리면 복원을 거부한다(종료 코드 5). "복원은 되돌리는 것이니 안전하다"는 직관이 틀리는 지점이다 — 복원도 쓰기고, 쓰기는 전부 가드를 받는다.

#### 보호 디렉터리 **하위의 개별 파일**은 저널이 가른다 (2026-08-28)

위 문단은 한동안 "보호 목록에 걸리면 무조건 거부" 로 구현돼 있었다. 그런데 §3 1층은 **보호 디렉터리 하위의 개별 파일 삭제를 조건부로 허용한다.** 두 규칙이 갈라지면 **"지울 수는 있는데 되돌릴 수는 없는" 대상**이 생긴다.

Linux 에서 그것이 거의 전부였다 — 보호 목록에 `/etc` 와 `/usr` 가 있고 systemd 유닛 · cron · XDG autostart · 신뢰 인증서가 전부 그 아래 산다. Windows 에서도 `System32` 하위의 악성 DLL 이 같은 상태였다. 설계-09 §2 *"되돌리는 길이 없는 파괴는 만들지 않는다"* 와 정면으로 어긋난다.

**그렇다고 컨테이너가 지시하는 대로 열어 줄 수는 없다.** 컨테이너는 패스프레이즈나 조직 복구 키로도 열리므로, 넘겨받은 격리물 하나로 System32 에 임의 파일을 심는 데 **기계 장악이 필요하지 않다** — 분석가에게 "고객 격리물인데 복원해 달라" 고 건네는 것으로 족하다.

**판별자는 이 기계의 저널이다.**

| 조건 | 복원 |
|---|---|
| 보호 디렉터리 **자체** · 드라이브/파일시스템 루트 · 사용자 홈 | **거부(5)** — 무엇으로도 |
| 보호 디렉터리 하위의 **디렉터리 나무** | **거부(5)** — 계획기가 그 자리의 재귀 삭제를 거부하므로 그런 엔트리는 애초에 생기지 않는다 |
| 보호 디렉터리 하위의 **개별 파일**, 저널이 보증함 | **허용** |
| 보호 디렉터리 하위의 **개별 파일**, 보증 없음 | **거부(5)** — `--extract-to` 로만 꺼낸다 |

보증은 `<state>/journal/<run_id>.jsonl` 이 그 run 에서 `Intent{target}` 과 `Backup{entry_id}` 를 함께 기록했고, 그 `target` 이 컨테이너 엔트리의 `origin` 과 **같을 때** 성립한다. 대상까지 대조하지 않으면 `e0` 같은 엔트리 이름을 재사용한 컨테이너가 통과한다.

넘겨받은 컨테이너에 저널이 없는 것은 결함이 아니라 **설계다** — 설계-02 §9 가 *"여는 것과 되돌리는 것은 다르다"* 로 이미 그 경로를 `--extract-to` 로 정해 두었다. 제자리 복원이 원래 머신에서만 보장되는 이유와 같은 문장이다.

> **이 규칙은 실기기가 만들었다.** 앞선 판에서 보호 목록 검사를 §3 과 같은 두 겹으로 바꿨더니 `testbed/harness/guest/Verify-P5.ps1` 의 *"보호 경로 항목이 있으면 가드 중단(5)"* 이 실기기에서 깨졌다 — 미끼 파일 이름이 `remedy-should-never-write.dll` 이다. 시험 833개가 전부 통과한 상태였다.

쓰기를 세 종류로 나누고, 그중 둘만 `remedy-platform` 의 쓰기 경계를 지난다.

| 무엇을 쓰나 | 어디에 | 쓰기 경계 경유 | Phase |
|---|---|---|---|
| 격리 컨테이너 · 저널 | remedy 자기 상태 디렉터리 | **아니오** | P5 |
| 복원 (원본 위치로 되돌리기) | **시스템 경로** | **예** | **P5** |
| Op 별 파괴 | 시스템 경로 | 예 | P6~P8 |

자기 상태 I/O 까지 경계에 넣으면 "시스템에 손대는 곳은 여기 하나"라는 성질이 흐려진다. 격리소에 쓰는 것은 Action 이 아니라 Action 의 부산물이며, 감사 로그에 독립 항목으로 남을 것도 아니다.

**복원 쓰기가 파괴 쓰기보다 먼저 경계를 여는 것은 순서 자체가 안전장치이기 때문이다** — 되돌리는 길이 없는 파괴는 만들지 않는다(설계-09 §2).

## 6. 플러그인 신뢰: 서명과 폐기

### 서명 강제

- 서명되지 않았거나 검증 실패한 플러그인은 **로드 거부**. 개발 모드(`--allow-unsigned`)는 별도 빌드 태그가 붙은 개발 바이너리에서만 존재하며, 배포 바이너리에는 플래그 자체가 없다
- 서명 대상은 플러그인 디렉터리 전체의 매니페스트(파일별 다이제스트)여야 한다. 룰 파일 하나만 서명하면 YARA 룰·스크립트 교체가 가능해진다

이유는 방어보다 **오용 방지**에 가깝다. 임의의 파일을 지우고 프로세스를 죽이는 서명된 바이너리가 임의의 텍스트 파일을 지시서로 받아들이면, 그 자체가 배포된 파괴 도구다.

> **2026-08-26 (P10-D) 구현.** 이 절의 2층이 섰다 — 서명된 폐기 목록, 코어에 컴파일되는 최소 버전 표, 그리고 역행 금지. 모드별 신선도 정책도 함께 왔다. **`revocation fetch` 만은 만들지 않았다**: HTTP 를 배포 바이너리에 링크하는 일이고 설계-01 D9 가 치료 경로의 네트워크를 막는다. 목록을 어떻게 받든 들어오는 문은 `revocation import` 하나이므로 폐기 메커니즘 자체는 완결이다.

### 킬 스위치는 2층

감염 PC는 인터넷이 차단된 경우가 흔하므로 온라인 폐기 목록 하나에 의존할 수 없다. 조사한 모든 선례(TUF, UEFI dbx, Android Verified Boot, Windows 드라이버 차단 목록, Chrome CRLSet, Firefox OneCRL, Java blacklist)가 예외 없이 같은 구조였다.

> **판정은 로컬에서 하고, 네트워크가 필요한 것은 규칙의 배포뿐이다.**

그리고 온라인 조회 단독은 신뢰할 수 없다 — 네트워크를 차단할 수 있는 공격자는 폐기 조회도 차단할 수 있으므로, 조회 실패를 통과로 처리하는 soft-fail은 공격자가 스스로 유발할 수 있는 실패다. Chromium이 온라인 폐기 조회를 기본 비활성화하고 사전 배포형 CRLSet으로 옮긴 이유가 이것이다.

**(a) 온라인 폐기 목록** — 서명된 revocation list(`plugin_id`, 버전 범위, 사유, 발행 시각). HTTPS로 받아 캐시하고 서명 검증 후 적용. 최신·세밀한 통제 담당.

**(b) 바이너리 내장 최소버전 + 역행 금지** — 코어 바이너리에 `min_plugin_version` 을 **컴파일해서** 배포하고, 한 번 관측한 것보다 낮은 버전의 플러그인·폐기 목록을 거부한다.

**(b)를 만료 시각이 아니라 버전 정수로 두는 것이 핵심이다.** 악성코드는 시스템 시계를 흔히 조작하므로 만료 기반 규칙은 공격자가 시계를 되돌려 무장 해제할 수 있지만, 컴파일된 정수 비교는 그렇지 않다. Android Verified Boot가 정확히 이 형태다(`rollback_index >= stored_rollback_index`, 변조 감지 가능 저장소에 기록). 역행 금지가 없으면 공격자가 알려진 결함 버전을 다시 제시할 수 있다.

### 신선도 정책은 실행 모드로 가른다

캐시된 폐기 목록이 낡았거나 없을 때의 정책을 **하나로 정하지 않는다.**

| 모드 | 정책 | 근거 |
|---|---|---|
| **대화형** (사용자가 직접 실행) | 동작 + 명시적 신선도 경고 | 인터넷 없는 감염 PC가 이 도구가 가장 필요한 상황이다. 여기서 막으면 도구가 아니라 장애물이 된다 |
| **무인·대량 배포** | **fail-closed** (중단) — 단, 아래 오프라인 반입 경로가 있다 | 사고를 키우는 것은 언제나 무인 대량 배포다. 사람이 보고 있지 않다면 보수적으로 멈춘다 |

### 폐쇄망을 막다른 길로 만들지 않는다

위 표를 그대로 적용하면 모순이 생긴다. **폐쇄망 기업 환경이 곧 "신선도 확인 불가" 상태**인데, 거기가 무인 대량 배포의 주 무대다. 규칙대로면 도구가 가장 필요한 곳에서 항상 중단된다.

해소는 **폐기 목록을 네트워크가 아닌 경로로도 반입할 수 있게** 하는 것이다.

```
  인터넷 연결된 관리 서버
     -> remedy revocation fetch --output revocations.sig
     -> (파일 공유 / 이동식 매체로 폐쇄망 반입)
     -> 배포 시:  remedy run --yes --revocations \\share\revocations.sig
```

- 반입된 목록도 **서명 검증과 역행 금지를 동일하게 거친다.** 반입 경로가 신뢰를 낮추지 않는다 — `revocation import` 가 그 둘을 그대로 태운다 (P10-D)
- 목록에 담긴 발행 시각이 신선도 판정의 기준이 된다. 관리자가 얼마나 자주 갱신할지는 그 조직의 정책이다
- 이 경로 없이 `--yes` 를 쓰면 중단된다. **관리자가 신선도에 대해 의식적으로 책임지게 하는 것**이 목적이지, 실행을 막는 것이 목적이 아니다

Windows의 신뢰할 수 없는 인증서 목록(disallowed CTL)이 정확히 이 형태다 — 온라인 갱신이 기본이되, 연결이 전혀 없으면 파일을 받아 이동식 매체로 옮기는 경로를 공식 문서가 안내한다. 오프라인 반입은 예외 처리가 아니라 **정식 배포 경로 중 하나**로 설계한다.

이 분기는 임의 절충이 아니라 업계 선례가 갈리는 지점 그대로다 — Microsoft 자신도 Safety Scanner(MSERT)는 다운로드 후 10일 만료를 걸고, Malicious Software Removal Tool(MSRT)은 만료 없이 경고만 한다. **"만료가 옳다"는 합의는 존재하지 않으므로, 우리는 위험이 실제로 다른 두 모드를 분리한다.**

판단 기준으로는 HTTP 캐싱 표준의 `must-revalidate` 정의가 가장 명료하다 — **낡은 데이터를 받아들이는 것이 "조용한 오작동"을 유발할 때만 fail-closed**로 가고, 단지 확신이 낮아지는 것뿐이라면 경고로 족하다. 무인 배포에서 폐기된 플러그인이 도는 것은 조용한 오작동이고, 대화형 실행에서 신선도 정보가 낡은 것은 확신 저하다.

## 7. 감사 로그

NDJSON 스트림. **결과뿐 아니라 판단 근거를 남긴다** — "무엇을 지웠나"만으로는 오탐 사후 분석이 불가능하다.

```json
{"ts":"...","run_id":"...","phase":"plan","event":"action_planned",
 "action":{"seq":3,"op":"file.delete","target":"C:\\...\\main.js","sha256":"...","size":1234},
 "because":["dropped-payload#0"],"rule_hits":[{"rule":"dropped-payload","yara":"evilai_locust_js"}],
 "guards":{"protected_path":false,"trusted_signature":false,"cap_remaining":197}}
```

필수 필드: 실행 식별자, 호스트·OS, 플러그인 ID/버전/다이제스트/서명 주체, 단계, 이벤트, Action 전문, **증거 참조(`because`)**, 통과한 가드 판정, 결과·오류.

- 모든 파괴 Action은 `because`가 비어 있을 수 없다 — 계획기가 강제한다
- 제외(스킵)된 대상과 그 사유도 기록한다. 오탐 분석에서는 "왜 안 지웠나"보다 "왜 지웠나"가 필요하지만, 미탐 분석에서는 그 반대다
- **인텔 조회와 제출도 기록한다.** 무엇을 물어봤고 무엇을 받았는지(`enrich`), 무엇을 꾸러미에 담았는지(`submit`)가 남아야 한다. 나가는 데이터에 대한 사후 확인 수단이 로그뿐이다 (설계-00 §7)
- 사후에 엔진 정식 기능으로 승격시킬 때 이 로그가 근거 자료가 된다. **치료 성공률·잔존율·오탐 건수·복원 요청 건수가 집계 가능한 형태**여야 한다 (설계-00 §5-1)

## 8. 재부팅 후 검증

`verify_after_reboot`는 코어가 일회성 자동실행 항목(Windows: RunOnce, Linux: systemd oneshot — `@reboot` 은 쓰지 않는다, P12 D1)을 등록해 `remedy verify --run <id> --plugin <경로>`를 수행하게 한다.

> **`--plugin` 이 빠져 있었다 (2026-08-28 v1 점검에서 발견).** 예약되던 것은 `verify --run <id>` 뿐이었고, `verify` 는 룰을 `--plugin` 으로 읽으므로 그 명령은 **사용법 오류로 즉시 끝난다.** RunOnce 는 콘솔 없이 돌고 OS 가 항목을 먼저 지우므로 아무 흔적도 남지 않는다 — 즉 P10-F 가 닫힌 뒤로 이 절의 약속이 한 번도 지켜지지 않았다.
>
> 단위 시험이 놓친 이유는 **레지스트리 값을 쓰는지만 쟀기** 때문이다. 그 값이 실행 가능한 명령인지는 아무도 묻지 않았다. 지금은 `crates/remedy-cli/tests/scheduled_verify.rs` 가 **예약될 문자열을 그대로 실행해** 확인한다.
>
> 그래서 예약은 **플러그인 경로를 아는 실행에서만** 선다(`remedy run --plugin ...`). `apply --plan` 은 계획서만 받고 계획서에는 기계 경로가 없으므로 — 그 파일은 사람이 읽고 승인하는 문서다 — **예약하지 않고 그 사유를 말한다.**

### `verify` 는 재판정이지 경로 확인이 아니다

"제거한 경로가 여전히 비어 있는가"만 보면 **랜덤 이름을 쓰는 위협 앞에서 무력하다.** 페이로드가 `%LOCALAPPDATA%\Programs\<랜덤>` 에 있었다면 재감염 시 **다른 랜덤 이름**으로 생기고, 원래 경로는 계속 비어 있다.

따라서 `verify` 는 **수집과 평가를 다시 돌려 판정이 재현되는지**를 본다.

```
  verify = re-collect -> re-evaluate -> 같은 플러그인이 다시 판정하는가?
             |
             +-- 판정 없음 · 다 봄    -> 치료 성공
             +-- 판정 없음 · 다 못 봄 -> 치료를 확인하지 못함 (종료 6, 2026-10-26)
             +-- 다시 판정됨          -> 재발. 새 증거를 보고하고 재치료 여부를 묻는다
             +-- 일부 항목만 잔존     -> 부분 치료로 보고
```

> **다 보지 못한 재평가는 "치료 성공" 이 아니다 (결정 2026-10-26).** 그 전에는 재평가가 잘리거나(상한) · 막히거나(접근 거부) · 범위에 든 subject 를 수집하지 못했거나 · 선언한 자리가 전부 없거나 · YARA 를 재지 못해도(`Observation::is_complete` 의 다섯 사유) 판정도 남은 증거도 없으면 `clean` · 종료 0 이 나갔다. 재부팅 뒤 회차에는 사람이 없어 그 0 이 **"치료가 유지됐다"** 로 읽힌다. 이제 그 자리는 `incomplete` · 종료 6 이다. 갈래는 `scan` 의 종료 코드와 같은 규칙으로 가린다 — **찾은 것이 먼저다**: 다시 선 판정(2) > 남은 증거(3) > 다 못 봄(6) > 성공(0). 다 보지 못한 것은 "없다" 만 뒤집고, 찾은 것은 그래도 유효하다.

이것이 `resume` 과 **정반대 성격**임을 분명히 한다. `resume` 은 이미 승인된 계획을 이어 실행하며 **절대 재스캔하지 않는다**(사용자가 승인한 것과 다른 일이 벌어지면 안 되므로). `verify` 는 반대로 **반드시 재평가한다**(같은 결과가 나오는지가 질문이므로). 두 명령을 분리한 것이 이 때문이다.

재발이 확인되면 자동으로 다시 치료하지 않는다. **같은 치료를 반복해도 같은 결과가 나올 가능성이 높고**, 재발은 우리가 놓친 지속성 경로가 있다는 신호이므로 사람의 판단이 필요하다.

**자기 흔적 규칙**: 도구가 스스로 만든 지속성 항목은 (1) 고정된 식별 가능한 이름을 쓰고, (2) 검증 직후 스스로 제거하며, (3) 감사 로그에 자기 항목으로 기록된다.

### 판정은 `<state>/verify/<run_id>.jsonl` 에 남는다 (2026-08-29)

예약된 실행에는 **사람이 없다.** 콘솔 출력은 아무도 보지 않고, 종료 코드는 그 프로세스와 함께 사라진다. 2026-08-29 실기기 측정에서 재부팅 뒤 `verify` 가 **실제로 도는 것**을 확인했는데(프로세스 생성 감사 4688 — 부팅 29초 뒤), **판정이 무엇이었는지는 어디에서도 알 수 없었다.**

§5 는 무인 배포에서 종료 코드 3(부분 치료)이 *"후속 조치의 트리거"* 라고 적는다. 받는 쪽이 없으면 그 문장이 성립하지 않는다.

그래서 `verify --run <id>` 는 판정을 상태 디렉터리에 **덧붙인다.** 그 자리에 이미 이 run 의 나머지가 있다 — `plan/`(무엇을 하려 했나) · `journal/`(무엇을 했나) · `quarantine/`(되돌리는 수단). 재평가는 **그 run 에 대한 판정**이므로 같은 자리에 붙는다.

| | |
|---|---|
| 무엇이 적히나 | 시각 · run_id · 플러그인 id/버전 · `outcome` · **종료 코드** · 다시 선 판정 · 남아 있는 증거 · 다 보지 못했으면 결과와 무관하게 **그 관측**(무엇을 못 봤나 — 본문 상한 같은 원인은 회차 로그에. 2026-10-26, 온전한 회차의 줄에는 없다) |
| 언제 적히나 | `--run` 이 있을 때. 없으면 어느 치료에 대한 판정인지가 없어 **붙일 자리가 없다** |
| 덮어쓰나 | **아니다.** 예약된 것 한 번, 사람이 한 번 부를 수 있고, 뒤엣것이 앞엣것을 지우면 *"재부팅 직후에는 무엇이었나"* 를 물을 수 없다 |
| 못 적으면 | 경고만 하고 종료 코드는 바꾸지 않는다. 기록하지 못한 것과 판정하지 못한 것은 다르다 |

`support-bundle` 이 이 파일을 함께 담는다 — 오탐을 의심하는 사람이 가장 먼저 볼 것 중 하나다(설계-04 §6).

> **남는 틈**: 기록 실패는 조용하다. 소비자는 *"재평가가 안 돌았다"* 와 *"돌았는데 못 적었다"* 를 구분하지 못한다. 두 번째 채널 없이는 닫을 수 없다.

> **RunOnce 는 로그온 때 돈다 — 부팅 때가 아니다.** 로그온하지 않는 기계(서버·키오스크·사용자가 한동안 돌아오지 않는 PC)에서는 재부팅 후 검증이 **일어나지 않는다.** 우리 코드의 성질이 아니라 그 기계의 성질이고, 배포 시 알고 있어야 한다 (2026-08-29 실측: 랩 VM 은 자동 로그온을 켠 뒤에야 예약이 발화했다).

> **2026-08-26 (P10-F) 구현.** RunOnce 를 고른 결정적 이유가 규칙 (2) 였다 — **OS 가 항목을 실행 직전에 지운다.** 예약 작업이면 우리가 지워야 하고, 지우기 전에 실패하면 치료 도구가 정체불명의 자동실행을 남긴다. 규칙 (1)은 `remedy-verify` 고정 이름(run_id 는 값 데이터의 인자로 들어간다), (3)은 `apply` 가 예약한 자리를 그대로 출력하는 것으로 진다. 그리고 이 요청은 매니페스트가 아니라 **계획**이 나른다 — `apply` 는 계획만 받고 `resume` 은 재스캔하지 않기 때문이다. 치료 도구가 정체불명의 자동실행을 남기면 그 자체가 타 백신의 탐지 대상이 된다.

> **2026-09-23 (P12) 리눅스 구현.** systemd oneshot 유닛(`/etc/systemd/system/remedy-verify.service` + `multi-user.target.wants` 링크)을 **파일로만** 심는다 — `systemctl` 을 부르지 않는다. systemd 는 RunOnce 처럼 항목을 지워 주지 않으므로 규칙 (2) 는 유닛이 `ExecStartPre=-/bin/rm` 으로 **실행 직전에 자기 파일과 링크를 지우는 것**으로 진다. RunOnce 와 달리 **로그온이 아니라 부팅** 때 돈다. systemd 가 init 이 아닌 기계(컨테이너·WSL·OpenRC)와 유닛 자리가 읽기 전용인 기계에서는 걸지 않고, 계획 화면이 **승인 전에** 그렇다고 말한다. 규칙 (3) 은 이제 두 플랫폼 모두 **실행기가 `End` 앞에서 걸고 감사 로그(저널)에 적는 것**으로 진다 — 저널은 마지막 줄이 `End` 여야 끝난 회차이기 때문이다. **2026-09-23 P12 P7 에서 진짜 재부팅으로 확인했다** — Debian 12.15 랩 VM(systemd 252)에서 유닛이 부팅 때 돌아 실행 직전에 자기 파일과 링크를 지웠고, 재평가가 clean · 종료 0 으로 기록됐다(흔적 0, 두 회차 합격). `multi-user.target` 은 재평가가 끝난 뒤에 닿는다(실측) — 실제 플러그인은 제 재평가 시간만큼 부팅 완료를 늦춘다.

## 9. 플러그인 배포 자체가 사고 원인이 된다 — CrowdStrike Channel File 291

우리 플러그인은 구조적으로 CrowdStrike의 "Rapid Response Content"와 같은 것이다: **코드가 아니라 데이터이고, 제품 릴리스 게이트를 우회해 빠르게 배포되며, 코어의 동작을 바꾼다.** 2024년 7월 19일 사고를 그대로 읽을 필요가 있다.

사고의 형태: 콘텐츠 검증기(Content Validator)는 템플릿이 **21개 입력 필드**를 받는다고 보고 검증했는데, 실제 실행기(Content Interpreter)에는 **20개만** 전달되고 있었다. 21번째를 참조하는 인스턴스가 배포되자 배열 범위 밖 읽기가 발생해 커널이 죽었다. 78분 만에 되돌렸으나 Microsoft 추정 850만 대가 영향을 받았다. CrowdStrike의 근본원인 분석은 이를 세 요인의 합류로 정리한다 — **검증기와 실행기의 입력 개수 불일치, 실행기의 런타임 경계 검사 부재, 해당 필드에 대한 테스트 부재.**

여기서 remedy에 그대로 적용되는 규칙 네 가지를 도출한다.

**(1) 검증기와 실행기는 같은 스키마 정의를 공유해야 한다.** 플러그인 스키마를 검증하는 코드와 소비하는 코드가 각자 필드 목록을 들고 있으면 CF291과 같은 종류의 불일치가 생긴다. **스키마는 단일 소스에서 생성하고, 검증기와 실행기 양쪽이 그 생성물을 쓴다.** 두 곳에 손으로 적지 않는다.

**(2) 스키마 검증을 통과했다는 이유로 런타임 경계 검사를 생략하지 않는다.** CF291에서 검증기는 "통과"를 반환했고, 그 통과가 곧 사고였다. 플러그인 데이터를 인덱싱·참조·역참조하는 모든 지점에 경계 검사를 둔다. 설계-02 §10의 "알 수 없는 필드는 무시하지 않고 거부"도 같은 원칙의 다른 면이다.

**(3) 플러그인도 단계적 링 배포를 한다.** 카나리 → 좁은 링 → 넓은 링, 각 단계마다 관측 시간(bake-in)을 두고, 지표가 나쁘면 승격을 멈추고 되돌린다. CF291 당시 Rapid Response Content에는 단계적 배포가 **없었고**, 사고 후 도입 항목 1번이 그것이었다.

**(4) 고객이 배포 시점을 통제할 수 있어야 한다.** CrowdStrike는 센서 버전에는 고객 통제(N/N-1/N-2)를 제공했지만 콘텐츠에는 제공하지 않았다. 사고 후 추가한 것이 콘텐츠 배포에 대한 고객 통제다. remedy도 플러그인 갱신을 자동으로 밀어 넣는 모드를 기본값으로 삼지 않는다.

> 되돌리기의 비용도 함께 기억해야 한다. Microsoft가 부트 관리자 폐기(KB5025885)를 2023년 5월에 배포하고도 2026년 8월 현재까지 **기본 강제 단계에 들어가지 않은** 이유는, 폐기를 강제하면 일부 장치가 부팅 불가가 되고 **적용된 폐기는 디스크를 포맷해도 되돌릴 수 없기** 때문이다. 강제력이 강한 안전장치일수록 단계적으로, 되돌릴 수 없음을 알고 배포한다.

### 레지스트리 보호 목록 — 키 자체는 못 지우고 하위는 지운다 (P8)

경로 보호 목록과 **같은 두 겹**이다 (§3). 아래 키들은 통째로 지울 수 없고, 그
하위의 개별 키는 지울 수 있다.

| 보호 키 | 하위에서 무엇을 지우게 되나 |
|---|---|
| `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options` | 하이재킹된 `<이미지 이름>` |
| `HKLM\SYSTEM\CurrentControlSet\Services` | `service.delete` 의 대상 |
| `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon` | (값만 건드린다) |
| `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` · `HKCU\...\Run` | `autorun.remove` 의 값 |
| `HKLM\SOFTWARE\Microsoft\SystemCertificates` | `cert_store.remove` 의 `<지문>` |
| `HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot` | (건드리지 않는다 — 회피 경로다) |
| `HKLM\SOFTWARE\Classes` | 하이재킹된 파일 연결 |

**부모를 통째로 막으면 첫 플러그인부터 동작하지 않는다.** 악성코드는 실제로
이 아래에 자기 항목을 만들고, 그것을 지우는 것이 치료다. 반대로 부모를 열어
두면 IFEO 를 통째로 지우는 계획 하나가 그 기계의 디버깅 구성을 날린다.

### G6 의 상한은 대상의 모양마다 다르다

G6 은 두 가지를 본다 — **보호 경로 불가침**과 **읽기 상한(`scan_roots`) 밖은 지울 수 없다**. 후자를 모든 대상에 똑같이 적용하면 **파일 시스템 밖의 대상이 전부 막힌다.** 레지스트리 값(`HKLM\...`)도 예약 작업 등록 경로(`\Microsoft\Windows\...`)도 `scan_roots` 라는 경로 목록에 담기지 않기 때문이다.

실제로 그랬다. P7 게이트를 올리는 순간 **청정 코퍼스에서 `persistence.disable` 200여 건이 전부 G6 위반**으로 나왔다. P6 까지는 계획될 수 있는 Op 이 `file.quarantine_only` 하나뿐이라 이 결함이 드러날 자리가 없었다.

설계는 처음부터 옳게 적혀 있었다 — 설계-02 §4 는 `scan_roots` 를 두고 *"프로세스·서비스 열거나 레지스트리 읽기처럼 경로 개념이 없는 대상에는 적용되지 않는다"* 고 말한다. **코드가 문서를 따라가지 못한 것이고, 게이트를 올리기 전에는 그 차이를 아무도 잴 수 없었다.**

| 대상의 모양 | 읽기 상한은 무엇인가 |
|---|---|
| 절대 경로 (`C:\...` · `\\서버\공유` · `/...`) | `scan_roots` |
| 레지스트리 값 (`HKLM\...` 등 아는 하이브) | **선언된 `subjects`** — 수집기는 선언되지 않은 subject 를 열거하지 않는다 |
| 예약 작업 등록 경로 (역슬래시 **하나**로 시작) | 같음 |
| 그 밖의 모양 | **거부.** 상한을 대조할 수 없는 대상은 지우지 않는다 |

마지막 줄이 중요하다. 규칙이 "경로가 아니면 통과" 가 되면 `scan_roots` 를 우회하는 길이 **모양 하나 바꾸는 것**으로 열린다. 그래서 아는 모양만 통과시킨다.

### 안전만 재면 제품이 느려지는 것을 못 본다

G1~G9는 전부 **"안전한가"**를 잰다. 제품의 존재 이유인 **"빠른가"**를 재는 지표가 하나도 없다. 그래서 운영 지표로 **플러그인 자립률**(새 위협 대응 중 코어 수정 없이 완료된 비율)을 함께 추적한다 — 정의와 활용은 설계-01 D10.

자립률은 출시를 막는 게이트가 아니라 **추세 지표**다. 떨어지면 배포를 멈추는 것이 아니라, 미달 사유를 세 범주(관찰 대상 없음 / 파괴 동작 없음 / 로직 표현 한계)로 분류해 **다음에 무엇을 코어에 넣을지**를 정한다.

G9는 파일 코퍼스 전수 스캔이라 매 커밋 CI가 아니라 **릴리스 전 게이트**다.

**G9는 처음에 수동 게이트다.** 분석가가 룰을 정상 파일 코퍼스에 돌리고 **결과를 릴리스 기록에 첨부**한다. 수동이라는 이유로 건너뛰지 않는다. G1(청정 환경 아티팩트)과 축이 다르다 — G1은 "정상 시스템 상태에서 계획이 안 나오는가", G9는 "정상 파일 검체에 룰이 안 걸리는가"이며 서로를 대체하지 않는다.

**측정 대상은 "가용한 최대 정상 파일 코퍼스"이지 특정 저장소가 아니다** (2026-08-25 정정). 처음에는 사내 검체 저장소(내부 문서 설계-05 §6)를 방법으로 적었으나, 닿을 수 없는 저장소만을 경로로 두면 **통과할 수 없는 게이트**가 된다 — 바로 위에서 경계한 것이 그 상황이다. 게이트가 재는 것은 "정상 파일에 오탐 0건"이고 검체 공급원은 수단이다.

그래서 **그 시점에 닿을 수 있는 가장 크고 다양한 정상 파일 집합**을 쓴다. 개발 기계와 테스트 VM의 `Program Files`·`System32`·설치된 소프트웨어 트리만으로도 십수만 개가 나온다. 사내 검체 저장소는 그것을 **키우는 경로 중 하나**이며, 붙으면 코퍼스가 커질 뿐 게이트의 정의가 바뀌지 않는다. `remedy-enrich`(설계-09 P13)가 이 스캔을 자동화한다.

**규모와 다양성을 릴리스 기록에 적는다.** "오탐 0건"만 적으면 열 개를 훑고 통과한 것과 십만 개를 훑고 통과한 것이 같아 보인다.

**훑지 못한 파일은 수와 사유를 함께 적는다 — 못 훑은 것은 미매치가 아니다.** 다만 "못 훑음 0건"을 통과 조건으로 두지는 않는다. 라이브 OS 디렉터리에서는 그것이 **원리적으로 불가능**하기 때문이다 — 실측에서 `System32` 27,614개 중 549개가 접근 거부(SYSTEM 전용 하이브 트랜잭션 로그)이거나 다른 프로세스가 열고 있었다(`catroot2\edb.log`). 오프라인 이미지를 뜨지 않는 한 남는다.

사유를 갈라서 다룬다.

| 못 훑은 사유 | 처리 |
|---|---|
| OS 가 막는다 (접근 거부·사용 중) | 기록하고 넘어간다. 그 파일들은 스캔 시점에 누구도 읽을 수 없다 |
| **우리 설정이 막는다** (크기 상한 등) | **상한을 올려 다시 훑는다.** 이것을 남겨 두면 "안 봤다"를 "안 맞았다"로 흘리는 것이다 |

`cargo xtask yara` 는 두 경우를 모두 실패로 내고 목록을 낸다. 판단은 사람이 하되 **목록을 보지 않고 통과시키지 않는다.**

**골든 클린 이미지 세트**는 최소한 Windows 클라이언트/서버, 주요 리눅스 배포판, 그리고 **오탐 유발 가능성이 높은 정상 소프트웨어가 설치된 이미지**(개발 도구, Node.js 런타임, 원격 관리 도구, 브라우저 확장 다수)를 포함한다. G1은 깨끗한 기본 설치본에서만 통과해서는 의미가 없다 — EvilAI 룰이 `node.exe` + `.js` 조합을 본다는 것은 정상 Node 개발 환경이 바로 오탐 후보라는 뜻이다.

### 사고 발생 시 회수 경로

G1~G8을 통과해도 사고는 가능하다. 사고 시 순서는 **(1) 온라인 폐기 목록으로 해당 플러그인 버전 무효화 → (2) `remedy restore` 를 이용한 복구 안내 배포 → (3) 감사 로그 수집·원인 분석 → (4) 재발 방지 기준을 이 문서의 G 항목으로 추가**다. 격리 컨테이너를 자동 삭제하지 않는 정책(5장)이 (2)의 전제다.

## 미결 사항

- §4 상한 초기값 — 첫 플러그인 실측 후 확정. 상한 간 부등식 검사는 그와 무관하게 먼저 구현
- 2층 신뢰 서명 검증의 오프라인 동작 범위(인증서 체인·실효성 확인) — 플랫폼 API 실증 후 확정.
  **P8 에서 좁혀진 것**: `yara-x` 의 Authenticode 파서가 이미 워크스페이스에 있으나 그
  `verified` 는 체인을 PE 안의 마지막 인증서에서 끊고 그것을 유효한 것으로 친다 —
  **자기서명이 통과한다.** 파싱은 싸고 신뢰 판정은 비싸며, 비싼 쪽이 이 미결의 내용이다
- ~~**`Signature.trusted` 가 `bool` 이라 "확인하지 않았다" 를 표현할 수 없다.**~~ **끝** (P10-B) — `Option<Signature>` 가 그것을 표현한다. `None` 은 "확인하지 않았다", `Some(trusted: false)` 는 "확인했고 서명이 없다" 이고, `remedy-collect/src/signature.rs` 가 그 계약을 주석과 시험으로 못 박았다. 원문: 파싱은 됐지만
  신뢰 여부를 모르는 상태가 실재하는데 스키마가 그것을 참/거짓 중 하나로 강요한다.
  `Option<bool>` 로 바꾸는 것이 이 저장소의 "없다 vs 못 봤다" 원칙과 맞는다 — 같은 원칙이
  `FileRecord.signature` 주석에는 이미 적혀 있고 필드 자체에는 적용돼 있지 않다
- **평가기가 "채워지지 않는 필드" 를 알리지 않는다.** 없는 필드는 조용한 미매치이고
  `issues` 에도 남지 않아, 오타와 미구현이 구분되지 않는다. 이것이 있었으면 예시 EvilAI 룰의
  죽은 `exclude` 가 P4 에 드러났다. 다만 **"없는 값은 비교할 수 없다"는 판정 자체는 옳다**
  (§1 — 오타 난 필드 이름이 조용히 참이 되면 안 된다). 고칠 것은 판정이 아니라 **침묵**이다
- 청정 코퍼스의 환경 목록과 갱신 주기 — 설계-04 §3.3

**해소됨** — 격리 컨테이너 평문 헤더 범위는 §5 "평문 헤더는 세 물음에만 답한다"에서 확정했다(P5 착수 전). 검토하라고 남겨 두었던 "불투명 식별자 + 암호 영역 매핑" 절충은 **채택하지 않았다** — 결정적이면 상관관계가 남고 무작위면 쓸모가 없으며, 애초에 키 없이 위협 이름을 알아야 하는 시나리오가 없기 때문이다.
