# 설계 07 — 플러그인 워크스루 (실물 작성 → 동작 전수 추적)

> 작성일: 2026-08-20 · 목적: 설계를 실물 플러그인으로 검증하고 무너지는 지점을 찾는다
> 선행: [설계-02 SDK 계약](설계-02-SDK-계약.md) · [설계-03 안전장치](설계-03-안전장치.md)

## TL;DR

- **무엇을**: 현실적인 위협 네 가지를 실제 `plugin.yaml` 로 적고, 코어가 그것을 읽어 `collect → evaluate → plan → apply → verify` 를 도는 과정을 한 단계씩 따라갔다.
- **결과**: 시나리오 A는 설계대로 동작한다. **시나리오 B에서 설계가 무너진다.**
- **가장 심각한 결함**: **부분 편집(partial edit)이 설계에 아예 없다.** `Userinit` 값이 `userinit.exe,malware.exe` 로 오염됐을 때, 현재 설계로는 **값 전체를 지우는 것밖에 못 한다 — 그러면 로그온이 되지 않는다.** 실제 치료에서 가장 흔한 작업 하나를 표현할 수 없다.
- **그 외 결함 7건**: 프로세스 트리 종료 불가, 프로세스 보호 목록 부재, 서비스 복구 옵션 무력화 불가, 사용자 작업 손실 경고 없음, ADS 미처리, `verify` 의미 모호, 정상 기본값 복원 경로 없음.
- **판단 포인트**: §7의 수정 8건을 반영하면 SDK 스키마가 한 번 더 넓어진다. 넓히지 않으면 첫 플러그인부터 T3(코어 수정)로 넘어간다.

## 시나리오 A — 예약 작업 + 랜덤 폴더 (설계대로 동작함)

랜덤한 폴더명에 페이로드를 두고 예약 작업으로 기동하며 Run 키로 이중화한 형태. "랜덤하게 변하는 폴더명 삭제" 요구가 여기 해당한다.

```yaml
schema_version: 1
id: evilai-locust
version: 0.1.0
min_core: "1.0.0"
platforms: [windows]
name: { ko: "EvilAI(Locust) 제거", en: "EvilAI (Locust) Removal" }

scan_roots:
  - "%SystemRoot%\\System32\\Tasks"
  - "%LOCALAPPDATA%\\Programs"
subjects: [persistence, file, autorun, process, av_exclusion]

detect:
  - id: task
    subject: persistence
    where:
      all:
        - { field: command, op: matches, value: "(?i)\\\\node\\.exe$" }
        - { field: args,    op: matches, value: "(?i)\\.js(\\s|$)" }
        - { field: win.task.register_path, op: starts_with, value: "\\Microsoft\\Windows\\" }
    capture:
      script_path: "args | first_path"
      payload_dir: "${script_path} | dirname"
    exclude:
      - { field: "file(command).signature.subject", op: equals, value: "Microsoft Corporation" }
      - { field: source, op: contains, value: "\\Microsoft VS Code\\" }

  - id: payload
    subject: file
    from: "${task.payload_dir}"
    where:
      - { yara: "rules/evilai.yar:evilai_locust_js" }

  - id: runkey
    subject: autorun
    where:
      - { field: command, op: contains, value: "${task.payload_dir}" }

verdict:
  require: "task and payload"

remediate:
  remove:
    - { ref: task }
    - { ref: payload }
    - { ref: runkey }
    - { path: "${task.payload_dir}", recursive: true, guard: payload }
  restore:
    - av_exclusions
  verify:
    after_reboot: true
```

> **2026-09-30 표시** — 위 예시의 `exclude` 두 줄(`file(command).signature.subject` · `source contains`)은
> 지금 매니페스트에 없다. 둘 다 발동할 수 없음이 실측으로 드러나 P9 에서 지웠다 — 실기기의 `node.exe` 는
> OpenJS 서명이고, 예약 작업의 `source` 는 정의 파일 경로라 설치 경로가 들어갈 자리가 없다. 값을 고쳐
> 살릴 수 있는 술어도 아니다(위협이 정상 실행 파일을 그대로 쓴다). 지금의 매니페스트와 그 까닭은
> `plugins/evilai-locust/plugin.yaml` 의 주석에 있다.

### 코어의 동작 추적

**collect** — `scan_roots` 두 곳과 `subjects` 다섯 종만 열거한다. `%SystemRoot%\System32\Tasks` 의 작업 XML, `%LOCALAPPDATA%\Programs` 하위 파일 메타데이터·해시, 자동실행 항목, 프로세스 목록, Defender 예외 목록이 `artifacts.json` 에 담긴다. **판단은 하지 않는다.**

**evaluate** — 참조 DAG는 `task → payload`, `task → runkey`. 위상 정렬로 `task` 를 먼저 평가한다. 작업이 2건 매치되면 **증거 그룹 2개**가 생기고, 각 그룹 안에서 자기 `payload_dir` 로만 `payload` 와 `runkey` 를 평가한다. 그룹 #0만 `require` 를 통과하면 치료는 #0의 증거에만 적용된다.

**plan** — 플러그인은 순서를 적지 않았고 코어가 도출한다.

```
  seq 1  process.kill      match={image_path:...node.exe, cmdline_contains:<payload_dir>}
                           max_targets=8 max_retries=3   because=[task#0]
  seq 2  task.disable      \Microsoft\Windows\Locust      because=[task#0]
  seq 3  autorun.remove(disable 단계)                     because=[runkey#0]
  seq 4  backup            q:0001..0004 (작업 XML, 파일, Run 값, 예외 목록)
  seq 5  task.delete       \Microsoft\Windows\Locust
  seq 6  file.delete       <payload_dir>\main.js  sha256=... reversible=true
  seq 7  registry.delete_value  HKCU\...\Run  "Locust"
  seq 8  dir.delete_recursive   <payload_dir>  guard=payload#0
  seq 9  av.restore_exclusions
  seq 10 reboot.verify_request
```

**가드 판정** — `payload_dir` 는 `%LOCALAPPDATA%\Programs\<랜덤>` 이며 `scan_roots` 안이다. 1층 보호 목록과 교차하지 않는다. `guard=payload#0` 이 그 디렉터리 안의 악성 판정 파일을 가리키므로 재귀 삭제가 허용된다. **`payload_dir` 가 capture 해석 오류로 `%LOCALAPPDATA%\Programs` 자체가 되었다면, 그 안에 악성 판정 파일이 없어 seq 8이 계획에 들어가지 않는다.**

**apply** — seq 4 이전에 실패하면 중단(아무것도 파괴 안 됨). seq 5 이후 실패하면 **롤백하지 않고 계속 진행**하고 실패 항목은 재부팅 재시도 큐로 간다.

**판정: 시나리오 A는 설계대로 동작한다.** 랜덤 폴더명, 다중 매치, 재귀 삭제 가드가 모두 의도대로다.

## 시나리오 B — 서비스 + 로그온 하이재킹 + 인증서 (설계가 무너지는 곳)

훨씬 흔한 형태다. 서비스로 상주하고, `Userinit` 을 오염시켜 로그온마다 재실행하며, 악성 루트 인증서를 심고, `hosts` 로 보안 업데이트를 차단한다.

**작성자가 적고 싶은 것:**

```yaml
detect:
  - id: svc
    subject: service
    where:
      all:
        - { field: image_path, op: contains, value: "\\ProgramData\\" }
        - { field: image_path, op: matches,  value: "(?i)\\\\[a-z0-9]{8}\\.exe$" }
    capture: { svc_bin: "image_path | first_path" }

  - id: userinit-hijack
    subject: registry_value
    where:
      all:
        - { field: key,  op: equals,   value: "HKLM\\SOFTWARE\\Microsoft\\Windows NT\\CurrentVersion\\Winlogon" }
        - { field: name, op: equals,   value: "Userinit" }
        - { field: data, op: contains, value: "${svc.svc_bin}" }

  - id: bad-root
    subject: cert_store
    where:
      - { field: thumbprint, op: equals, value: "a1b2c3..." }

  - id: blocked-update
    subject: hosts_entry
    where:
      - { field: hostnames, op: contains, value: "update.av-vendor.example" }

verdict:
  require: "svc and userinit-hijack"

remediate:
  remove:
    - { ref: svc }
    - { ref: bad-root }
    - { ref: blocked-update }
  edit:                                    # <-- 이 절이 설계에 없다
    - { ref: userinit-hijack, op: strip, value: "${svc.svc_bin}" }
```

### 여기서 무너지는 것

**결함 1 (치명) — `remediate.edit` 절이 존재하지 않는다.**

현재 설계의 `remediate` 에는 `remove` 와 `restore` 뿐이다. `Userinit` 값은 `C:\Windows\system32\userinit.exe,C:\ProgramData\a8f3d2b1.exe` 이므로, **악성 부분만 떼어내야 한다.** 현재 표현 수단은 `registry.delete_value` 하나뿐인데 그것을 쓰면 값 전체가 사라지고 **사용자가 로그온할 수 없게 된다.**

이 패턴은 예외가 아니라 주류다.

| 대상 | 오염 방식 | 필요한 동작 |
|---|---|---|
| `Winlogon\Userinit` | `,악성.exe` 추가 | 해당 토큰만 제거 |
| `Winlogon\Shell` | `explorer.exe,악성.exe` | 동상 |
| `AppInit_DLLs` | DLL 경로 추가 | 해당 항목만 제거 |
| 서비스 `ImagePath` | 정상 바이너리 + 악성 인자 | 인자만 제거 |
| 환경변수 `PATH` | 악성 디렉터리 추가 | 해당 경로만 제거 |
| `text_config` 라인 | 라인 추가 | 라인 제거 (이것만 Op 존재) |

**결함 2 — 서비스를 멈출 수 없고 복구 옵션을 끌 수 없다.**

Op 목록에 `service.disable` / `service.delete` 는 있으나 **`service.stop` 이 없다.** 그리고 악성 서비스는 대개 실패 시 자동 재시작(recovery action)이 설정돼 있어, 프로세스를 종료하면 **SCM이 즉시 되살린다.** 종료 재시도 3회는 SCM과의 경쟁일 뿐 이기지 못한다.

올바른 순서는 **복구 옵션 제거 → 서비스 정지 → 비활성화 → 삭제**이며, 앞의 둘을 표현할 수 없다.

**결함 3 — 정상 기본값으로 되돌릴 방법이 없다.**

`Shell` 값이 통째로 악성으로 교체된 경우, 떼어낼 것이 없고 **알려진 정상값(`explorer.exe`)으로 복원**해야 한다. `registry.set_value` 가 Op 표에는 있으나 **플러그인이 임의 값을 쓸 수 있게 하면 그 자체가 공격 도구**가 된다 — 서명된 도구가 임의 레지스트리 값을 쓸 수 있다는 뜻이기 때문이다.

## 시나리오 C — 워치독 쌍 (프로세스 트리)

두 프로세스가 서로를 감시하며 되살린다. "프로세스 종료(트리 구조)" 요구가 여기다.

```
  loader.exe (부모)
    +-- worker.exe   <- loader 가 죽으면 worker 가 재생성
    +-- guard.exe    <- worker 가 죽으면 guard 가 재생성
```

**결함 4 — 트리를 지정할 수 없다.**

`process.kill` 은 술어 매칭만 지원한다. `guard.exe` 가 정상 프로세스와 이름이 겹치면 술어로 잡을 수 없고, **부모-자식 관계로 지정할 방법이 없다.** `process` subject에 `ppid` 는 있지만 "이 프로세스와 그 모든 자손"을 표현하는 문법이 없다.

**결함 5 — 순차 종료가 경쟁에서 진다.**

세 프로세스를 술어로 다 잡았다고 해도, 구현이 순차 종료라면 `loader` 를 죽이는 사이 `guard` 가 되살린다. **정지(suspend) 후 종료**가 표준 기법인데 설계에 없다. 전체를 먼저 정지시키면 재생성 코드가 돌지 못한다.

**결함 6 — 프로세스 보호 목록이 없다.**

1층 보호 목록은 **경로**에만 있다. 악성코드가 `svchost.exe` 로 위장하거나 정상 프로세스에 인젝션한 경우, 룰이 `image_path` 로 매칭하면 **`csrss.exe` · `winlogon.exe` · `smss.exe` 같은 임계 프로세스가 대상이 될 수 있다.** 이들을 종료하면 즉시 블루스크린이다.

경로 보호 목록이 이것을 막지 못하는 이유는, 종료는 파일을 건드리는 동작이 아니기 때문이다.

## 시나리오 D — WMI 영구 구독 (막히는 것을 확인)

```
  __EventFilter + __EventConsumer + __FilterToConsumerBinding  (root\subscription)
```

**설계대로 막힌다.** WMI 저장소는 레지스트리도 파일도 아니므로 T2(선언적 확장)로 도달하지 않고, `subjects` 에 해당 타입이 없어 `plugin lint` 가 거부한다. **작성자는 명확한 오류를 받고 T3(코어 통합)를 요청하게 된다** — 조용히 미탐이 되지 않는다는 점에서 설계 의도대로다.

## 추가로 드러난 것

**결함 7 — 사용자 작업 손실 경고가 없다.**

브라우저 확장을 제거하려면 브라우저를 종료해야 한다. 오피스 문서를 잠근 악성 프로세스도 마찬가지다. 현재 계획 렌더러는 "무엇을 지우는가"는 보여주지만 **"어떤 프로그램이 종료되어 저장하지 않은 작업이 사라지는가"**를 말하지 않는다.

**결함 8 — `verify` 의 의미가 모호하고, 랜덤 이름 앞에서 무력하다.**

설계-03 §8은 `verify` 를 "제거 대상이 여전히 부재한가"로 정의했다. 그런데 시나리오 A의 페이로드는 **랜덤 폴더명**이다. 재감염되면 `%LOCALAPPDATA%\Programs\<다른 랜덤>` 에 생기므로, **원래 경로만 확인하면 재발을 놓친다.**

`verify` 는 원래 Action 대상 확인이 아니라 **탐지를 다시 돌려 판정이 재현되는가**를 봐야 한다. 이것은 `resume`(승인된 계획을 이어 실행, 재스캔 금지)과 **정반대 성격**이며, 두 명령을 분리한 것이 옳았음이 여기서 확인된다.

**결함 9 — ADS 를 다루지 못한다.**

`file.txt:payload.exe` 처럼 대체 데이터 스트림에 숨은 경우, 호스트 파일은 정상이므로 지울 수 없고 스트림만 제거해야 한다. `file` subject에 스트림 개념이 없다.

**재발 방지의 경계** — 요구사항에 "재발 방지"가 있다. 설계상 재발 방지는 **악성이 바꿔 놓은 것을 원복하는 것까지**다(예외 목록, hosts, 프록시, 인증서). **새로운 방어를 추가하는 것은 아니다** — 방화벽 규칙 추가, 정책 강화 등은 설계-00 §3의 비목표다. 이 경계를 가이드에 명시해야 작성자가 룰로 방어 정책을 심으려 하지 않는다.

## 발견 결함과 수정

| # | 결함 | 심각도 | 수정 |
|---|---|---|---|
| 1 | 부분 편집 부재 — `Userinit` 통째 삭제 시 로그온 불가 | **치명** | `remediate.edit` 절 + `registry.strip_value` · `env.strip_path` |
| 2 | `service.stop` · 복구 옵션 무력화 없음 | **높음** | `service.stop` · `service.clear_recovery` Op, 표준 순서에 편입 |
| 3 | 정상 기본값 복원 경로 없음 | 높음 | `registry.restore_default` — **코어가 아는 OS 기본값 카탈로그**에서만 복원 |
| 4 | 프로세스 트리 지정 불가 | 높음 | `process.kill` 에 `include_descendants` |
| 5 | 순차 종료가 워치독에 진다 | 높음 | **정지 후 종료**를 실행 규칙으로 고정 |
| 6 | 프로세스 보호 목록 없음 | **치명** | 1층 보호 목록에 **종료 금지 프로세스** 추가 |
| 7 | 사용자 작업 손실 경고 없음 | 중간 | Action에 `user_impact`, 계획 렌더러가 경고 |
| 8 | `verify` 가 재판정을 하지 않음 | 중간 | `verify` = 재수집 + 재평가. `resume` 과 명시적 구분 |
| 9 | ADS 미처리 | 낮음 | `file.streams[]`, `file.delete_stream` |

**1번과 6번이 치명인 이유가 같다 — 둘 다 "치료하려다 시스템을 못 쓰게 만드는" 경로다.** 설계-00 §1의 1순위(사용자 시스템 무결성)를 정면으로 위반한다.

### 수정 후 시나리오 B

```yaml
remediate:
  remove:
    - { ref: svc }
    - { ref: bad-root }
    - { ref: blocked-update }
  edit:
    - { ref: userinit-hijack, op: strip, value: "${svc.svc_bin}" }
  restore:
    - { ref: shell-hijack, to: default }     # 코어의 OS 기본값 카탈로그
```

계획기가 도출하는 순서:

```
  seq 1  service.clear_recovery  <svc>            # SCM 이 되살리지 못하게 먼저
  seq 2  service.stop            <svc>
  seq 3  process.kill            match={image_path:<svc_bin>} include_descendants=true
                                 (정지 -> 종료 -> 확인)
  seq 4  service.disable         <svc>
  seq 5  backup                  서비스 설정 / Userinit 원본 전체 / 인증서 DER /
                                 hosts 라인 / Shell 원본
  seq 6  registry.strip_value    Winlogon\Userinit  remove="C:\ProgramData\a8f3d2b1.exe"
  seq 7  registry.restore_default Winlogon\Shell -> "explorer.exe"
  seq 8  service.delete          <svc>
  seq 9  file.delete             <svc_bin>
  seq 10 cert_store.remove       thumbprint=a1b2c3...        # 명시적 승인 필요
  seq 11 hosts.restore_line      update.av-vendor.example
  seq 12 reboot.verify_request
```

**부분 편집의 백업은 값 전체다.** 복원하면 오염된 원본이 그대로 돌아온다 — 그것이 옳은 동작이며, 사용자가 오탐이라 판단했다는 뜻이기 때문이다. 이 성질을 가이드에 명시한다.

## 이 워크스루가 확인해 준 것

무너진 곳만큼 **버틴 곳도 기록해 둔다.**

- 증거 그룹 의미론이 다중 매치에서 정확히 동작한다 (시나리오 A)
- 재귀 삭제 `guard` 가 capture 해석 오류를 실제로 막는다
- 예외 목록 원복이 파일 제거 **뒤에** 오는 표준 순서가 옳다 — 먼저 원복하면 Defender가 우리보다 먼저 파일을 가져가 격리 경로가 갈린다
- 파괴 중 실패 시 롤백하지 않는 정책이 부분 치료를 만들되 위협 재무장을 막는다
- T3 경계가 조용한 미탐이 아니라 **명확한 린트 오류**로 나타난다 (시나리오 D)
- `verify` 와 `resume` 을 분리한 것이 옳았다 (결함 8이 그 근거)
