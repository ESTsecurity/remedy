# 설계 01 — 아키텍처 결정 (ADR)

> 작성일: 2026-08-20 · 대상: `remedy` 코어
> 후속: [설계-02-SDK-계약.md](설계-02-SDK-계약.md) · [설계-03-안전장치.md](설계-03-안전장치.md) · [설계-04-저장소-부트스트랩.md](설계-04-저장소-부트스트랩.md)

## TL;DR

- **무엇을**: 템플릿+플러그인 전용백신의 구현 언어·YARA 엔진·플러그인 실행 모델·배포 형태를 확정한다. 이 문서의 D1~D3만 승인되면 코어 스캐폴딩에 착수할 수 있다.
- **핵심 결정**: 구현 언어는 **Rust**, YARA는 **yara-x 크레이트를 네이티브로 임베드**, 배포는 **OS별 네이티브 CI 러너에서 빌드한 정적 단일 바이너리**, 플러그인은 **선언적 룰 전용(스크립트 런타임은 v1 제외)**.
- **사전조사와 달라진 점**: 사전조사는 Go를 1순위로 권했다. **이 문서는 그 권고를 뒤집는다.** 근거는 아래 실측 6건과 "Go에서 YARA를 쓰려면 어차피 CGO와 Rust 툴체인이 둘 다 필요하다"는 사실이다.
- **상태**: D1(Rust 채택) **2026-08-20 승인 완료.** 대안 경로 B는 기록으로만 남긴다.
- **남은 판단 포인트**: **Windows 7/8.1 지원 여부**(설계-00 §4). 기술이 아니라 사업 결정이며, 지원한다면 부트스트랩 1주차에 tier 3 빌드 실증이 선행되어야 한다.

## D1. 구현 언어 = Rust

### 실측 근거 (이 저장소 개발 환경에서 직접 수행)

| # | 시험 | 결과 |
|---|---|---|
| 1 | Rust 1.96.0 + `x86_64-pc-windows-{msvc,gnu}`, `x86_64-unknown-linux-musl` 타깃 | 설치 완료 |
| 2 | Windows 호스트 → Linux musl 정적 ELF 크로스 빌드 (hello world, 동봉 `rust-lld`만 사용) | **성공** (ELF, 565 KB, 외부 툴체인 0) |
| 3 | `yara-x` 1.19.0 호스트(Windows msvc) 빌드 + 룰 컴파일·스캔 실행 | **성공** (`matched rules = 1`) |
| 4 | `yara-x` → `i686-pc-windows-msvc` (**32비트 Windows**) 빌드 후 **실행** | **성공** (18.9 MB, `matched rules = 1`) |
| 5 | `yara-x` + `RUSTFLAGS=-C target-feature=+crt-static` → 임포트 DLL 확인 | **`KERNEL32`, `ntdll`, `bcryptprimitives`만.** `VCRUNTIME140.dll`·`api-ms-win-crt-*` 전부 소거 |
| 6 | `yara-x` → `x86_64-unknown-linux-musl` 크로스 빌드 | **실패** — `cc-rs: failed to find tool "x86_64-linux-musl-gcc"` |
| 7 | **32비트 Pulley 성능** (P4 검증). 같은 스냅샷(본문 60건·11.7 MB)을 두 바이너리로 `evaluate`. 룰 있을 때와 없을 때의 차이가 YARA 몫이다 | x86_64 **532 MB/s** · i686 **171 MB/s**. YARA 몫만 보면 **3.11배**, 실행 전체로는 1.63배 |

7번은 32비트에서 wasmtime 이 JIT 대신 **Pulley 인터프리터**로 떨어지기 때문이다. 세 배가 넘지만 **쓸 수 있는 수준이다** — 전용백신이 훑는 것은 수십 MB 규모이고, 11.7 MB 를 69ms 에 훑는다. 이 값을 적어 두는 이유는 나중에 "32비트가 느리다" 는 말만 남지 않게 하려는 것이다. 늘어나면 이 숫자와 견주면 된다.

측정 방법을 함께 적는다. `Start-Process` 로 재면 같은 실행에 약 1.02초가 더 붙는다(`ProcessStartInfo` 는 0.03초). **재는 쪽이 재는 대상보다 느리면 남는 것은 도구의 그림자다.**

4번과 5번이 결정적이다. 전용백신은 구형·32비트 Windows에서 돌아야 하고, 감염된 PC에 VC++ 재배포 패키지 설치를 요구할 수 없다. **두 조건이 Rust에서 추가 작업 없이 충족된다.**

6번의 원인은 yara-x가 아니라 그 의존인 wasmtime이다 (`cargo tree -i cc` → `cc → wasmtime 43.0.2 → yara-x`). wasmtime의 빌드 스크립트가 C 파일 하나를 컴파일하는데, **Windows 타깃에서는 이 단계를 건너뛴다** — 4·5번이 성공하고 6번만 실패한 이유가 이것이다. 즉 **주 타깃인 Windows는 C 컴파일러가 전혀 필요 없고, Linux 타깃만 필요하다.**

### Go를 기각한 이유

사전조사는 "Go = CGO 없는 단일 정적 바이너리 + `GOOS`/`GOARCH`"를 근거로 Go를 1순위로 놓았다. 이 전제는 **플랫폼 API에 대해서는 참이고, YARA에 대해서는 거짓이다.**

- **플랫폼 API는 전부 순수 Go로 가능하다** (별도 조사로 확인): 레지스트리·서비스(`x/sys/windows`), 예약 작업(`go-ole` — README에 "shared libraries **instead of cgo**"), Authenticode 검증(`WinVerifyTrustEx` 바인딩 또는 `sassoftware/relic`), 프로세스·커맨드라인(`gopsutil`), `MoveFileEx`, ACL/SDDL 백업·복원, cron·systemd(`coreos/go-systemd`의 `sdjournal`만 CGO), xattr. **CGO를 강제하는 필수 항목은 YARA 외에 없다.**
- **그런데 YARA가 CGO를 강제한다.** 공식 yara-x Go 바인딩은 `import "C"` + `pkg-config yara_x_capi`이며, 공식 CI는 Linux/macOS만 돌고 **Windows CI가 없으며** `LD_LIBRARY_PATH`를 쓴다 — 즉 **동적 링크가 검증된 경로**다. 정적 링크 관련 이슈 3건이 미해결이고, 릴리스 자산의 Windows용 C API는 MSVC ABI(`.lib`)라 mingw 기반 cgo가 그대로 링크할 수 없다.
- **가장 강한 신호**: Velociraptor 팀(Velocidex)은 Go+cgo 크로스컴파일 숙련 팀임에도 yara-x 정적 링크를 **포기하고 런타임 동적 로딩으로 전환**했다. 사유로 "많은 아키텍처에서 지원되지 않거나 빌드가 매우 복잡"과 라이브러리 크기(~25MB)를 명시했다.
- 결국 Go 경로는 **Go 툴체인 + C 툴체인 + Rust 툴체인(yara-x-capi 빌드용)** 세 개를 타깃마다 관리하게 된다. Rust 경로는 하나다.

### 대안 경로 B (팀이 Rust를 감당하지 못할 때)

**Go + 클래식 libyara(`hillu/go-yara`) + CGO 정적 링크.** 문서화된 레시피가 있고 Velociraptor가 실제로 이 방식으로 배포한다. 대가: 타깃마다 libyara 선빌드, `musl-gcc.specs`의 한계로 musl 크로스 아키텍처(arm64 등) 차단, `hillu/go-yara` 저활성(최종 릴리스 2025-07-01).

**경로 B로 갈 조건은 단 하나 — 인력이다.** 기술적 근거로는 Rust가 우세하므로, 이 결정만 사람이 판단하면 된다.

### YARA를 포기하는 제3안 (검토했고 기각)

순수 Go YARA 구현체 `sansecio/yargo`는 실재하고 프로덕션에서 돌지만, **pe·elf·hash·math 모듈이 전무**하고 `#a`/`@a`/`!a`, 수량자(`2 of them`), `for` 루프, 산술·비트 연산, `wide`/`xor`를 지원하지 않는다. 사내 분석가의 기존 YARA 룰 자산과 공개 룰셋을 재사용할 수 없게 되므로 기각한다. 이 자산 재사용이 애초에 YARA를 넣는 이유였다.

## D2. YARA 엔진 = yara-x 크레이트 네이티브

- yara-x는 **1.0.0 GA(2025-06-04)**, 현재 1.19.0. 클래식 YARA도 유지보수 중(4.5.8, 2026-07-28)이므로 어느 쪽도 사멸 위험은 없다.
- Rust에서 직접 쓰면 **FFI가 없다.** 암호 연산이 전부 RustCrypto 순수 Rust이며 **OpenSSL 의존이 없다**. 유일한 C 의존은 `magic-module`이고 **기본 비활성**이다 → **켜지 않는다** (libmagic 동적 링크 + 매직 DB 동봉이 필요해져 단일 바이너리가 깨진다).
- **룰 호환성은 "대부분 그대로"이지 완전 호환이 아니다.** 문서화된 차이: 정규식 이스케이프 엄격화(`{` 강제 이스케이프), `of` 문에서 룰 이름 와일드카드 미지원, `base64` 최소 3자, 음수 배열 인덱스 거부. **기존 사내 룰을 그대로 옮길 수 있다고 가정하지 말고, 이관 시 컴파일 검증 단계를 둔다.**

### 알아 두어야 할 두 가지 특성

**(a) 32비트에서는 인터프리터로 떨어진다.** yara-x는 룰 조건을 WASM으로 컴파일해 내장 wasmtime으로 실행하는데, Cranelift JIT은 x86_64/aarch64/riscv64/s390x만 지원한다. 32비트는 Pulley 인터프리터 백엔드로 동작한다 — **정확하지만 느리다**(실측 4번은 동작만 확인했고 성능은 측정하지 않았다). 전용백신은 대상 경로가 좁아 스캔량이 적으므로 수용 가능하다고 판단하나, 32비트 지원이 성능 요구를 동반한다면 실측이 선행돼야 한다.

**(b) JIT은 실행 가능 메모리 페이지를 요구한다.** W^X가 강제되는 강화 환경에서는 Pulley로 전환해야 한다. 이 스위치를 빌드 플래그로 노출해 둔다.

### 미해결 위험

- **musl 타깃 미검증.** yara-x 공식 릴리스 매트릭스에 musl이 없고, musl 빌드 실패 이슈가 2024-08-29부터 **열린 상태**다. 실측 6번도 실패했다(원인은 C 크로스 컴파일러 부재로 보이며, 진짜 musl 툴체인을 주면 해소될 성격이다). **Linux 배포 형태를 정적 musl로 할지 정적 glibc로 할지는 CI에서 실증한 뒤 결정한다** — D3 참조.
- **yara-x는 파일을 mmap 한다**(`memmap2`). 스캔 중 다른 프로세스가 파일을 잘라내면 SIGBUS가 발생할 수 있다. 감염 호스트의 살아 있는 파일시스템을 스캔하는 도구에서는 실제 위험이므로, **스캔 경로에 시그널 처리 또는 사전 복사 전략이 필요하다.** 상위 문서에 이 위험이 명시돼 있지 않으므로 우리가 처리해야 한다.

## D3. 배포 = OS별 네이티브 CI 러너 + 정적 단일 바이너리

**단일 호스트에서 전 플랫폼을 크로스컴파일하려는 시도를 하지 않는다.**

- `cargo-zigbuild`은 Windows GNU까지는 CI로 검증되지만 **glibc 정적 링크(`+crt-static`)를 지원하지 않고**, MSVC는 CRT/SDK를 공급할 수 없다.
- `cross`는 macOS/MSVC 프리빌트 이미지를 제공하지 않는다.
- **macOS는 Apple의 Xcode/SDK 계약이 비-Apple 하드웨어에서의 SDK 사용을 금지한다** — 법적으로 Apple 하드웨어에서 빌드해야 한다. (macOS는 v1 범위 밖이지만 로드맵에 둔다면 이 제약이 확정 사항이다.)
- yara-x 자신도 OS별 러너 매트릭스로 릴리스한다.

### 타깃 매트릭스 (v1)

| 타깃 | 러너 | 정적화 | 상태 |
|---|---|---|---|
| `x86_64-pc-windows-msvc` | Windows | `+crt-static` | **실측 검증 완료**(5번) |
| `i686-pc-windows-msvc` | Windows | `+crt-static` | 빌드·실행 검증(4번), 정적화 재확인 필요 |
| `x86_64-unknown-linux-*` | Linux | musl 정적 또는 glibc `+crt-static` | **CI에서 실증 후 확정** |
| `aarch64-unknown-linux-*` | Linux | 동상 | 동상 |

Windows 타깃은 C 컴파일러가 필요 없다. Linux 타깃만 러너에 C 툴체인이 필요하다.

**Linux 정적화 방식은 지금 결정하지 않는다.** musl 정적(Rust 기본 동작)과 glibc `+crt-static`(yara-x 상위가 실제로 쓰는 방식) 중 어느 쪽이 wasmtime과 함께 깨끗하게 링크되는지는 실증 문제이며, 부트스트랩 첫 주에 CI에서 판정한다(설계-04). 미리 고르면 근거 없는 결정이 된다.

## D4. 룰 ↔ 스크립트 경계

### 경계선: **스크립트는 읽고, 룰은 쓴다**

- **치료(remediate)는 100% 선언적 룰.** 스크립트가 파괴 동작을 할 수 없다.
- **스크립트는 탐지(detect)에서만**, 부작용 없는 순수 판정·추출 함수로만 허용한다.

근거는 설계-03 §1의 불변식 P(계획 완전 결정)다. 스크립트가 파괴 동작을 할 수 있으면 실행 전에 계획을 알 수 없고, 드라이런의 정확성·삭제 상한의 사전 차단·감사 로그의 완전성·testbed의 계획 비교 회귀 검증이 **한꺼번에** 무너진다. 이 한 줄이 안전 설계 전체의 지지대다.

### v1에서는 스크립트 런타임을 구현하지 않는다

첫 플러그인(EvilAI)은 선언적 룰만으로 표현된다(설계-02 §4). 실제 필요가 없는 상태에서 런타임을 고르면 쓰지 않는 기능을 만드는 것이고, 사전조사의 조언("이 API가 없어서 불편하다를 기록해 API 명세로 삼으라")과도 어긋난다. **스키마에 자리만 예약하고 비워 둔다.**

### 나중에 고를 때의 판정 기준 (미리 고정)

1. **기본값이 안전한가** — 아무 설정 없이 시작했을 때 파일·네트워크·프로세스 접근이 이미 차단돼 있는가
2. **상한이 결정적인가** — 벽시계 타임아웃이 아니라 **실행 스텝/연료 카운터**여야 한다. 벽시계로 하면 같은 입력이 CI 머신 속도에 따라 다른 결과를 내고, 설계-03 G3(계획 비교 회귀 검증)이 성립하지 않는다
3. **C 의존이 없는가**
4. **서명 대상이 사람이 리뷰할 수 있는 형태인가**

현재 유력 후보는 **wasmtime**이다. yara-x 의존으로 **이미 트리에 존재**하고(추가 의존 0), 연료 계량이 결정적이며, 게스트가 자기 선형 메모리 밖을 주소지정할 수 없어 **진짜 하드 메모리 상한**을 갖는 유일한 방식이다. 대가는 기준 4 — 플러그인 스크립트가 컴파일된 바이너리가 되어 리뷰가 어려워진다. 채택 시 **소스 동봉 + 재현 가능 빌드**를 패키지 요건으로 강제해 상쇄한다.

## D5. 코어/GUI 경계와 JSON 출력

- **코어는 CLI다.** 하위 명령과 단계별 JSON 아티팩트가 제품의 실제 계약이다(설계-02 §8).
- **GUI는 v1 범위 밖이며, 이후에도 `remedy-core` 를 링크하는 얇은 셸로만 만든다.** 서버 OS에는 GUI가 없고, 기업 대량 배포·자동화는 CLI만 쓴다. GUI를 먼저 만들면 CLI가 GUI의 부산물이 되어 계약이 흐려진다.
- 진행 상황은 NDJSON 이벤트 스트림으로, 최종 결과는 단일 JSON 객체로 낸다. 종료 코드는 설계-02 §8 표를 따르며, **안전 가드에 의한 중단(5)을 실행 실패(3)와 분리**하는 것이 무인 배포에서 후속 조치를 가른다.

### 하위 명령

| 계열 | 명령 | 비고 |
|---|---|---|
| 파이프라인 | `collect` · `evaluate` · `plan` · `apply` | `scan` = collect+evaluate, `run` = 전 단계. **네트워크 없음** |
| 인텔 | `enrich` | 위 파이프라인 **밖**. 사내 실행 기본 (D9). **`submit` 은 제품에서 뺐다** — 설계-09 "제출을 제품 밖으로" |
| 사후 | `restore` · `verify` · `resume` | `resume` 은 재부팅 재시도 큐를 이어 실행 (설계-03 §5) |
| 플러그인 도구 | `plugin lint` · `plugin verify` | 작성자·배포자용. **서명 생성은 여기 없다** — 아래 |
| 운영 | `revocation import` · `revocation verify` | 폐쇄망 오프라인 반입 경로 (설계-03 §6). **`fetch` 는 아래** |
| 운영 | `allowlist import` · `allowlist verify` | 조직 서명 허용 목록 (설계-03 §3 5층). **폐기 목록과 같은 레일, 방향만 반대** |
| 지원 | `support-bundle` | 신고 첨부물 자동 생성 (설계-04 §6) |

`verify` 와 `resume` 을 분리한 것은 의미를 흐리지 않기 위해서다. `verify` 는 **확인**이고 `resume` 은 **실행**이다. 재부팅 후 자동으로 도는 것은 `resume` 이며, 이미 승인된 계획을 이어서 수행할 뿐 새로 스캔하지 않는다.

`plugin lint` 가 별도 명령인 이유는 룰 작성자가 서명 전에 스키마 위반을 잡을 수 있어야 하기 때문이다. 검증이 배포 시점에만 일어나면 작성자는 매번 서명해 봐야 오류를 안다.

**`revocation fetch` 도 CLI 에 없다 (2026-08-26, P10-D).** 설계-03 §6 이 그 이름을 적었으나, HTTP 클라이언트를 배포 바이너리에 링크하는 일이고 **D9 가 치료 경로의 네트워크를 막는다.** 목록을 어떻게 받든 들어오는 문은 `import` 하나이고 그 문이 서명 검증과 역행 금지를 태우므로, 폐기 메커니즘 자체는 `fetch` 없이 완결이다. 어디에 둘지는 코어 자기무결성과 함께 판단한다.

**서명 생성(`sign`)은 CLI 에 두지 않는다 — `cargo xtask sign` 이다.** 이 표는 원래 `plugin sign` 을 적고 있었으나, 미결 5 를 닫으며 실측한 결과 서명기가 `rpassword`(암구호 입력)·`scrypt`·`salsa20` 을 끌어온다. **개인키를 다루는 코드가 배포 바이너리에 링크될 이유가 없고**, 고객 기계에서 도는 바이너리가 서명할 수 있으면 그 능력이 곧 공격 표면이다 — D7 과 같은 판단이다. 검증(`plugin verify`)은 반대로 제품이 해야 하며, 검증기는 의존성이 0 개다.

**룰을 AI가 작성한다는 전제에서 `plugin lint` 의 위상이 올라간다.** AI의 실제 학습 경로는 산문 독해가 아니라 `작성 → lint → 오류 → 수정` 루프이므로, **오류 메시지가 가이드의 절반**이다. 진단마다 유효값 전수 또는 근접 후보와 문서 앵커를 함께 낸다. 검사 목록과 과광범위 경고 규칙은 [설계-06 §7](설계-06-플러그인-가이드.md).

### 계획을 사람에게 보여 주는 것은 별개 기능이다

승인 게이트가 성립하려면 사용자가 계획을 **이해할 수 있어야** 한다. `plan.json` 을 그대로 띄우는 것은 승인이 아니라 승인의 형식만 갖춘 것이다. 코어에 **계획 렌더러**를 둔다 — 무엇을(경로·항목 이름), 왜(증거 요약), 되돌릴 수 있는지(reversible 표시), 재부팅이 필요한지를 사람의 문장으로 요약한다.

**부작용을 먼저 말한다.** 브라우저 확장을 제거하려면 브라우저를 종료해야 하고, 그러면 저장하지 않은 작업이 사라진다. 삭제 목록만 보여주고 이것을 말하지 않으면 승인은 정보에 근거한 것이 아니다. Action의 `user_impact`(설계-02 §8)를 **목록보다 앞에** 표시한다.

렌더러는 `plan.json` 만 입력으로 받는 순수 변환이며, 렌더링된 문장과 실제 실행 사이에 불일치가 생길 수 없도록 **같은 Action 배열에서 나온다.**

## D6. 플러그인 신뢰 — 오프라인에서 실제로 강제되는 것

조사한 모든 선례(TUF, UEFI dbx, Android Verified Boot, Windows 드라이버 차단 목록, Java blacklist, Firefox 애드온 차단, Chrome CRLSet)가 예외 없이 같은 구조였다.

> **판정은 로컬에서, 네트워크가 필요한 것은 규칙의 배포뿐이다.**

그리고 온라인 조회 단독은 신뢰할 수 없다 — 네트워크를 막을 수 있는 공격자는 폐기 조회도 막을 수 있고, soft-fail은 그래서 무력하다. Let's Encrypt가 6일 인증서에 OCSP/CRL URL을 아예 넣지 않는 것이 이 결론의 극단이다.

**따라서 remedy의 신뢰 모델은 2층이며, 오프라인에서 실제로 강제되는 것은 (b)다.**

**(a) 온라인 폐기 목록** — 서명된 목록. 최신·세밀한 통제. 네트워크가 있을 때만 갱신된다.
**(b) 코어 바이너리에 컴파일된 `min_plugin_version` + 단조 증가 강제** — 네트워크가 없어도, **시계가 조작돼도** 유효하다.

(b)를 만료 시각이 아니라 **버전 정수**로 두는 것이 중요하다. 악성코드는 시스템 시계를 흔히 조작하므로 만료 기반 규칙은 무장 해제될 수 있지만, 컴파일된 정수 비교는 그렇지 않다. Android Verified Boot가 정확히 이 형태다(`rollback_index >= stored_rollback_index`, 변조 감지 가능 저장소에 기록).

여기에 **역행 금지**를 더한다: 한 번 본 것보다 낮은 버전의 플러그인·폐기 목록은 거부한다. 이것이 없으면 공격자가 오래된 결함 버전을 다시 제시할 수 있다.

만료·오프라인 정책의 모드별 분기와 상세는 설계-03 §6에서 다룬다.

## D7. 코어 자체의 신뢰와 갱신

플러그인 신뢰만 설계하고 코어를 빼놓으면 앞뒤가 맞지 않는다. 임의의 파일을 지우는 서명 안 된 바이너리를 고객이 실행할 이유가 없다.

- **코어 바이너리에 코드서명**한다. 고객이 실행 전에 출처를 확인할 수 있어야 하고, 서명이 없으면 다른 보안 제품이 우리를 차단한다
- **자기무결성 검사**: 시작 시 자기 서명을 검증하고, 실패하면 파괴 동작을 수행하지 않는다(스캔·보고까지만). 변조된 remedy가 파괴 도구로 쓰이는 경로를 막는다

  > **2026-08-26 (P10-E) 구현.** `remedy-core::integrity` 가 `current_exe()` 를 P10-B 의 Authenticode 검증에 태우고, CLI 가 `apply`·`run`·`resume` 앞에서 그 답을 본다. **`restore` 는 막지 않는다** — 복원은 파괴가 아니라 그 반대이고, 변조된 바이너리로 복구하는 위험보다 복구할 길이 끊기는 위험이 크다(설계-03 §11). 실측: 자기서명 사본과 서명 후 한 바이트를 고친 사본 모두 `apply` 에서 exit 5, `scan`·`restore` 는 그대로 돈다.
- **자기 격리소·저널을 자기 삭제 대상으로 삼지 않는다.** 코어의 작업 디렉터리는 1층 보호 목록에 준해 취급한다 — **2026-08-26 (P10-E) 구현.** `%ProgramData%
emedy` 와 `/var/lib/remedy` 가 보호 목록에 들어갔다. `--state-dir` 로 다른 곳을 지정하면 그 경로는 목록에 없다; 그것은 사용자가 의식적으로 고른 자리다

### 갱신은 전체 재배포다

**자동 업데이트 기능을 넣지 않는다.** 새 버전이 필요하면 새 바이너리를 받아 실행한다. KVRT가 같은 방식이고(DB 갱신 경로 없이 전체 재다운로드), Microsoft Safety Scanner도 그렇다.

이유가 두 가지다. 첫째, 단발 실행 도구에 자동 갱신 채널을 만들면 **그 채널 자체가 공격 표면**이 되고, 그것을 지키기 위해 또 다른 신뢰 체계가 필요해진다. 둘째, `min_plugin_version` 이 코어에 컴파일되어 있으므로(D6) **코어 재배포가 곧 폐기 메커니즘의 집행**이다 — 갱신 경로를 단순하게 유지하는 것이 안전장치의 신뢰성을 높인다.

대가는 사용자가 매번 최신본을 받아야 한다는 것이고, 이는 이 제품군의 통상적 사용 방식과 일치한다.

## D8. 기업 배포 통합

전용백신은 한 대가 아니라 수천 대에 뿌려진다. **전용 관리 서버를 만들지 않고, 파일 산출물과 종료 코드만으로 통합한다.**

| 필요 | 방식 |
|---|---|
| 실행 | 원격 실행 도구(기존 배포 인프라)가 CLI를 호출 |
| 설정 배포 | 설정 파일 1개 + 명령행 인자. 레지스트리·GPO 의존을 만들지 않는다 |
| 결과 수집 | `--output <경로>` 로 `result.json` 을 공유 폴더·로컬 경로에 기록. 전송은 배포 인프라가 담당 |
| 판정 | **종료 코드**로 분기 (설계-02 §8). 특히 5(가드 중단)는 3(부분 실패)과 다른 후속 조치를 요구한다 |
| 동시 실행 방지 | 전역 뮤텍스, 한 호스트에 하나 (설계-00 §5) |

**치료 경로에는 네트워크가 없다.** `collect` · `evaluate` · `plan` · `apply` 어느 단계도 밖으로 나가지 않는다. 결과를 서버로 보내는 주체는 고객의 배포 인프라이며, remedy는 파일을 남길 뿐이다. 이 경계가 데이터 취급 정책(설계-00 §7)을 단순하게 유지한다.

> 위협 인텔 조회와 인텔 제출은 D9에서 다루며, **둘 다 위 네 단계 밖에 있다.**

## D9. 위협 인텔 조회와 인텔 제출

> 요구사항: (1) C2 지표를 사내 악성코드 자동분석시스템에 조회, (2) 평판·감염 소스 등 데이터 수집.

### 이것은 하나가 아니라 둘이고, 방향이 반대다

| | **조회 (enrich)** | **제출 (submit)** |
|---|---|---|
| 방향 | 밖 → 안 | 안 → 밖 |
| 목적 | 판정 보강, 분석 지원 | 위협 인텔 축적, 캠페인 추적 |
| 나가는 것 | 해시·도메인·IP 같은 **지표** | 감염 소스, 아티팩트, 경우에 따라 검체 |
| 위험 | 응답 조작 → 오탐/미탐 유도, 조회 자체가 정보 노출 | **개인정보·기업 기밀 유출** |
| 동의 | 조직 정책 | **명시적·기능별 동의 필수** |

**하나의 "데이터 연동" 기능으로 묶으면 안 된다.** 위험도 동의 요건도 다르고, 폐쇄망에서의 가능 여부도 다르다.

### 결정 1 — 사내 시스템 조회는 고객 PC에서 하지 않는다

사내 악성코드 자동분석시스템은 **사내망에 있다.** 고객 PC가 직접 조회하려면 그 시스템을 외부에 노출해야 하는데, 그것은 이 요구사항이 감당할 만한 대가가 아니다.

따라서 **`enrich` 를 별도 단계로 두고, 사내에서 실행하는 것을 기본으로 한다.**

```
  [고객 PC]                          [사내]
  collect  -> artifacts.json  ---->  enrich   -> artifacts.json (+ 조회 주석)
                                     evaluate -> scan.json
                                     (분석가 판단, 플러그인 제작)
  <------------------------------    치료 배포
```

- `enrich` 는 `artifacts.json` 을 입력으로 받아 **같은 형식의 artifacts** 를 낸다. 멱등하고, 생략 가능하고, 여러 번 돌려도 된다
- 고객 PC에서 도는 바이너리 경로에는 여전히 **네트워크 코드가 없다**
- 기업 무인 배포에서 조회가 필요하면 **고객사 관리 서버가 프록시** 역할을 하며, 이는 옵트인이다

### 결정 2 — 조회 결과는 아티팩트에 기록한다 (결정성 보존)

가장 큰 위험은 기능이 아니라 **결정성 붕괴**다. 평판 조회가 `evaluate` 안에서 일어나면 같은 입력이 날마다 다른 결과를 내고, 그러면 무너지는 것이 이것들이다.

- G1(청정 코퍼스 무해성) — 어제 통과한 코퍼스가 오늘 실패
- G3(계획 비교) — 계획이 재현되지 않음
- 설계-03 §1의 "스냅샷에서 0건이면 실제로도 0건" 건전성 논증

해소는 **조회를 `collect`/`enrich` 단계에 두고 결과를 아티팩트에 박는 것**이다. `evaluate` 는 여전히 순수 함수이고, 코퍼스는 조회 결과를 포함한 스냅샷이므로 재현된다. 조회가 없었으면 "정보 없음"으로 기록되고 판정은 그대로 성립한다.

**수집과 평가를 나눈 것(설계-03 §1)이 여기서 다시 배당을 낸다.** 나누지 않았다면 이 요구사항은 결정성과 정면 충돌했을 것이다.

### 결정 3 — 조회는 삭제를 늘릴 수 없고 줄일 수만 있다

조회 결과가 파괴 대상을 **추가**하는 것을 금지한다. 허용되는 방향은 하나뿐이다 — 무해 판정으로 **삭제를 취소**하는 것(설계-03 §3의 화이트리스트 5층).

> **실측 후 정정(2026-08-20).** 조회 결과의 가장 낮은 등급도 "정상" 을 뜻하지 않는다. 점수가 낮은 이유에는 회피·패킹·부분 실패가 포함되므로, **점수를 제외 근거로 쓰면 회피에 성공한 악성코드가 자동 면제된다.** 줄이는 쪽의 근거를 점수가 아니라 **명시적 화이트리스트 태그**로 좁힌다. 연동의 세부는 내부 문서 설계-05 §3.

근거는 비대칭이다. 감염 호스트에서는 DNS·프록시 하이재킹이 가능하다고 이미 가정했다(설계-00 §2 T1). 그 환경에서 조회 응답을 신뢰해 파괴를 늘리면, **공격자가 응답을 조작해 정상 파일을 지우게 만들 수 있다.** 반대로 응답 조작으로 삭제가 취소되면 결과는 "치료 안 함"이고, 그것은 이미 도구를 실행하지 않은 것과 같은 상태다. 설계-00 §1의 우선순위 — 못 지우는 것보다 잘못 지우는 것이 나쁘다 — 를 그대로 적용한 것이다.

### 결정 4 — 제출은 전송이 아니라 파일 생성이 기본이다

`submit` 은 **제출 꾸러미를 만드는 명령**이지 보내는 명령이 아니다. 실제 전송은 고객사의 배포·지원 인프라나 분석가가 한다.

- 기본 **비활성**. 켜야 만들어진다
- 만들기 전에 **무엇이 들어가는지 보여준다**(`--preview`). 사람이 보지 않고 나가는 데이터가 없어야 한다
- 폐쇄망에서는 파일을 옮기는 것이 유일한 경로이므로, 파일 생성이 기본인 것이 제약이 아니라 정상 동작이다
- 직접 전송(`--upload`)은 옵트인이며, 그 경우에도 **치료 경로와 분리된 별도 실행**이다

치료 도구가 스스로 데이터를 본사로 보내면 그 자체가 다른 보안 제품의 탐지 대상이 되고 고객 신뢰를 잃는다. 기능을 포기하는 것이 아니라 **전송 주체를 옮기는 것**이다.

### 크레이트 경계로 강제한다

의존 금지 목록에 세 줄이 추가된다(설계-04 §1).

- `remedy-detect ↛ remedy-enrich` — 판정 코드는 조회를 호출할 수 없다
- `remedy-apply ↛ remedy-enrich`

마지막 줄이 핵심이다. 파일을 지우는 코드와 데이터를 내보내는 코드가 같은 바이너리 경로에 있으면, 사고 하나가 두 종류의 피해를 동시에 만든다.

## D10. 확장 계층과 자립률 — "룰만 쓰면 되는가"에 대한 답

### 현재 설계로는 "무조건 룰만"이 되지 않는다

제품의 존재 이유는 **속도**다. 위협마다 개발자가 붙어 코어를 고쳐야 한다면 사전조사가 경고한 "유형 B: 개별 단품형"으로 돌아가고, 관리 비용이 다시 누적된다. 그런데 현재 명세를 그대로 감사하면 플러그인 작성자가 벽에 부딪히는 지점이 셋이다.

| 막히는 지점 | 예 | 성격 |
|---|---|---|
| **관찰 대상이 없다** | WMI 영구 이벤트 구독, COM 하이재킹, IFEO, AppInit_DLLs, PAM, LD_PRELOAD | **설계 미흡** — 상당수는 열거 능력만 있으면 룰로 표현 가능하다 |
| **파괴 동작이 없다** | 레지스트리 **키** 삭제, 임의 설정 파일의 라인 제거 | **일부 미흡, 일부 의도** — 아래 참조 |
| **수집·제출을 선언할 수 없다** | "이 위협은 이 로그도 함께 받아야 분석된다" | **설계 미흡** — 지금은 표현 수단이 아예 없다 |

세 번째가 특히 공백이다. 요구사항의 "분석시스템 전송, 필요 정보 수집"을 **플러그인이 지금은 한 글자도 말할 수 없다.**

### 확장을 세 계층으로 나눈다

지금까지의 설계는 "플러그인이냐 코어냐"의 이분법이었다. 실제로 필요한 것은 셋이다.

| 계층 | 무엇을 하는가 | 릴리스 필요 | 리드타임 |
|---|---|---|---|
| **T1 — 룰 조합** | 기존 subject와 Op의 조합 | 없음 | 시간 단위 |
| **T2 — 선언적 확장** | 임의 레지스트리 트리·파일 글로브·텍스트 설정 파일을 **선언으로** 관찰·제거 | 없음 | 시간 단위 |
| **T3 — 코어 통합** | 새 OS 메커니즘(WMI 등), 새 파괴 동작 종류 | **필요** | 릴리스 주기 |

**T2가 빈약한 것이 현재 설계의 진짜 결함이다.** IFEO·COM 하이재킹·AppInit_DLLs는 전부 레지스트리이고, PAM·LD_PRELOAD·udev는 전부 텍스트 설정 파일이다. **와일드카드 열거와 텍스트 설정 파일 관찰만 있으면 이들이 T3에서 T2로 내려온다.** 반면 WMI 저장소는 레지스트리도 파일도 아니라 T3로 남는다.

따라서 SDK에 다음을 추가한다(설계-02).

- `registry_value` 의 **와일드카드 경로 열거** (`HKLM\...\IFEO\*\Debugger`)
- `file` 의 **글로브 열거**
- **`text_config` subject** — ini/conf/줄 기반 파일의 라인을 관찰 대상으로
- Op: `registry.delete_key`, `text_config.remove_line`, `file.quarantine_only`

`registry.delete_key` 가 없던 것은 의도가 아니라 누락이다. IFEO 항목은 **값이 아니라 키 단위**로 만들어지므로, 값 삭제만으로는 제거되지 않는다.

### 무엇은 계속 코어에 남는가 (의도된 마찰)

**새로운 *종류*의 파괴 동작은 플러그인이 만들 수 없다.** 이것은 유지한다. 파괴 동작마다 되돌림 등급·필수 백업·위험 등급을 코어가 정하고(설계-03 §2), 그 판단이 리뷰를 거치게 하는 것이 안전 설계의 뼈대다. `registry.delete_key` 를 추가하는 것은 **빠진 것을 채우는 일**이지 이 원칙을 무르는 것이 아니다.

마찬가지로 **삭제 상한·보호 경로·백업 여부는 플러그인이 조정할 수 없다.** 작성자가 끌 수 있는 안전장치는 안전장치가 아니다.

### 수집·제출은 "선언"만 허용하고 "실행"은 허용하지 않는다

플러그인이 분석에 필요한 것을 말할 수 있어야 하지만, 그것이 곧 전송 명령이 되면 안 된다. 둘을 분리한다.

```yaml
collect_extra:        # 분석에 유용한 추가 수집 (파괴 아님, scan_roots 상한 적용)
  - { ref: dropped-payload, content: true }
  - { path: "${malicious-task.script_dir}/config.json", max_size: 1MB }

submit_hint:          # 제출 시 무엇이 유용한지에 대한 제안
  samples: [dropped-payload]
  confidentiality_min: 1
```

**`submit_hint` 는 제안이지 명령이 아니다.** 실제 제출은 여전히 사용자 동의·미리보기·마스킹을 거치며(설계-00 §7), 플러그인이 `confidentiality` 를 낮추는 방향으로는 영향을 줄 수 없다 — `confidentiality_min` 은 하한만 올릴 수 있다.

### 자립률을 측정한다

안전 게이트 G1~G9는 전부 "안전한가"를 잰다. **"빠른가"를 재는 지표가 없었다.** 제품의 존재 이유가 속도인데 그것이 측정되지 않으면, 자립률이 서서히 떨어져도 아무도 모른다.

> **플러그인 자립률** = 새 위협 대응 건수 중 **코어 수정 없이 플러그인만으로 완료된 비율**

이 값이 떨어지면 그 자체가 "코어에 무엇을 추가해야 하는지"의 신호다. 미달 사유를 위 표의 세 범주로 분류해 기록하면, 다음에 무엇을 T2로 내릴지가 데이터로 나온다. 사전조사의 조언("없어서 불편한 API를 기록하라")을 상시 지표로 만든 것이다.

### 스크립트 런타임은 여전히 v1 제외 — 다만 도입 조건을 정한다

요청이 "스크립트나 룰"을 전제했으므로 이 결정을 다시 검토했고, **v1 제외를 유지한다.**

근거는 자립률의 미달 사유가 대개 **로직 표현의 한계가 아니라 열거 능력의 부족**이기 때문이다. IFEO를 못 다루는 것은 조건문이 없어서가 아니라 그 경로를 열거할 수 없어서다. 스크립트를 먼저 넣으면 작성자가 열거 부족을 스크립트로 우회하게 되고, **그 순간 우리가 T2로 내려야 할 대상이 무엇인지 알 수 없게 된다.** 열거 부족이 스크립트 안에 숨어 버린다.

**도입 트리거**: 자립률 미달 사유를 분류했을 때 "로직 표현 한계"가 상위 요인으로 나오면 그때 D4의 판정 기준으로 런타임을 고른다. 그 전에는 근거 없는 선택이다.

## D11. 살아 있는 네트워크 연결은 관찰 대상이 아니다

> 사전조사가 탐지 API로 "네트워크: 연결 목록, hosts 파일, 프록시 설정"을 들었고, 그에 따라 `network_conn` 이 subject 카탈로그 18종에 들어가 있었다. **뺀다.**

### 미룬 것이 아니라 안 하기로 한 것이다

처음에 이것이 남은 이유는 구현 장벽이었다. 연결 목록을 읽으려면 `iphlpapi` 가 필요한데 배포 바이너리 검사(`cargo xtask static`)가 그 임포트를 막는다. 그래서 "임포트 금지와 D9의 뜻이 어긋나는 자리"로 적어 두고 판단을 미뤘다.

**판단해 보니 임포트는 이유의 넷 중 하나일 뿐이었고, 나머지 셋이 더 무겁다.**

### 근거 1 — 계획에 닿지 못한다

Op 카탈로그(설계-03 §2, 당시 28종) 중 연결을 건드리는 것이 없고, 있어서도 안 된다. 소켓을 닫는 것은 치료가 아니다 — 30초 뒤에 다시 연결된다.

그러면 연결을 근거로 세운 판정은 둘 중 하나로 끝난다.

- `pid`·`image_path` 를 타고 **프로세스로 옮겨간다.** 그러면 애초 대상이 `process` 였고, 그것은 이미 수집하고 이미 `process.kill` 이 있다
- 옮겨갈 곳 없이 **Op 없는 발견**으로 남는다

어느 쪽도 `network_conn` 을 필요로 하지 않는다.

### 근거 2 — 선언하는 것만으로 종료 코드 6이 영구 고장난다

이것이 실측으로 확인된 실제 피해이고, 뺀 결정을 급하게 만든 이유다.

`uncollected_subjects` 가 비지 않으면 `Observation::is_complete()` 가 거짓이고, 위협을 찾지 못한 실행은 0이 아니라 **6(관측 불완전)** 으로 끝난다. 즉 플러그인이 `network_conn` 을 선언하는 순간 **깨끗한 PC 가 영원히 6으로 끝나고, 운영자가 할 수 있는 조치가 없다.**

6의 존재 이유는 그 반대였다 — "관리자 권한 없이 돌아 `System32\Tasks` 를 못 읽은 실행"처럼 **다시 돌리면 해결되는** 상태를 0과 가르려고 만들었다(설계-02 §8). 수천 대 무인 배포에서 해결 불가능한 6이 상시로 섞이면 운영자는 6을 정상으로 학습하고, 그러면 6이 잡으라고 만든 신호가 죽는다. **구멍을 감추지 않으려고 넣은 장치가 다른 구멍을 감추는 장치가 되어 있었다.**

논증이 아니라 실측이다. 같은 테스트 VM(갓 복원한 Windows 10)에서 같은 실험용 플러그인을 돌린 두 실행이다.

| 실행 | 선언한 subject | `collect` 종료 코드 |
|---|---|---|
| `verify-p4-20260822-021309` | 18종 (`network_conn` 포함) | **6** — 관측 불완전 |
| `verify-p4-20260822-093205` | 17종 | **0** — 위협 없음 |

감염되지 않은 PC 가 "검사받았고 깨끗하다"고 말할 수 있게 된 것이 이 결정의 즉각적인 효과다.

### 근거 3 — 표본이라, 미탐을 "위협 없음"으로 포장한다

연결표는 5분마다 비커닝하는 임플란트의 **1밀리초 표본**이다. 같은 감염 PC를 두 번 검사하면 답이 다르다. 자고 있는 임플란트는 보이지 않고, **보이지 않는 방식이 성공과 구별되지 않는다.**

설계-00 §1은 "못 지우는 것보다 잘못 지우는 것이 나쁘다"로 미탐을 허용하지만, 이것은 **미탐을 깨끗하다고 보고하는** 미탐이다. 관측 01 D2("없다 vs 못 봤다")가 없애려던 실패가 그것이다. 연결 표본은 구조적으로 "못 봤다"인데 "없다"로 나간다.

### 근거 4 — DLL을 열면 송신 원시함수가 같이 들어온다

`IPHLPAPI.DLL` 의 내보내기 313건을 직접 파싱해 확인했다(Windows 11, 2026-08-22).

| | 내보내기 |
|---|---|
| 우리가 원한 것 | `GetExtendedTcpTable` · `GetExtendedUdpTable` · `GetTcpTable2` … |
| **같은 DLL 에 함께 있는 것** | `IcmpSendEcho` · `IcmpSendEcho2` · `IcmpSendEcho2Ex` · `Icmp6SendEcho2` · `IcmpCreateFile` |

검사는 DLL 이름으로 판정하므로, 이 DLL 을 허용하면 임포트 테이블만 보고는 "표를 읽으려고 넣었다"와 "보낼 수 있게 되었다"를 구분할 수 없다.

### 기각한 대안

**심볼 단위 허용목록.** 임포트 테이블에 함수 이름이 있으니 기술적으로는 가능하다. 기각한 이유는 지금 검사의 값어치가 **제3자가 PE 뷰어로 10초 만에 확인할 수 있다**는 데 있기 때문이다. 폐쇄망·금융·공공에 사고 대응으로 들어가는 도구에서 "이 바이너리는 네트워크 DLL 을 임포트하지 않는다"는 남이 검증할 수 있는 주장이고, 심볼 허용목록은 그것을 "우리 목록을 믿어라"로 바꾼다. `xtask/src/staticlink.rs` 머리말이 이미 경고하고 있다 — *"새 Windows API 를 쓸 때마다 이 검사가 깨지면 사람이 목록을 기계적으로 늘리게 되고, 그러면 검사가 형식이 된다."* 첫 예외가 그 시작이다.

**현상 유지(선언하면 미수집 보고).** 근거 2 때문에 안 된다. 지금 상태는 "아직 안 만들었다"로 읽히는데 실제로는 "안 만들기로 했다"이고, 둘이 같은 통로로 나가고 있었다.

### 대신 무엇을 보는가 — 지속되는 네트워크 설정

전용백신이 실제로 **치료해야 하는** 네트워크 흔적은 전부 설정이다. 설정은 지속되고, 재현되고, 임포트가 필요 없다. 아래는 실기기에서 존재를 확인한 것이다.

| 흔적 | 자리 | 왜 |
|---|---|---|
| 방화벽 규칙 | `…\FirewallPolicy\FirewallRules` (값 812건) | 자기 인바운드 허용, 보안 제품 아웃바운드 차단 |
| 포트 프록시 | `…\Services\PortProxy\v4tov4\tcp` | 없는 것이 정상 → **존재 자체가 신호.** 횡적 이동 터널 |
| Winsock LSP/NSP | `…\WinSock2\Parameters\Protocol_Catalog9` | 트래픽 가로채기 지속점 |
| 정적 DNS | `…\Tcpip\Parameters\Interfaces\{GUID}\NameServer` | DNS 하이재킹(설계-00 T1)의 지속 형태 |

**넷 중 셋은 새 subject 없이 `registry_value` 의 `scan_roots` 선언만으로 지금 된다.** 남는 하나는 방화벽 규칙인데, `av_exclusion`·`proxy_config` 가 일급 subject 인 이유(악성코드가 건드리는 보안 설정이고 **되돌려 놓아야** 한다)가 그대로 적용된다. `firewall_rule` + `firewall.restore_rule` 은 별건으로 남긴다 — 이 결정의 일부가 아니다.

### 그래도 연결 목록이 필요하면

FRST·KVRT 가 연결을 찍는 것은 **분석가가 읽는 로그**지 자동 판정 입력이 아니다. 이 구조에서 그 자리는 `collect → evaluate` 가 아니라 `enrich` / `support-bundle` 이고 D9가 이미 갈라 놓았다. 게다가 **D9 결정 3이 enrich 는 삭제를 줄일 수만 있고 늘릴 수 없다**고 못 박았으므로, 연결 정보를 넣어도 파괴 대상을 만들 수 없다.

### 뺀 자리에 이유를 남긴다

`RETIRED_SUBJECTS` (`remedy-sdk/src/catalog.rs`) 에 id 와 사유를 남기고, `Subject` 의 역직렬화가 그것을 본다. `network_conn` 을 쓴 룰은 "모르는 subject" 가 아니라 **왜 뺐는지와 무엇을 대신 쓸지**를 받는다.

린트가 아니라 역직렬화에 둔 이유는, 그래야 `plugin.yaml` 뿐 아니라 **예전에 만들어진 `artifacts.json` 을 읽을 때도** 같은 설명이 나오기 때문이다.

정의를 뺀 결정은 한 번 내리고 끝나지 않는다. 새 작성자마다 다시 물어진다. 그 물음에 그 자리에서 답하는 것이 목록의 값어치다.

### 이 결정이 남긴 것 — 미수집 통로에 지금 생산자가 없다

`network_conn` 이 `uncollected_subjects` 의 **유일한 실제 생산자**였다. 빼고 나면 `collect_all` 이 선언된 17종을 전부 담으므로, 그 통로로 나갈 subject 가 지금은 없다.

통로는 그대로 둔다. 다음에 수집기 없는 subject 를 정의할 때 필요한 안전망이고, 성질 자체는 `remedy-artifacts/tests/format.rs` 가 직접 시험한다. `remedy-collect` 쪽 시험은 반대 방향으로 바뀌었다 — **subject 를 새로 넣고 `collect_all` 에 수집 줄을 빠뜨리면 깨지는 가드**(`every_declared_subject_gets_collected`).

## D12. 예약 작업은 OS 자신의 관리 경로로 손댄다

> `persistence.disable` · `persistence.delete` 를 구현하려다 걸린 자리다. **수집기는 정의
> 파일을 직접 읽는데(`remedy-collect/src/task.rs`), 쓰기도 같은
> 방식이면 되지 않는가?** 답은 아니오다.

### 읽기와 쓰기가 대칭이 아닌 이유

작업 스케줄러의 권위 있는 상태는 **두 곳에 나뉘어 있다.**

| 어디 | 무엇 | 우리가 다룰 수 있는가 |
|---|---|---|
| `%SystemRoot%\System32\Tasks\<등록 경로>` | 정의 XML | 읽기 ○ · 쓰기 ✗ |
| `HKLM\...\Schedule\TaskCache\{Tree,Tasks,Boot,Logon,...}` | GUID 색인 · 트리거·액션 이진 blob · 보안 디스크립터 · **XML 무결성 해시** | ✗ |

읽는 쪽은 XML 하나로 충분하다 — 룰이 묻는 것(명령·인자·트리거·주체)이 전부
거기 있다. **쓰는 쪽은 그렇지 않다.**

- XML 만 고치면 `TaskCache` 의 해시와 어긋난다. 그때 Windows 는 그 작업을
  "비활성" 이 아니라 **"손상"** 으로 취급한다. 치료 도구가 남긴 결과가
  "꺼졌다" 가 아니라 "깨졌다" 이고, 사용자는 그것을 UI 에서 정리할 수도 없다.
  **아무것도 하지 않은 것보다 나쁘다.**
- `TaskCache` 를 직접 쓰는 것은 문서화되지 않은 이진 형식을 재현하는 일이고,
  그 키는 관리자에게도 온전한 권한이 열려 있지 않다. 형식 하나를 틀리면
  스케줄러 서비스 전체가 흔들린다.

### 기각한 안

**COM (`ITaskService`)** — 정공법이다. 그러나 `windows` 크레이트의 COM 표면은
전부 `unsafe fn` 이고, 이 저장소는 18개 크레이트 전부에 `forbid(unsafe_code)`
를 걸고 있다. 예약 작업 하나 때문에 그것을 여는 것은 값이 맞지 않는다.

**정의 XML 직접 편집** — 위의 이유로 기각.

**P8 로 미루기** — 진지하게 검토했다. 그러나 첫 플러그인 `evilai-locust` 의
주 대상이 예약 작업이다. 이 둘이 없으면 P9 의 플러그인이 아무것도 치료하지
못한다. 미루는 것은 결정을 늦추는 것일 뿐 없애지 않는다.

### 그래서 프로세스를 띄운다 — 그리고 좁힌다

이 도구가 다른 실행 파일을 부르는 **유일한 자리**다. 그만큼 좁힌다.

| 위험 | 어떻게 좁혔나 |
|---|---|
| PATH 하이재킹 | `%SystemRoot%\System32\schtasks.exe` 를 **절대 경로**로 부른다 (WOW64 는 `Sysnative`) |
| 스위치 주입 | 등록 경로에 `/`·따옴표·`%`·제어문자가 있으면 **부르기 전에 거부**한다. `/` 는 schtasks 의 스위치 문자다 |
| 경로 탈출 | `..`·빈 조각·앞뒤 공백/점을 거부한다. 등록 경로는 `Tasks\<id>` 로 풀리므로 `..` 은 임의 파일 접근이다 |
| **IFEO 하이재킹** | `Image File Execution Options\schtasks.exe\Debugger` 가 걸려 있으면 거부한다 |
| 출력 파싱의 지역화 | 출력을 **읽지 않는다.** 판단은 종료 코드로만 |

IFEO 항목이 이 중 가장 중요하다. 이 도구의 위협 모델은 IFEO 를 **T2(선언으로
도달 가능한 지속성)** 로 명시한다(설계-02 §2). 우리가 잡으려는 기법에 우리가
걸려 악성코드를 띄우면, 치료 도구가 곧 실행 수단이 된다. 이 검사는
레지스트리 조회를 주입받는 순수 함수라 **켜졌는지 시험으로 확인된다** —
켤 수 없는 가드는 켜졌는지 알 수 없는 가드다.

### P8 이 이 문을 셋으로 늘렸다

`schtasks.exe` 하나를 위해 만든 문을 P8 이 두 개 더 쓴다. 이유는 매번 같다 —
**OS 가 관리하는 상태를 우리가 직접 쓰면 그 관리자와 어긋난다.**

| 도구 | 무엇에 | 직접 쓰면 무엇이 어긋나나 |
|---|---|---|
| `schtasks.exe` | 예약 작업 | `TaskCache` 의 무결성 해시 — 작업이 "손상" 이 된다 |
| `sc.exe` | 서비스 정지·비활성·삭제·복구 동작 | 돌고 있는 서비스의 SCM 내부 상태. 정지는 레지스트리로 아예 불가능하다 |
| `powershell.exe` | 시스템 복원 지점 | 복원 지점 API 는 COM 이고 `unsafe` 를 요구한다 |

셋 다 같은 좁은 문(`system_tool`)을 지난다. **도구 이름은 코드가 정한다** —
목록이 상수로 박혀 있고, 계획이나 매니페스트에서 온 문자열이 실행 파일 이름이
되는 길은 없다. IFEO 확인·절대 경로·셸 없음·출력 미파싱도 그대로 적용된다.

복원 지점만 인자에 문자열이 들어간다. 그것도 **코어가 만든 `run_id` 를 영숫자로
접어서** 넘긴다 — PowerShell 인자에 임의 문자열을 넣는 순간 그 문이 명령 주입
자리가 된다.

### 남는 한계 — 적어 둔다

- **지정 계정으로 도는 작업은 되돌리지 못할 수 있다.** `schtasks /Create /XML`
  은 저장된 암호를 다시 요구하는 경우가 있고, 우리는 암호를 갖지 않는다.
  실패는 종료 코드로 드러나며 그 사유를 오류 문구에 적는다.
- **복원된 작업은 같은 작업이지 같은 등록이 아니다.** 다시 등록하면
  `TaskCache` 의 GUID 와 보안 디스크립터가 새로 만들어진다. 불변식 R 이
  요구하는 것은 "기록된 자리에 기록된 내용을" 이고, 작업의 정체성은 등록
  경로와 정의이므로 그 요구는 충족된다 — 다만 바이트 단위 동일성은 아니다.

### 대상은 파일 경로가 아니라 등록 경로다

`Action.target` 에 정의 파일 경로를 적으면 두 가지가 함께 깨진다.

1. 정의 파일은 `%SystemRoot%\System32` 아래에 있어 **보호 목록에 걸린다**
   (설계-03 §3). 그러면 이 두 Op 은 언제나 거부된다.
2. 파일을 가리키면 "파일을 고친다" 는 뜻이 되는데, 위에서 본 대로 그것이
   바로 하면 안 되는 일이다.

그래서 대상은 `\Microsoft\Windows\Locust` 같은 **등록 경로**이며, 이는
레지스트리 값의 대상이 `<하이브>\<키>\<값>` 인 것과 같은 성질이다 — 파일
시스템 밖의 완전히 지정된 이름. 복원도 이 모양을 "완전히 지정된 대상" 으로
받아들인다.

## D13. 프로세스 정지는 강등한다 — 그리고 저널에 적는다

> 설계-03 §2 가 `process.kill` 의 실행 규칙을
> `해소 → 전부 정지(suspend) → 전부 종료 → 재평가` 로 고정했는데,
> **이 코어는 정지를 못 한다.** P8 을 닫으려면 이 어긋남을 결정해야 했다.

### 사실관계 — 정지에는 unsafe 말고 길이 없다

| 길 | 왜 안 되나 |
|---|---|
| `SuspendThread` · `NtSuspendProcess` | `windows`·`ntapi` 어느 쪽이든 **raw FFI 다.** 호출부가 `unsafe` 를 써야 한다 |
| `sysinfo` | Windows 에서 `Signal::Kill` 만 지원한다 (Linux 는 `Signal::Stop` 이 있으나 그 백엔드는 프로세스 Op 자체를 구현하지 않았다) |
| OS 관리 도구 (D12 의 `system_tool`) | **정지를 시키는 기본 제공 exe 가 없다.** `pssuspend` 는 Sysinternals 이고 배포되지 않는다 |

D12 가 `schtasks`·`sc`·`powershell` 로 unsafe 를 피할 수 있었던 것은 그 자리에
**OS 자신의 관리 경로가 있었기 때문**이다. 정지에는 그것이 없다.

### 채택 — 능력으로 재정의하고, 없으면 그 사실을 남긴다

규칙은 그대로 두되 **강등 경로**를 명시한다. 정지할 수 있는 플랫폼은 정지하고,
못 하는 플랫폼은 집합 종료로 진행하되 **저널에 "정지 단계를 건너뛰었다" 를
적는다.** 오늘 Windows 는 언제나 후자다.

근거는 셋이다.

1. **실측이 있다.** 30ms 로 되살리는 워치독 쌍에게 집합 종료가 이겼다 —
   직후 0, 1.5초 뒤 0 (설계-09 P8 시나리오 A). 정지가 사 주는 이득을 아직
   재지 못했다.
2. **`forbid(unsafe_code)` 는 18개 크레이트 전부에 걸린 검증 가능한
   불변식이다.** 필요를 재지 못한 능력을 위해 검증된 불변식을 깨는 것은
   나쁜 거래다.
3. **규칙을 지우는 것은 이 도구가 제품에게 금지한 동작이다.** 관측이
   불완전할 수 있듯 실행도 불완전할 수 있고, 둘 다 말하지 않으면 완전한
   것으로 읽힌다. 저널에 남기면 감사에서 보인다.

### 기각한 안

**unsafe 전용 크레이트를 지금 신설** — `xtask arch` 가 "unsafe 는 이 크레이트
에만" 을 검사하게 하면 오염을 한 곳에 가둘 수는 있다. 그러나 위 1번 때문에
**지금은 값을 치를 이유가 없다.** 아래 방아쇠가 당겨지면 이 안으로 돌아온다.

**규칙 자체를 삭제** — 못 하니까 지우는 것이고, 그러면 저널이 규칙을 다 돈
것처럼 읽힌다. 기각.

### 다시 여는 조건 — 측정 가능한 방아쇠

**집합 종료가 지는 픽스처를 하네스가 만들어 낼 때** unsafe 전용 크레이트를
연다. 후보는 셋이다 — 3자 이상 상호 감시, `max_targets` 를 넘는 군집, 소생
간격 5ms 미만. 그때 unsafe 는 값을 치르고 들어온다. 그 전까지는 들어오지
않는다. (설계-09 P10)

## 미결 사항

**사업 판단이 필요한 것**

1. **Windows 7/8.1 지원 여부** — `win7-windows-msvc` 는 tier 3(rustup 배포 목록에 없음)이라 nightly + `-Z build-std` 가 필요하고, yara-x·wasmtime 트리가 그 타깃에서 빌드되는지는 미검증. **지원 대상이 아니라면 그렇게 선언해야 한다** (설계-00 §4)

**부트스트랩 중 실증으로 해소**

2. ~~**Linux 정적화 방식**~~ — **P0에서 해소. `x86_64-unknown-linux-musl` 채택.**

   네이티브 Linux(`rust:1.96` + `musl-tools`)에서 `yara-x` 를 포함한 채로 두 후보를 **모두** 빌드했다.

   | 후보 | 결과 | 크기 |
   |---|---|---|
   | **A. `x86_64-unknown-linux-musl`** | **채택** — 추가 플래그 없이 정적, `selftest` 통과 | 18.6 MB |
   | B. `x86_64-unknown-linux-gnu` + `+crt-static` | 동작함 (대안으로 유효) | 19.4 MB |

   A를 고르되 **B도 동작한다는 사실이 중요하다.** musl 특유의 문제(기본 스레드 스택 128 KB, 할당자 성능)가 나중에 드러나도 갈아탈 곳이 있다. 산출물은 **static-pie** 다 — `objdump -p` 에 `DYNAMIC` 세그먼트는 있지만 `INTERP` 와 `NEEDED` 가 없다. 자기 재배치용이지 동적 의존이 아니다.

   > **설계 단계의 실측과 결론이 반대로 나왔다.** Windows 호스트에서 musl로 크로스 빌드했을 때는 `cc-rs: failed to find tool "x86_64-linux-musl-gcc"` 로 실패했고, 그 때문에 "musl 미검증"으로 남겨 두었다. 실패 원인은 musl 자체가 아니라 **wasmtime 이 요구하는 C 컴파일러가 크로스 환경에 없었던 것**이었다. 네이티브 러너에 `musl-tools` 가 있으면 문제가 사라진다.
   >
   > 이것이 설계-09가 P0에 **의존성 스파이크**를 넣은 이유다. 빈 크레이트로 판정했다면 "링크된다"는 무의미한 초록을 받았을 것이고, 크로스 실패만 보고 판단했다면 **없는 문제를 피해 glibc로 갔을 것**이다. 두 오판을 모두 막았다.
3. **32비트 Pulley 인터프리터 성능** — 실제 룰셋·대상 경로로 실측 (3주차)
4. **mmap SIGBUS 대응 전략** — yara-x 가 파일을 mmap 하므로, 스캔 중 악성코드가 파일을 잘라내면 SIGBUS 가 발생할 수 있다. 스캔 전 복사 vs 시그널 처리 중 선택 (3주차)
5. ~~**서명 방식 확정**~~ — **2026-08-25 (P10) 확정.** minisign 포맷(Ed25519)을 채택했다. 실증은 D1 과 같은 방식으로 했다 — 후보를 실제로 넣고 의존성을 재서 판정했다.

   | 크레이트 | 무엇을 끌어오나 | 어디에 |
   |---|---|---|
   | `minisign-verify` (검증) | **없음. 0 개** | `remedy-trust` — 제품 경로 |
   | `minisign` (서명) | `rpassword`(→ `windows-sys`) · `scrypt` · `salsa20` · `pbkdf2` | **`xtask`** — 개발 도구 |

   이 차이가 배치를 갈랐다. 서명기가 끌어오는 것은 개인키를 풀고 사람에게 암구호를 묻는 도구의 의존성이다. **치료 도구가 서명 능력을 갖지 않는 것은 자기 갱신 채널을 갖지 않는 것(D7)과 같은 이유다.** 그래서 설계-09 가 산출로 적었던 CLI `plugin sign` 은 `cargo xtask sign` 이 되었다.

   `trusted_comment` 가 서명 대상에 포함된다는 성질도 소스에서 확인했다(서명 값과 주석을 이어 붙인 것에 대한 두 번째 Ed25519 서명을 검증한다). **역행 금지 판정의 근거가 서명 안에 있다**는 뜻이고, 그래서 주석 형식을 `remedy-plugin id=… version=… signed=…` 로 못 박았다.
6. ~~**의존성 라이선스 감사**~~ — **P0에서 해소.** `cargo-deny` 를 CI에 넣었고 라이선스·중복·출처는 전부 통과했다. 보안 권고 3건이 나왔고 각각의 판단 근거와 재검토 조건을 `deny.toml` 에 남겼다.

   | 권고 | 판단 |
   |---|---|
   | `wasmtime` RUSTSEC-2026-0222 | **해당 없음** — 임베더가 Engine 두 개를 만들어 객체를 섞을 때만 발생하며, 상위 권고가 *"guest WebAssembly 프로그램으로는 촉발할 수 없다"*고 명시한다. yara-x 1.19 가 wasmtime 43 에 고정되어 있고 43 계열에는 수정본이 없다 — **2026-11-02 지웠다**: yara-x 1.22.1 이 wasmtime 48.0.8 로 올라 수정본에 들었다 |
   | `rsa` RUSTSEC-2023-0071 (Marvin) | **해당 없음** — 개인키 연산의 타이밍 누출이며 네트워크 관측이 전제다. remedy 는 RSA 개인키를 갖지 않고(yara-x 는 서명 *검증*에만 사용) 네트워크 서비스도 노출하지 않는다(D8) |
   | `bincode` RUSTSEC-2025-0141 | 취약점이 아니라 미유지보수 공지. yara-x 내부 의존이며 대체가 없다 |
   | `unsafe-libyaml` RUSTSEC-2024-0449 | 취약점이 아니라 미유지보수 공지(2026-11-02 더했다). serde_yaml_ng 의 파서이고 그 크레이트가 마지막 판이라 올려 풀 수 없다. 공격자가 만든 YAML 이 이 파서에 닿는 경로가 없다 — 서명 검증 뒤의 매니페스트 · 운영자 입력 · 분석가 초안만 읽는다 |

   **세 건 모두 "무시"가 아니라 "조건부 유예"다.** yara-x 가 wasmtime 을 올리면 첫 항목을 지우고, 코어가 RSA 개인키를 다루게 되면(P10 서명 방식 확정) 둘째를 재평가한다. 상용 배포 직전에 몰아서 보면 늦다는 판단이 맞았다 — 첫날에 세 건이 나왔다

   **2026-11-02 — 첫 항목의 조건이 섰다.** 그 사이 공지된 12건(wasmtime 8 · zip 3 · crypto-bigint 1)과 함께 yara-x 를 1.22.1 로 올려 풀었다. 올리기 전에 잰 바로도 12건 모두 우리 쓰임새에서 닿지 않았다 — 꺼진 wasmtime 기능(컴포넌트 모델 · async · GC · WASI)과 aarch64 전용 결함, 디스크에 푸는 zip API, 비밀 정수의 연산이다. 권고 검사는 CI 의 리눅스 잡이 PR 마다 돈다

**성능 예산 (3주차에 수치 확정)**

전용백신은 사용자 PC에서 돌므로 체감 성능이 곧 제품 품질이다. 대상 경로가 좁아 전 디스크 스캔은 없지만, 아래를 측정하고 상한을 정한다 — 스캔 소요 시간, 최대 메모리, I/O 우선순위(사용자 작업 방해 최소화), 진행률 보고 주기, **취소 가능성**(취소는 계획 단계까지만 안전하며, apply 중 취소는 부분 치료를 만든다는 점을 UI에 명시).
