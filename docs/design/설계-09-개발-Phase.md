# 설계 09 — 개발 Phase (검증 게이트 방식)

> 작성일: 2026-08-20 · 2차 개정: 2026-08-20 (추적성 감사 반영)
> **설계-04 §5의 주차 계획을 대체한다**

## TL;DR

- **무엇을**: Phase마다 **그 시점에 실제로 수행 가능한 완료 조건**을 두고, 통과해야 다음으로 넘어가는 개발 순서를 확정한다.
- **순서를 정한 원리 셋**:
  1. **파괴 능력은 그것을 제약하는 가드보다 늦게 들어온다.** 되돌리기(격리·복원)가 지우기보다 먼저다.
  2. **표면을 넓히기 전에 수직으로 관통한다.** P2는 subject 2종·Op **0종**으로 파이프라인 전체를 완성한다.
  3. **가장 위험한 기술 리스크를 앞으로 당긴다.** yara-x·wasmtime 링크 문제는 P0에서 실증한다.
- **가드는 통과할 때가 아니라 막을 때 검증된다.** 완료 조건에 **일부러 위반해 실패를 확인하는 절차**를 넣는다.
- **§3의 추적성 매트릭스가 이 문서의 본체다.** 설계 문서의 모든 Op·subject·명령·게이트·크레이트가 어느 Phase에 속하는지 전수로 적혀 있고, **그 대조를 CI가 수행한다**(P0).
- **v1 = P0~P11.** 지금 시작할 Phase는 **P0**.

## 2. 이 순서가 막는 실수

| 흔한 실수 | 막는 방법 |
|---|---|
| 파괴 코드가 가드보다 먼저 들어온다 | P3(가드)·P5(복원)가 P6(실행기)보다 앞 |
| 되돌릴 수 없는 상태를 만든다 | **격리·복원이 첫 파괴보다 먼저** |
| 빌드·링크 문제를 뒤늦게 발견한다 | P0의 의존성 스파이크 |
| 스키마와 코드가 어긋난다 | P1의 CI 재생성 diff |
| **설계와 계획이 어긋난다** | **P0의 추적성 검사** |
| 안전 불변식이 조용히 깨진다 | P0에서 의존 금지 테스트를 코드보다 먼저 |

| 문서와 구현이 갈라진다 | 공통 완료 조건 4번 |

### 3.2 Op 29종 → Phase (축약 없이 전수)

| Phase | 위험 | Op |
|---|---|---|
| **P6** | 저 | `file.quarantine_only` |
| **P7** | 저 | `shortcut.strip_args` · `av.restore_exclusions` · `hosts.restore_line` · `proxy.restore` · `firewall.restore_rule` |
| **P7** | 중 | `file.delete` · `file.delete_on_reboot` · `file.delete_stream` · `registry.delete_value` · `registry.strip_value` · `registry.restore_default` · `persistence.disable` · `persistence.delete` · `autorun.remove` · `text_config.remove_line` · `structured_config.remove_key` · `structured_config.restore_default` · `env.strip_path` · `browser_ext.remove` |
| **P8** | 중 | `process.kill` · `service.clear_recovery` · `service.stop` · `service.disable` · `service.delete` |
| **P8** | 고 | `registry.delete_key` · `cert_store.remove` · `boot.restore_default` |
| **P10** | 고 | `dir.delete_recursive` |

> P8의 `process.*`·`service.*` 는 위험 등급이 **중**이지만 P8에 둔다. 정지 후 종료·보호 프로세스 목록·SCM 경쟁 등 **운영 복잡도가 고위험 Op에 준하고 VM 실증이 필요**하기 때문이다.

> `dir.delete_recursive` 만 **P10** 이다. 이 Op 을 안전하게 만드는 것은 설계-03 §4 의 세 번째 조건 — *"하위에 신뢰 서명 파일이 존재하면 거부"* — 이고, 그것은 설계-03 §3 **2층(신뢰 서명 검증)** 의 일부다. 2층은 `remedy-trust` 와 함께 P10 에 온다.
>
> **가드 없이 이 Op 을 열면 안 되는 이유는 설계-08 시나리오 F 가 이미 걸어 보았다.** 정상 서명된 `LegitApp.exe` 옆에 악성 `version.dll` 이 놓이면 guard 조건("그 안에 악성 판정 파일 1개 이상")은 통과한다 — 막는 것은 서명 조건 하나뿐이고, 그것이 없으면 **정상 프로그램 폴더가 통째로 사라진다.**
>
> 실행기·복원기·왕복 시험은 P8 에서 이미 만들었다. 없는 것은 판정 재료뿐이다.

### 3.3 subject 20종 → Phase

| Phase | subject |
|---|---|
| **P2** | `file` · `persistence` |
| **P4** | `autorun` · `service` · `process` · `registry_value` · `registry_key` · `text_config` · `structured_config` · `shortcut` · `hosts_entry` · `browser_extension` · `av_exclusion` · `cert_store` · `proxy_config` · `firewall_rule` · `boot_config` · `indicator` · `package` · `unix_socket` |

> `package` 는 P12 회차(2026-10-27 · C-2)에 더해졌는데 **P4** 다. 이 칸은
> *"언제 커밋했는가"* 가 아니라 **어느 표면이 소유하는가**이고 수집 표면은
> P4 다 — `firewall_rule` 이 같은 자리에 있다. 이 subject 는 **Linux 전용**
> 이다(`windows: false`): 개념은 Windows 에도 있으나(MSI · winget · Appx) 이
> 코어에 수집기가 없고, 그 축에는 `linux_from` 같은 *"아직"* 칸이 없다.
>
> `unix_socket` 도 같은 까닭으로 **P4** 다(코어 1.2.0 · 2026-11-08). `/proc/net/unix` 의
> 이름 있는 소켓을 파일로 읽는 **Linux 전용 · 찾기 전용** subject 이고, Ebury 의 현재 주
> 탐지법(추상 소켓 이름)을 룰로 쓰려고 열었다. 살아 있는 연결 목록을 뺀 결정(설계-01 D11)과
> 무엇이 다른지는 그 결정의 덧붙임에 있다.

> **측정 대상은 특정 저장소가 아니라 "가용한 최대 정상 파일 코퍼스"다** (2026-08-25 정정).
> 처음에는 사내 검체 저장소(내부 문서 설계-05 §6)를 방법으로 적었는데, **그 저장소에 닿을
> 수 없는 상태에서 그 경로만 두면 위에서 해결했다는 모순이 그대로 돌아온다.** G9가 재는
> 것은 "정상 파일에 오탐 0건"이고 검체 공급원은 수단이다. 개발 기계와 테스트 VM의
> `Program Files`·`System32`·설치 트리만으로도 십수만 개가 나오며, 사내 저장소가 붙으면
> 코퍼스가 커질 뿐 정의는 바뀌지 않는다. 확정된 정의는 설계-03 §10.

### 3.6 엔트리 종류 14종 → Phase

격리 컨테이너의 엔트리 종류는 **P5에서 전부 정의**되고(설계-02 §9), 아래는 그 **직렬화가 실제로 들어오는** Phase다. 격리물은 자동 삭제하지 않으므로 포맷 실수는 영구적이다 — 그래서 정의를 미루지 않는다.

| Phase | 엔트리 종류 |
|---|---|
| **P6** | `file` |
| **P7** | `file_stream` · `directory` · `registry_value` · `task` · `cron` · `unit` · `text_line` · `structured_config` · `av_exclusion` |
| **P8** | `registry_key` · `service` · `cert_store` · `boot_config` |

> 종류는 그것을 쓰는 Op보다 **늦게 올 수 없다.** 늦으면 그 Phase는 백업 없이 파괴하게 된다. `process.kill` 만 백업 종류가 없으며, 그것이 이 Op이 되돌릴 수 없는 유일한 Op이라는 사실과 정확히 대응한다. 둘 다 SDK 테스트가 강제한다.

## 4. 공통 완료 조건

1. **그 시점에 활성인 CI 작업 전부 초록** (§5 활성 시점 표)
2. **회귀 없음** — 이전 Phase의 검증이 전부 여전히 통과
3. **가드 역검증** — 이 Phase에서 추가한 가드·불변식을 **일부러 위반해 실패하는 것을 확인**하고 그 케이스를 테스트로 남긴다. 추가한 가드가 없으면 **"해당 없음"을 명시**한다
4. **문서 동기화** — 구현이 설계 문서와 다르면 둘 중 하나를 고친다. **설계 오류를 발견하면 문서를 먼저 고치고 그 다음 코드를 고친다**
5. **추적성 검사 통과** — §3 매트릭스와 설계 문서 인벤토리가 일치한다 (P0부터 자동)

완료 시 **`phase/PN` 태그**를 단다.

> 3번이 이 계획의 성격을 결정한다. "테스트가 통과했다"는 가드가 동작한다는 증거가 아니다. **막아야 할 것을 넣었을 때 막는지**를 봐야 한다.

### 되돌아가는 규칙

- 게이트 검증이 **2회 연속 실패**하면 구현이 아니라 **이전 Phase의 가정을 의심**한다
- 워크스루 두 차례에서 26건이 나왔듯 **구현 중에도 설계 오류가 나온다.** 발견 시 Phase를 멈추고 문서를 고친 뒤 재개한다 — 코드에 임시 우회를 넣고 진행하지 않는다

## P5 — 격리·복원·저널 (지우기 전에 되돌리기)

**산출**: `remedy-quarantine`(컨테이너 포맷·키 wrap 3종), `remedy-journal`(fsync append-only·재시도 큐), CLI `restore`, **복원 쓰기 경계**(`remedy-platform`), **디스크 공간 사전 확인**(설계-00 §5-2)

**선행 결정** (완료 — 설계-03 §5)
- 평문 헤더 범위: 세 물음(무엇인가·열 수 있나·어느 실행인가)만. 플러그인 ID·위협 이름·원본 경로는 암호 영역
- 알고리즘: XChaCha20-Poly1305 · Argon2id · X25519+HKDF-SHA256. 헤더에 식별자를 담아 포맷은 알고리즘 중립
- 격리소·저널 I/O 는 쓰기 경계를 지나지 않고, **복원 쓰기만** 지난다

**검증**
- **속성 기반 테스트**: 임의 파일·메타데이터 → 격리 → 복원 → 원본 동일. 손실 항목 목록이 실제와 정확히 일치
- Windows ACL/SDDL, Linux mode·xattr 복원
- **로컬 키 wrap만 있는 컨테이너가 경고를 낸다**
- 조직 복구 공개키로 감싼 컨테이너를 **다른 머신에서 열어 꺼낼 수 있다**(`restore --extract-to`). 제자리 복원은 원래 머신에서만 보장하므로 이것이 검증 대상이다 — 설계-02 §9 "여는 것과 되돌리는 것은 다르다". 개발 중에는 테스트 키쌍 + 호스트↔VM 으로 실증하고, 조직 실물 키는 배포 시점 산출물이다
- **제자리 복원이 다른 머신에서 거부된다** — SID가 해석되지 않는 곳에 SDDL 을 억지로 적용하면 잘못된 권한이 붙는다
- **불변식 R**: 컨테이너에 토큰 경로가 들어가지 않는다 · 복원이 기록된 경로 밖에 쓰지 않는다
- **보호 목록 역검증**: 보호 경로를 가리키도록 조작한 컨테이너의 복원이 거부된다(종료 코드 5)
- 저널이 크래시 지점에서 잘려도 파싱 가능하고 마지막 완료 지점을 안다
- **여유 공간 부족 시 백업 전에 중단**한다

## P6 — 실행기 골격 · 첫 Op 🔒 첫 시스템 변경

**Op는 `file.quarantine_only` 하나뿐이다.**

**선행 결정** — `plan` 이 **매니페스트를 입력으로 받는다** (설계-03 §2)

`remediate` 는 매니페스트에 있고 `scan.json` 에는 없다. 지금까지 계획기는 `scan.json` 만 받았고 그래서 Action 이 **언제나 0건**이었다 — 가드는 매 실행에서 돌지만 잴 대상이 없었다. P6 에서 첫 Op 이 붙으려면 이 입력이 먼저 열려야 한다.

- `plan(scan, manifest, limits, protected)` · CLI `plan --scan <파일> --plugin <plugin.yaml> --out <파일>`
- `scan.json` 에 치료 지시를 실어 보내는 대안은 채택하지 않았다 (설계-03 §2 참조)

**산출**: `remedy-apply`, **계획기의 Action 도출**(`remediate` → 순서·백업 부여), CLI `apply` · `run` · **`--dry-run`**, **대화형 승인 흐름**, **NDJSON 진행 이벤트**, **전역 뮤텍스**(동시 실행 방지), VM testbed 하네스

**검증**
- VM에서 격리 → `restore` → 원본 일치
- **실패 주입 시 롤백하지 않고 나머지 계획을 계속 수행** (Action 2건 이상)
- **크래시 후 재기동 시 저널을 읽어 이어서 수행**
- **`--dry-run` 이 계획을 출력하고 아무것도 변경하지 않는다**
- **승인 없이 `apply` 가 진행되지 않는다** (대화형)
- **두 번째 인스턴스가 뮤텍스에 막힌다**
- **G3**: `apply` 중 계획에 없던 Action 0건
- **제품 바이너리에 네트워크 심볼이 링크되지 않는다** — `remedy-apply` 는 라이브러리라 따로 링크되지 않는다. 검사 대상은 그것을 링크한 `remedy.exe` 이며, 임포트 테이블을 직접 읽는다(`cargo xtask static`)

## P7 — 저·중위험 Op

**대상**: §3.2의 P7 행 19종

**산출**: 위 Op + **`regenerator` 속성**(유발자 우선 제거) + **`allow_removable`·`%REMOVABLE%` 파괴 시 대화형 승인**

**검증**
- **Op마다 apply → restore 왕복**이 원본을 복원한다 (**G2**)
- **백업 실패 시 즉시 중단하고 아무것도 변경되지 않는다** (격리와 파괴가 분리된 첫 Phase)
- 부분 편집(`strip`) 백업이 **편집 전 값 전체**
- `restore_default` 가 카탈로그에 없는 대상을 린트에서 거부
- **유발자가 산출물보다 먼저** 실행된다 (예약 작업 → 드롭 파일)
- 잠긴 파일이 재부팅 예약으로 넘어간다
- **이동식 매체 대상이 무인 모드 계획에서 제외**된다
- **G1이 여기서부터 의미를 갖는다** — 청정 코퍼스 전체에서 파괴 Action 0건

### 닫으면서 드러난 것

**게이트를 올리는 것이 검사였다.** `IMPLEMENTED_THROUGH` 를 P7 로 올리자 그전까지 아무도 재지 못했던 두 결함이 즉시 드러났다.

| 무엇 | 왜 그전에는 몰랐나 |
|---|---|
| **G6 이 파일 경로가 아닌 대상을 전부 막았다** | P6 까지 계획될 수 있는 Op 이 `file.quarantine_only` 하나뿐이었다. 레지스트리·예약 작업 대상이 계획에 들어온 적이 없다 (설계-03 §10) |
| **`default_backend()` 가 Windows 에서도 파일 백엔드를 돌려줬다** | 시험이 가짜 백엔드를 쓴다. 실기기에서는 레지스트리 Op 8종이 전부 `Unsupported` 로 실패했을 것이다 |

**G2 는 표로 강제한다.** Op 별로 왕복 시험을 흩어 두면 새 Op 이 시험 없이 넘어간다. `remedy-core/tests/g2_roundtrip.rs` 가 **카탈로그를 기준으로** 돌며 게이트 이하의 모든 Op(현재 20종)에 왕복 사례를 요구하고, 사례가 없으면 깨진다. 왕복은 세 번 잰다 — `수행 전`, `수행 후`(달라야 한다), `복원 후`(같아야 한다). 가운데를 빼면 **아무것도 하지 않는 Op 도 왕복 시험을 통과한다.**

### 구현했지만 아직 계획될 수 없는 Op — 2종

"Op 을 구현했다" 와 "플러그인이 그것을 쓸 수 있다" 는 다르다. 둘을 뭉뚱그리면 Phase 완료 보고가 절반만 참이 된다. 목록으로 못박고 시험이 강제한다(`remedy_plan::NOT_PLANNABLE_YET`).

| Op | 왜 |
|---|---|
| `file.delete_stream` | **수집기가 대체 스트림을 열거하지 않는다.** 열거에는 `FindFirstStreamW` 가 필요하고 그것은 unsafe 다 — 이 저장소는 크레이트 전부에 `forbid(unsafe_code)` 를 건다. 이름을 아는 스트림만 훑는 방식은 임의 이름을 쓰는 악성 스트림을 체계적으로 놓치므로 열거의 대체재가 되지 못한다. 실행기·복원기는 완성돼 있고 왕복도 통과한다 |
| `structured_config.restore_default` | **OS 기본값 카탈로그에 구조적 설정 항목이 하나도 없다.** 값의 출처는 카탈로그뿐이므로(설계-03 §2) 항목이 생기기 전에는 되돌릴 값이 없다. 브라우저 `Preferences` 처럼 OS 가 정하지 않는 파일에는 애초에 "기본값" 이 없다 |

둘 다 **조용한 구멍이 아니다.** 시험이 이 목록을 강제하므로, 새로 비는 자리가 생기면 여기 적게 되고 해소되면 이 줄을 지우게 된다.

### 이동식 매체는 계획 시점에 갈린다

`allow_removable` 선언은 **읽어도 좋다**까지다. 그 위의 것을 부수는 판단은 눈앞의 매체를 보는 사람만 할 수 있다 — 드라이브 문자는 재사용되므로 스냅샷을 뜬 시점의 `E:` 와 수행 시점의 `E:` 가 같은 매체라는 보장이 없다.

- **무인 모드**: 계획기가 아예 만들지 않는다. 조용히 빼지 않고 `deferred` 에 이유와 함께 남긴다
- **대화형**: 계획하되 `user_impact: removable_media` 를 달고, CLI 가 **일반 승인과 별도로** 한 번 더 묻는다
- **남의 계획을 받는 `apply --plan --yes`**: 이런 Action 이 들어 있으면 종료 코드 5 로 거부한다. 계획은 다른 기계에서 만들어져 올 수 있다

판단의 근거는 스냅샷에 적힌 `removable_roots` 다. 계획 시점에 지금 꽂힌 매체를 다시 물으면 같은 스냅샷이 같은 계획을 내지 않는다.

### 복원은 재부팅 예약도 취소한다

`file.delete_on_reboot` 는 파일을 남기고 큐에 넣는다. 복원이 파일을 되돌려도 그 예약이 그대로면 **다음 부팅이 다시 지운다** — 사람은 복원에 성공했다고 보고받고 다음 날 파일이 없다. 그래서 파일 복원은 되돌린 경로 하나의 예약을 함께 취소한다. 큐에는 다른 설치 관리자의 항목이 함께 있으므로 짝 단위로, 그 경로만 뺀다.

## P8 — 고위험 Op 🔒 되돌릴 수 없는 동작

**대상**: §3.2의 P8 행 9종

**산출**: 위 Op + **시스템 복원 지점 생성 시도**(설계-00 §5-2)

**검증** — **VM 실증 없이 통과시키지 않는다**
- 워치독 쌍 VM에서 **집합 종료가 이기고, 순차 종료로는 지는 것**을 함께 확인 — 정지(suspend)는 설계-01 D13 으로 **강등했고**, 그 사실을 저널이 매번 적는다. 잰 것을 적는다: 우리가 실증한 것은 정지 후 종료가 아니라 집합 종료다
- 서비스 복구 동작을 남긴 채 종료하면 SCM이 되살리는 것을 **재현**하고, 순서를 지키면 이기는 것을 확인
- 보호 프로세스를 지목하는 술어가 **해당 대상만 제외**하고 감사 로그에 사유를 남긴다
- `registry.delete_key`: `guard` 없으면 거부 / 증거에서 추출된 키가 아니면 거부 (재귀 삭제와 **같은 가드**를 받는다 — 설계-03 §4)
- `registry.delete_key`: IFEO 부모 키가 보호 목록에 걸린다
- `cert_store.remove` 가 **무인 모드 계획에 포함되지 않는다**
- 복원 지점 생성이 실패해도 **치료는 진행**된다 (대체재가 아니라 추가 안전망)

### 닫혔다 — `IMPLEMENTED_THROUGH = P8`

**VM 실증 두 건이 끝나서 게이트를 올렸다.** 검증 목록 일곱 줄이 전부 증거를
갖는다.

| 무엇 | 상태 |
|---|---|
| Op 8종 · 백업·복원·가드 | **끝** — G2 왕복 표가 29종 전부를 돈다 |
| `dir.delete_recursive` | **P10 으로 옮겼다** (아래) — 구현·왕복 시험은 남아 있다 |
| 계획기가 P8 Op 을 낸다 | **낸다** — 게이트를 올리면서 서비스 제거의 차례까지 뚫었다 (아래) |
| 워치독 쌍 (A) | **실증 완료** — 아래 |
| SCM 복구 동작 (B) | **실증 완료** — B1(되살아난다)·B2(순서가 이긴다) 둘 다 통과 |
| `정지 후 종료` | **강등을 결정했다** (설계-01 D13). 저널이 매번 그 사실을 적는다 |
| `include_descendants` | **구현 완료** — 상한·보호 대상·재사용된 PID 방어까지 |

VM 없이 잰 것과 재지 못한 것을 섞지 않는 것이 요점이다. `p8_guards.rs` 가
재는 것은 "계획과 술어가 지목한 것 중 무엇을 손대고 무엇을 손대지 않는가" 이고,
그것은 워치독 경쟁이나 SCM 의 되살림을 대신하지 않는다.

> **P8 은 8종이다.** 처음 잡을 때는 9종이었고 `dir.delete_recursive` 가
> 서명 가드(설계-03 §4 조건 3) 때문에 P10 으로 옮겨 갔다. 태그가 가리키는
> 범위는 8종이다.

### 게이트를 올린 값어치 — 계획기가 서비스를 반만 지우고 있었다

게이트를 올리자마자
`every_implemented_op_is_either_plannable_or_listed_with_a_reason` 가
**`service.clear_recovery` 와 `service.stop` 을 계획기가 낼 수 없다**고
보고했다. 이유는 자료 구조 하나였다.

```rust
Subject::Service => &[Op::ServiceDisable, Op::ServiceDelete],
//   그리고 소비하는 쪽은  ops.iter().find(|o| available(*o))
```

목록이 **차례가 아니라 우선순위**였다. 그래서 악성 서비스에 대해 계획기가
내는 것은 언제나 `service.disable` **하나**였다 — 복구 동작 제거도 정지도
갈 길이 없었다.

**VM 하네스가 방금 실증한 것이 실제 계획으로는 도달할 수 없는 성질이었다.**
B1·B2 가 보인 "복구 제거를 먼저 하면 SCM 을 이긴다" 를 만들어 낼 계획을
계획기가 낼 수 없었다.

`stage()` 에는 그 차례가 이미 적혀 있었다(`ServiceClearRecovery`=1,
`ProcessKill`=2, …). **표는 있는데 아무도 그 자리에 닿을 수 없었다.**

그래서 두 뜻을 형으로 갈랐다.

| | 뜻 | 예 |
|---|---|---|
| `Removal::Choice` | 쓸 수 있는 **첫 하나** | 파일 — 격리하거나 지우거나 |
| `Removal::Sequence` | 쓸 수 있는 것 **전부** | 서비스 — 하나만 해서는 사라지지 않는다 |

이제 `remove: [{ref: svc}]` 하나가 설계-03 §2 의 차례를 그대로 낸다.

```
1  service.clear_recovery   (1단계 자동 소생 차단)
2  service.stop             (1단계)
3  service.disable          (3단계 재기동 차단)
4  service.delete           (5단계 유발자 제거 — regenerator)
```

**`service.stop` 의 단계도 함께 고쳤다.** 3단계(재기동 차단)에 있었는데
설계-03 §2 는 1단계("복구 동작 제거, 서비스 정지")에 둔다. 3단계에 있으면
프로세스 종료(2단계)가 정지보다 먼저 돌고, 그것은 정상 정지가 아니라
**크래시**다 — SCM 은 예기치 않은 종료에만 복구 동작으로 반응한다. 복구
제거가 성공했다면 결과는 같지만, 실패했다면(권한·잠금) 순서가 그대로 지는
자리가 된다.

### VM 하네스가 잰 것 — 시나리오 A (워치독 쌍)

`testbed/harness/guest/Verify-P8.ps1` · 픽스처 `testbed/fixtures/watchdog`.

**A 는 VM 이 없어도 돈다.** 사용자 모드 프로세스 두 개면 되므로 개발 기계에서
바로 돌릴 수 있고, 그것이 이 검증을 자주 돌릴 수 있게 하는 자리다. 실측 결과:

| 검사 | 결과 |
|---|---|
| 쌍이 선다 | 2개 |
| 한쪽을 죽이면 되살아난다 | **31ms** — 공정한 상대다 |
| 순차 종료로는 진다 | 남은 수 **2** |
| remedy 의 `process.kill` 이 이긴다 | 직후 **0** · 1.5초 뒤 **0** |
| 이기지 못했으면 그렇게 보고한다 | 통과 |
| 표식을 가진 프로세스가 남지 않았다 | 0 |

**"이겼다" 는 상대가 공정할 때만 뜻이 있다.** 그래서 되살리기 간격을 숫자로
남긴다 — 되살리기가 제품의 종료 창보다 느린 감시자는 어떤 구현에게도 지고,
그때의 통과는 아무것도 재지 못한 것이다. 처음 만든 PowerShell 감시자가 정확히
그랬고, 그래서 픽스처를 컴파일된 바이너리로 바꿨다.

> **`정지 후 종료` 는 강등했다 — 설계-01 D13.** 이 코어는 정지를 하지
> 못한다. `SuspendThread`·`NtSuspendProcess`·잡 오브젝트가 전부 `unsafe` 를
> 요구하고, `sysinfo` 는 Windows 에서 `Signal::Kill` 하나만 지원하며, D12 가
> 쓴 것 같은 **OS 관리 도구도 이 자리에는 없다.**
>
> 규칙을 지우지 않았다. 정지할 수 있으면 하고, 못 하면 집합 종료로 가되
> **저널에 강등을 적는다** — 오늘 `process.kill` 은 매번 그 줄을 남긴다.
> 말하지 않으면 저널이 규칙을 다 돈 것처럼 읽히고, 그것은 이 도구가 제품에게
> 금지한 동작이다.
>
> 근거는 실측이다. 30ms 소생 상대에게 **집합 종료만으로 이겼다.** 더 빠른
> 상대나 셋 이상의 고리에는 질 수 있고, 그것은 **재지 않았다** — 지는 픽스처가
> 나오는 날이 unsafe 전용 크레이트를 여는 날이다 (D13 의 방아쇠, P10).

### VM 하네스 — 시나리오 B (SCM 복구 동작)

**되살림을 재현하려면 진짜로 도는 서비스가 있어야 한다.** 첫 판은
`binPath = cmd.exe /c exit 1` 이었는데 SCM 핸드셰이크를 하지 않아 RUNNING 에
도달하지 못했고, **되살릴 대상이 애초에 없었다.** 그래서 그때의 검사는 "복구
동작이 설정돼 있다" 까지만 볼 수 있었다 — 그것은 전제이지 재현이 아니다.
(게다가 그 검사는 앞 검사의 불리언을 그대로 다시 판정하는 항진명제였다.)

`testbed/fixtures/labsvc` 가 그 자리를 채운다. `windows-service` 크레이트가
핸드셰이크를 안전하게 감싸므로 unsafe 가 필요 없고, **워크스페이스 밖**이라
크레이트 수·금지 의존·`cargo deny` 어디에도 섞이지 않는다. 제품은 이 크레이트를
의존하지 않는다 — remedy 는 서비스를 *만드는* 쪽이 아니라 *고치는* 쪽이다.

B 가 재는 것은 **두 실행의 차이**다.

| 계획 | 기대 | 무엇을 보이나 |
|---|---|---|
| `[process.kill]` — 복구 동작을 남긴 채 | 되살아난다 | **적이 진짜다** |
| `[service.clear_recovery, process.kill]` | 되살아나지 않는다 | **순서가 이긴다** |

시나리오 A 와 같은 모양이다 — 적이 실제로 이기는 것을 먼저 보이고 나서 제품을
붙인다. 저널의 줄 번호를 세는 것보다 강하다.

**`service.stop` 이 아니라 `process.kill` 이다.** 정상 정지는 복구 동작을
유발하지 않는다 — SCM 은 예기치 않은 종료에만 반응하고, 그것이 설계-03 §2 가
1단계(복구 제거)를 2단계(종료) 앞에 둔 이유다.

관리자 권한이 없어도 도는 검사가 하나 있다 — **픽스처가 진짜 서비스인가.**
SCM 이 부르지 않은 서비스 바이너리는 1063 으로 거절당하고, 그 거절이 곧
핸드셰이크를 한다는 증거다.

> 순서 검사를 하네스에서 **뺐다.** 하네스가 계획을 손으로 쓰면서 순서를 이미
> 정해 놓으므로 거기서 재는 것은 "실행기가 배열 순서를 따른다" 뿐이었고,
> 그것은 실기기가 필요 없다. `remedy-apply/tests/execute.rs` 의
> `actions_are_performed_in_the_order_the_plan_lists_them` 으로 옮겼다 —
> 배열 순서와 `seq` 순서를 일부러 어긋나게 두어 무엇을 따르는지 가린다.
>
> 계획기가 단계를 정하는 것(`ServiceClearRecovery`=1 < `ProcessKill`=2)은
> `actions_are_ordered_by_stage_and_renumbered` 가 이미 잰다.

### B 가 잰 것 — 실측

| 검사 | 결과 |
|---|---|
| 복구 동작을 남긴 채 죽이면 SCM 이 되살린다 | 시작 기록 **1→2** · Running · **PID 바뀜** |
| 복구 동작을 먼저 지우면 되살아나지 않는다 | **2→2** · Stopped |
| 복구 동작이 실제로 지워졌다 | `FAILURE_ACTIONS` 줄이 사라졌다 |
| `service.disable` 이 시작 유형을 바꾼다 | `START_TYPE : 4 DISABLED` |

**PID 가 바뀐 것이 요점이다.** 같은 프로세스가 살아 있었던 것이 아니라 SCM 이
새 프로세스를 띄웠다. 그리고 두 실행의 유일한 차이는 앞에 붙은 한 줄
(`service.clear_recovery`)이다 — 그것이 순서의 값어치다.

복구 동작이 소진돼서 안 되살아난 것도 아니다. `reset= 0` 에 restart 세 번을
걸었고 B1 이 한 번만 썼다.

### B 의 첫 관리자 실행이 찾아낸 것 — 하네스 결함 다섯

첫 판은 `11/12` 였고 실패는 "서비스가 RUNNING 에 도달했다" 하나로 보였다.
**그 한 줄이 다섯을 가리고 있었다.**

| | 결함 | 어떻게 드러났나 |
|---|---|---|
| F1 | `-Bin`·`-Watchdog`·`-LabService` 를 절대화하지 않았다 | `sc qc` 가 상대 경로를 그대로 보여 주었다. SCM 은 `%SystemRoot%\System32` 기준으로 풀기 때문에 서비스가 아예 뜨지 않았다 |
| F2 | `sc start` 의 답을 `[void]` 로 버렸다 | 실패 이유(오류 2)가 손에 있었는데 화면에는 "상태 Stopped" 만 남았다 |
| F3 | PS 5.1 이 네이티브 인자 안의 따옴표를 escape 하지 않는다 | 실측: `'"C:\a b\x.exe" --dir "C:\c d"'` 이 sc.exe 에 닿을 때 **따옴표가 전부 사라진다.** 경로에 공백이 없어 우연히 살아 있었다 |
| F4 | **재지 못한 검사가 결과에서 사라졌다** | `if ($running)` 이 거짓이라 B1·B2·복구확인 셋이 증발했다. JSON 검사 수가 12 (15 여야 했다) |
| F5 | `Get-Date -UFormat %s` 가 로컬 시각을 epoch 로 준다 | 실측 **+32401초(9시간)**. 픽스처는 진짜 UTC epoch 로 비교하므로 마감이 5분이 아니라 9시간 5분이었다 — 픽스처를 남지 않게 하는 두 겹 중 한 겹이 꺼져 있었다 |

**F4 가 가장 무겁다.** `11/12` 는 "하나 실패" 로 읽히지만 실제로는 **셋을 재지
못한 것**이다. 이 저장소가 exit 6 과 `Observation` 으로 제품에게 강제하는
"없다 vs 못 봤다" 를 하네스가 스스로 어겼다. 이제 RUNNING 에 도달하지 못하면
그 셋이 `서비스가 RUNNING 이 아니라 재지 못했다` 로 **결과에 남는다.**

**F3 은 알고 보니 결함이 둘이었다.** 되짚어 재면서 갈라졌다.

| 어디 | 무엇이 깨지나 | 실측 |
|---|---|---|
| `& sc.exe @A` | PS 5.1 이 인자 안의 따옴표를 escape 하지 않고 흘린다 | sc.exe 가 받는 문자열에서 **따옴표가 전부 사라진다** |
| 옛 `Quote-Arg` | 따옴표 앞 역슬래시를 두 배로 늘리지 않았다 | `C:\my lab\` 과 다음 인자가 **한 덩어리로 뭉개졌다** — `<C:\my lab" TAIL>` |

첫째가 이번 판을 날린 쪽이고, 둘째는 되짚다 나온 것이다. 지금 인용은 MSDN 의
역슬래시 규칙을 따르고, `Invoke-Exe` 로 넘긴 binPath 는 자식 프로세스의 argv 에
**따옴표를 단 채 한 조각으로** 도착한다 — 그것을 실제 argv 로 확인했다.

> F2·F4 는 **되짚어 확인하지 못했다.** 관리자 권한 없이는 그 자리에 닿지
> 않는다. F1·F5 는 하네스가 매번 재는 검사로 바꿔 두었으므로 비관리자 실행에서
> 되짚었다 — 되돌리면 그 검사가 빨개진다.

### 그 수정이 회귀 하나를 낳았다 — 인코딩

F3 을 고치며 `sc.exe` 를 `Invoke-Exe` 로 돌렸더니 `StandardOutputEncoding =
UTF8` 을 함께 물려받았다. **`sc.exe` 는 리다이렉트된 핸들에 ANSI 코드페이지
바이트를 쓴다** — 이 기계는 CP949 다. (콘솔 코드페이지가 아니다. 여기 콘솔은
65001 인데도 949 로 왔다.)

결과가 둘로 갈렸고, **둘째가 훨씬 무겁다.**

| | 무엇이 됐나 |
|---|---|
| `복구 동작이 설정됐다` | **거짓 실패.** 설정은 됐는데 `다시 시작` 을 못 읽었다 |
| `복구 동작이 실제로 지워졌다` | **조용히 빈 검사가 됐다.** 판정이 그 문자열의 *부재*였는데, 모지바케에는 애초에 없다 — **복구 동작이 남아 있어도 통과한다** |

| 판정식 | 복구 설정됨 | 복구 지워짐 |
|---|---|---|
| `RESTART\|다시 시작` (그때) | False | False |
| `FAILURE_ACTIONS` (ASCII) | **True** | **False** |

**이미 답이 있는 문제였다.** 설계-01 D12 가 제품에게 "출력을 읽지 않는다.
판단은 종료 코드로만" 을 강제하는 이유가 정확히 지역화다. 제품은 그것을
`Stdio::null()` 로 지키고 있는데, 하네스가 그 짐을 스스로 졌다.

그래서 셋을 바꿨다.

1. **인코딩은 부르는 대상이 정한다.** `Invoke-Exe` 가 인코딩을 인자로 받고,
   remedy 는 UTF-8, `sc.exe` 는 ANSI 코드페이지로 읽는다.
2. **판정은 ASCII 토큰으로만.** `FAILURE_ACTIONS` · `START_TYPE : 4` 는
   sc.exe 가 영어로 찍는 필드 이름과 숫자다. 지역화된 값은 detail 에 보여
   주기만 한다.
3. **오독을 검사로 만들었다.** 없는 서비스를 물어 `1060`(ASCII)이 보이고
   대체 문자(U+FFFD)가 없는지 본다 — 관리자 권한 없이 매번 돈다. 코드페이지
   추측이 다른 로캘에서 틀리더라도 **판정이 아니라 이 검사가 빨개진다.**

다른 하네스의 `-match "한글"` 은 무관하다. 그것들은 **remedy 자신의 UTF-8
출력**을 읽는다 — 우리 문자열이지 OS 의 로캘이 아니다.

#### 전제가 무너지면 통과가 아니라 "재지 못했다"

B 의 세 검사는 사슬이다.

```
복구 동작이 설정됐다  ->  되살아난다(B1)  ->  순서를 지키면 안 되살아난다(B2)
                                         ->  복구 동작이 지워졌다
```

앞이 없으면 뒤는 **통과로 보이는데 아무것도 재지 않는다.** 복구 동작이 설정된
적이 없으면 "되살아나지 않는다" 는 되살릴 것이 없어 참이고, "지워졌다" 는 지울
것이 없어 참이다. 되살림을 보이지 못했으면 B2 는 비교할 것이 없다. **성공처럼
보이는 공백이 가장 나쁘다** — 실패는 눈에 띄지만 이것은 띄지 않는다.

그래서 어느 갈래로 가든 검사 수가 셋으로 고정되고, 채우지 못한 것은
`재지 못했다` 로 남는다.

> **사슬을 되짚다가 진짜 결함을 잡았다.** 채운 것을 `measured` 에 표시하지
> 않아 마지막 그물이 같은 셋을 다시 적었다 — 실패 갈래에서만 **검사가 셋이
> 아니라 여섯**이 됐다. 성공 갈래는 멀쩡했으므로 다음 관리자 실행이 실패했을
> 때에야 드러났을 것이다.
>
> 그 자리에서 일반 규율로 올렸다: `Add-Check` 가 **같은 이름을 두 번 받으면
> 실패 검사로 드러낸다.** 검사가 사라지지 않게 하는 것과 부풀지 않게 하는
> 것은 같은 규율이고, 이제 시나리오와 무관하게 매 실행이 그것을 지킨다.

### 하네스가 찾아낸 것 — 셋

**하네스를 만든 값어치가 여기 있다.** 단위 시험이 전부 초록인 상태에서 셋을
찾았고, 셋 다 실기기에서만 드러나는 것이었다.

**1. `process.kill` 이 PATH 를 타는 실행 경로였다.** `sysinfo` 의 `kill()` 은
Windows 에서 `Command::new("taskkill.exe")` 를 띄운다 — **이름으로** 부르므로
PATH 를 쥔 쪽이 이긴다. 설계-01 D12 가 만든 문(절대 경로·허용 목록·IFEO 확인)을
프로세스 종료만 우회하고 있었다. 파괴 경로에 뚫린 실행 경로이므로 같은 문으로
되돌렸다.

**2. `process.cmdline` 이 언제나 비어 있었다.** `sysinfo::refresh_processes` 의
기본 갱신 종류에 `cmd` 가 없다. **수집기도 같은 함수를 쓴다** — 지금까지 뜬
모든 스냅샷의 `cmdline`·`cmdline_decoded`·`args`·`user` 가 비어 있었다는 뜻이다.
설계-02 가 `cmdline_decoded` 를 둔 이유("인코딩은 은폐 수단이지 실행 방식이
아니다 — 룰이 원문만 볼 수 있으면 `powershell -enc <base64>` 한 줄로 모든 문자열
룰이 무력해진다")가 통째로 성립하지 않고 있었다.

하네스가 이것을 잡은 방식이 요점이다 — `image_path` 술어로는 죽였는데
`cmdline_contains` 로는 못 죽였고, WMI 는 그 명령줄을 보여 주고 있었다.
**가짜 백엔드로는 영원히 드러나지 않는 종류의 결함이다.**

**3. 재평가가 곧바로였다.** 종료 직후에 세면 되살리기가 아직 도착하지 않아
언제나 0건이고, 그러면 실패를 성공으로 보고한다. 실제로 `exit=1`("치료했다")을
내면서 둘 다 살아 있었다. 한 박자(300ms — 실측 소생 간격의 열 배) 쉬고 센다.

### 대상의 모양이 다시 문제였다

P7 이 G6 에서 겪은 것과 같은 자리다. **서비스와 인증서의 대상은 이름이 아니라
레지스트리 키**로 적는다.

| Op | 대상 |
|---|---|
| `service.*` | `HKLM\SYSTEM\CurrentControlSet\Services\<이름>` |
| `cert_store.remove` | `HKLM\SOFTWARE\Microsoft\SystemCertificates\<저장소>\Certificates\<지문>` |
| `process.kill` | **없다.** PID 는 계획에 들어갈 자리가 없고 술어가 그 자리를 대신한다 |

이름 하나짜리 문자열(`EvilSvc`)로 적으면 보호 목록 대조도 G6 의 상한 판정도
걸리지 않는다 — 둘 다 대상의 **모양**을 보고 갈리기 때문이다. 그리고 인증서는
실제로 레지스트리 키 하나이므로(수집기가 거기서 읽는다) 이 표기가 곧 사실이다.

부수 효과로 셋이 같은 기계를 쓴다 — `registry.delete_key`·`cert_store.remove`·
`service.*` 의 백업·복원이 전부 "키 하위 트리 하나" 다. 라벨(`EntryKind`)만
Op 이 정한다.

### 레지스트리 보호 목록이 여기서 처음 필요해졌다

P7 까지의 레지스트리 Op 은 **값 하나**만 건드린다. `registry.delete_key` 는
다르다 — 키 하나를 지우면 그 아래 전부가 함께 사라진다. 규칙은 파일 쪽과 같은
두 겹이다: **목록에 적힌 키 자체는 지울 수 없고, 그 하위의 개별 키는 지울 수
있다.** 악성코드는 실제로 이 아래에 자기 항목을 만들며(IFEO 하이재킹), 부모를
통째로 막으면 첫 플러그인부터 동작하지 않는다.

### 결정 — `dir.delete_recursive` 는 P10 으로 옮긴다

검증 목록의 "재귀 삭제: **신뢰 서명 파일 존재 시 거부**" 를 만족할 수단이 없어
이 Op 은 언제나 거부됐다. 미루지 않고 결정했다.

**1. 지금 만들면 가드가 없는 것보다 나빠진다.**

`yara-x` 가 이미 워크스페이스에 있고 Authenticode 파서를 갖고 있으므로
"`unsafe` 없이는 불가능" 은 정확하지 않다. 문제는 그 `verified` 가 무엇을
뜻하느냐다 — 체인을 *"self-signed 인증서를 만나거나 PE 안에 없는 인증서를
만날 때까지"* 검증하고 **그 마지막 인증서를 언제나 유효한 것으로 친다**
(`yara-x/src/modules/pe/authenticode.rs`). 즉 **자기서명이 통과한다.** 그것을
"신뢰 서명" 으로 쓰면 악성코드가 스스로 서명하는 것만으로 삭제에서 빠지고,
가드가 공격자의 도구가 된다.

제대로 하려면 체인을 **이 기계의 신뢰 루트**에 앵커해야 한다. 루트 저장소는
이미 읽고 있으므로(`certstore.rs`) 재료는 있지만, 남는 것은 X.509 경로
검증기를 손으로 쓰는 일이다. 반쯤 만든 경로 검증기가 내놓는 거짓 "신뢰함" 은
**조용한 화이트리스트**다. 폐기 확인(CRL/OCSP)은 네트워크라 D8 로 막혀 있고,
설계-03 미결 사항이 이미 *"2층 신뢰 서명 검증의 오프라인 동작 범위 — 플랫폼
API 실증 후 확정"* 이라고 적어 두었다. **설계가 이 질문에 답한 적이 없다.**

**2. 이것은 §4 조건 하나가 아니라 설계-03 §3 2층 전체다.**

2층은 재귀 삭제 전용 가드가 아니라 *모든* 삭제에 걸리는 화이트리스트 층이다.
지금 그 층은 통째로 없고, 세 곳이 그것을 참조하며, 어느 Phase 에도 없다.
자세한 것은 설계-03 §3 의 "2층은 아직 없다" 를 보라.

**3. 그래서 Op 을 P10 으로 옮긴다.**

`implemented_in` 을 P10 으로 두면 계획기가 *"P10 에 온다"* 로 미루고
(`deferred`), 실행기·복원기·왕복 시험은 그대로 남는다. 이것이 "정의는 전부,
구현은 점진적으로" 가 원래 다루려던 상황이다 — **능력이 틀린 것이 아니라
그것을 안전하게 만드는 재료가 아직 없다.**

잃는 것은 크지 않다. §4 자신이 *"2번이 핵심이다"* 라고 적은 대로 재귀 삭제의
주 가드는 **증거 파생 경로 + 그 안의 악성 판정**이고 둘 다 살아 있으며,
`registry.delete_key` 가 같은 가드를 받으므로 그 코드도 P8 에서 계속 돈다.
이 Op 이 더하는 것은 "스냅샷이 판정하지 않은 잔여물까지 지우는 것" 이고, 그
증분을 위해 반쯤 만든 신뢰 판정을 들이는 것은 값이 맞지 않는다.

**기각한 대안**

| 대안 | 왜 아닌가 |
|---|---|
| 카탈로그에서 뺀다 (D11 식) | 능력이 틀린 것이 아니라 가드가 없는 것이다. `network_conn` 은 "지울 Op 이 없어서" 뺐다 — 이유가 다르다 |
| `yara-x` 의 `verified` 를 그대로 쓴다 | 자기서명이 통과한다. 가드가 아니라 우회로다 |
| "등록된 `InstallLocation` 이면 거부" 로 대체 | 스냅샷이 답할 수 있지만, EvilAI 류는 **설치된 앱으로 위장하려고 언인스톨 항목을 등록한다.** 정작 지워야 할 것을 막는다 |
| 미판정 파일 비율 상한 | 임의 상수. 악성 디렉터리에도 미판정 파일은 많다 |
| 그대로 두고 `phase/P8` 태그를 단다 | 검증 목록 한 줄이 거짓이 된다 |

### `service.stop` 은 되돌릴 수 없다

카탈로그가 `reversible: true` 로 적고 있었다. 설계-03 §2 는 **"불가 / 없음(상태
기록)"** 이다. 정지는 상태 변화이고 정의는 그대로 남으므로 담을 것이 없다 —
담아 둔 정의를 되돌려도 다시 시작되지는 않는다. **G2 왕복 표가 "되돌릴 수
있다면서 컨테이너를 만들었다" 로 잡았다.**

## P9 — 첫 플러그인과 사후 흐름

**산출**: `evilai-locust`, `verify`(재수집+재평가), `resume`(재스캔 금지), **안전 모드 가용성·부팅 건전성 선행 점검**, `remedy-report`(계획 렌더러·결과 리포트·**i18n ko/en**), **자립률 지표 집계**

### 착수 전 점검 — 첫 플러그인 초안을 실제로 돌려 봤다

종이로 "될 것 같다" 를 보는 대신 `docs/design/예시-EvilAI-플러그인.md` 의
`plugin.yaml` 을 그대로 뽑아 `lint` 와 `plan` 에 넣었다. **네 가지가 조용히
비어 있었고, 그중 셋은 첫 플러그인이 실제로 밟는 자리였다.**

| | 무엇이 비어 있었나 | 어떻게 드러났나 |
|---|---|---|
| A | **`signature` 는 P10 까지 언제나 비는데 아무도 말하지 않았다** | 코퍼스 파일 레코드 5532건 중 `signature` 키를 가진 것 **0건**. lint 통과, `issues` 도 비어 있었다 |
| C | `Subject::Persistence` 가 택일이라 **`persistence.delete` 가 계획되지 않았다** | 서비스에서 고친 것과 같은 구조. 예제 ex01 은 `remediate` 가 없어 `actions: []` 라 잡지 못했다 |
| D | `verify.after_reboot: true` 를 **읽는 곳이 없었다** | `grep` 결과 `manifest.rs` 한 줄뿐 |
| E | `include_descendants` 를 **매니페스트가 요구할 길이 없었다** | P8 에서 실행기 쪽만 만들었다 |
| **F** | **`process.kill` 이 어떤 계획에도 들어갈 수 없었다** | 아래 |

**A 가 가장 무겁다.** EvilAI 의 오탐 방어 두 줄 중 하나가
`file(command).signature.subject equals "Microsoft Corporation"` 인데,
그 술어는 조용히 거짓이 된다. **`exclude` 에 있으므로 제외가 일어나지 않고,
조용히 더 공격적인 쪽으로 무너진다** — 작성자는 있다고 믿는 방어가 없다.

`Subject::NOT_POPULATED_YET` 을 두어 lint 가 작성 시점에 경고하고 `evaluate`
가 `scan.json` 의 `issues` 에 남긴다. **린트는 건너뛸 수 있고 실행하는 사람은
매니페스트를 읽지 않으므로**, 산출물이 홀로 읽혀야 한다는 요구(설계-03 §1)를
지키려면 두 자리 다 필요하다. 판단은 한 함수(`unpopulated_field_uses`)가
하고 둘이 그것을 읽는다 — 두 자리에 적으면 갈라진다.

#### F — `process.kill` 이 계획될 수 없었다

E 를 확인하려고 프로세스 증거로 계획을 내 보다가 드러났다. **두 가지가 함께
빠져 있었다.**

1. `ProcessRecord` 에는 `path`·`source`·`id` 가 없어 `target_of` 가 `None` 을
   주고, remove arm 이 그 자리에서 Action 을 버렸다.
2. `locator` 에 프로세스 분기가 없어 술어가 실리지 않았고, 실렸더라도 G6 이
   "무엇을 종료할지 계획이 말하지 않았다" 로 막았을 것이다.

**대상이 비는 것이 정상이다.** PID 는 계획 시점과 실행 시점 사이에 바뀌므로
계획에 들어갈 자리가 없고(설계-03 §1), 대신 술어가 고정한다. G6 의 상한
검사도 `target` 이 없으면 건너뛴다 — 프로세스에는 `scan_roots` 에 대응하는
것이 없다.

그래서 P8 의 process.kill 작업 전부(하네스 승리·보호 프로세스 제외·계보
확장)가 **실제 플러그인에서는 닿을 수 없는 자리에 있었다.** 서비스 차례
때와 같은 종류의 공백이고, 같은 방식으로 드러났다 — 실제로 돌려 보니 나왔다.

#### 남은 것 — 착수 전 결정이 필요하다

#### 코퍼스를 넓혔다 — 그리고 더 큰 구멍이 나왔다

`Win10x64-Test` 에 Node/VS Code 를 설치하고 스냅샷을 다시 떴다. 절차는
`testbed/harness/host/New-CorpusSnapshot.ps1` 에 넣었다 — **손으로 뜨면
스크러빙을 언젠가 빠뜨리고, 그러면 기계 이름이 저장소에 실린다.**

| | 전 | 후 |
|---|---|---|
| 스냅샷 | 3 | **7** |
| 파일 레코드 | 44,445 | **101,420** |
| 커버되는 subject | 2 (`file`·`persistence`) | **5** (+`autorun`·`process`·`av_exclusion`) |

**subject 쪽이 진짜 구멍이었다.** `collect --root` 만 주면 진단 모드이고,
진단 모드는 `Scope::diagnostic` 이 정한 대로 `file` 과 `persistence` 만
모은다. 기존 코퍼스 셋이 전부 그 모드였다 — 즉 EvilAI 가 선언한 다섯 subject
중 **셋은 G1 이 태울 레코드가 한 건도 없었다.**

실측으로 보였다. 최상위 `autorun` 룰 하나를 일곱 스냅샷에 돌리면 새로 뜬
`declared` 한 곳만 16건을 실제로 훑고 나머지 여섯은 훑을 것이 없다.
`collect --plugin` 으로 뜬 스냅샷이 그 자리를 채운다.

> **그래도 EvilAI 의 `exclude` 는 여전히 태워지지 않는다.** 그 룰 트리는
> `task` 하나에 매달려 있고, `task` 는 `\Microsoft\Windows\` 아래에서
> `node.exe` 가 `.js` 를 도는 예약 작업을 찾는다. 실측: 218개 작업 중 그런
> 것은 **0건**이고, 정상 기계에는 있을 이유가 없다. `exclude` 는 룰이 발화한
> **뒤에야** 의미가 있으므로 청정 코퍼스로는 원리상 닿지 않는다 — 그것은
> `corpus/infected/` 의 몫이다 (설계-04 §3.2).
>
> 넣은 것이 산 것은 **파일 표면**이다. nodejs 하위 1,987건과 VS Code 트리가
> 이제 G1 안에 있다.

첫 플러그인의 YARA 룰은 실검체 3건 이상을 요구하므로(`condition: false` 스텁),

| `verify` (재수집 + 재평가) | **끝** |
| `resume` (재스캔 금지) | **끝** |

#### 재시작을 권하기 전에 읽는다

실행기가 `process.kill` 실패 문구에 **"안전 모드에서 다시 시도할 것"** 을 달고
있었다. 아무 확인 없이. 그것이 설계-00 §6 이 지목한 결함 그 자체다 —
악성코드가 `SafeBoot` 키를 지워 두었으면 그 안내가 부팅되지 않는 컴퓨터를
만든다.

이제 **실행기는 무슨 일이 있었는지만 적고**, 권할지는 CLI 가 부팅 건전성을
읽은 뒤에 정한다. 판정은 `remedy-platform` 한 곳에 있다 — 수집기는 관찰로,
실행기는 권하기 전에 같은 것을 묻는데 `remedy-apply` 는 `remedy-collect` 를
의존할 수 없으므로(설계-04 §1) 양쪽에 적으면 갈라진다.

`Partial`(둘 중 하나만 있음)도 권하지 않는다. 온전하지 않은 안전 모드는
들어갔다가 못 나오는 자리를 만든다. 반대로 **복구 환경을 "모르는 것" 은 막지
않는다** — BCD 가 마운트되어 있지 않아 지금은 모든 기계가 그렇고, 그것까지
막으면 재부팅 제안이 통째로 사라진다.

#### `verify` 는 경로 확인이 아니다

"제거한 경로가 여전히 비어 있는가" 만 보면 **랜덤 이름을 쓰는 위협 앞에서
무력하다.** 그래서 수집과 평가를 다시 돌려 판정이 재현되는지 본다.

```
  판정 없음 · 다 봄    -> 치료 성공     (exit 0)
  판정 없음 · 다 못 봄 -> 확인 못 함    (exit 6, 2026-10-26)
  다시 판정됨          -> 재발          (exit 2, 자동 재치료 안 함)
  원래 증거만 잔존     -> 부분 치료     (exit 3)
```

**판정이 먼저다.** 증거 id 가 전부 새것이어도 판정이 서면 재발이다 — 재감염은
다른 경로에 다른 id 로 생기므로 증거 대조로는 잡지 못한다. 그리고 치료 전
증거(`--run`)를 모르면 "일부만 잔존" 을 **주장하지 않는다.**

**다 보지 못한 재평가는 0 이 아니다** (결정 2026-10-26). `scan` 의 6 과 같은 규칙으로
찾은 것(2 · 3) 다음, 성공(0) 앞에 선다. 그 전에는 재부팅 뒤 사람 없는 회차가 잘리거나
막힌 채로도 *"치료가 유지됐다"* 고 적었다(설계-03 §8).

#### `resume` 은 절대 재스캔하지 않는다

재부팅 뒤에 이것을 부르는 쪽에는 사람이 없다 — 그래서 계획을 인자로 받지
않는다. 그런데 **계획이 저장되지 않고 있었다.** `apply` 가
`<state>/plan/<run_id>.json` 에 남기게 했다(`journal_path` 와 같은 규약).
저널의 `plan_sha256` 이 짝을 판정하므로, 저장된 것을 다시 넣으면 "다른
계획이다" 가 아니라 "이미 수행됐다" 가 나온다.

#### `remedy-report` — 부작용을 목록보다 먼저

**순서가 규격이다** (설계-01 D5). 브라우저 확장을 제거하려면 브라우저를
종료해야 하고 그러면 저장하지 않은 작업이 사라진다 — 삭제 목록만 보여 주고
그것을 말하지 않으면 승인은 정보에 근거한 것이 아니다. 렌더러가
`user_impact` 를 목록 **앞에** 놓는다.

CLI 가 문구를 직접 만들지 않는다. 만들면 그 문구가 사실상 API 가 되고, 고칠
때마다 파싱하는 쪽이 깨진다. 기계가 읽는 것은 NDJSON 과 JSON 이다.

**`--lang ko|en`** (없으면 `REMEDY_LANG`, 그것도 없으면 한국어). 파일 출력은
언어와 무관하게 **UTF-8 고정**이고 BOM 을 붙이지 않는다 — 콘솔 코드페이지에
맞춰 쓰면 리다이렉트했을 때 깨지고, BOM 을 붙이면 파서가 거부한다.

> **알려진 한계 — 번역되는 것과 지나가는 것.** 렌더러는 **제가 만든 문장만**
> 번역한다. `DeferredItem.reason` · `ActionResult.error` · `ScanBody.issues` 는
> 계획기·실행기·평가기가 쓴 그대로의 자료이고, 임의 문자열을 번역할 방법은
> 없다. 진단문 전체를 구조화된 코드로 바꾸는 것은 SDK 전반의 결정이라 P9 의
> 크기가 아니다.
>
> **CLI 자신의 문구도 아직 한국어뿐이다** (91곳). 이것도 감추지 않는다 —
> 보안 도구의 문구는 서둘러 옮길 것이 아니다. 시험이 이 경계를 못 박는다.

#### 자립률 — `cargo xtask metrics`

> **플러그인 자립률** = 새 위협 대응 건수 중 코어 수정 없이 완료된 비율
> (설계-01 D10)

입력은 `apply` 가 남긴 `<state>/plan/<run_id>.json` 이다 — `resume` 이 찾는
그 자리. **따로 지표용 파일을 만들지 않는다.** 만들면 그것을 쓰는 코드와
실제 실행이 갈라지고, 그러면 지표가 실행을 반영하지 않는다.

제품 CLI 가 아니라 `xtask` 인 이유: 한 실행의 성질이 아니라 **추세**다. 계획
하나만 보면 0% 아니면 100% 라 아무것도 말해 주지 않는다. 하위 명령 표
(설계-01)에도 이런 명령이 없다. **`all` 에도 넣지 않는다** — 값이 낮다고
빌드를 멈추면 지표가 아니라 게이트다 (설계-03 §7).

실측:

```
자립률: 67% (2/3 계획이 코어 수정 없이 끝난다)
  파괴 동작이 없다 : 1
  막고 있는 Op (많은 순):
    dir.delete_recursive  1
```

**세 범주 중 하나만 셀 수 있다는 사실을 감추지 않는다.** 미룸이 Op 을 이름으로
들기 때문에 지금 세어지는 것은 `파괴 동작이 없다` 뿐이다. 관찰 대상이 없거나
로직을 표현할 수 없는 경우는 룰을 **쓸 수조차 없어** 계획까지 오지 못한다.
그 둘의 입력은 사람이 적는 목록이고, 그것이 P9 의 "없어서 불편한 API 목록
문서화" 다. 도구가 그 사실을 출력에 적는다.

그리고 **재지 않은 것을 0% 로 접지 않는다.** 표본이 없는 실행이 "자립률 바닥"
으로 읽히면 그 수치가 사람을 잘못된 곳으로 보낸다.

#### 검체를 확보했다 — 룰을 채우고 오탐을 실측했다

해시를 모르는 상태에서 시작해 엔진명으로 추적했다. EvilAI = VT **`meadowlocust`**
이고, 결정적 근거는 샌드박스 행위
`"C:\Program Files\nodejs\node.exe" "…\preload.js"` 가 첫 플러그인의 detect
규칙과 그대로 맞는다는 것이다. JS 16건 + PE 2건을 받았다.

검체는 전부 obfuscator.io 계열 난독화이고 **평문 IOC 가 0건**이었다. 대신
커스텀 base64 알파벳이 키 없이 남아 있어 정적으로 풀리고, 풀면
`createDecipheriv`·`aes`·`zlib` 가 나오는 AES+zlib 로더다.

**군집을 전제하지 않았다.** 쌍별 겹침만 재서 셋이 나왔다 — 소형 로더 8건(공유
상수 90), 대형 번들 3건(고유 상수 11), 상수를 공유하지 않는 rc4 계열 5건.
임계값은 `밖 최대 < T ≤ 안 최소` 를 단언으로 걸고 정했다.

> **그 단언이 사고를 하나 잡았다.** 군집 정의를 바꾸면서 공유 상수가 90→12 로
> 줄었는데 임계값은 20 그대로여서, **절대 참이 될 수 없는 검사**가 되어 있었다.
> 그때 나온 `0/11 적중` 은 "안 맞았다" 가 아니라 **"잴 수 없었다"** 였다.
> P8 하네스에서 반복해 나온 것과 같은 종류다.

실측 — 전부 제품 엔진(`remedy-yara`)으로 쟀다:

| | 결과 |
|---|---|
| 탐지 | **16 / 16** |
| 오탐 — 호스트 청정 `.js` | **0 / 25,863** |
| 오탐 — VM 청정 `.js` (Defender 실시간보호 켠 상태) | **0 / 3,750** |
| 오탐 — 타 패밀리 검체 25종 | **0 / 625** |
| 못 훑음 | 세 측정 모두 **0건** |

**VM 에 검체는 올리지 않았다.** YARA 는 정적 매칭이라 실행이 필요 없고, 오탐
시험에 필요한 것은 청정 파일뿐이다. 올린 스캐너·룰은 복사 후 SHA-256 을
재확인해 백신이 먹지 않았음을 확인했다 — 삼켜진 것을 모르고 지나가면 그 뒤
결과가 전부 헛것이 된다.

**엔진 제약 하나를 찾았다.** 같은 문자열 리터럴이 한 `.yar` 의 두 룰에
중복되면 yara-x 가 컴파일 중 스택을 넘긴다. 단독은 정상이고 합성 문자열로는
90+23 조합도 정상이므로 개수가 아니라 중복이 원인이다. 컴파일이 안 되면 룰이
틀린 게 아니라 **전부 미평가**가 되고, 그 상태의 "오탐 0건" 은 거짓이다.
플러그인 작성 가이드(P11)에 넣을 것.

도구는 `cargo xtask yara` 다. **안 맞았다 / 못 훑었다 / 안 봤다 를 섞지 않는다** —
`--expect clean` 인데 못 훑은 파일이 있으면 오탐이 0건이어도 실패로 끝낸다.
첫 실행에서 그 동작이 21건 미스캔을 잡았다. 훑을 파일이 0개여도 실패한다.

#### 검체가 문서 하나를 뒤집었다 — 서명

설계-03 §3 2층과 설계-04 §2 는 "EvilAI 계열은 정상 코드서명 인증서로 서명된
AI 앱으로 위장" 을 전제로 `signed_malware` 열거를 요구했다. **확보한 검체에서
그것을 확인하지 못했다** — `engines:meadowlocust tag:signed` 0건, 구성원 40건
개별 조회에서 `signature_info.subject` 보유 0건, 받은 PE 2건은 파일 바이트에서
인증서 테이블 크기 0.

"서명되지 않는다" 로 단정하지는 않았다. 확보한 것은 detect 규칙과 행위가
일치하는 군집이고, 공개 보고가 말하는 서명된 설치 파일 단계가 그 라벨을 달지
않았을 수 있다. **못 봤다와 없다를 섞지 않는다.** 세 문서를 그렇게 고쳤다.

귀결: `signed_malware` 를 **비워 둔 채로 플러그인을 완성한다.** 목록이 곧
플래그이므로 비어 있으면 예외가 없고, 서명된 대상을 만나면 2층이 삭제를 막고
보고한다 — 근거 없이 열거를 지어 넣는 것보다 옳은 실패 방향이다.

#### 매니페스트 — 초안에서 세 군데를 고쳤다

`plugins/evilai-locust/plugin.yaml` 이다. 초안(`docs/design/예시-EvilAI-플러그인.md`)
을 그대로 옮기지 않고 셋을 바꿨다.

**(1) 프로세스 규칙을 넣었다.** 초안은 `subjects` 에 `process` 를 선언해 두고
쓰는 규칙이 없었다 — 권한 상한만 넓히고 아무 능력도 얻지 못하는 상태이자,
finding F 가 지적한 "P8 의 process.kill 작업이 실제 플러그인에서는 닿을 수 없는
자리에 있다" 그 자체다. 규칙 하나로 둘 다 해소된다.

```yaml
- id: payload-process
  subject: process
  where:
    all:
      - { field: image_path, op: matches,  value: '(?i)\\node\.exe$' }
      - { field: args,       op: contains, value: "${task.payload_dir}" }
```

> **필드 이름이 subject 마다 다르다.** 프로세스에는 `command` 가 없다 —
> `image_path` 다(예약 작업은 `command`). 역검증에서 이 자리를 `command` 로
> 바꿔 보니 `process.kill` 이 계획되지 않아 시험이 실패했다. 조용히 미매치가
> 되는 자리라 시험 없이는 드러나지 않는다.

좁히는 것은 두 번째 조건이다. `payload_dir` 는 악성으로 판정된 작업에서 나온
경로이므로, 그 경로를 인자로 물고 있는 node 프로세스만 대상이 된다.
`verdict` 에는 넣지 않았다 — 재부팅 직후처럼 돌고 있지 않은 순간이 있고,
그때 판정이 서지 않으면 치료할 수 없다.

**(2) `signed_malware` 를 비웠다** (위 서명 항목).

**(3) 근거 없는 `collect_extra` 를 뺐다.** 초안의
`${task.payload_dir}/config.json` 은 검체에서 근거를 찾지 못했다(평문 IOC 0건).
없는 것을 선언해 두면 감염마다 "선언한 것을 못 봤다" 가 보고돼 **진짜 미해소
항목이 그 소음에 묻힌다.**

**검증** — `plugin lint` 오류 0 · 경고 2(둘 다 알려진 것: P10 서명 필드,
재부팅 자동 재평가). G1 은 플러그인 축을 붙여 7개 청정 스냅샷 전부 무판정.
감염 픽스처에서는 `process.kill`(2단계) → `persistence.disable`(3단계) →
`persistence.delete`·`autorun.remove` 순으로 계획되고, `dir.delete_recursive` 는
P10 이라 **미룸으로 보고된다.**

역검증으로 시험이 공허하지 않음을 확인했다 — 룰 이름 오타 · 치료에서 프로세스
제거 삭제 · 프로세스 필드를 `command` 로 · YARA 임계값 20→90, 네 가지를 각각
넣어 보니 전부 실패했다.

> 감염 픽스처의 페이로드 바이트는 **룰 파일에서 만든다.** 저장소에 악성코드를
> 넣지 않으면서 룰이 실제로 발화하는지 볼 수 있고, 상수를 시험에 베껴 두었을
> 때 룰만 고쳐 조용히 어긋나는 일도 막는다. 룰의 **정확도**는 여기서 재지
> 않는다 — 그것은 실검체가 필요하고 `cargo xtask yara` 의 몫이다.

한 가지가 픽스처 오류로 드러났다: `AvExclusionRecord.source` 는 짧은 이름이
아니라 **전체 레지스트리 키**다(`HKLM\SOFTWARE\Microsoft\Windows Defender\
Exclusions\Paths`). 계획기가 `source\value` 로 대상을 만들고 G6 이 그것을
레지스트리 값 경로로 대조하므로, 짧은 이름을 넣으면 계획 전체가 G6 에서 막힌다.

> 줄이 아무것도 거르지 못하고 있어 제거했다.** 배선 자체는 살아 있다(악성

> 레코드가 아예 없다.

> `C:\Program Files\nodejs\node.exe` 를 그대로 실행하므로, 서명 주체를

> `apply → restore → 재부팅 → verify` 를 한 세션에 돈다. 통과 9 · 실패 0 ·
> 미실증 3.

> 실측에서 `System32` 27,614개 중 548개가 접근 거부(SYSTEM 전용 하이브 트랜잭션
> 로그)이거나 다른 프로세스가 열고 있었다. 대신 **수와 사유를 기록**하고, 사유가
> 우리 설정(크기 상한 등)이면 조정해 다시 훑는다.
>
> **그 구분이 실제로 값을 했다.** 1차 측정(상한 256MB)에서 26건이 크기 상한에
> 걸렸는데 — `msedge.dll` 342MB 같은 것들이다 — 그것을 남겨 두면 "안 봤다" 를
> "안 맞았다" 로 흘리는 것이다. 상한을 1GB 로 올려 35분을 다시 돌려 0 으로 만들었다.
> 최종: **정상 파일 274,498개 · 오탐 0건 · 크기 상한 탓 미측정 0건**
> (`plugins/evilai-locust/RELEASE.md`).
>
> **VM 전체 스캔은 접었다.** 테스트 VM 의 `C:\` 는 파일이 **292만 개**이고,
> Defender 실시간보호와 알약이 모든 읽기를 가로채 8시간을 돌고도 끝나지 않았다.
> 호스트 24만 개로 판정이 서므로 그 이상은 비용만 크다 — 코퍼스를 키우려면
> **정적 트리를 골라** 더할 것.
>
> **자립률의 첫 값이 나왔다 — 1건 중 0건(0%).** 첫 플러그인은 코어 수정 없이
> 완료되지 못했다(계획기의 `autorun` 대상 생성 누락). 그리고 **그 미달 사유가
> D10 의 세 범주 어디에도 없다** — 사유는 "없어서 못 했다" 가 아니라 "있는데
> 틀렸다" 였다. 미달 사유에 네 번째 범주("코어 결함")를 둘지는 설계-01 D10 을
> 손대는 일이라 별건으로 남긴다. 막힌 자리는 8건이고, 과광범위 린트 오경보율은
> 표본 5개 · 경고 1건 · 오경보 0건으로 임계값을 유지했다.
>
> 그 조사에서 하나가 더 나왔다 — **설계-06 §7 이 요구한 과광범위 검사 다섯 중
> "재귀 삭제 대상이 사용자 홈 직하" 가 구현되어 있지 않다.** `evilai-locust` 가
> 이미 `recursive: true` 를 쓰고 그 매니페스트 주석이 정확히 이 린트가 잡아야 할
> 위험을 우려한다. 태울 대상이 하나뿐이고 통과하므로 `dir.delete_recursive` 가
> 열리는 P10 에서 함께 볼 것.
>
> **항목 4 는 막혀 있다 — 그리고 2026-08-31 에 열렸다.** 아래는 그때까지의
> 판단이고, 두 근거가 모두 실측으로 반증됐다.
>
> > 항목 4 는 구조적으로 막혀 있다. SafeBoot 하위 키는 관리자·SYSTEM 모두
> > 삭제가 거절되고(소유권 획득 필요), 더 근본적으로 `advise_restart` 의
> > 진입 조건(`reboot_required || failed() > 0`)을 이 플러그인 구성으로는
> > 만들 수 없다 — 파일을 잠가 실패를 유도해도 백업 단계 가드에 먼저 걸린다.
>
> **진입 조건은 만들 수 있다.** 잠금의 *공유 모드* 문제였다. `FileShare.None`
> 은 백업 단계의 읽기까지 막아 파괴 전 통째 중단(exit 5)이 되고 `failed` 가
> 0 인 채 끝나지만, `FileShare.Read` 면 백업은 읽히고 삭제만 막혀 실행 단계
> 실패가 생긴다(exit 3). 인자 하나다.
>
> **삭제가 막히는 것은 `SafeBoot` 때문이 아니다.** `SafeBoot`·`Minimal`·
> `Network` 는 Administrators 가 `KA` 이고 그 아래 새 키를 만들고 지우는 것도
> 된다. 잠긴 것은 **기존 자손**이다 — `Network\AFD` 등은 소유자가
> `NT SERVICE\TrustedInstaller` 이고 DACL 이 `D:PAI`(상속 차단)로
> Administrators 에게 `KR` 만 준다. `DeleteSubKeyTree` 는 모든 자손을
> read+write 로 열어야 하므로 첫 자식에서 멈추고, .NET 은 그것을 *"하위 키가
> 없다"* 로 옮겨 원인을 가린다.
>
> 하네스는 지우는 대신 **`Minimal` 하나를 가린다**(`Deny Everyone ReadKey`).
> 제품이 보는 `key_exists` 는 열리지 않는 키를 없는 것으로 읽으므로 판정이
> `SafeBoot::Partial` 이 되고, **그 값은 둘 중 하나만 보이는 기계에서만
> 나온다** — 출력의 `진입 가능 여부: partial` 이 판정이 실기기를 읽었다는
> 증거다.
>
> G2·G4 의 정의가 "**감염 스냅샷에서** `apply`" 다(설계-03 §10 게이트 표):
> G2 는 `apply → restore` 가 원본을 되돌리는가, G3 는 `apply` 중 계획에 없던
> Action 이 0 인가, G4 는 `apply` 후 **재부팅** → `verify` 에서 지속성 잔존·
> 재생성이 0 인가. 셋 다 **실제로 감염된 기계에서 치료를 실행해야** 재진다.
> 무해한 픽스처 위에서 도는 기존 P6·P8 하네스로는 닿지 않고, 저장소의
> `g2_roundtrip.rs` 계열이 재는 것은 **Op 단위 왕복**(P7)이라 감염 전체 왕복과
> 다르다.
>
> `New-InfectedSnapshot.ps1` 은 감염을 세우지만 스냅샷을 뜬 뒤 **스스로
> 되돌린다** — 코퍼스를 뜨는 것이 목적이었기 때문이다. 치료를 재려면 그 상태를
> **유지한 채** `apply → restore → 재부팅 → verify` 를 돌아야 한다. 감염 구성
> 로직은 이미 있으므로 그것을 재사용하는 하네스 하나가 3·4·5 를 함께 연다.
> 항목 5 의 "랜덤 폴더명이 바뀐 재감염" 도 같은 세션에서 폴더명만 바꿔 두 번째
> `verify` 를 돌리면 된다.

#### 아직 저장소 밖에 있는 것

- **G9 의 코퍼스는 저장소 밖에 있다** (설계-03 §7). 정상 파일 트리도 악성 검체도
  저장소에 넣지 않는다. 스캔 경로를 인자로 받으므로 CI 에는 넣지 않는다 — 없을 때
  조용히 넘어가면 "재 봤다" 와 "잴 것이 없었다" 가 같아진다. 그래서 **무엇을
  얼마나 훑었는지를 릴리스 기록에 적는다**(설계-03 §10).
- `dir.delete_recursive` 가 P10 이라 **첫 플러그인은 페이로드 디렉터리를
  지우지 못한다.** 작업·Run 키·예외 목록은 제거되고 페이로드는 격리되므로
  위협은 돌지 않지만, 빈 디렉터리가 남는다. 미룸으로 보고된다.

**검증**
- **G1~G4 전체**가 스냅샷·VM에서 통과
- **G9 수동 게이트** — 가용한 최대 정상 파일 코퍼스에 전수 스캔, 오탐 0건. 규모와 못 훑은 수·사유를 릴리스 기록에 첨부
- **`SafeBoot` 를 손상시킨 VM에서 안전 모드를 제안하지 않고 손상을 보고한다**
- 랜덤 폴더명이 바뀐 재감염을 `verify` 가 잡는다 (경로 확인만으로는 못 잡는 것도 확인)
- 계획 렌더러가 `user_impact` 를 삭제 목록보다 **앞에** 표시한다
- **한국어·영어 출력이 모두 나오고 파일 출력은 UTF-8 고정**(설계-00 §5-2)
- 과광범위 린트 **오경보율 재확인**
- **"없어서 불편한 API" 목록 문서화** — 자립률 지표의 첫 입력

## P10 — 신뢰와 배포

**산출**: `remedy-trust`(서명 검증·폐기 목록·`min_plugin_version`·역행 금지), CLI `plugin verify`·`revocation import`·`revocation verify`·`support-bundle`, **`xtask sign`**(서명 생성), 코어 코드서명·자기무결성

> **2026-08-26 정정 — `revocation fetch` 를 뺐다.** 설계-03 §6 이 그 이름을 적었으나 HTTP 를 배포 바이너리에 링크하는 일이고 D9 가 치료 경로의 네트워크를 막는다. 대신 반입한 목록을 사람이 읽어 보는 `revocation verify` 가 들어왔다 — 무엇을 반입하는지 보지 않고 넣는 것보다 낫다. 폐기 메커니즘은 `import` 하나로 완결이다.

> **2026-08-25 정정 — 서명 생성은 CLI 가 아니다.** 이 줄은 원래 CLI `plugin sign` 을 적고 있었다. 서명 방식을 확정하며 실측한 결과(설계-01 미결 5), 서명기 `minisign` 은 `rpassword`·`scrypt`·`salsa20` 을 끌어온다 — **개인키를 풀고 사람에게 암구호를 묻는 도구**의 의존성이다. 치료 도구가 그것을 링크할 이유가 없고, 고객 기계에서 도는 바이너리가 서명할 수 있으면 그 능력이 곧 공격 표면이다(D7 과 같은 논리). 그래서 서명은 `cargo xtask sign`, 검증만 제품이 한다. 검증기 `minisign-verify` 는 **의존성이 0 개**라 배포 표면이 늘지 않는다.

**여기서 함께 오는 것 — 설계-03 §3 2층 (신뢰 서명 검증)**

우리 플러그인의 서명을 검증하는 것과 **남의 파일의 Authenticode 를 검증하는
것**은 다른 일이다. 둘 다 "신뢰" 이고, 2층이 없으면 `signed_malware` 예외도
`dir.delete_recursive` 도 서지 않으므로 **같은 Phase 에 둔다.**

> **2026-08-25 정정 — 근거가 "재료 공유" 는 아니다.** 이 자리는 원래
> *"필요한 재료(PKCS#7 파싱·X.509 경로 검증·신뢰 루트 앵커)가 같다. 두 번 만들
> 것이 아니므로"* 를 근거로 들었다. 서명 방식을 확정하고 재료를 실제로 대 보니
> **겹치는 코드가 없다.**
>
> | | 우리 플러그인 서명 (확정) | 남의 파일 Authenticode |
> |---|---|---|
> | 서명 구조 | Ed25519 두 개 (minisign) | PKCS#7 `SignedData` |
> | 신뢰 앵커 | 우리 공개키 하나 (바이너리 내장) | 이 기계의 루트 저장소 |
> | 경로 검증 | 없다 — 직접 서명이다 | X.509 체인 검증이 본체다 |
> | 알고리즘 | Ed25519 + BLAKE2b | RSA·ECDSA + SHA-1/SHA-256 |
>
> X.509 를 읽는 코드는 오히려 다른 곳에 이미 있다 — `remedy-collect/src/certstore.rs`
> 가 순수 Rust DER 파서로 인증서 주체·발급자·만료를 읽는다(343줄). 2층에서
> 재사용할 것은 그쪽이다.
>
> **근거를 바로잡아야 순서를 정할 수 있다.** 재료를 공유한다면 함께 만들어야
> 하지만, 아니므로 규모가 확실한 쪽을 먼저 끝낼 수 있었다.

- `FileRecord.signature` 를 실제로 채운다 — 지금은 언제나 `None` 이다
- 신뢰 판정을 **이 기계의 루트 저장소**(`certstore.rs` 가 이미 읽는다)에 앵커한다.
  파싱만으로 "신뢰함" 이라고 말하지 않는다 — 자기서명이 통과한다
- 오프라인 동작 범위를 확정한다 (설계-03 미결). **폐기 확인은 네트워크이므로
  D8 이 막는다** — 못 하는 것을 못 한다고 적는다
- `dir.delete_recursive` 가 이때 열린다 (설계-09 §3.2)

**검증**
- **G8**: 미서명·변조·폐기 플러그인 로드 거부
- **2층**: 자기서명 실행 파일이 "신뢰 서명" 으로 판정되지 **않는다**
- **2층**: `signed_malware` 열거 없이는 서명된 대상이 삭제에서 빠진다 (포괄적 무시 불가)

- 역행 금지: 낮은 버전의 플러그인·폐기 목록 거부

**판정은 그대로 선다.** 파괴만 하지 않고, 사유와 함께 보고된다.

#### 함께 고친 것 — 보고가 두 갈래를 섞고 있었다

`deferred` 가 *"아직 이 코어에 없는 Op 을 요구한다"* 하나로 렌더됐다. **2층이 선
뒤로 신뢰 서명 때문에 빠진 것까지 그렇게 보고됐는데 그 Op 은 있었다.** 운영자가
할 일이 완전히 다르다 — 앞은 코어를 올리는 일이고, 뒤는 서명·목록·매체를 다루는
일이다. `arrives_in` 을 게이트와 견주어 가른다.

### AI 합격 시험 — 무엇이 고정되고 무엇이 고정되지 않는가

| 고정 | 어디 |
|---|---|
| 프롬프트 | `testbed/ai-exam/PROMPT.md` |
| 위협 설명 | `testbed/ai-exam/threats/<위협>/THREAT.md` — **감염 스냅샷에서 실측해 쓴다** |
| 분석가 제공물 | `testbed/ai-exam/threats/<위협>/rules/*.yar` — 없는 위협도 있다 |
| 주입 파일 21개 | `testbed/ai-exam/inject.txt` = `xtask::exam::INJECT`. **`xtask guide` 가 둘의 일치를 강제한다** |
| 응시 꾸러미 | `cargo xtask exam --bundle` — 조각을 사람이 붙이지 않는다. 출제 메모가 새지 않는지도 검사한다. **파일에 직접 쓴다** — stdout 을 거치면 셸이 바이트를 바꾼다(r0 실측) |
| 기대 Op 목록 | `testbed/ai-exam/threats/<위협>/expected-ops.txt` — 채점 4 번이 이것으로 잰다 |
| 합격 판정 | `cargo xtask exam --dir <답> --threat <위협>` — **넷** 전부 자동 |

**모델은 고정할 수 없다.** 그래서 이것은 회귀 시험이 아니라 관측 도구다 —
설계-06 §10 이 말한 *"AI 가 무엇을 틀리는가"* 를 재고, 그 관측이 남은 문서의
목차를 정한다.

채점은 넷이다. **3 번(감염 스냅샷에서 판정이 서는가)** 이 없으면 아무것도
탐지하지 않는 룰이 1·2 를 만점으로 통과한다. **4 번(계획 완결성)** 이 없으면
판정은 서는데 **재발원을 남기는** 룰이 통과한다 — 둘 다 실측했다.

**회차의 채점 결과는 회귀로 고정되어 있다**(`xtask::exam` 테스트). 린트를
느슨하게 고치면 과거 회차가 조용히 통과하는데, 그것을 막는 장치가 없었다.
합격/불합격이 아니라 **숫자까지** 고정한다 — 진단 수가 줄어드는 것이 먼저
나타나기 때문이다.

> **2026-08-26 r2 — 변별력이 낮다는 진단이 반쯤 틀렸다.** 같은 모델·같은
> 위협으로 다시 돌렸더니 **우리 첫 플러그인의 결함 둘과 계획 가드의 구멍
> 하나**가 나왔다. 응시자가 문서에 없는 방어를 스스로 넣었고 그것이 실재하는
> 위험을 막았다 — 재귀 삭제가 `scan_roots` 상한 자체를 겨누는 경우다.
> 설계-03 §4 에 조건 5 를 더했다.
>
> **모델과 위협을 고정하면 문서 변화의 효과만 분리된다** — 다른 벤더로 돌리는
> 것보다 나은 통제였다. 아래 진단은 "같은 결과가 나올 것" 이라는 전제였는데,
> 답이 같아도 **그 답이 우리 것보다 나을 수 있다.**

**시험은 위협마다 나뉜다** (`testbed/ai-exam/threats/`). 위협 설명 · 분석가 룰 ·
감염 스냅샷 · 기대 Op 이 위협별이고 청정 코퍼스는 공유한다.

| 위협 | 무엇을 재는가 | 감염 스냅샷 |
|---|---|---|
| `evilai-locust` | 예약 작업 + 난독화 JS. **본문 판정(YARA)** | `corpus/infected/` (격리 VM 실측) |
| `service-userinit` | 서비스 + 레지스트리. **삭제하면 안 되는 값을 되돌리는 판단** | 위협 폴더 (**합성**) |

**합성 스냅샷은 코퍼스에 넣지 않는다.** `corpus/infected/` 의 *"실제로 뜬 것"*
이라는 성질(설계-04 §3)을 지키기 위해서다. 합성이라도 *"규격을 지켜 룰을
쓰는가"* 는 재고, 실검체 탐지는 `cargo xtask yara` 가 따로 잰다.

**위협마다 참조 답안이 있어야 한다** — 없으면 그 기대 Op 이 도달 가능한지
아무도 모르고 응시자만 떨어진다. 테스트가 위협 목록과 대조한다.

> **2026-08-26 r3 — 두 번째 위협의 첫 회차.** 판단은 전부 옳았는데
> `to: default` 를 `restore` 가 아니라 `remove` 절에 넣어 **파싱에서 멈췄다.**
> 그 문법 예시가 주입 문서 21개 중 **0건**이었다 — `REFERENCE.md` 의 한 줄은
> 제약 설명이지 문법이 아니다.
>
> **채점기가 파싱 실패를 못 다루던 것도 드러났다.** `Err` 로 빠져나가 회차를
> 기록에 남길 수 없었다. `Score::parse_error` 를 넣고 회귀 표가 위협과 파싱
> 여부까지 고정한다.
>
> **두 회차 전에 메운 빈칸 둘이 그대로 작동했다** — `ProgramData` 상한 방어와
> "재귀 삭제와 파일 `ref` 는 겹침이지 대체가 아니다" 를 응시자가 읽고 적용했다.

> **2026-08-26 svc-r2 — 방식 자체가 세 번 연속 검증됐다.** r3 가 드러낸
> `to: default` 빈칸을 메운 뒤 받은 회차가 **주석까지 그 구분을 적으며** 정확히
> 썼다. 그리고 참조 답안보다 하나 더 했다 — 폴더의 나머지 파일까지 격리해
> 재귀 삭제 보류에 대비했고, 그것을 참조 답안에 반영했다.
>
> | 회차 | 드러낸 빈칸 | 다음 회차 |
> |---|---|---|
> | r0 | `from` 의 subject · `restore` 의 짝 | r1 이 정확히 씀 |
> | r2 | `ProgramData` 상한 · 재귀 삭제와 `ref` 의 겹침 | r3 가 정확히 씀 |
> | r3 | `to: default` 의 절 | **svc-r2 가 정확히 씀** |
>
> **관측 → 빈칸 → 메움 → 확인** 이 세 번 돌았다. 설계-06 §10 이 요구한 것이
> 우연이 아니라는 실측이다.

**채점이 재지 못하는 것도 관측됐다** — `scan_roots` 는 평가 시 확장되지 않으므로
존재하지 않는 경로를 선언해도 네 판정을 통과한다(r1). 자동 판정 대신 문서와
리뷰 체크리스트로 막았다.

관측이 지금까지 린트 세 건과 채점 한 건을 만들었다 —
`check_yara_without_content` · `check_from_subject` · `check_restore_named` ·
채점 4 번. 자세한 것은 설계-06 §10.

### 제출을 제품 밖으로 (2026-08-28 P13 결정)

`remedy-submit`(제출·마스킹·동의)을 **제품 범위에서 뺐다.** 분석가가 필요할 때 손으로 올리고, remedy 는 `support-bundle` 까지만 만든다.

| 왜 | |
|---|---|
| **되돌릴 수 없는 유일한 동작이 된다** | 이 저장소의 모든 파괴는 격리 컨테이너로 되돌린다. **나간 데이터는 회수할 수 없다** — 그 하나를 위해 전체 안전 모델과 다른 규칙을 세워야 한다 |
| 선행 조건이 설계 밖에 있다 | 법무 검토(개인정보 최소 수집 · 동의 방식 · 국외 이전 · 보존 기간, 설계-00 §7)가 끝나야 켤 수 있고, **그 넷은 설계로 결정할 수 없다** |
| 기다릴 이유가 없다 | 분석가가 손으로 올리는 경로가 이미 있고, 그 첨부물을 `support-bundle`(P10-G)이 만든다 |
| 자동화하면 안 되는 것이 섞여 있다 | C2 URL 을 분석 시스템에 자동으로 넘기면 분석 과정에서 **그 주소에 실제로 접속할 수 있다** (내부 문서 설계-05 부록 B) |

**설계-00 §7 은 지운다는 뜻이 아니다.** 그 절은 *"제출을 켜려면 무엇이 필요한가"* 의 분석이고, 지금은 **그것을 켜지 않는 이유**로 읽힌다. 언젠가 켜게 되면 그 조건들이 그대로 선행 조건이다.

#### 함께 사라진 것 · 남은 것

| | |
|---|---|
| `remedy-submit` 크레이트 | **지웠다.** P0 골격 5줄이었고 아무도 의존하지 않았다 |
| `remedy-apply ↛ remedy-submit` 금지 규칙 | **지웠다.** 없는 크레이트에 대한 규칙은 지킬 것이 없다 — `cargo xtask arch` 가 바로 잡아냈다 |
| CLI `submit` | 표에만 있었고 구현된 적이 없다. 표에서 뺐다 |
| **`submit_hint` 매니페스트 필드** | **남긴다 — 뜻이 바뀐다.** 아래 |

**`submit_hint` 은 자동 제출기가 볼 값이 아니라 손으로 올리는 사람이 볼 판단 근거다.** 첫 플러그인이 이미 그것을 적고 있고(`samples: [payload]` · `confidentiality_min: 1`), 그 판단은 제출을 자동화하든 안 하든 유효하다 — *"무엇을 함께 올리면 유용한가"* 와 *"이것을 어느 등급으로 다뤄야 하는가"* 다.

### 잠긴 안전 모드 키는 풀지 않는다 (2026-08-31 결정)

악성코드가 `SafeBoot` 키를 **지우는** 것은 설계-00 §6 이 이미 다룬다 — 탐지하고, 재시작을 권하지 않고, 복원은 OS 복구 도구에 넘긴다. 2026-08-31 에 **잠그는 변종**(키에 `Deny` ACE 를 걸어 읽을 수 없게 만드는 것)이 논의에 올랐고, 그것을 remedy 가 풀어 주는 치료 Op 을 **짓지 않기로 했다.**

| 왜 | |
|---|---|
| **검체가 없다** | 코퍼스에도 설계에도 *삭제*만 있다. 잠금 변종은 P9 사이클 C 하네스를 위해 **우리가 고안한 것**이고, 악성코드가 그렇게 한다는 근거를 본 적이 없다. `evilai-locust` 가 서명 주체 열거를 확인하지 못해 필드를 비운 것과 같은 자리다 — **넓히려면 검체가 먼저다** |
| **설계-00 §5-1 이 이미 답했다** | *"치료 도구가 백신을 무력화하는 기능을 가지면 그 기능 자체가 악성코드의 표적이 된다. 대신 **실패를 정확히 진단**한다."* 안전 모드 키의 보호를 벗기는 것은 같은 부류이고, 그 절이 지시한 대안을 2026-08-31 에 구현했다(아래) |
| **새 능력이 들어온다** | remedy 는 지금 **아무것의 소유권도 가져오지 않는다.** `meta.rs` 의 `Owner` 는 *우리가 격리한 파일* 의 소유자를 되돌리는 것이고 실패하면 DACL 만으로 물러선다. OS 소유 시스템 키의 소유권을 빼앗는 것은 질적으로 다르다 |
| **판정 조건을 정할 수 없다** | 관측은 *"읽을 수 없다"* 까지만 말한다. 정책이 잠근 것인지 악성코드가 잠근 것인지 가를 표지가 없고, 가르지 못하면 치료해서는 안 된다 — 정책 잠금을 푸는 것은 치료가 아니라 **보안 설정 무력화**다 |

**대신 무엇을 했나.** 관측이 잠긴 것과 없는 것을 가르게 하고(`SafeBoot::Unreadable`), 룰이 그 값을 판정 근거로 쓸 수 있게 하고, 사용자에게 *"키는 있으나 읽을 수 없다 — 권한이 막혀 있다"* 고 말한다. 손으로 푸는 절차는 운영자에게 문서로 준다.

**언제 다시 여는가.** 셋이 모이면 열고, 그때 쓸 측정과 구현 계획은 이미 세워 두었다.

1. 잠금 변종을 쓰는 **검체를 관측**한다
2. 그 검체에서 **정책 잠금과 구분할 표지**를 찾는다
3. 2 를 룰로 표현할 수 있는지 확인한다 — 표현할 수 없으면 판정할 수 없고, 판정할 수 없으면 치료하지 않는다

> **조사는 이미 끝났다.** 되는 방법(소유권 → DACL → 소유자 원복)과 안 되는 방법(DACL 직접 쓰기 · `ProtectedDacl`)을 실기기에서 다 쟀다. 미루는 비용이 싼 것은 그 때문이고, 그것이 미루기로 한 이유의 절반이다.

## P12 — Linux 수집기·실행기

**산출**: `remedy-platform` 의 Linux 백엔드, Linux 청정 코퍼스, Op 카탈로그의

### trait 경계는 감당한다 — 조건 셋이 붙는다

2026-08-26 실측. `PlatformWrite` 44 메서드와 read trait 다섯을 Linux 개념과
대조했다.

| | 메서드 | Linux |
|---|---|---|
| **그대로 된다** | 파일 열거·읽기·삭제·복원, 텍스트/구조 설정, 프로세스 조회·종료, 디렉터리 | 표준 라이브러리와 `/proc` |
| **개념은 있으나 구현이 다르다** | 서비스 다섯, 예약 작업 다섯, 바로가기, 재부팅 후 실행 예약 | systemd · cron · `.desktop` |
| **없다** | 레지스트리 여덟, 보안 제품 예외 둘, 대체 데이터 스트림 둘, 재부팅 삭제 예약 둘, 복원 지점, 서명 확인 | `Unsupported` 를 낸다 |

**기본 구현이 이미 오류다.** trait 이 Linux 를 막지 않는다 — `Infallible` 스텁이
컴파일을 지키고 있고(`read.rs` · `write.rs`), `live()` 가 `None` 을 낼 뿐이다.

**재부팅 삭제 예약은 Linux 에 필요 없다.** Windows 는 사용 중 파일을 지우지
못하지만 Linux 는 `unlink` 가 된다. 없는 것이 아니라 **필요가 없는 것**이고,
그 구분이 카탈로그에 드러나야 한다.

### 결정 1 — Op 카탈로그에 플랫폼 축이 없다

`SubjectInfo` 는 `windows`·`linux` 를 갖는데 **`OpInfo` 는 없다.** 그리고
계획기의 가용성 판정은 Phase 만 본다.

```rust
fn available(op: Op) -> bool {
    op.info().implemented_in <= remedy_sdk::IMPLEMENTED_THROUGH
}
```

subject 가 `linux: false` 면 그 증거가 없어 Op 도 안 나온다 — 레지스트리 계열은
그렇게 간접적으로 막힌다. **`persistence` 는 다르다.** 둘 다 지원이므로 Linux 의
cron·systemd timer 증거에서 Op 이 도출되는데, 그 Op 이 Windows 예약 작업 이름을
달고 있다.

그러면 **계획은 초록인데 실행에서 실패한다** — 부분 실패(종료 코드 3)로 나가고
사용자는 *"치료했다는데 안 됐다"* 를 본다. 계획 단계에서 `deferred` 로 나가야
한다.

**`OpInfo` 에 플랫폼 축을 더하고 `available` 이 그것을 보게 하는 것이 P12 의
첫 작업이다.**

> **2026-08-26 — 끝.** `OpInfo.linux_from: Option<Phase>` 를 더했다.
> `SubjectInfo` 의 `windows`/`linux` 가 *"관찰할 수 있는 대상인가"* 인 것과 달리
> 이쪽은 **"이 코어가 실제로 수행하는가"** 이고, `implemented_in` 과 같은 축이다.
>
> `None` 여덟은 그 플랫폼에 **개념이 없는 것**이다 — 레지스트리 넷 · 대체 데이터
> 스트림 · Defender 예외 · 부팅 구성(되돌릴 기본값 카탈로그가 Windows 것뿐이다) ·
> **재부팅 삭제 예약**(없는 것이 아니라 `unlink` 로 끝나 필요 없다).
>
> 나머지 21 은 `Some(P12)` 다. `IMPLEMENTED_THROUGH` 가 P10 이므로 **Linux 는
> 지금 아무것도 수행하지 않고 전부 미룸으로 나간다** — 그것이 옳다. 예제 `ex03`
> 이 그 상태를 실물로 보여 준다.
>
> `deferred` 의 `arrives_in` 이 *"아직"* 과 *"영원히"* 를 가른다 — 기다리면 되는
> 것과 룰을 고쳐야 하는 것이 같은 표시를 달면 작성자가 무엇을 할지 모른다.

### 결정 2 — 예약 작업 Op 의 이름

`persistence` 를 제거하는 Op 둘만 Windows 개념의 이름이다. 다른 subject 는 전부
중립이다 — 서비스·자동 실행·파일·설정·바로가기·부팅 구성·인증서 저장소.

| 선택지 | |
|---|---|
| 이름을 그대로 두고 Linux 가 cron 으로 해석 | 이름이 거짓말이 된다 |
| 플랫폼별 Op 을 따로 둔다 | 카탈로그가 커지고 플러그인이 플랫폼을 의식하게 된다 |
| **중립 이름으로 바꾼다** | 카탈로그·문서·생성물·계획 스키마에 걸친 변경 |

**세 번째가 설계와 일치하지만 가장 비싸다.** subject 를 중립으로 둔 것과 같은
층위여야 한다(설계-02).

> **2026-08-26 — 세 번째로 정했다.** `persistence.disable` · `persistence.delete`.
> 실측해 보니 **플러그인과 예제는 Op 이름을 직접 쓰지 않는다**(계획기가
> 도출한다) — 영향이 코드 식별자 9 파일과 생성물 넷에 그쳤다.
> `PlatformWrite` 의 메서드 이름도 함께 바꿨다. `task_disable` 이 Linux 에서
> cron 을 다루면 같은 문제이기 때문이다.

### 결정 3 — Linux 에 신뢰 서명 개념이 없다

2층(설계-03 §3)과 재귀 삭제 조건 3·6 이 `survey_recursive_target` 에 기댄다.
Linux 스텁은 `Unsupported` 를 내고, `signature::of` 가 그것을 `None` 으로 바꾼다 —
**"확인하지 않았다"** 이므로 2층은 통과시키지 않는다.

방향은 안전하다. 다만 **Linux 에서 2층이 아무것도 막지 않는다**는 뜻이고,
재귀 삭제 조건 3 은 언제나 거부가 된다(확인할 수 없으므로).

| | |
|---|---|
| 그대로 둔다 | Linux 에서 재귀 삭제를 못 쓴다 |
| 패키지 관리자 서명을 본다 | `dpkg -S` · `rpm -qf` 는 **파일이 패키지 소유인지**를 말하지 서명을 말하지 않는다 |
| 규모 상한(조건 6)만으로 간다 | 조건 3 을 플랫폼별로 다르게 두는 것 |

**"없다" 도 답이다.** 다만 명시돼야 하고, 그때 `survey_recursive_target` 의
계약이 플랫폼마다 달라진다는 것을 문서가 말해야 한다.

> **2026-08-27 — 첫 번째로 정했다. 다만 실행 시점이 아니라 카탈로그에서 닫는다.**
> `dir.delete_recursive.linux_from = None`.
>
> Linux 백엔드가 컴파일되자마자 G2 가 이것을 잡았다 — *"이 코어에는 서명을
> 검증할 수단이 없다"*. 실행 시점 거부로 두면 **계획은 초록인데 실행에서 부분
> 실패**이고, 그것이 이번 Phase 에서 이미 두 번 고친 형태다(결정 1 · subject 축).
>
> 패키지 관리자로 대신할 수 없다. `dpkg -S` 는 파일이 패키지 소유인지를 말하지
> 서명을 말하지 않고, **악성코드가 사는 `~/.local` · `/tmp` 는 어느 패키지도
> 소유하지 않아 거기서는 조건 3 이 늘 통과한다** — 가드가 있는 것처럼 보이면서
> 실제로는 없는 상태가 된다.
>
> G2 의 `ops_in_gate` 와 `ops_with_a_case` 가 플랫폼을 보게 했다. Linux 는 아직
> 게이트 안에 Op 이 0개이고, 그 0 이 "시험이 안 돈다" 로 조용히 바뀌지 않도록
> 숫자로 못 박았다.

### 선행 조건 — Linux 청정 코퍼스

`corpus/clean/` 일곱과 `corpus/infected/` 하나가 **전부 Windows** 다.
**G1(청정 환경 무해성)을 Linux 에서 잴 수 없다.**

실행기를 여는 것은 그 게이트를 다시 지나는 일이므로, **코퍼스가 실행기보다
먼저다.**

예제 `ex03` 이 Linux 스냅샷으로 평가 경로가 도는 것을 이미 확인했다 —
`text_config` 수집 · `%HOME%` 토큰 · 경로 정규화. 그것은 예제 하나이지

> **2026-08-27 — 끝.** 두 환경에서 다섯 개를 떴다.
>
> | 스냅샷 | 파일 | 지속성 |
> |---|---|---|
> | `wsl-ubuntu24-etc` · `-usr` · `-home` | 1461 · 19634 · 10 | 226 |
> | `docker-debian12-etc` · `-usr` | 619 · 6253 | 21 |
>
> **환경이 둘인 것이 핵심이다.** WSL 은 systemd 가 돌아 지속성 226건이고 컨테이너는
> 21건이다 — 같은 수집기가 다른 환경에서 다른 답을 낸다는 것은 코퍼스 하나짜리로는
> 확인되지 않는다.

> `testbed/harness/linux/new-corpus-snapshot.sh` 가 강제한다 — root 가 아니면
> 멈춘다.

> **2026-08-27 — 순서를 3↔4 로 바꿨다.** 손으로 쓴 Linux 코퍼스는 측정이 아니라
> 픽스처다. 수집기가 있어야 실물을 뜰 수 있으므로 read 백엔드가 먼저다.

### 결정 5 — Linux 지속성을 끄고 지우는 계약

**2026-08-27.** 파일 계열은 [`FsRestore`] 위임으로 끝났는데 `persistence` 둘이
지금 계약으로 안전하게 되지 않는다.

| | 무엇이 막는가 |
|---|---|
| cron | disable 은 줄 주석인데 `persistence_disable(id)` 에 **대조할 줄 내용이 오지 않는다.** 이 저장소는 줄 번호만으로 고치지 않는다 — `text_config.remove_line` 은 `(path, line_no, line)` 을 받는다 |
| systemd | disable 은 `.wants/` 링크 제거인데 **백업 슬롯이 파일 본문 하나**라 링크 목록을 담을 자리가 없다. 유닛 파일만 되살리면 그 유닛은 꺼진 채로 돌아온다 |

| 선택지 | |
|---|---|
| 계약을 넓힌다 | `persistence_disable/delete` 가 백업 바이트를 함께 받고, `persistence_read` 가 링크 목록까지 담는 형식이 된다. **Windows 구현·실행기·G2 Bench 시그니처가 함께 바뀐다** |
| 파일 계열 Op 으로 흘린다 | `removal_ops` 가 플랫폼을 본다. 계약은 그대로지만 `.wants/` 링크가 남아, 같은 이름의 유닛이 다시 놓이면 부활한다 |
| 파일 직접 + 새 메서드 | Linux 전용 메서드를 더한다. trait 이 플랫폼별로 갈라지기 시작한다 |

**"파일을 직접 다룬다" 는 이미 정했다** (2026-08-27). `systemctl --user` 는 그
사용자의 세션 버스를 요구하는데 root 로 도는 치료 도구에는 그것이 없고,
**사용자 유닛이 가장 흔한 지속성 자리**다. 남은 것은 위 표의 선택뿐이다.

### 마감 뒤에 드러난 결함 둘 (2026-08-28)

`cert_store` 를 **실기기에서 처음 돌려 보고** 둘이 나왔다. 둘 다 P12 가
"통과" 로 닫힌 뒤에도 살아 있었고, 둘 다 **시험이 그 상태를 고정하고 있었다.**

#### 1. 배포되는 바이너리가 Linux 라이브 백엔드를 쓰지 않았다

`restore.rs` 의 `default_backend()` 가 non-Windows 에서 `FsRestore` 를
돌려줬다. 순서 8 이 `linux::Live` 를 세우면서 **여기를 갱신하지 않았다.**

게이트가 P12 로 올라 Linux Op 14종이 열렸지만 **실제 바이너리는 파일 계열만
수행할 수 있었다** — `persistence.*` · `service.*` · `process.kill` 은 실기기에서
`Unsupported` 로 실패했을 것이다. 시험은 전부 통과했다. 시험이 가짜 백엔드를 쓰기
때문이다.

> **같은 함수에서 같은 결함이 두 번 났다.** 첫 번째는 Windows 였고(P7), 그때
> 남긴 주석이 *"시험이 재던 것과 배포되는 것이 달랐다"* 라고 정확히 적고 있다.
> 그런데 그 옆 시험이 `assert_eq!(name, "fs")` 로 non-Windows 를 못박아 두어
> **두 번째를 오히려 고정했다.**

이제 `the_default_backend_is_the_live_one` 이 `live()` 와 같은 것인지 이름으로
잰다 — 능력을 하나씩 재면 새 Op 이 들어올 때 그 목록이 낡는다.

#### 2. Linux 에서 복원이 사실상 전부 막혀 있었다

복원의 보호 검사가 **한 겹**이었다 — `protected.check()` 가 무엇이든 돌려주면
막았다. 계획기는 **두 겹**이다: 보호 디렉터리 *자체*·루트·홈은 무엇으로도 못
건드리고, **하위의 개별 파일은 조건부로 허용**한다 (설계-03 §3 1층).

그 갈라짐이 **"지울 수는 있는데 되돌릴 수는 없는" 대상**을 만들었다. Linux 에서
특히 심하다 — 보호 목록에 `/etc` 와 `/usr` 가 있고 systemd 유닛 · cron · XDG
autostart · 신뢰 인증서가 **전부** 그 아래 산다. 즉 실제 치료 대상 거의 전부가
복원 불가였다. Windows 에서도 `System32` 하위의 악성 DLL 이 같은 상태였다.

**P12 마감의 실기기 시연이 `/tmp/p12lab/` 에서 돌아 드러나지 않았다.**

`protected_for_restore()` 가 계획기와 같은 두 겹을 쓴다. 여는 것은 보호 디렉터리
하위의 **개별 파일 하나**를 우리가 담았던 그 자리에 되돌리는 것뿐이고, 디렉터리
통째 복원은 열지 않는다.

### 순서 9 에서 드러난 것 — 카탈로그가 정답을 갖고 있었다

**2026-08-27.** `.service` 를 `persistence` 에 담고 있었다. 그런데 이 문서가

| | |
|---|---|
| `persistence` | 예약 작업 · cron · systemd **timer** |
| `service` | Windows 서비스 · systemd **service** · SysV init |

유닛 파일과 **enable 상태**")이 P7 부터 있었는데 `Task` 를 쓰고 있었다. `Unit`

**규율**: 카탈로그의 요약과 구현이 어긋나면 요약이 옳다고 보고 먼저 대조한다.

### `cert_store` 를 연 방법 (2026-08-28)

**"X.509 파서가 없다" 가 틀렸다.** `certstore.rs` 에 `parse_certificate` 가
P4 부터 있었다 — Windows 레지스트리의 `Blob` 에서 DER 을 꺼내 주체·발급자·만료를
읽는 손으로 쓴 파서다. 필요한 것은 파서가 아니라 **지문**이었다.

| | |
|---|---|
| 새 의존 | `sha1` 0.10 (RustCrypto, MIT/Apache-2.0 — `deny` 통과) |
| 왜 SHA-1 인가 | Windows 는 신뢰 저장소의 **레지스트리 키 이름**이 곧 SHA-1 지문이라 공짜로 얻는다. Linux 에서 다른 해시를 쓰면 **같은 인증서가 플랫폼마다 다른 지문을 갖고**, 악성 루트 CA 하나를 잡는 룰이 값을 둘 적어야 한다 |
| 보안 속성인가 | **아니다. 식별자다.** 인증서의 신뢰를 이 해시가 결정하지 않는다 — 코드에 그렇게 적어 두었다 |

교차검증: `openssl x509 -fingerprint -sha1` 과 우리 값이 일치한다.

#### 어디를 보는가

| 저장소 | 자리 | 실측 |
|---|---|---|
| `local` | `/usr/local/share/ca-certificates` | **손으로 더한 CA 가 오는 자리.** 두 환경 모두 0건 |
| `system` | `/usr/share/ca-certificates` | Ubuntu 24.04 **121** · Debian bookworm **142** |

`/etc/ssl/certs` 는 보지 않는다. 그 아래는 거의 전부 심볼릭 링크(실측 243개)이고
실제 파일 둘 중 하나는 **번들**이라 같은 인증서를 다시 담는다.

#### 파일을 지우는 것은 치료가 아니다

실측: `/usr/share/ca-certificates/**.crt` 를 지워도
`/etc/ssl/certs/ca-certificates.crt` 번들에 그 인증서가 **그대로 남는다.** TLS
검사는 그 번들을 읽는다.

그래서 `PlatformWrite` 에 `cert_*` 가족을 따로 뒀다 — `destroy_file` 로 대신할 수
없다. 지우기·되돌리기 **양쪽 다** `update-ca-certificates` 를 부른다.

- **도구를 먼저 찾고 그 다음에 지운다.** 순서가 반대면 배포판이 달라 도구가 없는
  기계에서 파일만 사라지고 신뢰는 남는다 — 치료가 안 됐는데 증거가 없어진다.
- 도구 목록은 **절대 경로**로 코드에 박혀 있다(`/usr/sbin/update-ca-certificates` ·
  `/usr/bin/update-ca-trust`). `PATH` 를 타면 치료 도구가 공격자의 실행 파일을
  부른다 — Windows 의 `SYSTEM_TOOLS` 와 같은 규율이고, 시험이 절대 경로임을 잰다.

`update-ca-certificates` 로 번들에 넣은 뒤(번들 121 → 122), 치료하고 되돌렸다.

### systemd `Restart=` 데몬 실증 (2026-09-29)

**물음.** 리눅스 백엔드는 `systemctl` 을 부르지 않는다(결정 5). 서비스는 유닛 파일과
`.wants/` 링크를 지워서 끄고 지우며, 돌고 있는 것은 `process.kill` 이 멈춘다(카탈로그의
`service.stop` 주석). 그런데 systemd 는 `Restart=` 가 걸린 유닛의 주 프로세스가 죽으면
**메모리에 올린 정의로** 다시 띄운다. 컨테이너는 systemd 가 PID 1 이 아니어서 이것을 잴
수 없었다.

**잰 법.** 리눅스 랩 VM(Debian 12 · systemd 252)에서 무해한 데몬 — `sleep` 의 사본 — 을
`Restart=` 유닛으로 띄우고, 가이드 모양의 플러그인(실행 파일 · 유닛 · 프로세스를
`remove`)으로 `remedy run` 을 돌렸다. 회차마다 스냅숏으로 되돌리고, 치료 뒤 15초를 지켜본
다음 재부팅해 한 번 더 봤다. 하네스는 `testbed/harness/linux/invoke-restart-verify.sh`.
하네스 판정 · systemd 저널 · remedy 저널 · 시각별 표본 넷이 일곱 회차 모두 서로 맞았다.

| 회차 | 유닛 | 종료 → 재기동 | 종료 코드 | 15초 뒤 데몬 | 재부팅 뒤 |
|---|---|---|---|---|---|
| `fast` ×5 | `Restart=always` · 간격 기본값(100ms) | 191 · 237 · 309 · 356 · 356 ms | 3 · 3 · 3 · **1 · 1** | **다섯 번 다 돈다** | 없다 |

**드러난 것 셋.**

1. **치료가 `Restart=` 데몬을 멈추지 못한다.** 계획의 차례는 종료(2단계) → 비활성(3) →
   삭제(5)다. 종료하는 순간 systemd 는 유닛을 메모리에 들고 있고, 유닛 파일을 지워도
   `daemon-reload` 전까지는 옛 정의로 되살린다(`LoadState=loaded` · `NeedDaemonReload=yes` ·
   `NRestarts=1`). 되살아난 데몬은 **재부팅할 때까지** 돈다. 재부팅하면 유닛 파일이 없으므로
   뜨지 않는다.
2. **"치료 완료" 가 사실과 어긋날 수 있다.** 실행기는 종료 뒤 300ms(`SETTLE` — 워치독 쌍에서
   잰 33ms 의 열 배)를 쉬고 다시 센다. systemd 는 재시작 타이머를 정확도 없이 걸어 기본값
   250ms 가 붙으므로(v252 `service_arm_timer` → `sd_event_add_time(…, usec, 0, …)` →
   `DEFAULT_ACCURACY_USEC`), `RestartSec=100ms` 도 **100–350ms 사이**에 깬다(잰 값: 종료 →
   재시작 예약 169–338ms). 창을 넘으면 실행기는 아무것도 못 보고 종료를 "수행" 으로 적는다 —
   `fast` 다섯 번 중 두 번, `slow` 는 언제나.
3. **데몬 실행 파일이 격리되지 않는다 — 대조군에서도.** 계획기는 돌고 있는 프로세스가 잡은
   파일을 `file.delete_on_reboot` 로 돌리는데(`removal_ops_for`), 그 Op 은 리눅스에 없다
   (`linux_from: None` — *"Linux 는 `unlink` 가 된다 — `file.delete` 로 끝난다"*). 그래서
   미룸으로 빠진다. `Restart=` 와 무관한 계획기 결함이고, 잠금 검사를 재는 시험 다섯이 전부
   Windows 경로라 드러나지 않았다. **고쳤다 (`3000713`)** — 잠금 규칙을 Windows 스냅숏에만
   적용한다(`running_images_are_locked`).
