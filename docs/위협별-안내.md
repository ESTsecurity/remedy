## CWPdoor — Control Web Panel 을 쓰는 리눅스 서버

- **치료하면** 백도어가 든 `cwpsrv` 를 **격리**하고, 그것을 띄우는 `cwpsrv.service` 를 **멈추고 지웁니다.**
- **꼭 할 일** 공급사의 **최신 버전**으로 패널을 다시 설치해 켜고(`yum install cwpsrv` — 이미 최신이면
  `yum reinstall cwpsrv` → `systemctl enable --now cwpsrv`), **패널 자격 증명을 모두 바꿉니다.**
- **못 보는 것** 서명 키가 다른 배포 · 지금 돌고 있는 창구 — 패널을 되살린 뒤 `ss -axp | grep integrity`
  가 아무것도 내지 않는지 보십시오.

<details>
<summary>자세히 — 다시 설치 · 창구 확인 · 되돌리기 · CWP 가 없는 서버</summary>

- **CWPdoor 제거** 는 백도어가 든 `cwpsrv` 를 **격리**하고, 그것을 띄우는 `cwpsrv.service` 를
  **멈추고 지웁니다**. 패널은 그 뒤 공급사의 **최신 버전**을 설치하고(`yum install cwpsrv` 로 올립니다.
  같은 버전을 다시 깔려면 `yum reinstall cwpsrv` — 어느 쪽이든 서비스 파일이 함께 돌아옵니다)
  `systemctl enable --now cwpsrv` 로 다시 켭니다. 침입에 쓰인 구멍이 깔려 있던 버전의 것일 수 있어
  공개 보고는 최신 버전으로 올리라고 권합니다.
- 패널을 되살린 뒤 **백도어가 열던 창구가 사라졌는지 한 번 보십시오.** 아래가 아무것도 내지 않아야
  합니다. 이 도구는 이것을 재지 못합니다(돌고 있는 창구는 검사 대상이 아닙니다).

  ```sh
  ss -axp | grep integrity
  ```

- 백도어는 임의 명령을 돌릴 수 있었으므로 **패널 자격 증명을 모두 바꾸고**, 서버 전체를 침해된 것으로
  보고 다른 흔적을 살피십시오.
- **치료가 끝나도 '이 서버에 CWPdoor 가 없다' 는 뜻은 아닙니다.** 이 룰은 공개 보고가 밝힌 활성화
  방식과 공격자의 서명 키를 **함께** 지닌 파일을 찾습니다 — 서명 키가 다른 배포는 찾지 못합니다.
  의심되면 위 `ss` 확인과 함께 담당자에게 알리십시오.
- 공급사 버전을 다시 설치한 뒤에는 **치료를 되돌리지 마십시오** — 되돌리면 격리해 둔 백도어가
  새로 설치한 정상 파일을 덮어씁니다. 되돌리기는 오탐이라 판단했을 때, 다시 설치하기 전에만 씁니다.
- CWP 가 깔리지 않은 서버에서는 두 항목 모두 검사할 경로(`/usr/local/cwpsrv/bin`)가 없어 *관측이
  불완전해 '위협 없음' 을 말할 수 없습니다* 로 끝나고, 빠른 · 정밀 검사의 요약에는 **해당 없음** 으로
  나옵니다.

</details>

## Ebury — 리눅스 서버의 sshd (찾기만 합니다)

- **치료하지 않습니다** — 가짜 `libkeyutils.so.1` 을 옮기면 그것을 싣는 `sshd` · `sudo` 가 뜨지 못해 원격
  접속이 끊기므로, 찾은 것만 알려 드립니다.
- **꼭 할 일** **콘솔에서** 정상 패키지를 다시 설치하고(`keyutils-libs` · `libkeyutils1`) 다시 점검한 뒤
  재부팅하고, 이 서버로 들어오고 나간 **자격 증명을 모두 바꿉니다.**
- **못 보는 것** OpenSSH 실행 파일 자체를 고친 경우 · 이름이 알려지지 않은 파일과 창구 · 지금 돌지 않는
  백도어의 창구 — ESET 점검 스크립트를 함께 돌리십시오.

<details>
<summary>자세히 — 여섯 단계 · 창구(@ 로 시작하는 이름) · ESET 점검 스크립트</summary>

Ebury 는 `libkeyutils.so.1` 자리에 가짜 라이브러리를 둡니다 — 그것을 옮기면 그 라이브러리를
싣는 `sshd` · `sudo` 가 뜨지 못해 원격 접속이 끊기므로 remedy 가 손대지 않습니다. 발견되면 메뉴
화면의 *검사 완료* 줄 아래에 찾은 파일이 번호와 함께 나옵니다(명령으로 돌리면 화면에 경로가 나오지
않습니다 — `--out-dir <폴더>` 를 주면 그 폴더의 `scan.json` 에 남습니다) — 아래에서 *결과에 나온 파일* 은
그것입니다. 아래 차례대로 합니다.

1. **콘솔(가상 콘솔 · IPMI 등)에서 합니다.** SSH 로 들어가면 그 접속의 자격 증명이 다시 넘어갑니다.
2. **정상 버전을 다시 설치합니다.** RHEL 계열은 `yum reinstall keyutils-libs`(또는 `dnf`), Debian ·
   Ubuntu 는 `apt-get install --reinstall libkeyutils1`.
3. **다시 점검한 뒤, 패키지에 없는 파일만 지웁니다.** Ebury 점검을 다시 돌려 *위협 없음* 이면
   다시 설치가 가짜 파일을 덮은 것이니 4단계로 갑니다. 아직 나오면 `ls -l` 로 `libkeyutils.so.1` 이
   결과에 나온 파일을 더는 가리키지 않는지 봅니다. 결과에 나온 파일이 어느 패키지의 것도 아니면
   (`rpm -qf <경로>` · `dpkg -S <파일 이름>` 이 패키지를 대지 못하면) 지우고 `ldconfig` 를 실행한 뒤,
   링크를 한 번 더 봅니다. `dpkg -S` 에는 경로 말고 **파일 이름만** 줍니다 — `/lib` 가 `/usr/lib` 를
   가리키는 서버에서는 결과에 같은 파일이 두 경로로 나오는데, 한쪽 경로로 물으면 정상 파일도
   패키지가 없다고 나옵니다. 다시 설치가 되지 않았거나 링크가 여전히 그 파일을 가리키면
   **지우지 말고** 담당자에게 알리십시오 — 지우면 `sshd` · `sudo` 가 뜨지 못합니다.
4. **재부팅합니다.** 이미 떠 있는 `sshd` 등에는 가짜 라이브러리가 실려 있습니다.
5. **자격 증명을 모두 바꿉니다.** 이 서버로 들어온 비밀번호 · SSH 키와, 이 서버에서 다른 서버로
   나간 키 — Ebury 는 둘 다 훔칩니다.
6. **서버 전체를 침해된 것으로 봅니다.** 심으려면 root 권한이 필요했습니다. 다시 설치를 검토합니다.

결과에 `@` 로 시작하는 이름만 나오면 그것은 파일이 아니라 **돌고 있는 백도어가 여는 창구**(추상 UNIX
소켓)입니다. 그때는 콘솔(1단계)에서 먼저 그 창구를 연 프로세스와 그 프로세스가 실은 라이브러리를 찾으십시오 —
가짜 라이브러리가 알려지지 않은 이름일 수 있습니다. 명령은 `plugins/ebury-check/RELEASE.md` 의
*위협이 나오면* 절에 있습니다.

**'위협 없음' 이 Ebury 가 없다는 뜻은 아닙니다.** 이 항목은 라이브러리 **파일의 내용**과, ESET 가
공개한 **창구 이름 24개**를 봅니다. 공개 보고(ESET)는 다섯 가지 설치 방법을 적는데, 이 룰은 그 가운데
**보고가 이름을 밝힌 파일들**을 봅니다 — OpenSSH 실행 파일 자체를 고친 경우와 아직 이름이 알려지지
않은 파일 · 창구는 찾지 못하고, 백도어가 지금 돌고 있지 않으면 창구도 없습니다. 침해가 의심되면
ESET 가 공개한 점검 스크립트를 함께 돌리십시오(root 권한 — 창구에 실제로 접속해 봅니다).

```sh
curl -LO https://raw.githubusercontent.com/eset/malware-research/master/ebury/detect_ebury.sh
sudo bash detect_ebury.sh
```

</details>

## EvilAI(Locust) — Windows PC

- **치료하면** 페이로드를 돌리던 `node.exe` 를 멈추고 예약 작업 · 시작 프로그램 항목을 지우고, 페이로드와
  그 폴더를 **격리**합니다 — 이 PC 의 **모든 사용자 계정**을 봅니다.
- **꼭 할 일** PC 를 **다시 시작해 관리자로 로그온**하고(한 번 더 자동 검사), 가짜 앱(`PDF Editor` 등)을
  *설정 → 앱* 에서 지우고, 비밀번호를 **다른 기기에서** 바꿉니다.
- **못 보는 것** 확보한 유형 밖의 페이로드와 EvilAI 가 내려받은 다른 악성코드 — **백신으로 PC 전체를
  검사**하십시오.

<details>
<summary>자세히 — 무엇을 지우고 남기나 · 다시 시작 · 찾는 유형 · 가짜 앱 서명자</summary>

- **EvilAI(Locust) 제거** 는 페이로드를 돌리던 `node.exe` 프로세스를 멈추고, 예약 작업과 시작
  프로그램(Run) 항목을 지우고, 페이로드(`.js`)와 그 폴더를 **격리**합니다. 페이로드가 임시
  폴더(`TEMP`) 바로 아래에 있으면 **그 파일만** 격리하고 임시 폴더는 건드리지 않습니다. 페이로드
  폴더(`AppData\Local\Programs\<이름>`)를 백신 검사 예외에 넣어 두었다면 그 예외도 지웁니다. Node.js
  자체는 정상 프로그램이라 손대지 않습니다.
- **이 PC 의 모든 사용자 계정을 검사합니다** — 담당자가 자기 관리자 계정이나 배포 도구(SYSTEM)로
  실행해도 감염된 사용자의 것을 찾고, 그 사용자가 **로그온해 있으면** 그 사용자의 시작 프로그램
  항목까지 지웁니다. 로그오프한 사용자의 항목은 남을 수 있습니다 — 그 항목이 가리키는 파일은
  격리되므로 실행되지 않습니다.
- 치료한 뒤 **PC 를 다시 시작하고 관리자 계정으로 로그온하십시오** — 그때 한 번 더 자동으로
  검사합니다. 표준 사용자로 로그온하면 이 검사는 돌지 않으므로, 관리자가 메뉴의 *3. 치료가
  유지됐는지 다시 보기* 로 확인합니다.
- **'위협 없음' 이 이 PC 가 깨끗하다는 뜻은 아닙니다.** 이 항목은 확보한 검체의 유형과 공개 보고(Trend
  Micro)가 적은 유형을 찾습니다 — 페이로드가 `AppData\Local\Programs` 아래 폴더나 임시 폴더(`TEMP`)
  바로 아래에 있고, 예약 작업이 그것을 `node.exe` 로 직접 또는 `cmd.exe` 를 거쳐 띄우는 유형입니다
  (작업이 어느 폴더에 등록됐는지는 묻지 않습니다). 보고가 이름을 밝힌 시작 프로그램 항목
  (`PDFEditorUpdater`)은 감염이 확인된 PC 에서, 시작 메뉴 바로 가기(`PDF Editor`)는 페이로드가 임시 폴더에
  있는 유형에서 그 사용자의 것만 함께 치료합니다(둘 다 복원할 수 있습니다). 임시 폴더 안의 하위 폴더에 둔
  페이로드처럼 그 밖의 유형은 찾지 못합니다. 감염이 의심되면 백신으로 PC 전체를 검사하고 담당자에게
  알리십시오.
- **가짜 앱 자체는 지우지 않습니다.** EvilAI 는 'PDF Editor' 같은 정상처럼 보이는 앱을 깔게 해서
  들어옵니다 — *설정 → 앱* 에서 그 앱을 제거하십시오. 공개 보고가 밝힌 서명자는 App Interplace LLC ·
  Byte Media Sdn Bhd · Echo Infini Sdn. Bhd. · GLINT SOFTWARE SDN. BHD. · Global Tech Allies ltd ·
  Pixel Catalyst Media LLC 입니다.
- EvilAI 는 다른 악성코드를 풀어 실행하는 로더입니다. 이 도구는 EvilAI 가 남기는 항목만 보므로
  **백신으로 PC 전체를 검사**하고, 이 PC 에서 쓰던 비밀번호는 **다른 기기에서** 바꾸십시오.

## Log4j — 자바 라이브러리 (점검만 합니다)

- **점검만 합니다** — 이 기계의 디스크 전체에서 jar · war · ear 파일을 찾아, 그 안의 Log4j(log4j-core 2.x ·
  log4j 1.x)와 logback 이 Log4Shell(CVE-2021-44228) 계열의 취약한 버전인지 봅니다. war · ear · Spring Boot 파일
  안에 든 라이브러리까지 봅니다. 아무것도 바꾸지 않습니다.
- **꼭 할 일** *취약* 이면 그 앱의 Log4j 를 고친 버전(2.17.1 · Java 7 은 2.12.4 · Java 6 은 2.3.2) 이상으로,
  logback 은 1.2.9 이상으로 올리고 그 앱을 **다시 시작**합니다. log4j 1.x 는 지원이 끝나 고친 버전이 없으니 2.x 로
  옮깁니다. 앱을 만든 곳이 따로 있으면 그곳이 낸 고친 버전을 받습니다.
- **못 보는 것** 실행 중인 자바 프로그램이 어느 Log4j 를 실었는지 · 버전 정보(`pom.properties`) 없이 클래스만 옮겨
  담은 파일 · 네트워크 드라이브와 이동식 매체.

<details>
<summary>자세히 — 판정 · 확인 필요가 나오는 경우 · 보는 자리</summary>

- **판정** — 파일 이름의 버전(`log4j-core-2.14.1.jar`), Maven Central 공식 파일의 해시(이름을 바꿔도), 파일 안
  `pom.properties` 의 버전으로 가립니다. log4j-core 2.0 ~ 2.17.0(2.3.2 · 2.12.4 는 제외) · log4j 1.x 전부 ·
  logback-core 1.2.9 미만이 *취약* 입니다.
- **찾은 것마다** 그 파일 · 안쪽 경로 · 버전을 적고, 바로 아래 줄에 그 라이브러리와 해당 CVE 를 적습니다(같은
  라이브러리라도 버전에 따라 해당하는 CVE 가 달라 *버전에 따라 일부* 라고 적습니다).
- **확인 필요가 나오는 경우** — log4j-core 가 들어 있는데 버전이 적혀 있지 않을 때, 파일을 끝까지 읽지 못했을 때
  (깨진 파일 · 잘린 파일 · 너무 큰 파일 · 암호). 화면의 항목 줄이 그 파일과 까닭을, *주의* 줄이 할 일을 알려 드립니다.
- **보는 자리** — Windows 는 고정 드라이브 전부, 리눅스는 로컬 디스크 전부입니다(가상 · 네트워크 파일 시스템은 보지
  않습니다). 이름이 `.jar` · `.war` · `.ear` 인 파일만 기록합니다 — 디스크가 크면 몇 분이 걸릴 수 있습니다.

판정 표와 근거(공지 번호)는 룰 폴더 `log4j-check` 의 `RELEASE.md` 에 있습니다.

</details>

## Java — 자바 런타임 (점검만 합니다)

- **점검만 합니다** — 이 기계에 깔린 자바 런타임(JDK · JRE)의 버전이 Java4Shell(CVE-2026-114938)의 영향을 받는
  버전인지 봅니다. 아무것도 바꾸지 않습니다. 앞의 *Log4j 점검* 과 다릅니다 — 그쪽은 앱이 쓰는 **라이브러리**를,
  이쪽은 앱을 돌리는 **자바 자체**를 봅니다.
- **꼭 할 일** *취약* 이면 그 자바를 고친 버전으로 올리고, 그 자바로 돌던 **서비스를 다시 시작**합니다. 올려도 다시
  시작하지 않으면 그 프로그램은 고치기 전 코드로 계속 돕니다. 고친 버전이 아직 나오지 않았다면, 그 자바로 돌리는
  프로그램에 `-XX:-UseBASE64Intrinsics` 옵션을 주어 문제가 되는 부분을 끌 수 있습니다(공지가 알려 준 방법입니다).
- **못 보는 것** 아래 *보는 자리* 밖에 압축을 풀어 두었고 돌지도 않는 자바 · 앱 파일(jar) 안에 담긴 코드 ·
  컨테이너 이미지 안의 자바(그쪽은 *이미지 파일 · 컨테이너* 점검이 봅니다).
- **관리자도 열 수 없는 폴더**(Windows) — `C:\Program Files` 아래에 관리자 권한으로도 열리지 않는 폴더(예: Microsoft
  Defender for Endpoint 의 설정 폴더)가 있으면, 1.24.0 부터는 그 폴더만 건너뛰고 나머지로 결과를 내며 *관리자 권한으로도
  열리지 않는 폴더 N곳을 빼고 모두 확인했습니다* 와 그 폴더를 적습니다. 1.23.0 까지는 그 폴더 하나 때문에 *확인 필요* 로
  끝났습니다 — 그때 화면의 *거부된 자리* 가 그 폴더이고 나머지는 모두 봤습니다.
- **대응 기록** — 1차 2026-11-18 `rules-2026.11.18`(OpenJDK 17 · 21 · 25 · 27 의 고친 버전 · 지원이 끝난 버전 · 표준 설치
  자리) → 2차 2026-11-18 `rules-2026.11.18.2`(Java SE 8 성능 빌드 · 사용자마다 깐 자바 · 제품이 담은 자바 · 대체 링크로 띄운
  서비스) → 3차 2026-11-18 `v1.24.0`(GraalVM EE 21.3 · VS Code Java 확장의 자바 · 관리자도 열 수 없는 폴더). 범위가 넓어질 때마다
  새 버전이 나옵니다 — 다시 받아 다시 점검하십시오.

## OpenSSH — Alpine 의 sshd (점검만 합니다)

- **점검만 합니다** — Alpine(musl) 의 PAM 없는 sshd(`openssh-server`)가 비밀번호 인증 우회(CVE-2026-123158)를
  고치기 전 버전인지 봅니다. `/etc/shadow` 의 비밀번호 칸이 `*` 인 계정(Alpine 3.16 부터 `root`)이 있으면 아주 긴
  아무 비밀번호로 로그인되는 취약점입니다. 아무것도 바꾸지 않습니다.
- **꼭 할 일** *취약* 이면 `apk upgrade openssh-server` 로 그 브랜치의 고친 버전 이상으로 올리고 sshd 를
  **다시 시작**합니다. 올리기 전에는 `/etc/ssh/sshd_config` 에 `PasswordAuthentication no` 를 두는 것이 막는 길입니다.
- **못 보는 것** `*` 계정이 실제로 있는지(`/etc/shadow` 는 읽지 않습니다) · 실행 중인 sshd 가 어느 파일인지.
  호스트 개인키(`ssh_host_*_key`)는 읽지도 기록하지도 않습니다.

## Apache — 웹서버의 HTTP/2 (점검만 합니다)

- **점검만 합니다** — 리눅스 · Windows 의 Apache 웹서버가 HTTP/2 처리 모듈(mod_http2)의 원격 코드 실행
  취약점(CVE-2026-119618)을 고치기 전 버전인지, 그리고 HTTP/2 를 켜 두었는지 봅니다. 아무것도 바꾸지 않습니다.
- **꼭 할 일** *취약* 이면 배포판의 보안 업데이트로 고친 버전 이상으로 올리고(Debian · Ubuntu 는 `apache2`, RHEL 계열 ·
  Amazon Linux 는 `mod_http2`, Alpine 은 `apache2-http2`) Apache 를 **다시 시작**합니다. 직접 빌드했으면 2.4.71 이상으로
  다시 빌드합니다. Windows 는 Apache Lounge 2.4.71 이상으로 바꿉니다(XAMPP 는 2026-11-14 확인 때 고친 버전이 없었습니다).
  올리기 전까지는 설정의 `Protocols` 에서 `h2` · `h2c` 를 빼 HTTP/1.1 만 쓰는 것이 막는 길입니다.
- **못 보는 것** 정해 둔 자리 밖의 직접 빌드(리눅스) · 정해 둔 자리 밖에 풀어 두기만 한 Apache 와 따로 바꿔 끼운
  mod_http2(Windows) · `Include` 로 다른 곳에서 읽는 설정 · 컨테이너 안. TLS 개인키(`*.key` · `*.pem`)는 읽지도 기록하지도
  않습니다.

## nginx — 웹서버 nginx2root (점검만 합니다)

- **점검만 합니다** — Windows 와 리눅스를 봅니다(Windows 는 룰 2026.11.19.2 부터 — 아래 대응 기록). 이 기계에 깔린 nginx
  의 버전이 nginx2root(CVE-2026-123007 · CVE-2026-123634 · CVE-2026-123633 · CVE-2026-121810 · CVE-2026-113425)의 영향을
  받는 버전인지 봅니다. 아무것도 바꾸지 않습니다.
- **꼭 할 일** *취약* 이면 nginx 를 고친 버전(1.31.9 이상 · stable 갈래는 1.30.7 이상 · 배포판이 고친 패키지를 내면 그
  패키지 · Windows 는 nginx.org 의 고친 zip)으로 올리고 **다시 시작**합니다 — 설정을 다시 읽는 것(reload)으로는 실행 파일이 바뀌지 않습니다. 배포판의 고친 패키지가 아직 없으면 쓰지 않는
  기능을 꺼서 막습니다: HTTP/2 끄기(1.25.1 이상은 server 블록에 `http2 off;` 와 listen 의 `http2` 빼기 · 그 아래는 listen 의
  `http2` 빼기) · HTTP/3 끄기(`quic` listen 줄을 빼고 `http3 off;`) · 메일 프록시 리스너는 루프백이나 믿는 주소에만 · 요청
  값으로 업스트림을 정하는 `proxy_pass` 에 `mirror` 를 쓰면 고정 upstream 으로(필요 없으면 `mirror off;`). SCTP 를 쓰지 않는
  호스트는 커널 SCTP 를 막습니다(`/etc/modprobe.d/` 의 설정 파일에 `install sctp /bin/false` — 이미 실린 모듈은 그대로라
  확인합니다). 이 방법들은 분석 글이 알려 준 임시 조치입니다.
- **못 보는 것** 아래 *보는 자리* 밖에 깔았고 돌지도 않는 nginx(Windows 는 nginx.org 안내의 기본 자리 `C:\nginx-<버전>`
  처럼 버전마다 이름이 다른 폴더도 — 돌거나 서비스면 *확인 필요* 로 알립니다) · 컨테이너 안의 nginx · NGINX Plus(F5)와 nginx 를

  다시 점검하십시오.

## Node.js — Node2Shell (점검만 합니다)

- **점검만 합니다** — `node` 실행 파일이 Node.js 공식 빌드의 어느 버전인지(파일 해시)와 배포판 패키지의 보안
  공지로 Node2Shell(CVE-2026-111497 · Brotli 압축 해제)이 고쳐졌는지 봅니다. Windows 에서는 PHP 폴더의
  `brotlidec.dll` 도 봅니다. 아무것도 바꾸지 않습니다.
- **꼭 할 일** *취약* 이면 Node.js 를 고친 버전(22.23.4 · 24.22.1 · 26.12.1)으로 올리고 그것을 쓰는 서비스를
  **다시 시작**합니다 — 18 · 20 은 지원이 끝나 고친 버전이 없으니 위의 고친 버전으로 옮깁니다. PHP for Windows 는
  Brotli 를 고쳐 다시 지은 공식 빌드(2026-10-26 의 `8.x.y-1`) 이후의 것으로 바꿉니다.
- **못 보는 것** 다른 제품 안에 든 Node.js(Electron 앱 · 단일 실행 파일 · 컨테이너 이미지) · 정해 둔 자리 밖에
  놓였을 뿐 실행 중도 아니고 어디에도 적히지 않은 `node` · 옛 파일이 남은 채 떠 있는 프로세스가 고친 버전을
  실었는지. 정해 둔 자리 밖의 `node` 가 **실행 중이거나**, 서비스(Windows 서비스 · NSSM · systemd 유닛 · SysV ·
  OpenRC · Upstart 시작 스크립트)나 Node.js 설치 프로그램(Windows)이 그 자리를 가리키면 경로를 적어 *확인 필요* 로
  알립니다 — 그 `node` 는 판정하지 않습니다. 시작 스크립트는 실행하지 않고 읽어, 글자 그대로 풀리는 실행 파일
  자리만 봅니다(셸 함수 · 명령 치환으로 정한 경로 · `pm2` · `npm` 으로 띄우는 앱은 보지 않습니다).
  리눅스에서 고친 뒤 다시 시작하지 않아 지워진 옛 파일(`node` · `libnode` · Brotli 라이브러리)을 실은 채 도는
  프로세스도 *확인 필요* 입니다.

## PHP — PHP2Shell · 세션 업로드 진행 설정 (점검만 합니다)

- **점검만 합니다** — PHP 의 버전 · 공식 빌드(파일 해시) · 배포판 패키지로 PHP2Shell(CVE-2026-109618 · 109619)이
  고쳐졌는지, 설정 파일로 세션 업로드 진행 기능(CVE-2026-115560)이 켜졌는지 봅니다. 아무것도 바꾸지 않습니다.
- **꼭 할 일** *취약* 이면 PHP 를 쓰는 계열의 고친 버전(8.2 는 8.2.35 · 8.3 은 8.3.36 · 8.4 는 8.4.27 · 8.5 는
  8.5.12, 또는 배포판의 보안 갱신)으로 올리고 PHP 를 쓰는 웹 서버 · PHP-FPM 을 **다시 시작**합니다 — 8.1 이하는
  고친 버전이 없어 이 가운데 하나로 옮깁니다. 11월 보안 업데이트까지 막으려면 8.2.36 · 8.3.37 · 8.4.28 · 8.5.13 이상으로
  올립니다([PHP 11월 보안 업데이트 점검](#php-2026-11)). 세션 결함(CVE-2026-115560)은 2026-11-19 보안 업데이트가
  고쳤습니다 — 그 버전 이상으로 올리고, 설정에서 업로드 진행을 켠 곳이 있으면 올린 뒤에도 같은 세션 저장소를 쓰는 앱 · 풀의
  `session.serialize_handler` 를 같게 맞추거나 업로드 진행을 끕니다(아래 *세션 설정*). 세션 점검은 룰 2026.11.20.3 부터
  찾은 PHP 가 모두 고친 버전이고 설정에서 직접 켜지 않았으면 *취약한 곳을 찾지 못했습니다* 로 끝나고, 그 밖에는 *확인 필요*
  입니다 — 고치기 전 버전에서 앱이 실행 중에 `session.serialize_handler` 를 바꾸면 `session.upload_progress.enabled = 0`
  으로 두고 다시 시작합니다.
- **못 보는 것** 옛 파일이 남은 채 떠 있는 PHP 가 고친 버전을 실었는지 · 정해 둔 자리 밖에 놓였을 뿐 쓰이지도
  적히지도 않은 PHP · 앱 코드가 실행 중에 바꾸는 설정(`ini_set()`) · 웹 폴더의 `.user.ini` · `.htaccess`, 웹 서버가 넘기는
  `PHP_VALUE`, 명령줄 · IIS FastCGI 의 `-d` 로 켠 세션 업로드 진행 설정(고친 버전에서 그렇게만 켰다면 세션 점검이
  *취약한 곳을 찾지 못했습니다* 로 끝나도 직렬화기를 같게 맞추십시오). Windows 의 WampServer 는 Apache 폴더에 두는 PHP 링크
  때문에 고친 버전으로 올려도 두 점검이 *확인 필요* 로 남습니다. 정해 둔 자리 밖의 PHP 를 IIS(Windows) · Apache
  설정 · 서비스가 가리키거나, 그 PHP 가 **실행 중이거나** 다른 프로그램(Apache 등 · Windows)에 모듈로 실려
  있으면 경로를 적어 *확인 필요* 로 알립니다 — 그 PHP 는 판정하지 않습니다. 리눅스에서 고친 뒤 다시 시작하지 않아
  지워진 옛 파일(실행 파일 · `libphp`)을 실은 채 도는 PHP 도 *확인 필요* 입니다.

## PHP2Shell · Apache HTTP/2 원격 점검 — 웹서버 응답 헤더 (네트워크를 씁니다)

- **바깥에서 봅니다** — 적어 주신 주소(URL)의 웹서버가 응답 헤더로 알리는 버전을 견줍니다. PHP 는 PHP2Shell
  (CVE-2026-109618 · 109619)의 고친 버전과, Apache 는 HTTP/2 모듈 원격 코드 실행(CVE-2026-119618)의 영향 범위와
  봅니다. 이 기계는 검사하지 않고, 그 서버에도 아무것도 바꾸지 않습니다. **소유하거나 점검을 허락받은 서버에만**
  쓰십시오 — 시작할 때 이용 조건에 동의를 받습니다.
- **Apache 는 HTTP/2 를 켰을 때만 취약입니다** — 헤더가 아파치 재단 소스로 지은 버전(OS 표시 `Unix` · `Win32` ·
  `Win64`)의 영향 버전(2.4.55 ~ 2.4.70)을 알리고, 같은 응답이 HTTP/2 를 알리면(`Upgrade: h2` · `h2c`) *취약* 입니다.
  배포판이 지은 Apache(`Debian` · `Ubuntu` · `Rocky Linux` 등)는 버전을 그대로 두고 패치를 넣어 헤더로는 가릴 수
  없으므로 *확인 필요* 로 나옵니다. 요청은 PHP 와 같은 HEAD 한 번입니다.
- **꼭 할 일** *취약* 이든 *확인 필요* 든 **그 서버에서** remedy 의 *PHP2Shell 점검* · *Apache HTTP/2 점검* 으로
  확인합니다. 헤더는 서버가 스스로 적는 글자라, 이 점검은 '괜찮다' 를 말하지 않습니다 — *취약* 이 나오지 않아도
  안전하다는 뜻이 아닙니다.
- **못 보는 것** 버전을 숨긴 서버 · 리버스 프록시 뒤의 실제 서버 · 배포판이 고쳐 넣은 패치(백포트) · HTTP/2 를
  알리지 않게 한 Apache(`H2Upgrade off`) · PHP 세션 설정.

<details>
<summary>자세히 — 누가 통신하나 · 보내는 요청 · 네트워크를 쓰지 않으려면 · 명령으로 돌리기</summary>

- **누가 통신하나** — `remedy` 실행 파일은 통신하지 않습니다. 이 항목을 고르면 그렇다고 알린 뒤, 받은 폴더의
  `remedy-net` 폴더에 든 프로그램을 실행해 맡깁니다. 실행하기 전에 그 프로그램의 서명을 룰과 같은 방식으로
  확인하고, 맞지 않으면 실행하지 않습니다.
- **보내는 요청** — 주소마다 HEAD 요청 한 번(서버가 HEAD 를 받지 않을 때만 GET 한 번, 본문은 읽지 않습니다).
  요청 사이는 2초이고 주소는 50개까지입니다. 리다이렉트를 따르지 않고, 프록시 · 쿠키 · 로그인 정보를 쓰지
  않습니다. 서버가 요청 제한이나 오류로 답하면 그 서버에는 더 요청하지 않습니다. 서버의 접속 기록에는 남습니다.
- **권한** — 관리자 권한이 없어도 됩니다. 리눅스에서 `sudo ./remedy` 로 띄운 메뉴에서 고르면 `remedy-net` 은
  root 가 아니라 sudo 를 건 사용자의 권한으로 실행됩니다. 그 사용자가 받은 폴더에 닿지 못하면(root 의 홈에
  풀었을 때 등) 그렇다고 알리고 root 로 실행합니다.
- **결과 파일** — 메뉴에서 고르면 받은 폴더의 `out/<시각>/remedy-net/` 에 남고, 화면 끝에 그 경로가 적힙니다.
- **네트워크를 쓰지 않으려면** — 받은 폴더의 `remedy-net` 폴더를 지우십시오. *원격 점검* 항목과 아래 이미지 ·
  컨테이너 점검이 빠지고, `remedy` 의 검사 · 치료는 그대로 씁니다.
- **명령으로 돌리기** — Windows: `.\remedy.exe scan --plugin .\plugins\php2shell-url-check\plugin.yaml --out-dir
  .\out --url https://<주소>` · 리눅스: `./remedy scan --plugin ./plugins/php2shell-url-check/plugin.yaml --out-dir
  ./out --url https://<주소>` (`--url` 은 여러 번 줄 수 있습니다). 결과는 화면과 `out` 폴더의 JSON 파일에 남습니다.
  `remedy-net` 을 직접 실행하면(`./remedy-net/remedy-net url https://<주소>`) `--runtime php` · `apache` 로 하나만
  고를 수 있습니다 — 주지 않으면 둘 다 봅니다.

## 이미지 파일 · 컨테이너 — PHP · Node.js · Apache (점검만 합니다)

- **이미지와 컨테이너를 봅니다** — 메뉴에는 없고, 받은 폴더의 `remedy-net` 을 직접 실행합니다. 이미지
  파일(`docker save` · OCI)이나 이 기계에서 실행 중인 컨테이너의 PHP · Node.js 를 봅니다. PHP2Shell · Node2Shell 은 받은
  폴더의 판정 기준(아래 *못 보는 것* 의 2026-10-30 버전)으로 보고, 세션 업로드 진행 설정은 버전을 보지 않아 PHP 가 있으면
  늘 *확인 필요* 로 알립니다(위 세션 점검의 '고친 버전이고 직접 켜지 않았으면 문제없음' 은 이 점검에 해당하지 않습니다).
  Apache 는 HTTP/2 모듈 원격 코드 실행(CVE-2026-119618) 기준으로 봅니다. 아무것도 바꾸지 않고, 시작할 때 이용 조건에 동의를
  받습니다.
- **Apache 판정은 리눅스 Apache 점검과 같습니다** — 배포판의 고친 판보다 낮고 HTTP/2 를 켠 설정(모듈 적재와
  `Protocols` 의 `h2` · `h2c`)이 있으면 *취약*, 켠 흔적을 다 찾지 못하면 *확인 필요* 입니다. 판은 패키지 기록이
  실제 모듈 파일과 맞을 때만 믿고, 공식 `httpd` 이미지는 그 이미지가 밝힌 판(`HTTPD_VERSION`)으로 봅니다.
- **꼭 할 일** *취약* 이면 고친 버전으로 이미지를 다시 짓고 컨테이너를 새로 띄웁니다. 컨테이너 점검은 엔진에서
  읽을 수 있는 파일만 보므로 '괜찮다' 를 말하지 않습니다 — *취약* 이 나오지 않아도 안전하다는 뜻이 아닙니다.

- **명령** — Windows: `.\remedy-net\remedy-net.exe image app.tar` · `.\remedy-net\remedy-net.exe container --list`

  PHP · Node.js · Apache 를 모두 보고, `--runtime php` · `node` · `apache` 로 하나만 고를 수 있습니다.
- **여러 컨테이너를 한 번에** — 한 번 실행에 엔진 요청은 128회까지입니다. 셋을 모두 보면 컨테이너 하나에 서른 번
  안팎이 들어(2026-11-14 실측 — 둘에 61회) 넷쯤을 넘으면 뒤의 것은 *확인 필요* 로 남을 수 있으니 나눠
  실행하십시오.
- **받는 형식** — `docker save` 로 저장한 파일 · OCI 아카이브 · OCI 레이아웃 폴더(gzip · zstd 레이어도). 여러
  플랫폼이 든 이미지는 플랫폼마다 결과가 나오고, 저장되지 않은 플랫폼은 *확인 필요* 로 남습니다 — `docker save
  --platform linux/amd64 …` 처럼 하나만 저장하면 깔끔합니다. 이미지 하나로 된 파일은 결과 폴더 아래에 잠시
  풀었다가 지우므로 그만큼 디스크가 필요합니다.
- **권한** — 이미지 점검은 관리자 권한이 필요 없습니다. 컨테이너 점검은 리눅스에서 root 로 실행합니다 — 엔진
  (dockerd · podman)이 정말 떠 있는지 확인하고, 꺼져 있으면 접속하지 않습니다(접속이 엔진을 띄울 수 있어서입니다).

  않습니다(종료 코드 4) — 받은 파일을 통째로 다시 푸십시오.
