# 제거 대상 선언

선행: `00-invariants.md` · 전수는 `machine/ops.json`

**순서를 적지 않는다.** 프로세스 종료·비활성화·백업·삭제의 차례는 코어가 정한다.
플러그인은 **무엇을 없앨 것인가**만 선언한다 — 그래야 순서 실수가 플러그인마다
재발하지 않는다.

---

## 두 가지 선언 방식

```yaml
remediate:
  remove:
    - { ref: task }                                    # 증거를 가리킨다
    - { path: "${task.payload_dir}", recursive: true, guard: payload }   # 경로를 가리킨다
  restore:
    - av_exclusions
  verify:
    after_reboot: true
```

| | 언제 |
|---|---|
| `ref` | **기본형.** 증거 하나가 곧 대상이다. 대상 문자열은 계획기가 만든다 |
| `path` | 증거가 아니라 **그 증거가 가리킨 디렉터리**를 없앨 때. `guard` 필수 |

`ref` 가 어떤 Op 으로 바뀌는지는 **subject 가 정한다** — 파일은 격리, 예약 작업은
비활성화+삭제, 서비스는 정해진 차례, **바로가기는 인자만 뗀다**(`shortcut.strip_args` ·
파일은 남는다), **설정 항목은 그 키만 뺀다**(`structured_config.remove_key`).
플러그인이 Op 을 직접 고르지 않는다.

> **`persistence` 는 없어지는 것이 플랫폼마다 다르다.** cron 은 **그 줄만**
> 빠지고 **파일은 남는다** — `id` 가 `<파일>:<줄번호>` 인 그대로다. systemd 는
> 유닛과 `.wants/` 링크를 함께 지운다. **파일째 치워야 하면 `file` 규칙을 따로
> 둔다** — 드롭인에 검체의 줄 하나뿐이면 빈 파일이 남는다.

## 재귀 삭제 — 여섯 조건을 전부 만족해야 한다

```yaml
    - { path: "${task.payload_dir}", recursive: true, guard: payload }
```

| | 조건 | 어디서 본다 |
|---|---|---|
| 1 | 대상이 **증거에서 파생된 경로** (리터럴 금지) | 계획 |
| 2 | 그 디렉터리 **안에서** 악성 판정된 것이 최소 1개 (`guard`) | 계획 |
| 3 | 하위에 **신뢰 서명 파일**이 있으면 거부 | 실행 (파괴 직전) |
| 4 | 1층 보호 목록과 교차하면 거부 | 계획 |
| 5 | 대상이 **`scan_roots` 상한 자체**면 거부 | 계획 |
| 6 | 하위 항목 수·깊이가 **규모 상한**을 넘으면 거부 | 실행 (파괴 직전) |

**6번도 실행 시점이다.** 그 폴더에 몇 개가 얼마나 깊이 있는지는 계획 시점에
알 수 없다. 상한은 코어 정책이고 **플러그인이 조정할 수 없다** — 계획에 각인되어
보고에 나오므로 걸렸을 때 무엇에 걸렸는지는 보인다.

**걸리면 대상이 너무 넓다는 신호다.** `capture` 를 한 겹 더 좁히거나(조건 5 의
정규식처럼) 재귀 삭제를 빼고 파일 하나하나를 `ref` 로 지운다.

**3번이 실행 시점인 이유**: 계획기는 파일 시스템을 열거할 수 없다. 그 디렉터리에
무엇이 들어 있는지는 실행기만 안다. 판정 자리가 **백업 전**이므로 막는다는 성질은
그대로다.

### 재귀 삭제를 써도 파일 `ref` 를 함께 둔다

```yaml
    - { ref: payload }                                          # ← 함께 둔다
    - { path: "${task.dir}", recursive: true, guard: payload }
```

폴더를 통째로 지우니 개별 파일 제거는 불필요해 보인다. **그런데 재귀 삭제는
걸릴 수 있고, 걸리는 자리마다 결과가 다르다.**

| 무엇에 | 언제 | 걸리면 |
|---|---|---|
| `guard` 가 아무것도 못 잡음 | 계획 | **그 Action 만 미뤄진다.** 나머지는 수행되고 이유가 보고에 남는다 |
| 그 밖 (1·2·4·5) | 계획 | **계획 전체가 거부된다** (종료 코드 5). 하나도 실행되지 않는다 |
| 3 · 6 | 실행 | 그 Action 만 실패한다 (코드 3) |

가르는 것은 **기계별 사실이냐 매니페스트 결함이냐**다. guard 가 못 잡은 것은
그 폴더에 악성이 없다는 사실이고, 리터럴 경로나 바깥을 가리키는 근거는
언제나 결함이다. 둘째 줄은 `deferred` 가 아니라 **가드 위반**이다.

> **`guard` 를 필수 아닌 근거에 걸어도 된다.** `A and (B or C)` 에 `guard: B`
> 면 B 가 없는 기계에서 재귀 삭제만 미뤄지고 A·C 는 치료된다 — *"안에서
> 실제로 찾았을 때만 폴더째 지운다."* 그 폴더의 파일은 아래 `ref` 가 맡는다.

`file.quarantine_only` 는 위험 `low` 이고 되돌릴 수 있다.
`dir.delete_recursive` 는 `high` 다. **덜 위험한 경로를 빼고 더 위험한 것만
남기지 않는다** — 둘은 대체가 아니라 겹침이다.

**페이로드만이 아니다.** 폴더 전체가 검체가 만든 것이라면 나머지 파일도 함께
겹쳐 둔다.

```yaml
- id: companion                       # 같은 폴더의 나머지 — 판정에는 쓰지 않는다
  subject: file
  from: "${svc.dir}"
  where:
    - { field: path, op: not_equals, value: "${svc.exe}" }
```

그 파일들이 **검체가 모아 둔 것**일 수 있다. 격리하면 분석에 넘길 수 있고
(`submit_hint.samples`), 재귀 삭제가 보류돼도 남지 않는다.

**부모가 디렉터리만 capture 했다면** 뺄 파일 경로가 없다. 그때는 `where` 를
`{ field: path, op: exists }` 로 두고 `from` 에게만 범위를 맡긴다. **린트가
경고하고 그것이 맞다** — `from` 은 *어디*를 좁히지 *몇 개*를 좁히지 않는다.
`starts_with "${svc.dir}"` 로 돌려 적어도 같은 경고다. 서명 단계에서 "폴더
전체가 검체의 것" 이라는 관측을 이유로 적는다.

> **3번이 걸리면 룰을 고쳐야 한다.** 정상 서명된 프로그램 폴더에 악성 파일이
> 떨어진 경우가 그것이다 — 폴더를 통째로 지우면 정상 프로그램이 부서진다. 그때는
> 재귀 삭제를 빼고 **파일 하나하나를 `ref` 로** 지운다.

**`guard` 는 그 안을 가리켜야 한다.** 계획기가 다시 확인한다 — `because` 가 비어
있지 않다는 것만으로는 부족하고, 근거가 엉뚱한 곳을 가리키면 거부된다.

### 조건 5 — `capture` 가 한 단계 얕게 풀리는 것을 막는다

**조건 2 가 못 막는 경우가 있다.** 페이로드가 상한 바로 아래에 있으면
`dirname` 이 상한 자체가 되는데, 그 안에 악성 판정 파일이 있으므로 조건 2 는
통과한다.

```
args = "…\AppData\Local\Programs\loader.js"
  → first_path → "…\Programs\loader.js"
  → dirname    → "…\Programs"          ← 상한 자체
```

`%LOCALAPPDATA%\Programs` 에는 **사용자가 설치한 정상 프로그램이 전부 있다.**

계획기가 이것을 거부하지만(조건 5), **거부는 마지막 방어선이지 정상 경로가
아니다.** 룰 쪽에서 그 모양이 나오지 않게 한다.

```yaml
# 폴더가 최소 하나 있어야 매치된다 — dirname 이 상한이 될 수 없다
- { field: args, op: matches,
    value: '(?i)\\AppData\\Local\\Programs\\[^"]+\\[^\\"]+\.js("|\s|$)' }
```

**위협 설명이 "폴더 안에" 라고 말했다면 그 한 겹을 조건에 넣는다.** 넣지 않으면
룰은 상한 자체도 매치하고, 그 계획은 실행 직전에 멈춘다.

## 신뢰 서명이 삭제를 막는다

유효한 신뢰 벤더 서명이 있는 실행 파일은 **기본적으로 삭제 대상에서 빠진다.**
그리고 빠졌다는 사실이 `deferred` 로 보고된다 — 조용히 사라지지 않는다.

```yaml
# 서명된 악성코드를 지워야 한다면 — 주체나 지문을 열거한다
signed_malware:
  - { subject: "CN=Some Vendor, O=Some Vendor" }
  - { thumbprint: "3EB14A3AEF84B7153E139397F0A49E2FAC662B0E" }
```

**빈 목록으로는 아무것도 통과하지 못한다.** 목록 자체가 플래그이므로 "무시" 를
표현할 방법이 없다 — 근거 없이 예외를 여는 것보다 옳은 실패 방향이다.

**모르면 비워 둔다.** 서명된 대상을 만나면 삭제가 막히고 그 사실이 보고되므로,
그때 실제 주체를 보고 넣는다.

## 값의 일부만 지운다 — `edit`

**통째로 지우면 시스템을 못 쓰게 되는 대상이 오히려 주류다.** 로그온 셸을
지우면 로그인이 안 되고, 검색 경로를 지우면 명령이 안 돈다. 그럴 때는 값을
남기고 **검체가 덧붙인 부분만** 뺀다.

```yaml
remediate:
  edit:
    - { ref: hijack, op: strip, value: "${hijack.payload}" }
```

`op` 는 지금 `strip` 하나다. 대상이 검색 경로 계열이면 `env.strip_path`,
아니면 `registry.strip_value` 가 된다 — **계획기가 증거를 보고 정한다.** 바로가기
인자는 여기가 아니라 `remove` 다(위).

**`value` 는 증거에서 파생돼야 한다.** 리터럴 문자열로 임의 편집을 지시할 수
없다 — 그것을 허용하면 이 도구가 "무엇이든 고칠 수 있는 것" 이 되고, 서명의
뜻이 *"이 지시서를 검토했다"* 에서 *"이 프로그램을 검토했다"* 로 바뀐다
(`31-nonexistent.md` 의 같은 이유).

### `value` 는 **무엇과 견주는가**

대상 값의 타입이 자르는 단위를 정한다. 여기를 모르고 적으면 **아무것도 지우지
않고 성공으로 끝난다** — 두 자리 다 실제로 그렇게 됐다 (2026-09-05 실기기).

| 값의 타입 | 자르는 단위 | `value` 에 적을 것 |
|---|---|---|
| `REG_SZ`·`REG_EXPAND_SZ` | 부분 문자열 | 뺄 조각 그대로 (`,C:\evil.exe`) |
| `REG_MULTI_SZ` | **항목 하나** | 항목 전체, 또는 명령줄 항목의 앞 토큰 |
| 경로 변수(`env.strip_path`) | **`;` 로 가른 항목** | 경로만 — **`;` 를 붙이지 않는다** |

- **목록에서 부분 문자열로 자르지 않는다.** `alyac.exe` 가 정상 보안 제품의
  `bootalyac.exe` 에 걸리면 부팅 항목을 잘못 없앤다.
- `REG_MULTI_SZ` 의 **빈 항목도 항목이다.** 남는다.
- 그 밖의 타입(`REG_DWORD` 등)은 거부된다 — 거기서 문자열을 잘라 내는 것은
  편집이 아니라 손상이다.

> **`remove` 와 헷갈리지 말 것.** 같은 증거를 `remove` 에 넣으면 값이 통째로
> 사라진다. 값 전체가 검체의 것이면 그것이 맞고, 원래 값에 덧붙은 것이면
> `edit` 이 맞다. **어느 쪽인지는 관측이 말한다** — 정상값을 알 수 없으면
> `to: default`(아래)를 쓸 수 있는지부터 본다.

## 원복은 파괴가 아니다

```yaml
  restore:
    - av_exclusions      # 보안 제품 예외 목록에서 우리 경로를 뺀다
```

`restore` 는 별도 절이다 — 상한·백업·롤백의 대상이 아니다. 되돌리는 것이므로
되돌릴 것이 없다.

### 되돌릴 **증거**가 있어야 한다

`restore: [av_exclusions]` 는 *"제외 목록을 비워라"* 가 아니다. **`av_exclusion`
subject 의 증거를 되돌린다** — 룰이 짚은 항목만.

그래서 그 subject 를 탐지하는 규칙이 하나도 없으면 **되돌릴 것이 잡히지 않고
Action 이 아예 만들어지지 않는다.** `deferred` 에도 걸리지 않으므로 계획은
초록인데 제외 경로는 그대로 남는다.

```yaml
detect:
  - id: av-exclusion                       # ← 이것이 있어야 한다
    subject: av_exclusion
    where:
      - { field: value, op: contains, value: "${task.dir}" }
remediate:
  restore:
    - av_exclusions
```

| 이름 | 되돌릴 증거의 subject |
|---|---|
| `av_exclusions` | `av_exclusion` |
| `hosts` | `hosts_entry` |
| `proxy` | `proxy_config` |
| `firewall` | `firewall_rule` |

`plugin lint` 가 짝이 없는 경우를 오류로 막는다.

### `to: default` — OS 기본값으로 되돌린다

**검체가 만든 것이 아니라 덮어쓴 값이 있다.** 로그온 셸(`Winlogon\Shell`·
`Userinit`)과 AppInit 스위치(`LoadAppInit_DLLs`)가 그렇다. 지우면 로그인이
깨지거나, **안 깨져도 감염 전으로 돌아가지 않는다**(30 §14).

```yaml
remediate:
  restore:
    - { ref: userinit, to: default }     # ← restore 절이다. remove 가 아니다
```

**`remove` 절에 쓸 수 없다.** `remove` 는 `{ ref: … }` 와 `{ path: … }` 만
받으므로 `to: default` 를 거기 두면 **린트가 아니라 파싱에서 멈춘다.**

```
remediate.remove: data did not match any variant of untagged enum RemoveTarget
```

되돌릴 수 있는 대상은 **코어가 내장한 카탈로그에만** 있다 — 전수는
`machine/REFERENCE.md` §`restore_default` 가 되돌릴 수 있는 대상. 거기 없는
것을 지정하면 린트가 거절한다. 플러그인이 임의 레지스트리 값을 쓸 수 있으면
서명된 도구가 그 자체로 공격 도구가 되기 때문이다.

**규칙이 대상을 리터럴로 못박아야 한다.** `hive`·`key`·`name` 을 전부
`equals` 로 적어야 린트가 그것이 카탈로그에 있는지 확인할 수 있다.

```yaml
- id: userinit
  subject: registry_value
  where:
    all:
      - { field: hive, op: equals, value: "HKLM" }
      - { field: key,  op: equals, value: "SOFTWARE\\Microsoft\\Windows NT\\CurrentVersion\\Winlogon" }
      - { field: name, op: equals, value: "Userinit" }
      - { field: data, op: contains, value: "${svc.exe}" }   # 이 감염에 묶는다
```

못박지 않으면 대상이 증거마다 달라지므로 **계획 단계에서 판정**되고, 린트는
그 사실을 경고로 남긴다.

> **왜 룰이 짚은 것만 되돌리는가.** 제외 목록을 통째로 비우면 사용자가 의도해서
> 넣은 예외(사내 도구·개발 폴더)까지 사라진다. 그것은 원복이 아니라 파괴다.

## 재부팅 후 재평가

```yaml
  verify:
    after_reboot: true
```

`apply` 가 끝나면 코어가 **일회성 자동실행 항목**을 등록해 재부팅 뒤
`remedy verify --run <id> --plugin <경로>` 를 돌린다.

**`verify` 는 경로 확인이 아니라 재판정이다.** *"제거한 경로가 여전히 비어
있는가"* 만 보면 랜덤 이름을 쓰는 위협 앞에서 무력하다 — 재감염은 **다른 랜덤
이름**으로 생기고 원래 경로는 계속 비어 있다. 그래서 수집과 평가를 다시 돌려
**같은 플러그인이 다시 판정하는지**를 본다.

| 결과 | 뜻 |
|---|---|
| 판정 없음 | 치료 성공 — 다 못 봤으면 종료 6 |
| 다시 판정됨 | **재발.** 자동으로 다시 치료하지 않는다 — 우리가 놓친 지속성 경로가 있다는 신호이므로 사람이 본다 |
| 일부만 잔존 | 부분 치료로 보고 |

> 코어가 심는 자동실행 항목은 **고정된 이름**을 쓰고, **실행 직전에 지워지며**
> (Windows 는 OS 가 RunOnce 를, 리눅스는 systemd 유닛이 스스로), 걸린 자리가
> 화면과 감사 로그에 남는다. 치료 도구가 정체불명의 자동실행을 남기면 그 자체가
> 타 백신의 탐지 대상이 된다.

**걸 수 없는 기계가 있다.** 리눅스는 systemd 가 init 인 기계에서만 건다. 아닌
곳(컨테이너 등)에서는 계획 화면이 **승인 전에** 그렇다고 말하고, 치료 뒤 직접 부를
명령을 준다 — 걸지 못해도 치료의 실패가 아니다.

---

## 계획에 들어가지 못한 것은 보고된다

Op 이 아직 오지 않았거나 가드에 걸리면 그 항목은 `deferred` 로 나온다.
**조용히 빠지지 않는다** — 빠진 채로 초록이 뜨면 사용자는 치료가 끝난 줄 안다.

```
계획에 넣지 못한 것 1건
  remediate.remove[3]  dir.delete_recursive — …
```

`deferred` 가 비어 있지 않으면 **이 계획은 치료의 전부가 아닙니다.**

---

## 자주 막히는 곳

**`ref` 는 규칙 id 를 가리킨다.** 증거 id(`payload#0`)가 아니다.

**`path` 에 리터럴을 적을 수 없다.** `${…}` 보간을 거친 파생 경로만 받는다.

**`recursive: true` 는 `guard` 를 문법 수준에서 요구한다.** 린트가 거부하므로
계획기까지 가지 않는다.

**격리는 삭제가 아니다.** 파일 제거는 가장 덜 위험한 Op 으로 간다 — 격리는
옮기는 것이라 되돌리기가 Op 의 정의 자체에 들어 있다. 격리물은 자동으로 지워지지
않으므로 오탐이어도 `remedy restore --run <id>` 로 되돌릴 수 있다.
