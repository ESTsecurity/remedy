# 본문 수집과 제출 힌트

선행: `20-detect-recipes.md` · 전수는 `machine/plugin.schema.json`

## `collect_extra` 가 필요한 이유

**평가기는 파일 시스템을 열 수 없다.** 그래서 YARA 가 훑을 바이트는 **수집
시점에 스냅샷에 담겨 있어야** 하고, `collect_extra` 가 그 바이트가 들어오는
**유일한 문**이다.

선언하지 않으면 YARA 술어는 *"안 맞았다"* 가 아니라 **"재지 못했다"** 를 낸다.
관측 불완전으로 이어지고 판정이 서지 않는다. `plugin lint` 가 막는다.

**파괴가 아니다.** 계획에 나타나지 않고 승인 게이트를 거치지 않는다. 그래서
상한이 더 중요하다 — `scan_roots` 밖은 담지 않는다.

---

## 세 가지 형태

```yaml
collect_extra:
  - { ref: payload-file, content: true }              # 증거가 가리킨 파일의 본문
  - { path: "${task.dir}\\config.json", max_size: 1MB }  # 경로의 본문
  - { subject: text_config, path: "${task.dir}" }    # 그 경로를 이 subject 로도 본다
```

| 형태 | 본문을 담는가 | 언제 |
|---|---|---|
| `ref` | `content: true` 일 때만 | **기본형.** 증거가 가리킨 파일 |
| `path` | 담는다 | 증거에서 파생된 특정 경로 하나 |
| `subject` | **담지 않는다** | 그 경로를 다른 관점으로도 훑게 한다 |

### `subject` 형은 본문을 담지 않는다

*"이 경로를 이 subject 로도 보라"* 는 뜻이고, 실제 수집은 그 subject 의
수집기가 한다. **YARA 를 쓰면서 이것만 두면 본문이 없다.**

`scan_roots` 안이어야 하고, 그 subject 가 매니페스트의 `subjects` 에 선언돼
있어야 한다. 아니면 미해소로 보고된다.

---

## `ref` 형은 두 번째 패스에서 풀린다

`ref` 는 **증거를 가리킨다.** 증거는 평가가 만들고, 평가는 수집 뒤에 온다.
그래서 수집 시점에는 그 이름이 무엇을 가리키는지 알 수 없다.

```
  수집 → 1차 평가 → (증거로 ref 해소) → 본문 담기 → 재평가
```

**`collect` 단독 실행에서는 풀리지 않는다.** 증거가 없기 때문이고, 그 사실이
미해소로 보고된다 — 조용히 건너뛰면 그 본문에 걸린 YARA 규칙이 영영 미평가인데
판정은 "안 맞았다" 로 나간다. 해소하려면 `scan` 이나 `run` 으로 돌린다.

### 가리킬 규칙은 본문 없이 매치될 수 있어야 한다

```yaml
  - { ref: payload, content: true }        # ✗ payload 가 YARA 뿐이면 순환
  - { ref: payload-file, content: true }   # ✓ 경로로 매치되는 규칙
```

1차 평가에서 매치되지 않으면 담을 것을 정하지 못한다. `30-antipatterns.md`
1번이 이 항목이다.

### 없는 규칙과 안 맞은 규칙은 다르다

- **없는 규칙**을 가리키면 린트 오류다. 영영 해소되지 않는 선언이다.
- 있는데 **안 맞았으면** 정상이다. 담을 것이 없는 것이고 미해소가 아니다.

## 상한

| | 값 |
|---|---|
| 파일 하나 | `max_size` 로 지정. 없으면 **8 MB** |
| 스냅샷 전체 | **64 MB** |

`max_size` 는 `1MB` · `512kb` · `2048`(단위 없으면 바이트) 로 적는다.

상한을 넘은 파일은 **조용히 빠지지 않는다** — 미해소로 보고된다. 상한이 없으면
룰 하나가 `%APPDATA%` 를 통째로 담을 수 있고, 스냅샷은 사내 분석 시스템으로
오가는 물건이라 개인정보가 그만큼 실려 간다.

**필요한 것만 담는다.** 본문 담기는 스냅샷을 키우고 개인정보 위험을 올린다.

## `submit_hint` — 손으로 올리는 사람에게 남기는 말

```yaml
submit_hint:
  samples: [payload]          # 제출하면 유용한 증거의 규칙 id
  confidentiality_min: 1      # 기밀 등급 하한
```

**제출 기능은 제품에 없다.** 분석가가 필요할 때 손으로 올리고, remedy 는
`support-bundle` 까지만 만든다 (설계-09 "제출을 제품 밖으로").

그래서 이 값은 자동 제출기가 볼 것이 아니라 **그 꾸러미를 들고 올리는 사람**이
본다. 계획이 그것을 나르고 `support-bundle` 이 보여 준다.

```
플러그인이 남긴 것 — 손으로 올릴 때 보십시오
  함께 올리면 유용한 증거: payload
  기밀 등급 하한: 1 — 이 등급 아래로 다루지 마십시오
```

### `confidentiality_min` 은 하한만 올린다

| 값 | 의미 |
|---|---|
| 0 | 공개 — **API 기본값** |
| 1 | 대외비 |
| 2 | 기밀 |
| 3 | 극비 |

**플러그인은 이 값을 낮추는 방향으로 영향을 줄 수 없다.** 낮출 수 있으면 서명된
룰 하나가 고객 데이터의 등급을 내릴 수 있고, 그것은 그 자체로 유출 경로다.

기본값 0(공개)이 위험한 자리라 하한을 올려 두는 것이 이 키의 목적이다. 고객
PC 에서 나온 검체에는 경로의 사용자 계정명·문서 내용이 들어 있을 수 있다.

### 자동으로 나가는 것은 없다

`remedy submit` 은 **없다.** 이 필드를 적어도 아무것도 전송되지 않는다 — 사람이
`support-bundle` 을 만들고, 그 안의 README 에서 이 값을 읽고, 무엇을 올릴지
스스로 정한다.

> 한동안 이 자리에 *"`remedy submit` 은 P14 다"* 라고 적혀 있었다. 그 Phase 를
> 제품에서 뺐다 (2026-08-28) — 나간 데이터는 회수할 수 없고, 그것은 이 도구에서
> **되돌릴 수 없는 유일한 동작**이 됐을 것이다.

`collect_extra` 는 다르다. **지금 동작한다** — YARA 가 그것에 의존한다.

## 자주 막히는 곳

**`ref` 는 규칙 id 를 가리킨다.** 증거 id(`payload#0`)가 아니다.

**`content: true` 를 빠뜨리면 본문이 담기지 않는다.** `ref` 만 적으면 그 증거를
표식으로만 남긴다.

**경로는 `${…}` 보간을 거친 파생 경로여야 한다.** 리터럴 절대 경로는 감염마다
바뀌는 것을 못 따라간다.

**미해소는 선언한 것을 담지 못했다는 뜻이다.** 본문이 빠졌으면 거기 걸린 YARA 가
결과를 가를 때 관측 불완전(6)이 된다. 줄마다 사유가 적힌다 — 대개 `scan` 이 아니라
`collect` 로 돌렸거나 · `scan_roots` 밖이거나 · 상한을 넘었거나 · 읽지 못했다.
