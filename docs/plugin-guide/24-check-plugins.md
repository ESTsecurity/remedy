# 점검 전용 플러그인 — 아무것도 바꾸지 않는 룰

선행: `00-invariants.md` · `10-manifest.md` · `20-detect-recipes.md` · 실물은 `examples/ex04-check-only`

**점검 플러그인은 `kind: check` 를 적고 `remediate` 를 뺀 플러그인이다.** 무엇이
**있는지** 만 말하고 아무것도 지우지 않는다. 대상은 **취약한 버전 · 노출된 설정**
처럼 감염이 아니라 상태다.

**선언을 적는 이유는 코어가 유추할 수 없기 때문이다.** `ex01` 도 `remediate` 가
없지만 감염 흔적을 찾는다 — 유추하면 악성 예약 작업에 *"취약"* 이라고 말한다.
적으면 코어가 **종료 코드와 화면 어휘**를 점검의 것으로 바꾼다(아래).

## 규약

| | 규약 | 왜 |
|---|---|---|
| 1 | **`kind: check` 를 적고 `remediate` 키를 뺀다** | 선언이 종료 코드와 화면 어휘를 가른다. 빈 계획은 승인을 묻지 않고 아무것도 바꾸지 않는다 — 둘을 함께 적으면 린트 오류다 |
| 2 | **`scan_roots` 를 좁게 적는다** | 바꾸지 않는다고 넓게 읽어도 되는 것이 아니다. 상한은 읽기 권한이다. 미설치 기계는 `kind: check` 덕에 **0** 으로 나간다(아래) |
| 3 | **판정 근거를 둘로 세울 수 있으면 세운다** | 아래 §근거 하나 |
| 4 | **설치본마다 그룹을 가른다** — `capture` + `from` | 섞이면 한 설치본의 사실이 다른 설치본의 판정을 바꾼다(아래 §그룹) |
| 5 | **실효값을 정하는 자리를 다 본다** | 한 파일의 한 줄이 실효값이 아닌 경우가 흔하다(아래 §설정의 실효값) |
| 6 | 꾸러미에 치료와 함께 담으면 **폴더 이름이 차례**다 | 안내 모드가 폴더를 이름순으로 늘어놓는다 — `<사고>-1-check` · `<사고>-2-clean` |

## 결과를 읽는 법 — 종료 코드가 곧 점검 결과다

| 종료 코드 | 점검의 뜻 | 화면 |
|---|---|---|
| **2** | **찾았다** — 취약하거나 노출됐다 | *취약합니다. 아래 근거를 확인하십시오.* |
| **0** | 선언한 범위에서 **없다**, 또는 그 범위가 **이 기계에 없다** | *취약한 곳을 찾지 못했습니다.* |
| **6** | **다 보지 못했다** — 수집이 잘렸거나 · 거부됐거나 · subject 를 못 모았거나 · **YARA 를 재지 못했거나** · **버전을 견주지 못했거나** · **자리를 물어보지도 못했다** · 룰이 *확인 필요* 를 냈다 | *다 보지 못해 '취약하지 않다' 를 말할 수 없습니다.* |

**`kind: check` 면 선언한 자리가 전부 없는 것은 6 이 아니라 0 이다**(B-6). `/etc/php`
가 없는 기계는 *확인 필요* 가 아니라 **해당 없음**이고 그것이 가장 흔한 경우다. 0 이
두 뜻을 담게 되었으므로 *"점검 대상이 이 기계에 없습니다"* 안내 줄이 **없던 경로와
함께** stdout 으로 나온다 — `주의:` 가 아니다(불완전이 아니다). 경로를 적는 이유는
코어가 **미설치**와 **선언 오타**를 가릴 수 없기 때문이다. 그 판단은 읽는 사람 몫이다.

단 `apply --plan`·`resume` 은 계획만 읽어 종류를 몰라 6 이다(B-7).

**`kind` 를 적지 않으면 그대로 6 이다** — 아무 곳도 열어 보지 못한 스캔이 *"위협
없음"* 을 내는 구멍(관측 01 D2)의 회귀 방지가 그쪽에 걸려 있다. **다른 사유가 섞이면
점검도 6 이다**: 면제는 *루트 전부 없음* 하나뿐이고 나머지 여섯은 그대로다(실측).

**찾은 것은 불완전보다 우선한다** — 수집이 잘려도 이미 찾은 것은 2 로 남는다.
**`not` 으로 세운 판정과 `exclude` 의 YARA · 버전은 예외다.** 잘린 수집에서는 *끄는
줄* 도 보이지 않고, 재지 못한 YARA 규칙은 *안 맞았다* 로 세어지고, 재지 못한 제외는
일어나지 않으므로 불완전이 판정을 만들 수 있다 — **못 읽은 버전도 같다**: `exclude`
에서 못 읽으면 패치된 기계가 취약으로 나간다. 2 와 함께 `주의:` 줄이 나오면 *확인 필요* 로 읽는다.

**YARA 를 재지 못해 레코드의 매치가 갈리면 6 이다**(결정 2026-10-26). 형제 술어가
이미 거짓인 레코드는 세지 않는다 — 술어 순서와 무관하다. 판정식은 보지 않는다 — 다른
필수 규칙이 0 이어도 6 이 될 수 있다(보수 쪽). 사유 줄은 *"YARA 규칙 N개를 평가하지
못했습니다: rules/…"* 이고, 규칙마다 왜 못 쟀는지는 그 위의 주의 줄이, 본문이 상한에
걸렸으면 더 위의 미해소 보고가 말한다. 판정이 섰으면 위의 규칙대로 2 가 우선한다.
YARA 로 버전을 보는 점검은 본문이 반드시 담기게 쓴다(`23-collect-and-submit.md`) —
`path` 형은 `max_size` 로 상한을 올리지만 `ref` 형은 **8 MiB 고정**이다. 그보다 큰
바이너리는 **재지 못한 것**이므로 6 이다.

*2026-10-25 까지는 0 이 나갔다*(적대 검증 · 재현). 주의 줄만 stderr 에 남았는데
무인 배포는 stderr 를 버린다 — 재지 못한 스캔이 *"위협 없음"* 을 말했다.

> **화면도 점검의 낱말을 쓴다** (B-2 · 2026-10-26). `kind: check` 면 판정 칸이
> *위협 M건* 이 아니라 **취약 M건**이고, 결과 줄과 `verify` 의 네 문구도 함께
> 갈린다 — *"치료 성공"* 은 이 룰이 한 적 없는 일이므로 *"다시 점검했습니다"* 다.
> **`검사 완료` 와 `흔적` 은 그대로다** — 하네스가 그 줄로 *"한 회차는 한 언어"* 를
> 재고, `흔적 N건` 을 읽는다.
>
> **차례는 안내문이 말한다.** 점검과 치료를 한 꾸러미로 받은 사람에게 *"점검 먼저,
> 치료 나중"* 을 알리는 것은 도구가 아니라 안내문이다(꾸러미 표준 §4). 우클릭으로
> 띄우면 안내 모드가 *"검사 항목 N개를 찾았습니다"* 로 번호를 묻는다.

## 기본값이 켜짐인 설정 — "켰다" 가 아니라 "끄지 않았다"

설정 점검에서 가장 흔한 실수다.

```yaml
verdict:
  require: "pool and not turned_off"   # ✓ 끄는 줄이 없으면 켜져 있다
```

```yaml
verdict:
  require: "pool and turned_on"        # ✗ 줄이 없는 설치본을 놓친다
```

기본값이 켜짐이면 **설정 파일에 그 줄이 없는 것이 가장 흔한 노출**이다. 주석 처리된
줄(`;` · `#`)은 수집되지 않으므로 그것도 *없음* 이다. `On` 을 찾는 규칙은 그 둘을
전부 놓친다.

**`not` 은 혼자 쓰지 않는다.** 부모가 서지 않으면 자식은 평가되지 않아 *안 맞았다*
로 세어지고, `not 자식` 은 **참**이 된다 — 혼자 쓰면 그 소프트웨어가 없는 기계에서도
증거 0건으로 판정이 선다(실측). 판정을 설치본으로 좁히는 것은 식 앞의 **`pool and`**
다.

**거짓 표기를 다 덮는다.** 수집기의 `value` 는 `=` 뒤를 다듬기만 한 원문이라 따옴표와
줄 끝 주석이 남는다. 꺼 둔 줄을 *안 껐다* 로 읽으면 오탐이다 — `ex04` 의 정규식을 본다.

## 설정의 실효값

한 파일의 한 줄이 실효값이 아닌 경우가 흔하다. 점검이 보지 않은 자리에서 **껐으면
오탐, 다시 켰으면 미탐**이다.

| 실효값을 바꾸는 것 | 예 |
|---|---|
| 포함 파일 | `conf.d/*.ini` — 이름순으로 뒤에 읽힌다 |
| 서버 쪽 덮어쓰기 | FPM 풀의 `php_value[…]` · `php_admin_value[…]` · 웹 서버가 넘기는 `PHP_VALUE` |
| 디렉터리별 설정 | `.user.ini` · `.htaccess` |
| 같은 키의 뒤 줄 | 한 파일에서 뒤에 나온 값이 이긴다 — **집합 조건으로는 쓸 수 없다** |
| 경로 · 호스트 한정 섹션 | `[PATH=…]` · `[HOST=…]` 안의 값은 그 자리에만 걸린다 |

**수집기가 못 보는 자리도 있다.** 심볼릭 링크를 따라가지 않는다(Debian 의 `phpenmod`
가 `conf.d` 에 만드는 것이 링크다). `.htaccess` 처럼 확장자가 없는 설정은 설정 수집
대상이 아니다. 보지 않는 자리는 예제 README 처럼 **"보지 않는 것"** 으로 적는다.

## 그룹 — 설치본마다 가른다

한 기계에 같은 소프트웨어가 여럿 깔린다(버전마다 · CLI 와 서버마다). 부모 규칙이
설치본의 폴더를 `capture` 하고 자식 규칙이 `from` 으로 그 안만 보게 한다.

```yaml
- id: pool
  capture:
    fpm_dir: "path | dirname | dirname"   # 캡처 함수는 이어 쓴다
- id: turned_off
  from: "${pool.fpm_dir}"
```

**`from` 을 빼면 `ex04` 의 판정이 0 이 된다**(실측). 설치본이 한 그룹에 섞여, 어느 한
곳의 *"껐다"* 가 전부를 지운다 — 노출된 설치본을 놓치고 *"없다"* 라고 말한다.

섞였을 때 어느 쪽으로 틀리는지는 판정식이 정한다. **`not` 으로 쓴 판정은 조용히
덜 보고**, 긍정 조건으로 쓴 판정(*설치본 and 취약 버전*)은 **다른 설치본의 사실로
판정이 선다**(오탐). 어느 쪽이든 `capture` + `from` 으로 가른다.

## 근거 하나

린트는 **detect 규칙이 둘 이상인데 판정식이 그중 한 이름만 쓰면** 경고한다. 규칙이
하나뿐인 플러그인에는 경고가 없다 — 이름 수를 센다. 경고의 이유는 *"룰 하나의
오탐이 곧바로 삭제로 이어지지 않게"* 다 — 점검에는 삭제가 없다.

- **둘로 세울 수 있으면 세운다.** 단 `not` 항은 이름을 하나 더할 뿐 **증거를 더하지
  않는다.** `ex04` 의 판정은 `pool` 한 건의 증거로 선다 — 린트가 0·0 이어도 그 점을
  안다
- **버전 하나가 곧 판정**이면(취약 버전 점검) 근거가 하나인 것이 정상이다. 본문을 담을
  경로 규칙과 버전 규칙처럼 규칙이 둘이면 경고가 붙는다 — 그대로 두고 **왜 하나인지
  주석에 적는다**

## 버전

**`version_lt` · `version_gt` 가 버전을 견준다.** 점으로 나눈 숫자만 받고, 없는
성분은 `0` 이다(`8.2` = `8.2.0`). `gt` · `lt` 는 수와 RFC3339 시각만 보므로 버전에
쓰면 **판정을 세우지 못하고 진단만 남긴다** — 린트가 경고로 새 연산자를 가리킨다.
두 자리로 줄여 적는 우회는 **순서를 뒤집는다** — 수로는 `8.10 < 8.9` 다.

```yaml
- { field: version, op: starts_with, value: "8.2." }    # 계열을 좁히고
- { field: version, op: version_lt,  value: "8.2.29" }  # 수정판 미만이면 취약
```

**버전은 따옴표로 감싼다.** 없으면 YAML 이 `8.10` 을 **실수로** 읽어 `8.1` 로
도착하고 **뒤의 0 은 돌아오지 않는다** — `8.9` 가 양호로 나간다(실측). 린트 오류이고
`scan` 도 6 으로 멈추지만 원문은 복원하지 못한다. 정수(`value: 8`)는 왕복한다.

**꼬리는 받지 않는다.** `8.4.0RC1`(사전 배포)은 `8.4.0` 보다 **낮고**
`8.2.29-1ubuntu1`(패키지 개정)은 `8.2.29` 보다 **높다** — 모양이 같고 순서가 반대다.
리터럴이면 린트 오류, **관측된 값이면 종료 6** 이다 — *"안 맞았다"* 가 아니라 *"재지
못했다"* 로 세어 YARA 와 같은 레일을 탄다. 단 `not` 항과 `exclude` 아래서는 2 가
먼저다 — 위 §결과의 예외와 같다.

## 패키지

리눅스에서 **배포판이 깐 소프트웨어의 판**은 `package` 가 들고 있다. 수집기는
DB 를 **파일로 직접 읽고**(`dpkg status` · `apk installed` · rpm DB) 매니저를 부르지 않는다.
판을 셋으로 나눠 담으므로 **꼬리 때문에 6으로 끝나지 않는다**:

| 필드 | `1:2.38.1-5+deb12u3` |
|---|---|
| `version` | 그대로 전부 — 원문이 증거다 |
| `upstream_version` | `2.38.1` — `version_lt` 가 받는 모양 |
| `revision` | `5+deb12u3` — 배포판 개정 |

```yaml
- { field: source,           op: equals,     value: "php8.2" }   # 계열 전체
- { field: upstream_version, op: version_lt, value: "8.2.29" }
```

**상류 판만 보면 백포트를 못 가린다.** 배포판은 상류 번호를 올리지 않고 고치므로
**고친 기계도 위 룰에 걸린다.** 그 자리는 **`pkg_version_lt`** 다 — `version` 을
배포판이 적은 그대로, 개정까지 견준다:

```yaml
- { field: source,  op: equals,         value: "php8.1" }
- { field: version, op: pkg_version_lt, value: "8.1.2-1ubuntu2.21" }   # 고친 판 미만
```

순서는 **dpkg 의 규칙**이다(데비안 정책 §5.6.12) — `~` 가 무엇보다 먼저이므로
`1.0~rc1 < 1.0 < 1.0+b1` 이고, `2.9 < 2.28` 이다(수로 견준다). apk 의 `-rN` 도
같은 규칙으로 선다. **`_` 는 받지 않는다** — apk 는 `_alpha` 를 그 판보다 낮게,
dpkg 의 규칙은 높게 읽어 **순서가 반대**다. 그때는 추측하지 않고 6 이다.
**반대 방향은 없다** — `not pkg_version_lt` 가 `>=` 이므로 범위는 둘로 적는다.

> **고친 판은 배포판마다 다르다.** 룰이 그 숫자를 들고 있어야 하고, 그것은
> 공급사 공지에서 온다. 상류 판만 보는 룰(`upstream_version`)은 배포판 기계에서
> **고친 것까지 취약으로 보고**한다.

**RPM 판은 `rpm_version_lt`** 다(코어 1.3.0 · `manager: rpm`). RHEL 의 개정(`8.el9_8.1`)은
`_` 를 담아 위 연산자가 거절하고, 순서도 rpm 의 규칙(`rpmvercmp`)이다. **같은 판을 여러
공급사가 낸다** — Rocky · Alma 가 RHEL 의 판을 그대로 적으므로 `vendor` 로 가른다:

```yaml
- { field: vendor,  op: equals,         value: "Red Hat, Inc." }
- { field: version, op: rpm_version_lt, value: "0:8.0.30-8.el9_8.1" }
```

`package` 에는 **치료 Op 이 없다**: 패키지를 올리는 것은 공급사의 일이다.
`upstream_version` 은 읽지 못하면 **빈 문자열**이고 그 술어는 거짓이 된다.

**견줄 필드.** Windows 실행 파일은 **`file.version`** — PE 가 선언한 **문자열
`FileVersion`** 이다(공백 뒤 주석 `(WinBuild…)` 만 버린다). 2진 `VS_FIXEDFILEINFO`
가 아니다 — 공급사는 **문자열 눈금으로 공지한다.** **ELF 에는 그 구조가 없다** —
리눅스는 대신
**`package.upstream_version`** 을 본다(아래 §패키지). 그 밖에
`browser_extension.version`, 그리고 값에 버전이 든 `text_config.value` ·
`registry_value.data`(Windows 는 Uninstall **아래 제품 키**의 `DisplayVersion` —
수집은 선언한 키의 값만 모으므로 제품 키를 모르면 끝에 `\*` 를 적어 직속 하위
키로 펼친다).

**읽지 못한 파일은 비고, 그 술어는 거짓이 된다.** 본문 상한(`max_hash_bytes`)을
넘었거나 PE 가 아니면 `version` 이 없다 — `sha256` 과 같은 자리다. 큰 바이너리는
`collect_extra` 의 **`path` 형**에 `max_size` 를 주면 채워진다(실측 36 MB) — `ref` 형은
8 MiB 고정이라 올릴 수 없다. 그래서 버전 점검은 **경로로 못박고** 쓴다. **해시만 있으면
되는 큰 실행 파일**은 `hash_large`(`10-manifest.md` · 코어 1.3.0)에 이름을 적는다 — 256 MiB
까지 흘려 읽어 `sha256` 만 채운다. 공식 `node.exe`(83 MiB)를 공식 해시로 가리는 자리다.

**필드가 비는 자리는 YARA 가 남는다** — 리눅스 바이너리의 문자열이 그 자리다. 본문을
담아야 하고 `ref` 는 8 MiB 고정이라 큰 바이너리가 6 으로 끝나며, 개발 빌드의 `pe`
모듈은 스택 넘침으로 죽는다. 예제로는 둘 수 없다.

**모르면 `verdict.unconfirmed` 로 말한다**(코어 1.3.0). `require` 가 서지 않은 그룹에서
그 줄의 `when` 이 서면 6 이고, 룰이 적은 `why`(ko · en)가 사유 줄이 된다 — 백포트를
모르는 설치본이 그 자리다. 찾은 것이 앞선다(2). 이것 없이 판정을 세우지 않으면
0 이 나가고, 0 은 *"이 기계는 괜찮다"* 로 읽힌다.

## 선언한 자리 밖의 런타임 — 찾으면 확인 필요

`scan_roots` 밖의 설치본은 수집되지 않아 0 으로 끝난다(실측: 같은 취약 PHP 가 `C:\php` 면 2,
`C:\inetpub\php83` 이면 0). 그 자리를 알려 주는 곳을 함께 읽고 **선언한 자리는 `exclude` 로
뺀다** — 남은 것이 자리 밖이다. 그 파일은 열지 않고 `unconfirmed` 로 낸다.

- **IIS 설정** — `structured_config` 는 XML(`.xml` · `.config`)도 편다(코어 1.6.0). 요소는 `/`,
  같은 이름 형제는 `[n]`, 속성은 `/@이름` 이다: `…/fastCgi[0]/application[0]/@fullPath`.
  `subject_roots` 로 `C:\Windows\System32\inetsrv\config` 만 읽는다
- **실행 중 프로세스** — `process.image_path`. 요청이 없어 떠 있지 않은 FastCGI 는 못 본다

```yaml
- id: iis_php
  subject: structured_config
  where:
    - { field: key_path, op: matches, value: '(?i)/(application\[\d+\]/@fullPath|add\[\d+\]/@scriptProcessor)$' }
    - { field: value, op: matches, value: '(?i)\\php-cgi\.exe(\|.*)?$' }
  exclude:
    - { field: value, op: matches, value: '(?i)^(c:|%systemdrive%)\\php\\' }
```

## 바깥을 보는 점검 — `network`

이 기계가 아니라 **적어 준 주소의 서버**를 보는 점검은 `network: url` 을 적는다(코어 1.4.0).
본체는 통신하지 않는다 — 그 룰을 고르면 서명을 확인한 동반 프로그램 `remedy-net` 을 띄워
맡기고 종료 코드만 받는다(설계-04 §1). 그래서 **이 기계를 읽는 칸은 전부 비운다**:
`scan_roots` · `subjects` · `detect` 는 `[]`, `verdict` 는 적지 않는다 — 채우면 로드가
거부한다. `kind: check` 와 `min_core: "1.4.0"` 이 함께 온다. 값은 닫힌 집합이고 지금은
`url` 하나다. 판정 기준은 룰이 아니라 `remedy-net` 에 있다(`plugins/php2shell-url-check`).

## 청정 코퍼스

시험은 **청정 기계에서 판정 0** 을 요구한다(`every_example_is_clean_against_the_clean_corpus`).
치료 플러그인에게 그것은 오탐이다. **점검에게는 뜻이 다르다** — 감염 없는 기계도
취약할 수 있다.

- 지금은 **청정 코퍼스에서 서지 않는 조건**으로 쓴다. `ex04` 가 그렇다
- 청정 코퍼스에는 **PHP 가 설치된 기계가 없다.** PHP 점검 룰의 *"정상 서버에서
  잘못 서는가"* 는 아직 잴 자리가 없다 — 0건 통과는 *오탐이 없다* 가 아니라
  *재지 않았다* 다

## 하지 않는 것

| | |
|---|---|
| 고치기 | 패치 · 업그레이드 · 설정 적용. `remediate` 가 없으므로 할 수도 없다 |
| *"설정만으로 안전"* | 노출 조건이 꺼져 있다는 것은 **안전하다는 뜻이 아니다.** 판정을 세우지 않는 근거로만 쓴다 |
| 컨테이너 안 | 이 기계의 파일 · 설정 · 프로세스만 본다. 원격은 `network` 룰이 따로 본다(위) |
