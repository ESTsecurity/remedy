# 서명 전 확인 — 사람이 읽는다

AI 가 쓴 룰은 **사람이 서명한다.** 서명은 *"이 파괴 지시서에 우리 이름을 건다"* 는
뜻이므로, 무엇을 보아야 하는지가 여기 있다.

---

## 아홉 가지

**1. `verdict.require` 의 각 항목이 서로 독립적인 근거인가.**
같은 사실의 두 표현이 아닌가. `command matches node\.exe` 와
`args matches \.js` 는 같은 예약 작업의 두 필드이므로 **하나의 근거**다 —
독립적이려면 다른 대상(파일 내용·레지스트리)에서 와야 한다.

**2. 그 근거들이 남는 위험이 큰 것인가 — 이 판정이 서지 않는 기계는 어떤
상태인가.**

1번은 고른 것들이 독립적인지 묻고, 이것은 **옳은 것을 골랐는지** 묻는다.
독립적인 근거가 셋인데 둘로 판정을 세우면 **나머지 하나만 남은 기계는 치료되지
않는다.**

근거마다 *"이것이 없어도 위협인가"* 를 물어 본다. 없어도 위협인 것 — 신뢰
저장소에 심긴 인증서, 되살리는 지속성 — 이 판정에 들어가야 한다. 실행 파일은
다시 받으면 그만이고, **남은 쪽이 그것을 다시 부른다.**

> **실측 (P11 `tls-r1`).** 같은 검체에 판정을 다르게 세운 답 둘이 **채점 넷을
> 모두 통과했다.** 한쪽은 심긴 인증서와 돌려진 이름으로, 다른 쪽은 프록시
> 바이너리와 그 개인키로 세웠다. 갈린 것은 **바이너리가 이미 지워진 기계**뿐이고
> — 관리자가 폴더만 지웠거나 다른 백신이 실행 파일만 잡은 기계다. 앞은 인증서를
> 빼고 이름을 되돌렸고, 뒤는 아무것도 하지 않았다. **채점은 이 차이를 보지
> 못한다.**

**3. 정상 소프트웨어가 이 조건을 만족할 수 있는가 — 어떤 제품인지 이름을 댈 수
있는가.**

**이 항목이 가장 중요하다.** *"오탐 가능성이 낮다"* 가 아니라 **"어떤 정상 제품이
걸릴 수 있는지 이름을 대라"** 고 요구한다. 이름을 대지 못하면 검토가 이뤄지지 않은
것이고, 이름을 대면 **그 제품이 청정 코퍼스에 추가된다** — 이후 모든 플러그인이 그
환경에서 검증된다.

**4. 제거 대상이 전부 증거에서 파생됐는가.** 리터럴 절대 경로가 하나라도 있으면
그것은 증거 없는 삭제다.

**5. 재귀 삭제·키 삭제에 `guard` 가 붙어 있고, 그 guard 가 실제로 그 디렉터리·키
안의 것인가.** 계획기도 확인하지만, 사람이 먼저 본다.

> 경고하지만 **좁은 쪽은 아무도 경고하지 않는다.** 코퍼스 시험도 `xtask exam`
> 도 이것을 재지 못한다 — 스냅샷은 이미 수집된 것이라 매니페스트의

**7. 청정 코퍼스에서 파괴 Action 0건인가.** G1 결과를 첨부한다.

> **0건이 두 가지 뜻이라는 것을 알고 읽는다.** 레코드 12만 건을 걸러 낸 것과
> 볼 레코드가 한 건도 없었던 것이 같은 0건으로 보고된다. 그래서 G1 과 시험
> 채점은 **뿌리 규칙이 마주한 레코드 수**를 함께 낸다 — 그 수가 0 이면 게이트는
> 이 규칙을 시험한 적이 없다.
>
> **파생 규칙(`from:` 또는 `${부모.…}`)은 청정 코퍼스가 시험하지 못한다.**
> 부모가 서지 않으면 자식은 평가가 시작조차 되지 않는다. 오탐 안전은 사실상
> **뿌리 규칙 하나가 떠받친다** — 거기를 좁히지 않고 자식에 조건을 쌓는 설계는
> G1 이 초록이어도 검증된 것이 아니다.

**8. 린트 경고가 남아 있다면 각각에 대해 남긴 이유가 설명되는가.**
경고는 로드를 막지 않는다 — **막는 것은 이 자리다.**

**9. `submit_hint` 의 `confidentiality_min` 이 대상 데이터에 맞는가.**

## 서명한다

서명은 개인키를 다루므로 **제품 바이너리가 아니라 빌드 도구가** 한다.

```
cargo xtask sign plugin --dir plugins/<id> --secret-key <키> --signed-at 2026-08-26T09:00:00Z
```

| 만들어지는 것 | 무엇 |
|---|---|
| `MANIFEST` | 트리 전체의 파일별 sha256 목록 |
| `MANIFEST.minisig` | 그 목록의 서명. 주석에 id·버전·서명 시각이 들어간다 |

**파일 하나가 아니라 트리 전체에 서명한다.** 파일마다 서명하면 **파일을 하나 더
넣는 공격**을 막지 못한다 — 기존 파일을 건드리지 않고 `rules/extra.yar` 를 넣으면
모든 서명이 유효한 채로 내용이 바뀐다.

확인은 제품이 한다.

```
remedy plugin verify --dir plugins/<id>
```

거부되는 것 넷 — **바뀐 파일 · 없어진 파일 · 목록에 없는 파일 · 다른 키의 서명.**

**`--signed-at` 은 손으로 적는다.** 자동으로 "지금" 을 넣으면 같은 트리를 두 번
서명했을 때 서명이 달라져 재현되지 않고, 이 값이 역행 금지 판정의 근거다.

## 폐기 — 내보낸 뒤에 잘못을 알았을 때

오탐 사고가 나면 폐기 목록으로 그 버전을 무효화한다.

```
cargo xtask sign revocations --entries e.json --serial 8 \
    --issued 2026-08-26T09:00:00Z --secret-key <키> --out revocations.sig
```

```json
[ { "plugin": "<id>", "below": "1.2.0", "reason": "오탐 — 정상 Node 환경을 겨눴다" } ]
```

| 필드 | 뜻 |
|---|---|
| `below` | 이 버전 **미만** 전부. 결함이 어느 판에서 고쳐졌는지 알 때 |
| `exact` | 그 버전 하나만 |
| `reason` | **비워 둘 수 없다.** 사유 없는 폐기는 나중에 누구도 되돌릴지 판단할 수 없다 |

`below: 1.2.0` 은 `1.2.0` **을 겨누지 않는다** — *"1.2.0 에서 고쳤다"* 가 곧
*"1.2.0 은 괜찮다"* 이므로, 한 칸 틀리면 고친 판까지 폐기한다.

목록은 파일 하나이고 **폐쇄망에는 파일로 반입한다.**

```
remedy revocation verify --file revocations.sig     # 무엇이 담겼는지 본다
remedy revocation import --file revocations.sig     # 반입한다
```

**반입 경로가 신뢰를 낮추지 않는다** — 파일 공유로 온 목록도 서명 검증과 역행
금지를 똑같이 거친다. `serial` 이 전에 본 것보다 낮으면 거부된다.

**버전은 `x.y.z` 만 받는다.** `1.2.0-rc1` 은 폐기 판정을 할 수 없어 거부된다 —
통과시키면 `-rc1` 을 붙이는 것만으로 폐기를 피할 수 있다.

## 오탐 신고가 들어오면

```
1. remedy restore --run <id>            복구가 먼저다
2. remedy support-bundle --run <id>     신고 첨부물
3. 재현·판정                             그 환경을 청정 코퍼스에 편입
4. 폐기                                  위의 revocation
5. 기준 추가                             재발 방지 조건을 게이트로
```

**3번이 핵심이다.** 한 번 겪은 오탐 환경이 골든 클린 세트에 들어가면 이후 모든
플러그인이 그 환경에서 검증된다. 그러지 않으면 같은 유형의 오탐이 플러그인마다
반복된다.

`support-bundle` 은 계획·저널·환경 정보를 모으고 **격리 컨테이너와 봉인 키는
담지 않는다** — 그 사실을 첨부물의 `README.txt` 가 경로까지 적어 말한다.

## 서명하지 않는 경우

아래 중 하나라도 답하지 못하면 서명하지 않는다.

- 2번에서 **정상 제품 이름을 대지 못한다**
- G1 결과가 없거나 파괴 Action 이 0 이 아니다
- 린트 경고가 있는데 이유가 설명되지 않는다
- 재귀 삭제의 `guard` 가 무엇을 가리키는지 확인하지 못했다

**서명은 되돌릴 수 있다**(폐기 목록). 그러나 그 사이에 배포된 것은 이미 돌았다.
