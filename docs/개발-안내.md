# 개발 안내 — 이 저장소에서 일할 때 걸리는 것들

이 문서는 **코어를 고치거나 검증을 돌리는 사람**이 읽는다. 룰만 쓰는 사람은
[`plugin-guide/README.md`](plugin-guide/README.md), 도구를 돌리는 사람은
[`operator.md`](operator.md) 가 먼저다.

여기 적힌 것은 전부 **한 번씩 겪고 나서 알게 된 것**이다. 대부분은 실패가
엉뚱한 곳을 가리키는 종류여서, 모르면 같은 자리에서 같은 시간을 쓴다.

## 저장소 한눈에 — README 에서 옮겨 왔다 (2026-11-06)

`README.md` 는 받아서 쓰는 사람의 첫 장이 되었다. 개발자가 알아야 할 것은 여기 둔다.

**템플릿 하나 + 위협별 플러그인.** 위협마다 단품 도구를 찍어내면 관리 비용이 무한히
누적된다. remedy 는 바이너리 하나를 두고 위협별 대응을 **선언적 룰**로 표현한다. 새 위협
대응은 `plugin.yaml` 과 `rules/*.yar` 만 배포하면 된다 — 코어를 다시 만들지 않는다.
실행 파일은 CRT 정적 링크라 재배포 패키지가 필요 없고, **네트워크를 말하는 코드가
링크되지 않는다** — 임포트 전수를 `cargo xtask static` 이 매번 확인한다.

**설계의 척추 셋.**

1. **파괴 동작은 실행 전에 계획으로 완전히 확정된다.** `collect → evaluate → plan →
   apply` 각 단계가 파일 아티팩트로 나뉘며, `apply` 는 `plan.json` 에 있는 것만 수행한다.
   드라이런의 정확성 · 삭제 상한의 사전 차단 · 감사 완전성이 전부 여기서 파생된다.
2. **스크립트는 읽고, 룰은 쓴다.** 플러그인은 관찰과 제거 대상만 선언하고, 순서 · 백업 ·
   프로세스 종료는 코어가 정한다.
3. **되돌리기가 지우기보다 먼저다.** 격리 · 복원이 첫 파괴 동작보다 앞선 Phase 에 완성된다.

**규칙은 문서가 아니라 CI 가 지킨다** — 아래 "커밋하기 전에" 의 명령 일곱이 그것이다.
`arch` 의 금지 의존 목록과 `trace` 의 인벤토리는 **코드에 박혀 있지 않고 설계 문서에서
읽는다** — 같은 사실을 두 곳에 적으면 반드시 갈라지기 때문이다.

## 커밋하기 전에

| 명령 | 무엇을 보나 |
|---|---|
| `cargo fmt --all -- --check` | 서식 |
| `cargo clippy --workspace --all-targets -- -D warnings` | 린트 |
| `cargo clippy -p remedy-cli -p remedy-net -- -D clippy::print_stdout -D clippy::print_stderr -D clippy::dbg_macro` | 실행 파일의 코드(두 실행 파일과 그것이 링크하는 작업 공간 크레이트)가 화면에 `println!` 류로 쓰지 않는가 — 읽는 쪽이 먼저 닫힌 파이프에서 패닉해 1.21.0 까지는 치료 도중에 7 로 멈췄다. 본체는 `outln!` · `screen_err!` 등, `remedy-net` 은 `crate::outln!` 등으로 쓴다 |
| `cargo xtask all` | 저장소 검사 열일곱 가지 |
| `cargo xtask g1` | 저장소의 룰 전부(데이터 · 원격 점검 룰 빼고)를 청정 코퍼스(`corpus/clean`)에 — 판정 · 파괴 동작 0(G1). 관측 모자람(6)은 알림이다. 디버그 빌드로 약 35초(22코어 PC · 스레드 8) — `xtask all` 밖의 CI 걸음 |
| `cargo test --workspace` | 시험 전부 |
| `cargo xtask leaks` | 공개하지 않는 값 · 넣는 목록 밖의 파일 |
| `cargo deny check` | 의존의 보안 권고 · 라이선스 · 출처 · 금지 — 권고는 새 공지가 나오면 코드와 상관없이 실패한다 |

**도구를 바꾸면 절차 문서도 함께 고친다**(2026-11-22) — `cargo xtask all` 의 `procdocs` 가 절차 문서(AGENTS · README ·
긴급 대응 · 이 문서 · 이슈 처리 · 전체 그림 · 하네스 README)의 경로 · 링크 · 명령 인자와 지금 값을 저장소와 견준다. 지금 값은
값 표(`xtask/src/procdocs.rs` 의 `values` — 스냅샷 수 · 이 표의 검사 수 · AI-CONTEXT 상한 · 엔진 0줄을 가리는 경로 · rc 묶음의
단계 수 · 하네스 README 의 스크립트 이름)로 본다 — 절차 문서에 새 지금 값을 적으면 그 표에 한 줄을 더한다. 날짜를 단 옛 기록
절은 제목 바로 아래 `<!-- 기록: YYYY-MM-DD 의 사진 -->` 표지로 경로 · 값 검사에서 뺀다(링크는 본다).

**`cargo xtask all` 과 `cargo test` 는 서식·린트를 보지 않는다.** 그 둘만 돌리고
커밋해 CI 의 fmt 가 깨진 적이 있다. CI(`.github/workflows/ci.yml`)는 위 표의
명령을 그대로 돈다(룰 · 문서 · 하네스만 바뀐 PR 은 일부를 건너뛴다 — 아래).

**룰 잠금과 업데이트 내역 조각은 git 바탕과 견준다**(2026-11-21 — 전에는 견줄 상대를 `plugins/versions.lock.json` ·
`plugins/RULES-VERSION` 으로 커밋했고, 룰 PR 마다 그 파일을 고쳐 함께 지으면 늘 충돌했다). `xtask all` 의 `plugin-lock` 은
바탕보다 파일이 바뀐 룰의 `version` 이 올랐는지, `fragments` 는 `version` 을 올린 룰마다 바탕 뒤에 더한 조각
(`docs/changes/` — [그 폴더의 안내](changes/README.md))이 있는지 본다. 바탕은 `--base <ref>` → 환경 `REMEDY_BASE` → `origin/main` 과의
병합 바탕(로컬 가지 · PR 의 CI) → HEAD 가 병합 커밋이면 그 첫 부모(`origin/main` 이 없는 얕은 받기 — PR 의 Windows 잡) 차례로
고르고, 하나도 서지 않으면 멈춘다. main 에 병합된 뒤의 CI(리눅스 잡)는 지금 Latest 와 견준다 — 출시 잡의 같은 확인을 병합 때
먼저 한다.

**엔진 0줄인 PR**(`crates/` · `Cargo.toml` · `Cargo.lock` 이 그대로 — 룰 · 문서 · 하네스만)은 로컬에서 셋만 돈다 —
`cargo xtask all` · `cargo xtask leaks`(새 파일을 스테이징한 뒤) · 룰을 고쳤으면 G1(`cargo xtask g1` · `긴급-대응.md`
*단계 0 ~ 2 에서 걸리는 것* 의 G1). 위 표의 나머지 다섯(fmt · clippy 둘 · 전체 `cargo test` · deny)은 PR CI 에 맡긴다(2026-11-19 결정 ·
`긴급-대응.md` *단계와 시간* 의 2). 그 CI 도 바뀐 것이 `plugins/` · `docs/` · `README.md` · `testbed/harness/` 안뿐인 PR 은
가벼운 길로 간다(`ci.yml` 의 `scope` 걸음 · 2026-11-21) — fmt · clippy 둘 · Windows 의 `cargo test` · 버전 검사 시험을
건너뛰고(입력이 `crates/` · `xtask/` · `ci/` 와 의존 목록이라 결과가 바탕과 같다) `leaks` · `xtask all` · 릴리스 본문 시험 ·
리눅스의 `cargo test --workspace` 는 돈다. deny 는 돌되 막지 않는다 — 입력에 새로 나오는 권고가 있어 신호는 보이게 하고,
엔진과 상관없는 권고가 룰 PR 의 병합을 막지는 않게 한다. 그 가운데 이미 있던 룰 폴더를 건드리지 않은 PR(새 룰만 더했거나 문서 ·
하네스만 고친 것)은 재채점 시험 둘(`every_recorded_run_still_scores_the_same` ·
`every_threat_has_a_reference_answer_that_passes`)도 건너뛴다. PR 이 아닌 실행(main 에 병합된 뒤 · 손으로
`gh workflow run ci.yml --ref …`)은 전부 돈다. **PR 의 룰 하네스**(2026-11-22)는 가벼운 길이든 아니든 PR 에서만 돈다 —
PR 이 바꾼 룰의 하네스와 PR 이 고친 하네스(머리의 `# 룰:` 줄)를 두 잡이 러너에서 개발 빌드로 돈다(`bash ci/batch.sh
pr-harnesses` · `긴급-대응.md` *단계와 시간* 의 3). 그래서 공지된 취약점 점검 룰은 docker · 랩 VM 이 없는 PC 에서도 짓는다(악성코드 탐지 · 치료 룰과 미공지 취약점의 룰은 공개 저장소 밖에서 짓는 동안 올리기 전에 하네스를 돈다 — `AGENTS.md`). 병합 뒤에는 출시 전
필수 점검 ① 이 정식 파일로 다시 잰다.

**`leaks` 는 push 하기 전에 돌린다 — CI 는 병합을 막을 뿐이다.** PR 에 올라간
커밋은 가지를 지워도 그 PR 로 닿는다. PR 의 참조(`refs/pull/`)는 읽기 전용이라
지우려면 GitHub 지원에 맡겨야 하고, 저장소가 public 이 되면 PR 과 함께 보인다.

**로컬 목록 `.cargo/leaks.yml`**(커밋하지 않는다 · 새 PC 에서 처음 만든다) — 이 PC 와 조직의 정확한 내부 값을 `values:`
아래에 한 줄에 하나씩 적는다: 랩 VM 의 주소 · 이름, 이 기계의 호스트명 · 사용자 이름, 사내 도메인 · 사내 계정 이름(세 글자
이상 · 대소문자와 구분 문자는 가리지 않는다 — `xtask/src/leaks.rs` 의 `LocalList`). 공개 트리에 그 값이 나오면 `leaks` 가
막고, 자리(경로:줄)만 알린다. 비밀번호 · 키는 적지 않는다 — 그 꼴은 일반 규칙이 본다.
값은 부분 일치로 찾는다 — 짧은 값은 그 값이 든 낱말마다 걸리므로(`han` 이면 `handler` · `changes`) 예외
목록(`xtask/leaks-except.txt`)에 넣지 말고 경로 꼴로 적는다(사용자 이름이면 `users/<이름>` — `C:\Users\<이름>` ·
`/c/Users/<이름>` 이 다 걸린다). 사내 도메인은 도메인에 가입한 PC 면 PowerShell 의 `$env:USERDNSDOMAIN` 이 보여 준다.
비었거나, 일반 꼴이 보는 도메인(`xtask/src/leaks.rs` 의 *회사 도메인의 호스트* 규칙)이거나 그 아래면 적지 않는다 — 그 아래의
호스트 · 메일 주소는 일반 꼴이 본다. 그 밖의 도메인(그룹의 다른 회사 · `.local` 등)은 적는다(2026-11-24).

```yaml
values:
  - <랩 VM 주소>
  - <이 기계의 호스트명>
```

랩이 없는 PC 는 랩 VM 의 줄(견본의 `<랩 VM 주소>`)만 빼고 호스트명 · 사용자 이름은 늘 적는다 — 목록이 비어도 `leaks` 는
실패하지 않으니 머리줄을 본다(아래 worktree 단락 끝 · 2026-11-25).

**worktree 에서 일하면 셋을 맞춘다.** 커밋하지 않는 `.cargo/*.yml`(`host.yml` ·
`leaks.yml` 등)은 그 자리에 없다 — 복사한다(커밋하지 않는다). 하네스는 그 값이 없으면
멈춘다(`musl-dev-build.sh` 의 `wsl.cargo_home` 등). 커밋하지 않는 시료(`testbed/harness/results/rc-inputs/`
— `net-apache-verify.sh --images` 등)도 없으니 본 사본의 그 자리를 준다. xtask 는 **지어진 사본의 뿌리**
(`CARGO_MANIFEST_DIR`)를 검사한다 — 다른 사본의 `target` 에 있는 `xtask.exe` 를 부르면 그
사본을 본다. worktree 에서 `cargo xtask` 로 부르면 그 자리에서 다시 짓는다(2026-11-19
모의 1차 — 약 2분 · `target` 3.3 GB). `leaks` 의 머리줄이 *로컬 값 0 개* 이거나 *로컬 목록 … 이 없다 — 일반
꼴만 본다* 면 로컬 목록 없이 돈 것이라 통과로 읽지 않는다.

**rustfmt 가 한 번에 안 맞는 자리가 있다.** 중첩 안의 긴 한글 문자열
(`f(&x, format!("…"))` 꼴)은 한 번 돌린 뒤에도 `--check` 가 다른 모양을
요구한다. 두 번째에 수렴하지만 들여쓰기가 흐트러진 채 남으므로, 메시지를
`let why = format!(…);` 로 먼저 빼서 중첩을 줄이는 편이 낫다. **`fmt` 뒤에는
`--check` 를 한 번 더 돌린다.**

**`cargo test -p xtask` 는 시험 실행만 10분이 넘는다**(`exam` 쪽이 무겁다).
컴파일이 느린 것이 아니다. 시한에 걸려 끊긴 것을 "멈췄다" 로 읽지 않도록,
처음부터 백그라운드로 돌리고 기다린다. 새로 쓴 모듈만 볼 때는
`cargo test -p xtask <모듈 이름>` 으로 걸러 수십 초에 끝난다.

## 빌드와 산출물

**`target/release/xtask.exe` 는 저장소에 없으므로 낡는다.** 마지막으로 지은
사람의 판이 남아, 새로 더한 서브커맨드를 모르고 `알 수 없는 작업` 으로 떨어진다.
하네스의 정적 링크 검사는 그 exe 가 있으면 **그것을 먼저 부르므로**, 낡은 판으로
조용히 통과할 수도 있다. `xtask` 로 무언가를 재기 전에 `--help` 로 그 명령을
아는지 보고, 모르면 `cargo build --release -p xtask` 로 다시 짓는다.

**무거운 빌드를 겹치지 않는다.** 전체 시험 · 리눅스 CI · 컨테이너 빌드를 함께
돌리면 링커가 `LNK1102: out of memory` 로 죽는다. 원인은 여유 RAM 이 아니라
**커밋 한도**다 — VM 과 WSL 이 쥔 양이 합산된다. 그 뒤 재실행은 반쯤 쓴 산출물
때문에 코드와 무관한 오류(`required to be available in rlib format`)를 낸다.
복구는 **오류에 이름이 나온 크레이트만** `cargo clean -p <크레이트>` 다 —
`cargo clean` 전체는 채점에 쓰는 공식 바이너리까지 지운다.

**시작할 때 잰 여유로는 막지 못한다** — 켜진 랩 VM 을 되돌려 다시 켜는 순간처럼 도중에
떨어진다(15.1 → 7.0 GB). 긴 랩 일(콘솔 재캡처 · rc 묶음 · 벤치마크)에는
`testbed/harness/host/Watch-CommitHeadroom.ps1 -Log <일의 기록> -Out <여유 기록>` 을 나란히 띄운다 —
15초마다 재고, 기준(기본 6 GB) 아래면 곧바로 끝나 알린다. 일의 기록 끝에 `DONE` 줄을 쓰면 함께 끝난다.

**변이 시험 뒤에는 디버그 바이너리를 되살린다.** 소스를 해시까지 확인하며
되돌려도 `target/debug` 에는 **마지막 변이로 지은 바이너리**가 남는다. 그것으로
한 즉석 실험은 소스에 없는 결함을 보고한다.

**컨테이너 빌드는 툴체인을 내려받는다.** `rust:1.96-bookworm` 이미지의 판은
`rust-toolchain.toml` 이 고정한 판과 다르므로 rustup 이 매번 받는다. 망에서
TLS 가로채기가 걸리면 실패하고, 캡처 스크립트는 빌드 출력을 숨겨 **"빌드 실패"
한 줄만** 남긴다. 그때는 같은 마운트로 `cargo build` 를 따로 돌려 stderr 를 본다 —
호스트 쪽 rustup 의 같은 판 툴체인을 읽기 전용으로 붙이면 내려받기를 건너뛴다.

**프로그램이 읽는 환경 변수는 열하나다**(2026-11-17 · `git grep -o 'REMEDY_[A-Z_]*' -- 'crates/*.rs'`). 운영자에게
알리는 것은 `REMEDY_LANG` 하나이고(`docs/operator.md` · `--help`), 나머지는 시험과 하네스의 자리다.

| 변수 | 무엇을 바꾸나 | 배포 빌드 |
|---|---|---|
| `REMEDY_LANG` | 화면 언어 (`--lang` 이 이긴다) | 읽는다 |
| `REMEDY_ASCII` | `1` 이면 장식을 ASCII 로, `0` 이면 UTF-8 로 (`--ascii` 와 같다) | 읽는다 |
| `REMEDY_HEARTBEAT_SECS` · `REMEDY_TOOL_WARN_SECS` | 심장박동 주기 · 오래 걸리는 도구를 알리는 시점(시험은 1초) | 읽는다 |
| `REMEDY_NET_CRITERIA` | remedy-net 이 판정 기준(데이터 룰)을 읽는 폴더 — 서명 확인은 그대로다 | 읽는다 |
| `REMEDY_TRUST_ANCHOR` · `REMEDY_TARGET` | 빌드 때 박는 값(공개키 · 타깃 이름) — 실행 중에는 읽지 않는다 | 빌드 때만 |
| `REMEDY_ELEVATION` · `REMEDY_NET_ANCHOR` · `REMEDY_PANIC_TEST` · `REMEDY_SLOW_COLLECT_MS` | 권한 검사 대신 · 동반 프로그램 공개키 · 패닉 시험 · 수집 지연 | 읽지 않는다(`cfg(debug_assertions)`) |

## 채점과 증거

**채점 전에 배포 바이너리가 지금 코드로 지어진 것인지 본다.** 자리·해시·빌드
명령과 그 해시를 만든 코드 커밋은 운영 정보 파일(`.cargo/host.yml` 의
`binaries`)에 있다. 증거의 `binary_sha256` 이 그 해시와 달라지면 재측정 전체가
헛일이 된다.

**내려받은 배포물로 잴 때는 하네스에 그 경로를 준다** — 저장소 산출물
(`target\...`)을 덮지 않는다. 덮으면 위 해시 대조가 그 자리에서 깨진다.
메뉴 하네스와 종료 코드 하네스 넷(`Invoke-GuardVerify` · `Invoke-ObsVerify` ·
`Invoke-PartialVerify` · `Invoke-SignVerify`)은 `-Package <푼 꾸러미 폴더>`, 시연 쪽은
`-Bin <remedy.exe>`, 리눅스는 `--bin <파일>` 이고, 그렇게 주면 **짓지도 서명하지도 않는다**.

**리눅스 하네스는 WSL 쪽 자리의 바이너리를 먼저 집는다.** 캡처·CI 가 docker
이름 볼륨에 빌드하면 하네스가 돌리는 것과 기록된 해시가 어긋난다. 재측정 전에
`sha256sum` 으로 운영 정보의 해시와 같은지 확인한다.

**새 위협의 첫 감염 스냅숏을 뜨기 전에 대상 JSON 을 미리 만들어 둔다**
(`testbed/ai-exam/threats/<위협>/infected/<위협>.json`, `{}` 두 글자면 된다).
`New-ThreatSnapshot.ps1` 은 오타로 엉뚱한 자리에 쓰지 않도록 그 파일이 없으면
멈추는데, **새 위협에는 아직 그 파일이 없다.** 가드는 고치지 않는다 — 그 줄이
막는 오타가 더 비싸다.

**`console-doc` 은 문서와 기준선만 댄다.** 제품의 화면 문자열을 바꾸면 기준선이
바이너리와 어긋나는데도 그 게이트는 초록이다 — 문서와 기준선이 둘 다 옛 문구를
담고 서로 맞기 때문이다. 그것을 잡는 것은 재캡처와 `console-diff` 뿐이다.

PR 에서 표를 고쳤으면 통과해야 한다).

**룰 PR 은 룰의 자리만 고친다**(2026-11-21) — 자기 룰 폴더 · 자기 하네스 · 업데이트 내역 조각 하나(`docs/changes/<룰 id>-<새
버전>.md` · 꼴은 [그 폴더의 안내](changes/README.md)) · 위협별 안내의 그 위협 절 · 그 제품의 찾는 조건 원본(`products/` · 아래),
그리고 [새 룰을 더할 때](#새-룰을-더할-때--룰-폴더-밖에서-손대는-자리)의 조건부 자리. 그 밖(도구 · 하네스 바탕 · 출시 스크립트 · 워크플로 · 엔진)을 함께 고치면 PR CI 의 `rule scope` 걸음
(`ci/rule-scope.sh` · 2026-11-22)이 멈춘다 — 필수 점검은 태그의 트리로 돌아, 룰 PR 이 함께 고친 도구가 다음 묶음의 게이트가
된다. 도구는 따로 PR 로 먼저 낸다. 룰 버전 · README 두 표 · 업데이트 내역 파일 · 하네스 표 · rc 묶음 등록은
손으로 고치지 않는다 — 출시 때 태그 나무와 git 에서 짓거나(룰 버전 · 릴리스 본문) 하루 한 번 생성물로 갈아 끼운다(아래). 그래서
서로 다른 위협의 PR 이 늘 함께 고치는 파일은 위협별 안내 하나이고, 여럿을 같은 main 에서 열어 갱신 없이 차례로 병합한다 —
같은 자리에 절을 넣어 충돌하면 뒤에 병합하는 PR 만 main 을 받는다([`긴급-대응.md`](긴급-대응.md#1차-범위) *위협별 안내 절*).

**출시는 명령 하나와 승인 한 번이다** — 조직 Owner 가 저장소 루트(git · gh 로그인 · bash · cargo)에서 부른다. 랩 VM · WSL 이
없는 PC 에서도 된다 — 필수 점검은 GitHub 호스팅 러너가 돈다(2026-11-22).

```bash
bash ci/batch.sh status     # 지금 Latest · 진행 중인 초안 · 다음 묶음에 들 조각 · 멈춤 이슈
bash ci/batch.sh            # origin/main 머리를 묶어 낸다(시험판은 --rc — 공개 걸음을 시험만 하고 공개하지 않는다)
bash ci/batch.sh --local    # 필수 점검을 이 PC 의 WSL · 랩 VM 으로(러너가 막힌 날 · 둘을 견줄 때)
```

| 걸음 | 하는 일 |
|---|---|
| 1 | 이 사본의 도구(`ci` · `testbed/harness` · `.github` · `xtask`)가 origin/main 과 같은지 · 멈춤 이슈 · 진행 중인 초안을 본다(엔진 출시의 초안이 있으면 그 공개까지 룰 공개를 멈춘다) |
| 2 | 묶음 = origin/main 머리다. 지금 Latest 뒤에 든 조각을 보여 주고, 다음 룰 버전(한국 날짜 · 같은 날 둘째부터 `.2` …)으로 버전 검사를 지난 뒤 `rules-<룰 버전>` 태그를 민다. 동료가 같은 이름을 먼저 밀었으면 밀기가 실패한다 — 다시 부르면 다음 이름을 쓴다 |
| 3 | 배포 워크플로가 지금 Latest 의 서명된 실행 파일을 싣고, 그 엔진으로 모든 룰을 lint 한 뒤 초안을 올린다 — 끝까지 본다 |
| 4 | 초안을 `testbed/harness/results/batch/<태그>/` 에 받아 필수 점검([`긴급-대응.md`](긴급-대응.md#출시-전-필수-점검) ①~④)을 돈다. ①②③ 은 그 자산 셋의 해시로 `.github/workflows/checks.yml` 을 그 태그에서 불러 끝까지 보고, 두 잡(linux · windows)이 기록에 찍은 요약을 보인다 — 바뀐 룰의 하네스는 잡이 그 머리의 `# 룰:` 줄로 스스로 찾는다(리눅스 · Windows 둘 다). YARA 가 바뀐 룰이 있으면 G9 를 잰 기록을 `G9_DONE=<기록 파일>` 로 줘야 지나고, 그 기록에 적힌 sha256 과 초안 꾸러미의 그 `.yar` 가 같아야 한다(잰 `.yar` 의 `sha256sum` 줄을 기록에 남긴다). `--local` 이면 ①②③ 을 이 PC 의 WSL · 랩 VM 으로 돈다(Windows 룰 하네스는 돌리지 않는다) |
| 5 | 승인 — 터미널이면 y/N 을 묻는다. 터미널이 아니면(작업자가 돌린 셸) 승인 대기로 종료 3 — 사람이 결과를 보고 승인하면(카드) `bash ci/batch.sh approve <태그>` 로 잇는다. 점검 기록이 없는 다른 PC 에서도 된다 — 초안을 다시 받아 같은 자산 셋으로 성공한 러너 점검을 찾는다(`--local` 의 점검은 그 PC 에서만 잇는다) |
| 6 | 공개 워크플로(`.github/workflows/publish.yml` · 동시 실행 그룹 하나라 한 번에 하나)가 최종 확인(초안의 자산 = 점검한 그 파일 · 지금 Latest 가 조상 · 룰 버전 · 엔진 역행 없음 · 본문에 자리 표시 없음 · 그 커밋의 main CI 가 실패하지 않았다 · **그 태그 커밋 · 그 자산 셋으로 돈 러너 점검의 잡 둘이 성공했다**(i — `--local` 이면 d 의 묶기로) · 열린 '모아 내기 멈춤' 이슈가 없다(j)) → 공개 → 180초 뒤 익명 확인(실패하면 지난 Latest 로 되돌린다 — latest 의 태그 · 불변 · 자산 수를 묻는 줄은 익명 한도에 걸리면 기다렸다 다시 묻고 그래도 막히면 잡 토큰으로 묻는다 · 받기 여섯은 늘 익명 · [`긴급-대응.md`](긴급-대응.md#출시-전-필수-점검) ⑤) → 룰마다 보인 시간(그 조각을 들인 PR 을 연 때 → 공개)을 잰다 |

**잰 값**(2026-11-21 리허설) — 같은 main 에서 3분 안에 연 룰 기록 PR 셋(#132 · #133 · #134 · CI 각 11분 남짓)을 갱신 없이
차례로 병합했다: 둘째 · 셋째는 main 보다 2 · 4 커밋 뒤였지만 충돌 0 · 다시 하기 0. 이어 `bash ci/batch.sh --rc` 가 15분 7초에
끝났다 — 태그 → 자산 셋 6분 26초 · 필수 점검 리눅스 36초 · Windows 7분 7초 · 공개 워크플로의 시험 실행 15초. 공개 워크플로에
일부러 틀린 입력을 준 셋(해시 틀림 → d · 자리 표시 본문 → e · 연달아 두 번 → 겹치지 않고 차례로)과, 그 최종 확인이 부르는 버전
검사에 조상이 아닌 커밋을 준 것(→ 멈춤)이 모두 기대대로였다.

**60분 상한**(`AGENTS.md` *배포 전 룰은 올리지 않는다* 의 예외) — 6 이 잰 시간이 60분을 넘은 점검 룰이 있으면 그 출시는
공개하되 '모아 내기 멈춤 — <태그>' 이슈를 연다. 그 이슈가 열려 있는 동안 `batch.sh` 는 다음 묶음을 시작하지 않고, 그 전에
시작한 묶음도 공개 확인 j 에서 멈춘다(2026-11-22 — 앞 출시의 노출 시간 걸음은 공개 + 180초 뒤에 돈다) — 까닭을 적고 닫은 뒤
다시 부른다. 노출의 시작은 PR 을 연 시각이라 가지는 PR 을 열 때 함께 민다.

**멈추는 자리의 음성 시험**(2026-11-22) — 위 리허설의 손 시험과 나머지 칸을 CI 의 리눅스 잡이 돈다. 공개 확인은
`bash ci/publish-check-test.sh`(가짜 `gh` · 임시 저장소 — 칸 a ~ j 마다 깨뜨린 입력과 노출 시간 셋, 공개 뒤 익명 확인은 가짜 `curl` ·
`sleep` 으로 한도에 걸린 latest · 토큰 길 · 받은 latest 의 판정(태그 · 불변 · 초안 · 시험판 · 자산 수) · 받은 바이트 · jq 가 드는
곳), 묶음 명령의 멈춤(G9 대조 · 도구 최신 · 멈춤 이슈)은 `bash ci/batch.sh selftest`, 필수 점검 리눅스 몫은
`bash ci/emergency-checks-test.sh <지금 Latest 의 remedy-linux-x64.tar.gz>`(종료 1 하네스 · 데이터 룰 한 파일을 바꾼 꾸러미 —
깨뜨린 칸만 실패하는지 · docker · 74초)다. 게이트마다의 막는 자리 · 음성 시험 · CI 여부는 [하네스 README](../testbed/harness/README.md) 의 *출시 길의 게이트* 표에
있다 — 게이트를 고치면 그 시험을 함께 고친다.

**실패하면** — 점검이 실패한 초안은 `bash ci/batch.sh clean <태그>` 로 지운다(태그는 남는다 — 다음 묶음은 다음 룰 버전을
쓴다). 버린 묶음의 조각은 Latest 에 들지 않았으므로 다음 묶음에 저절로 실린다. 점검만 다시 하려면 `bash ci/batch.sh publish
<태그>`.

**하루 한 번 — 생성물.** `bash ci/batch.sh views` 가 README 의 *다루는 위협* · *위협별 안내* 두 표, 업데이트 내역 파일의 생성
구간(공개한 출시마다 그 조각으로 짓고 옮긴 조각은 지운다), 하네스 README 의 표를 `cargo xtask views --write` 로 지어 PR 하나로
병합한다(가벼운 길 CI). 그래서 저장소 첫 화면의 표와 업데이트 내역 파일은 최대 하루 늦다 — 받는 사람이 보는 릴리스 본문 ·
꾸러미 · 위협별 안내 절은 공개 때 맞다(위협 절은 룰 PR 과 함께 병합된다).

**새 엔진이 필요한 룰** — 싣는 엔진은 지금 Latest 의 것이다. 그 엔진이 읽지 못하는 룰(높은 `min_core` · 새 술어 · 모르는 칸)이
main 에 들면 다음 묶음이 배포 잡의 lint 에서 멈춘다. 그래서 룰 · 문서 · 하네스만 바뀐 PR 의 CI 가 지금 Latest 의 엔진으로 모든
룰을 lint 해 미리 막는다(엔진을 고친 PR 에서는 알리기만 한다). 그런 고침은 그 엔진을 공개한 뒤의 PR 로 나눈다.

### 버전 번호

**버전은 둘이다 — 엔진 버전과 룰 버전.** 받는 사람이 받는 것은 엔진과 그 OS 의 룰이 함께 든
파일 하나지만, 둘은 따로 오른다(2026-11-16 결정 — 엔진과 탐지 내용을 따로 매기는 보안 도구의
관행 · Defender 의 플랫폼 · 엔진과 보안 인텔리전스, ClamAV 의 엔진과 서명 DB, Nuclei 의 엔진과
템플릿). 전에는 룰만 더해도 엔진 버전의 마이너를 올려 열흘에 마이너가 19번 올랐고, 버전만
보고는 엔진이 바뀌었는지 알 수 없었다.

| 버전 | 자리 | 꼴 | 언제 오르나 |
|---|---|---|---|
| 엔진 | `Cargo.toml` 의 `[workspace.package] version` | SemVer `X.Y.Z` | 엔진(실행 파일을 짓는 코드)이 바뀔 때만 — 아래 표 |
| 룰 | 출시 때 정한다 — 룰만 바뀐 출시는 태그 이름(`bash ci/batch.sh` 가 고른다), 엔진 출시는 주석 태그의 메시지. 저장소에는 없다(2026-11-21 — 배포 잡이 꾸러미의 `plugins/RULES-VERSION` 에 써 넣는다) | 날짜 `YYYY.MM.DD` · 같은 날 둘째부터 `.2` · `.3` … | `plugins/` 의 룰이 지금 Latest 와 다를 때만 — 그 출시를 태그한 날(한국 날짜) |

| 엔진에서 바뀐 것 | 올리는 자리 | 예 |
|---|---|---|
| 종료 코드 · 명령줄 약속(인자 · 결과 파일의 꼴)을 바꾼다 | 메이저 | 아직 없다 |
| 엔진 기능 — 새 술어 · 화면 · 명령 · 동반 프로그램의 새 점검 | 마이너 | 1.16.0(메뉴를 하는 일로 묶었다) · 1.14.0(새 술어 `apk_version_lt`) |
| 버그 고침 · 의존성 · 툴체인 올림 | 패치 | 1.1.1(상대 경로로 띄운 치료의 재부팅 재검사) · 1.19.1(이미지 점검의 관리자 주소) |

'엔진' 은 실행 파일을 짓는 것 전부다 — `crates/` · `Cargo.toml` · `Cargo.lock` · `rust-toolchain.toml` ·
`.cargo/config.toml`. 새 룰 · 룰의 판정 고침 · 고친 버전 표 갱신은 **룰 버전만** 올린다. 룰마다의 버전도
그대로 있다(`plugin.yaml` 의 `version` — 룰을 고치면 올리고 `cargo xtask plugin-lock` 이 git 바탕과 견준다 · 위 "커밋하기 전에").

**태그는 출시의 종류를 말한다.**

| 출시 | 태그 | 시험판 | 업데이트 내역 칸 · Release 이름 |
|---|---|---|---|
| 엔진이 바뀐 출시(룰도 바뀔 수 있다) | `v<엔진 버전>` — `v1.20.0` | `v1.20.0-rc.1` | `## 1.20.0 · 룰 2026.11.15 — <공개일>` · `프로그램 1.20.0 · 룰 2026.11.15` |
| 룰만 바뀐 출시 — 엔진 코드가 지난 공개본과 같다 | `rules-<룰 버전>` — `rules-2026.11.18` | `rules-2026.11.18-rc.1` | `## 룰 2026.11.18 · 프로그램 1.20.0 — <공개일>` · `프로그램 1.20.0 · 룰 2026.11.18` |

**Release 이름은 한 꼴이다** — 출시의 종류와 상관없이 `프로그램 <엔진> · 룰 <룰>`(시험판은 태그가 이름 붙인 쪽에 `-rc.<N>` ·
배포 워크플로의 초안 잡이 짓는다). 2026-11-19 에 지난 Release 의 이름도 이 꼴로 고쳤다 — 룰 버전이 없던 1.19.1 까지는
`프로그램 1.19.1` 꼴이다. 업데이트 내역 칸의 머리는 그대로다(공개한 글이 그 머리로 지은 주소로 잇는다 — 2026-11-21 부터 그
칸은 하루 한 번 `cargo xtask views --write` 가 공개한 Release 의 이름 · 공개일과 그 출시가 실은 조각으로 짓는다).

두 태그 모두 같은 배포 워크플로가 꾸러미를 꾸리지만 실행 파일이 오는 곳이 다르다(2026-11-21). 엔진이 바뀐 출시(`v*`)는 그
커밋에서 짓고 두 걸음으로 간다(짓기 → 코드서명 걸음 → 둘째 걸음 · 위 "출시 검증" 3 · 5). 룰만 바뀐 출시(`rules-*`)는
**엔진을 짓지 않는다** — 버전 검사(`ci/version-check.sh`)가 견준 지금 Latest 의 꾸러미를 받아(`ci/release.sh fetch-prev`)
체크섬(SHA256SUMS) · 코드서명(Windows — 유효 · 주체 · 타임스탬프) · 정적 링크 · 버전 줄(= Latest 의 엔진 버전)을 재고, 그
엔진으로 모든 룰을 lint 한 뒤 그 실행 파일 둘을 그대로 싣는다. main 의 엔진 코드가 Latest 보다 앞서 있어도 된다(2026-11-21 —
전에는 엔진 코드가 지난 공개본과 같아야 해서, main 에 공개 전 엔진 변경이 들면 룰 출시가 멈췄다 · 첫 공개 뒤 시간의 42%). 그래서 **태그 push 한 번**으로 두 OS 꾸러미와
SHA256SUMS 까지 초안에 올라가고(코드서명 걸음 · 둘째 걸음이 없다 — 그 태그에서 `workflow_dispatch` 를 부르면 잡이 멈춘다),
받는 사람의 실행 파일은 지난 공개본과 같은 바이트(Windows 는 같은 코드서명)다. 그 공개본의 Release 가 공개된 정식(초안 ·
시험판이 아니고 자산 셋)이 아니거나 불변이 아니면(공개 뒤 자산을 바꿀 수 있으면) 초안을 만들기 전에 멈추고, 지난 공개본으로
고르는 태그는 정식 꼴(`v<엔진 버전>` · `rules-<룰 버전>` — 사선이 든 이름은 빼고)만이다. 배포 키를 바꾼 뒤의 첫 출시는
`v*` 여야 한다 — 받은 실행 파일은 옛 공개키를 담아 룰 서명 확인이 거부로 멈춘다. 룰만 바뀐 출시는 지난 공개본의 엔진을 그
엔진의 알려진 권고 · 결함까지 그대로 싣는다(다시 짓던 때도 같은 소스 · 같은 의존이었다) — 엔진을 고칠 일이면 `v` 출시로
내고, 그 뒤의 룰 출시가 고친 엔진을 싣는다. 두
태그 모두 태그 보호 룰셋 `release-tags` 로 조직 Owner 만 만들고, 서명 비밀을 든 Environment
`release` 는 두 태그에서만 열린다. 릴리스 본문 2절의 머리는 두 버전을 칸마다 지난 공개본과 견준다 — 같으면 `<값> 그대로`,
다르면 `<지난 값> → <이번 값>`(예: `(프로그램 1.26.0 → 1.27.0 · 룰 2026.11.27 그대로)` · 차례는 Release 이름과 같다 ·
`ci/release-notes.sh` 가 지난 값을 지난 공개본의 Release 이름에서 읽는다 · 2026-11-28 — 전에는 태그 종류마다 한 칸이라 종류가 다른
두 출시 사이에서 `룰 2026.11.27` → `프로그램 1.27.0` 처럼 다른 것을 견줬다). 본문의 바뀐 내용은 업데이트 내역 파일의 칸이 아니라
조각에서 짓고(2026-11-21), 첫 화면에는 칸마다 꼭대기 항목의 제목 줄만, 나머지는 그 칸의 접기에 원문 그대로 둔다(2026-11-28).

받는 사람은 두 버전을 함께 본다 — 화면 머리말 첫 줄(`ESTsecurity 전용백신 1.20.0 · 룰 2026.11.15`) ·
`--version` 의 둘째 줄 · 꾸러미 `README.txt` 의 `프로그램` · `룰` 줄 · Release 이름. 엔진은 꾸러미의
`plugins/RULES-VERSION`(배포 잡이 써 넣는다 — 저장소에는 없다)을 읽어 **보여 주기만 한다** — 서명 밖의 파일이라 무엇을 돌릴지
정하는 데 쓰지 않는다(`remedy_sdk::rules_version`). 저장소 사본으로 지은 개발 빌드는 그 파일이 없어 룰 버전 줄을 보이지 않는다.

**정책을 따르는지는 배포 워크플로가 본다** — 시험판 태그에서부터(`ci/version-check.sh <태그>` —
저장소 루트에서 `bash` 로 그대로 돈다 · `bash ci/batch.sh` 는 태그를 밀기 전에 부른다). **지금 Latest**(공개된 정식
Release — gh 로 읽는다)와 견준다(2026-11-21 — 전에는 첫 부모 역사에서 가장 가까운 정식 태그였고, 병합으로 들어온 긴급 태그를
건너뛰어 낮은 룰 버전의 태그가 지났다). 그 스크립트를 고치면 `bash ci/version-check-test.sh` 를 돌린다 — 이 저장소의 역사를
쓰지 않고 임시 폴더에 작은 저장소를 지어 34 경우(통과 11 · 멈춤 21 · 잡 출력 둘)를 돌린다. CI 의 리눅스 잡도 이 시험을
돈다(가벼운 길의 PR 은 건너뛴다). 릴리스 본문 스크립트(`ci/release-notes.sh`)는 `bash ci/release-notes-test.sh` 가 같은 꼴로
본다 — 저장소 밖 사본에 가짜 버전의 조각과 위협 표 · 지난 공개본의 이름을 파일 · 인자로 줘 본문 다섯(룰만 · 엔진 · 각 rc 꼬리 ·
짧은 꼴의 가장자리 — 버전 줄과 2절 본문을 기대 본문과 바이트로)과 멈춤 장치 열둘 · 표 머리 이름 바꿈을 돌린다(18 경우). PR 의 CI 리눅스 잡이 돌리므로 위협 표 머리 · '하는 일' 문구와 스크립트가 어긋나면 태그 전에 드러난다.

- 둘 다 — 지금 Latest 가 그 커밋의 조상이다(아니면 새 Latest 가 지금 Latest 의 룰을 빠뜨린다) · 룰이 바뀌었으면 룰 버전이
  Latest 보다 높고, 그대로면 룰 버전도 그대로다 · 룰 버전의 날이 오늘(한국 날짜) + 1 을 넘지 않는다
- `v` 태그 — 태그 = `Cargo.toml` 의 엔진 버전 · 엔진이 Latest 가 싣는 엔진(태그 `v<그 버전>` 의 나무)과 다르다 · 엔진 버전이 더
  높다 · 룰 버전은 주석 태그 메시지의 첫 줄 `프로그램 <엔진> · 룰 <룰 버전>`(`bash ci/batch.sh engine-tag` 가 짓는다)
- `rules` 태그 — 태그 = 룰 버전 · 룰이 바뀌었다. main 의 엔진은 앞서 있어도 된다 — 싣는 것은 Latest 의 엔진이고, 배포 잡이 그
  실행 파일로 모든 룰을 lint 한다

엔진이 바뀌었는지는 버전 줄을 가린 꼴로 견준다(`Cargo.toml` 의 `[workspace.package]` · `Cargo.lock` 의
작업 공간 크레이트) — 버전만 올린 것은 엔진이 바뀐 것이 아니다. 기능인지 고침인지는 사람이 가린다. 룰은 `plugins/` 전부다 —
옛 룰 버전 파일 · 잠금 · 룰 폴더의 개발 키 서명(`MANIFEST` · `MANIFEST.minisig`)은 빼고 견준다.
엔진도 룰도 아닌 것(꾸러미를 짓는 `xtask/` · 문서 · 하네스)만 바뀐 것은 혼자 내지 않는다 — 어느 태그도
통과하지 못하고, 다음 출시에 함께 실린다. 룰 PR 은 `crates/` · `xtask/` 0줄이다(`긴급-대응.md` *쓰는 조건*).

## 새 룰을 더할 때 — 룰 폴더 밖에서 손대는 자리

엔진 코드(`crates/`)는 0줄이다 — 제품 코드에 룰 id 를 박은 목록이 없고, 배포 워크플로는 룰 목록을
`xtask threats --dirs <os>` 로 받는다. 룰 폴더(`plugins/<id>/`) 밖에서 손대는 자리는 셋이다(2026-11-21 — 전에는 일곱이었고
그 가운데 넷(잠금 · README 표 · 룰 버전 · 업데이트 내역 칸)을 룰 PR 마다 고쳐 함께 지으면 늘 충돌했다 · 위 "출시 검증" 의
*모아 내기*). README 두 표 · 하네스 README 표 · 업데이트 내역 파일 · 룰 버전은 손으로 고치지 않는다 — 출시 때 짓거나 하루 한 번
생성물로 갈아 끼운다.

| # | 자리 | 무엇을 | 빠뜨리면 |
|---|---|---|---|
| 1 | `docs/changes/<룰 id>-<새 버전>.md` | 업데이트 내역 조각 하나 — 꼴은 [그 폴더의 안내](changes/README.md)(합쇼체 `* **바뀐 것**` 과 설명 줄 · 위협 소제목은 생성기가 위협 표 이름으로 짓는다) | `xtask all` 의 `fragments` 가 막는다(`version` 을 올린 룰에 바탕 뒤의 조각이 없거나 꼴이 어긋나면). 릴리스 본문의 *2. 변경 내용* 은 그 출시가 지금 Latest 뒤에 새로 실은 조각을 모은 것이다(첫 화면은 칸마다 꼭대기 항목의 제목 줄 · 나머지는 그 칸의 접기) — 미리 보기: `bash ci/release-notes.sh rules-<다음 룰 버전>` · 원문은 `cargo xtask changes --since <지금 Latest 의 태그>` |
| 2 | `docs/위협별-안내.md` 의 그 위협 절(세 줄 · 자세히 · 제목 위 고정 주소 `<a id="<위협>"></a>`)과 그 바로 아래 표지 줄 `<!-- 안내 표: <위협> \| <OS> \| <링크 글> -->` | 손으로 쓴다 — 다운로드 페이지 글이 그 고정 주소를 가리킨다(`docs/긴급-대응.md` *사용방법 틀*). README *위협별 안내* 표는 표지 줄에서 하루 한 번 짓는다 | 막는 검사가 없다 |
| 3 | `testbed/harness/{linux,host}/<룰>-verify.*` | 하네스 새 파일. 머리에 줄 셋 — `# 룰: <룰 id>…`(리눅스 · Windows — PR CI 의 룰 하네스와 모아 내기의 필수 점검 ① 이 이 줄로 찾는다) · `# rc 묶음: <단계 이름>`(rc 묶음 두 스크립트가 이 줄로 찾는다 — 표준 인자 `--bin` · `--plugins` · `--out` 을 받는 하네스만) · `# 하네스 표: <실행 위치> \| <역할>`(하네스 README 표). 필수 점검은 러너가 돌므로 리눅스는 `# 이미지:`(미리 받을 이미지) · Windows 는 `# 입력:`(받아 대조할 공식 zip — [하네스 README](../testbed/harness/README.md) *머리 줄로 찾는 하네스* · 받을 것이 없으면 `# 입력: 없음`)도 단다 | PR CI 와 필수 점검 ① 이 멈춘다(2026-11-22 — 전에는 적기만 하고 지났다) — 판정 파일(`plugin.yaml` · `rules/` · 데이터 파일)을 고친 룰에 그 OS 의 `# 룰:` 하네스가 없으면. 데이터 룰(`kind: data`)은 하네스 대신 `cargo xtask net-criteria` 가 본다. `# 이미지:` 가 모자라면 그 하네스가 러너에서 종료 2 로 멈춘다 |

룰 폴더 안 — 점검 룰의 `RELEASE.md` 맨 앞(버전 절보다 위)에 *0 을 내는 갈래* 표(`| 갈래 | 근거 | 하네스 칸 |`)를, 린트 경고가
남은 룰은 *린트 경고* 표(`| 자리 | 까닭 |`)를 둔다 — `cargo xtask rule-records`(`xtask all`)가 본다(2026-11-22). 갈래마다 1차
출처와 그 갈래를 재는 하네스의 기대 0 칸 id 를 적는다. 댈 수 없으면 `근거 없음 — <무엇이 없는지>` · `없음` 으로 적는다 — 빈틈이다.
빈틈은 git 바탕보다 늘면 막히고, 새 룰은 빈틈 없이 든다. 보지 않는 자리(기록의 *보지 않는 것*)는 갈래가 아니라 넣지 않는다.

**같은 제품의 찾는 조건은 원본 한 곳에서**(2026-11-23) — 같은 제품의 점검 룰은 그 제품을 찾는 조건(깔린 자리 · 패키지 밖 · 도는
프로세스 · 서비스 · 설정이 싣는 모듈 · 다시 시작하지 않음 · 바뀐 파일)을 룰마다 다시 적었고, 그 고침을 손으로 옮기다 어긋났다. 이제
그 조건은 `products/<제품>.yaml` 의 칸(`# === <칸>` 줄부터 다음 칸까지 · 들여쓰기 없이)에 두고, 룰의 `plugin.yaml` 은 그 자리에
울타리 두 줄 `# >>> 제품 <제품> <칸>` · `# <<< 제품 <제품> <칸>` 을 둔다. 울타리 사이는 손으로 고치지 않는다 — 원본을 고치고
`cargo xtask products --write` 로 같은 제품의 룰을 모두 채운다(울타리 줄의 들여쓰기만큼 민다). `xtask all` 의 `products` 가 원본과
다른 울타리를 막고, 채운 룰마다 버전 올림과 조각은 `plugin-lock` · `fragments` 가 요구한다 — 같은 제품의 룰이 함께 나간다. 울타리
밖(고친 판의 줄 · 문구 · 판정식)이 그 룰의 몫이다. 원본은 꾸러미에 들지 않는다 — 받는 사람에게는 채운 `plugin.yaml` 이 그 룰
폴더째 서명되어 간다. 원본은 같은 제품 · 같은 OS 의 점검 룰 둘 이상이 같은 찾는 조건을 나눠 쓸 때 둔다(2026-11-25) — 새 제품의
첫 룰은 원본 없이 그 조건을 `plugin.yaml` 에 바로 적는다(울타리 없는 룰은 `products` 가 건너뛴다). 원본 이름(울타리의 `<제품>`)은
`product` 값이 아니라 제품과 OS 를 붙인 `php-linux` 꼴이고 지금은 이 하나다 — Windows PHP 룰 셋은 같은 찾는 갈래 여덟을 아직
룰마다 적는다(원본으로 옮기기 전이다 — 그때까지 그 갈래를 고치는 PR 은 셋을 함께 고친다).

조건에 따라 더 — 표준 인자 밖의 인자가 드는 하네스는 rc 묶음 두 스크립트(`linux/rc-bundle.sh` · `host/Invoke-RcBundle.ps1`)에
손으로 단계를 쓴다. 리눅스 룰이면 콘솔 기준선 4벌과 화면 문서도 바뀐다(리눅스 캡처가 리눅스 룰 전부를 담는다) — 룰 PR 이 아니라
공개 뒤의 미룬 검증(재캡처 · 후속 PR)이 갈아 끼운다(`docs/긴급-대응.md` *뒤로 미루는 것*). remedy-net 기준과 같은 공지를 쓰는 룰
(PHP · Node · Apache)이면 `plugins/remedy-net-criteria/*.json` 과 `xtask/src/netcriteria.rs`(룰 id 가 박혀 있다) — 기준
파일을 룰과 같은 값으로 맞추고 그 데이터 룰의 `version` 을 올린 뒤(조각의 `rules` 에 그 데이터 룰을 위협 룰과 함께 적는다) `cargo xtask net-criteria` 로 본다(이
검사는 기준 → 룰 쪽만 견준다 — 룰에 더한 공급사 · 배포판 줄은 기준에도 손으로 더한다 · `docs/긴급-대응.md` *단계 0 ~ 2 에서
걸리는 것*). AI
시험 위협으로 두면 `xtask/src/exam.rs` 의 REFERENCES. leaks 오탐이 나면 `xtask/leaks-except.txt`.

**룰 수에 비례하는 비용** — *모두 검사* 는 룰마다 처음부터 다시 수집한다(합성 1,000개: 리눅스 약 3.5분 · Windows 약
35분 — 11-16 결정 D9 로 1시간 안). 실제 룰이 수백 개가 되면 한 번의 모두 검사 동안 읽기 결과를 나눠 쓰게 한다 —
`remedy-platform` 의 읽기 trait 넷을 감싸 기억하는 장식자 하나와, `remedy-core` 의 `collect_declared` 두 자리가 그
백엔드를 받게 하는 변경이다(한 크레이트 안 · 수집기와 결과 파일은 그대로). 뿌리의 합집합을 한 번 걷는 길은 범위 ·
잘림 · 관측 완전성 판정이 룰마다 달라져 크레이트 셋에 걸친 구조 변경이다 — 앞의 것으로 모자랄 때 다시 잰다.

## 화면을 고칠 때

고객이 보는 경로의 한국어는 **실패·거절·미룸 사유까지 전부 합쇼체**다. 조사는
`remedy_sdk::i18n` 의 조사 함수로 앞말 받침에 맞춰 고르고 `이(가)` 병기는 쓰지
않는다. 일부러 해라체로 남긴 자리가 있다 — `--help-all` · `plugin lint` 진단 ·
매니페스트 검증 · 카탈로그의 필드 설명(작성자·개발자용).

**화면 문구를 바꾸면 하네스의 판독 문구도 함께 고친다.** 긍정 단정은 실패로
드러나지만 **부정 단정과 세는 단정**(`-notmatch` · `[regex]::Matches`)은 옛 꼴을
0건으로 세어 **조용히 늘 통과한다.** 옛 문구로 `testbed/harness` 전체를 찾고,
변수에 담은 패턴까지 본다.

## Windows·WSL 에서 겪는 것

**새로 뜨는 콘솔의 코드페이지가 UTF-8 이 아닐 수 있다.** 그런 기계에서 하네스를
숨은 창으로 띄우면 UTF-8 한글 판정 줄이 깨져 전부 `판정 못 읽음` 이 된다. 줄 끝
바이트가 선행 바이트가 되면 **줄바꿈까지 먹혀 두 줄이 붙는다.** 출력을 직접 읽는
쪽은 `StandardOutputEncoding` 을 UTF-8 로 두고, 셸을 거칠 때는 그 셸의
코드페이지를 확인한다.

**`$LASTEXITCODE` 는 프로세스 전역이다.** `& <스크립트>` 는 같은 프로세스에서
돌므로, 그 스크립트가 `exit` 를 두지 않으면 읽는 쪽은 **앞서 돈 다른 네이티브
명령**의 코드를 본다. 하네스가 성공 경로에서 `exit` 를 두지 않아 11/11 인 회차가
실패로 찍힌 적이 있다. `exit $변수` 도 주의한다 — 변수가 비면 0(통과)이 된다.

**`.ps1` 은 UTF-8 BOM 으로 저장한다.** BOM 이 없으면 PowerShell 5.1 이 ANSI 로
읽어 한글 주석의 바이트를 따옴표·괄호로 오독하며 파싱이 무너진다. **`.json` 은
그 반대로 BOM 이 없어야 한다** — 대부분의 파서가 거부한다.

**`.ps1` 을 `sed -i` 로 고치지 않는다.** 이 저장소의 `.ps1` 은 줄 끝이 섞여
있고(CRLF 와 LF), `sed -i` 는 CRLF 파일을 다시 쓰며 LF 로 바꾼다. 한 줄만 고쳐도
diff 가 파일 전체로 부푼다.

**변수나 종료 코드가 들어가는 WSL 명령은 스크립트 파일로 부른다.**
`wsl … bash -c '… $VAR … $?'` 는 셸이 두 번 끼어들어 변수가 비고 `$?` 가 언제나
0 이 된다. 종료 코드는 스크립트 안에서 파일에 적어 그 파일로 확인한다.

**다른 프로세스가 덧붙여 쓰는 파일에 `tail -f` 를 걸지 않는다.** Windows 에서는
그 파일이 잠겨 쓰는 쪽이 실패하고, 그 실패는 조용히 삼켜질 수 있다.

**Git Bash 에서 WSL 스크립트는 `MSYS_NO_PATHCONV=1 wsl -e bash /mnt/…` 로 부른다.** 없으면
Git Bash 가 `/mnt/…` 를 `C:/Program Files/Git/mnt/…` 로 바꿔 스크립트를 찾지 못하고 127 로 끝난다.

## 서명

`cargo xtask sign` 은 `REMEDY_SIGN_PASSWORD` 가 없으면 **TTY 에 암호를 묻는다.**
자동화에서는 stdin 이 리다이렉트되어 그 프롬프트가 끝나지 않는다. 종료도 오류도
없이 0바이트 파일만 남아 **"빌드가 느리다" 처럼 보인다.**

**저장소의 룰 폴더에는 서명이 없다**(2026-11-21). 전에는 룰 · 데이터 룰마다 개발 키 서명(`MANIFEST` ·
`MANIFEST.minisig`)을 커밋했다 — 배포물 · CI · 하네스 어느 것도 그 서명을 믿지 않았고, 트리와 어긋난 서명이 CI 를 지나
출시된 일이 두 번 있었으며(#26 → v1.1.0 · #57 → v1.9.0), 키와 암호가 한 PC 에만 있어 처음 보는 사람이 막혔다. 지금은 서명이
필요한 자리에서 그때 한다.

| 자리 | 누가 · 어떤 키로 |
|---|---|
| 배포 꾸러미 | 배포 워크플로가 Environment `release` 의 배포 키로(`ci/release.sh`) |
| remedy-net 개발 빌드가 판정 기준을 읽을 때(PR 전 하네스) | `bash ci/dev-sign.sh --out <폴더> plugins/remedy-net-criteria` — 그 자리에서 만든 일회용 키로 사본을 서명하고 앵커(`<폴더>/anchor.txt`)를 낸다. 개인키는 서명 뒤 지운다 |
| 서명 확인이 도는가(CI) | `bash ci/sign-check.sh <remedy> [<remedy-net>]` — 일회용 키로 모든 룰의 사본을 서명해 확인 · 고친 사본의 거부(종료 5) · remedy-net 의 기준 확인을 본다(리눅스 잡) |

일회용 키도 `cargo xtask sign` 으로 짓고 서명한다 — 두 스크립트는 암호를 그 자리에서 만들어 `REMEDY_SIGN_PASSWORD` 로
넘긴다. 손으로 `cargo xtask sign plugin` 을 부를 때는 `--signed-at`(`YYYY-MM-DDTHH:MM:SSZ` · UTC)을 빠뜨릴 수 없다.

## 매니페스트 값의 원문 모양

따옴표 없는 YAML 값은 뜻이 바뀐다. `8.10` 은 실수로 읽혀 `8.1` 이 되고, 그러면
`version_lt` 가 완전히 패치된 기계를 양호로 보낸다. **버전·고정 폭 식별자는
따옴표로 감싼다.** 코드 쪽 가드는 린트와 평가기 **양쪽**에 있어야 한다 — `scan`
은 린트를 돌리지 않는다.

Windows PE 의 버전은 **두 눈금**이다(문자열과 2진 `VS_FIXEDFILEINFO`, 실물의
20%가 서로 다르다). 공급사는 문자열 눈금으로 공지하므로 2진 값을 담으면 권고대로
적은 비교가 틀린 답을 낸다. 권위는 `crates/remedy-collect/src/peversion.rs` 의
머리말이다.
