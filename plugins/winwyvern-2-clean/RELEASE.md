# winwyvern-2-clean — 릴리스 기록

**버전 0.2.0** · 대상: WinWyvern — 정상 AI 도구(Ollama) 배포 페이지로 위장한 사이트로 퍼진 악성코드가, 보안 제품을 무력화하는
악성 드라이버 WinWyvern 을 올리려고 심는 취약 드라이버 NeacSafe64(CVE-2025-45737) · Windows · **치료**(서비스 · 되돌릴 수 있다)

> 같은 위협의 다른 하나는 `winwyvern-1-check`(탐지만)다. 판정은 둘이 같다.

## 0.2.0 — 3차: 다시 시작해야 끝나는 치료를 엔진이 알린다 (2026-11-26 · 코어 1.26.0)

긴급 대응의 3차다. **룰의 판정 · 치료 줄은 0.1.0 그대로**이고 `min_core` 만 1.26.0 으로 올렸다 — 아래는 그 엔진이 이 룰의 치료에서
바꾸는 것이다(엔진 조각 `docs/changes/engine-restart-pending-2026-11-25.md` · 이슈 #172 ⑥). 아래 0.1.0 의 *판정* · *치료 뒤 운영자가 할
일* · *이 룰이 보지 않는 것* 은 그대로다.

그대로 맞고, 다시 시작하기 전의 복원은 이제 엔진이 막는다.

## 0.1.0 — 2차 (2026-11-25)

긴급 대응의 2차다(`docs/긴급-대응.md` *2 · 3차* · 코어 그대로 — 엔진을 고치지 않았다). 1차(`winwyvern-1-check` 0.1.0)가 찾기만
하던 것 가운데 **서비스를 치료**한다. 드라이버 파일은 남겨 흔적으로 알린다. 숨긴 DLL 은 1차처럼 보지 못해 남는다 — 위협별
안내의 *꼭 할 일* 이 알린다(아래 *이 룰이 보지 않는 것*).

**1차 출처** — ASEC, *"BYOVD를 통한 국내 보안 제품 무력화 시도: 정상 AI 도구로 위장한 악성코드 유포 주의"*(한국어판
2026-11-23 <https://asec.ahnlab.com/ko/96707/> · 영문판 2026-11-20 <https://asec.ahnlab.com/en/96708/>). 지표는 이 보고에 있는
것만 쓴다(1차와 같다). 실검체는 없다 — 측정과 하네스는 표지 글자만 담은 자리 채우기와 시작하지 않는 서비스 등록으로 잰다.

### 무엇을 하나

- **판정** — `winwyvern-1-check` 와 같다(조건 · 라벨 · 판정식이 같은 줄이다). 레지스트리의 서비스 등록과 디스크의 드라이버
  파일, 독립적인 두 근거가 함께 서야 위협이다. 하네스가 두 룰의 판정을 꼴마다 견준다.
- **치료** — 서비스 `NeacSafe64` 하나다. 엔진이 정한 차례로 복구 설정 해제 → 정지 → 사용 안 함 → 삭제(4건)를 한다(설계-03 §2).
  정지 말고 셋은 서비스의 정의 키를 하위 트리째(`Instances` 포함) 백업한 뒤에 하므로 `restore` 로 되돌린다.
- **드라이버 파일은 치료하지 않는다** — `%SystemRoot%\System32\neacsafe64.sys` 는 판정의 근거로만 쓰고 흔적으로 남긴다. NetEase
  의 정상 서명된 안티치트 드라이버라(ASEC) 진짜 파일이면 엔진이 서명을 보고 격리를 미루고(2층), 서비스가 없으면 부팅 뒤
  올라오지 않는다. 치료 뒤 검사는 그 파일을 흔적 1건으로 적고 0 을 낸다.
- **재부팅 뒤 재검사** — `verify.after_reboot`. 치료가 HKLM 의 RunOnce(`remedy-verify`)에 같은 룰의 재판정을 걸고, PC 를 다시
  시작해 **관리자로 로그온하면** 돈다(`docs/operator.md` §6 — 표준 사용자로 로그온하면 돌지 않는다). 서비스가 다시 생겼으면
  재발(2)이다.
- **`kind: check` 가 아니다** — 감염의 흔적이다(1-check 와 같다). **빠른 검사에 남는다** — 보는 자리는 레지스트리의 서비스 목록과
  `%SystemRoot%\System32` 바로 아래의 그 이름 파일뿐이다(깨끗한 기계는 6 이 아니라 0). **고르는 화면** — `added: "2026-11-25"`
  라 *새로 추가된 항목* 에 선다(코어 1.25.0).

### 치료 뒤 운영자가 할 일

위협별 안내의 *꼭 할 일* 과 같은 차례다(인터넷이 막힌 곳을 위해 여기에도 둔다).

1. **다시 시작하기 전에** 화면의 *검사 완료* 줄과 찾은 항목(명령으로 돌렸으면 `--out-dir` 폴더의 `scan.json`)을 담당자에게
   보낸다 — 다시 시작하면 그 화면이 닫힌다. 화면 캡처나 메뉴의 *신고에 붙일 것 모으기*(치료한 기록이 있을 때 보인다 · 다시
   시작한 뒤에도 만들 수 있다)로 보낸다.
2. **PC 를 다시 시작해 관리자로 로그온한다** — 그때 재부팅 뒤 재검사가 돈다. 표준 사용자로 로그온하면 돌지 않으므로 관리자가
   메뉴의 *3. 치료가 유지됐는지 다시 보기* 로 확인한다. 위협이 다시 나오면(서비스가 다시 생겼으면) 담당자에게 알린다.
3. **다시 시작한 뒤** 백신을 최신 버전으로 올려 PC 전체를 정밀 검사한다 — 메모리에만 올라간 WinWyvern 드라이버는 백신의
   메모리를 고쳐 탐지 · 치료 기능을 끄려 하므로(ASEC) 다시 시작하기 전에는 백신이 고쳐진 채일 수 있다. 숨긴 DLL 은 치료 뒤에도
   남으므로, 결과가 깨끗해도 이 PC 를 감염된 것으로 보고 담당자의 안내를 따른다.
4. Windows 보안의 *장치 보안 → 코어 격리* 에서 *메모리 무결성* 과 *Microsoft 취약 드라이버 차단 목록* 을 켜고 PC 를 다시
   시작한다.

정상 설치를 지웠다고 판단해 되돌릴 때는 **PC 를 먼저 다시 시작한 뒤** `restore` 로 되돌리고 한 번 더 다시 시작한다(아래 *잰 것*
— 삭제가 미뤄진 갈래).

### 잰 것 — 2026-11-25 랩

Windows 10 22H2(빌드 19045) 랩 VM · 개발 꾸러미(엔진 1.25.4 — 지금 Latest 와 같은 엔진 코드 · 일회용 키 서명) · 이 룰의 초안(판정 ·
치료 줄이 0.1.0 과 같고 이름만 달랐다). 서비스는 `sc.exe create`(파일 시스템 드라이버 · 자동 시작)로 등록만 하고 시작하지

값)을 더했다.

| 재부팅 뒤 확인 | 랩은 재부팅 뒤 로그온이 없어 OS 가 띄우지 않았다(RunOnce 는 로그온 때 돈다) — 걸린 명령줄을 그대로 띄워 0 · 기록 `outcome: clean` · 그 뒤 예약이 지워졌다 |

**삭제가 미뤄진 갈래 — 서비스 핸들을 열어 둔 채 잰 것**(같은 날 · 같은 랩 · 다시 지은 개발 꾸러미 · 룰은 이 0.1.0 과 같은
바이트). 위 표와 하네스 `T5` · `T6` 은 시작한 적 없는 서비스라 삭제가 곧바로 끝나 키가 사라진 갈래다. 정지가 실패했거나 서비스
핸들이 열려 있으면 삭제가 미뤄진다 — 서비스 관리자는 서비스가 멈추고 핸들이 모두 닫혀야 지우고, 멈추지 못한 서비스는 다시 시작할
때 지우며, 지울 때 서비스 키와 하위 키를 지운다(Microsoft DeleteService 문서). 자동 시작인 정상 설치의 드라이버는 돌고 있을
가능성이 커 오탐을 되돌리는 기계가 이 갈래일 수 있다. 게스트의 프로세스 하나가 그 서비스의 핸들(상태 조회 권한만)을 쥔 채로
치료하고 두 되돌리기 차례를 견줬다(세운 꼴은 위와 같다 — 치료 전 값 목록 11줄).

| 무엇 | 결과 |
|---|---|
| 치료(`run --yes`) | 1 · 4건 모두 끝남 · 화면은 '치료 완료' — 곧바로 지워진 치료와 같다(저널 · `--events` 도). 그런데 **서비스 키가 남았다** — `Start` 4 · `DeleteFlag` 1 · 하위 키 그대로 · 서비스 관리자도 그 서비스를 안다(`sc.exe query` 0 · 멈춤). 다시 검사 0(두 룰 · 흔적 1 — 시작 유형이 자동이 아니라 서비스 근거가 서지 않는다) |
| 다시 시작하기 전에 곧바로 복원 | 0 · 3건 · 다시 검사 2(두 룰) — 되돌아온 것처럼 보인다. 그러나 `DeleteFlag` 가 남았고, **핸들을 쥔 프로세스가 끝나자 서비스 관리자가 복원한 키를 하위 키째 지웠다**(끝난 것을 본 뒤 0.27초 안에 — 0.25초 간격으로 봤다) — 그 뒤 `sc.exe query` 1060 · 다시 검사 0(두 룰) |
| 안내의 차례 — 먼저 다시 시작 → 복원 → 한 번 더 다시 시작 | 첫 재시작 뒤 키가 없다(미뤄진 삭제가 끝났다 · 1060) → 복원 0 · 3건 · 값 목록이 치료 전과 같다(`DeleteFlag` 없음 · 아직 1060) → 둘째 재시작 뒤 서비스 관리자가 그 서비스를 안다(`sc.exe query` 0 · 자동 시작) · 값 목록 그대로 · 다시 검사 2(두 룰) |

그래서 안내 · 조각의 차례(*먼저 다시 시작 → 복원 → 한 번 더 다시 시작*)가 맞다. 화면으로는 이 갈래인지 알 수 없다 — 엔진은
`sc.exe delete` 의 0 만 보고 키가 남았는지 보지 않고(`crates/remedy-apply/src/lib.rs`), 복원은 남은 키를 그대로 열어 백업한 값만
써 넣어 `DeleteFlag` 를 남긴다(`crates/remedy-platform/src/windows.rs` 의 `registry_key_restore` · 백업 셋은 모두 동작 전 상태).
안내가 갈래를 가리지 않고 늘 먼저 다시 시작하라고 적는 것이 그 빈자리를 덮는다(*다음 차수 후보*). 둘째 재시작에서 서비스 관리자는
복원한 자동 시작 서비스를 올리려 했다 — 자리 채우기라 올라오지 못했고(193 · 부팅은 이어졌다) 정상 설치라면 그 드라이버가
올라올 것이다(실물로 재지 않았다).

**재지 못한 것** — 도는(실린) 드라이버의 정지와 미뤄진 삭제: 무해하게 재현할 수 없다. 서비스 관리자가 정지를 받지 않는
드라이버면 정지가 실패해 3(일부만)일 것이다 — 사용 안 함 · 삭제는 이어 돌고, 멈추지 못한 서비스의 삭제는 다시 시작할 때
끝난다(같은 문서). 지울 표시가 남는 것은 위 열린 핸들 갈래와 같고 끝나는 때만 다르다 — 안내의 차례는 첫 재시작이 미뤄진 삭제를
끝낸다는 데 기대므로 이 갈래에도 맞을 것이다(재지 않았다).

재부팅 칸(치료 → 재부팅 → 검사 · 재부팅 뒤 확인)과 삭제가 미뤄진 갈래는 한 OS(Windows 10)에서만 쟀다 — 위 첫 표의 치료 ·
복원 · 값 목록 칸은 러너(Windows Server 2025)에서도 PR CI 의 하네스가 쟀다(아래 *게이트* 의 하네스).

### 이 룰이 보지 않는 것 — 종료 0 이 뜻하는 것

- **대체 데이터 스트림에 숨긴 악성 DLL**(ASEC — `C:\Windows\System32:msedge.exe`) — 엔진이 대체 데이터 스트림을 모으지 않고(파일
  기록의 `streams` 칸을 채우지 않는다) 지우는 동작도 계획하지 않는다. **치료 뒤 0 이어도 남는다** — 위협별 안내의 *꼭 할 일*
  (백신 정밀 검사 · 담당자).
- **드라이버 파일** — 보지만 치료하지 않는다(위 *무엇을 하나*). 치료 뒤 그 파일만 남아 흔적 1건이고 0 이다.
- **커널 쪽** — 커널 메모리에만 올린 WinWyvern 드라이버(따로 된 드라이버 파일이 없다 — 숨긴 DLL 안에 있다가 커널 메모리에
  올라간다 · ASEC) · 이미 올라와 도는 취약 드라이버(서비스를 지워도 다시 시작할 때까지 메모리에 남을 수 있다) · 무력화된 보안
  제품의 메모리. 지금 도는 드라이버 · 장치는 관측 대상이 아니다.
- **서비스를 다시 만드는 것** — 숨긴 DLL 이 서비스를 스스로 다시 만드는지는 공개되지 않았다(ASEC 그림 9 는 드로퍼가 서비스를
  만들거나 자동 시작으로 바꾼다고 보인다). 다시 만들면 재부팅 뒤 재검사가 재발(2)로 드러낸다.
- **정상 NetEase 설치** — 확인하지 못했다. 정상 설치의 서비스 모양(시작 유형 · 자리)은 ASEC 에 없고 실물로 재지 않았다. 정상
  설치가 이 판정의 꼴(자동 시작 · System32 바로 아래의 그 파일)과 같다면 그 안티치트 서비스를 지운다 — PC 를 먼저 다시 시작한
  뒤 `restore` 로 되돌리고 한 번 더 다시 시작한다(위 *잰 것* — 삭제가 미뤄진 갈래). 2차는 서비스를 지우므로 오탐의 대가가
  찾기만 하는 1차보다 크다.
- **서비스나 파일 하나만 남은 기계 · 다른 시작 유형 · 다른 자리 · 다른 이름** — 1-check 와 같다. 흔적으로 적고 0 이며 치료하지
  않는다.
- **설치 파일과 C2 가 내려보낸 페이로드 · 드로퍼** — 1-check 와 같다(ASEC 이 지표를 내지 않았다 · 드로퍼는 MD5 만 공개됐다).

그래서 치료 뒤의 종료 0 은 *"이 룰이 보는 꼴 — 자동 시작으로 등록된 그 서비스와 System32 의 그 파일 — 이 함께 있지 않다"* 이지
*"이 PC 에서 WinWyvern 을 치웠다"* 가 아니다.

## 서명 — 배포본은 배포 키

저장소의 이 폴더에는 서명이 없다. 배포본은 태그의 배포 잡이 배포 키로 서명하므로, 내려받은 배포 파일에 든 이 폴더는 배포
키의 서명이다(`plugin verify` 로 확인한다).
