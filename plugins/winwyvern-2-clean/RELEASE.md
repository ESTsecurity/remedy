# winwyvern-2-clean — 릴리스 기록

**버전 0.1.0** · 대상: WinWyvern — 정상 AI 도구(Ollama) 배포 페이지로 위장한 사이트로 퍼진 악성코드가, 보안 제품을 무력화하는
악성 드라이버 WinWyvern 을 올리려고 심는 취약 드라이버 NeacSafe64(CVE-2025-45737) · Windows · **치료**(서비스 · 되돌릴 수 있다)

> 같은 위협의 다른 하나는 `winwyvern-1-check`(탐지만)다 — 폴더 이름의 숫자가 안내 모드의 차례다(점검 먼저, 치료 나중).
> 판정은 둘이 같다.

## 0.1.0 — 2차 (2026-11-25)

긴급 대응의 2차다(`docs/긴급-대응.md` *2 · 3차* · 코어 그대로 — 엔진을 고치지 않았다). 1차(`winwyvern-1-check` 0.1.0)가 찾기만
하던 것 가운데 **서비스를 치료**한다. 드라이버 파일과 숨긴 DLL 은 남겨 알린다.

**1차 출처** — ASEC, *"BYOVD를 통한 국내 보안 제품 무력화 시도: 정상 AI 도구로 위장한 악성코드 유포 주의"*(한국어판
2026-11-23 <https://asec.ahnlab.com/ko/96707/> · 영문판 2026-11-20 <https://asec.ahnlab.com/en/96708/>). 지표는 이 보고에 있는
것만 쓴다(1차와 같다). 실검체는 없다 — 측정과 하네스는 표지 글자만 담은 자리 채우기와 시작하지 않는 서비스 등록으로 잰다.

### 무엇을 하나

- **판정** — `winwyvern-1-check` 와 같다(조건 · 라벨 · 판정식이 같은 줄이다). 레지스트리의 서비스 등록과 디스크의 드라이버
  파일, 독립적인 두 근거가 함께 서야 위협이다. 하네스가 두 룰의 판정을 꼴마다 견준다.
- **치료** — 서비스 `NeacSafe64` 하나다. 엔진이 정한 차례로 복구 설정 해제 → 정지 → 사용 안 함 → 삭제(4건)를 한다(설계-03 §2).
  정지 말고 셋은 서비스의 정의 키를 하위 트리째(`Instances` 포함) 백업한 뒤에 하므로 `restore` 로 되돌린다.
- **드라이버 파일은 치료하지 않는다** — `%SystemRoot%\System32\neacsafe64.sys` 는 판정의 근거로만 쓰고 흔적으로 남긴다. NetEase
  의 정상 서명된 안티치트 드라이버라(ASEC) 진짜 파일이면 엔진이 서명을 보고 격리를 미루고(2층), 서비스가 없으면 부팅 뒤
  올라오지 않는다. 치료 뒤 검사는 그 파일을 흔적 1건으로 적고 0 을 낸다.
- **재부팅 뒤 재검사** — `verify.after_reboot`. 치료가 HKLM 의 RunOnce(`remedy-verify`)에 같은 룰의 재판정을 걸고, PC 를 다시
  시작해 **관리자로 로그온하면** 돈다(`docs/operator.md` §6 — 표준 사용자로 로그온하면 돌지 않는다). 서비스가 다시 생겼으면
  재발(2)이다.
- **`kind: check` 가 아니다** — 감염의 흔적이다(1-check 와 같다). **빠른 검사에 남는다** — 보는 자리는 레지스트리의 서비스 목록과
  `%SystemRoot%\System32` 바로 아래의 그 이름 파일뿐이다(깨끗한 기계는 6 이 아니라 0). **고르는 화면** — `added: "2026-11-25"`
  라 *새로 추가된 항목* 에 선다(코어 1.25.0).

### 잰 것 — 2026-11-25 랩

Windows 10 22H2(빌드 19045) 랩 VM · 개발 꾸러미(엔진 1.25.4 — 지금 Latest 와 같은 엔진 코드 · 일회용 키 서명) · 이 룰의 초안(판정 ·
치료 줄이 0.1.0 과 같고 이름만 달랐다). 서비스는 `sc.exe create`(파일 시스템 드라이버 · 자동 시작)로 등록만 하고 시작하지
않았고, 미니필터 등록의 일반 꼴(의존 값 하나 · `Instances` 하위 키 둘 — 값은 자리 채우기)을 더했다.

| 무엇 | 결과 |
|---|---|
| 엔진이 내는 복구 설정 해제(`sc.exe failure NeacSafe64 reset= 0 actions= ""`) | 종료 0 — 드라이버 서비스에서도 거부되지 않았다 |
| 치료(`run --yes`) | 1 · 4건 모두 끝남(정지는 1062 — 시작한 적 없음 · 목표 상태) · 백업 3건(모두 동작 전에) · 재부팅 뒤 확인을 RunOnce 에 걸었다 |
| 치료 뒤 | 서비스 키 없음 · 서비스 관리자가 모름(`sc.exe query` 1060) · 드라이버 자리 파일 그대로 · 다시 검사 0(두 룰 · 흔적 1 · 위협 0) |
| 복원(`restore --yes`) | 0 · 3건 · 서비스 키 하위 트리의 **값 목록(키 · 이름 · 종류 · 데이터)이 치료 전과 같다**. `reg export` 바이트는 다르다 — 뿌리 키의 **값 차례만**(엔진이 값을 이름 차례로 담아 그 차례로 되쓴다 · 하위 키 둘은 줄까지 같고, 펴지 않은 값 · 여러 줄 값의 원시 바이트도 같다) |
| 복원 뒤 | 서비스 관리자가 그 서비스를 모른다(`sc.exe query` 1060) — **PC 를 다시 시작해야 다시 안다.** 검사는 레지스트리를 보므로 2(두 룰). 복원 화면은 다시 시작을 말하지 않는다 |
| 치료 → 재부팅 → 검사 | 0(두 룰 · 흔적 1 — 남긴 파일 · 위협 0) |
| 재부팅 뒤 확인 | 랩은 재부팅 뒤 로그온이 없어 OS 가 띄우지 않았다(RunOnce 는 로그온 때 돈다) — 걸린 명령줄을 그대로 띄워 0 · 기록 `outcome: clean` · 그 뒤 예약이 지워졌다 |

**재지 못한 것** — 도는(실린) 드라이버의 정지: 무해하게 재현할 수 없다. 서비스 관리자가 정지를 받지 않는 드라이버면 정지가
실패해 3(일부만)일 것이다 — 사용 안 함 · 삭제는 이어 돌고, 멈추지 못한 서비스의 삭제는 다시 시작할 때 끝난다(Microsoft
DeleteService 문서). 한 OS(Windows 10)에서만 쟀다 — 러너(Windows Server 2025)는 PR CI 의 하네스가 잰다. 복원 뒤 다시 시작하는
것은 재지 않았다.

### 이 룰이 보지 않는 것 — 종료 0 이 뜻하는 것

- **대체 데이터 스트림에 숨긴 악성 DLL**(ASEC — `C:\Windows\System32:msedge.exe`) — 엔진이 대체 데이터 스트림을 모으지 않고(파일
  기록의 `streams` 칸을 채우지 않는다) 지우는 동작도 계획하지 않는다. **치료 뒤 0 이어도 남는다** — 위협별 안내의 *꼭 할 일*
  (백신 정밀 검사 · 담당자).
- **드라이버 파일** — 보지만 치료하지 않는다(위 *무엇을 하나*). 치료 뒤 그 파일만 남아 흔적 1건이고 0 이다.
- **커널 쪽** — 커널 메모리에만 올린 WinWyvern 드라이버(따로 된 드라이버 파일이 없다 — 숨긴 DLL 안에 있다가 커널 메모리에
  올라간다 · ASEC) · 이미 올라와 도는 취약 드라이버(서비스를 지워도 다시 시작할 때까지 메모리에 남을 수 있다) · 무력화된 보안
  제품의 메모리. 지금 도는 드라이버 · 장치는 관측 대상이 아니다.
- **서비스를 다시 만드는 것** — 숨긴 DLL 이 서비스를 스스로 다시 만드는지는 공개되지 않았다(ASEC 그림 9 는 드로퍼가 서비스를
  만들거나 자동 시작으로 바꾼다고 보인다). 다시 만들면 재부팅 뒤 재검사가 재발(2)로 드러낸다.
- **정상 NetEase 설치** — 확인하지 못했다. 정상 설치의 서비스 모양(시작 유형 · 자리)은 ASEC 에 없고 실물로 재지 않았다. 정상
  설치가 이 판정의 꼴(자동 시작 · System32 바로 아래의 그 파일)과 같다면 그 안티치트 서비스를 지운다 — `restore` 로 되돌리고 PC
  를 다시 시작한다. 2차는 서비스를 지우므로 오탐의 대가가 찾기만 하는 1차보다 크다.
- **서비스나 파일 하나만 남은 기계 · 다른 시작 유형 · 다른 자리 · 다른 이름** — 1-check 와 같다. 흔적으로 적고 0 이며 치료하지
  않는다.
- **설치 파일과 C2 가 내려보낸 페이로드 · 드로퍼** — 1-check 와 같다(ASEC 이 지표를 내지 않았다 · 드로퍼는 MD5 만 공개됐다).

그래서 치료 뒤의 종료 0 은 *"이 룰이 보는 꼴 — 자동 시작으로 등록된 그 서비스와 System32 의 그 파일 — 이 함께 있지 않다"* 이지
*"이 PC 에서 WinWyvern 을 치웠다"* 가 아니다.

## 서명 — 배포본은 배포 키

저장소의 이 폴더에는 서명이 없다. 배포본은 태그의 배포 잡이 배포 키로 서명하므로, 내려받은 배포 파일에 든 이 폴더는 배포
키의 서명이다(`plugin verify` 로 확인한다).
