# log4j-check — 릴리스 기록

**버전 0.1.0** · 대상: Log4j(CVE-2021-44228 Log4Shell 계열) · log4j 1.x · logback — Windows · 리눅스의 디스크 전체 jar ·
war · ear · **점검**(바꾸지 않는다)

## 0.1.0 — 처음 (2026-11)

옛 사내 도구 `Log4jScanner`(Log4jScannerExample)를 대신한다. 코어 1.11.0 의 `archive_entry`(아카이브 안의 항목) ·
`file_names` · `%FIXED_DISKS%` 를 쓴다 — 이 룰을 위해 더한 코어 능력에는 log4j 의 이름이 없다(같은 꼴의 다음 점검도
룰만으로 쓴다).

## 무엇을 하나

**디스크 전체의 jar · war · ear** 를 본다 — Windows 는 고정 드라이브, 리눅스는 로컬 디스크 마운트(가상 · 네트워크 ·
`9p` 공유는 걷지 않는다). war · ear · Spring Boot jar 안은 4겹까지 연다.

| 갈래 | 판정 |
|---|---|
| **이름**에 취약한 판(`log4j-core-2.14.1.jar` · `log4j-1.2.17.jar` · `logback-core-1.2.8.jar`) — 디스크의 파일 · 아카이브 안의 jar | **취약(2)** |
| **공식 빌드의 SHA-256**(Maven Central) — 이름을 바꿔도 · 아카이브 안에 넣어도 | **취약(2)** |
| 압축을 푼 **`pom.properties` 의 `version`** — shade 한 jar · 다시 묶은 jar(배포판 패키지) · 이름이 다른 안쪽 jar | **취약(2)** |
| log4j-core 의 좌표는 있는데 판이 적혀 있지 않다 | **확인 필요(6)** |
| 아카이브를 끝까지 읽지 못했다(깨진 목록 · 잘린 파일 · 상한 · 암호 · 모르는 압축) | **확인 필요(6)** — 항목 줄에 그 파일과 *못 본 까닭* 이 있다 |

| 라이브러리 | 취약 판 | CVE |
|---|---|---|
| log4j-core 2.x | 2.0-alpha1 ~ 2.17.0, **2.3.2 · 2.12.4 는 뺀다**(Java 6 · 7 의 고친 판) | 2021-44228 · 45046 · 45105 · 44832 |
| log4j 1.x | **전부**(2015 년 지원 종료) | 2021-4104 · 2019-17571 · 2022-23302 · 23305 · 23307 · 2023-26464 |
| logback-core | 1.2.9 미만 · 1.3.0-alpha10 이하 | 2021-42550 |

2017-5645 · 2020-9488 은 위 범위 안이다. 2025 ~ 2026 의 중간 위험 공지(특정 appender · layout 을 쓸 때만)는 넣지
않는다 — 파일로는 그 설정을 쓰는지 가릴 수 없다.

## 결과 읽기

| 종료 코드 | 뜻 |
|---|---|
| 2 | **취약** — 항목 줄이 그 파일과 안쪽 경로를 적는다(`app.war!/WEB-INF/lib/a.jar!/…/pom.properties (내용 version=2.14.1)`). 그 앱의 log4j · logback 을 고친 판(2.17.1 · 2.12.4 · 2.3.2 · logback 1.2.9 이상)으로 올리고 다시 시작한다. log4j 1.x 는 2.x 로 옮긴다 |
| 0 | 취약한 곳을 찾지 못했다 |
| 6 | **확인 필요** — `주의:` 아래 줄이 무엇을 확인할지 말한다 |

## 이 룰이 보지 않는 것

- 실행 중인 자바 프로세스가 어느 log4j 를 실었는가 — 디스크의 파일만 본다.
- 좌표(`pom.properties`) 없이 클래스만 옮겨 담은 jar 의 판 — log4j-core 가 들어 있다는 것도 알리지 못한다.
- 2.x 를 쓰는 앱이 `JndiLookup.class` 를 뺐는가 — 판으로 판정한다(뺀 jar 도 45105 · 44832 가 남는다).
- 네트워크 드라이브 · 이동식 매체 · 리눅스의 NFS · CIFS · `9p` 공유 안.

## 근거 — 공개 자료

- Apache Logging Services 보안 공지 — https://logging.apache.org/security.html
- CVE 원본 레코드(CNA) — **CVE-2021-44832** 는 웹 페이지가 45105 의 범위(2.17.0 에서 고침)를 적었고 CNA(apache) 레코드는
  `2.0-beta7 through 2.17.0 (excluding 2.3.2 and 2.12.4)` · 2.17.1 · 2.12.4 · 2.3.2 에서 고침이다 → 레코드를 따른다.
  **CVE-2021-42550** 은 설명이 *"1.2.7 and prior"* 지만 레코드 범위는 `<1.2.9 · <1.3.0-alpha11` 이다 → 레코드를 따른다
- log4j 1.x — CVE-2021-4104 · 2019-17571 · 2022-23302(*"all versions of Log4j 1.x"*) · 2022-23305 · 2022-23307 ·
  2023-26464 의 CNA(apache) 레코드
- 공식 jar 해시 — Maven Central 의 log4j-core 11개 · log4j 1.2 셋 · logback-core 셋(게시된 SHA-1 로 대조한 뒤 SHA-256 을 적었다)

## 서명 — 저장소 사본은 개발용 키, 배포본은 배포 키

저장소의 `MANIFEST` · `MANIFEST.minisig` 는 저장소 사본을 확인하려고 **개발용 키로** 서명한 것이다. 배포본은
태그의 배포 잡이 배포 키로 다시 서명하고 그 공개키를 박아 빌드하므로, 내려받은 배포 파일에 든 이 폴더는 배포
키의 서명이다(`plugin verify` 로 확인한다). 개발용 키로 서명된 룰은 배포 앵커가 박힌 실행 파일에서 거부된다.
