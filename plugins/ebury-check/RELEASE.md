# ebury-check — 릴리스 기록

**버전 0.1.1** · 대상: Ebury — sshd 를 가로채 자격 증명과 SSH 키를 훔치는 리눅스 백도어
(`libkeyutils.so.1` 자리의 가짜 라이브러리) · 리눅스

> 출시 게이트(설계-03 §10) 기록이다. **찾기만 한다** — Ebury 를 치료하는 룰은 없다.

## 0.1.1 — 이 기록만 바뀌었다 (2026-11-07)

탐지 · 치료에 쓰이는 값 — 룰의 조건 · 수집 대상 · 판정 — 은 0.1.0 과 같다. 이 기록의 낱말
('꾸러미' · '판')과 서명 절(배포본은 배포 키로 서명된다 — 전에는 *개발용 키다. 이대로 배포하지
않는다* 라고만 적어 배포본을 받은 사람이 읽으면 틀린 말이었다)을 고쳤다. **운영자가 할 일의 차례도
고쳤다** — 전에는 가짜 파일을 지운 다음에 링크를 확인했고(링크가 아직 그 파일을 가리키면 지우는
순간 `sshd` · `sudo` 가 끊긴다), `dpkg -S` 에 경로를 주라고 읽혀 `/usr` 를 합친 기계에서 정상
파일을 지우게 할 수 있었다. 이 파일도 서명 대상이라 버전을 올렸다. 아래 게이트 결과는 0.1.0 에서
잰 그대로 이 버전에 선다.

## 무엇을 하나

- **판정** — 라이브러리 자리(`/usr/lib64` · `/usr/lib/x86_64-linux-gnu` · `/lib/x86_64-linux-gnu`)에서
  이름이 `libkeyutils` 로 시작하는 **실제 파일**(링크 제외)에 ESET 의 공개 규칙 둘 중 하나가 맞는다:
  `libkeyutils_with_ctor`(SONAME 이 `libkeyutils.so.1` 인데 생성자가 하나 더 있다) ·
  `Ebury_v1_7_crypto`(v1.7 · v1.8 의 문자열 복호 루틴).
- **바꾸지 않는다** — 화면은 *"위협 발견, 치료하지 않았습니다."* 다.
- **본문은 규칙 없이 담는다** — `collect_extra` 의 `glob` 형(코어 1.0.2 부터 · `min_core`). 고르는 규칙을
  두면 그 규칙이 정상 libkeyutils 에도 맞아 모든 정상 서버에 *흔적* 이 뜬다(청정 코퍼스 시험이 막았다).
- **왜 치료하지 않나** — 그 파일을 옮기면 그것을 싣는 `sshd` · `sudo` 가 뜨지 못한다. 원격 접속이
  끊긴 서버는 콘솔로만 되살릴 수 있다. 그래서 복구는 운영자가 콘솔에서 한다(아래).
- **훅에 속지 않는다** — 배포 엔진은 정적 링크라 동적 로더를 거치지 않는다. 디렉터리 읽기를 가로채
  이름을 숨기는 훅(`LD_PRELOAD`)을 건 채로도 감염을 2 로 낸다(하네스 C5 · 같은 훅에 동적 링크인
  `ls` 는 속는다).

## 위협이 나오면 — 운영자가 할 일

1. **콘솔(가상 콘솔 · IPMI 등)에서 한다.** SSH 로 들어가면 그 접속의 자격 증명이 다시 넘어간다.
2. **정상 버전을 다시 설치한다.** RHEL 계열은 `yum reinstall keyutils-libs`(또는 `dnf`), Debian ·
   Ubuntu 는 `apt-get install --reinstall libkeyutils1`.
3. **다시 점검한 뒤, 패키지에 없는 파일만 지운다.** Ebury 점검을 다시 돌려 *위협 없음* 이면 다시
   설치가 가짜 파일을 덮은 것이다(제자리에서 바꿔치기한 경우) — 지울 것이 없으니 4로 간다. 아직
   나오면 `ls -l` 로 `libkeyutils.so.1` 이 결과에 나온 파일을 더는 가리키지 않는지 본다. 결과에 나온
   파일이 어느 패키지의 것도 아니면(`rpm -qf <경로>` · `dpkg -S <파일 이름>` 이 패키지를 대지
   못하면) 지우고 `ldconfig` 를 돌린 뒤 링크를 한 번 더 본다(`rpm -V keyutils-libs` ·
   `dpkg -V libkeyutils1`). **`dpkg -S` 에는 파일 이름만 준다** — `/usr` 를 합친 기계에서는 결과에
   같은 파일이 두 경로로 나오는데(아래 *결과 읽기*), dpkg 의 기록은 한 경로뿐이라 다른 경로로
   물으면 정상 파일도 *no path found* 다(Debian 12 · Ubuntu 22.04 실측 2026-11-07: `/usr/lib/…` 로
   물으면 종료 1, `/lib/…` 나 파일 이름만 주면 `libkeyutils1`). 다시 설치가 되지 않았거나 링크가
   여전히 그 파일을 가리키면 **지우지 않는다** — 지우면 `sshd` · `sudo` 가 뜨지 못한다. 순서가
   이렇다: 지운 뒤에 확인하면, 번호가 높은 가짜 파일로 `ldconfig` 가 링크를 다시 건 경우를 놓친다
   (2026-11-07 검토).
4. **재부팅한다.** 이미 떠 있는 `sshd` 등에는 가짜 라이브러리가 실려 있다.
5. **자격 증명을 모두 바꾼다.** 이 서버로 들어온 비밀번호 · SSH 키, 그리고 이 서버에서 다른 서버로
   나간 키 — Ebury 는 둘 다 훔친다.
6. **서버 전체를 침해된 것으로 본다.** 심으려면 root 권한이 필요했다. 다시 설치를 검토한다.

Control Web Panel 을 쓰는 서버라면 같은 배포 파일(`remedy-linux-x64`)의 *CWPdoor 점검* 으로도 본다 —
고르는 화면의 1번 *모두 검사만* 이 그 파일의 룰을 한 번에 본다.

## 결과 읽기

| 종료 코드 | 뜻 |
|---|---|
| 2 | **위협 발견** — 위 차례대로 |
| 0 | 위협 없음 |
| 6 | 다 보지 못했다 — 위 세 자리가 하나도 없는 기계(예: Alpine)도 6 이다 |

`/usr` 를 합친 기계(Debian 12 · Ubuntu 22.04 이후 등)에서는 `/lib` 가 `/usr/lib` 를 가리켜 같은 파일이
`/lib/x86_64-linux-gnu/…` 와 `/usr/lib/x86_64-linux-gnu/…` **두 경로로** 보인다 — 파일은 하나다. `/usr` 를
합치지 않은 옛 Debian 의 자리까지 보려고 둔 것이다.

## 지표 — 공개된 것만

`rules/ebury.yar` 는 ESET 이 공개한 규칙 파일(github.com/eset/malware-ioc · `windigo/ebury.yar`)을
**고치지 않고** 담는다 — 머리의 BSD 2-Clause 고지는 그 저장소의 것이다.

**쓰지 않는 것** — 사건 표본에서만 나온 문자열 · 해시: 공개 보도에 없다. 해시만으로 잡기: 표본마다
빌드가 달라(공개 표본 11개 · 크기 15,688 ~ 64,600 B) 한 빌드만 잡는다. 접속 주소: remedy 는 연결을
관측하지 않는다.

## 서명 — 저장소 사본은 개발용 키, 배포본은 배포 키

저장소의 `MANIFEST` · `MANIFEST.minisig` 는 저장소 사본을 확인하려고 **개발용 키로** 서명한 것이다.
**배포본은 이 서명을 쓰지 않는다** — 태그의 배포 잡(`.github/workflows/release.yml`)이 배포 키로 다시
서명하고 그 공개키를 박아 빌드하므로, 내려받은 배포 파일에 든 이 폴더는 배포 키의 서명이다(`plugin
verify` 로 확인한다). 개발용 키로 서명된 룰은 배포 앵커가 박힌 실행 파일에서 거부된다.
