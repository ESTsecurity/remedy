# php2shell-check-linux — 릴리스 기록

**버전 0.6.0** · 대상: PHP2Shell(CVE-2026-109618 · CVE-2026-109619) — 리눅스의 PHP 런타임 · **점검**(바꾸지 않는다)

## 0.6.0 — 시작 스크립트 · Apache 설정 (2026-11)

멈춰 있어도 남는 자리 둘을 더 본다(목표 결정 28). 둘 다 선언한 자리 밖의 PHP 면 그 경로를 적어 **확인 필요(6)** 로
내고, 그 PHP 의 파일은 열지 않는다.

- **SysV · OpenRC · Upstart 의 시작 스크립트** — 코어 1.10.0 이 `/etc/init.d/*` · `/etc/init/*.conf` 를 **실행하지
  않고** 읽어, 글자 그대로 풀리는 실행 파일 자리를 서비스로 낸다: 실행 파일 변수(`DAEMON` · `EXEC` · OpenRC 의
  `command` · 끝이 `_BIN` 인 것 — PHP 가 내는 php-fpm 스크립트의 `php_fpm_BIN`), `exec <경로>`, `start-stop-daemon
  --exec <경로>`, `daemon <경로>`. 덮어쓰는 설정(`/etc/default/<이름>` · `/etc/sysconfig/<이름>` 은 스크립트가 그
  경로를 적었을 때, OpenRC 는 `/etc/conf.d/<이름>`)도 읽는다. 0.5.0 의 서비스 규칙(`service_php`)이 그대로 본다 —
  항목 줄은 `<스크립트 이름>  (실행 파일 <경로>)` 이다.
- **Apache 설정의 `LoadModule` 줄** — 이름에 `php` 가 든 모듈(`php_module` · `php7_module` · `php_zts_module` …)을
  싣는 줄. 읽는 자리는 Debian 계열 `/etc/apache2`(모듈 줄은 `mods-available/*.load` — 켠 것을 가리키는
  `mods-enabled` 는 링크라 따라가지 않으므로 켜지 않은 모듈의 줄도 읽힌다) · RPM 계열 `/etc/httpd` · 직접 빌드
  `/usr/local/apache2/conf` · XAMPP `/opt/lampp/etc`. 배포판 패키지가 모듈을 두는 자리(`/usr/lib(64)/apache2*` ·
  `httpd*` — SUSE 의 `/usr/lib64/apache2/mod_php8.so` 포함)와 RPM 계열의 `ServerRoot` 기준 `modules/` 는 선언한
  자리로 친다 — 그 PHP 는 패키지 규칙이 판정한다. 직접 빌드 · XAMPP 의 `modules/` 는 그 Apache 아래라 확인 필요다.
  항목 줄은 `<파일>:<줄 번호>  (줄 <그 줄>)` 이다.

코어 1.10.0 이 필요하다(시작 스크립트의 서비스). 그 밖의 판정은 0.5.0 과 같다.

## 0.5.0 — 서비스로 등록된 PHP (2026-11)

systemd 유닛이 선언한 자리 밖의 PHP 를 띄우면(`ExecStart` 의 첫 낱말) 그 유닛과 실행 파일을 적어 **확인 필요(6)** 로
낸다 — 돌고 있지 않아도 유닛 파일이 남는다(목표 결정 28 · 0.2.0 의 실행 중 규칙과 같은 자리 정규식). 그 PHP 의
파일은 열지 않는다. 항목 줄은 `<유닛>  (실행 파일 <경로>)` 이다. 셸로 감싼 `ExecStart=/bin/sh -c …` 는 그 셸이
첫 낱말이라 보지 않는다. SysV · Upstart · OpenRC 의 시작 스크립트는 아직 읽지 않는다.

## 0.4.0 — 다시 시작하지 않은 PHP · 직접 빌드의 자리 (2026-11)

- **고친 뒤 다시 시작하지 않은 PHP 를 알린다** — 패키지를 올리면 옛 파일이 지워지고 새 파일이 같은 이름에
  들어선다. 커널은 지워진 파일을 실은 프로세스의 실행 파일 · 실린 모듈 경로에 ` (deleted)` 를 붙이므로, 그 꼬리가
  붙은 PHP(`php` · `php-cgi` · `php-fpm` · `lsphp` 실행 파일, 아파치에 실린 `libphp*.so`)는 고치기 전 코드를 실은
  채 돈다. 디스크의 파일로 서는 판정이 그 프로세스를 말하지 않으므로 그 경로를 적어 **확인 필요(6)** 로 낸다(사내
  runtime-scanner 의 *삭제된 실행 파일이 계속 실행 중입니다* 와 같은 규칙). 옛 파일이 지워지지 않고 남은 채 떠
  있는 경우는 여전히 가리지 못한다. Windows 는 실행 중인 파일을 지울 수 없어 이 신호가 없다.
- **직접 빌드의 흔한 접두사 `/usr/local/php` · `/opt/php` 를 선언한 자리로 읽는다**(runtime-scanner 의 기본 자리와
  같다) — 그 아래(판마다 하위 폴더를 두는 꼴도)의 `bin` · `sbin` 실행 파일과 `lib` 의 `libphp*.so` 를 공식 빌드
  해시로 가린다. 공식 빌드를 옮겨 둔 것이면 그 판으로, 아니면 확인 필요다. 0.3.0 은 그 자리의 PHP 가 돌지 않으면
  보지 못해 *취약한 곳을 찾지 못했습니다* 였다.

## 0.3.0 — 패키지가 깐 PHP 실행 파일을 패키지 기록과 대조한다 (2026-11)

패키지 버전으로 서는 판정은 그 패키지가 깐 PHP 실행 파일이 **패키지 기록과 같을 때만** 세운다 — 코어 1.7.0 의
`file.package` · `file.package_match`(dpkg `.md5sums` 의 MD5 · RPM 헤더의 다이제스트)를 쓴다. 다르거나 · 기록이
없거나 · 끝까지 읽지 못했으면 그 패키지 버전으로 판정하지 않고 그 경로를 적어 **확인 필요(6)** 로 낸다. 공식
빌드 해시 판정(`official_vuln`)은 패키지 밖의 파일이라 그대로다. 코어 1.7.0 이 필요하다.

- 대조하는 것은 **PHP 실행 파일 자리뿐**이다 — Debian 계열 `php8.2` · `php-cgi8.2` · `php-fpm8.2` · Apache 모듈
  `libphp8.2.so`, RPM 계열 `php` · `php-cgi` · `php-fpm` · httpd 모듈 `libphp*.so`. 같은 폴더(`/usr/bin` 등)의
  다른 패키지 파일이 기록과 달라도 판정에 들지 않는다(해시 상한을 넘는 `dockerd` 같은 파일은 늘 끝까지 못 읽는다).
- PHP 실행 파일 하나라도 기록과 다르면 그 기계의 패키지 판정을 모두 세우지 않는다 — 판정 묶음이 하나다.
- **Debian · Ubuntu 의 메타 패키지를 세지 않는다** — `apt install php-cli` 가 까는 `php-cli` · `php-fpm` ·
  `php-cgi` · `libapache2-mod-php`(원본 `php-defaults`, 버전 `2:8.2+93` 꼴)는 실행 파일이 없고 버전 붙은 패키지
  (`php8.2-cli` 등)를 끌어올 뿐이다. 0.2.0 은 이것을 *기준 없는 PHP 패키지* 로 세어, 고친 버전을 그렇게 깐 서버도
  확인 필요(6)였다(v1.6.0 rc 실측: Debian 12 `8.2.35-1~deb12u1` · Ubuntu 24.04 `8.3.6-0ubuntu0.24.04.13`).
- 화면 문구: 사유가 경로를 *위 경로* 로 가리킨다(항목 줄이 주의 줄보다 위에 선다 — 0.2.0 은 *아래* 라고 적었다) ·
  확인할 고친 버전을 계열마다 적는다.

## 0.2.0 — 선언한 자리 밖에서 실행 중인 PHP 를 알린다 (2026-11)

실행 파일이 `php` · `php-cgi` · `php-fpm` · `lsphp`(뒤에 버전 숫자가 붙어도)인 프로세스가 선언한 실행 파일 자리
(`/usr/bin` · `/usr/sbin` · `/usr/local/bin` · `/usr/local/sbin` 바로 아래) 밖에서 돌면 그 경로를 적고 **확인
필요(6)** 로 낸다. 그 PHP 는 판정하지 않는다 — 룰은 선언한 자리만 읽는다(목표 결정 22). 패키지 · 공식 빌드 해시
판정은 0.1.0 과 같고, 코어는 1.3.0 그대로다(`process` 는 그 전부터 있다).

- 바뀐 뒤 다시 시작하지 않은 프로세스의 실행 파일에는 ` (deleted)` 가 붙어 이 이름 꼴에 맞지 않는다 — 재시작
  여부는 이 룰이 보지 않는다.
- **컨테이너 안에서 돌리면** 다른 사용자로 도는 프로세스(php-fpm 의 www-data 작업자 등)를 들여다보지 못해
  관측 불완전(6)이다 — 실행 파일 경로와 실린 모듈이 같은 ptrace 검사로 함께 막힌다. 사유 줄이
  `docker exec --privileged` 로 들어가 다시 돌리라고 안내한다(코어 1.6.0). 호스트에서 root 로 돌면 막히지 않는다.
- 판정 묶음이 하나라 **하나라도** 취약(2)이 나온 회차에는 확인 필요 항목(자리 밖의 PHP · 기준 없는 패키지 ·
  기록과 다른 실행 파일)이 화면에 나오지 않는다 — 찾은 것이 모르는 것보다 앞선다. 고친 뒤 다시 검사하면 나온다.

## 0.1.0 — 처음 (2026-11)

배포판 패키지 10줄 · RPM 공급사 7줄(RHEL 4 · Oracle Linux 2 · SLES 1) · 공식 빌드 해시 33 + 다시 지은 이미지 5 로

| 실행 중인 PHP 의 실행 파일 · 실린 `libphp*.so` 가 지워진 옛 파일이다(` (deleted)` · 0.4.0) | **확인 필요(6)** — 고친 뒤 다시 시작하지 않았다. 그 서비스를 다시 시작한 뒤 다시 검사한다 |

## 이 룰이 보지 않는 것

- **옛 파일이 남은 채 떠 있는 PHP 가 고친 버전을 실었는가** — 옛 파일이 지워졌으면 0.4.0 이 확인 필요로 알리지만,
  지워지지 않았으면(같은 파일을 덮어쓰지 않고 다른 자리에 깐 경우 등) 다시 시작했는지 가리지 못한다.
- 선언한 자리 밖에 놓였을 뿐 실행 중도 아니고 서비스 · Apache 설정에도 적히지 않은 PHP(예: `/opt` 아래 직접 빌드 ·
  RHEL 의 Software Collections) · 위에 적은 자리 밖의 Apache 설정(`Include` 로 다른 곳에서 읽는 설정) · 셸 함수 ·
  명령 치환으로 정한 시작 스크립트의 경로 · 컨테이너 안의 PHP(그 컨테이너 안에서 돌리거나 `remedy-net container`).
- 패키지가 깐 PHP 가 싣는 공유 라이브러리 · 확장이 바뀌었는가 — 패키지 기록과 대조하는 것은 실행 파일 자리뿐이다.
  apk(Alpine)는 대조하지 않는다(Alpine 의 PHP 패키지는 늘 확인 필요다).

## 근거 — 공개 공지와 공식 빌드

- 상류 고친 버전 8.2.35 · 8.3.36 · 8.4.27 · 8.5.12 — php.net 2026-10-21 보안 공지(8.1 이하는 고친 버전이 없다)
- Ubuntu USN-8948-1(22.04 · 24.04 · 26.04 · 26.10) · USN-8948-2(ESM) · Debian security-tracker CVE-2026-109618
- RHEL RHSA-2026:87080 · 87073 · 87151 · 88693(7.9 — 109619 만) · Oracle Linux ELSA-2026-87080 · 87151 ·
  SUSE SUSE-SU-2026:4844-1 — 줄마다 공급사 이름 · 계열 정규식 · 고친 버전은 공지 그대로다
- 공식 빌드 해시 — Docker 공식 이미지 `php:8.3.35-*` · `php:8.3.36-*`(amd64 · 386 · cli · fpm · apache)와
  `php:5.6.40-cli` · `php:7.4.33-cli`(amd64)의 실행 파일 · 코어 라이브러리. 값마다 룰에 버전 · 플랫폼 · 자리를 적었다
- **공식 이미지의 현재 태그는 다시 지어진다**(기반 이미지가 바뀔 때마다) — 실행 파일 해시가 그때마다 바뀐다.
  2026-11-09 에 받은 `php:8.3.36-cli` · `-fpm`(2026-11-05 에 다시 지은 이미지)이 그 전 목록과 달라 *확인 필요* 로
  나왔고, 그 실행 파일 다섯을 재서 더했다. 그 뒤에 다시 지은 이미지는 목록이 따라올 때까지 *확인 필요* 다

## 서명 — 저장소 사본은 개발용 키, 배포본은 배포 키

저장소의 `MANIFEST` · `MANIFEST.minisig` 는 저장소 사본을 확인하려고 **개발용 키로** 서명한 것이다. 배포본은
태그의 배포 잡이 배포 키로 다시 서명하고 그 공개키를 박아 빌드하므로, 내려받은 배포 파일에 든 이 폴더는 배포
키의 서명이다(`plugin verify` 로 확인한다). 개발용 키로 서명된 룰은 배포 앵커가 박힌 실행 파일에서 거부된다.
