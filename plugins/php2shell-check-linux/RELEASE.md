# php2shell-check-linux — 릴리스 기록

**버전 0.2.0** · 대상: PHP2Shell(CVE-2026-109618 · CVE-2026-109619) — 리눅스의 PHP 런타임 · **점검**(바꾸지 않는다)

## 0.2.0 — 선언한 자리 밖에서 실행 중인 PHP 를 알린다 (2026-11)

실행 파일이 `php` · `php-cgi` · `php-fpm` · `lsphp`(뒤에 판 숫자가 붙어도)인 프로세스가 선언한 실행 파일 자리
(`/usr/bin` · `/usr/sbin` · `/usr/local/bin` · `/usr/local/sbin` 바로 아래) 밖에서 돌면 그 경로를 적고 **확인
필요(6)** 로 낸다. 그 PHP 는 판정하지 않는다 — 룰은 선언한 자리만 읽는다(목표 결정 22). 패키지 · 공식 빌드 해시
판정은 0.1.0 과 같고, 코어는 1.3.0 그대로다(`process` 는 그 전부터 있다).

- 바뀐 뒤 다시 시작하지 않은 프로세스의 실행 파일에는 ` (deleted)` 가 붙어 이 이름 꼴에 맞지 않는다 — 재시작
  여부는 이 룰이 보지 않는다.
- **컨테이너 안에서 돌리면** 다른 사용자로 도는 프로세스(php-fpm 의 www-data 작업자 등)를 들여다보지 못해
  관측 불완전(6)이다 — 실행 파일 경로와 실린 모듈이 같은 ptrace 검사로 함께 막힌다. 사유 줄이
  `docker exec --privileged` 로 들어가 다시 돌리라고 안내한다(코어 1.6.0). 호스트에서 root 로 돌면 막히지 않는다.
- 선언한 자리의 패키지가 **모두** 취약(2)으로 판정된 회차에는 자리 밖의 PHP 가 화면에 나오지 않는다 — 고친 뒤
  다시 검사하면 확인 필요로 나온다.

## 0.1.0 — 처음 (2026-11)

배포판 패키지 10줄 · RPM 공급사 7줄(RHEL 4 · Oracle Linux 2 · SLES 1) · 공식 빌드 해시 33 + 다시 지은 이미지 5 로
낸다. 코어 1.3.0 의 `verdict.unconfirmed` · RPM 수집 · `rpm_version_lt` · `vendor` 를 쓴다.

## 무엇을 하나

| 갈래 | 판정 |
|---|---|
| **배포판 패키지**(Ubuntu 22.04 · 24.04 · 26.04 · 26.10 · ESM 14.04~20.04 · Debian 12 · 13) | 줄마다 **같은 계열의 판인가**(정규식)를 먼저 보고 공지의 수정 판과 견준다(`pkg_version_lt`) — 낮으면 **취약(2)** |
| 줄 밖의 PHP 패키지(다른 저장소 · 기준에 없는 배포판 · Alpine) | **확인 필요(6)** — 판이 높아 보여도 그 공급사가 고쳤는지 알 근거가 없다 |
| **패키지 밖의 PHP**(공식 Docker 이미지 · 직접 빌드 — `/usr/local` · Apache 이미지의 `libphp.so`) | 공식 빌드 해시와 맞으면 그 판으로 판정(8.3.35 · 5.6.40 · 7.4.33 → 2 · 8.3.36 → 0), 맞지 않으면 **확인 필요(6)** |
| **RPM 패키지**(RHEL 8.10 php:7.4 · php:8.2 · 9.8 · 7.9 · Oracle Linux 8.10 php:7.4 · 9.8 · SLES 15 SP7 php8) | 줄마다 **공급사(`vendor`) → 계열(정규식) → 판(`rpm_version_lt`)** — 낮으면 **취약(2)**. RHEL 7.9 는 공지가 CVE-2026-109619 만 고쳐 그 판 이상이 **확인 필요(6)** |
| RPM 줄 밖(Rocky · Alma · CentOS · openSUSE · Remi · 이전 마이너의 빌드 · 다른 모듈 스트림 · SCL) | **확인 필요(6)** — Rocky · Alma 는 RHEL 의 판 문자열을 그대로 적지만 공지는 그 공급사의 빌드에만 말한다 |
| RPM 의 자리(`/usr/bin/php` · `/usr/sbin/php-fpm` · httpd 의 `libphp*.so`)의 정규 파일인데 RPM 의 PHP 패키지가 없다 | **확인 필요(6)** — 패키지가 깔지 않은 PHP 다. 패키지가 있으면 그 파일은 패키지의 것으로 보고 위 줄이 판정한다 |

런타임 패키지(CLI · CGI · FPM · Apache 모듈)만 본다 — 같은 원본의 확장 패키지는 판이 같아 화면만 길어진다.

## 결과 읽기

| 종료 코드 | 뜻 |
|---|---|
| 2 | **취약** — 화면의 항목을 수정 판 이상으로 올리고 PHP · 웹 서버를 다시 시작한다 |
| 0 | 취약한 곳을 찾지 못했다 — 고친 판이거나, 선언한 자리에 PHP 가 없다 |
| 6 | **확인 필요** — `주의:` 아래 줄이 무엇을 확인할지 말한다(공급사 패치 여부 · 판과 받은 곳). 선언한 자리 밖에서 실행 중인 PHP 면 항목 줄에 그 경로가 있다 |

## 이 룰이 보지 않는 것

- **실행 중인 PHP 가 고친 판을 실었는가** — 패키지를 고쳐도 다시 시작하지 않은 php-fpm · Apache 는 옛 판이다.
- 선언한 자리 밖에 놓였을 뿐 실행 중이 아닌 PHP(예: `/opt` 아래 직접 빌드 · RHEL 의 Software Collections) ·
  Apache 가 싣는 선언 밖의 `libphp*.so` · 컨테이너 안의 PHP(그 컨테이너 안에서 돌리거나 `remedy-net container`).
- 패키지가 깐 실행 파일을 다른 것으로 바꿨는가 — 패키지 DB 의 파일 해시와 대조하지 않는다.

## 근거 — 공개 공지와 공식 빌드

- 상류 수정 판 8.2.35 · 8.3.36 · 8.4.27 · 8.5.12 — php.net 2026-10-21 보안 공지(8.1 이하는 고친 판이 없다)
- Ubuntu USN-8948-1(22.04 · 24.04 · 26.04 · 26.10) · USN-8948-2(ESM) · Debian security-tracker CVE-2026-109618
- RHEL RHSA-2026:87080 · 87073 · 87151 · 88693(7.9 — 109619 만) · Oracle Linux ELSA-2026-87080 · 87151 ·
  SUSE SUSE-SU-2026:4844-1 — 줄마다 공급사 이름 · 계열 정규식 · 수정 판은 공지 그대로다
- 공식 빌드 해시 — Docker 공식 이미지 `php:8.3.35-*` · `php:8.3.36-*`(amd64 · 386 · cli · fpm · apache)와
  `php:5.6.40-cli` · `php:7.4.33-cli`(amd64)의 실행 파일 · 코어 라이브러리. 값마다 룰에 판 · 플랫폼 · 자리를 적었다
- **공식 이미지의 현재 태그는 다시 지어진다**(기반 이미지가 바뀔 때마다) — 실행 파일 해시가 그때마다 바뀐다.
  2026-11-09 에 받은 `php:8.3.36-cli` · `-fpm`(2026-11-05 에 다시 지은 이미지)이 그 전 목록과 달라 *확인 필요* 로
  나왔고, 그 실행 파일 다섯을 재서 더했다. 그 뒤에 다시 지은 이미지는 목록이 따라올 때까지 *확인 필요* 다
