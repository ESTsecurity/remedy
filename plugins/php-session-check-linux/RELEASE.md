# php-session-check-linux — 릴리스 기록

**버전 0.3.0** · 대상: PHP 세션 업로드 진행 설정(CVE-2026-115560 · php.net 2026-10-23 공지) — 리눅스 · **점검**(바꾸지 않는다)

## 0.3.0 — 직접 빌드의 자리 (2026-11)

직접 빌드의 흔한 접두사 `/usr/local/php` · `/opt/php` 를 선언한 자리로 읽는다 — 그 아래의 PHP 실행 파일이 있으면
PHP 가 있는 기계로 보고(확인 필요), 그 아래의 설정(`lib/php.ini` · `etc/php.ini` · `etc/conf.d` 등 `.ini` · `.conf`)을
읽는다. `php2shell-check-linux` 0.4.0 과 같은 자리다. 0.2.1 은 그 자리의 PHP 가 돌지 않으면 PHP 가 없는 기계로 보아
*취약한 곳을 찾지 못했습니다* 였다.

## 0.2.1 — 화면 문구 (2026-11)

판정은 0.2.0 과 같다. 사유가 경로를 *위 경로* 로 가리키고(항목 줄이 주의 줄보다 위에 선다), *끈 설정이
있습니다* 와 *설정을 찾지 못했습니다* 에 다음 할 일(다시 시작 · 0 으로 두기)을 붙였다.

## 0.2.0 — 선언한 자리 밖에서 실행 중인 PHP 를 알린다 (2026-11)

`php2shell-check-linux` 0.2.0 과 같은 규칙으로 선언한 실행 파일 자리 밖에서 도는 PHP 를 찾아 그 경로를 적고
**확인 필요(6)** 로 낸다. 그 PHP 의 설정 파일은 열지 않는다. 컨테이너 안에서 다른 사용자로 도는 프로세스를
들여다보지 못하면 관측 불완전(6)인 것도 같다. 코어는 1.3.0 그대로다.

## 0.1.0 — 처음 (2026-11)

PHP 가 있으면 늘 확인 필요로 내고, 까닭을 설정 상태로 가른다. 코어 1.3.0 의 `verdict.unconfirmed` 를 쓴다.

## 무엇을 하나

- **판정(2)을 세우지 않는다.** 공지는 고친 버전을 내지 않았고(다음 정기 버전), 위험은 세 조건이 겹칠 때뿐이다 —
  `session.upload_progress.enabled` 가 켜져 있고, 서버의 `session.serialize_handler` 가 `php_binary` ·
  `php_serialize` 이며, 앱이 `session_start()` 전에 `ini_set()` 으로 그것을 `php` 로 바꾼다. 셋째는 앱 코드다.
- PHP(배포판 런타임 패키지 또는 PHP 실행 파일)가 있으면 **확인 필요(6)** — 설정이 켜짐 · 꺼짐 · 없음(기본값은
  켜짐)에 따라 할 일을 갈라 적는다. PHP 가 없으면 설정 파일이 남아 있어도 **해당 없음(0)** 이다.
- 설정을 읽는 자리: Debian 계열 `/etc/php/<버전>/` · RPM 계열 `/etc/php.ini`(`/etc` 바로 아래 파일 하나라 글롭
  뿌리 `/etc/php*.ini` 로) 와 `/etc/php.d` · SUSE `/etc/php8` · Alpine `/etc/phpNN` · 공식 이미지 `/usr/local/etc/php`.

## 결과 읽기

| 종료 코드 | 뜻 |
|---|---|
| 0 | PHP 가 없다 — 선언한 자리에도, 실행 중인 프로세스에도 |
| 6 | **확인 필요** — 앱이 실행 중에 handler 를 바꾸면 `session.upload_progress.enabled=0` 으로 두고 PHP 를 다시 시작한다(공지). 선언한 자리 밖에서 실행 중인 PHP 면 항목 줄의 그 경로의 설정을 확인한다 |

## 이 룰이 보지 않는 것

- 실행 중인 PHP 에 반영된 값(다시 시작했는가) · FPM 풀 · Apache 설정의 `php_admin_value` · 앱의 `ini_set()`.
- 선언한 자리 밖의 설정 파일 · 실행 중이 아닌, 선언한 자리 밖의 PHP.

## 근거

- php.net 2026-10-23 *Informational advisory: Session upload progress* — 조건 · 권고(`session.upload_progress.enabled=0`)

## 서명 — 저장소 사본은 개발용 키, 배포본은 배포 키

저장소의 `MANIFEST` · `MANIFEST.minisig` 는 저장소 사본을 확인하려고 **개발용 키로** 서명한 것이다. 배포본은
태그의 배포 잡이 배포 키로 다시 서명하고 그 공개키를 박아 빌드하므로, 내려받은 배포 파일에 든 이 폴더는 배포
키의 서명이다(`plugin verify` 로 확인한다). 개발용 키로 서명된 룰은 배포 앵커가 박힌 실행 파일에서 거부된다.
