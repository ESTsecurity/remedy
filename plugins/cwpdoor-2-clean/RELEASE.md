# cwpdoor-2-clean — 릴리스 기록

**버전 0.1.1** · 대상: CWPdoor — 백도어를 심은 `cwpsrv`(Control Web Panel 의 패널 웹 서버) · 리눅스

> 출시 게이트(설계-03 §10) 기록이다. 같은 배포 파일의 다른 하나는 `cwpdoor-1-check`(탐지만)다 —
> 폴더 이름의 숫자가 안내 모드의 차례다(점검 먼저, 치료 나중).

## 0.1.1 — 이 기록만 바뀌었다 (2026-11-07)

탐지 · 치료에 쓰이는 값 — 룰의 조건 · 수집 대상 · 판정 · 치료 Op — 은 0.1.0 과 같다. 이 기록의 낱말
('꾸러미' · '판')과 서명 절(배포본은 배포 키로 서명된다 — 전에는 *개발용 키다. 이대로 배포하지
않는다* 라고만 적어 배포본을 받은 사람이 읽으면 틀린 말이었다)을 고쳤다. 이 파일도 서명 대상이라
버전을 올렸다. 아래 게이트 결과는 0.1.0 에서 잰 그대로 이 버전에 선다.

## 무엇을 하나

- **판정** — `/usr/local/cwpsrv/bin/cwpsrv` 에 두 근거가 **둘 다** 있다: 활성화 헤더 셋
  (`X-Ngx-Integrity-Data` · `-Time` · `-Sig`, 평문)과 명령 서명을 확인하는 공격자 RSA 공개키
  (바이트마다 0x55 로 XOR). 둘의 논리곱이라 문자열 한 무리의 오탐이 곧바로 격리로 이어지지 않는다.
- **치료** — 그 바이너리를 **격리**한다(지우지 않는다 — `restore` 로 돌아온다). 그 바이너리를
  띄우는 `cwpsrv.service` 를 **중지 → 비활성화 → 삭제**한다(삭제도 되돌릴 수 있다). 공급사 유닛이
  `Restart=always` · `RestartSec=5` 라 중지가 먼저여야 격리 전에 백도어가 다시 뜨지 않는다.
  리눅스에 없는 '복구 동작 제거' 는 계획 JSON 에 *미룸* 한 줄로 남는다 — 빠진 치료가 아니어서 1.1.1
  부터 화면의 *"이 계획은 치료의 전부가 아닙니다"* 에는 세지 않는다.
- **남기는 것** — `cwpsrv.prev-<날짜>-<시각>`. 공격 스크립트가 바꿔치기 전에 남긴 **원래 바이너리의
  사본**이다. 흔적으로 보이고 치료하지 않는다.

## 치료 뒤 운영자가 할 일

1. **패널을 되살린다** — 공급사 버전을 다시 설치한다(`yum reinstall cwpsrv` — 유닛도 함께
   돌아온다). 그다음 `systemctl enable --now cwpsrv`. `cwpsrv.prev-…` 는 공격 스크립트가 남긴
   사본이라 복구원으로 권하지 않는다 — 침입자가 손댈 수 있었던 자리이고, 그 길로는 치료가 지운
   유닛도 돌아오지 않는다. **다시 설치한 뒤에는 치료를 되돌리지 않는다** — 되돌리면 격리한
   백도어가 새로 설치한 정상 파일을 덮는다(복원 계획은 그 자리를 *덮어씁니다* 로 알린다).
2. **패널 자격 증명을 모두 바꾼다** — 백도어는 임의 명령을 돌릴 수 있었다.
3. **기계 전체를 침해된 것으로 보고** 다른 위협을 살핀다.

(2·3 은 XLab 보고의 권고다.)

## 지표 — 공개된 것만

XLab(QiAnXin) 보고 *CWPdoor: The Invisible Backdoor Living Inside Control Web Panel* 이 밝힌 것만
쓴다 — 활성화 헤더 셋, 공격자 공개키(보고서에 PEM 그대로 실렸다), 표준 설치 경로, 서비스 이름.

**쓰지 않는 것** — 소켓 이름 `ngx_http_integrity_helper`: 트로이 버전 1.15.10 에 평문도 0x55 XOR
꼴도 없었다. 공개키 본문 첫 줄: 모든 2048비트 RSA 키에 공통인 머리다. PEM 머리 하나만: VirusTotal 에서
CWPdoor 와 무관한 파일 38개(APK · PE)가 0x55 XOR 한 같은 머리를 담는다 — 그래서 키 본문 줄을
함께 요구한다. 드로퍼의 SHA-256: 공개 보도에
없다. 내려받는 서버 주소: remedy 는 연결을 관측하지 않는다.

## 서명 — 저장소 사본은 개발용 키, 배포본은 배포 키

저장소의 `MANIFEST` · `MANIFEST.minisig` 는 저장소 사본을 확인하려고 **개발용 키로** 서명한 것이다.
**배포본은 이 서명을 쓰지 않는다** — 태그의 배포 잡(`.github/workflows/release.yml`)이 배포 키로 다시
서명하고 그 공개키를 박아 빌드하므로, 내려받은 배포 파일에 든 이 폴더는 배포 키의 서명이다(`plugin
verify` 로 확인한다). 개발용 키로 서명된 룰은 배포 앵커가 박힌 실행 파일에서 거부된다.
