# 테스트 VM 하네스

remedy 를 격리된 Windows VM 에 배포해 실행하고, **시스템이 실제로 어떻게 바뀌었는지**를
remedy 와 독립적으로 관찰한다.

설계-09 P0 선행 준비의 "VM 인프라" 항목이며, P6(apply) 이후 파괴적 테스트의 토대가 된다.

## 왜 독립 관찰인가

remedy 의 감사 로그는 **무엇을 하려 했는가**를 말한다. `Capture-State.ps1` 은
**실제로 무엇이 바뀌었는가**를 말한다. 둘이 어긋나는 지점이 곧 버그다.

`Compare-State.ps1` 에 `plan.json` 을 주면 **불변식 P**(설계-03 §1)를 검사한다 —
계획에 없는 변경이 실제로 일어났다면 위반이다. 이것이 이 하네스의 존재 이유다.
치료 도구가 계획서에 없는 것을 지웠다면, 그게 바로 2차 사고다.

관찰 코드는 remedy 를 전혀 쓰지 않는다. 검증자가 피검증자를 신뢰하면 검증이 아니다.

#### 모르는 것을 통과로 만들지 않는다

하네스마다 판정 줄의 모양이 다르다 — 다섯이다(`판정 N/M` · `게스트 검사 N/M`

`채점 5 합격`). 스크립트는 그 다섯을 읽고, **종료 코드와 판정을 둘 다 본다.**

- 종료 코드가 0 이어도 판정이 `12/14` 면 실패다
- 판정을 **못 읽었으면** 종료 코드가 0 이어도 `판정 못 읽음` 으로 적고 실패다
- 종료 코드를 **내지 않았으면** `없음` 으로 적고 실패다 (아래)
- `-SkipLinux` 없이 docker 가 없으면 실패다 — 조용히 건너뛰면 한 바퀴가 무엇을
  재었는지 알 수 없다

**채점 5 는 판정 하나(1/1)로 센다.** 합격·불합격 하나짜리 관문이기 때문이다.

##### 종료 코드 칸은 하네스의 말이어야 한다 (2026-10-26)

`$LASTEXITCODE` 는 프로세스 하나를 함께 쓰는 전역이고, `exit` 없이 끝난 스크립트는
그것을 **건드리지 않는다.** 그래서 비우지 않으면 그 칸에 **이 프로세스에서** 마지막
으로 돈 네이티브 명령의 코드가 찍힌다 — 흔히 **그 하네스 자신의 것**이고, 앞 하네스
안이든 `-Build` 의 빌드든 묶음을 부르기 전 그 콘솔에서든 상관없다. 어느 쪽이든
하네스의 판정이 아니다.

여섯(`Sign` · `Obs` · `Guard` · `Panic` · `SlowStop` · `Partial`)이 성공 경로에서
`exit` 를 두지 않았고, 실패하면 `exit 1` 만 불렀다. 그래서 `-Only SlowStop` 이
**11/11 인데 칸이 비어 실패로 찍혔다** — 그 바퀴의 첫 단계였고, 그 하네스의
`sc.exe` 는 전부 원격 세션 안이라 호스트의 그 전역을 건드릴 것조차 없었다.
전체 바퀴(`sweep-20261026-134020`)에서는 여섯 다 `exit=0` 으로 **우연히** 맞았다.
`Sign` 하나만 돈 바퀴(`sweep-20261026-170247`)도 0 이었다 — 앞 단계가 없었으니 자기
안의 `cargo` 호출에서 온 값이다. 그래서 "첫 단계면 칸이 빈다" 가 아니다.

둘을 같이 고쳤다.

| | |
|---|---|
| 하네스 | 여섯이 성공도 말한다 — `exit $(if ($passed -ne $checks.Count) { 1 } else { 0 })` |
| 묶음 | 부르기 전에 그 전역을 비워 `없음` 을 가려낸다. 없으면 실패다 |

`exit` 가 `finally` 를 건너뛰지 않는 것을 먼저 실측했다(모형으로 0·1 양쪽). 여섯의
`finally` 에는 원격 세션 닫기 · 임시 폴더 삭제 · `Sign` 의 서명 비밀번호 복원과
개인키가 든 TEMP 폴더 삭제가 들어 있다 — 건너뛴다면 그것들이 남았을 것이다.
`Panic` 의 `$env:RUSTFLAGS` 는 바깥 `finally` 에도 있지만 빌드 직후 안쪽
`finally` 가 이미 되돌리므로, 그쪽은 이 변경과 무관하게 안전했다.

**비우기로 잡는 것은 "아무것도 내지 않았다" 뿐이다.** PowerShell 은 명시적 `exit 9`
와 스크립트 끝에 남은 네이티브 9 를 구분해 주지 않는다. 칸을 하네스의 말로 만드는
것은 하네스마다 `exit` 를 두는 쪽이고, 비우기는 그것을 잊은 하네스를 조용히
지나가지 않게 하는 그물이다 — 새 하네스를 넣을 때 `exit` 를 두는지 보라.

`exit <변수>` 는 그 그물 밖이다. PowerShell 은 `$null` · 숫자 아닌 문자열 · 배열을
조용히 **0(통과)** 으로 만든다(실측). 변수로 나가는 다섯(`P2` · `P4` · `P5` · `P6` ·
`P8`)은 그 값이 늘 정수라 무사하지만, 새로 그 꼴을 쓸 때는 null 을 먼저 가려내고
`[int]` 로 못박을 것.

**묶음도 자기 규칙 안에 넣었다.** 성공한 바퀴의 종료 코드가 마지막 하네스의 값을
물려받은 것이었다 — 이제 묶음도 `exit $(if ($bad.Count -gt 0) { 1 } else { 0 })` 로
끝난다. 겸해서 `-Only` 와 `-SkipLinux` 가 겹쳐 목록이 비면 던진다: 전에는 루프가 한
번도 돌지 않은 채 `합계 0/0` 이 **초록으로** 찍혔다.

##### 리눅스 다섯이 처음엔 `판정 못 읽음` 이었다 — 부르는 쪽 콘솔이 CP949 였다

첫 호출은 도구 실행 상한을 피하려고 새 `powershell.exe` 를 숨은 창으로 띄워 돌렸다. 리눅스 다섯이
전부 **`판정 못 읽음`**(종료 0)으로 섰고, 묶음은 **설계대로 그것을 실패로 셌다**(exit 1). 하네스는 끝까지
돌아 통과했다 — 다섯 다 종료 0 이고, 깨진 글자 속에 판정 줄(`통과 20 · 실패 0 · 못잼 0  (전체 20)` ·
`판정 7/7` · `채점 5 합격.`)이 있었다. 콘솔을 거치지 않는 산출물(`verify-linux.json` 20/20 · 채점 셋의
`apply-result.json` 합격)도 재호출과 같다.

원인은 **콘솔 인코딩**이다. WSL 이 내는 UTF-8 한글이 CP949 로 풀려 묶음의 판정 정규식이 그 줄을 못
읽었다. 첫 호출 세션의 인코딩은 기록하지 않았고, 둘이 그것을 가리킨다. 같은 방식으로 띄운 숨은
`-NoProfile` 탐침 세션의 `[Console]::OutputEncoding` 이 ks_c_5601-1987(CP949)이었다. 그리고 재호출 로그의
줄을 WSL 이 낸 꼴(LF — CRLF 는 `*>` 가 붙였다)로 다시 이어 그 UTF-8 바이트를 통째로 CP949 로 풀면, 첫
호출의 로그가 줄마다 재현된다 — 다른 것은 실행 번호 · 시각 · trunc 컨테이너 이름(`실행 기계`)과 trunc 의
진행 줄 하나뿐이다. 줄 끝 바이트가 CP949 의 앞 바이트 자리에 오면 줄바꿈까지 먹혀 두 줄이 붙는다
(exam-ldso 42줄 → 37줄). 09-14 바퀴는 리눅스 판정을 그대로 읽었고(그때 부른 콘솔이 UTF-8 을 풀었다),
재호출은 에이전트 도구 셸(UTF-8 콘솔)에서 돌았다.

- **숨은 창이나 `-NoProfile` 이 원인이 아니다.** 이 PC 의 시스템 코드 페이지가 949(ACP · OEMCP)이고
  콘솔 코드 페이지 재정의(`HKCU\Console` 과 그 아래 창별 키)도 PowerShell 프로필도 없어, 새 콘솔은
  보이든 숨든 CP949 로 뜬다. 사람이 일반 창에서 위 사용법대로 불러도 리눅스 다섯은 같은 식으로
  `판정 못 읽음` 이 된다(보이는 창에서 재지는 않았다 — 코드 페이지는 창이 보이는지와 상관없이 정해진다).
- 로그 파일의 꼴은 별개 설정이다. 첫 호출의 로그 20개는 모두 UTF-16LE(`FF FE` — `*>` 의 기본값)였고,
  09-14 와 재호출의 로그는 BOM 있는 UTF-8 이었다. 판정 읽기에는 무해하다(묶음이 BOM 을 보고 읽는다).
  다만 하네스가 예외로 끝나면 묶음이 덧붙이는 사유(`[하네스가 예외로 끝났다] …`)를 UTF-8 로 못박고
  있어 UTF-16LE 로그 안에서 깨졌다. 콘솔을 맞춰도 남는 자리다 — 로그 꼴은 `*>` 가 정하고, 처방을 둔
  탐침의 로그도 `FF FE` 였다. **고쳤다**(아래 "스스로 맞춘다"). 이번 바퀴에는 예외가 없었으므로 잃은
  것은 없다.
- 같은 세션에서 Windows 하네스 안의 로컬 네이티브 호출(`xtask static` 등) 출력도 로그에서 깨졌다(P4 ·

  remedy 출력은 호스트에서는 `StandardOutputEncoding = UTF8` 로 직접 풀고, 나머지는 게스트 안에서 읽어
  이 호스트의 콘솔을 거치지 않는다 — Windows 15개가 같은 세션에서 섰던 까닭이다. 게스트 쪽 인코딩은
  따로다. UTF8 을 지정하지 않고 원격 세션에서 `&` 로 받은 출력은 게스트의 CP949 를 탄다(아래 "원격
  세션은 한국어를 깨뜨린다"). `Assert-CanDestroy`(`VmSession.ps1` — `& $b resume --help 2>&1 | Out-String` 에 `-match "신뢰할 수
  없"`)가 그런 자리라, 이 가드는 걸리지 못할 가능성이 크다(이번 바퀴와 무관 · 판정 수 밖 · 보고만).

##### 그래서 묶음이 스스로 맞춘다 — 부르는 환경에 기대던 세 곳 (2026-10-26)

**부르는 사람에게 숙제를 남기지 않는다.** 처음 적은 처방은 *"묶음을 UTF-8 콘솔에서 불러라"* 였는데,
그것은 한 바퀴를 돌릴 때마다 사람이 기억해야 하는 전제다. 잊으면 통과한 하네스가 실패로 찍히고, 그
사실은 로그를 열어 봐야 안다. 환경에 기대던 세 곳을 묶음 안으로 들였다.

| 기대던 것 | 들인 자리 | 안 하면 |
|---|---|---|
| 콘솔이 UTF-8 이어야 WSL 의 한글 판정을 읽는다 | `Invoke-WithUtf8Console` 이 그 호출만 감싸고 되돌린다 (리눅스 다섯 · bookworm 빌드) | 통과한 리눅스 다섯이 `판정 못 읽음` (위) |
| 로그가 BOM 있는 꼴이어야 다시 읽힌다 | `$PSDefaultParameterValues['Out-File:Encoding']` 을 `utf8` 로 못박는다 | `oem`·`ascii` 로 둔 세션에서 판정을 다시 못 읽는다 |
| 32비트가 지금 코드여야 P2 의 WOW64 둘이 지금을 잰다 | `-Build` 가 `i686` 도 짓는다 | 그 검사 둘만 묵은 바이너리로 선다 |
| 예외 사유가 로그와 같은 꼴이어야 읽힌다 | `Get-LogEncoding` 이 로그의 BOM 을 보고 고른다 | 예외로 끝난 회차에 정작 이유를 못 읽는다 |

`*>` 는 `Out-File` 로 구현되어 **부른 세션의 기본 인코딩을 따른다** — 기본값(UTF-16LE)과 `utf8` 은 BOM
이 있어 묶음이 바로 읽지만, `oem`·`default`·`ascii` 로 둔 세션에서는 BOM 없는 CP949 로그가 되어 10-26
과 같은 실패가 되돌아온다(실측). 못박은 뒤 로그는 BOM 있는 UTF-8 이다. 하네스에도 물려가지만 하네스는
`Out-File` 에 늘 `-Encoding` 을 주고 파일 리다이렉션은 이 묶음에만 있어, 바뀌는 것은 이 로그들뿐이다.

**콘솔은 그 호출만 감싼다**(`Invoke-WithUtf8Console`). 세터가 콘솔 창 전체 — 부른 쪽 셸까지 — 의 출력
코드페이지를 바꾸므로, 전역으로 두면 한 바퀴가 중간에 죽을 때 부른 사람의 창이 UTF-8 로 남는다.
호스트의 CP949 네이티브 출력을 읽는 자리도 있다(`Reset-Vm.ps1` 의 `vmrun listSnapshots` 이름 비교 —
지금 이름 넷이 전부 ASCII 라 무사하지만, 한글 이름이 생기면 전역 변경에 걸린다). 끝나면 되돌리므로
Windows 단계와 부른 쪽 세션은 부른 그대로를 본다(`before=949 after=949` 실측). **이미 UTF-8 이면
손대지 않는다** — 콘솔이 없는 프로세스에서 세터가 던지므로, ACP 가 65001 인 기계에서 멀쩡한 단계를
실패로 만들지 않기 위해서다. 맞추기에 실패하면 삼키지 않고 올려, 한 바퀴가 그 단계를 예외(99)로 적는다.

건지지 못하는 한 부류가 남는다 — **`wsl.exe` 자신의** 오류 문구는 UTF-8 이 아니라 UTF-16LE 라 949 든
65001 든 로그에서 읽히지 않는다. WSL 이 뜨지 않은 회차의 사유는 종료 코드로만 안다(판정 집계는
무사하다 — 판정 줄이 아예 없고 종료 코드가 0 이 아니므로 실패로 바르게 센다).

*"`SeBackupPrivilege` 때문"* 이라고 적었는데 **절반만 맞았다** — 특권을

| 길 | 막는 법 | 확인한 방법 |
|---|---|---|
| **소유권** — 소유자가 `BUILTIN\Administrators` 면 DACL 에 허용이 하나도 없어도 연다 | `icacls /setowner` 로 SYSTEM 에게 | 상속을 끊고 SYSTEM 만 남겨도 열렸다 |
| **특권** — `SeBackupPrivilege` 등이 ACL 을 우회한다 | 자식에서 전부 끈다 | 소유자를 넘겨도 특권이 켜져 있으면 열렸다 |

끄면 뒤이은 정리(`takeown`)가 `SeTakeOwnershipPrivilege` 를 잃어 실패한다.
끄는 범위를 자식 하나로 가둔다.

**전제도 판정에 넣는다** — 소유자가 SYSTEM 인지, ACL 조차 못 읽는지. 픽스처가
조용히 무력해지면 그 회차는 아무것도 재지 못한 채 초록이 되기 때문이다.

|---|---|---|
| `Refused` | 경계가 막았다. 그 뒤로 아무 일도 없다 | 사유를 없애야 한다 |

생기고, 무엇보다 **시험이 물어볼 자리가 없다.**

`remedy` 가 상한에 걸려 자식을 죽이는 일은 없으므로(결정 2026-09-07) 이

예외가 정상 등록됐고 throw 는 나지 않았다. 재현 수단으로 쓸 수 없다.

누군가 "Reset-Vm 이 해 주니까" 하고 배포를 뺄 수 있다. 이 스크립트가 빌드
산출물에 의존하게 되는 것도 값이다. **읽고 알리기만 하고 조치는 사람이 한다.**

한 시간 넘게 차이 날 때만 경고하고, 아니면 `OK 랩의 bin\remedy.exe 09-14 판`
한 줄이다. 양쪽 갈래를 실측으로 확인했다.

### 코퍼스 스냅샷 — `New-CorpusSnapshot.ps1`

`corpus/clean/` 에 쌓이는 아티팩트 스냅샷이 **오탐 방지의 실질적 사거리**다
(설계-04 §3.2). VM 이미지로는 몇 개밖에 못 돌리지만 스냅샷은 매 커밋 돌아간다.

```powershell
# 진단 모드 — file · persistence 만 모은다
.\testbed\harness\host\New-CorpusSnapshot.ps1 -Label win10x64-dev -Build

# 매니페스트 선언대로 — 그 플러그인이 보는 subject 를 전부 모은다
.\testbed\harness\host\New-CorpusSnapshot.ps1 -Label win10x64-dev -Plugin plugins\evilai-locust\plugin.yaml
```

**`-Plugin` 이 없으면 `file` 과 `persistence` 뿐이다.** `Scope::diagnostic` 이
그렇게 정한다. 그래서 `autorun`·`process`·`av_exclusion` 을 보는 룰은 그런
스냅샷에서 **태울 레코드가 한 건도 없다** — 코퍼스를 셋이나 갖고도 커버리지가
0인 자리가 실제로 있었다 (설계-09 P9 준비 점검).

**이 스크립트가 존재하는 이유는 스크러빙이다.** 손으로 뜨면 언젠가 빠뜨리고,
그러면 기계 이름과 실행 시각이 저장소에 실린다. 지우고 나서 **다시 파싱해
확인**하고, 레코드 수가 왕복에서 바뀌지 않았는지도 본다 — PS 5.1 의
`ConvertTo-Json` 은 한글을 `\uXXXX` 로 escape 하므로 원문 문자열 대조는
걸리지 않는다.

경로의 사용자 이름은 **지우지 않는다.** 데이터의 일부이고 지우면 경로 모양에
걸린 룰을 검증할 수 없다. 그래서 **랩 기계에서만 뜬다.**

`Invoke-VmTest.ps1` 과 `Invoke-P2Verify.ps1` 은 묻는 것이 다르다. 앞의 것은
"시스템이 계획대로만 바뀌었는가"(불변식 P), 뒤의 것은 "Phase 가 약속한 성질이
실기기에서 성립하는가"다. 목적이 다르므로 합치지 않는다.

연결 절차의 진단(호스트 WinRM 정지 · 빈 비밀번호 · UAC 토큰 필터링은 전부 같은
'액세스 거부'로 나타난다)은 `VmSession.ps1` **한 곳에만** 있다. 복사본이 갈라지면
다음 사람이 같은 길을 처음부터 다시 헤맨다.

## 준비 순서

VM 은 기본 상태에서 ping 도 WinRM 도 응답하지 않는다. **호스트에서 원격으로
준비할 수 없으므로 VM 콘솔에서 먼저 실행해야 한다.**

**1) VM 콘솔** — `testbed\harness\guest\` 폴더 전체를 VM 으로 옮긴 뒤, 관리자 PowerShell 에서:

```powershell
powershell -ExecutionPolicy Bypass -File .\Setup-Guest.ps1 -HostAddress <호스트의 VMnet8 주소>
```

방화벽은 호스트 IP 하나만 연다. 옆 VM 에 노출될 이유가 없다.

**2) 호스트** — 관리자 PowerShell 에서:

```powershell
Start-Service WinRM                        # 이걸 빼면 다음 줄이 실패한다
Set-Service  WinRM -StartupType Automatic  # 재부팅 후에도 유지
Set-Item WSMan:\localhost\Client\TrustedHosts -Value <호스트의 VMnet8 주소>28 -Force
```

`Set-Item WSMan:...` 은 **로컬** 설정을 바꾸는 명령인데, `WSMan:` 드라이브 자체가
로컬 WinRM 서비스가 떠 있어야 열린다. 서비스가 멈춰 있으면
"클라이언트가 요청에 지정된 대상에 연결할 수 없습니다" 라는 오류가 나는데,
여기서 말하는 '대상'은 VM 이 아니라 **호스트 자신**이다. VM 문제로 오해하기 쉽다.

`winrm quickconfig` 는 쓰지 말 것. 호스트에 리스너를 만들어 원격 접속 대상으로
노출시킨다. 클라이언트로 쓰는 데 필요한 건 서비스 기동뿐이다.
`Invoke-VmTest.ps1` 은 위 세 줄을 사전 점검에서 자동으로 처리한다(관리자 권한 필요).

**3) 확인** — 포트와 **원격 세션의 관리자 권한**을 둘 다 본다.

```powershell
Test-NetConnection <호스트의 VMnet8 주소>28 -Port 5985

$c = Get-Credential            # 예: <호스트의 VMnet8 주소>28\test
Invoke-Command -ComputerName <호스트의 VMnet8 주소>28 -Credential $c -ScriptBlock {
    $w = [Security.Principal.WindowsIdentity]::GetCurrent()
    [pscustomobject]@{ user = $w.Name
        admin = (New-Object Security.Principal.WindowsPrincipal($w)).IsInRole(
                    [Security.Principal.WindowsBuiltInRole]::Administrator) }
}
```

`admin` 은 **True 여야 한다.** 워크그룹 PC 에 로컬 계정으로 원격 접속하면 UAC 가
토큰에서 Administrators 를 걸러내고, 그 상태로는 remedy 의 서비스 삭제·HKLM
쓰기·프로세스 종료가 전부 '액세스 거부' 로 실패하는데 원인이 remedy 인지 권한인지
구분할 수 없다.

**이 설정은 `Setup-Guest.ps1` 이 자동으로 세운다**
(`LocalAccountTokenFilterPolicy = 1`, 쓴 뒤 되읽어 확인하고 실패하면 멈춘다).
예전에는 손으로 넣어 스냅샷에만 남아 있었고, VM 을 다시 만들거나 기준 스냅샷을
새로 뜨면 함께 사라져 하네스가 전부 '액세스 거부' 로 멈췄다 — 원인이 코드
어디에도 적혀 있지 않은 채로. 위 확인은 그것이 실제로 걸렸는지 보는 자리다.

그래도 False 로 나온다면 그룹 정책이 덮고 있는 것이다. VM 콘솔에서 직접:

```powershell
New-ItemProperty -Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System' `
    -Name LocalAccountTokenFilterPolicy -PropertyType DWord -Value 1 -Force
```

원격 로컬 관리자 로그온에 완전한 토큰을 준다. 격리된 테스트 VM 에서는 받아들일
수 있는 완화지만 **실제 업무 PC 에는 적용하지 말 것.**
(`Invoke-VmTest.ps1` 도 매 실행마다 이 권한을 확인하고, 없으면 시작하지 않는다.)

**UAC 자체(`EnableLUA`)는 끄지 않는다.** 끄면 Defender 동작과 스토어 앱이 달라져
시험 환경이 실제 사용자 PC 와 다른 것이 된다 — 전용백신을 그런 곳에서 검증하면
통과가 아무것도 뜻하지 않는다. 하네스는 원격 세션으로만 들어오므로 그 경로에
완전한 토큰을 주는 것으로 충분하다.

**4) 기준 상태 재캡처** — `Setup-Guest.ps1` 이 뜬 baseline 이 예전 판이면 다시 뜬다.

```powershell
powershell -ExecutionPolicy Bypass -File C:\remedy-lab\scripts\Capture-State.ps1 `
    -OutFile C:\remedy-lab\baseline\state.json
```

`-ExecutionPolicy Bypass` 가 필요하다. VM 의 기본 정책은 Restricted 라 `.ps1` 을
그냥 실행하면 막힌다. (호스트에서 도는 `Invoke-VmTest.ps1` 은 게스트 스크립트를
`powershell.exe -ExecutionPolicy Bypass -File` 자식 프로세스로 돌리므로 VM 의
정책을 바꾸지 않아도 된다.)

`파일 루트 N개` 줄과 `파일 M` 이 0 이 아닌지 확인할 것. 0 이면 경로가 없는 것이다.

**5) 여기서 스냅샷을 찍는다.** 이름은 **공백·괄호 없이** 지을 것 — 스크립트 인자로
오가는 값이다. 현재 기준 지점은 `remedy-lab-base-v2` 이고 `Reset-Vm.ps1` 의 기본값이다.

호스트에서 만들 수도 있다. 실행 중인 VM 은 메모리까지 담느라 5분 남짓 걸린다.

```powershell
& 'C:\Program Files (x86)\VMware\VMware Workstation\vmrun.exe' -T ws `
    snapshot '<VM 폴더>\Win10x64-Test.vmx' 'remedy-lab-base-v3'
```

**게스트 스크립트를 고친 뒤에 스냅샷을 다시 찍을 필요는 없다.** 복원할 때마다
`Reset-Vm.ps1` 이 저장소 최신본으로 맞춘다. 다만 스냅샷 안에 **위험한** 판이 들어간
경우는 다르다 — VMware UI 로 되돌린 뒤 VM 콘솔에서 직접 실행하면 동기화를 거치지
않기 때문이다. `v2` 를 새로 찍은 이유가 그것이다.

### 스냅샷에 넣는 것 / 넣지 않는 것

| 넣는다 | 넣지 않는다 |
|---|---|
| WinRM·방화벽 설정 | remedy 바이너리 (빌드마다 바뀐다) |
| `C:\remedy-lab\` 디렉터리 구조 | 테스트 픽스처 (매 테스트마다 새로 만든다) |
| `scripts\` 의 게스트 스크립트 | 실행 결과 |
| `baseline\` 의 기준 상태 3종 | |

스냅샷은 **깨끗한 실험대**여야 한다. 매 테스트는 같은 지점에서 출발해야 결과를 비교할 수 있다.

## 실행

```powershell
# 가장 단순한 확인 — 정적 바이너리가 이 Windows 에서 뜨는가
.\host\Invoke-VmTest.ps1 -RemedyArgs @('selftest')

# 픽스처를 깔고 스캔
.\host\Invoke-VmTest.ps1 -Fixture basic -RemedyArgs @('scan','--json')

# 자격 증명 저장 (DPAPI — 현재 사용자·현재 머신에서만 풀린다)
# 접속에 성공한 뒤에만 저장하므로 틀린 자격 증명이 캐시에 남지 않는다.
.\host\Invoke-VmTest.ps1 -SaveCredential -RemedyArgs @('selftest')

# 관측 범위를 시나리오에 맞게 지정
.\host\Invoke-VmTest.ps1 -RemedyArgs @('scan') `
    -FilePaths 'C:\remedy-lab\fixtures','C:\ProgramData\Something' -MaxFiles 50000
```

`-FilePaths` 는 전/후 캡처에 **동일하게** 적용된다. 범위가 다르면 있지도 않은
변경이 만들어지므로 한쪽만 바꿀 수 있게 두지 않았다.

### Phase 검증

```powershell
# 설계-09 P2 의 판정 요건 전체 (64·32비트 둘 다 빌드해 배포한다)
.\host\Invoke-P2Verify.ps1 -Build

# 통과한 결과의 청정 스냅샷을 corpus/clean/ 으로 들인다 (gzip)
.\host\Invoke-P2Verify.ps1 -ImportCorpus

# 성능·WOW64 만 다시 볼 때. %ProgramFiles% 수집(약 4분)을 건너뛴다
.\host\Invoke-P2Verify.ps1 -SkipCorpus -Repeat 5
```

**32비트 빌드가 필요하다** (`rustup target add i686-pc-windows-msvc`). WOW64
검사는 32비트 프로세스가 없으면 성립하지 않는다.

`-SkipCorpus` 로 돌린 실행은 통과가 아니라 **미결**이 남고 종료 코드가 2 다.
건너뛴 검사를 통과로 세면 검증이 없는 것만 못하다.

#### P2 는 왜 8분인가 — 시간의 79%가 코퍼스다

2026-09-11 실측, **`remedy-lab-base-v3`**(자동 갱신 끈 지점) 되돌리기 포함, 총
**496초**:

| 무엇 | 초 | 비고 |
|---|---|---|
| 코퍼스 수집 세 뿌리 | **393** | tasks 1.3 · user-programs 114.5 · **program-files 276.8** |
| 성능 예산 (§6) | 약 55 | scan · drivers · tasks 를 `-Repeat` 회 + 메모리 1회 |
| 나머지 | 약 48 | 되돌리기 · 게스트 시계 안정화 · 배포 · 항목 2~5 · 상태 캡처 |

**v2 에서 673초였다.** 자동 갱신을 끈 것만으로 코퍼스가 501→393초, 전체가
673→496초가 됐다(**−26%**). 판정 14/14 · 파일 수 · `denied_dirs = 0` 은 그대로다 —
잰 것은 같고 소음만 빠졌다.

**비용은 파일을 읽고 해시하는 것 자체다. Defender 가 아니다** — 이미 예외로 열려
있는 `%LOCALAPPDATA%\Programs` 가 파일당 21ms 로, 예외가 아닌 `%ProgramFiles%`
(8.2ms)보다 오히려 느리다. 큰 파일이 많은 쪽이 느릴 뿐이다.

**코퍼스 검사는 시간을 판정에 쓰지 않는다** — 판정은 `denied_dirs = 0` ·
`truncated = false` · "뿌리 셋" 이다. 그래서 시간을 줄이려면 **재는 것을 줄여야
한다.** 잃는 것 없는 지렛대는 하네스 안에 없다.

### P8 — 워치독 쌍은 VM 없이도 돈다

시나리오 A(워치독 쌍)는 **사용자 모드 프로세스 두 개**면 되므로 관리자 권한도
VM 도 필요 없다. 개발 기계에서 바로 돌릴 수 있고, 그것이 이 검증을 자주 돌릴 수
있게 하는 자리다.

```powershell
# 픽스처는 워크스페이스 밖이라 따로 빌드한다
cargo build --release --manifest-path testbed\fixtures\watchdog\Cargo.toml
cargo build --release --manifest-path testbed\fixtures\labsvc\Cargo.toml
cargo build

powershell -File testbed\harness\guest\Verify-P8.ps1 `
  -Bin target\debug\remedy.exe `
  -Watchdog testbed\fixtures\watchdog\target\release\lab-watchdog.exe `
  -LabService testbed\fixtures\labsvc\target\release\lab-service.exe `
  -OutDir testbed\harness\results\p8 -LabRoot $env:TEMP\remedy-p8-lab
```

> `-OutDir` 은 **`testbed\harness\results\` 아래**를 쓴다. 그 경로만
> `.gitignore` 에 있고, 결과 JSON 에는 감염 시스템의 경로·프로세스가 그대로
> 담긴다 — 저장소에 실리면 고객 환경 정보가 유출된다 (설계-00 §7).

시나리오 B(SCM 복구 동작)는 서비스를 만들고 정지시키므로 **`-AllowSystemService`
를 명시해야** 돈다. `Invoke-P8Verify.ps1` 이 그것을 붙이는 유일한 자리이고,
그래서 실수로 개발 기계에서 돌아가지 않는다.

**워치독 쌍은 스스로를 되살리는 프로세스다.** 세 겹으로 묶여 있다 — 절대 마감
시각, 세대 상한, 그리고 하네스가 쓰는 정지 파일. 그래도 무언가 남았다면
`taskkill /F /IM lab-watchdog.exe` 를 몇 번 부르거나, 마감(기본 40초)을
기다리면 된다.

> 픽스처가 **컴파일된 바이너리**인 이유: 되살리기가 제품의 종료 창보다 느린
> 감시자는 어떤 구현에게도 지고, 그때의 "이겼다" 는 아무것도 재지 못한 것이다.
> 실측 소생 간격이 결과 JSON 의 `facts.revive_ms` 에 남는다 — 그 숫자가 없으면
> 판정을 믿을 수 없다.

**시나리오 B 도 같은 이유로 진짜 서비스를 쓴다.** 첫 판은
`binPath = cmd.exe /c exit 1` 이었는데, 그것은 SCM 핸드셰이크를 하지 않아
RUNNING 에 도달하지 못하고 **되살릴 대상이 애초에 없었다.** `labsvc` 픽스처는
`windows-service` 로 핸드셰이크를 하므로 진짜로 돌고, 죽이면 SCM 이 정말
살려 낸다.

B 가 재는 것은 **두 실행의 차이**다.

| 계획 | 기대 |
|---|---|
| `[process.kill]` — 복구 동작을 남긴 채 | 되살아난다 (**적이 진짜다**) |
| `[service.clear_recovery, process.kill]` | 되살아나지 않는다 (**순서가 이긴다**) |

`service.stop` 이 아니라 `process.kill` 인 것이 요점이다 — 정상 정지는 복구
동작을 유발하지 않는다. SCM 은 예기치 않은 종료에만 반응하고, 그것이 설계-03
§2 가 1단계(복구 제거)를 2단계(종료) 앞에 둔 이유다.

**경로는 스크립트가 절대 경로로 고친다.** SCM 은 상대 경로를
`%SystemRoot%\System32` 기준으로 풀기 때문에 `binPath` 에 상대 경로가 들어가면
서비스가 아예 뜨지 않는다 — 첫 관리자 실행을 그것으로 날렸다. 이제 준비
단계에서 그것을 검사로 보고하므로, 관리자 없이 도는 실행에서도 보인다.

**결과에서 검사가 사라지지 않는다.** 서비스가 RUNNING 에 도달하지 못하면 B1·B2
와 복구 확인이 `재지 못했다` 로 남는다. 앞선 판은 그 셋이 통째로 증발해
`11/12` 가 "하나 실패" 로 읽혔는데, 실제로는 셋을 재지 못한 것이었다 — 제품에게
exit 6 으로 강제하는 규율을 하네스가 어기면 안 된다.

**전제가 무너지면 통과가 아니라 "재지 못했다" 다.** 세 검사는 사슬이다.

```
복구 동작이 설정됐다  →  되살아난다(B1)  →  순서를 지키면 안 되살아난다(B2)
                                          →  복구 동작이 지워졌다
```

앞이 없으면 뒤는 **통과로 보이는데 아무것도 재지 않는다** — 복구 동작이 설정된
적이 없으면 "되살아나지 않는다" 는 되살릴 것이 없어 참이고, "지워졌다" 는 지울
것이 없어 참이다. 성공처럼 보이는 공백이 가장 나쁘다.

**판정은 ASCII 토큰으로만 한다.** `FAILURE_ACTIONS`·`START_TYPE : 4` 는 sc.exe
가 영어로 찍는 필드 이름과 숫자다. 지역화된 값(`다시 시작`)으로 판정했다가
코드페이지 하나가 어긋나면서 한 검사는 거짓 실패가, 옆 검사는 **빈 검사**가
됐다. 설계-01 D12 가 제품에게 "출력을 읽지 않는다" 를 강제하는 이유와 같다 —
지역화된 문자열은 detail 에 보여 주기만 한다.

인코딩은 부르는 대상이 정한다 (remedy → UTF-8, `sc.exe` → ANSI 코드페이지).
오독은 준비 단계 검사가 잡는다: 없는 서비스를 물어 `1060` 이 보이고 대체
문자(U+FFFD)가 없는지 본다.

P6 은 `C:\remedy-lab` 안에서만 돌지만 그 안에서는 진짜로 파괴한다. 검사 8 갈래는
설계-09 P6 의 판정 요건과 일대일로 대응한다.

| G | **G3** — 계획에 없던 변경이 없다 | 게스트 + **호스트**(`Compare-State`) |
| H | 대화형 승인 — '예/아니오' 가 실제로 갈린다 | 게스트 |
| — | 네트워크 심볼이 링크되지 않는다 | **호스트**(`cargo xtask static`) |

**네트워크 심볼은 VM 이 알려주지 못한다.** 소켓을 열지 않는 실행을 아무리
관찰해도 "열 수 없다"는 증명되지 않는다. 임포트 테이블을 직접 보는 수밖에 없고,
그래서 배포 **전에** 호스트에서 판정한다.

D 의 실패는 대상 하나를 `FileShare.Read` 로 붙들어 만든다 — 읽기는 되고 삭제는
거부되므로 **백업은 성공하고 파괴만 실패**한다. 실기기에서 흔한 실패 모양이고,
백업과 파괴가 섞여 돌았다면 여기서 드러난다.

E 는 프로세스를 **진짜로 죽인다**(`Stop-Process -Force`). 죽이는 자리는 진행
이벤트로 잡는다 — `action` 은 나왔는데 `finished` 는 아직인 순간이 파괴 도중이다.
실측으로 400건 계획에서 52~128번째 사이에 걸렸다.

검사 결과는 `verify-p2.json` 에 항목별로 남는다. 판정은 셋이다 —
`pass` · `fail` · `inconclusive`. **전제를 세우지 못한 검사는 통과가 아니다.**
(예: `SysWOW64\Tasks` 와 `System32\Tasks` 의 내용이 같으면 32비트가 어느 쪽을
읽었는지 개수로 가를 수 없으므로 미결이다.)

결과는 양쪽에 남는다.

- 호스트: `testbed\harness\results\<run-id>\` (git 추적 제외)
- VM: `C:\remedy-lab\results\<run-id>\`

`stdout.txt` · `stderr.txt` · `run.json` · `state-before.json` ·
(픽스처를 쓰면) `state-armed.json` · `state-after.json` · `diff.json`.

픽스처를 쓰면 **`state-armed.json`** 이 비교 기준이 된다. 픽스처 생성 자체도 시스템
변경이므로, 그것까지 diff 에 섞이면 "remedy 가 한 일"을 분리할 수 없다.

## 채점 5 — 치료가 실기기에서 실제로 됐는가

`cargo xtask exam` 의 네 판정은 **전부 계획까지만 잰다.** 계획이 정상으로 서고
실행에서 거부되거나 조용히 아무것도 하지 않는 Action 은 어디에도 걸리지 않는다.
2026-09-05 하루에 그 틈으로 결함 셋이 지나갔고 셋 다 네 판정이 초록이었다.

```powershell
.\Invoke-ExamApply.ps1 -Threat search-hijack -Revert
.\Invoke-ExamApply.ps1 -Threat service-userinit -Plugin ..\..\ai-exam\runs\<회차>\plugin.yaml
```

### 되돌리기가 갱신기를 깨웠다 — v3 가 그것을 껐다

한동안 `-Revert` 는 채점 5 를 **불합격시켰다.** 되돌린 게스트는 시계가 맞춰지는
순간 자기가 열이레를 건너뛴 것으로 보고(기준 스냅샷이 2026-08-24 판이었다),
Chrome 과 Windows Update 가 **회차 도중에** 움직였다.

2026-09-11 실측 — `-Revert` 로 돌린 `evilai-locust` 가 불합격:

```text
치료가 만든 변화 4건 — 범위 밖인데 치료 전에는 없었다
  services/changed        GoogleChromeElevationService
  scheduled_tasks/added   \Microsoft\Windows\UpdateOrchestrator\MusUx_LogonUpdateResults
  scheduled_tasks/changed \Microsoft\Windows\UpdateOrchestrator\Reboot_AC
  scheduled_tasks/changed \Microsoft\Windows\UpdateOrchestrator\Reboot_Battery
```

**넷 다 remedy 가 한 일이 아니었다.** 차분을 열어 보면 Chrome 이 스스로
`151.0.7922.173` → `152.0.7977.83` 으로 갱신했다. 채점 5 는 전체 상태를 견주므로
그 소음을 *"치료가 만든 변화"* 로 센다.

**그래서 기준 스냅샷을 다시 떴다 — `remedy-lab-base-v3`** (같은 날). v2 에
자동 갱신 끄기를 더한 지점이다:

| 무엇 | 어떻게 |
|---|---|
| Windows Update | `wuauserv`·`UsoSvc`·`edgeupdate`·`edgeupdatem` 을 **Disabled** · `NoAutoUpdate` 정책 |
| Chrome · Edge | 갱신 예약 작업을 끄고 `UpdateDefault=0`·`AutoUpdateCheckPeriodMinutes=0` |
| **Defender** | **건드리지 않는다** — 실시간 보호·변조 방지 켠 채다 |

`UpdateOrchestrator` 의 예약 작업 열 몇 건은 **TrustedInstaller 소유라 관리자도 끌
수 없다**(`액세스가 거부되었습니다`). 그래서 서비스와 정책으로 위에서 막았다.

**이 손질은 `host\Disable-LabUpdaters.ps1` 한 줄로 다시 할 수 있다.** 스냅샷은
뜨지 않는다 — 되돌릴 수 없는 일은 사람이 한다. `-ReportOnly` 는 아무것도 바꾸지
않고 지금 상태만 찍는다.

상태 보고에 `wuauserv … Manual` 이 보여도 고장이 아니다. `WaaSMedicSvc` 가
Windows Update 를 고치는 것이 제 일이고 그 서비스는 끌 수 없어, **끈 직후에만
`Disabled` 로 보이고 곧 되돌아온다** — v3 로 되돌린 기계도 자리를 잡으면 같다.
**실질은 정책 키**이고, 갱신이 실제로 도는지는 채점 5 의 합격과 P2 의 시간이
말한다.

같은 명령이 그 뒤에 **합격했다** — `채점 5 합격 · exit 0`. **v2 는 지우지 않았다**;
되돌아갈 자리가 필요하면 `-Snapshot remedy-lab-base-v2` 로 준다.

재연결 자체는 되돌리기 경로에서도 정상이다 — `Invoke-ExamApply` 와
`New-ThreatSnapshot` 을 `-Revert` 로 한 번씩 돌려 확인했다(같은 날).

**세 시점을 뜬다** — 청정 → 감염 → 치료후. 그리고 차분 둘을 겹쳐 읽는다.

| 청정→감염 | 청정→치료후 | 뜻 |
|---|---|---|
| 있음 | **있음** | 위협이 밟는 자리면 **불일치**(불합격) |
| 있음 | 없음 | 치료됨 |
| 없음 | **있음** | 범위 밖이면 **치료가 만든 변화**(불합격) |

**위협마다 새로 적을 자료가 없다.** 판정 기준이 기계 자신이고, 어디를 볼지는
`expected-ops.txt` 가 정한다 — 응시자의 `plan.json` 에서 뽑으면 검증자가
피검증자를 믿는 것이고, 아무것도 계획하지 않은 답안이 아무 데도 안 보이는 채로
통과한다.

### 걸러 내는 것과 그 이유

| 갈래 | 왜 판정에서 빼는가 |
|---|---|
| 재부팅 대기 | `file.delete_on_reboot` 의 대상은 **다음 부팅까지 남아 있는 것이 맞다** |
| 우리 흔적 | 설계-03 §8 의 고정된 이름들 |
| 치료 전부터 있던 변화 | 살아 있는 기계가 스스로 한 것. 크롬이 부팅 직후 낡은 확장 판본을 정리하며 파일 179건을 지운다 |
| 판정 불가 | 남아야 하는 자리인데 **청정 기계에는 없었다** — 픽스처가 위협과 함께 설치한 정상 소프트웨어(appinit 의 Acme 에이전트) |

### 리눅스는 컨테이너에서 돈다

```bash
testbed/harness/linux/invoke-exam-apply.sh --threat ldso-preload     --bin /tmp/remedy-bookworm/release/remedy
```

새 컨테이너가 청정 기준이라 **되돌리기가 필요 없고, 살아 있는 기계가 스스로
만드는 잡음도 없다** — Windows 에서 181건이던 자리가 0이다.

판정 규칙은 같지만 **범위 안을 재는 방법이 하나 더 있다.** 리눅스 위협의
`expected-ops.txt` 는 `line=` 으로 지울 줄을 못박는다. 그러면 청정 기준과
견주는 대신 **그 줄만 빠졌는지**를 본다 — 감염 상태에서 그 줄들만 뺀 것과
치료 뒤 파일이 같아야 한다.

그래야 하는 이유가 실측으로 나왔다. `tls-intercept` 의 픽스처는 `/etc/hosts` 에
미끼 줄 하나를 더하고 컨테이너 자신의 호스트명 줄을 덮어쓴다. 청정 파일과
견주면 치료가 정확히 두 줄을 뺐는데도 **영원히 불합격**이 된다.

**대상이 남아야 하는지 없어져야 하는지는 손으로 적지 않는다.**
`machine/ops.json` 의 `edits_in_place` 를 두 하네스가 함께 읽는다 — 출처는
`Op::edits_in_place` 하나이고 `match` 에 와일드카드가 없어 Op 이 늘면
컴파일러가 분류를 요구한다.

#### 사람이 있는 회차 — `--attended`

`--yes` 는 *"화면 앞에 사람이 없다"* 는 선언이고, 그러면 계획기가
`cert_store.remove` 를 뺀다. `tls-intercept` 는 그래서 무인 회차에서 **미결**로
끝난다 — 잰 자리는 맞았지만 인증서를 재지 못했다.

```bash
testbed/harness/linux/invoke-exam-apply.sh --threat tls-intercept --attended     --bin /tmp/remedy-bookworm/release/remedy
```

코어는 stdin 이 **터미널인지**까지 본다. 파이프로 답을 밀어 넣으면 *"승인할
사람이 없습니다"* 로 거절되고 **그 거절은 승인 경로를 재지 않은 채 통과한다.**
그래서 컨테이너 안에서 `script` 로 pty 를 만든다 — Windows 쪽
`Approve-Interactive.ps1` 이 콘솔 핸들을 물려주는 것과 같은 이유다.

**승인 흐름은 두 갈래이고 둘 다 잰다.** 먼저 `아니오` 로 한 번 돌려 기계가
그대로인지 보고, 그다음 `예` 로 돌린다 — 승인하지 않았는데 무엇인가 바뀌는
것이 이 도구가 낼 수 있는 최악의 실패다. Windows 는 그것을
`Approve-Interactive.ps1` 이 재고 있었고 **리눅스에서는 이번이 처음이다.**

판정 줄이 `하네스가 사람 대신 '예' 로 답했다` 를 적는다. 그 회차의 합격은
*"사람이 승인하면 깨끗해진다"* 는 뜻이지 *"사람 없이 깨끗해진다"* 가 아니다.

| 위협 | 회차 | 판정 | |
|---|---|---|---|
| `ldso-preload` | 무인 | **합격** | 종료 1 · 범위 안 4곳 전부 |
| `tls-intercept` | 무인 | **미결** | 잰 3곳은 맞았다. 인증서는 코어가 미룬다 |
| `tls-intercept` | `--attended` | **합격** | 4곳 전부 · 계획이 5건으로 늘고 인증서가 사라진다 |

게이트가 무는지도 쟀다. `text_config.remove_line` 을 뺀 답안으로 돌리면
`ldso-preload` 가 **불합격**이 되고 `/etc/ld.so.conf.d/libc.conf` 에 남은 줄을
짚는다 — 그때도 `apply` 의 종료 코드는 **1(완전 치료)** 이다.

### 실행 중 상태 — 순서가 걸리는 자리

`evilai-locust` 의 위협 설명이 요구한다 — *"실행 중인 프로세스도 다뤄야 한다 …
있을 때도 없을 때도 처리돼야 한다."* **코퍼스 스냅샷에는 그 프로세스가 없어서
그 요구는 한 번도 시험된 적이 없었다.**

`Start-InfectedProcess` 가 세운다. 두 가지가 의도적이다.

- 진짜 페이로드는 함수를 정의하고 **곧바로 끝난다**(254 바이트 상수 배열).
  그래서 node 를 살려 두는 무해한 코드를 함께 준다 — 플러그인이 보는 것
  (이미지가 `node.exe` 로 끝나고 인자가 페이로드 폴더를 품는다)은 그대로다.
- **현재 디렉터리를 페이로드 폴더로 쥔다.** 그래야 죽이는 것이 지우는 것보다
  먼저 와야 한다는 요구가 진짜로 걸린다.

**두 쪽을 다 재고 다 기록한다.** `-NoProcess` 로 돌리면 프로세스를 세우지 않고,
증거는 `apply-result-no-process.json` 으로 따로 남는다 — 한 파일에 합치면 한
갈래를 다시 재는 것이 다른 갈래의 기록을 지운다. `cargo xtask exam-apply` 가
**둘 다** 요구한다: 한 쪽만 두면 *"탐지가 프로세스에 의존하게 되는 회귀"* 를
게이트가 못 잡는다.

| 갈래 | 계획 | |
|---|---|---|
| 기본 (프로세스 있음) | **7건** | `process.kill` 이 [1], `dir.delete_recursive` 가 [6] |
| `-NoProcess` | **6건** | `process.kill` 이 서지 않는다 — 판정은 그대로 선다 |

정답으로 돌리면 둘 다 종료 코드 1 이다. `payload-process` 를 뺀 사본으로 돌리면 —

```
종료 코드 3
  실패 [5] dir.delete_recursive … 다른 프로세스가 파일을 사용 중 (os error 32)

  남은 파일·폴더 1건 · 살아 있는 프로세스 1건
```

### 차분이 못 보는 자리 둘을 기계에 직접 묻는다

첫 물기 시험에서 **`범위 안 불일치 0건`** 이 나왔다 — 폴더 삭제가 실패했는데도.
관측기의 파일 섹션은 루트 **안의 파일**을 적지 루트 자신은 적지 않기 때문이다.

그래서 판정 직전에 게스트에 직접 묻는다.

| 검사 | 무엇을 |
|---|---|
| 남은 파일·폴더 | 없어져야 할 범위 안 대상이 아직 있는가 (`Test-Path`) |
| 살아 있는 프로세스 | 없어져야 할 자리를 인자로 쥔 프로세스가 아직 도는가 |

**재부팅 대기 대상은 뺀다** — `file.delete_on_reboot` 의 대상은 다음 부팅까지
남아 있는 것이 정상이라, 넣으면 `search-hijack` 이 매 회차 거짓 불합격이 된다.

### 재었다는 증거를 저장소에 둔다 — `--record` / `-Record`

채점 5 는 랩 기계가 필요해 `cargo xtask all` 안에서 돌 수 없다. 그래서
**아무도 안 돌리면 안 돌아간다.** 2026-09-05 에 그 구멍으로 실제로 지나갔다 —
`appinit-implant` 의 정답과 기대 Op 을 바꾸면서 실기기 결과가 낡았는데
알려 주는 것이 없었다.

합격 회차는 위협 폴더에 `apply-result.json` 을 남긴다. **정답의 자리는
`xtask` 의 `exam::REFERENCES` 가 안다** — `evilai-locust` 만 제품이 싣는
`plugins/evilai-locust` 이고 나머지 다섯은 시험 전용이다. 위협 폴더만 뒤지면
그 하나가 **정답 없는 위협으로 보이고 조용히 면제된다** (2026-09-05 실측).

지문은 정답 폴더의 **파일마다** 적는다. `plugin.yaml` 하나만 잡으면
`rules/*.yar` 이 바뀌어도 증거가 낡지 않는데, evilai 의 판별자가 정확히 그
YARA 룰이다.

```powershell
.\Invoke-ExamApply.ps1 -Threat search-hijack -Revert -Record
```
```bash
testbed/harness/linux/invoke-exam-apply.sh --threat tls-intercept --attended --record
```

`cargo xtask exam-apply`(그리고 `all`)가 그 증거를 본다.

| 무엇이 바뀌면 | |
|---|---|
| 정답 플러그인 | **게이트가 빨개진다** — 다른 답을 잰 결과다 |
| `expected-ops.txt` | **게이트가 빨개진다** — 다른 기준으로 잰 결과다 |
| 치료 코드 | 증거는 낡지만 **오프라인에서는 못 본다** |

마지막 줄이 이 검사의 한계다. 바이너리는 커밋되지 않아 견줄 것이 없고, 소스
지문으로 묶으면 무관한 커밋마다 빨개져 아무도 보지 않게 된다. 증거에 바이너리
지문과 시각을 적어 두는 것은 사람이 그 판단을 할 수 있게 하기 위해서다
(`snapshots` 검사가 같은 자리에서 같은 말을 한다).

**증거는 정답 플러그인의 것만 남는다.** 응시자 답안으로 `--record` 를 주면
하네스가 거절한다 — 그 위협의 *"정답이 기계를 고친다"* 는 기록이 응시자의
답으로 바뀌면 안 된다. 그리고 **합격만 증거가 된다.** 미결·불합격을 남기면
게이트가 그것을 보고 빨개지는데, 그때 할 일은 파일을 고치는 것이 아니라 다시
재는 것이다.

### 위협마다 무엇이 세우는가

| 위협 | 감염을 세우는 것 |
|---|---|
| `appinit-implant` · `service-userinit` · `search-hijack` | `guest/New-ThreatFixtures.ps1` |
| `evilai-locust` | **`host/InfectedState.ps1`** — **실행 중 상태까지 세운다**(아래). — P9 부터 있던 위협이라 코퍼스 스냅샷·P9 검증과 같은 모듈을 쓴다. 페이로드 바이트는 **룰 파일에서 만든다**(`Get-SynthPayloadBytes`) — 상수를 베껴 두면 룰만 고쳤을 때 조용히 어긋나고, 그때 발화하지 않는 페이로드로 "치료가 됐다" 가 나온다 |

**플러그인은 폴더째 보낸다.** `plugin.yaml` 하나만 보내면 `rules/*.yar` 이

그 회차는 이 플러그인을 잰 것이 아니라 일부가 빠진 사본을 잰 것이다.

## 픽스처 — 전부 무해한 모형

악성코드의 *구조*만 흉내 낸다. 페이로드는 로그 한 줄을 쓰고 끝난다.
네트워크 접속도, 암호화도, 은폐도 없다. 전부 `REMEDY-LAB-` 접두사가 붙어
찾아 지울 수 있고 실제 시스템 항목과 헷갈리지 않는다.

| 시나리오 | 만드는 것 | 무엇을 검증하려는 것인가 | 실전 확인 |
|---|---|---|---|
| `basic` | 랜덤 폴더의 페이로드 + 예약 작업 + Run 키 | 이름이 매번 바뀌는 대상의 탐지·제거 | 됨 |
| `watchdog` | 서로를 되살리는 프로세스 쌍 | 정지 후 종료 (설계-03 §2) | 됨 |
| `service` | 복구 동작이 걸린 서비스 등록 | 자동 소생 차단 (설계-03 §2) | 됨 |
| `hijack` | Winlogon `Userinit` 부분 오염 | 통째 삭제가 아닌 부분 편집 (설계-07 결함 1) | **미확인** |

**`watchdog` 은 실제로 재생성된다.** 안전판이 셋이고 하나라도 빠지면 VM 을 잡아먹는다.

1. 상대 탐지를 CIM 으로 한다. PS 5.1 의 `Get-Process` 에는 `CommandLine` 이 **없어서**
   항상 빈 값이 나온다. 그러면 상대를 영원히 못 찾아 매 주기마다 새로 띄우고,
   띄워진 것들이 또 띄우면서 지수로 불어난다 — 실측으로 30초 만에 **143개**까지 갔다.
2. 감시 프로세스 총수가 4를 넘으면 아무것도 띄우지 않는다. (1) 이 다시 틀려도
   폭주하지 않게 하는 이중 방어다.
3. 10분 뒤 스스로 종료한다.

고친 뒤 실측: 4초 만에 2개(alpha+beta)로 안정되어 32초간 그대로였고, 정리 1회차에
모두 종료됐다.

**`service` 는 등록과 복구 동작까지만 만들고 시작하지 않는다.** `cmd.exe` 는 서비스
제어 디스패처를 부르지 않으므로 SCM 이 30초를 기다린 뒤 1053 으로 실패시키고,
복구 동작이 걸려 있으면 재시작마다 또 30초씩 먹는다. remedy 가 제거해야 할 산출물은
'등록된 서비스 + 복구 동작'이고 그것은 정지 상태에서도 그대로 관측된다.
실제 SCM 재시작 경쟁까지 재현하려면 진짜 서비스 바이너리가 필요하다 —
**이 픽스처의 한계로 남겨 둔다.**

`hijack` 은 **원복에 실패하면 로그온이 막힌다.** `-IAcceptLoginRisk` 를 명시해야
동작하고, 스냅샷이 있는 상태에서만 쓴다.

정리는 `New-Fixtures.ps1 -Remove` 또는 스냅샷 복원. **확실한 쪽은 스냅샷 복원이다.**

## VM 이 죽었을 때

파괴적 테스트에서는 remedy 가 원격 세션 자체를 끊어버릴 수 있다. 그래서 모든
산출물을 **먼저 VM 디스크에 쓰고 마지막에 회수한다** — 결과를 연결 위에 얹어
두면 가장 알고 싶은 실패에서 정확히 그 데이터를 잃는다.

연결이 끊겨도 결과는 `C:\remedy-lab\results\<run-id>\` 에 남는다. 순서대로 시도할 것.

1. VM 재부팅 후 WinRM 이 살아나면 `Copy-Item -FromSession` 으로 회수
2. 부팅은 되는데 WinRM 이 죽었으면 VM 콘솔에서 VMware 공유 폴더로 복사
3. 부팅이 안 되면 가상 디스크를 다른 VM 에 붙여 마운트해서 꺼낸다
4. **회수한 뒤에** 스냅샷을 복원한다

## 알아둘 것

**인코딩 규칙이 파일 종류마다 정반대다.**

- `.ps1` 은 **BOM 이 있어야 한다.** 없으면 Windows PowerShell 5.1 이 ANSI(CP949)
  로 읽고, 한글 주석의 바이트를 따옴표나 괄호로 오독하면서 파싱이 무너진다.
- `.json` 은 **BOM 이 있으면 안 된다.** serde_json 을 비롯한 대부분의 파서가
  거부한다 (RFC 8259). 그래서 산출물은 `Out-File` 대신 `WriteAllText` 로 쓴다.

`Invoke-VmTest.ps1` 이 배포 직전에 BOM 과 문법을 모두 검사하므로, 편집기가
BOM 을 떼면 VM 에 닿기 전에 걸린다.

**WinRM 세션에는 콘솔이 없다. 그런데 만들 수는 있다.**

`apply` 는 `--yes` 가 없으면 stdin 이 터미널인지 본다. 원격 세션에서는 언제나
거짓이라 "승인할 사람이 없습니다"로 거절되고, **예/아니오 응답 경로가 통째로 시험
밖에 남는다.** `Approve-Interactive.ps1` 이 그 구멍을 메운다.

- `CONIN$` 를 **먼저 열어 본다.** 그것이 "콘솔에 붙어 있는가"의 진짜 답이다.
  `GetConsoleWindow` 은 창 없는 콘솔에서 거짓말을 하고, `AllocConsole` 부터
  부르면 이미 붙어 있을 때 실패한다. 두 방식 모두 실측으로 어긋났다.
- 열리지 않으면 `AllocConsole`. **WinRM 세션(세션 0, 대화형 데스크톱 없음)에서도
  성공한다** — 실측으로 remedy 가 실제로 승인 질문을 띄웠다.
- 그 핸들을 `SetStdHandle(STD_INPUT_HANDLE)` 로 못 박고, 자식은 stdin 을
  재지정하지 않고 띄운다. 핸들은 **상속 가능**해야 한다 — stdout·stderr 를
  재지정하면 `STARTF_USESTDHANDLES` 가 켜지고 상속 불가 핸들은 닿지 않는다.
- 답은 `WriteConsoleInput` 으로 밀어 넣는다. 파이프로는 안 된다 — 파이프면
  터미널이 아니고, 터미널이 아니면 애초에 묻지 않는다.

**이것을 별도 스크립트로 뺀 이유**가 있다. `AllocConsole` 은 프로세스의 표준
핸들을 갈아 끼우고, `FreeConsole` + `SetStdHandle` 로 되돌려도 PowerShell 의
호스트는 콘솔 화면 버퍼를 다시 잡지 못한다. 이후 `Write-Host` 가
"핸들이 잘못되었습니다"로 죽고 그 뒤의 로그가 통째로 사라진다. 한 스크립트
안에서 하다가 실제로 그렇게 됐다.

**돌고 있는 프로세스가 쓰는 파일은 `ReadAllText` 로 못 읽는다.**
`File::ReadAllText` 는 `FileShare.Read` 로 열어 글쓴이를 밀어낸다. 진행 이벤트
파일처럼 도는 동안 읽어야 하는 것은 `FileShare.ReadWrite -bor Delete` 로
직접 열 것. 모르고 쓰면 "다른 프로세스가 사용 중"으로 검사 자체가 죽는다.

**자식 프로세스의 출력 인코딩을 매번 명시할 것.** 빠뜨리면 .NET 이 콘솔
코드페이지(이 VM 은 CP949)로 디코드하는데 remedy 는 UTF-8 로 쓴다. 한글 문구가
깨져 `-match` 가 조용히 어긋나고, 시험은 "그 문구가 없다"고 보고한다. 호스트에서
예행할 때는 코드페이지가 달라 통과했다가 VM 에서만 실패했다.

**PowerShell 의 `foreach` 는 같은 스코프에 대입한다.** `Compare-State.ps1` 에서
`$a` 는 **후 상태**인데 루프 변수로 `$a` 를 썼다가 그대로 덮어써졌고, 그 뒤의
모든 섹션이 비어 보였다 — 프로세스 171건·서비스 281건이 "사라졌다"로 나왔다.

**상태 캡처에 `Get-Content` 를 쓰지 말 것.** `Get-Content` 는 각 줄에
`PSPath`·`PSDrive`·`PSProvider` 노트 속성을 붙인다. `PSProvider`(`ProviderInfo`)
가 다른 객체들을 물고 있는 그래프라 `ConvertTo-Json -Depth` 가 지수적으로
폭발한다. 실측으로 hosts 파일 **3줄**이 Depth 2 에서 이미 4,275자(평문 135자)
였고, Depth 8 에서는 끝나지 않다가 `capacity was less than the current size`
로 죽었다. `[System.IO.File]::ReadAllLines()` 를 쓰고 `[string[]]` 로 캐스팅한다.

**`Get-ChildItem` 은 경로가 `\*` 로 끝나면 `-Recurse` 를 무시한다.** 같은 디렉터리에
대해 `'C:\ProgramData\*' -Recurse -File` 은 **1건**, `'C:\ProgramData' -Recurse -File`
은 **10,605건**이 나온다. 이 함정 때문에 첫 VM 기준 캡처가 `파일 0` 으로 나왔고,
평평한 폴더로만 시험한 초기 검증은 이를 통과시켰다. `Capture-State.ps1` 은 이제
재귀를 직접 돌리며 후행 `\*` 를 떼고, 재파스 지점은 따라가지 않는다(순환·중복 방지).

**`-FilePaths` 기본값은 일부러 좁다.** `C:\ProgramData` 같은 큰 루트를 넣으면
백신 시그니처·로그가 끊임없이 바뀌면서 매 실행마다 가짜 변경이 쏟아지고 진짜
변경이 그 속에 묻힌다. 이 VM 에는 알약과 Defender 가 둘 다 있어 특히 그렇다.
넓은 범위가 필요하면 그 실행에서만 명시적으로 넘길 것.

### 판정 세 가지를 구분할 것

| 판정 | 뜻 |
|---|---|
| `pass` (exit 0) | 실제 변경이 모두 계획에 있었다 |
| `violation` (exit 1) | 계획에 없는 변경이 실제로 일어났다 |
| `inconclusive` (exit 2) | 계획 밖 변경은 못 찾았지만 **관측 자체를 믿을 수 없다** |

`inconclusive` 는 파일 목록이 상한에 걸려 잘렸거나, 전/후 캡처가 서로 다른 루트를
훑었거나, 훑은 루트가 아예 없을 때 나온다. 잘림과 루트 불일치는 변경을 **숨길** 수는
있어도 **만들어낼** 수는 없다 — 그래서 위반 판정은 그대로 믿을 수 있고 통과 판정만
미결로 낮춘다. **`inconclusive` 를 통과로 읽으면 안 된다.**

상태 스키마는 `remedy-lab.state/5` 이고, 판이 다른 캡처끼리는 `Compare-State.ps1` 이
비교를 거부한다. `/1`→`/2` 는 파일 수집이 재귀하게 된 판이라 수천 건의 가짜 '추가'가
나고, `/2`→`/3` 은 서비스에 복구 동작(`failure_action`)이 추가돼 모든 서비스가
'변경'으로 잡힌다. **스냅샷 안의 `baseline\state.json` 은 `/2` 판이다** — 비교는
매번 새로 뜨는 캡처끼리 하므로 문제되지 않지만, 그 파일을 직접 비교에 쓰면 거부된다.

**스냅샷을 되돌리면 게스트 스크립트도 스냅샷 시점 판으로 돌아간다.** `Reset-Vm.ps1`
이 복원 직후 저장소 최신본으로 맞춰 주지만(자격 증명이 저장돼 있을 때만), 이 함정은
한 번 실제로 밟았다 — 이미 고쳐 둔 fork bomb 이 복원과 함께 되살아나 VM 에
프로세스가 143개까지 쌓였다.

캡처 한 번은 프로세스 500여 개 기준 **5~10초**다. 픽스처를 쓰는 실행은 캡처가
세 번(before/armed/after)이므로 30초 안팎을 예상하면 된다. 파일 루트를 넓히면
해시 계산 때문에 훨씬 길어진다.

**Defender 는 끄지 않는다.** 설계-00 §5-1 에 따라 보안 제품이 깔린 환경이
주 배포 대상이다. 기본 스냅샷은 실시간 감시가 **켜진** 상태를 권장한다 —
그것이 고객 환경이다. 끈 상태의 스냅샷이 필요하면 별도로 하나 더 만들 것.

현재 테스트 VM 은 Windows 10 Enterprise 19045(22H2) 64비트, PS 5.1.19041 이고
**알약과 Windows Defender 가 함께 설치**되어 있으며 Defender 실시간 감시와
변조 보호가 모두 켜져 있다. 자사 제품이 깔린 상태를 그대로 재현한다는 점에서
좋은 조건이지만, 두 가지를 예상해 둘 것.

- remedy 바이너리가 두 제품 모두에게 실시간 검사를 받는다. 배포·실행이 느려지거나
  차단될 수 있고, 그것 자체가 확인해야 할 사항이다(설계-01 D7 서명·화이트리스트).
- **변조 보호가 켜져 있으면 Defender 예외 목록 원복이 막힐 수 있다.** 설계-03 §2 의
  해당 Op 를 시험할 때는 차단되는 것이 정상 동작인지 결함인지 먼저 구분할 것.

**VM 은 정적 링크 여부를 알려주지 못한다.** 테스트 VM 에는 UCRT 와 VC++
런타임이 깔려 있어 동적 링크 바이너리도 잘 돈다. 실제로 `+crt-static` 이
CI 의 `RUSTFLAGS` 에만 있던 동안 로컬 빌드는 전부 `VCRUNTIME140.dll` 을
임포트했고, **그 바이너리로 P2 검증 12/12 를 통과했다.** 검증은 통과하는데
배포될 물건은 다른 것이었고, 고객 PC 에서만 실행이 안 됐을 것이다.

지금은 `.cargo/config.toml` 이 플래그를 박고, 두 호스트 스크립트가 배포 전에
`cargo xtask static` 으로 산출물을 직접 본다. 설정을 믿지 않는다 —
`RUSTFLAGS` 환경변수가 설정되면 그 설정을 **통째로 덮기** 때문이다.

**빈 입력에 통과 도장을 찍지 말 것.** `@($null)` 은 빈 배열이 아니라 **null 하나를
담은 1개짜리 배열**이다. 이 함정 때문에 첫 P2 검증에서 모든 개수가 1로 나왔고,
"관찰 0바이트 동일" 같은 공허한 통과가 만들어졌다. 검증에서 가장 위험한 결과는
실패가 아니라 **아무것도 보지 않고 난 통과**다. `Verify-P2.ps1` 은 이제
비교할 것이 없으면 통과가 아니라 실패로 보고한다.

**`Start-Process` 로 성능을 재지 말 것.** 같은 바이너리 같은 인자가
`Start-Process -Wait -PassThru -RedirectStandard*` 로는 약 1.02초,
`ProcessStartInfo` 로는 약 0.03초다. 36배가 전부 측정 도구의 몫이다. 이것을
모르고 "실행 하한 1초" 를 remedy 의 성질로 보고한 적이 있다 — 그 위에 예산을
세웠다면 있지도 않은 문제를 고치러 갔을 것이다. **재는 쪽이 재는 대상보다
느리면 남는 것은 도구의 그림자다.** `Verify-P2.ps1` 은 `ProcessStartInfo` 를 쓴다.

`Invoke-VmTest.ps1` 은 그럼에도 `Start-Process` 를 쓴다. 자식이 **파일에** 쓴
출력은 remedy 가 세션을 끊어도 남기 때문이다. 대신 그쪽의 `duration_sec` 은
성능 수치가 아니다.

**최대 메모리는 살아 있는 동안 표본해야 한다.** 종료 후 `PeakWorkingSet64` 는
0 을 돌려준다(성능 카운터가 이미 사라졌다). 그리고 폴링은 소요 시간을 부풀리므로
**시간과 메모리는 서로 다른 실행에서 잰다.**

`corpus/clean/` 의 스냅샷은 이 하네스가 실제 Windows 에서 뜬 것이다.
`Invoke-P2Verify.ps1 -ImportCorpus` 로 갱신하며, gzip 으로 보관한다
(실측 12.9MB → 1.9MB). CI 는 VM 없이 그 스냅샷으로 오탐 게이트를 돌린다.

반입할 때 `run_id` · `created` · `collected_at` · `hostname` 을 고정값으로
바꾼다. **같은 기계가 같은 상태면 같은 파일이 나와야 한다** — 그러지 않으면
검증을 한 번 돌릴 때마다 내용이 같은 2MB 짜리 블롭이 이력에 새로 쌓인다.
파일의 `mtime` · `ctime` 은 건드리지 않는다. 그것은 실행이 아니라 관찰이고
룰이 조준할 수 있는 값이라, 지우면 코퍼스가 검사하는 범위가 조용히 줄어든다.

**불변식 P 대조는 P6 부터 의미를 갖는다.** 그 전에는 계획이 늘 비어 있어
`pass` 가 "계획에 없는 변경이 없었다" 가 아니라 "검사할 계획이 없었다" 였다.

대조에 쓰는 문자열은 **`actions[].target` 과 `actions[].match` 뿐이다.**
처음에는 `plan.json` 의 모든 문자열을 재귀로 긁었는데, 봉투의 `host.os` 가
`"windows"` 라서 **`C:\Windows` 아래에서 무엇이 바뀌어도 "계획에 있다"** 로
읽혔다. 치료 도구가 가장 큰 사고를 낼 수 있는 자리가 통째로 검사에서 빠진 채
판정은 통과로 나왔고, P6 첫 VM 검증에서 실제로 그렇게 나왔다.

**저절로 일어나는 변화는 판정에서 뺀다.** 프로세스 증감, 그리고 서비스의
**실행 상태만** 달라진 것이다 (실측: `W32Time` 이 시각 동기화를 마치고 스스로
멈췄다). 진단하지 못하는 것을 위반이라 부르면 검증은 늑대소년이 되고, 그러면
진짜 위반이 났을 때 아무도 보지 않는다. 다만 **숨기지는 않는다** — 뺀 것은
`volatile_changes` 로 남고 화면에도 뜬다. 서비스의 시작 유형·이미지 경로·복구
동작이 달라진 것은 저절로 일어나지 않으므로 그대로 위반이다.

**관측자는 자기 자신을 세지 않는다.** 캡처를 두 번 뜨면 그 두 프로세스는 인자가
달라 서로 다른 항목으로 잡히고, 아무도 하지 않은 변경이 diff 에 생긴다.
`Capture-State.ps1` 이 `$PID` 를 걸러 낸다.

이 대조기가 실제로 실패하는지는 따로 확인했다 — 진짜 캡처를 가져다 계획에 없는
파일 삭제·서비스 시작 유형 변경·복구 동작 변경·예약 작업 삭제를 각각 심었고
넷 다 위반으로 나왔다. 실행 상태만 바꾼 것과 아무것도 안 바꾼 것은 통과였다.

## Linux — 컨테이너에서 돈다

Windows 쪽은 VM 스냅샷으로 격리를 얻는다. Linux 는 **컨테이너**로 얻고, 그 편이
싸다 — 되돌릴 것이 없이 버리면 된다.

개발용 WSL 에서 돌리지 않는다. 하네스가 `/etc/hosts` 를 고치고 systemd 유닛을
지우고 프로세스를 죽인다. WSL 에는 그 밖에 **systemd 가 PID 1 이 아니라는**
문제도 있는데, Linux 의 `service.disable`·`service.delete` 는 순수 파일 조작
(`.wants/` 링크와 유닛 파일 제거)이라 그것 없이도 잰다.

| 파일 | 실행 위치 | 역할 |
|---|---|---|
| `linux/lab-plugin.yaml` | — | 검증용 실험 플러그인 (**치료까지 간다**) |
| `linux/new-fixtures.sh` | 컨테이너 | 무해한 픽스처 생성/정리. `--force` 없이 컨테이너 밖에서는 멈춘다 |
| `linux/capture-state.sh` | 컨테이너 | 상태 캡처. **remedy 를 전혀 쓰지 않는다** |
| `linux/verify-linux.sh` | 컨테이너 | 검증 본체 — 수집·판정·계획·치료·격리·복원·저널 |
| `linux/trunc-verify.sh` | 컨테이너 | **수집 상한에 걸려 잘렸을 때 6 이 나오는가** (아래) |
| `linux/invoke-linux-verify.sh` | 호스트 | 컨테이너를 띄워 위를 부른다 |

### 이것이 재는 것

**Linux 에서 `apply` 가 한 번도 실기기에서 돈 적이 없었다.** 쓰기 백엔드의 단위
시험은 전부 임시 디렉터리 위에서 돈다. 진짜 `/etc` · 진짜 systemd 유닛 · 진짜
cron 파일 · 진짜 프로세스 위에서 무엇이 일어나는지는 이 하네스가 처음 봤고,
**첫 회차에 제품 결함 여섯을 냈다** (2026-09-03):

| 결함 | 어디 |
|---|---|
| 모르는 `restore` 이름이 조용히 엉뚱한 Op 이 된다 | `remedy-sdk/src/lint.rs` |
| `%ALLUSERPROFILES%` 가 `/root` 아래를 전부 홈으로 센다 | `remedy-platform/src/linux.rs` |
| G6 의 고정 자리 목록에 이름 원복 넷이 빠졌다 | `remedy-plan/src/guard.rs` |
| `restore` 가 술어를 안 붙여 `apply` 가 통째로 멈춘다 | `remedy-plan/src/derive.rs` |
| hosts 줄을 재구성해 탭 하나에 대조가 걸린다 | `remedy-artifacts/src/record.rs` |
| 끈 cron 줄을 "없다" 로 봐 `delete` 가 건너뛰어진다 | `remedy-platform/src/linux.rs` |

넷은 **Windows 에도 있던 것**이다 — Linux 가 처음 밟았을 뿐이다.

### 판정은 셋이다

통과 · 실패 · **못 잼**. 셋째가 없으면 잴 수 없던 것이 둘 중 하나로 접히고,
어느 쪽으로 접든 거짓말이 된다. 통과로 접으면 *"재지 않았다"* 가 *"오탐이
없다"* 로 읽히고, 실패로 접으면 고칠 것이 없는 자리를 계속 붉게 보여 사람이
실패를 무시하는 법을 배운다. `verify-linux.json` 에서 못 잰 것은 `ok: null` 이다.

### 이미지를 고르는 이유

`cert_store.remove` 가 `update-ca-certificates` 를 요구한다 — 인증서 파일만
지우면 `ca-certificates.crt` 번들에 남아 신뢰가 사라지지 않기 때문이다. 그 도구가
없는 이미지에서는 그 Op 이 **거부되는 것이 옳고**, 하네스는 그 자리를 "못 잼"
으로 적는다.

| 이미지 | glibc | update-ca-certificates |
|---|---|---|
| `rust:1.96-bookworm` | 2.36 | **있다** ← 기본값 |
| `debian:12` | 2.36 | 없다 |
| `ubuntu:24.04` | 2.39 | 없다 |

바이너리도 bookworm 에서 만든다. 2.36 에서 만든 것은 셋에서 전부 돌지만, 2.39
에서 만든 것은 bookworm 에서 안 돈다.

### 수집 상한 — `trunc-verify.sh`

관측 불완전(6)의 사유 넷 중 **잘림만** 아무 데서도 재어지지 않았었다.
까닭은 상한이 크고 손잡이가 없다는 것이다 — `Scope::max_files` 는
**500,000 이 코드에 박혀** 있고(`scope.rs` · `pipeline.rs` 두 자리)
매니페스트로도 `--config` 로도 바꿀 수 없다. 그래서 **진짜로 넘긴다.**

```bash
docker run --rm \
    -v "$PWD:/repo" \
    -v <Windows 쪽 .cargo 의 WSL 경로>/registry:/usr/local/cargo/registry \
    -v remedy-bookworm-target:/tmp/remedy-bookworm \
    -e CARGO_TARGET_DIR=/tmp/remedy-bookworm \
    rust:1.96-bookworm bash /repo/testbed/harness/linux/trunc-verify.sh
```

**파일 50만 개를 만들고 지우는 일이라 컨테이너가 맞는 자리다.** 끝나면
컨테이너와 함께 사라지고 랩 VM 의 디스크를 50만 inode 로 채우지 않는다.
`split -b 20` 으로 찍어 내면 만드는 것도 싸고, 20바이트짜리는 읽기도
해시도 싸다.

> **2026-10-26 — 사유 단정을 `수집이 상한에 걸려 잘렸습니다`(화면 마감 뒤 문구)로 맞췄다 · 판정
> 7/7.** 같은 바이너리(볼륨의 `317f61dc…`)로 맞추기 전에 돈 회차는 6/7 이었다.

**2026-09-12 실측 — 판정 7/7.**

| 무엇 | 관측 |
|---|---|
| 500,001개 | **6** · `수집이 상한에 걸려 잘렸습니다` |
| 처리 시간 | `항목 500001개 · 처리 500000개 · 경과 5초` |
| 잘려도 | `흔적 0건` 을 그대로 보고한다 — *아무것도 못 봤다* 가 아니다 |
| 100개 (음성 대조) | **0** · `위협이 발견되지 않았습니다` |

음성 대조가 없으면 6 이 나왔다는 사실만으로는 *"이 룰은 늘 6 을 낸다"* 와
구별되지 않는다.

**보고만**: `max_files` 500,000 이 두 자리에 각각 박혀 있다
(`Scope::diagnostic` 과 `pipeline.rs`). 한쪽만 고치면 진단 모드와 일반
회차의 상한이 갈라진다.

레지스트리를 읽기 전용으로 걸면 안 된다 — `yara-x` 의 빌드 스크립트가 그 아래에

**레지스트리는 Windows 쪽을 물린다**(`<Windows 쪽 .cargo 의 WSL 경로>/registry`).
WSL 의 `~/.cargo/registry` 를 쓰던 예전 줄은 **오프라인 빌드를 깨뜨린다** —
그쪽은 Windows 에서 매일 도는 빌드를 따라가지 못해 낡고, `--offline` 이 새
의존을 못 찾아 선다(2026-09-12 실측). 콘솔 캡처는 이미 Windows 쪽을 물고
있었다 — **한 저장소가 두 말을 하고 있었다.**

### 실측 (2026-09-12 · rust:1.96-bookworm)

**통과 20 · 실패 0 · 못 잼 0.** 계획된 Op 13종이 전부 수행됐고, 미룬 둘
(`service.stop` · `service.clear_recovery`)은 카탈로그가 `linux_from: None` 이라
선언한 것이다. 2026-09-03 에 잰 값과 **하나도 달라지지 않았다.**

결과는 `results/linux-<태그>/verify-linux.json` 에 남는다. `results/` 는
`.gitignore` 에 있으므로 **저장소에 들어가지 않는다** — Windows 쪽과 같다.
숫자를 남기려면 이 문단처럼 문서에 적는다.

### 위협 스냅샷도 실기기에서 뜬다 (2026-09-04)

AI 시험 위협 다섯의 감염 스냅샷이 **전부 손으로 쓴 JSON** 이었다. 그런 스냅샷은
두 가지를 못 한다 — **다시 뜰 수 없고, 실기기가 낼 수 없는 모양을 담을 수 있다.**
둘 다 실제로 일어났다.

리눅스 둘(`ldso-preload` · `tls-intercept`)을 옮겼다. 컨테이너에 감염 상태를
실제로 세우고 진짜 `collect` 를 돌린다.

```bash
testbed/harness/linux/new-threat-snapshot.sh --threat ldso-preload
testbed/harness/linux/new-threat-snapshot.sh --threat tls-intercept
```

| | 합성 | 실기기 |
|---|---|---|
| ldso-preload | 12건 | **18건** |
| tls-intercept | 11건 | **155건** (인증서 143) |

tls 쪽 인증서가 3 → 143 이 된 것이 이 이동의 값이다. 청정 루트 CA **142개**가
같은 스냅샷에 함께 있으므로, *"자가서명으로 가르면 안 된다"* 를 이제 채점이
실제로 잰다.

**옮기자 우리 정답 플러그인이 무너졌다.** `tls-intercept` 정답이 인증서를
`store equals "system"` 으로 좁히고 있었는데, 수집기는
`/usr/local/share/ca-certificates` 를 `local` 이라 적는다 — 소스가 그 자리를
*"악성 루트 CA 가 들어오는 자리"* 라 부르는 곳이다. 실기기 스냅샷에서 **판정이
서지 않았다.**

뿌리는 더 아래였다. `ENUMERATED_FIELDS` 의 `cert_store.store` 값 전수에
`local` 이 없었고 `defined: true` 라, 작성자가 옳은 값을 쓰면 린트 오류가
나고 목록에 있는 `system` 을 쓰면 조용히 0건이 됐다. 값 전수를 고치고 수집기
상수와 카탈로그를 묶는 시험을 붙였다.

**페이로드는 실검체가 아니다** — 크기만 맞춘 무해한 자리 채우기다. 그래서
`corpus/infected/` 에는 넣지 않는다.

> **2026-09-05 정정.** 여기 *"그쪽은 실검체 바이트가 들어간 것만 담는다"* 고
> 적었다. **틀렸다.** `corpus/infected/` 도 파일 본문은 실검체가 아니라
> **룰에서 합성한 바이트**다 — 저장소에 악성 바이트를 들이지 않기로 한
> 결정이고, `xtask/src/yara.rs`
> 가 *"검체는 저장소 밖에 있고 앞으로도 들어오지 않는다"* 고 적는 그 규칙이다.
>
> 두 곳을 가르는 것은 바이트가 아니라 **레코드의 출처**다. `evilai-locust` 의
> 경로·지속성·AV 예외는 실검체에 감염된 VM 에서 수집기가 뜬 그대로이고,
> `New-InfectedSnapshot.ps1` 이 커밋 직전에 **본문만** 바꿔친다. 실검체
> 바이트로 룰이 발화하는지는 `cargo xtask yara`(G9)가 따로 잰다 — 16/16.

`ctime` 과 이미지가 소유한 파일들의 시각은 다시 뜰 때 달라진다. 우리가 세우는
파일의 `mtime` 은 고정하지만 `ctime` 은 고정할 수 없다 — **기계의 사실이므로
감추지 않는다.**

### Windows 위협 스냅샷도 실기기에서 뜬다 (2026-09-04)

리눅스 둘에 이어 Windows 셋(`appinit-implant` · `service-userinit` ·
`search-hijack`)을 옮겼다. **다섯 위협의 감염 스냅샷이 전부 손으로 쓴 것**
이었고, 그런 자료는 다시 뜰 수 없고 실기기가 낼 수 없는 모양을 담을 수 있다.

```powershell
.\testbed\harness\host\New-ThreatSnapshot.ps1 -Threat service-userinit
```

| | 합성 | 실기기 |
|---|---|---|
| appinit-implant | 16건 | **574건** (방화벽 규칙 510) |
| service-userinit | 8건 | **6,392건** (서비스 713) |
| search-hijack | 16건 | **355건** (프로세스 164) |

#### 되돌린다 — 여기가 이 하네스의 위험한 자리다

게스트 스크립트가 `AppInit_DLLs` · `Userinit` · `BootExecute` · `Path` 를
만진다. **틀리면 기계가 로그온되지 않는다.** 그래서

- 바꾸기 전에 전부 `threat-backup-<위협>.json` 에 담고, 그 파일을 **덮어쓰지
  않는다** — 두 번째 생성이 감염 상태를 원본으로 담으면 되돌릴 곳이 없어진다
- 호스트 스크립트가 `finally` 에서 반드시 정리를 부른다
- 정리한 뒤 값이 실제로 돌아왔는지 **되읽어 확인**하고, 남아 있으면
  스냅샷으로 되돌리라고 말한다

재부팅하지 않는다. 값을 세우고 수집한 뒤 곧바로 되돌리므로 창이 초 단위다.

#### 실기기가 합성과 다른 자리 넷

| | 합성이 적던 것 | 수집기가 내는 것 |
|---|---|---|
| `service.state` | `running` · `stopped` | **`unknown`** — 실행 여부는 레지스트리에 없다 |
| `service.start_type` | `demand` | **`manual`** — `Start=3` 의 이름 |
| `service.name` | `Host Cache Service` | **`SvcHostCache`** (고쳤다, 아래) |
| `file.signature` | 없음 | `{"trusted": false}` 가 실행 파일마다 붙는다 |

앞의 셋이 `service-userinit` 하나에 몰려 있었고, THREAT.md 가 *"상태 실행 중"*
과 *"표시 이름 Host Cache Service"* 를 적고 있었다 — **둘 다 스냅샷에 없는
값**이었다. 출제자 주의 2번이 금지하는 바로 그 갈라짐이다.

`service.name` 은 제품을 고쳤다. `id` 의 복사본이라 아무 정보도 나르지 않았고,
사람이 보는 이름이 버려졌다. 이제 `DisplayName` 을 담되 OS 서비스의 간접
문자열(`@%SystemRoot%\...,-101`)은 담지 않는다 — 읽을 수 없는 값이므로 그때는
키 이름을 쓴다. 실기기 713개 중 **82개**가 진짜 이름을 갖게 됐다.

`service.state` 는 제품이 옳다. THREAT.md 쪽에 *"관측 도구는 돌고 있는지를
담지 못한다"* 를 적어 보고서와 자료를 맞췄다.

#### 넓은 경로 + `structured_config` = 종료 코드 6

`appinit-implant` 을 `C:\ProgramData` 로 뜨자 **잘림**이 났다. 범인은 Windows
자신의 원격 분석 설정이다 — `utc.privacy.json` 4.0 MB · `utc.allow.json`
2.4 MB. JSON 하나가 잎 수만 개를 내고 `scope.max_files`(5만)를 삼킨다.

**잘린 스냅샷은 채점 데이터가 될 수 없다.** 그 상태의 "위협 없음" 은 "못 봤다"
이기 때문이다. 그 위협만 벤더 폴더까지 좁혔고, 폭 경고가 이제 무엇을 잃는지
말한다(`lint.rs`).

#### 크기

`service-userinit` 이 1.9 MB 로 가장 크다 — `C:\ProgramData` 의 파일 5,642개가
대부분이다. 다시 떠도 바뀌는 것은 우리가 만든 파일 셋의 `ctime` 뿐이므로
churn 은 작다. 남겨 두는 이유는 THREAT.md 가 *"`C:\ProgramData` 는 정상 벤더도
쓰는 자리다"* 를 오탐 위험으로 적고 있어서다 — 그 문장이 이제 자료에 있다.

## CI 에서 무엇이 돌고 무엇이 못 도는가 (2026-09-05)

하네스를 `.gitlab-ci.yml` 에 걸었다. **셋 다 성격이 다르다.**

| 잡 | 무엇을 재는가 | 어디서 도는가 |
|---|---|---|
| `snapshots` | 커밋된 스냅샷이 지금 수집기가 낼 수 있는 모양인가 | 아무 러너 |
| `testbed:linux` | 수집·판정·계획·치료·격리·복원이 진짜 `/etc` 위에서 도는가 + 위협 스냅샷이 낡지 않았는가 | linux 러너 (**컨테이너 실행기**) |
| `testbed:windows` | P4·P10 (읽기 전용) | **전용 러너** — 없으면 안 돈다 |

### `snapshots` — 오프라인에서 잡을 수 있는 것만 잡는다

`cargo xtask snapshots` 가 청정 코퍼스 16개와 감염 스냅샷 6개를 읽어 넷을 본다.

- 값 전수에 없는 낱말 (`defined: true` → 오류, `false` → 경고)
- 카탈로그에 없는 필드 이름
- 그 플랫폼에서 수집되지 않는 subject
- `truncated` · `denied_dirs`

**이것이 있었다면 손으로 쓴 값 셋이 커밋되던 날 걸렸다** — `service.state:
"running"` · `start_type: "demand"` 는 수집기가 낸 적 없는 낱말이다.

> **못 잡는 것도 분명히 해 둔다.** `tls-intercept` 의 `cert_store.store:
> "system"` 은 값 전수 **안에** 있어서 이 검사로는 잡히지 않았다. 자리가
> 틀렸을 뿐이다. 그런 것은 실기기에서 다시 뜨는 수밖에 없다.

### `testbed:linux` — 잡의 컨테이너가 곧 실험대다

하네스가 `/etc/hosts` 를 고치고 systemd 유닛을 지우고 프로세스를 죽인다.
개발 기계에서 못 돌리니 `invoke-linux-verify.sh` 는 컨테이너를 띄우지만,
**CI 잡은 이미 컨테이너 안에 있다.** 거기서 또 docker 를 부르려면 dind 가
필요하고 그러면 `-v $PWD:/repo` 가 잡의 파일이 아니라 dind 호스트를 가리켜
조용히 엉뚱한 것을 마운트한다. 그래서 `ci/linux-testbed.sh` 는 컨테이너를
띄우지 않고 지금 이 컨테이너를 쓴다 (`new-threat-snapshot.sh --local`).

> **셸 러너에 떨어지면 이 잡은 반드시 실패한다.** 러너 호스트의 `/etc/hosts`
> 를 고치게 되기 때문이다. `new-fixtures.sh` 의 컨테이너 검사가 거기서 멈추고,
> 스크립트는 그 거절을 통과로 바꾸지 않는다.

두 번째로 재는 것이 **위협 스냅샷의 낡음**이다. 커밋된 것을 다시 떠서
`ctime` 만 빼고 비교한다 — 다르면 수집기나 이미지가 바뀐 것이고 어느 쪽이든
사람이 봐야 한다. 실측으로 확인했다: 필드 하나를 지운 스냅샷을 넣자 그 자리를
짚고 다시 뜨는 명령까지 알렸다.

### `testbed:windows` — 전용 러너가 필요하다

일반 러너에서 돌 수 없다. VMware 와 `Win10x64-Test` VM, 고정 주소, 호스트
WinRM 클라이언트가 있어야 한다. `$RUN_TESTBED_WINDOWS` 로 켠다 — `fuzz` 와
같은 이유로, 러너가 없는 동안 파이프라인마다 대기 상태로 남으면 안 된다.

**자격 증명이 그대로는 안 된다.** 개발자가 손으로 돌 때는 DPAPI 로 저장된
것을 쓰는데(`Get-LabCredential`) 그것은 사용자 프로필에 묶여 있어 러너 서비스
계정이 풀지 못한다. 그래서 CI 잡은 `LAB_VM_*` 마스킹 변수로 자격 증명을 만들어
`-Credential` 로 넘긴다.

**읽기 전용 둘만 돌린다.** P6·P8·P9·P10F 는 파괴적이라 스냅샷 복원이 필요하고,
그것은 러너가 VM 을 독점할 때만 안전하다 — 손으로 돌린다.

### 위협 스냅샷 재수집은 CI 가 하지 않는다

커밋을 만드는 일이라 잡으로 두지 않는다. 낡았다는 것만 알리고, 다시 뜨는 것은
사람이 한다 — Windows 쪽은 VM 이 필요해 어차피 자동화되지 않는다.

## 리눅스 청정 코퍼스를 다섯 배포판으로 (2026-09-05)

리눅스 스냅샷 8장이 **배포판 둘**에서만 왔다 — WSL Ubuntu 24.04 와 Docker
Debian 12. G1(오탐 게이트)의 실질 사거리가 거기까지였다는 뜻이다.

| | 전 | 후 |
|---|---|---|
| 스냅샷 | 8장 | **17장** |
| 배포판 | 2 | **5** |

더한 셋: **Fedora 41**(rpm 계열) · **Alpine 3.21**(musl · busybox · OpenRC) ·
**Ubuntu 22.04**.

### 기본 이미지는 실제 기계가 아니다

그냥 띄우면 얇다. 실측:

```
fedora:41   /etc 332 파일 · /usr 366 · systemd 없음 · cron 없음 · CA 0개
alpine:3.21 /etc  45 파일 · /usr  17 + 심볼릭 137
WSL Ubuntu 24.04              /usr 19,634 파일
```

그래서 **대표 패키지를 깔아 실제 기계 모양으로 만든 뒤** 뜬다 — 시작 관리자·
예약 실행·신뢰 저장소 셋이 있어야 `persistence`·`service`·`cert_store` 룰이
태울 레코드가 생긴다. 무엇을 깔았는지는 `invoke-corpus-snapshot.sh` 의
`install_cmd` 에 있다.

### 씻는 것은 호스트가 한다

`cargo xtask corpus` 가 스크러빙을 하는데 fedora·alpine 에는 cargo 가 없다.
`new-corpus-snapshot.sh --raw-out <디렉터리>` 를 더해 **수집과 스크러빙을
갈랐다** — 컨테이너는 모으기만 하고 호스트가 씻는다.

### alpine 은 musl 이라 바이너리가 다르다

glibc 로 만든 것은 alpine 에서 실행되지 않는다(`sh: /r: not found`).
`x86_64-unknown-linux-musl` 로 만들어야 하고, 그것이 이 코어의 리눅스 **배포
타깃**이기도 하다(`rust-toolchain.toml`). 이번에 만들어 `static-pie linked`
로 나오는 것을 확인했다 — 선언된 배포 구성이 아직 성립한다.

### 늘리자 결함이 하나 나왔다 — rpm 계열의 신뢰 저장소

Fedora 스냅샷의 `cert_store` 가 **0건**이었다. alpine 은 145건인데.

`CERT_DIRS` 가 보던 두 자리는 **Debian 계열의 것**이고 rpm 계열에는 그
디렉터리가 아예 없다:

```
/usr/local/share/ca-certificates          없음
/usr/share/ca-certificates                없음
/etc/pki/ca-trust/source/anchors          있음  ← 손으로 더하는 자리
/usr/share/pki/ca-trust-source/anchors    있음
```

**신뢰 저장소에 심어진 루트 CA 를 겨누는 룰이 Fedora·RHEL·Rocky·openSUSE
전체에서 조용히 0건이었다.** `update-ca-trust` 는 `SYSTEM_TOOLS` 에 이미
있었다 — 지울 줄은 아는데 볼 줄을 몰랐다.

두 자리를 더했고 실기기에서 확인했다: Fedora 컨테이너에 CA 를 심자
`store: "local"` 로 잡힌다(고치기 전에는 0건). 시험이 두 계열을 다 요구한다.

> **번들은 여전히 읽지 않는다.** rpm 계열의 배포판 루트는 개별 파일이 아니라
> `ca-bundle.trust.p11-kit` 한 덩이(2.4 MB)에 있다. `/etc/ssl/certs` 를 보지
> 않는 것과 같은 이유다. 그래서 rpm 기계에서는 **배포판 루트가 관측되지
> 않는다** — 겨누는 것(심어진 CA)은 anchors 로 오므로 목적은 달성되지만,
> "이 기계의 신뢰 루트 전부" 를 묻는 데는 쓸 수 없다.

### 쓰는 법

```bash
testbed/harness/linux/invoke-corpus-snapshot.sh --all --raw-out /tmp/corpus-raw
# 그 뒤 호스트에서 파일마다:
cargo xtask corpus --in <파일> --label <라벨> --out corpus/clean
cargo xtask snapshots
cargo test -p remedy-core --test corpus
```

## 화면 기준선 — 화면을 바꾸는 회차의 안전망

`docs/design/콘솔은-이렇게-보인다.md` 의 화면은 아래 두 캡처가 만든다. 화면을
고치는 회차는 그것을 다시 받아 **의도한 줄 외에 달라진 줄이 0** 인지 본다

| | |
|---|---|
| Windows | `host\Capture-Console.ps1 [-Build] [-Lang ko\|en]` — 랩 VM 에서 감염 → 검사 → 치료 → 재평가 → 복원 → **치료 심장박동** → 신고 꾸러미 → 오류 → selftest → 회차 로그 |
| Linux | `linux/capture-console.sh` — 컨테이너에서 같은 순서 + **일부러 일으킨** 종료 코드 3·5·6·7 |
| 견주기 | `cargo xtask console-diff <이번 캡처>...` — **기준선은 캡처 이름에서 고른다.** 실행 번호·시각·경과·바이트·pid·호스트명·키 지문을 자리표시자로 바꾸고 심장박동 줄을 뺀 뒤 `git diff --no-index` |
| 문서 대조 | `cargo xtask console-doc` — `docs/design/콘솔은-이렇게-보인다.md` 가 인용한 화면이 기준선에 실제로 있는지, 그리고 **커밋된 `.norm.txt` 가 원본과 맞는지**. **`all` 에 들어 있다** |

기준선은 `baseline/console/` 에 있고 이름이 고정이다. **그래서 인자로 주지 않는다** —
캡처 이름이 `…-win.txt` 인지 `…-linux.txt` 인지로 짝이 정해진다.

```
cargo xtask console-diff <이번 win 캡처> <이번 linux 캡처>
```

**한 명령으로 둘을 다 본다.** 앞의 것이 달라도 뒤의 것을 마저 견주고, 끝에서 어느
쪽이 달랐는지 이름을 댄다 — 첫 차이에서 멈추면 두 번 돌려야 하고 그 사이에 사람이
한쪽만 보고 넘어간다. 기준선을 캡처 자리에 주면 **크게 실패한다**: 예전 형식
(`<기준선> <이번>`)을 그대로 치면 기준선을 자기 자신과 견줘 `diff 0` 이 나오는데,
그것은 아무것도 재지 않고 초록을 내는 가장 나쁜 결과다.

같으면 종료 코드 0, 다르면 1 과 함께 달라진 줄을 낸다. `.norm.txt` 도 함께 커밋한다 —
정규화 규칙을 고치면 그 파일이 곧바로 갈라져 보이기 때문이다(`console-diff` 가 원본에서
다시 만들어 덮어쓴다).

화면을 바꾼 회차가 끝나면 새 캡처를 기준선으로 올린다. diff 가 의도한 줄만인지
확인한 **뒤에**. 그리고 **`cargo xtask console-doc` 을 부른다** —
`docs/design/콘솔은-이렇게-보인다.md` 는 화면을 통째로 인용하므로 기준선을 올리면
같이 낡는다. 그 문서는 첫 줄에서 *"지어낸 화면이 하나도 없다"* 고 말하는데,
2026-09-09 에 재어 보니 화면을 바꾼 회차 다섯을 지나는 동안 조용히 낡아 있었다.

**2026-09-11 부터 `cargo xtask all` 과 CI 의 `console-doc` 잡이 그것을 대신
기억한다.** 커밋된 파일 둘을
읽어 대조할 뿐이라 아무 데서나 돌기 때문이다 — 캡처와 `console-diff` 는 여전히
밖이다(실기기가 있어야 한다). 손으로 부르는 것은 캡처 직후에 빨리 보기 위해서다.

첫 기준선은 2026-09-08 에 받았다. Windows 443줄(21절) · Linux 457줄(27절)이고,
둘을 합쳐 종료 코드 **0·1·2·4·5·6·7** 이 들어 있었다. **3(부분 실패)만 비어 있었다** —
읽기 전용 마운트가 필요한데 컨테이너에 `CAP_SYS_ADMIN` 이 없었다.

**2026-09-09 에 `--cap-add SYS_ADMIN` 을 리눅스 캡처의 표준으로 삼아 채웠다.** 그

지금 기준선은 **2026-09-30** 것이다 — Windows 883줄(31절) · Linux 1095줄(42절). 화면 마감
회차(고객 경로 전부 합쇼체 · 조사 · 미룬 항목 절 · `--ascii` 의 줄표 · `--x 옵션이 필요합니다`)로

그날 절을 셋 더했다: 리눅스 `R`·Windows `M`(조직 복구 키 — `apply

**Windows 의 `D5. 치료 심장박동 — 도구가 도는 중` 절은 2026-09-11 에 늦게
더했다.** 두 기준선 중 어디에도 `치료 중 · 도구 <이름> N초 · 경과 M초` 가

**랩 이미지를 `remedy-lab-base-v3` 로 바꾼 뒤 Windows 캡처를 다시 받아 견줬다 —
`diff 0`.** 기준선은 그 앞 이미지에서 받은 것인데도 한 줄도 달라지지 않았고,
정규화본까지 바이트가 같았다. 자동 갱신을 끈 것이 **화면에는 보이지 않는다**는
뜻이다 — 0절이 보안 제품 예외를 고정해 기계 차이를 막고 있기 때문이다. 그래서
기준선 파일은 그때 그대로 뒀다: 바꿀 내용이 없는데 600줄을 흔들 이유가 없다.
(같은 날 늦게 `D5` 절을 더하면서 결국 다시 받았다 — 그때는 **바꿀 내용이
생겼기** 때문이다. 견줘 보니 새 절 54줄만 늘고 바뀐 줄·지워진 줄은 0 이었다.)

**리눅스도 같은 날 다시 받아 견줬다 — `diff 0`** (40절 · 종료 코드 여덟 개 ·
113초). 컨테이너라 랩 이미지와는 무관하지만, 이로써 **두 기준선이 같은 코드에서
확인된 상태**가 된다. 줄 수는 회차마다 한둘 흔들릴 수 있다 — 심장박동 줄이
나오는지가 시간에 달렸고 정규화가 그것을 뺀다. 먼저 견주는 값은 **절 수와 종료
코드 분포**다.
절 수와 종료 코드 분포는 새 캡처를 올릴 때 먼저 견주는 값이다. 절이 줄었으면
캡처가 중간에 끊긴 것이고, 종료 코드가 빠졌으면 그 갈래를 못 밟은 것이다 —
둘 다 diff 를 보기 전에 걸러야 한다.

```bash
grep -c '^##########' <새 캡처>          # Windows 31 / Linux 46
grep -o '\[exit=[0-9]\]' <새 캡처> | sort -u   # Windows 는 0·1·2·4·5, Linux 는 0~7 여덟 개
```

**2026-09-11 부터 캡처가 끝에서 스스로 센다.** 두 스크립트가 마지막에 한 줄로
판정한다 — Windows 는 콘솔에, Linux 는 stderr 에. **산출 파일에는 넣지 않는다**:
계측기가 자기를 재는 줄이지 제품 화면이 아니고, 파일에 넣으면 기준선이 그것까지
담아 *"diff 를 보기 전에"* 라는 말이 뜻을 잃는다. 위의 grep 은 **남에게서 받은
캡처**처럼 그 줄이 없는 파일을 볼 때 쓴다.

기대값은 스크립트 안에 있다 — `$ExpectSections`·`$ExpectCodes`(Windows) ·
`EXPECT_SECTIONS`·`EXPECT_CODES`(Linux). **절을 일부러 더한 회차는 그것도 함께
고친다.** 안 고치면 다음 회차가 붉게 뜨는데, 그때 붉은 것은 캡처가 아니라 기대값이다.

**stdin 은 재지정하고 닫는다.** `run` 은 `--yes` 없이 승인을 기다리는데, 재지정하지
않으면 그 앞에서 영원히 선다 (2026-09-07 에 5시간 26분). 그래서 이 캡처는 "승인할
사람이 없습니다" 갈래를 재고, 사람이 있는 갈래는 `Approve-Interactive.ps1` 이 잰다.

**심장박동 줄은 정규화가 뺀다.** 같은 기계에서 검사가 4초일 때와 84초일 때가 있어
(온액세스 백신이 읽기를 45배 늘린다) 줄이 나오는지 자체가 시간에 달렸다. 숫자를 전부
지우지는 않는다 — `흔적 6건`·`7 건을 수행합니다`·`[exit=2]` 는 뜻이라 바뀌면 diff 에
나와야 한다.

된다. 2026-09-10 에 16블록 134줄을 그렇게 확인했다).

### diff 0 은 "안 깨졌다" 이지 "됐다" 가 아니다

캡처가 **볼 수 없는 것**은 diff 에도 나오지 않는다. 2026-09-08 Phase 2 에서 밟았다 —
심장박동 형태와 사용법 스트림을 바꿨는데 리눅스 diff 가 0 이었다. 정규화가 심장박동을
빼고(게다가 그 회차는 검사가 빨라 한 줄도 안 나왔다), 사용법은 `2>&1` 로 합쳐 받아
스트림 구분이 사라졌기 때문이다.

**바꾼 것이 캡처에 보이는지 먼저 확인한다.** 안 보이면 보이게 만들 절을 더한다.
그래서 아래 둘이 있다.

| 절 | 무엇을 보이게 하나 |
|---|---|
| `A0. 인자 없이 부르면 창을 붙잡는가` | 터미널일 때만 일어나는 갈래 — Windows 는 진짜 콘솔, Linux 는 `script` 로 pty |
| `A4. 사용법이 어느 스트림으로 나가는가` | 두 스트림을 따로 세어 줄 수로 적는다 — 합쳐 받으면 사라지는 사실 |
| `A5. 심장박동의 형태` | 일부러 느린 검사(루트 셋, 하나는 없는 자리)를 만들어 그 줄을 남긴다 |
| `D5. 치료 심장박동 — 도구가 도는 중` (Windows) | 박동을 1초 주기로 두고 **같은 계획을 한 번 더** 수행한다. 치료가 3초인데 그 안에서 `powershell.exe` 가 두 번(복원 지점 · 예외 목록 원복) 도므로 `도구` 칸이 반드시 걸린다 — 도구가 박동 간격보다 오래 돌면 빠질 수 없다 |
| `A6. 안내 모드` | 꾸러미 모양을 만들어 **그 안에서** 인자 없이 띄운다 — 빌드 산출물 폴더에서는 안내 모드가 열리지 않는다 |
| `Q. 알려진 지표 목록` (Linux) | `c2-beacon` 을 세워 해시·도메인 목록으로 잡고 치료한다. 화면에는 `흔적 4건` 뿐이라 **`scan.json` 의 evidence 를 파일에서 그대로 찍는다** — 어느 목록의 어느 값에 맞았는지는 거기에만 있다 |

`A6` 에서 거절이 나오는 것이 **정답이다.** 캡처가 쓰는 빌드에는 신뢰 앵커가 박혀
있지 않으므로 어떤 꾸러미도 검증할 수 없다. 재는 것은 *"거절이 어떤 모양인가"* 이고,
서명이 실제로 통과하는 경로는 앵커를 박아 빌드해야 하며 `plugin verify` 와
`cargo xtask package` 가 그것을 잰다.

### 자를 때는 개수가 아니라 내용으로

고정 개수(`tail -N` · `Select-Object -First N`)로 자르면 **화면에 줄이 더해질 때마다
창 밖으로 한 줄이 밀려나고, 그것이 diff 에는 삭제로 보인다.** 진짜 삭제를 그 뒤에
숨길 수 있다.

2026-09-08 에 **세 번** 밟았다 — Phase 1 에서 창을 넓혔더니(14→22) Phase 3 에서 계획이
열 줄 늘어 다시 넘겼고, 넓혀 둔 다른 자리도 함께 넘겼다. **넓히는 것은 미봉책이다** —
화면은 계속 자란다. 그래서 규칙을 바꿨다.

**2026-09-09 에 네 번째로 밟았다 — 규칙을 쓴 그 Phase 가 규칙을 어기고 있었다.**
`A6` 의 두 번째 갈래(`꾸러미가 아예 없는 자리`)가 `tail -4`·`Select-Object -Last 4`
로 사용법 화면을 자르고 있었다. §1.4 로 사용법이 여덟 줄 줄자 창이 밀렸고, 지워진
것처럼 보인 두 줄(`6 …`·`7 …`)은 실은 창 밖으로 나간 것이었다. 규칙을 새로 만들 때
**이미 있는 자리를 전수로 훑지 않으면** 규칙과 코드가 같은 커밋에서 갈라진다.

리눅스 쪽에는 하나가 더 있었다. `remedy … | tail -4` 뒤의 `[exit=$?]` 는 `remedy` 가
아니라 **`tail` 의 종료 코드**다. 이 절이 증명하려던 "지금까지의 동작 그대로"(종료
코드가 그대로인가)를 **한 번도 재고 있지 않았다.** 파이프를 붙이면 `$?` 의 주인이
바뀐다 — 제품 화면 뒤에는 파이프를 두지 않는다.

전수 확인은 이렇게 한다.

```bash
grep -nE "remedy.*\|.*(tail|head)|\|\s*(tail|head)\s+-[0-9]" testbed/harness/linux/*.sh
grep -nE "Select-Object -(First|Last)" testbed/harness/host/*.ps1
```

걸린 것이 **제품 화면이면 고치고**, 픽스처 요약·크래시 기록·심장박동 표본이면 둔다.

| 무엇 | 어떻게 |
|---|---|
| 제품 화면 | **자르지 않는다.** 명령 하나의 출력을 통째로 담는다 |
| 회차 로그 발췌 | 내용으로 자른다 — `치료를 시작합니다` 줄까지(안전 상한 80줄) |
| 픽스처 요약·크래시 기록 | 제품 화면이 아니라 그대로 둔다 |

그래도 diff 에 `-` 가 나오면 **먼저 창이 밀렸는지 의심하고**, 지워진 줄이 원본
캡처에 남아 있는지 확인한다. 남아 있으면 계측기 문제이고, 없으면 진짜 삭제다.

리눅스 캡처는 WSL 에서:

```bash
docker run --rm --cap-add SYS_ADMIN \
  -v <저장소의 WSL 경로>:/repo \
  -v <Windows 쪽 .cargo 의 WSL 경로>/registry:/usr/local/cargo/registry \
  -v remedy-bookworm-target:/tmp/remedy-bookworm \
  -e CARGO_TARGET_DIR=/tmp/remedy-bookworm \
  rust:1.96-bookworm bash /repo/testbed/harness/linux/capture-console.sh \
  > testbed/harness/results/console-$(date +%Y%m%d-%H%M%S)-linux.txt
```

**`remedy-bookworm-target` 이 빌드 시간의 전부다.** 그 줄이 없으면 `/tmp` 는
컨테이너와 함께 사라지고 회차마다 릴리스·개발 두 벌을 **처음부터** 짓는다.
실측(2026-09-11):

| | 빌드 | 캡처 전체 |
|---|---|---|
| 볼륨 없이 (매번 차가움) | **292초** | 약 6분 |
| 볼륨을 두고 두 번째부터 | **30초** | **104초** |

##### `CAPTURE_LANG=en` — 영어 화면을 한 벌 (2026-09-16)

`-e CAPTURE_LANG=en` 을 더하면 같은 캡처를 **영어로** 받는다. 영어로 돌렸는데
한글이 남는 줄이 곧 **이중 언어가 빠진 자리**다.

**기본은 `ko`** 라 이 값을 주지 않으면 지금까지와 한 글자도 다르지 않다 —
넣은 날 기본값으로 한 벌 받아 `console-diff` **diff 0** 을 확인했다.

언어가 일부러 박힌 절 넷은 따라오지 않는다 — `A2`(사용법 한국어) · `A7` 의
한국어 갈래 · `E1`(verify 한국어) · `H1` 의 한국어 갈래. 그 넷은 저마다 짝이
되는 영어 절이 있고, **둘을 나란히 보이는 것이 그 절의 목적**이다.

읽는 법은 내부 기록에 있다 — 한글 줄을
세 갈래(캡처 스크립트 출력 · 의도적 한국어 절 · 제품이 낸 한글)로 가르지 않으면
숫자가 아무것도 말해 주지 않는다.

##### 영어에도 기준선이 있다 (2026-09-16)

`baseline/console/console-{win,linux}-en.txt` 다. **기준선은 넷이 됐다.**
`console-diff` 는 캡처 이름을 `-` 로 쪼갠 토막에 `en` 이 있으면 영어 기준선을
고른다 — `console-en-win.txt` 는 걸리고 `console-20260916-155601-win.txt` 는
걸리지 않는다.

**한국어 기준선만으로는 이 회귀를 잡을 수 없다.** 한국어가 한국어로 나오는
것은 언제나 옳기 때문이다. 09-07 에 *"영어 화면의 한글 줄 0"* 을 실측으로
선언하고도 7일 뒤 종료 코드 6 의 사유가 한국어로 나온 일이 그 증거다.

막는지 확인했다(09-16) — 영어 캡처의 한 줄을 고치기 전 한국어로 되돌려
견주자 `console-diff` 가 `exit 1` 로 그 줄을 짚었고, 영어 기준선의
`.norm.txt` 를 지우자 `console-doc` 이 `exit 1` 로 잡았다.

볼륨은 처음 쓸 때 도커가 알아서 만든다 — `docker volume create` 를 따로 칠
필요가 없다.

**저장소 안(`target/…`)에 두지 않는 이유**는 그쪽이 Windows bind mount 라서다.
빌드 산출물을 그 경계 너머로 쓰면 느려져 **다시 짓는 것보다 나쁠 수 있다.**
이름 있는 볼륨은 도커 VM 자신의 파일 시스템에 산다.

툴체인을 올리거나 산출물이 의심스러우면 `docker volume rm remedy-bookworm-target`
으로 버린다. 그다음 회차가 292초짜리 한 번을 다시 낸다.

**형제 하네스들과 다른 점 하나.** `invoke-linux-verify.sh` 계열은 WSL 의
`/tmp/remedy-bookworm` 을 bind mount 해서 **산출물을 호스트에 남긴다** — 그래야
그 스크립트들이 `--bin /tmp/remedy-bookworm/release/remedy` 로 집을 수 있다.
캡처는 컨테이너 안에서만 돌아 그 가시성이 필요 없으므로 볼륨을 쓴다. 대신
**캡처가 지은 바이너리는 WSL 에서 보이지 않는다** — 그쪽이 필요하면 그 하네스의
조리법을 쓸 것.

**WSL 안에서만 그대로 통한다.** PowerShell 이나 Git Bash 에서 부르면 WSL 경로
가 마운트되지 않아 `No such file or directory` 로 죽는다(2026-09-10 실측). 거기서는
호스트 경로로 바꾸고 리다이렉트를 컨테이너 안에 둔다 — 그래야 산출 파일에 BOM 이
붙지 않는다.

```powershell
docker run --rm --cap-add SYS_ADMIN `
  -v "<저장소의 WSL 경로>:/repo" `
  -v "<Windows 쪽 .cargo 의 WSL 경로>\registry:/usr/local/cargo/registry" `
  -v "remedy-bookworm-target:/tmp/remedy-bookworm" `
  -e CARGO_TARGET_DIR=/tmp/remedy-bookworm `
  rust:1.96-bookworm bash -c "bash /repo/testbed/harness/linux/capture-console.sh > /repo/testbed/harness/results/console-<시각>-linux.txt"
```
