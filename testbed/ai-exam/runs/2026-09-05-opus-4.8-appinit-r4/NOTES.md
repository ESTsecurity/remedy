## 이 회차가 재려던 것 — **문서만으로 새 기능이 쓰이는가**

사전 기준 ①에 적었다. 응시자는 웹 대화라 `plugin lint` 를 돌릴 수 없다.
r3 이 그 경고를 받은 것은 채점하며 내가 돌렸기 때문이고 **응시자는 본 적이
없다.** 그래서 통로가 셋뿐이었다.

| 통로 | 읽혔나 |
|---|---|
| `10-manifest.md` §`subject_roots` | **✅ 썼다** |
| `30-antipatterns.md` §12 | **✅ 되돌려 적었다** |
| `32-lint-errors.md` (진단 둘) | 오류를 내지 않아 알 수 없다 |

답안 43~44줄.

```yaml
# structured_config 를 %PROGRAMDATA% 전체에 펴면 JSON 잎이 상한(50,000)에
# 걸려 관측 불완전(종료 코드 6)이 된다. 대상 에이전트 폴더로만 좁힌다.
# (좁히는 것은 수집 비용을 줄일 뿐 삭제 상한은 여전히 scan_roots 다.)
subject_roots:
  structured_config: ["%PROGRAMDATA%\\Acme\\Agent"]
```

셋째 줄이 **전날 넣은 안티패턴 §12** 다. 쓰는 법과 **오해하지 말아야 할 것**을
함께 읽었다.

## 산출물 — **문서가 실기기 결과를 바꾼 것을 처음 봤다**

사전 기준 ③이 *"넓은 상한은 채점에 걸리지 않는다. 실기기 종료 코드는 내가
따로 돌려야 안다"* 고 적었다. 돌렸다.

**같은 기계(`Win10x64-Test`, 청정) · 같은 위협 · 같은 모델(4.8) · 하루 차이.**

| | 종료 코드 | `truncated` | `structured_config` |
|---|---|---|---|
| r3 답안 | **6** (관측 불완전) | true | 50,000 (상한) |
| r4 답안 | **0** | false | 0 |

열아홉 회차 동안 *"우리가 고친 것이 다음 응시자에게 닿는다"* 를 **답안의
문장**으로 봐 왔다(`tls-r2` · `appinit-r3`). 이번엔 **실기기 결과가 갈렸다.**

그리고 모델이 같다는 것이 이 비교를 깨끗하게 만든다 — 아래 §모델을 보라.

## 사전 기준 ②를 전부 통과했다

| 물은 것 | 결과 |
|---|---|
| 키가 아니라 **값**을 지우는가 | ✅ 둘 다. 주석이 *"같은 키의 다른 17개 값은 그대로"* — 고친 수를 읽었다 |
| 경로와 **스위치를 둘 다** | ✅ (r3 때는 채점이 못 잡던 자리, 지금은 잡는다) |
| `direction equals "In"` (대문자) | ✅ |
| `structured_config` 를 `key_path` 로 | ✅ |
| 방화벽을 방향만으로 판정하지 않는가 | ✅ `direction ∧ action ∧ application` |
| 설정 파일을 통째로 지우지 않는가 | ✅ 항목 하나만 |
| **무엇을 좁혔는가** | ✅ `structured_config` **만**. `file` 을 좁히면 페이로드를 못 찾는다 |
| **삭제까지 좁힌다고 믿는가** | ✅ 아니오 — 정확히 반대로 적었다 |

## 정답과 갈린 자리 — `loadflag` 를 파생으로 두었다

| | `loadflag` |
|---|---|
| 우리 정답 | **뿌리** 규칙. 키를 리터럴로 적는다 |
| 이 답안 | **파생**. `key equals "${appinit.key_norm}"` 로 *같은 키임*을 확인한다 |

`key_norm: "key | lower"` 로 뽑아 대조한다. 주입 값과 스위치가 **같은 키에
있음**을 규칙으로 강제하는 셈이고, 그쪽이 더 조인 설계다.

**대가가 있다.** 파생 규칙은 청정 코퍼스가 시험하지 못한다(부모가 서지 않으면
평가가 시작되지 않는다). 그래서 이 답안이 마주한 레코드가 **374 → 187** 로
반이다. 오탐 안전이 나빠진 것은 아니다 — 뿌리 `appinit` 이 187건을 보고 0건을
맞힌다 — 다만 **재는 양이 줄었다.**

`40-review-checklist.md` 7번이 *"오탐 안전은 사실상 뿌리 규칙 하나가
떠받친다"* 고 적은 그 자리다. 이 답안은 뿌리가 정확히 하나다.

## 모델 — 두 회차 연속 Opus 5 가 막혔다

꾸러미를 Opus 5 에 넣자 또 분류기에 막혔다. r3 과 같다.

**내가 넣은 방어 맥락은 듣지 않았다.** r3 채점 뒤 꾸러미 머리에 *"방어 목적
전용백신의 규칙 작성 · 산출물은 선언형 YAML · 페이로드는 무해한 자리
채우기"* 를 1 KB 적었는데, 이번에도 같은 자리에서 막혔다. **효과가 없었다고
적어 둔다** — 있었다고 착각하면 다음에 그 위에 더 쌓는다.

무엇이 걸리는지 볼 수 없어 고칠 방법이 없다. 안내 문구가 가리키는
**사이버 검증 프로그램**이 이 도구가 갈 길이다.

**곁가지로 이 막힘이 비교를 깨끗하게 만들었다.** r3 과 r4 가 둘 다 4.8 이라
*"문서가 닿았다"* 와 *"모델이 달랐다"* 가 섞이지 않는다. 사전 기준 ③이
걱정한 자리인데, 우연히 통제됐다.

## 못 재는 것

- ③에 적은 그대로다. **넓은 상한은 채점에 걸리지 않는다** — 실기기 종료 코드는
  따로 돌려야 안다. 이번에도 그렇게 했다.
- **`32-lint-errors.md` 가 읽혔는지 모른다.** 이 답안이 그 오류를 내지 않았다.
- **표본이 하나다.** 문서를 읽고 쓴 것인지, 같은 결론에 스스로 도달한 것인지
  가를 수 없다 — 다만 주석이 안티패턴의 문장을 거의 그대로 옮기므로 신호는
  강하다.
- 감염 기계에서 이 답안을 돌리지 않았다. 계획은 채점기가 감염 스냅샷으로
  확인했고(기대 6건 빠짐 0), 실기기 확인은 **청정 쪽 종료 코드**였다.

## 2026-09-05: 이 회차를 지금 다시 채점하면 **빠짐 2건**이다

`AppInit_DLLs` 와 `LoadAppInit_DLLs` 의 기대가 `registry.delete_value` 에서
`registry.restore_default` 로 바뀌었다. 둘은 청정 Windows 에 이미 있는 값이고
검체가 만든 것이 아니라 덮어쓴 것이다 — 채점 5(실기기 치료)가 그것을 냈다.

**이 답안이 틀렸던 것이 아니다.** 그날 코어의 기본값 카탈로그에 그 두 자리가
없었고, `to: default` 를 쓰면 린트가 거절했다. `remove` 가 그때 쓸 수 있는
전부였다. 위 채점표는 **그날의 기준**으로 읽을 것.
