## 이 회차가 재려던 것 (a) — **고침이 통했다**

r1 에서는 이 스냅샷에 `persistence` 레코드가 **0건**이라, 정기 작업을 그
subject 로 다룬 답안이 **판정 자체를 세우지 못했다.** `e24da93` 이 수집
매니페스트에 `persistence` 를 더하고 스냅샷을 다시 떴다(16건).

**이번 답안이 바로 그 길로 갔고, 판정이 섰다(1/1).** 고침이 실제로 통하는
것을 응시자 답안으로 확인했다.

```
  r1 (Opus 5)    persistence 규칙 → 매치 0건 → 판정 0 → 빠짐 6
  r2 (Opus 4.8)  persistence 규칙 → 매치      → 판정 1 → 빠짐 1
```

## 이 회차가 처음 보여준 것 — `persistence.delete` 는 줄만 뺀다

**실기기가 아니면 볼 수 없는 것이었다.** 치료 뒤 cron 파일이 남아 있다:

```
    /etc/cron.d/sync-agent
      기대: 없어야 한다
      실제: file 01ba4719c80b6fe911b091a7c05124b64eeece964e09c058ef8f9805daca546b
```

그 해시는 **개행 한 바이트**의 sha256 이다(`printf '\n' | sha256sum` 로
확인). 즉 **줄만 빠지고 빈 파일이 남았다** — `THREAT.md` 요구 사항 2 가
*"그 안의 줄만 빼면 빈 파일이 남는다"* 며 금한 바로 그 상태다.

### 서로 다른 모델 둘이 같은 오해를 했다

| 회차 | 모델 | 답안 주석 |
|---|---|---|
| r1 | Opus 5 | *"persistence 제거는 줄이 아니라 **항목 전체를 치운다**"* |
| r2 | Opus 4.8 | *"persistence 제거로 **유닛째 없앤다**. (…줄만 빼면 빈 파일이 남으므로 그 방식을 쓰지 않는다.)"* |

**둘 다 틀렸고, 둘 다 같은 방향으로 틀렸다.** 그리고 가이드가 그것을 적지
않는다:

```
  22-remediate-recipes.md   persistence 언급 0회
  machine/ops.json          persistence.delete 에 edits_in_place: false
```

**`edits_in_place: false` 가 오해를 부추길 수 있다** — *"제자리 편집이
아니다"* 를 *"통째로 지운다"* 로 읽기 쉽다. 실제로는 드롭인 파일 안의 항목
하나를 빼고 파일은 남긴다. 범위 밖이라 고치지 않고 적어 둔다.

## 사전 기준 ②를 대조한다

**②-1 어느 길로 갔는가** — 셋 중 어느 것도 아니고 **넷째다.**

```
  근거 1  persistence   source starts_with "/etc/cron.d/"
                        linux.cron.line contains "/.syncd" · "--spread"
  근거 2  file          path ends_with "/.syncd"   +   count(copy) >= 2
```

해시도 크기도 쓰지 않았다. 복제본은 **숨김 basename** 으로 모으고 *"여럿이
똑같다"* 를 `count()` 로 요구했다. 답안이 그 선택을 이렇게 적었다 —
*"정상 파일이 갖지 않는 숨김 basename `.syncd` 로 복제본을 모으고, 판정에서
count 로 「여럿」을 요구한다."*

**`count(<rule>) >= N` 은 문서 안의 문법이다** — `31-nonexistent.md` 59줄에
있고 꾸러미가 그것을 싣는다(2회). 응시자가 그 문법을 쓴 것은 이번이 처음이다.

**②-2 `persistence` 를 쓴다면 치료를 `file` 로 하는가** — ❌ 아니다. 그래서
빠짐 1건이다. **이 자리가 자동으로 갈렸다** — r1 때는 아예 재어지지 않았다.

**②-3 자리를 나열하지 않는가** — ✅ 나열하지 않았다. `detect` 에 리터럴 경로가
없고, 답안이 *"전체 경로를 리터럴로 적지 않으므로 여섯 번째 복제본도 상한
안에 있으면 함께 걸린다"* 고 적었다. **r1 과 같은 판단이다** (서로 다른 모델
둘이 같은 자리에서 유혹을 피했다).

## 정답과 다른 것

| | 정답 | 이 답안 |
|---|---|---|
| 복제본을 가르는 것 | 해시(`sha256 equals`) | **숨김 이름 + `count() >= 2`** |
| cron 을 다루는 것 | `file` 로 잡아 격리 | `persistence` 로 잡아 제거 |
| 판정식 | `clones and respawn` | `spreader and count(copy) >= 2` |

**이름으로 가른 것은 이 기계에서 맞지만 약하다.** 복제본 이름이 바뀐 변종에는
닿지 못한다 — 해시는 닿는다. 다만 응시자는 해시 값을 받지 못했고(출제자 주의
4 의 설계), 크기도 쓰지 않았으므로 **남은 길 중 하나를 고른 것**이다.

## 실기기 — 복제본은 전부 치웠다

```
  종료 코드 1 · 밟는 자리 6/6 · 남아야 하는 자리 6/6 · 치료가 만든 변화 0건
  수행 7건 — 복제본 다섯 격리 + cron 항목 비활성화·삭제
  범위 안 불일치 1건 — cron 파일이 빈 채로 남았다
```

**정상 파일 넷과 정상 정기 작업 둘은 하나도 건드리지 않았다.** 무너진 것은
cron 파일 하나뿐이고, 그것도 **빈 파일로 남았지 지워지지 않았다.**

## 이 회차가 남긴 것

1. **고침이 통한다는 것을 응시자 답안으로 확인했다.** r1 이 드러낸 자리를
   `e24da93` 이 열었고, r2 가 그 길로 걸어 판정을 세웠다.
2. **실기기가 아니면 못 볼 것을 하나 더 쟀다.** `persistence.delete` 가 cron
   드롭인에서 줄만 뺀다는 것은 계획만 봐서는 알 수 없다 — 개행 한 바이트가
   남은 파일이 그것을 보여 준다.
3. **가이드의 빈칸 하나가 두 회차로 확인됐다.** 서로 다른 모델 둘이 같은
   오해를 했다. 한 번은 우연이지만 둘은 신호다.
4. **사전 기준의 변형 표가 답안 점수를 미리 맞혔다.** 넷째 줄(빠짐 1 · 기대 밖
   2)이 그대로 나왔다 — 받고 나서 잣대를 만들지 않았다는 증거다.
